## Что есть сейчас (проверено по коду)

- **Эпик** — `TaskItem` с `Role = feature`, `FeatureId = null`, хранится в `data/tasks.json`.
  Поля «состояние фичи» нет.
- **Состояние** выводит `FeatureProjector.ComputeState` (`FeatureProjector.cs:1475`), девять
  значений по приоритету: `merged → closed → stopped → waiting → merging → merge_pending →
  running → not_started → idle`. `Bucket` (`:1514`) сводит их к четырём группам: `closed`,
  `attention`, `running`, `idle`. Это единая точка правды: строка индекса, порядок `OrderRuns`,
  плашка, рельса и шапка страницы читают `state`/`bucket`, а не считают сами.
- **«Закрыта» уже явная.** `closed` — это `epic.Status == Done` без мержа: решение человека
  «фича закончена». «Вернуть в работу» тоже уже есть: `TaskManager` разрешает перевод из
  `Done` в `Todo`/`InProgress` (`TaskManager.cs:760`), и проектор сам перестаёт видеть `closed`.
- **Паузы нет.** `stopped` — это остановленная задача исполнителя (`ExecutorStoppedAt`), то
  есть тревога «ждёт вас», а не решение «фича ждёт».
- **Членство «чат → фичи»** вычисляется, не хранится. Закрытие фичи членство не снимает. Но
  правило живёт в **четырёх** местах, и они расходятся (п. 2).

## 1. Явное состояние фичи

### Решение: одно новое хранимое поле, а не перечисление из четырёх значений

Из четырёх запрошенных состояний (draft/active/paused/closed) по-настоящему нового только
одно — **«работа не разрешена»**:

| Запрошено | Что это по данным | Новое хранение |
|---|---|---|
| closed | `epic.Status = Done` (уже есть) | нет |
| вернуть в работу | `Done → InProgress` у эпика (уже есть) | нет |
| active | отсутствие закрытия и паузы | нет |
| paused | новое: никакую работу фичи не вести, идущие ходы прервать | **да** |
| draft | новое: фичу готовят, исполнять шаги нельзя (см. «Черновик») | то же поле, своя причина |

Хранить `lifecycle: draft|active|paused|closed` отдельным полем рядом с `epic.Status` значит
завести **вторую точку правды о закрытии**: `Status = Done` при `lifecycle = active` или
наоборот. Её придётся синхронизировать в `tasks_complete`, `tasks_update`, на доске и в
переоткрытии. Поэтому закрытие остаётся на `Status`, а новое поле описывает только удержание.

**Контракт хранения (эпик, аддитивно):**

```
TaskItem (только role=feature)
  + Hold: FeatureHold?          // null — работа разрешена
FeatureHold
  { Reason: "draft" | "manual" | "queue",   // queue — задел под очередь, сейчас не ставится
    Since: DateTime,
    BySessionId: string?,  ByUser: bool }
```

`queue` в словаре сразу: очередь фич (идея волны 3, п. 2) — это та же пауза с другой причиной
и автоматическим снятием. Второе поле под очередь не понадобится.

### Черновик: своё значение `state`, но то же поле `Hold`

Андрей решил, что черновик — отдельный статус. По поведению он и правда отличается от паузы:

| | Черновик (`Reason = draft`) | Пауза (`Reason = manual`) |
|---|---|---|
| Когда | только **начальная** стадия: ни один исполнитель шага ещё не запускался | в любой момент жизни открытой фичи |
| Что разрешено | подготовка: задачи `cut`, `design`, `plan`, `consult` запускаются как обычно | ничего: гейт закрывает запуск любой задачи фичи |
| Идущие ходы | не трогает: шагов ещё нет, а подготовку человек сам и запускал | прерывает сразу (см. ниже) |
| Выход | «Запустить»: `draft → null`, фича становится активной | «Снять паузу»: `manual → null`, прерванные шаги продолжаются |
| Возврат | в черновик вернуться нельзя (409, если у фичи был хоть один запуск шага) | паузу можно ставить и снимать сколько угодно |

Хранить черновик отдельным полем (`IsDraft: bool` рядом с `Hold`) нельзя: черновик и пауза
взаимоисключающие, и два поля дали бы бессмысленную пару «черновик на паузе». Поэтому поле одно,
`Hold`, а различие задаёт `Reason`. Черновик — явная начальная стадия удержания со своим
гейтом и своим значением `state`, а не подпись на `paused`.

**Как черновик появляется.** Его ставит человек: при создании фичи из интерфейса или кнопкой
«В черновик» на странице, пока у фичи нет ни одного запуска шага. Эпики, которые оркестратор
заводит через `tasks_create(role=feature)`, рождаются активными, как сейчас: правило «удержание
ставит только человек» действует и тут (см. «Кто ставит и снимает»). Если Андрей захочет, чтобы
любая новая фича рождалась черновиком, это отдельное решение: оно меняет текущий конвейер Софьи,
у которой шаги сразу идут в работу.

**«Запустить»** — это `DELETE /api/tasks/features/{id}/hold` при `Reason = draft`. Сама кнопка
ничего не запускает: она снимает гейт, а шаги запускает оркестратор по плану, как сейчас. В
ключевой чат уходит карточка «фича запущена» **с ходом**: в отличие от снятия паузы, здесь
оркестратору действительно есть что делать (начать конвейер), и разбудить его — смысл кнопки.

### Производное состояние: значения `paused` и `draft`

```
merged → closed → paused → stopped → waiting → draft → merging → merge_pending → running → not_started → idle
```

- `paused` встаёт **после** `closed` (закрытая фича закрыта, даже если удержание не сняли) и
  **перед** `stopped`. Иначе пауза, прервавшая исполнителей, показала бы тревогу «ждёт вас»,
  хотя человек сам её поставил.
- `draft` встаёт **после** `stopped` и `waiting`. В черновике идёт подготовка, и если исполнитель
  разреза упал на 401 или ждёт ответа, тревога должна быть видна. Без тревог черновик показывает
  `draft`, даже когда разрез или план сейчас исполняются: человеку важнее «фича ещё не
  запущена», чем «агент работает».
- `Bucket(paused) = Bucket(draft) = "idle"`: фича не идёт и внимания не требует. Отдельная группа
  черновиков в списке — решение Майи, бэк его не диктует.
- Позже «в очереди» станет подписью на `paused` (`Reason = queue`), а не третьим значением:
  поведение очереди совпадает с паузой.
- `FeatureRun` + `Hold` (копия поля эпика), `FeatureIndexRow` + `HoldReason: string?`.

**Почему новые значения `state`, а не ортогональный флаг.** Флаг рядом с `state` оставил бы
потребителей нетронутыми. Но на паузе с прерванными исполнителями `state` показывал бы
`stopped` и красную тревогу, а в черновике с идущим разрезом — `running`. Итог — две правды на
одной плашке. Цена новых значений — пройти всех потребителей (см. «Риски»), и её стоит
заплатить.

### Кто ставит и снимает

Решение Андрея: **удержание ставит и снимает только человек, оркестратор только предлагает.**

- **Ручки:** `POST /api/tasks/features/{id}/hold` `{ reason: "draft" | "manual" }` и
  `DELETE /api/tasks/features/{id}/hold`. Под `[Authorize]`, с проверкой владельца эпика (как
  `GetFeature`) и `FeatureIdPattern`.
- **Только пользовательский токен.** Сервисный JWT хода (`typ = svc`) получает 403, как
  установка плагина (`PluginsController.IsServiceToken`). `[DenyOnDelegatedTurn]` здесь мало:
  он режет делегированный ход, а агент в собственном чате мог бы дёрнуть REST тем же сервисным
  токеном. Человек отличается от агента токеном, а не глубиной делегирования.
- **MCP-инструмента нет и не будет.** `Hold` не входит в схему `tasks_create`/`tasks_update`, а
  `TaskManager.Update` его не пишет, даже если поле придёт в теле. Состав `tools/list` не
  меняется.
- **Как оркестратор предлагает.** Существующими каналами, без нового механизма: текстом в
  ключевом чате или докладом `chats_report_up` вида «предлагаю поставить фичу на паузу:
  причина». Кнопку человек нажимает на странице фичи. Отдельную карточку «Поставить на паузу» с
  кнопкой в ленте не заводим: она стала бы вторым входом в ту же ручку, а выигрыш — один клик.
  Если Майя решит, что карточка нужна, она ведёт на ту же ручку и под тем же пользовательским
  токеном.
- **Промпт оркестратора.** В слот «Никогда» Софьи (и её локального двойника) добавить: «не
  ставь и не снимай паузу и черновик; если считаешь, что фичу надо остановить или запустить,
  предложи это человеку с причиной». Без этой строки оркестратор упрётся в 403 и начнёт искать
  обходы.
- **Отказы (409 с причиной):** удержание при `merged`, `closed`, `merging` (мерж идёт, его не
  тормозят посреди); `draft`, если у фичи уже был запуск шага; `manual` поверх `draft` (черновик
  и так закрывает шаги, а идущую подготовку человек останавливает обычным «Стоп»); снятие без
  удержания.
- **Закрытие снимает удержание** (`Done` у эпика → `Hold = null`, в одной функции
  `TaskManager`). Иначе после «вернуть в работу» фича молча оказалась бы на паузе.
- **Переоткрытие смерженной фичи ничего не меняет:** правило 1 `ComputeState` держит `merged`
  при принятом финале. Это правильно: доработка смерженного — новая фича. На странице кнопку
  «вернуть в работу» у `merged` не показываем. На бэке не запрещаем: переоткрыть эпик через
  трекер можно и сейчас.

### Что пауза делает: один гейт на сервере

Пауза имеет смысл, только если её соблюдает сервер. Гейт один:
`FeatureHoldGate.Allows(task, owner)`. Для задачи без фичи он всегда пропускает. Для задачи фичи
смотрит `Hold` её эпика: `manual` закрывает всё, `draft` пропускает только роли подготовки
(`cut`, `design`, `plan`, `consult`). Держат гейт три точки:

1. **Запуск исполнителя** (`TaskExecutionService`, точка `tasks_run_executor` и кнопки
   «Запустить»): задача, которую гейт не пропускает, → отказ с текстом «фича на паузе, снимите
   паузу на странице фичи» (или «фича — черновик, запустите её на странице фичи»). Висячий
   `FeatureId` (эпик не найден) гейт пропускает, как задачу без фичи: это отдельный дефект
   трекера, и блокировать из-за него работу не надо.
2. **Сторож зависших** (`ClassifyStall`): задачи удержанной фичи не окликаются и человека не
   зовут. Прерванные паузой задачи сторож и так пропускает (у них стоит `ExecutorStoppedAt`,
   `TaskExecutionService.cs:1299`). Явная проверка гейта нужна для остальных: задача в работе,
   ход которой закончился за миг до паузы, иначе через порог получит оклик.
3. **Пробуждения по докладам:** `chats_report_up` и доклад о завершении задачи удержанной фичи
   ложатся карточкой, но **не запускают ход** постановщику. Это касается и `blocker: true`:
   человек увидит карточку, оркестратор не проснётся.

Четвёртая точка прежней версии (`WorkLoop` исполнителя спрашивает гейт перед витком) больше не
нужна: прерывание (ниже) само гасит цикл «до готово», `SessionManager.Interrupt` сбрасывает
`WorkLoop` в `null`.

### Пауза прерывает идущие ходы сразу

Решение Андрея: **пауза прерывает работу немедленно, а не даёт ходу доиграть.** Новый механизм
прерывания не заводим: пауза зовёт ту же остановку, что «Стоп» человека на доске агентов
(`BoardController.InterruptAgent` → `SessionManager.Interrupt` +
`TaskExecutionService.MarkStoppedByUserAsync`), но со своей причиной.

**Кого прерываем.** Все задачи фичи, у которых `Status != Done`, есть `LinkedSessionId` и в
этой сессии сейчас идёт ход. В выборку входят и задачи подготовки, и ревью, и финал. **Ключевой
чат оркестратора не прерываем.** Он общий для нескольких фич (раздел 2), и его ход может быть
про другую фичу. Оркестратор узнает о паузе из карточки, а новые запуски по этой фиче у него
закроет гейт. Мерж (`merging`) пауза не трогает вовсе: на нём ручка отвечает 409.

**Что происходит с прерванным шагом.**

| | Что с ним | Почему так |
|---|---|---|
| Ход | `Interrupt`: процесс CLI гасится, очередь чата замораживается, `WorkLoop = null` | ровно путь «Стоп» человека: прерванный ход не присылает `result`, поэтому доклад о завершении и пробуждение постановщика не случаются |
| Статус задачи | не меняется: остаётся `InProgress` | все пометки остановки живут отдельными полями, статус держат доска, фильтры, MCP и напоминания (`TaskManager.MarkExecutorStopped`) |
| Пометка | `ExecutorStoppedAt = now`, `ExecutorStopReason = "feature_held"` | новая **терминальная** причина в `ExecutorStopClassifier`. Терминальная, иначе `MarkExecutorStopped` её не примет |
| Журнал задачи | `stopped` с `reason: feature_held` | пишет существующий `WriteJournalTransitions`, новых видов не нужно |
| Журнал эпика | `held` с `reason: manual` | одна запись на паузу, а не по записи на задачу |
| Таймлайн | work-интервал задачи кончается на `ExecutorStoppedAt` (`FeatureActivity`), дальше идёт `totals.paused` | работа на паузе не считается работой |
| Файлы в worktree | остаются как есть, вместе с недописанной правкой | пауза git не трогает: ни stash, ни коммита, ни отката. Откат потерял бы работу, а коммит закрепил бы полуфабрикат. Пока фича на паузе, worktree никто другой не правит |
| Уведомления | нет: ни `HandleExecutorStoppedAsync`, ни доклада постановщику | паузу поставил сам человек, он в курсе. В ключевой чат уходит одна карточка «фича на паузе, прервано N шагов», без хода |

**Почему своя причина, а не `interrupted_by_user`.** У `interrupted_by_user` две особенности,
которые паузе вредят. Её снимает **любой** новый ход в чате исполнителя
(`ResumeAfterUserStopAsync`, хук `TurnStarting`), так что пауза растаяла бы от первого же
сообщения. И проектор читает её как `stopped`, то есть «ждёт вас». `feature_held` снимает
только снятие паузы, а пока фича удержана, проектор показывает `paused`: правило 3 стоит выше
`stopped`.

**Человек пишет в чат прерванного исполнителя во время паузы.** Это разрешено, человек хозяин
своих чатов: гейт стоит на запусках исполнителей и пробуждениях агентов, а не на ходах человека.
Пометка `feature_held` от такого хода не снимается. Если человек хочет вернуть шаг в работу, он
снимает паузу.

### Как шаг продолжается после снятия паузы

Снятие паузы (`DELETE .../hold` при `Reason = manual`) **возвращает то, что пауза отняла**, и
ничего сверх этого:

1. Для каждой задачи фичи с `ExecutorStopReason = feature_held`:
   - **чат исполнителя жив** → ход-продолжение в **ту же** сессию (`--resume`, контекст
     исполнителя цел), и только после успешной доставки — `ClearExecutorStopped(id, "feature_held")`.
     Текст хода: «Пауза фичи снята.
     Ход был прерван на середине: проверь состояние рабочего дерева (`git status`) и продолжи с
     того места, где остановился». Статус не меняется, `ClaudeStartedAt` не сдвигается, в журнале
     появляется `stop_cleared`;
   - **чат исполнителя удалён** (истёк TTL `ExecutionExpiresAfterMinutes`, по умолчанию сутки
     от последней активности, или его удалил человек) → пометку **не снимаем, а меняем** на
     терминальную `feature_held_expired`. Проектор покажет обычный `stopped` («ждёт вас»), и
     дальше шаг перезапускает человек или оркестратор штатным `tasks_run_executor`
     (`MarkClaudeStarted` снимет пометку сам). Недописанная правка остаётся в worktree, её увидит
     новый исполнитель.
2. Задачи, остановленные по другим причинам (401, `subagent_stuck`, «Стоп» человека до паузы),
   остаются остановленными. Пауза их не останавливала и возвращать не должна.
3. Незапущенные задачи (`todo`) не запускаются: запуск шагов — дело оркестратора, как всегда.
4. В ключевой чат уходит карточка «пауза снята, продолжены N шагов» **с ходом** оркестратору: пока
   фича стояла, доклады ложились карточками без пробуждения (гейт, точка 3), и оркестратору надо
   их разобрать.

Это меняет прежнюю версию разреза («снятие паузы ничего не запускает само»). Тогда пауза давала
ходу доиграть, и снимать было нечего. Теперь пауза отнимает идущие ходы, и молча оставить их
отнятыми значит превратить паузу в «Стоп» по всей фиче с ручным перезапуском каждого шага.
Продолжение — это возврат к состоянию до паузы, а не автозапуск новой работы. Автозапуск
незапущенного по-прежнему появится только вместе с очередью.

**Цикл «до готово» не восстанавливается.** `Interrupt` его гасит, и продолжение идёт одним
ходом. Исполнитель задачи и без цикла доходит до `tasks_complete` или до доклада, ровно как
после «Стоп» человека сейчас. Запоминать флаг цикла на задаче ради этого — новое поле без
доказанной потребности.

**TTL чата исполнителя на паузе.** Срок чата считается от последней активности, а на паузе
активности нет. При паузе дольше суток продолжение упадёт во вторую ветку (перезапуск с нуля и
потеря контекста исполнителя). Дешёвое лечение без нового поля: при постановке паузы снимать
срок у прерванных чатов (`SessionManager.SetExpiry(id, null)`), а при снятии ставить заново
`task.ExecutionExpiresAfterMinutes` (`SetExpiry` сдвигает якорь на «сейчас»). Делать ли это в
первом шаге, решает Егор при планировании. Вторая ветка работает и без этого, просто дороже.

### Журнал и таймлайн

- Журнал `data/feature-journal/`: новые виды эпика `held` / `hold_cleared` (с `reason`). «Запуск
  черновика» отдельным видом не пишется: это `hold_cleared` с `reason: draft`. Формат `v:1`
  допускает расширение словаря видов, версия не растёт. Переходы эпика `Done ↔ InProgress` уже
  пишутся видом `status`.
- Журнал задач: прерывание и продолжение пишутся существующими `stopped` / `stop_cleared`, у
  которых `reason` = `feature_held` (или `feature_held_expired`). По паре `held` у эпика и
  `stopped: feature_held` у задачи таймлайн показывает, какие шаги отняла пауза.
- Таймлайн: интервал `held..hold_cleared` с `reason: manual` идёт отдельной строкой
  `totals.paused`, а не в `idle`. Иначе «простой» на странице раздует время, которое человек
  сам поставил на паузу. Черновик в `paused` не считается: до запуска фичи простоя нет, и
  таймлайн идёт от `hold_cleared` черновика, как сейчас идёт от первого запуска.

## 2. Ключевой чат во всех своих фичах

### Почему чат «исчезает» сейчас

Членство не теряется: оно вычисляется и закрытием не снимается. Чат пропадает из-за
**отображения**, а у отображения четыре разных правила:

| Где | Правило | Расхождение |
|---|---|---|
| `FeatureChatMembership.Build` | executor ∪ curator ∪ orchestrator (вкл. запуски дочерних) | эталон |
| `BuildIndexCore` → `index.chats` | эталон, но порядок связей — по силе, потом по порядку фичи | закрытая фича не понижается |
| `ProjectForSession` (шторка плашки, «Исполнение фичи») | только `epic.SourceSessionId` / `epic.ExecutorLaunchedBySessionId` | **нет** оркестратора через дочерние задачи |
| `BuildFeatureChats` (вкладка «Чаты» страницы) | только `Session.TaskId` ∈ задачи фичи | **нет** куратора и оркестратора без `TaskId` |

Сценарий исчезновения. Чат Софьи — куратор закрытой фичи A (создал эпик) и оркестратор
открытой фичи B (запускал её шаги). Сила связи `curator > orchestrator`, поэтому
`index.chats[чат][0] = A`. Список чатов кладёт чат в группу **первой** связи (`chatGroups.ts`,
`groupByFeatures`, п. 1), а это секция закрытых, свёрнутая по умолчанию. В группе B остаётся
только след «+1 чат в другой группе». На странице B чата нет вовсе (`BuildFeatureChats`), а
шторка плашки B не покажет (`ProjectForSession`).

### Решение

1. **Одно правило членства.** `ProjectForSession` и `BuildFeatureChats` берут множество из
   `FeatureChatMembership.Build`, а не из своих условий. Вид связи (`curator` / `orchestrator`
   / `executor`) определяется по тем же осям, что в `BuildIndexCore`. Логику определения вида
   вынести в одну функцию рядом с `FeatureChatMembership`, чтобы её не держали две копии.
   Вкладка «Чаты» страницы получает ключевой и кураторский чаты в каждой своей фиче.
2. **Порядок связей чата: открытые раньше закрытых.** В `BuildIndexCore` сортировка
   `chats[id]` становится такой: `bucket = closed` в конец, затем сила, затем порядок фичи.
   `PreferFirst` (своя фича по `TaskId`) действует внутри класса «открытые / закрытые», не
   поверх него. Тогда первая связь — всегда живая фича, если она есть, и группа в списке,
   плашка по умолчанию и шторка показывают её.
3. **Строка-ссылка в остальных группах (фронт).** Чат остаётся **одним узлом дерева** в группе
   первой связи. В группах остальных его фич он рисуется ссылкой: одна строка без поддерева,
   клик открывает тот же чат, подпись роли в той фиче. Данные уже есть (`index.chats` несёт все
   связи), бэк не нужен. Сейчас вместо этого там «+N чат в другой группе»
   (`otherGroupChatIds`), и это решение сводится к выбору Майи. Дублировать полную карточку
   нельзя: два узла одного чата ломают раскрытие, счётчики и «ещё N».
4. **В самом чате.** Плашка уже мультифичевая (`FeatureBanner`: `featureOf` и переключатель
   «ещё N»). После п. 2 по умолчанию показана открытая фича, закрытые остаются в переключателе
   с подписью «закрыта». Шторка и «Исполнение фичи» после п. 1 дают тот же набор фич, что
   плашка. Нового на бэке нет.

**Инвариант.** Множество фич чата одинаково во всех четырёх местах: индекс, шторка, вкладка
«Чаты» страницы, группировка списка. Различаться может только порядок, и он тоже выводится в
одном месте (индекс). Сторож — тест на фикстуре «чат-куратор закрытой A и оркестратор открытой
B»: все четыре потребителя видят {A, B}, первая связь — B.

**Расход не меняется.** `SharedSpendSplitter` уже делит расход общего чата по тому же
`FeatureChatMembership`. Сменится только порядок показа, знаменатель деления останется прежним.

## 3. Границы: что явное, что производное

| Явное (хранится, ставит человек) | Производное (считает проектор, не хранится) |
|---|---|
| `epic.Status = Done` — закрыта | `state` (11 значений), `bucket` (4) |
| `epic.Hold` — черновик / пауза / (очередь) | этапы и их состояния, `stepProgress`, готовность |
| `verification.verdict` задач (финал принят) | `merge_pending` / `merging` / `merged` |
| `FeatureId` / `Role` задач | членство «чат → фичи», ключевой чат, оркестратор |
| | тревога `attention`, «Сейчас», таймлайн |

Правило: **хранится только решение человека, его последствия выводятся.** Никакой снимок
производного состояния в эпик не пишется (ни «последний state», ни «готовность %»). Он протух
бы при первой же смене задачи, а потребители начали бы читать его вместо проектора.

## Контракты (сводно)

```
TaskItem (role=feature) + Hold: { reason: draft|manual|queue, since, bySessionId?, byUser }?
FeatureStates           + Paused = "paused"        // после Closed, перед Stopped; Bucket → idle
                        + Draft  = "draft"         // после Waiting, перед Merging; Bucket → idle
FeatureRun              + Hold (копия)
FeatureIndexRow         + HoldReason: string?
FeatureTimeline.totals  + paused: minutes          // только reason=manual
FeatureJournalEntry.kind+ "held" | "hold_cleared"
ExecutorStopClassifier  + FeatureHeldReason = "feature_held"                 // терминальная
                        + FeatureHeldExpiredReason = "feature_held_expired"  // терминальная, чат исполнителя пропал
POST   /api/tasks/features/{id}/hold   { reason: draft|manual }
         → 200 { interrupted: [taskId] }
         | 403 (сервисный токен)
         | 409 (merged/closed/merging; draft после запуска шага; manual поверх draft)
DELETE /api/tasks/features/{id}/hold
         → 200 { resumed: [taskId], expired: [taskId] }
         | 403 (сервисный токен) | 409 (нет удержания)
FeatureHoldGate.Allows(task, owner)                // запуск, ClassifyStall, пробуждения
                                                   // draft пропускает cut/design/plan/consult
FeatureChatMembership   — единственный источник для ProjectForSession и BuildFeatureChats
index.chats[id]         — порядок: открытые → сила → порядок фичи
```

Хранение аддитивное: nullable-поле у `TaskItem`, `BackupSchema.Version` не растёт, старые
записи читаются как «без удержания».

## Риски

- **Новые значения `state` у потребителей.** Их читают `Bucket`, `RailOf`, `ChipsOf`,
  `AttentionOf` на бэке и `FeatureBanner`, `FeaturePageHeader`, `FeatureRunView`,
  `FeatureStatsBits`, `pillModel`, `chatGroups` на фронте. У тех, где есть ветка `default`, новые
  значения молча уйдут в «простой» или «идёт». Требование к шагу: `FeatureState` на фронте
  остаётся объединением литералов, и все `switch` по нему исчерпывающие (`never` в `default`),
  чтобы `tsc` поймал пропуск. На бэке нужен тест «каждое значение `FeatureStates` даёт явную
  ветку `Bucket`».
- **Гейт с дырой.** Пауза, которую соблюдают не все точки, хуже отсутствия паузы: человек
  уверен, что агенты стоят. Самые вероятные места недосмотра — автопробуждение по `report_up` и
  оклик сторожа у задачи, ход которой закончился за миг до паузы. Приёмка шага — сценарий
  «поставил паузу при двух идущих исполнителях, один из них в `WorkLoop` → оба хода прерваны,
  у обоих `feature_held`, нового хода нет, оклика нет, доклад ушёл карточкой без хода».
- **Прерывание посреди правки.** Решение Андрея принимает эту цену: недописанный файл остаётся в
  worktree. Продолжение в той же сессии с подсказкой «проверь `git status`» её гасит, а
  перезапуск с нуля (ветка «чат пропал») — нет: новый исполнитель видит чужую полуправку. Это та
  же картина, что после «Стоп» человека сейчас, нового риска пауза не вносит, но умножает его на
  число прерванных шагов.
- **`feature_held` за пределами паузы.** Пометка обязана сниматься ровно в двух местах: снятие
  паузы и перезапуск (`MarkClaudeStarted`). Если её начнёт снимать хук `TurnStarting`, как
  `interrupted_by_user`, пауза растает от первого сообщения человека в чат исполнителя. Нужен тест
  «ход человека в чате прерванного исполнителя пометку не снимает».
- **Закрытие фичи с прерванными шагами.** Закрытие снимает `Hold`, но задачи с `feature_held`
  остаются `InProgress` со стоп-пометкой. Проектор закрытой фичи их не показывает (`closed` выше
  всех), а «вернуть в работу» покажет их как `stopped`. Это честно: шаги прерваны и ждут решения.
  Автоматически их продолжать при возврате не надо.
- **Вторая точка правды о закрытии.** Если кто-то положит `lifecycle` рядом с `Status` «для
  удобства фронта», закрытие разъедется. Закрытие — только `Status`, удержание — только `Hold`.
- **Шов индекса и страницы.** После п. 2 вкладка «Чаты» страницы и индекс берут членство из
  одного источника. Если вид связи снова начнут определять на месте, расхождение вернётся.
  Определение вида — одна функция.
- **Очередь позже.** `Reason = queue` в словаре сразу, но ставить его сейчас нельзя: автоснятие,
  порядок и уступка на `merge_pending` (решение Андрея из п. 5 идей) — отдельный разрез с
  хранимым порядком очереди. Это новое хранилище и требует отдельного «да».

## Решения Андрея (23.10)

| Вопрос | Моя рекомендация | Решение | Что изменилось в разрезе |
|---|---|---|---|
| Пауза прерывает идущие ходы? | дать доиграть | **прерывать сразу** | путь «Стоп» с причиной `feature_held`; снятие паузы продолжает прерванные шаги в их же сессиях; точка гейта `WorkLoop` ушла |
| Черновик отдельно от паузы? | одно и то же, разница в подписи | **отдельный статус** | `state = draft` со своим местом в приоритете; гейт пропускает подготовку; только начальная стадия; «Запустить» = снятие удержания с ходом оркестратору |
| Оркестратор ставит паузу сам? | только кнопка | **только человек** | ручки отказывают сервисному токену (403); оркестратор предлагает текстом или докладом; строка в «Никогда» Софьи |

Открытым остаётся один вопрос, и он не блокирует шаги: должна ли **любая** новая фича
рождаться черновиком (тогда меняется конвейер Софьи) или черновик ставит только человек при
создании из интерфейса. По умолчанию разрез берёт второе.

## Порядок работ

Точка 2 идёт первой: она чинит существующий дефект и от паузы не зависит. Точка 1 режется на
три шага, потому что прерывание чужих ходов опаснее остального и должно ревьюиться отдельно.

| Шаг | Что | Исполнитель | Зависит от |
|---|---|---|---|
| A | П. 2, бэк: одно правило членства, порядок `chats[id]`, тест на четырёх потребителей | Денис или Кузьма, ревью Глеба | — |
| B | П. 2, фронт: строка-ссылка в остальных группах | Кира | макет Майи, A |
| C | П. 1, бэк, данные: `Hold`, `paused` и `draft` в проекторе, `Bucket`, ручки с 403/409 (пока без прерывания), журнал `held`/`hold_cleared`, `totals.paused`, гейт `Allows` в трёх точках | Тимур | A (общий `FeatureProjector`) |
| D | П. 1, бэк, прерывание и продолжение: `feature_held`/`feature_held_expired` в `ExecutorStopClassifier`, прерывание в `POST hold`, продолжение в `DELETE hold`, карточки в ключевой чат, тест «ход человека не снимает пометку»; продление TTL — по решению Егора | Тимур | C |
| E | П. 1, фронт: исчерпывающие `switch` по `FeatureState` (`paused`, `draft`), подписи по `HoldReason`, кнопки «Пауза» / «Снять паузу» / «Запустить» / «В черновик», показ `interrupted`/`resumed` из ответа ручек | Полина | макет Майи, C (контракт ручек) |
| F | Промпт оркестратора: строка в «Никогда» Софьи и её локального двойника | Софья правит персону сама или через Андрея | C (до включения кнопок) |

C и D разделены намеренно. После C пауза уже работает как «не запускать новое», и фронт E может
идти параллельно с D. D трогает `TaskExecutionService` и сессии других чатов, поэтому
локальному исполнителю с узким контекстом его не отдавать, а ревью Глеба по нему — с прогоном
сценария из «Рисков». Кнопку «Пауза» в интерфейсе включать только после D: без прерывания она
обещала бы человеку больше, чем делает.

Швы гейта и прерывания (три точки гейта, прерывание, обе ветки продолжения) смотрю на финале
сам.
