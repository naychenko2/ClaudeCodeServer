# ADR-027: умный подбор фото персонажа под сюжет

- **Статус:** предложено 2026-10-10. Разрез — Александр (задача `bf32adbd`), план — Егор (`6cd0b115`), проба позы — Марк (`7f99efdc`, [отчёт](../research/face-pose-probe-2026-10.md)). Решения Андрея записаны как принятые и здесь не пересматриваются.
- **Флаг:** `character-smart-photos` (dark launch). Снимаем после замера сходства «подбор против главного фото» (шаг 21 плана), а не по календарю.
- **Связано:** [ADR-017](ADR-017-image-editor.md) (персонажи), [ADR-014](ADR-014-internal-subsystems.md) (границы вертикалей), [ADR-025](ADR-025-media-format.md), [ADR-026](ADR-026-character-lora-training.md), [ADR-007](ADR-007-model-preset-chains.md) §3 (пресет-маршруты мест).

## Контекст

Фото персонажа уходят в генерацию вслепую. `CharacterStore.ForRequest` ставит главное фото первым, остальные — по порядку манифеста: до 3 образцов (`PhotosPerRequest`) и до 10 фото эталона сходства (`facePhotos`). Локальная модель берёт первое фото (`EditRequestComposer`, `MaxCharacterPhotos: 1`). Под сцену «в профиль у окна» или «смеётся» фото не выбирается, и сходство проседает: замер команды — фото со смехом поднимает сходство с 0,59 до 0,76.

## Решения Андрея (вход, не пересматриваются)

1. Критерии подбора — только **ракурс** (анфас / три четверти / профиль и наклон) и **эмоция**. Свет, место, внешность — нет.
2. Исполнителя разметки выбирает админ в «Поставщиках моделей»: ракурс — `face-pose` локально или облачная vision-модель; эмоция — только vision; разбор сюжета — дешёвый текст плюс правила.
3. У локальной модели (одно фото) главное фото меняется на подобранное **только при уверенном совпадении**; порог даёт замер шага 21.
4. **Существующие фото размечаются автоматически в фоне, без отдельного согласия** — только у владельцев с включённым флагом. Это сознательное решение Андрея: фото, загруженные до фичи под согласие «на сервис рисования», уйдут в облачную vision-модель на разметку эмоции. Возражение разреза (`bf32adbd` §2, «только кнопкой») отклонено.
5. В карточке результата видно, какие фото взяты, и есть «Заменить» — новый запуск с явным списком фото.

## Решения

### 1. Метки — в `character.json`, в записи фото

```csharp
public sealed record CharacterPhoto(
    string File, bool Primary = false,
    string? Angle = null, string? Pitch = null, string? Emotion = null, string? LabelSource = null)
{
    [JsonExtensionData] public Dictionary<string, JsonElement>? Extra { get; init; }
}
```

| Поле | Значения |
|---|---|
| `Angle` | `front` · `three-quarter` · `profile` · `unknown` |
| `Pitch` | `level` · `up` · `down` · `unknown` |
| `Emotion` | `neutral` · `smile` · `laugh` · `serious` · `sad` · `surprised` · `unknown` |
| `LabelSource` | `auto` · `human` |

- `null` — разметка ещё не пробовалась. `unknown` — исполнитель ответил, но метки нет (лицо не найдено, модель отказала). Повторно такое фото **не размечается**; подбор считает `unknown` за отсутствие метки. Отдельного поля «попытка была» не заводим: `unknown` им и служит.
- `LabelSource = human` ставится при любой ручной правке меток фото. Авторазметка такое фото не трогает никогда, ни одно его поле.
- Значение вне словаря (старые записи `Angle`, ручная правка файла) читается как «нет метки» и не переписывается, пока его не поменяет человек.
- Запись меток — под существующим `KeyedLocks` персонажа, merge по имени файла поверх свежего чтения манифеста. Метка фото, удалённого за время разметки, отбрасывается.
- `[JsonExtensionData]` на `CharacterPhoto` — чтобы следующий откат кода не стёр новые поля при первой же правке. Нынешний откат на master их сотрёт, это приемлемо: метки восстанавливаются повторной разметкой.
- Ручная правка — тот же `PATCH` персонажа: `CharacterPatch.PhotoLabels: IReadOnlyDictionary<string, CharacterPhotoLabels>?` (ключ — имя файла из манифеста; чужое имя — 400).
- Метки — текстовые признаки, а не биометрический шаблон, и живут в папке проекта, не в `data/`: правок `BackupPaths`/`BackupSchema` не нужно.

### 2. Три места в `LocalActionCatalog` и признак «нужны картинки на вход»

`LocalAction` получает два поля: `ActionInput Input = ActionInput.Text` (`Text | Images`) и `bool FacePose = false`.

| Ключ | Группа | Вход | `FacePose` | По умолчанию |
|---|---|---|---|---|
| `character-photo-angle` | Персонажи | `Images` | да | `face-pose` (см. §3) |
| `character-photo-emotion` | Персонажи | `Images` | нет | слот профиля `Small` → слабая |
| `character-scene-parse` | Персонажи | `Text` | нет | `DefaultLocal: true`, только `RunFreeAsync` |

Правила для мест с `Input = Images`, по образцу `Agentic`:
- **Отказ на входе** (`LocalActionsAdminController.Set`, рядом с проверкой `Agentic`): 400 на `local` (локальная текстовая модель зрения не имеет), на `direct:*` (HTTP-клиент `CloudCheapClient` картинок не передаёт) и на `preset:*` (цепочки пресетов текстовые). Модель (`RouteKind.Model`) принимается, только если её провайдер `SupportsImages`. `face-pose` принимается только на месте с `FacePose = true`, на любом другом — 400.
- **Пропуск в пресетах** (`LocalActionPresetService.ApplyAsync`, рядом с пропуском `Agentic`): массовые пресеты места с картинками не трогают ни в одном режиме, включая `Tiers`.
- **Слот (`tier:*`) допустим**, но `SupportsImages` у слота проверяется в рантайме по владельцу (`UserModelTierResolver.ModelFor`): слот, развернувшийся в модель без зрения, — отказ `NoVision`, фото остаются без меток. Тихо ответить, не видя картинки, модель не должна: это уже случалось на GLM (`ClaudeSession`, ветка `SupportsImages`).
- Места с картинками **никогда** не идут через `ICheapTextRunner`.

`Describe` админ-ручки и блок мест в `GET /api/usage` отдают `input` и `facePose`; пикер (`RoutePicker`) на местах с картинками прячет «Локальную», `direct:`-модели, модели без зрения и пресеты, а на месте ракурса показывает пункт «Локально, InsightFace».

### 3. Маршрут `face-pose`

**Форма в маршрутизации — новое значение стора и новый вид маршрута**, а не переопределение «Локальной»:
- `LocalActionOverridesStore.FacePoseRoute = "face-pose"`, `RouteKind.FacePose`; `LocalActionRouter.Parse` разбирает строку в этот вид.
- Дефолт места с `FacePose = true` без настройки админа — `RouteKind.FacePose`, `RouteSource.Default`.
- `CheapTextRunner`, получивший `RouteKind.FacePose` (стор правили руками), идёт по дефолтному слоту места и пишет warning — как с битой ссылкой на пресет.

Переиспользовать `local` для ракурса отвергли: `RouteKind.Local` во всём продукте значит «Ollama/llama-server», `UsesLocal` проверяет живость Ollama, а пикер подписывает пункт именем текстовой модели. Двусмысленное значение стора — ровно та ошибка, которую потом никто не увидит. Цена своего значения — новый член enum и проход по 22 местам использования `RouteKind`; компилятор их перечислит.

**Транспорт — узел ComfyUI `CcsFacePose`, расчёт на CPU, граф из шаблона:**
- Узел живёт в пакете `deploy/comfyui/face/` рядом с `CcsFaceSimilarity` и устроен так же: тонкий узел внутри ComfyUI, расчёт — subprocess `worker_pose.py` в `~/ai-data/face-workers/.venv`, InsightFace `buffalo_l`, `CPUExecutionProvider`. Модель грузится один раз на прогон; на персонажа (до 10 фото) — около 2 с загрузки и 0,36 с на фото.
- Воркер отдаёт углы **именованными полями** (`yaw`, `pitch`, `roll`), а не массивом. `face.pose` у InsightFace — `[pitch, yaw, roll]` (сверено с `insightface/model_zoo/landmark.py` в venv gpuhost), и проба шага 2 уже перепутала оси (§5). Порядок разбирается в одном месте воркера и покрыт тестом.
- Шаблон — `ComfyWorkflows` (произвольный граф = запись файлов хоста, ADR local-media). Фото передаются, как эталоны сходства: загрузкой в input ComfyUI.
- Шов — новый метод `ILocalImageMedia`:

```csharp
Task<LocalFacePoseResult> FacePoseAsync(IReadOnlyList<byte[]> images, CancellationToken ct);

// Poses — по одному на вход, в том же порядке; null — лицо не найдено.
// Busy — очередь занята или ComfyUI не ответил: «попробуй позже», фото не помечаются
public sealed record LocalFacePoseResult(IReadOnlyList<LocalFacePose?>? Poses, string? Error, bool Busy = false);
public sealed record LocalFacePose(double Yaw, double Pitch, double Roll);
```

Метод сам подаёт задачу и ждёт её (потолок 60 с, как у воркера сходства); углы в категории переводит не он, а чистая функция в ImageEditor (§5). Арифметика порогов на C#, а не в Python: её покрывают тесты сборки, а пороги правит замер шага 21.

Почему через ComfyUI, а не отдельным CPU-сервисом. ComfyUI — единственный канал продукта к gpuhost; прогон держит исполнитель ComfyUI около 6 с на персонажа, GPU в это время свободен. Фоновая разметка подаётся **только при пустой очереди** (`QueueLengthAsync() == 0`), иначе откладывается — генерации человека она не задерживает. Отвергнуто:
- отдельный HTTP-сервис на gpuhost — новый порт, аутентификация, деплой и мониторинг ради шестисекундных задач;
- InsightFace на хосте бэкенда — новая рантайм-зависимость (onnxruntime/Python) на машине, где живут агенты под потолком `ccs-agents.slice`;
- `CUDAExecutionProvider` — 1,5–2 ГБ VRAM в общей видеокарте ради выигрыша в секунды на фоновой задаче.

Если local-media на инстансе не заведён (`ILocalImageMedia.Configured == false`), дефолтный `face-pose` места ракурса разворачивается в дефолтный слот места (vision). Явно выбранный админом `face-pose` не подменяем (правило редактора картинок): при недоступном ComfyUI фото ждут.

### 4. Шов `IImageLabeler` в Core

ImageEditor не ссылается на `ClaudeHomeServer.Llm` (ADR-014), а готового пути «картинка → дешёвая модель» нет: `ICheapTextRunner` и `CloudCheapClient` только текстовые. Шов — в `ClaudeHomeServer.Core`, namespace `ClaudeHomeServer.Services.Llm`:

```csharp
public interface IImageLabeler
{
    // Чем размечает место для этого владельца. Единственная точка, через которую
    // ImageEditor узнаёт маршрут, — второго чтения стора назначений нет
    ImageLabelRoute RouteOf(string actionKey, string ownerId);

    // Только Kind = Vision; FacePose сюда не приходит (его ведёт ILocalImageMedia)
    Task<ImageLabelResult> LabelAsync(ImageLabelRequest request, CancellationToken ct);
}

public enum ImageLabelRouteKind { FacePose, Vision, None }
public sealed record ImageLabelRoute(ImageLabelRouteKind Kind, bool Explicit, string? Model);

public sealed record ImageLabelRequest(
    string ActionKey, string OwnerId, string Prompt, IReadOnlyList<ImageLabelInput> Images);
public sealed record ImageLabelInput(byte[] Bytes, string ContentType);

public enum ImageLabelFailure { NoVision, Unavailable, Refused, Timeout, Failed }
public sealed record ImageLabelResult(string? Text, ImageLabelFailure? Failure);
```

- Реализация — в `ClaudeHomeServer.Llm`: маршрут через `LocalActionRouter`, слот через `UserModelTierResolver.ModelFor`, проверка `SupportsImages`, вызов — one-shot claude CLI с `--input-format stream-json` и image-блоками по образцу `ClaudeSession`. Расход идёт в общую аналитику по ключу места.
- `None` — место выключено или маршрут непригоден (модель без зрения): разметки нет, это не ошибка.
- Вызывающий (ImageEditor) сжимает фото до 512 px по длинной стороне в JPEG до отправки: меньше лиц в полном разрешении уходит наружу и меньше токенов.
- Промпт обязан говорить «не опознавай человека, опиши только позу и выражение, ответ — JSON по файлам». Отказ модели — `Refused`, фото получают `unknown`.
- Пачка — до 10 фото одного персонажа за вызов.

### 5. Пороги ракурса — поправка к пробе

Проба шага 2 приняла первую координату `face.pose` за yaw, а это pitch. Отсюда «системный сдвиг yaw при большом pitch» в отчёте и пороги с поправкой на pitch из его §5: они построены на перепутанных осях. Ручные метки наклона в таблице отчёта совпадают со знаком настоящего yaw, то есть не независимы от чисел. Пересчёт той же таблицы с правильными осями:
- по |yaw| с порогами 12° / 45° — 23 из 34 совпадений, ни одной путаницы анфас ↔ профиль;
- все расхождения — на границах «анфас ↔ три четверти» и «три четверти ↔ профиль», где ручная разметка сама противоречит себе: почти одинаковые позы (`andrey-1/face-07` и `andrey-2/face-08`, yaw ≈ 58,9°) размечены по-разному.

Вывод: инструмент годен (профиль с анфасом не путает, скорость приемлема), а **вердикт по точности и пороги — не доказаны**. Принимаем пороги только по yaw как стартовые:

| Категория | Правило |
|---|---|
| `front` | \|yaw\| ≤ 12° |
| `three-quarter` | 12° < \|yaw\| ≤ 45° |
| `profile` | \|yaw\| > 45° |
| `Pitch` | `level` при \|pitch\| ≤ 15°, иначе `up`/`down` по знаку |

- Знак pitch («вверх» — плюс или минус) у InsightFace не проверен: его фиксирует повторная проба.
- Пороги — константы одной чистой функции `FacePoseClassifier` в ImageEditor, с тестом на границы.
- **Условие для шага 14:** повторная проба с именованными осями, на наборе без дублей, с ручной разметкой исполнителем, не видевшим чисел. Приёмка — не меньше 85 % точных совпадений по трём категориям и ни одной путаницы анфас ↔ профиль. Не прошла — `face-pose` остаётся в пикере опцией, а дефолтом места ракурса становится vision.

### 6. Разбор сюжета

`character-scene-parse`: `ICheapTextRunner.RunFreeAsync` с `jsonFormat`, ответ `{angle?, pitch?, emotion?}` в словарях §1 (`null`, если сюжет молчит). Потолок 3 с, кэш по хешу промпта. Нет бесплатного маршрута, сбой или пустой ответ — словарь правил («в профиль», «вполоборота», «смеётся», «улыбается», «серьёзн…»). Платный claude здесь не используется. Вызов — только когда в запуске есть персонаж, промпт не пуст и флаг владельца включён.

### 7. Подбор и фолбэк

Подбор — чистая функция `CharacterPhotoPicker` в ImageEditor. Очки фото к сцене:
- ракурс: 2 за точное совпадение, 1 за соседний (`front ↔ three-quarter ↔ profile`);
- наклон: 1 за совпадение;
- эмоция: 2 за точную, 1 за родственную (`smile ~ laugh`).

Ничья — в пользу главного фото, затем по порядку манифеста. `unknown` и `null` дают 0.

Порядок образцов (`photos`, до 3):
1. первое место — лучшее фото, **если его очки не ниже порога уверенности `LocalConfidentScore`**, иначе главное;
2. дальше — второе из пары «лучшее / главное», затем остальные по очкам.

Главное фото у облачных моделей так всегда в наборе (якорь внешности), а локальная модель, которая берёт первое фото, получает подобранное только при уверенном совпадении (решение Андрея 3) — без знания о драйвере в подборе и без правок `EditRequestComposer`. До замера шага 21 `LocalConfidentScore` — «никогда» (`int.MaxValue`): главное фото первым всегда.

**Фолбэк — нынешний порядок байт в байт** («главное, затем манифест») в любом из случаев: флаг выключен; сюжет не дал ни ракурса, ни эмоции; у персонажа нет меток; у всех фото 0 очков. Тест сравнивает запрос драйверу с master побайтно.

**Эталон `facePhotos` (до 10) от подбора и от явного списка не зависит**: всегда главное плюс манифест. Иначе `Similarity` перестаёт быть сравнимой между версиями.

Где выполняется: в `ImageEditJobService` до вызова драйвера, а не в ассемблере — запуск уже асинхронный, разбор не держит HTTP-ответ «запустить». Котировка от подбора не меняется: число фото то же.

### 8. Запуск помнит выбор; явный список

```csharp
public sealed record ImageThreadLaunch(..., string? Prompt, ImageThreadCharacter? Character = null);

// Photos — имена файлов манифеста в порядке отправки драйверу, байтов не храним.
// Pick: auto — подобрано по сцене; manual — явный список человека; fallback — нынешний порядок
public sealed record ImageThreadCharacter(
    string Slug, IReadOnlyList<string> Photos, string Pick, CharacterScene? Scene);
public sealed record CharacterScene(string? Angle, string? Pitch, string? Emotion);
```

- Версия находит запуск по `JobId`, в версии ничего не дублируется. Старые нити читаются с `Character = null`.
- Агент видит выбор текстом в `image_state` и хвосте хода (по образцу `SimilarityText`). **Схемы MCP-инструментов не меняются** — `tools/list` стабилен, `McpToolsetStabilityTests` зелёный без правок. Явная подмена фото агентом — вне этого ADR: она требует нового аргумента `image_generate`.

Явная подмена — `ImageEditLaunchRequest.CharacterPhotos: IReadOnlyList<string>?` (и `characterPhotos` в HTTP-DTO):
- допустима только вместе с `CharacterSlug` и при включённом флаге владельца;
- каждое имя — **точное** совпадение с `File` в манифесте этого персонажа; путь строится через `SafePath`/`PhotoPath` с проверкой на символическую ссылку; дубли и больше `PhotosPerRequest` — отказ. Любое нарушение — 400 `character_photos_invalid`, без частичного применения: иначе поле становится чтением любого файла проекта;
- порядок значим и уходит драйверу как есть; подбор не выполняется, `Pick = manual`;
- подмена действует на один запуск и в префы не пишется; «Заменить» в карточке — новый запуск с тем же промптом и базой.

### 9. Фоновая разметка (бэкфилл)

`CharacterPhotoLabeling` — hosted-очередь в подсистеме ImageEditor:
- **Флаг.** Работает только для владельцев с включённым `character-smart-photos` (`IFeatureFlagGate`). Выключен — ни одного вызова.
- **Поводы постановки в очередь:** загрузка фото (`Create`/`Update` с `AddPhotos`), чтение списка персонажей и карточки персонажа, запуск генерации с персонажем. Обхода всех проектов на диске при старте нет: персонаж, которого никто не открывает, не используется и в разметке не нуждается. Так «существующие фото размечаются сами» (решение 4) без сканирования чужих папок.
- **Очередь:** один исполнитель на инстанс, задачи по одному персонажу, дедупликация по (корень проекта, slug). Очередь в памяти: после рестарта её заново наполняют те же поводы, состояние живёт в манифесте.
- **Без повторов:** кандидаты места — фото с `null` в его поле и без `LabelSource = human`. Ответ (включая «лица нет» и отказ модели) записывается сразу, `unknown` повторно не уходит. Временная недоступность (`Busy`, `Unavailable`, `Timeout`) ничего не пишет: фото дождутся следующего повода.
- **Нагрузка:** на персонажа — один прогон `face-pose` и один vision-вызов на пачку до 10 фото. `face-pose` подаётся только при пустой очереди ComfyUI, иначе задача откладывается (повтор не раньше чем через минуту). Vision-вызовы строго последовательны.
- Обучающие фото LoRA (`data/lora-training/`, ADR-026) не размечаются и в облако не уходят.

### 10. Флаг, согласие и фронт

- Флаг гейтится **на сервере**: при выключенном флаге нет разметки, разбора и подбора, `CharacterPhotos` отклоняется, DTO персонажа отдаёт метки как есть (их могло не быть), порядок фото прежний.
- Строка согласия про разметку облачной моделью добавляется к загрузке фото лица — только при включённом флаге; текст даёт Софья. На старые фото согласие не переспрашивается (решение Андрея 4).
- **Фронт меток живёт в новой панели персонажа** (`feat/character-panel`, план `33b30da3`), а не в `CharacterForm.tsx` — панель идёт первой и этот файл удаляет. Метки встраиваются в её шторку «Фото» через пропы `CharacterFacePhotos`: `renderCaption` (подпись меток под фото), `onSelectPhoto` (выбор фото для правки) и `labelsEditor` (редактор меток под сеткой). Компонент меток — `PhotoLabelChips.tsx`. Блок «Взятые фото» с «Заменить» — в карточке версии (`VersionCards.tsx`).

## Что не меняется

- LoRA, триггер и `LoraNamespace.VisibleTo` у local — как раньше; режим B «LoRA только вместе с образцом» держится: хоть одно фото уходит всегда.
- `MediaFormatResolver` и контракты ADR-025: фото персонажа под формат не подгоняются.
- Личная область: персонажей там нет, подбор не вызывается.
- Направление ссылок `Main → Vertical → Core`: ImageEditor видит только `IImageLabeler`, `ILocalImageMedia` и `IFeatureFlagGate`.

## Последствия

- В облако уходят фото лиц, в том числе загруженные до фичи, — по решению Андрея. С `face-pose` наружу уходит только разметка эмоции.
- Ракурс по `face-pose` не доказан до повторной пробы (§5); до неё дефолт места ракурса — условный.
- Новый вид маршрута `RouteKind.FacePose` — первый не-LLM исполнитель в каталоге мест. Следующий такой исполнитель (детектор, OCR) идёт тем же путём: значение стора, вид маршрута, признак места в каталоге, отказ на входе для чужих мест.

## Уточнения после реализации (12.10)

Финальное ревью (`7d9f3e20`) нашло расхождения между принятым текстом и кодом. Ниже — как это есть в ветке, без переписывания принятого.

### Источник автометки — по месту, а не на фото

`LabelSource` теперь только `human` (ручная правка: фото не трогаем целиком). `auto`/`noroute` — по месту разметки: `AngleSource` (ракурс + наклон) и `EmotionSource` (эмоция) независимы, общий источник их путал (дефекты а/б ревью). В DTO `labelSource` выводится общим: `human → auto → noroute → null`. Старый формат, где `LabelSource=auto/noroute` стоял на всё фото, раскладывается при чтении в `CharacterManifest.Parse` (`MigratePhotoLabels`): `noroute` → оба места `noroute`, `auto` → `auto` там, где значение заполнено.

### `noroute` — «разметить было нечем»

`noroute` = нет маршрута (модель разметки не настроена) или 3 сбоя подряд (ComfyUI/модель лежит). Такое фото **повторяется**: когда маршрут появится, разметка дойдёт. Пауза перед повтором — 5 минут, хранится в памяти (после рестарта обнуляется). Поводы повтора — ленивые: список, карточка, загрузка, генерация. В отличие от него `auto + unknown` — модель ответила «не знаю»: такое фото повторно **не** размечается.

### Поле `Op` — без флага, аддитивно

`Op` у `ImageThreadLaunch` и `ImageEditJobDto` идёт без флага (старые нити и запуски без операции — `null`), это аддитивно. Фронт по `op === 'inpaint'` прячет «Заменить»: у запуска с маской сервер сам превращает `edit` в `inpaint`, а перерисовка теряет промпт.

### Отступления от исходного текста

- (а) `Busy` и лежащий ComfyUI считаются **неудачей**: после 3 раз фото получает `noroute`, а не «ничего не пишет», как в §9. Допустимо, потому что `noroute` повторяется.
- (б) Дефолтный `face-pose` при `Configured=false` даёт `noroute`, а не переход на vision, как в §3. Облака так меньше, но на инстансах без local-media ракурс не размечается.
- (в) `character.json` при любой записи пишет `pitch/emotion/labelSource: null` (`DefaultIgnoreCondition = Never`); откат на master их прочитает.

### Фронт — через кит хоста

Фронт берёт флаги и прочие хостовые синглтоны только через `aihome_shell/kit` (ADR-018 §10.3); `shell-kit/index.ts` экспортирует `FLAGS`/`useFeature`. Поймал DEF-1 Веры.

### Условия снятия флага

По решению Александра флаг снимаем, когда:
1. исправление источника по месту закрыто (делано: `AngleSource`/`EmotionSource`);
2. ADR дописан (этот раздел);
3. повторная проба ракурса InsightFace (§5) проходит: ≥85 % точных совпадений и ни одной путаницы анфас ↔ профиль;
4. замер сходства «подбор против главного фото» не хуже; порог `LocalConfidentScore` выставлен по замеру.
