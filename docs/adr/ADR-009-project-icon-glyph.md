# ADR-009: Значок проекта — контракт ответа модели, белый список lucide и форма хранения

**Статус:** Принято (к реализации, волны 1–5 фичи «Значки проектов вместо картинок»)
**Дата:** 2026-08-16
**Принимающий решение:** Андрей (владелец продукта)
**Автор:** Александр (тимлид/архитектор)
**Реализация:** backend — Денис, frontend — Кира, приёмка — Вера
**Связанные:** [ADR-008](ADR-008-project-background-generation.md) — **образец**, которому
настоящий ADR следует буквально: «модель отдаёт данные, разметку собирает сервер», алфавит
команд пути, сборка через `XmlWriter`, сверка нового хранилища с бэкапом. Здесь повторяется
не текст, а приём; расхождения с ADR-008 оговорены явно (§4, §6).
Спека фичи (тексты интерфейса, критерии успеха, что осознанно отрезано) — заметка
«Иконки проектов — переход с картинок на SVG-значки», настоящий ADR текстов не задаёт.

## Контекст

Сегодня иконка проекта — растр: `ProjectIcon.Kind ∈ {Initials, Image}`, файл в
`data/project-icons/{id}/icon-{guid}.png`, генерация через `ImageGenerationService`
(`ImagePlaces.ProjectIcon` — fal.ai/glif), загрузка своей картинки с кропом
(`OriginalFile` + `Crop`), догон очередью `ImageBackfillService`. Цена: минута ожидания
внешнего сервиса, зависимость от чужого API, растр не перекрашивается под тему и мылится
на ретине.

Продуктовое решение (16.08.2026, владелец): **растровые иконки проекта убираются целиком.**
Значок — SVG: модель либо рисует его сама, либо называет готовый из набора lucide, которым
и так нарисован весь интерфейс. Цвет значка = цвет проекта, красится на клиенте. Инициалы
остаются фолбэком. Фича идёт **без фич-флага** — старый механизм не сосуществует с новым,
а заменяется им.

Вопрос, ради которого написан ADR, тот же, что в ADR-008: **модель порождает SVG, который
попадает в страницу пользователя.** Ответ тот же: разметки от модели не будет.

Что уже есть и на что контракт опирается:

- `ProjectIcon` в `data/projects.json` (`Kind`, `Color`, `ImageFile`, `OriginalFile`, `Crop`),
  `ProjectManager.SetIconImage/SetIconKind/DeleteAsset`, каскад удаления `IconsDir`.
- Конвейер выбора из четырёх кандидатов: `POST {id}/icon/generate` → грид → `POST {id}/icon/select`,
  поле «Опишите иконку», возврат на инициалы через `POST {id}/icon/mode`. Форма конвейера
  сохраняется, меняется начинка.
- `ICON_SIZE` / `ICON_STROKE` / `ICON_PROPS` ([components/ui/icons.ts](../../frontend/src/components/ui/icons.ts)):
  весь UI — lucide, Feather-канон, `strokeWidth = 2`, round caps, `currentColor`.
- `LocalActionCatalog` + `CheapTextRunner.RunAsync(actionKey, prompt, ownerId: …)` — каталог
  мест применения модели; исполнителя выбирает админ, слот резолвится по владельцу.
- `BackupSchema.Version` (сейчас **7**) и правило «новое хранилище → сверься с бэкапом».
- `ExtractJsonObject` в `DocumentAiService` — устойчивый разбор ответа фонового места.

## Решение

### 1. Модель не отдаёт разметку — как в ADR-008 §1

Обоснование не повторяю: оно целиком в [ADR-008 §1](ADR-008-project-background-generation.md)
(санитайзер чужой разметки fail-open; `foreignObject`, `use`, `image href`, `@import`,
`on*`, сущности; список не обновляется вместе с браузерами). Здесь та же развилка и то же
решение, с одним дополнением, которого у фона не было:

**У значка есть второй, ещё более узкий канал — имя.** Иконка «график», «дом», «гантель»
уже нарисована в lucide, и модели достаточно её назвать. Строка `"chart-line"`, проверенная
на членство в конечном множестве, — это ноль байт данных от модели в итоговом SVG.
Поэтому контракт двухвидовой, и вид «имя» — предпочтительный.

Инвариант, проверяемый тестом:

> В `data/projects.json` и в ответе `GET …/icon.svg` не существует ни одного символа,
> пришедшего от модели, кроме имени из белого списка §5 и символов алфавита путей §3
> (цифры, точка, минус, плюс, пробел, запятая, буквы команд).

### 2. Контракт JSON-ответа модели

#### 2.1. Что уходит в модель

`Project.Name` и, если пользователь его ввёл, поле «Опишите, что изобразить» (первые 200
символов). Больше ничего: ни `SystemPrompt`, ни файлов, ни истории чатов. У фона (ADR-008
§2.1) в промпт шёл ещё системный промпт проекта — значку он не нужен: значок опознаётся
по названию, а поверхность утечки в стороннего провайдера тем меньше, чем меньше вход.

В промпт входит **весь белый список имён §5** (≈120 имён, ~1.5 КБ). Без него модель называет
несуществующие иконки — проверено на любом наборе: она знает, что бывает «иконка кошелька»,
но не знает, как её зовут именно в lucide.

#### 2.2. Схема ответа

Ответ — один JSON-объект без markdown-обвязки; разбор устойчивый (срезаем ```-заборы, берём
подстроку от первой `{` до последней `}`, как `DocumentAiService.ExtractJsonObject`).
Просим **четыре** кандидата — грид выбора существует именно потому, что один вариант
«как получилось» запаса прочности не имеет.

Каждый элемент `glyphs` — **ровно одного вида**: либо `name`, либо `paths`. Оба поля сразу
или ни одного = элемент отбрасывается (не весь ответ).

Вид 1 — имя из набора:

```json
{
  "glyphs": [
    { "name": "piggy-bank" },
    { "name": "chart-line" }
  ]
}
```

Вид 2 — нарисованный значок (координаты в `viewBox="0 0 24 24"`, только штрих, без заливки):

```json
{
  "glyphs": [
    { "paths": ["M3 21H21", "M6 21V9L12 4L18 9V21", "M10 21V15H14V21"] },
    { "paths": ["M4 18L9 12L13 16L20 8", "M16 8H20V12"] }
  ]
}
```

Пути в примере записаны абсолютными командами намеренно: лимит §3.4 распространяется
на **каждое число** строки `d`, а не только на координаты, поэтому относительное смещение
вида `l6-5` (число −5) валидатор отбросит, хотя точка назначения лежит внутри холста.
Относительные команды разрешены — но их аргументы обязаны укладываться в тот же диапазон.

| Поле | Тип | Ограничение | Нарушение |
|---|---|---|---|
| `glyphs` | массив | 1–6 элементов; хвост сверх 6 отбрасывается | 0 годных после §3 → генерация не удалась (§7) |
| `glyphs[].name` | строка | `^[a-z][a-z0-9-]{1,39}$` **и** членство в белом списке §5 | элемент отбрасывается |
| `glyphs[].paths` | массив строк | 1–4 строки, каждая ≤ 256 символов, суммарно ≤ 768 | элемент отбрасывается |
| — | — | заполнено ровно одно из `name` / `paths` | элемент отбрасывается |

Годных кандидатов показываем не больше четырёх (грид фиксированный); просим шесть, чтобы
после отсева осталось из чего выбирать.

#### 2.3. Что модели запрещено (в промпте — явно)

Ни `fill`, ни `stroke`, ни `opacity`, ни `style`, ни `<text>`, ни `<g>`, ни `transform`,
ни градиенты, ни `viewBox`, ни любая SVG-разметка в ответе. Штрих, цвет и толщина заданы
шаблоном §4 и обязаны совпадать с остальными иконками интерфейса (`ICON_STROKE = 2`,
round caps, `currentColor`); любая заливка от модели либо игнорируется схемой, либо ломает
перекраску под цвет проекта и тему. Схема этих полей не принимает — запрет в промпте нужен,
чтобы модель не тратила на них бюджет вывода.

### 3. Валидация путей: алфавит команд и числовые лимиты

**Ревизия 17.08.2026.** Первая редакция §3 писалась до того, как ветку рисования увидели
на живых ответах. Прогон по выборке ответов сильной модели показал, что два порога режут
не мусор, а годные рисунки, причём молча — пользователь видит «значок не подобрался»:

- **«каждое число в `d` лежит в `[-4, 28]`»** отбраковывал любую относительную команду
  с отрицательной дельтой — `v-8`, `l6-5`, `c0-2 1-4 3-5`, — то есть доминирующий стиль
  записи путей. Насколько ловушка была неочевидна, видно по самому ADR: пример
  «дом» из §2.2 (`M6 21V9l6-5 6 5v12`) собственным лимитом §3.4 отбрасывался, и §2.2
  пришлось оговаривать это отдельным абзацем вместо того, чтобы починить правило.
- **«1–4 строки `d` на значок»** убивал целиком узнаваемые многоштриховые вещи: в живой
  выборке рисунки шли на 7, 9 и 12 путей (характерный случай — «самовар»). Отбраковывался
  не лишний путь, а весь кандидат.
- **отсутствие ведущей точки** (`.5`, законная компактная запись SVG) давало отказ на форме
  числа, которую модель пишет постоянно.

Пороги пересмотрены так, чтобы отсекать мусор, а не стиль записи. Строка `d` проходит те же
четыре проверки; провал любой = **кандидат** отбрасывается (не весь ответ). Значения ниже —
источник истины, они же константы `ProjectIconGlyphService`.

**(1) Алфавит** (без изменений). Допустимы ровно: `M m L l H h V v C c S s Q q T t A a Z z`,
цифры `0–9`, `.`, `-`, `+`, пробел, запятая, `\t`, `\r`, `\n`. Всё остальное — отказ.
Экспоненциальная запись (`e`/`E`) **запрещена**: это единственный дешёвый способ получить
координату в миллион парой символов, а иконке она не нужна.

**(2) Форма чисел.** `[+-]?(\d{1,2}(\.\d{1,2})?|\.\d{1,2})`. Две цифры до точки — потому что
холст 24 единицы; два знака после — потому что четверть пикселя на сетке 24 уже неразличима,
а «хвосты» вида `11.9999999` только раздувают строку. Ведущая точка (`.5`, `-.25`) разрешена:
это та же величина в меньшем числе символов, и запрет стоил отказов на ровном месте.
Формы `5.` и голая `.` числами не считаются.

**(3) Синтаксис.** Первый непробельный символ — `M` или `m`. Аргументы читаются шагами по
арности команды: `M/L/T` — 2, `H/V` — 1, `C` — 6, `S/Q` — 4, `A` — 7, `Z` — 0; лишний
неполный шаг — отказ. Повторные пары аргументов — следующий шаг той же команды по спеке SVG
(`M2 2 20 2 20 20` = `M` + два неявных `L`), и первый `M` при этом остаётся стартом субпути,
к которому возвращает `Z`. У дуги `A` флаги `large-arc` и `sweep` — строго `0` или `1`
(иное значение по спеке делает путь нерисуемым), радиусы — неотрицательные. Команд в одной
строке — **не больше 24**. Это не безопасность, а отсев мусора: значок из сорока команд
в 16 px превращается в кляксу.

**(4) Габарит: фактические точки, а не каждое число.** В `[-4, 28]` обязана лежать каждая
**точка** пути — для относительных команд после применения сдвига к текущей позиции,
включая контрольные точки `C`/`S`/`Q`/`T` (у `S`/`T` — и вычисленную отражением) и адресат
дуги; радиусы `A` — свой диапазон `[0, 28]`. Дельты сами по себе не проверяются: `l6-5` —
законная запись точки внутри холста. Допуск в четыре единицы за края холста — под контрольные
точки кривых и радиусы, которые законно выходят за bbox самой линии. Всё, что дальше, — либо
ошибка масштаба (модель нарисовала в `viewBox 100`), либо попытка раздуть документ; и то
и другое `<svg>` обрежет по вьюпорту, дав молчаливо пустой значок. Лучше отбросить кандидата
и показать соседний.

Это не ослабление проверки, а её перенос на то, что действительно рисуется. В одну сторону
правило мягче (отрицательные дельты проходят), в другую — **строже прежнего**: накопление
сдвигов старое правило не ловило вовсе — `M0 0 l9 9 l9 9 l9 9 l9 9` состоит из чисел внутри
`[-4, 28]`, а заканчивается в точке 36 далеко за холстом. Теперь такой путь отбрасывается.

**Лимиты объёма.** Строк `d` на значок — **1–12** (было 1–4), каждая ≤ 256 символов,
суммарно ≤ 768. Сверх лимита — не «обрежем хвост», а отбраковка кандидата: это не забытое
поле, а не тот ответ. Порог 12 взят по верхней границе живой выборки; общий вес рисунка
по-прежнему держат 256/768, и они не изменились — потолок документа тот же, что был,
изменилось только то, как этот вес разрешено разложить по путям.

**Что сохраняется как защита от мусорных путей.** Пересмотр не тронул ни одного барьера,
на котором держится инвариант §11.1:

| Барьер | Что режет |
|---|---|
| Алфавит (1) | `<`, `>`, `"`, `'`, `&`, буквы разметки, `url(`, `#` — любой символ, из которого собирается тег или ссылка |
| Запрет экспоненты (1) | координата в миллион двумя символами |
| Форма числа (2) | литерал ≥ 100 по модулю и «хвосты» произвольной длины |
| Габарит точек (4) | ошибку масштаба и уход за вьюпорт, включая накопление дельт |
| ≤ 24 команды, ≤ 256/путь, ≤ 768 суммарно, ≤ 12 путей | раздувание документа и кляксу |
| `GlyphSvg.Build` через `XmlWriter` (§4) | второй пояс: даже при баге валидатора значение уедет экранированным атрибутом |
| Повторная валидация в `icon/select` (§8) | клиент как недоверенный источник — тем же валидатором, на входе в стор |

Провал любой проверки даёт код причины (`path-char:*`, `path-number:*`, `path-start:*`,
`path-arity:*`, `path-coord:{значение}{граница}`, `path-radius:*`, `path-arc-flag:*`,
`path-length:*`, `path-total:*`, `path-count:*`, `path-empty`) — он уходит в лог отказа
вместе с именем проекта.

Порог годности ответа — **один** кандидат. У фона порог был восемь фигур из четырнадцати
(полупустой тайл выглядит браком); здесь брака от малого числа не бывает: один хороший
значок лучше, чем инициалы, а выбор из четырёх — комфорт, а не условие.

#### 3.5. Что этой ревизией отменено в §2.2

Правки вне §3 идут отдельными задачами волны; чтобы читатель не пользовался устаревшим
абзацем, отменённое перечислено явно (приём §5.5):

- **Строка таблицы** «`glyphs[].paths` — 1–4 строки» читается как **1–12 строк**; ограничения
  «каждая ≤ 256 символов, суммарно ≤ 768» остаются в силе.
- **Абзац под примером вида 2** («пути записаны абсолютными командами намеренно: лимит §3.4
  распространяется на каждое число, поэтому `l6-5` валидатор отбросит») **недействителен
  целиком**: относительная запись с отрицательными дельтами валидна, пока точки после сдвига
  лежат в `[-4, 28]`. Сам пример `M6 21V9l6-5 6 5v12` валидатор пропускает.

### 4. Сборка SVG — только на сервере

Разметку значка строит **единственная функция сервера** `GlyphSvg.Build(paths)` — из
константного шаблона, через `XmlWriter`, никакой конкатенации строк:

```
<svg xmlns="http://www.w3.org/2000/svg" width="24" height="24" viewBox="0 0 24 24"
     fill="none" stroke="currentColor" stroke-width="2"
     stroke-linecap="round" stroke-linejoin="round">
  <path d="{d}"/>   <!-- 1..4 -->
</svg>
```

- `XmlWriter`, а не строка, — второй пояс: даже при баге валидатора значение уедет
  в атрибут экранированным и не породит нового тега (ADR-008 §4.2).
- Числа в шаблоне константны, но всё, что форматируется, — через
  `CultureInfo.InvariantCulture`: запятая вместо точки в русской локали ломает `d` молча,
  и на Windows-хосте это не гипотеза (ADR-008 §4.3).
- Атрибуты шаблона повторяют `ICON_PROPS` фронта. Значок обязан стоять в одном ряду
  с иконками lucide, а не выделяться толщиной линии.
- `currentColor` работает только для inline-SVG. Потребитель эндпоинта `.svg` (§8), который
  вставит файл через `<img>`, получит чёрный штрих — это его забота, а не шаблона: цвет там
  задаётся снаружи (`mask-image` + `background-color`, приём ADR-008 §7) либо принимается
  как есть. Плодить параметр `?color=` не надо: цвет проекта уже есть у клиента.

**Где разметка оказывается в браузере — и где её нет.** Расхождение с ADR-008 (там тайл
всегда файл) осознанное:

| Путь показа | Что едет | Кто строит разметку |
|---|---|---|
| Список проектов, док, меню, шапка — React | данные значка в DTO проекта (`name` **или** `paths`) | никто: `name` рисует компонент lucide из карты §5, `paths` уходят **значением атрибута** `d` через JSX |
| `GET /api/projects/{id}/icon.svg` | собранный документ | `GlyphSvg.Build` |

`dangerouslySetInnerHTML` в пути значка **запрещён** — это условие того, что React-ветка
безопасна без санитайзера: JSX экранирует значение атрибута сам, а строки разметки на
фронте не существует вовсе. Проверяется ревью и тестом бэка (§11.1), а не доверием.

Почему в DTO едут данные, а не готовый SVG: значок нужен в **каждой** строке списка проектов,
в доке и в меню. Отдельный HTTP-запрос на проект ради 300 байт — худший обмен, чем те же
300 байт в ответе, который и так отдаётся. Тайл фона (2–6 КБ, один экран) — обратный случай,
и в ADR-008 он решён обратно; противоречия нет, разный размер и разная частота.

Эндпоинт `.svg` при этом нужен: он — единственная разрешённая форма значка как самостоятельного
ресурса (иконка вкладки, вложение, будущие поверхности вне React-дерева). Без него первый же
такой потребитель начнёт собирать SVG сам, и появится вторая точка сборки.

### 5. Весь набор lucide: доступ по имени через ленивый импорт

**Ревизия 17.08.2026 (владелец).** Прежняя редакция §5 требовала рукописную карту `GLYPHS`
на ≈120 имён со статическими импортами. Она отменена: ≈120 имён — это 6% набора, и всё, чего
в них нет, уходит в ветку рисования — самую слабую в контракте. Расширять карту руками до
полутора тысяч имён нельзя (это ровно тот рукописный список, от которого §5 и уходил), а
прежний запрет динамического доступа («тащит в бандл весь набор») опирался на неверную посылку:
в `lucide-react` 1.24 это не наивный `import(\`lucide-react/${name}\`)`, а штатная карта лениво
загружаемых модулей.

**Новое правило.** Значок с именем `X` принимается сервером тогда и только тогда, когда `X` есть
в наборе **установленного** `lucide-react` — множестве `iconNames` (= ключи `dynamicIconImports`)
из подмодуля `lucide-react/dynamic`. Рукописная карта `GLYPHS` и файл
`frontend/src/lib/projectGlyphs.ts` удаляются.

#### 5.1. Показ: `DynamicIcon`, ленивый чанк на иконку

Имя рисует компонент `DynamicIcon` из `lucide-react/dynamic`: он держит карту
`имя → () => import('./icons/{имя}.mjs')` и подгружает модуль иконки по требованию.
Замеры на установленной 1.24.0 — цена решения:

| Что | Сколько |
|---|---|
| имён в наборе (`iconNames`) | **1995** (модулей иконок в пакете — 1978, часть ключей делит модуль) |
| карта имя→loader во входном чанке | 118 КБ исходника, **14 КБ gzip** |
| модуль одной иконки | ~650 байт исходника (в чанке меньше), едет по требованию и кешируется |
| файлов в `dist` | +≈2000 крошечных чанков |

14 КБ gzip за весь набор вместо 6% — обмен принят. Требования к реализации, без которых
ломается §7:

- **`fallback` обязателен и равен инициалам.** Без него `DynamicIcon` рисует `null`: пока чанк
  не приехал (и навсегда — если имя неизвестно) в строке списка будет пустое место, а §7
  запрещает пустой значок в любом состоянии. `fallback` — **компонент**, не элемент: внутри
  делается `createElement(Fallback)`.
- Неизвестное имя `DynamicIcon` печатает в `console.error` и остаётся на `fallback` —
  тихая деградация §7 работает и без белого списка. Список на сервере нужен по другой
  причине (§5.2), а не ради безопасности показа.
- Пропсы — прежние `ICON_PROPS` (`strokeWidth = 2`, round caps, `currentColor`):
  `DynamicIcon` пробрасывает их в `Icon`, значок остаётся в одном ряду с иконками интерфейса.
- В 1.24.0 у пакета **нет поля `exports`** — подпуть резолвится по файлам. Проверено:
  `import('lucide-react/dynamic')` в чистом Node падает с `ERR_MODULE_NOT_FOUND`, работает
  только полное имя файла — `lucide-react/dynamic.mjs` (CJS-двойник `dynamic.js` отдаёт те же
  три экспорта). В коде фронта путь проходит через резолвер Vite и может стерпеть короткую
  форму, но в скриптах и тестах, которые исполняет Node напрямую (§5.2, §5.4), писать
  **`lucide-react/dynamic.mjs`**.
- Ветка `paths` (§3, §4) не меняется: она закрывает то, чего в наборе нет.

Не выбрано: разворачивать имя в `d` на сервере (генерируемая карта имя→геометрия, один путь
показа, ноль веса в бандле). 716 из 1978 иконок содержат не-`path` элементы (`circle`, `rect`,
`line`, `ellipse`, `polyline`, `polygon`), то есть шаблон §4 и валидатор пришлось бы расширять
на весь этот алфавит — дороже 14 КБ.

#### 5.2. Список имён на сервере — производная пакета, а не рукопись

Серверу множество имён всё равно нужно: кандидат с выдуманным именем обязан отсеиваться **до**
грида (плитка с инициалами среди четырёх кандидатов — брак выбора, а не фолбэк) и на входе
в стор (§11.3). `node_modules` у бэкенда в рантайме нет — значит нужна копия, но копия
**генерируемая**:

- Артефакт: `backend/ClaudeHomeServer/Services/ProjectIcons/lucide-icon-names.g.txt` —
  по имени на строку, отсортировано, `EmbeddedResource`. Первая строка — шапка
  «сгенерировано, руками не править, генератор — `frontend/scripts/gen-glyph-names.mjs`».
- `LucideGlyphs.All` — ленивый `HashSet<string>` (`StringComparer.Ordinal`) из этого ресурса.
  `LucideGlyphs.Domains` и `LucideGlyphs.Names` **удаляются**: доменные блоки существовали
  только ради промпта, а список в промпт больше не уходит (§5.3).
- Генератор: `frontend/scripts/gen-glyph-names.mjs`, запуск `node scripts/gen-glyph-names.mjs`
  из `frontend/` (место и приём — как у существующего `scripts/gen-icons.cjs`). Берёт
  `iconNames` из `lucide-react/dynamic.mjs`, пишет артефакт. Запускается **только** при
  апгрейде `lucide-react`.

Пополнение и удаление имени перестают быть «коммитом в два места»: состав набора меняется
исключительно вместе с версией пакета. Переименование иконки в новом lucide (в v1 их было
много: `chart-line` вместо `line-chart`, `house` вместо `home`) означает, что имя выпало из
набора → §7: такой значок тихо деградирует в инициалы, стор задним числом не чинится.

#### 5.3. В промпт список больше не уходит

1995 имён — это ≈26 КБ (~8k токенов) в каждом запросе, и это шум: список такого размера
модель не читает, а ищет в нём похожее, теряя смысл названия проекта. Поэтому имя модель
называет **по своему знанию lucide**, а членство проверяет сервер; в промпте остаётся десяток
имён-образцов (формат kebab-case, точность до символа) и предупреждение, что негодное имя
отбрасывается — значит лучше назвать заведомо существующую иконку, чем угадывать. Точная
формулировка промпта — дело реализации (§2.3); здесь фиксируется только источник имён.

Прямое следствие для §9: задача места модели изменилась — «выбрать из предъявленных 120 строк»
стало «знать набор из ~2000 имён», и уровень поднимается до `Strong`.

#### 5.4. Сверяемость: что и чем теперь сторожится

Предмет сверки меняется вместе с решением. Рукописных списков больше нет, поэтому сверять надо
не «фронт против бэка», а **коммитируемую копию против установленного пакета** — единственное
расхождение, которое теперь возможно (забыли перегенерировать после `npm i lucide-react@…`).
Симптом прежний и такой же тихий: сервер принимает имя, которого фронт не нарисует, либо
отбрасывает годное — значок молча не появляется, в логах ничего.

Сторожей два, по числу мест, где это может проскочить:

| Сторож | Где | Что делает | Когда сработает |
|---|---|---|---|
| `LucideGlyphWhitelistGuardTests` (остаётся, меняется предмет) | backend, xunit | ищет снизу вверх `frontend/node_modules/lucide-react/dist/esm/dynamicIconImports.mjs` (тем же `FindRepoFile`), вынимает ключи регуляркой `"([a-z][a-z0-9-]*)":\s*\(\)\s*=>` и сверяет на равенство с `LucideGlyphs.All` | у разработчика — сразу после апгрейда пакета: `dotnet test` красный |
| зеркальный vitest-тест (новый) | frontend, `npm test` — блокирующий шаг фронтового job CI | импортирует `iconNames` из `lucide-react/dynamic.mjs`, читает через `fs` тот же `lucide-icon-names.g.txt` бэка и сверяет множества | в PR и в master |

- Бэковый job CI ставит только .NET, `node_modules` там нет — это состояние бэковый сторож
  **пропускает явно**: `[SkippableFact]` + `Skip.If(…)` (пакет `Xunit.SkippableFact` в тестах
  уже подключён) с текстом «`lucide-react` не установлен — дрейф ловит vitest-сторож фронта».
  Молчаливого «зелёного без проверки» не возникает: в CI ту же сверку делает второй сторож,
  и он блокирующий. Один тест два места не покрывает: апгрейд делают на машине разработчика,
  а в master пускает CI.
- Оба сторожа читают **ключи карты loader'ов**, а не имена файлов в `icons/`: рисуется ровно
  то, что есть в карте, и валидировать надо то же множество.
- Регулярка — со `*`, а не с `+`, после первого символа. Проверено на 1.24.0: строгая версия
  `[a-z][a-z0-9-]+` вынимает 1994 ключа из 1995, теряя односимвольное имя `x` — сторож стал бы
  красным навсегда на пустом месте.

#### 5.5. Что этой ревизией отменено в остальном тексте ADR

Правки вне §5/§9 идут отдельными задачами волны; чтобы читатель не пользовался устаревшим
абзацем, отменённое перечислено явно:

- **§2.1** — «в промпт входит весь белый список §5 (≈120 имён, ~1.5 КБ)». Не входит: §5.3.
- **§2.2**, форма имени: `^[a-z][a-z0-9-]{1,39}$` требует минимум двух символов и отбраковывает
  существующую иконку `x`. На полном наборе читать как **`^[a-z][a-z0-9-]{0,39}$`**; членство
  в наборе (§5.2) остаётся главной проверкой, форма — только дешёвый предфильтр.
- **§11.5** — «белый список — производная карты фронта»; теперь производная **установленного
  пакета** (§5.2), равенство держат два сторожа (§5.4).
- **Альтернативы**, строка «Динамический импорт lucide по имени → убивает tree-shaking».
  Отклонён был наивный `import(\`lucide-react/${name}\`)`; штатный `DynamicIcon` tree-shaking
  не ломает и стоит 14 КБ gzip (§5.1).
- **Последствия**, «бандл фронта растёт на ≈120 иконок lucide» → растёт на карту loader'ов
  (14 КБ gzip), сами иконки в бандл не попадают вовсе.
- **«Что проверять»**, пункт про сторожа §5 → сверка идёт с установленным пакетом (§5.4).

### 6. Хранение: внутри `ProjectIcon`, в `data/projects.json`

```csharp
// Значение Image удалено; НОМЕРА ОСТАВШИХСЯ ЗАКРЕПЛЕНЫ ЯВНО, 1 выведен из обращения
public enum ProjectIconKind { Initials = 0, Glyph = 2 }

public sealed class ProjectIcon
{
    public ProjectIconKind Kind { get; set; } = ProjectIconKind.Initials;
    // Ключ цвета из палитры AGENT_COLORS; null — цвет из хеша id (без изменений)
    public string? Color { get; set; }
    // Значок; null — не подбирался. Заполнен ⇔ Kind может быть Glyph
    public ProjectGlyph? Glyph { get; set; }
    // УДАЛЕНЫ: ImageFile, OriginalFile, Crop
}

public sealed class ProjectGlyph
{
    // Имя из белого списка §5 — ВЗАИМОИСКЛЮЧИТЕЛЬНО с Paths
    public string? Name { get; set; }
    // 1–4 провалидированных строки d (§3)
    public List<string>? Paths { get; set; }
    public DateTime SetAt { get; set; }
}
```

**Почему номера enum заданы явно.** `ProjectManager.Load` десериализует `projects.json`
с единственной опцией `PropertyNameCaseInsensitive` — **`JsonStringEnumConverter` не подключён,
enum лежит на диске числом.** В старом сторе `Image == 1`. Если объявить `{ Initials, Glyph }`,
то `Glyph` получит номер 1 и каждый проект со старой картинкой молча станет «значковым»
с пустым `Glyph` — исключения не будет, будет тихая порча смысла. Явные `Initials = 0`,
`Glyph = 2` выводят 1 из обращения: старая запись читается как неизвестное значение и ведёт
себя предсказуемо (§7 — инициалы), а не притворяется чужим состоянием. Ту же дисциплину
обязан соблюдать любой, кто позже добавит сюда новое значение.

Отдельного файла и папки нет: `data/project-icons/` после миграции удаляется целиком.
Худший случай значка — 4 × 256 = 1 КБ, типичный — 150–300 байт; на 40 проектах это единицы
килобайт в сторе и в `GET /api/projects` (ср. 150–250 КБ, из-за которых тайл фона вынесен
в файл, — ADR-008 §6). Ради такого объёма заводить файловое хранилище, каскады удаления
и второй эндпоинт отдачи не стоит: значок — это данные записи, а не ассет.

Побочная выгода: вместе с файлами исчезает вся поверхность `SafeJoin` для иконок —
кандидаты, оригиналы, кроп, склейка пути из имени файла.

**Сверка с правилом «новое хранилище → сверься с бэкапом» (CLAUDE.md):**

1. *Кеш, лог, временный файл?* Нет — поле записи проекта. Едет в архив вместе с
   `projects.json`; исключений в `BackupPaths.ShouldInclude` не нужно.
2. *Секрет?* Нет. `BackupPaths.SecretFileNames` не трогаем.
3. *Хранилище вне `data/`?* Нет. `BackupCore.CopyDataTo` не трогаем.
4. *Не-JSON стор?* Нет, часть существующего JSON-стора. Своего способа снимка не требуется.
5. *Критичный стор?* `projects.json` уже проверяется `BackupValidation.Validate` — новых
   правил не добавляем.
6. *Формат стора?* **Ломается.** → `BackupSchema.Version` **7 → 8**, строкой комментария
   в [BackupSchema.cs](../../backend/ClaudeHomeServer/Services/Backup/BackupSchema.cs):

   > `8 — из ProjectIcon удалены ImageFile/OriginalFile/Crop и значение enum Image, добавлен Glyph`

   Инкремент обязателен, и это не формальность. Механика порчи здесь тише, чем у enum'ов
   персон (там строковый конвертер и падение десериализации): `ProjectIconKind` лежит числом,
   поэтому старый бинарь, восстановивший новый архив, прочитает `Kind = 2` как неизвестное
   значение, при первом же `Save` запишет запись **без** `Glyph` (поля он не знает) и
   значок молча исчезнет у всех проектов сразу. Ошибки при этом не будет ни одной —
   ровно поэтому гейт `BackupRestore` («архив новее кода») обязан сработать раньше.
   Прецедент того же рода — 5→6, удаление `Project.McpServersOff`.

### 7. Фолбэк — всегда инициалы, всегда молча

Инициалы + цвет проекта уже есть, работают без сети и без модели. Любой сбой оставляет
`Kind = Initials`, пользователь видит то же, что видел до фичи:

| Ситуация | Поведение |
|---|---|
| Место модели не настроено / провайдер недоступен / таймаут | значок не меняется; текст «Не удалось подобрать значок — оставили инициалы» (спека) |
| Ответ не разобрался как JSON | то же |
| Ни одного годного кандидата после §2.2 + §3 | то же |
| Кандидатов меньше четырёх | показываем сколько есть — это не ошибка |
| `Kind == Glyph`, но `Glyph == null` (руками правленный стор) | фронт рисует инициалы; сервер стор не чинит |
| Старая запись до миграции (`Kind = 1`, бывший `Image`) | значение неизвестно ни одному имени → фронт рисует инициалы (условие показа значка — строго `kind === 'glyph'`, а не «не initials») |
| `Glyph.Name` выпал из белого списка (иконку убрали из карты) | фронт рисует инициалы (§5) |
| `GET icon.svg` при `Kind != Glyph` или при `Name`-значке | 404: файл — форма только для `Paths`-значка |

Последняя строка требует внимания на фронте: `Kind` живёт в **двух представлениях** —
числом в `projects.json` (конвертера у `ProjectManager` нет) и строкой camelCase в HTTP-DTO
(`AddJsonOptions` + `JsonStringEnumConverter` в `Program.cs`). Неизвестное числовое значение
конвертер отдаст наружу как число, поэтому проверка показа обязана быть положительной
(`kind === 'glyph'`), а не отрицательной (`kind !== 'initials'`) — иначе старая запись
провалится в ветку значка, которого нет.

Пустого места на экране не бывает ни в одном состоянии. Это же означает, что фича не имеет
«переходного» состояния и не нуждается в фич-флаге: до подбора значка проект просто выглядит
как сегодня.

### 8. API

| Метод | Назначение | Гейт |
|---|---|---|
| `POST /api/projects/{id}/icon/suggest` | 4 кандидата от модели; **стор не меняется** | владелец |
| `POST /api/projects/icon/suggest-preview` | то же для ещё не созданного проекта (по имени) | авторизован |
| `POST /api/projects/{id}/icon/select` | принять значок: `Kind = Glyph`, `Glyph = …` | владелец |
| `POST /api/projects/{id}/icon/mode` | `initials` \| `glyph` — вернуться на буквы и обратно | владелец |
| `GET /api/projects/{id}/icon.svg?access_token=…&v={hash}` | собранный SVG (`Paths`-значок) | владелец |

- Владение — по конвенции контроллера: `p is null || p.OwnerId != UserId → NotFound()`.
- **`select` валидирует тело заново, целиком по §2.2+§3.** Кандидаты нигде не хранятся между
  вызовами, и клиент присылает значок телом — то есть источник значения не гарантирован.
  Инвариант формулируется так: **валидация стоит на входе в стор, а не на выходе модели.**
  Это и убирает необходимость во временном хранилище кандидатов.
- `v={hash}` — первые 8 hex от SHA-256 содержимого значка, поле DTO. Даёт cache-busting при
  смене значка; ответ — `Content-Type: image/svg+xml`, `X-Content-Type-Options: nosniff`,
  `Content-Security-Policy: default-src 'none'`, `Cache-Control: private, max-age=604800, immutable`.
- `access_token` в query — приём, уже использованный у `GET {id}/icon` и тайла фона.

**Удаляются** вместе с растровыми иконками: `icon/generate`, `icon/generate-preview`,
`icon/candidate/{file}`, `icon/set-image`, `icon/upload`, `icon/recrop`, `icon/original`,
`GET {id}/icon`, `icon/caps`, место `ImagePlaces.ProjectIcon` (секция «Картинки» остаётся
с одним местом «Аватар персоны»), `ImageBackfillKinds.ProjectIcon` и его очередь для иконок.

### 9. Место в каталоге моделей

```csharp
public const string ProjectIcon = "project-icon";
new(ProjectIcon, "Значок проекта", "Проекты", CheapProfile.Large,
    DefaultLocal: false, Tier: ModelTier.Strong)
```

**`Tier: Strong`** (ревизия 17.08.2026; было `Medium`). Прежнее обоснование — «подобрать имя
из готового списка проще, чем сочинить дудл» — держалось на том, что список ехал в промпт:
задача была на чтение 120 предъявленных строк. С §5.3 список в промпт не уходит, и место
стало другим по существу:

1. **Знание конкретной библиотеки.** Модель обязана назвать имя из ~2000 kebab-case имён
   lucide v1 без подсказки и с точностью до символа, причём часть имён в v1 переименована
   (`chart-line`, `house`, `building-2`). На таком вопросе слабая модель отвечает правдоподобным
   (`piggybank`, `bar-chart`, `home`) — сервер отбросит все шесть кандидатов, и пользователь
   получит честный отказ вместо значка (§7). Цена ошибки здесь — не «значок хуже», а «значка нет».
2. **Геометрия во второй ветке.** Нарисовать узнаваемую вещь двумя десятками чисел на сетке
   24 — не текстовая задача. В прогоне QA 17.08 на Medium **все** вернувшиеся кандидаты были
   именами, ни одного нарисованного: ветка `paths` фактически не работала.
3. **Цена одной ошибки высока.** Значок один на проект, живёт месяцами и попадает в каждый
   экран — список проектов, шапку, док, меню. Это не поток однотипных фоновых ответов, где
   слабая модель отыгрывает объёмом; промах виден постоянно и правится только вторым подбором
   вручную. (Смысловую точность Medium по прогону 17.08 судить нельзя: подсказка владельца
   до модели не доезжала из-за отдельного дефекта `prompt ≠ Hint`, и выдача строилась по
   одному названию проекта.)

Цена сильной модели здесь мала: место фоновое и редкое — один вызов на нажатие «Подобрать
значок» плюс разовая миграция, а не запрос на каждый ход. Админ может увести место на любую
модель — строка в диалоге «Поставщики моделей» появится сама.

- **`CheapProfile.Large` сохраняется, но по другой причине.** Прежняя («в промпт уходит весь
  белый список») с §5.3 недействительна: вход теперь ~0.5 КБ. Large держится на **выводе**:
  шесть кандидатов, каждый до четырёх строк `d` по 256 символов, — до ~6 КБ JSON плюс
  рассуждение сильной модели. На `Small`/`Text` потолок вывода обрежет ответ на полуслове,
  `ExtractJsonObject` вернёт `bad-json` — симптом, неотличимый от таймаута (ADR-008 §8).
- `DefaultLocal: false` — без изменений: рисование SVG не текстовая задача, локальная модель
  даёт кашу из линий. Заодно убирает локаль из страховочного шага цепочки `CheapTextRunner`:
  «сойдёт за успех» здесь дороже честного отказа на инициалы.
- Вызов — `RunAsync(ProjectIcon, prompt, ownerId: project.OwnerId)`: слот резолвится по
  владельцу проекта, а не по тому, кто нажал кнопку.

#### 9.1. Лимит ожидания места — **180 с, собственный** (решение 17.08.2026)

Подъём тира до `Strong` (§9) обнажил то, чего на `Medium` не было видно: **место не
укладывалось во время**. Значков не появлялось не потому, что модель ошибалась именем,
а потому, что ответа никто не дожидался.

Лимитов на пути подбора **два**, и работает всегда меньший:

```
 [браузер] fetch --------- 30 с ---------X  (FETCH_TIMEOUT_MS, оверрайда
     |                                       у suggestIcon/-Preview не было)
     v
 [сервер]  CheapTextRunner ------------------------ 300 с ---X
                                (потолок профиля Large, общий на все Large-места)
     v
 [модель]  Strong отвечает  |----- 52 .. 126 с -----|   (прод 17.08)
```

Отсюда обе беды, и они разнонаправленные:

1. **30 с клиента.** В этот лимит не укладывался **ни один** наблюдаемый успешный ответ
   (нижняя граница 52 с — почти вдвое больше). Браузер рвал HTTP, сервер получал
   `RequestAborted`, пользователь видел «Не удалось подобрать значок — оставили инициалы».
   Симптом неотличим от честного отказа модели (§7), и ровно поэтому дефект прожил
   незамеченным: фолбэк делает своё дело молча.
2. **300 с профиля.** Обратная крайность: *зависший* вызов держался пять минут. Миграция
   (§10) идёт не больше 2 одновременно на инстанс и 1 на владельца — при такой ширине
   очереди один залипший вызов останавливает прогон на полдня (наблюдалось на проде 17.08:
   «Узбекистан», «Общие вопросы», отказ `no-model`).

**Принято: у места `project-icon` собственный потолок ожидания облачного шага —
`CloudTimeoutMs: 180_000`.** 180 с покрывают верх наблюдаемого диапазона (126 с) с запасом
на хвост и на тихую ротацию подписки внутри хода, и втрое сокращают цену зависшего вызова
против профильных 300 с.

- Лимит **пер-местный, а не общий**: у `LocalAction` появилось необязательное поле
  `CloudTimeoutMs`, `null` = потолок профиля. Профиль `Large` не тронут — соседние
  Large-места (фон проекта, «Что нового», паспорта) остаются на 300 с. Это и есть смысл
  решения: **лимит поднят/опущен ровно для подбора значка, а не для LLM-слоя целиком.**
- **Единственная точка склейки** — `LocalActionRouter.CloudTimeoutMsFor(actionKey)`
  (каталог → профиль); `CheapTextRunner` берёт лимит только оттуда и своей арифметики
  не имеет. Дублировать эту склейку нельзя — по той же причине, по которой её нельзя
  дублировать у `UserModelTierResolver.ModelFor` (CLAUDE.md).
- **Инвариант двух лимитов: клиентский ≥ серверного.** Решает «время вышло» ровно один
  участник — серверный лимит места; клиент, который рвёт раньше, превращает диагностируемый
  отказ в молчаливый фолбэк. Поэтому вызовы `suggestIcon` / `suggestIconPreview` обязаны
  нести явный `timeoutMs` не меньше 180 с, а не жить на общем дефолте фронта.
- **Отказ по времени обязан называть цифры.** `LlmTimeoutException` несёт применённый лимит
  и фактическую длительность («лимит 180 с, ждали 179.5 с»); базовая подстрока «не ответил
  за отведённое время» сохранена — по ней `ChangelogService.DescribeFailure` отличает
  таймаут от сбоя CLI. Отмена **снаружи** (тот самый `RequestAborted`) названа отдельно:
  без этого «лимит 180 с, ждали 30 с» читается как ложный таймаут сервера, и искать
  начинают не там.
- **Не выбрано: поднять `CloudTimeoutMs` у профиля `Large`.** Дешевле по коду, дороже по
  смыслу — общий потолок стал бы заложником самого медленного места, а зависшие вызовы
  подорожали бы у всех Large-мест сразу.

**Модель слота.** Более быстрая сильная модель на этом решении **не выбиралась**: диапазон
52–126 с признан приемлемым для фонового места (одно нажатие кнопки, редко), и решение
осталось прежним — слот `Strong`, конкретную модель назначает админ в диалоге «Поставщики
моделей». Смена модели ADR не меняет: она меняет только то, к какому исполнителю
применяется критерий ниже. Порядок пересмотра при провале критерия — **сначала модель
места, потом лимит**: лимит уже покрывает наблюдаемый диапазон с запасом, и его дальнейший
рост лечит симптом, возвращая пятиминутные зависания §10.

**Критерий приёмки места (живая проверка):** **не реже 9 успехов из 10** прогонов на
**разных** названиях проектов и разных пожеланиях. Успех = грид получил хотя бы одного
годного кандидата; отказ по времени (`no-model` из-за таймаута — на любой стороне) в
успехи не засчитывается ни при каких условиях. Это критерий **работоспособности**, а не
вкуса: продуктовый «8 из 10 подобранных значков владелец оставляет как есть» (спека) —
про качество и живёт отдельно.

### 10. Миграция

Разовый прогон по всем проектам: каждому подбирается значок, `data/project-icons/**`
удаляется. Порядок обязателен:

1. **Снять бэкап каталога `data` штатным механизмом.** Растровые иконки после прогона
   не восстанавливаются ничем, кроме архива.
2. Прогон (фоновый, темп — как у фона: не больше 2 одновременно на инстанс, 1 на владельца:
   залп по всем проектам упрётся в rate limit, и половина получит отказ там, где виновата очередь).
3. Проект, которому значок не подобрался, остаётся на инициалах и повторно **не** долбится —
   у пользователя есть кнопка «Подобрать значок».

Состояние прогона живёт в самой записи (`Icon.Glyph == null` — кандидат), отдельного стора
«что уже прогнали» нет: второй запуск — no-op. Это тот же приём идемпотентности, что
в ADR-008 §10, и по той же причине — отдельный маркер был бы вторым источником истины.

### 11. Инварианты

1. **Ни байта разметки от модели.** От модели в системе живут только имя из белого списка §5
   и строки `d`, прошедшие §3. Разметку строит `GlyphSvg.Build` через `XmlWriter`; на фронте
   строки разметки не существует, `d` уходит значением атрибута.
2. **Фолбэк на инициалы, всегда молча.** Любой сбой — модели нет, JSON битый, кандидатов
   ноль, имя выпало из карты — оставляет `Kind = Initials`. Пустого значка не бывает (§7).
3. **Валидация на входе в стор, не на выходе модели.** `select` проверяет тело целиком, тем
   же валидатором: клиент — такой же недоверенный источник, как модель.
4. **Взаимоисключительность вида.** У `ProjectGlyph` заполнено ровно одно из `Name` / `Paths`.
   Пара «имя + пути» в сторе невозможна — валидатор такой кандидат отбрасывает.
5. **Белый список — производная карты фронта.** `LucideGlyphs.All` равен ключам `GLYPHS`;
   равенство держит тест-сторож. Имени вне карты сервер не принимает никогда.
6. **Цвет — прежняя единственная точка истины.** `Icon.Color` (ключ `AGENT_COLORS`), значок
   красится `currentColor` на клиенте. Отдельного «цвета значка» нет; смена темы и цвета
   проекта перегенерации не требует.
7. **Права владельца.** Подбор, выбор, смена режима и отдача `.svg` — только `OwnerId == UserId`;
   чужой проект — 404.
8. **Файлов у иконки больше нет.** Ни ассетов, ни кандидатов, ни оригиналов; каскад удаления
   проекта для иконок не нужен, поверхность `SafeJoin` для них исчезает.
9. **Формат стора сломан осознанно.** `BackupSchema.Version` 7 → 8 (§6.6); архив, снятый
   новой версией, обязан отвергаться старым кодом с внятной ошибкой.
10. **Значок — только штрих.** В собранном документе нет `fill` (кроме `none` шаблона),
    `opacity`, `style`, `text`, градиентов и ссылок наружу; толщина и скругления — из шаблона,
    совпадают с `ICON_PROPS`.

## Альтернативы, которые отклонены

| Вариант | Почему нет |
|---|---|
| Сырой SVG от модели + белый список тегов и атрибутов | Fail-open (ADR-008 §1). Значок ещё и попадает в DOM десятками штук — в списке проектов, доке, меню |
| Только имена lucide, без нарисованных значков | Набор конечен: «Финансы семьи» получит `wallet`, но специфический проект — общий `folder`. Рисованный путь стоит одного валидатора и закрывает хвост |
| Только рисование, без набора lucide | Из восьми нарисованных на тесте два вышли неузнаваемо. Готовая иконка узнаётся всегда — и это ещё и ноль байт от модели в SVG |
| Динамический импорт lucide по имени | Убивает tree-shaking: в бандл едет весь набор. Плюс имя перестаёт проверяться компилятором |
| Хранить собранный SVG строкой в `ProjectIcon` | Разметка в сторе = разметка в бэкапе и в каждом `GET /api/projects`; смена шаблона (толщина линии, viewBox) потребовала бы миграции стора вместо правки константы |
| Отдельный файл на значок, как тайл фона | 300 байт не стоят папки, каскада удаления и HTTP-запроса на каждый проект в списке. Обратный случай ADR-008 §6, и решён обратно осознанно |
| Оставить загрузку своего логотипа файлом | Отрезано владельцем 16.08.2026: тянет за собой кроп, ассеты, `SafeJoin` и растр, ради одного сценария (фирменный логотип) |
| Фич-флаг на фичу | Нечего гейтить: старый механизм не сосуществует с новым, а состояние «значка нет» = сегодняшние инициалы |
| Временное хранилище кандидатов + выбор по индексу | Стор ради полутора минут жизни данных. Повторная валидация в `select` дешевле и надёжнее (§8) |

## Последствия

- В диалоге «Поставщики моделей» появляется строка **«Значок проекта»**; из секции
  «Картинки» вкладки «Применение» исчезает место «Иконка проекта» — там остаётся
  «Аватар персоны».
- `BackupSchema.Version` = 8: архивы, снятые после релиза, старым бинарём не восстановятся —
  это и есть цель инкремента.
- Каталог `data/project-icons/` исчезает; размер архива уменьшается на вес всех растров.
- Значок появляется мгновенно и бесплатно относительно внешних сервисов: fal/glif из пути
  иконки уходят полностью, вместе с очередью догона.
- Бандл фронта растёт на ≈120 иконок lucide (единицы килобайт после tree-shaking) —
  цена статической карты §5.
- Риск, который ADR **не закрывает**: у похожих проектов значки совпадут (два проекта про
  финансы получат один `chart-line`, различать будет цвет). Лечится вторым кругом подбора
  «возьми другой, этот занят рядом»; заранее не делаем — сначала посмотрим, частое ли это.

## Что проверять при реализации

- Тест инварианта §11.1: `d` со `<`, `"`, `script`, экспонентой, координатой `1e6`, числом
  `999` — все отбиты валидатором; при искусственном обходе валидатора собранный `XmlWriter`
  документ всё равно не содержит нового тега.
- Тест взаимоисключительности: кандидат с `name` **и** `paths` отбрасывается; кандидат
  с именем вне белого списка отбрасывается; ответ из одних негодных кандидатов = отказ,
  `Kind` остаётся `Initials`.
- Тест сторожа §5: `LucideGlyphs.All` совпадает с ключами `GLYPHS` из `projectGlyphs.ts`.
- Тест повторной валидации: `POST icon/select` с телом, минующим модель (сырой `d` с `<`),
  получает 400 и стор не меняет.
- Тест лимита (§9.1): у места `project-icon` `CloudTimeoutMs == 180_000`, вызов уходит
  именно с ним, а соседнее Large-место (`project-background`) — с потолком профиля;
  сообщение таймаута содержит и «не ответил за отведённое время», и применённый лимит
  с фактической длительностью.
- Живая проверка места (§9.1): 10 подборов на разных названиях и пожеланиях, зачёт —
  не реже 9 успехов; отказ по времени в успехи не идёт.
- Тест локали: сборка под `ru-RU` даёт `d` с точками, а не запятыми.
- Тест прав: не-владелец получает 404 на `suggest`, `select`, `mode`, `icon.svg`.
- Тест совместимости стора: `projects.json` со старой записью (`"Kind": 1`, `"ImageFile": …`)
  читается новым кодом без исключения, лишние поля игнорируются, а проект показывается
  на инициалах — то есть номер 1 не превращается в `Glyph` (§6, явные номера enum).
- `BackupSchema.Version == 8`, и `BackupRestore` отвергает архив с `SchemaVersion = 8`
  на коде версии 7 с внятной ошибкой.
