# Детский режим: приёмка по 360 px — чек-лист и план стенда

Подготовка к приёмке фичи «Детский режим» (ADR-041, волны 1–4: уроки, студия, кабинет родителя)
на мобильной ширине **360 px**. Документ — подготовка: после гейта приёмка идёт по этому списку,
а не с нуля.

**Границы:** финальная приёмка на момент подготовки **не проводилась** — код меняется
(правка запретов персоны, снятие стора). Ниже нет ни одного «пройдено/упало»: только пункты,
чем мерить, и ожидаемый результат.

Ветка: `feat/kids-w4`. Дерево: `/home/an/Sources/ClaudeCodeServer-kids-w4`.

### 2.6 Отказ ребёнку в поиске по базе знаний чужого проекта

Бэк: граница — в одной точке `backend/ClaudeHomeServer/Controllers/ChildSubjectAccess.cs` (вынесена из
контроллеров в Х-W4-47): `IsChild` `:29`, `IsOwnSubjectProject` `:36`, отказ `NotOwnSubject` `:42`,

`Search` `:100-101` (стоит **до** ветки пустого `q` на `:103`).
Отказ — **403**, тело `{ code: "not_child_subject", message: "Знания доступны только в твоём предмете." }`
(сообщение собирается по названию области: `$"{what} доступны…"`, `what = "Знания"`, `ChildSubjectAccess.cs:43`).

**Уровень проверки — API.** В UI чужой проект ребёнку недостижим (§2.7: список `GET /api/projects`
— только свои, чужой по прямому запросу — 404, `ProjectsController.cs:168-177, 190-191`), поэтому
панель «Знания» чужого проекта открыться не может. Тот же 404 — и для обычного проекта ребёнка
в UI; ниже он меряется прямым вызовом ручки БЗ.

**На стенде чужой проект — обычный (не предметный).** Членство проекта-предмета пишет только
синхронизация профиля (Б14b, решение 62): `SyncSubjectProjectMembersAsync` зовётся только из
`ChildCuratorSync.cs:72,108`. Ручка `POST /api/projects/{id}/members` по проекту-предмету: для

`ProjectMembershipService.cs:54`; сам отказ формирует `SubjectProjectRefusal` `:366-368`, проверка `:72-73`;
проверка стоит после `RequireOwner`, `:63-64`), для **постороннего** (в том числе админа, не владеющего
чужим предметом) — 404 от `[ProjectScope]` (`ProjectMembersController.cs:16-17`,
`ProjectScopeAttribute.cs:114`), до сервиса он не доходит; для **куратора-участника** (не владельца)
— **403** от `RequireOwner` (`ProjectMembershipService.cs:66-70`): он отсекается раньше проверки
предмета. Три отказа различаются по статусу и телу ответа: **409** — `code = "managed_by_child_profile"`
(`ProjectMembershipService.cs:54`); **404** — `{ error: "Не найдено", code: "project_scope" }`
(`ProjectScopeAttribute.cs:114`, `:135-136`); **403** — `{ error: "Участниками проекта управляет только

## 4. Что обязательно требует живого стенда с данными

1. **Реальная раскладка 360 px** — юнит-тесты меряют классы стилей и счётчики, но не живой
   `scrollWidth` документа, не перекрытие двух шторок и не тач-размер в браузере.
2. **Стек двух модалок** — два портала в `document.body`, порядок отрисовки и перехват клика
   существуют только в живом DOM.
3. **Двойной тап «Новый урок»** — гонка двух запросов на живом бэке; юнит-тест мокает ответ.
   Серверной идемпотентности здесь нет — защита только клиентская (`ProjectRail.tsx:737`);
   поэтому спек мерит и обратное: два последовательных POST создают два чата (§2.5).
4. **Плашка активного предмета после перестановки** — зависит от `getBoundingClientRect`
   реального значка в доке.
5. **Отказ по БЗ чужого проекта** — нужен второй проект (**обычный, не предметный** — чужой
   предмет на стенде закрыт, см. §2.6), второй участник и включённый флаг
   `shared-projects` (живой сценарий доступа к чужому проекту).
6. **Гейт И1 в UI** — снимок `childSurface` приходит из живого `/api/auth/me`; в юнит-тесте он подставлен.
7. **Живой ход урока** — репетитор отвечает (нужен фейковый движок или живой провайдер),
   иначе шапка урока и лента проверяются на пустом чате.

1. Создать ребёнка (нужен **container**: галка и окно настроек доступны только пользователям

   токеном **админа** (флаг per-user; прячет только галку и кнопку «Настроить занятия» —

3. Профиль ребёнка (одна ручка записи, `PUT /api/users/{childId}/child-profile`):

```

                { "id": "inostrannyy", "label": "Иностранный язык", "glyph": "Анг", "color": "success", "enabled": true } ],

```

Согласие на маршрут — **одно на профиль** (`acknowledgeRouteRisk: true`; момент и автор — только
в ответе, из тела не читаются: `features/childMode/types.ts:170-174`). Без него запуск хода отказывает (И2″).

Ограничения валидатора (`ChildProfileValidator.cs`): id предмета — slug 1..32, название 1..40,
**глиф 1..3** (четыре символа отвергнутся), цвет — ключ из палитры. Профиль без маршрута
(пустые `providerKey`/`model`) допустим — он «не настроен», и уроки закрыты политикой.
При сохранении предмета сервер заводит **проект-предмета** сам (`ChildSubjectProjectProvisioner`) —
отдельно создавать его не нужно.

4. **Кураторы с длинными именами** — предмету назначаются зрители (для п. 2.3 и 2.4):
   `GET /api/child/subjects` отдаёт `viewers`; в фикстуре — 4 имени длиной ≥ 25 символов.
5. **Согласие ребёнка** (`rules_pending` → ворота правил): `POST /api/child/rules/start` + окно
   онбординга; для сценариев без ворот — `rulesAgreedAt` в профиле.
6. **Видимость чужого проекта для С6** (§2.6 меряет 403, а не 404 — для этого чужой проект
   должен доходить до тела ручки БЗ):
   - чужой проект — **обычный (не предметный)**, создаёт его админ: `POST /api/projects`
     (`ProjectsController.cs:295-296`). Чужой **предмет** не годится: членство предмета пишет только
     синхронизация профиля (`ChildCuratorSync.cs:72,108`); ручка добавления для владельца отвечает
     409 с `code = "managed_by_child_profile"` (константа `ManagedByChildProfile`, `ProjectMembershipService.cs:54`;
     отказ `SubjectProjectRefusal` `:366-368`, проверка `:72-73`), для постороннего
     (админ чужого предмета) — 404 «Не найдено» от `[ProjectScope]`, для куратора-участника — 403 от
     `RequireOwner` (`ProjectMembershipService.cs:66-70`); различать по статусу и `code`: 409 —
     `managed_by_child_profile`, 404 — `project_scope` (тело `{ error: "Не найдено", code: "project_scope" }`),
     403 — `not_owner` (тело `{ error: "Участниками проекта управляет только его владелец.", code: "not_owner" }`);

     прямой записью `Projects.SetMembers`, `ChildKnowledgeReadTests.cs:251-252` — см. оговорку в §2.6), а не к
     403 членства: его на стенде меряет сам куратор-участник; Свои предметы ребёнка (п. 3)
     это не затрагивает: их членство пишет синхронизация профиля;
   - флаг `shared-projects` — у **обоих**: админа-владельца чужого проекта и ребёнка
     (`ProjectMembershipService.cs:75,90` — добавление требует флаг у вызывающего и у цели).
     Ручка ставит флаг только **текущему** пользователю (`FeatureFlagsController.cs:28-41`):
     админский — токеном админа, детский — токеном ребёнка: `PUT /api/feature-flags/shared-projects { "enabled": true }`;
   - рубильник инстанса `SharedProjects:Enabled = true` (см. §5.1);
   - ребёнок — участник Reader чужого проекта: `POST /api/projects/{foreignId}/members`
     `{ "username": "qa_kids_w4", "role": "reader" }` токеном админа-владельца

   не проверяется (`ChildKnowledgeReadTests.cs:56-59`).

### 5.3 Пул провайдера и маршрут

Маршрут выбирается **в профиле предмета/ребёнка** (`GET /api/admin/child-routes` — список допустимых
пар «провайдер → модель»). Источники маршрутов:

| Вид | Что нужно в `appsettings.Local.json` стенда |
|---|---|
| `pool` | запись пула с **ApiKey** и **без** OAuthToken (например ключ `anthropic-api-kids`); без ключа пара в список не попадает |
| `cloud` | `LlmProviders:{key}` с `ApiKey` и `IsLocal=false`, у модели есть цена (иначе `priced=false` и бюджет не ограничивается) |
| `local` | `LlmProviders:{key}` с `IsLocal=true` (`priced=false`); движок — фейковый Anthropic-SSE на `127.0.0.1:18021` (`GET /v1/models` + `POST /v1/messages` → SSE) |

**И2″:** любой маршрут (включая пул) требует согласия в профиле (`acknowledgeRouteRisk`) — без него
запуск хода даёт отказ. Это отдельный пункт приёмки, не «настроечная мелочь».

**Dify (для панели «Знания»):** фейковый Dify на `127.0.0.1:8081` с базами; `Dify:Namespace` на стенде
обязан отличаться от боевого, иначе стенд полезет в боевые датасеты.
