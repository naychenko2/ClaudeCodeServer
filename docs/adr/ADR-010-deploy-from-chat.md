# ADR-010: Пересборка и переопубликация прода из чата

Статус: предложено · 2026-08-18 · автор: Александр (тимлид/архитектор)

## Контекст

Прод — хостовая публикация Windows: `deploy80.ps1` собирает фронт и бэк и кладёт всё в
`C:\deploy\claude`, сервер живёт под трей-супервизором `ClaudeHomeServer.Tray.exe`
(либо под внешним Runner `ClaudeServerTray.exe`). Выкатка сегодня — ручной запуск скрипта
на боевой машине. Хочется запускать её из чата самого прода и не остаться без прода,
если публикация не удалась.

Четыре факта определяют дизайн:

1. **Откатывать нечем.** `dotnet publish` пишет поверх `C:\deploy\claude`, прошлые
   бинарники не сохраняются. Снимок снимается только для `data` (`exe --backup`,
   шаг 0.5 скрипта). Неудачная публикация сегодня необратима.
2. **Сервер гасится раньше сборки.** Шаг 1 скрипта убивает процессы, шаги 2–3 собирают
   фронт и бэк. Ошибка компиляции = прод лежит всё время разбирательства.
3. **Чат прода — потомок сервера.** Чат работает через `claude.exe`, дочерний процесс
   `ClaudeHomeServer.exe`; трей при остановке делает `Kill(entireProcessTree: true)`.
   Деплой, запущенный прямо из чата, убивает собственного предка и обрывается на середине.
4. **Трей публикуется в ту же папку** (шаг 5 скрипта) — исполнителем деплоя быть не может,
   залочит собственный exe.

## Решение

**Сервер не деплоит себя.** Он проверяет права, пишет заявку и будит агента, который
не состоит с ним в родстве. Тяжёлая работа идёт при живом сервере, переключение —
короткое окно, здоровье проверяется автоматом, при провале агент сам возвращает прошлый
релиз. Результат новый инстанс подбирает из журнала на диске.

```
чат прода                ХОСТ (вне publish)
   |
   | POST /api/deploy   +-----------------------+
   +-----------------> | заявка + schtasks /run |
                       +----------+-------------+
                                  | (нет родства с сервером)
                          +-------v--------+
                          |  deploy-agent  |
                          +-------+--------+
  ФАЗА 1 (сервер ЖИВ):            |
    git-guard, npm build,         |
    dotnet publish -> staging,    |
    docker build sandbox          |
  ФАЗА 2 (окно 10-20 c):          |
    exe --backup (данные)         |
    stop tray + server            |
    bin -> releases\<stamp>       |
    staging -> C:\deploy\claude   |
    start tray                    |
  ФАЗА 3 (гейт):                  |
    health 3 раза / 90 с --ok--> готово
             |
             нет -> вернуть releases\<stamp>
                    -> start -> health
                    -> уведомление + пост в чат
```

### Компоненты

| Что | Где живёт | Зачем |
|---|---|---|
| `DeployController` | `Controllers/DeployController.cs` | приём заявки, статус, ручной откат; admin-only |
| MCP-инструменты `deploy_start` / `deploy_status` / `deploy_rollback` | `mcp/workspace-server` | поверхность для чата |
| `deploy-agent.ps1` | `C:\deploy\ccs-deploy\` — **вне** `PublishDir` | исполняет выкатку, переживает смерть сервера |
| Задача планировщика `CCS-Deploy` | Task Scheduler | разрывает родство процессов |
| Журнал `deploy-state.json` | `C:\deploy\claude.releases\` | единственная точка истины о ходе выкатки |
| Снимки релизов | `C:\deploy\claude.releases\<utc>\` | материал для отката |

### Почему именно так

- **Task Scheduler, а не detached-процесс.** `Kill(entireProcessTree: true)` строит дерево
  по `ParentProcessId`; процесс, порождённый планировщиком, потомок `svchost`, к серверу
  отношения не имеет. Трюк с промежуточным `cmd`, который «сразу умирает», держится на
  гонке — снимок дерева может успеть увидеть связь.
- **Копия релиза рядом, а не blue-green через junction.** Путь `C:\deploy\claude` зашит
  в `DockerPathMapper` (`{PublishDir}/mcp-dify`), ярлык автозапуска, `tray.json`, а рядом
  с бинарниками лежат `data`, `certs`, `appsettings.Local.json`. Переезд на схему
  `current -> releases\N` стоит дороже пользы; копирование каталога — секунды.
- **Сборка в staging до остановки.** Единственное изменение, которое убирает целый класс
  аварий: «не собралось» перестаёт быть инцидентом прода, а окно недоступности падает
  с минут до секунд.

## Контракт

### REST (все — `[Authorize]` + admin)

```
POST /api/deploy/start
  { ref?: string, skipFrontend?: bool, skipSandbox?: bool, allowDirty?: bool }
  -> 202 { deployId }
  -> 409 если выкатка уже идёт
  -> 400 если дерево грязное и allowDirty не задан (в теле — список файлов)

GET  /api/deploy/status  -> { current, history[], releases[] }
POST /api/deploy/rollback { releaseId? }  -> 202 { deployId }   // по умолчанию предыдущий
```

`ref` валидируется белым списком `^[A-Za-z0-9._/-]{1,100}$`. Никакие другие поля запроса
в командную строку агента не попадают: набор флагов фиксирован. Эндпоинт исполняет код на
хосте под учёткой владельца — это граница привилегий, а не просто ручка.

### Признак «поднялся именно новый»

`GET /api/health` остаётся анонимным и отдаёт `204` (его пингует фронт — контракт не
трогаем), но получает заголовок `X-Build: <deployId>`. Проверка живого процесса по файлу
на диске не годится: файл лежит там независимо от того, какой exe сейчас запущен.

### Журнал `deploy-state.json`

```json
{
  "current": {
    "id": "20260818-141230",
    "phase": "verifying",
    "ref": "master", "sha": "4dc7ddab", "dirty": false,
    "initiatedBy": { "userId": "...", "sessionId": "..." },
    "steps": [ { "name": "frontend", "status": "ok", "ms": 41200 } ],
    "result": null, "reported": false
  },
  "history": [ ],
  "releases": [ { "id": "20260818-135500", "sha": "8e28cba9", "path": "..." } ]
}
```

Фазы: `queued -> building -> switching -> verifying -> succeeded | rolled_back | failed`.

**Отчёт о результате.** Чат-инициатор умирает вместе с сервером, поэтому докладывает уже
новый инстанс: на старте читает журнал и при `result != null && !reported` шлёт уведомление
(`NotificationService`) и сообщение в `sessionId`, затем ставит `reported`. Без этого
«публикация не прошла» узнаётся по молчащему сайту.

## Guard'ы

- **Грязное дерево** — `git status --porcelain` не пуст → отказ без `allowDirty`. HEAD sha
  и список файлов пишутся в журнал. (На 18.08.2026 в рабочем дереве лежат чужие
  незакоммиченные правки — ровно этот сценарий.)
- **Один деплой за раз** — мьютекс `Global\ccs-deploy`, по аналогии с `InstanceLock`.
- **Живой Runner** — та же проверка, что в `deploy80.ps1`: два супервизора на порту 80
  ломают выкатку дважды.
- **Свободное место** — staging + `KeepReleases` снимков; проверять до начала, а не на
  середине копирования.

## Откат

**Код откатывается автоматом.** Не сошёлся health-гейт (3 успешных ответа за 90 с) →
агент гасит сервер, возвращает снимок релиза поверх `PublishDir`, стартует трей, проверяет
health ещё раз, пишет `rolled_back`. Не удалось и это — `failed` с явным текстом: дальше
нужен человек.

**Данные не откатываются никогда автоматически.** За минуты жизни новой версии в сторы уже
записались ходы пользователей и фоновые сервисы, а формат мог мигрировать — автоматический
`--restore` уничтожил бы свежие данные ради отката кода. Снимок `exe --backup` перед
выкаткой остаётся страховкой, восстановление — явное решение человека через меню трея.

## Что сознательно не делаем

- **Дренаж активных ходов.** Переключение режет идущие ходы. Правильно — перестать
  принимать новые и дождаться текущих, но это отдельная работа; в первой версии
  предупреждаем в ответе на `deploy_start`, сколько ходов сейчас активно.
- **Blue-green и нулевой downtime.** Окно в 10–20 секунд для домашнего инстанса дешевле,
  чем разнос путей и переезд `data`.
- **Выкатка контейнерного инстанса.** Механизм про хостовой прод; docker-путь живёт своей
  жизнью (`docker-compose.claude.prod.yml`).
- **Самообновление агента на лету.** Агент копируется из репы в свой каталог шагом 0 и
  запускается уже копией — скрипт не переписывает сам себя во время работы.

## Критерии проверки

1. Ошибка компиляции фронта — прод остаётся живым, статус `failed`, ни одна секунда
   недоступности не зафиксирована.
2. Новая версия стартует, но падает на старте — автооткат возвращает прошлый релиз,
   `X-Build` соответствует откаченному, в чат приходит отчёт.
3. Смерть сервера в момент фазы 2 **не убивает агента** — проверять явно, замером PID
   и дерева, а не «вроде отвязали».
4. Повторный `deploy_start` при идущей выкатке — 409, второй агент не стартует.
5. Грязное дерево — 400 со списком файлов; с `allowDirty` едет и пишет sha+dirty в журнал.
6. Ручной `rollback` на N-1 релиз поднимает прод и докладывает в чат.
