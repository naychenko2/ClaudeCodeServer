# LLM-wiki: «Ночной разбор» чатов

Срез Ф2 эпика LLM-wiki ([ADR-035](../adr/ADR-035-llm-wiki-single-writer.md), §12ж; макет — [llm-wiki-v2.html](../mockups/llm-wiki-v2.html), режим «Срез Ф2 02.11»). Сверено с кодом ветки `fix/wiki-night-busy` 06.11.2026 (волна WN). Судья спорных операций и чистка — [ADR-039](../adr/ADR-039-wiki-new-setup.md), решения 9 и 10; сверено с кодом `feat/wiki-judge` 12.11.2026 (шаги J0–J5, P1–P2).

## Что делает

В окне, которое владелец задал в настройках, служба `WikiNightlyService` проходит по его чатам и разбирает те, где накопилось новое (не меньше 3 реплик человека после курсора), — тем же разбором, что кнопка «Разобрать этот чат», но с местом `wiki-nightly`. Порядок: чаты с пометкой «важный», затем по свежести. Серые чаты проверяет ступень 2 (`wiki-triage`), только когда очередь дошла до чата. Чаты исполнения задач и чаты с пометкой «не разбирать» не берутся. Тумблер по умолчанию **выключен**. Ночь работает без облака: при локальном маршруте места — только локальная модель, без финального claude-шага (отказ модели — если не применено ни одного окна: чат не разобран, курсор не двигается; отказ позднего окна — частичный исход: применённые окна остаются, хроника пишется, курсор встаёт на конец последнего завершившегося без отказа окна; нет маршрута — ночь прерывается с `error`); явный облачный выбор админа для `wiki-nightly` не исполняется: `WikiIngestService.CallModelAsync` отказывает окно до вызова («ночной разбор только локальной моделью», `WikiIngestService.cs:636-647`, ADR-039 §6). Облако допускает только кнопка «Разобрать» (`wiki-ingest`). Занятость локального движка ходом исполнителя ночь не останавливает: облачного шага нет, пропуск был бы потерей вызова, — запрос идёт в занятый движок; не пустивший слот (`TryEnter` без ожидания) и есть отказ окна (исключение режима — [llm-providers](../architecture/llm-providers.md)).

## Новая постановка (ADR-039, волна С2)

Синтез — один локальный вызов на окно, сверено с кодом 11.11.2026:

- **claim и quotes.** Операция несёт утверждение `claim` (≈600 символов) и 1–3 цитаты (`quotes`); дословность проверяет код по цитатам, `Text` заполняется текстом `claim`. Синтез создаёт только `create`, `append`, `conflict`, `link` (`WikiPlanValidator.cs:514`); `rewrite`, `rename`, `merge` — волны С4/С7.
- **Причины спора.** Операция, которую решает не код, попадает в пакет с текстом причины и машинным `ReasonCode`, например «число не подтверждено цитатой: …» → `number_unconfirmed` (`WikiPlanValidator.cs:414`): каждое число `claim` обязано стоять в цитате. Кто решает спор по коду — судья или человек, см. ниже.
- **Поштучный приём.** Негодная операция отказывается сама (`Rejected`, с индексом и причиной), годные остальные идут в пакет — план целиком не отвергается.
- **Зоны чата.** `awaiting_human` — в пакете есть операции «на решении», применённых нет; `rejected_skipped` — окно пропущено курсором после отказов (`WikiChatIngestService.cs:116-125`).
- **Пропуск окна.** После трёх отказов подряд при ответившей модели (`RejectSkipAfter = 3`) курсор переходит через окно, зона `rejected_skipped` с причиной последнего отказа; отказ до модели (облако ночью, движок занят) серию не наращивает. Вручную чат разбирается пунктом меню.
- **Хроника.** Без модели: код дописывает «Что выяснили» утверждениями и цитатами из применённых операций (`WikiChatIngestService.cs:600`); проекция журнала — волна.

## Судья спорных операций (ADR-039, решение 9)

Спорные операции ИИ-пакетов решает не только человек: отдельный идемпотентный проход `WikiJudgeSweep` — облачная модель по новому месту `wiki-judge`, выбранному админом в «Поставщиках моделей». Точки запуска: ночь (тик или кнопка «Запустить сейчас») — ровно один полный проход в конце ночного прохода, его числа идут в итог ночи (`WikiNightlyService.cs:812-833`); ночная заявка посреди ночи судью не зовёт (guard по `actionKey`, `WikiIngestService.cs:272-273`); дневная заявка («Разобрать», `wiki_ingest`, `wiki_add_fact`) — сразу после заявки, кончившейся `awaiting_human` (`:262-285`). Вердикт один: apply / reject с причиной; «переписать» судья не выносит, почти верную операцию он отклоняет — следующая ночь переформулирует её сама. Ночной синтез при этом остаётся локальным: облако в ночи — только этот проход.

- **Кого судья касается.** Только нерешённые `inbox`-операции пакетов автора `ai`, и только по машинному коду причины: `number_unconfirmed`, `page_duplicate`, `section_new_pages_limit`, `after_model_repair`, `no_history_section`, `class_disabled`, `target_disputed`, `overrides_human`, `revert_quarantine`, `personal_to_common` (`WikiApplyPolicy.JudgeAdmitted`, `WikiApplyPolicy.cs:62`). `origin_url`, `unknown_op`, `no_class`, `bad_class`, `no_page` отклоняются кодом без вызова модели; пакет без кода (старый) не допущен; отброшенное валидатором судье не даётся вовсе. «Только для человека» — перенос «Личное → Общее», замена утверждения человека, правка поперёк карантина отката, выключенный класс — теперь тоже решает судья (решение Андрея 12.11, №1).
- **Ручной режим — тем же тумблером.** «Применять без ревью» (`AutoApplyEnabled`, по умолчанию включён) выключен → прохода нет вовсе, ни одного вызова, «Входящие» решает человек прежними кнопками. Нового тумблера нет.
- **«Входящие» как ручная очередь уходят.** При включённом тумблере очередь становится «очередью судьи» (лимит открытых 20 — он же), а её показ — видом «Решения судьи»: только чтение (операция, вердикт, почему, ссылка на страницу). Решать заново то, что уже решил судья, человек не может (`CodeAlreadyDecided`); его действие — откат пакета — только в «Журнале» → «Решения за ночь» и только у применённых пакетов.
- **3 попытки.** Битый или отсутствующий вердикт и отказ вызова — попытка по операции; на третьей отказ выносит код («судья не вынес решения за 3 попытки»): пакет не висит в очереди бесконечно. Отмена прохода попыток не карает. Этот отказ по попыткам — тот же счётчик, что и отказы по коду причины: та же метка `JudgeModelCode` и тот же «отклонено кодом» (`CodeRejected`) в карточке итога, в строке журнала и в теле уведомления (`WikiJudgeSweep.cs:350, 371-375`); «отклонил» судьи считает только вердикты модели.
- **Потолка вызовов за ночь нет** (решение Андрея 12.11, №3): их держит только лимит открытых пакетов — при упоре ночь заканчивается исходом `open_limit`, а не завалом непроверенного. Цена каждого вызова (`OneShotUsage.CostUsd`, делится на операции одного вызова) идёт в итог ночи.
- **«Личное» судье отдаётся без отдельного согласия** владельца (там же, №4).
- **Фронт.** При включённом тумблере «Входящие» показываются видом «Решения судьи» (только чтение: операция, вердикт, почему, ссылка на страницу); при выключенном — прежние «Входящие». Вид «Решения за ночь» — в «Журнале» (утренняя сводка); откат пакета — только там и только у применённых пакетов. Их данные на бэке: решения в файле пакета, `actor = "judge"` в `log.jsonl`.

## Где настраивается

«Вики» → «Настройки» → «Ночной разбор»: тумблер «Разбирать по ночам», окно (часы сервера, по умолчанию 03–06), бюджет входа (700 000 токенов), пакетов за ночь (20) и на раздел (6). Пометки «Важный» / «Не разбирать» — в меню чата; список отбора — «Отбор чатов».

## Ручной запуск

Кнопка «Запустить сейчас» — рядом с заголовком «Прошлая ночь» (WN-5, WN-6b); при выключенном тумблере неактивна с подписью «Ночной разбор выключен». Диалог подтверждения с лимитом пакетов за проход, затем `POST /api/wiki/settings/nightly/run` → 202 `{started:true}`; работа идёт в фоне службы, состояние кнопки («Идёт разбор…») — по `nightlyRunning` в GET. Это тот же проход, что у тика, и под тем же замком владельца: с тиком или другим ручным запуском параллельно он не идёт. Окно при ручном не проверяется, отметка «за дату уже пройдено» не мешает; сам проход дату не закрывает — ночной тик той же даты проходит ночь заново (в итоге поле `manual`). Отказы — 409 со своим кодом до любого состояния прохода: функция выключена (`wiki_llm_wiki_off`), ночь выключена (`wiki_nightly_disabled`), этот владелец уже проходит (`wiki_nightly_running`), настройки нечитаемы (`wiki_settings_invalid`); сервисному токену — 403, службы нет в этом составе — 503. Настроек действие не меняет.

## Итог ночи

Карточка в том же блоке по файлу `keeper/nightly-last.json`: выбрано, разобрано, применено пакетов, решения судьи (принято / отклонено / ждут / отклонено кодом), число его вызовов и их стоимость, оценка токенов, исход (`completed`, `budget`, `open_limit`, `window_closed`, `disabled_midway`, `error`).

Отказанные разборы (WN-2) считаются и называются: `rejected` — их число среди analyzed, `firstRejectReason` — причина первого из них; на каждый отказ — строка в журнал сервера, в карточке — «отказано N» пятой метрикой (только при N > 0). Когда отказаны все разобранные чаты и ни один токен не дошёл до модели, исход — `error`, а не `completed`: `error` дату не закрывает, следующий тик окна пробует снова (тот же `error` той же даты владельцу второй раз не сообщается).

Фактический вход `InputTokens` (сумма входа разобранных чатов и ступени 2) пишется в тот же файл — это мера нагрузки на GPU локали, а не деньги; бюджет ночь решает по оценке `EstTokens`, заранее, до вызова. Карточка и API фактического не показывают.

После записи итога приходит одно уведомление прохода (для ночного тика — утром), с 12.11 — новой формы: заголовок «Ночной разбор: применено N; судья принял K, отклонил L; ждут M; $X» (`WikiNightlyService.cs:1017-1018`). В теле — по одной сводной строке на каждую непустую меру: «Во «Входящих» N пакет ждёт решения» (`:967-968`), «судья недоступен — ждут решения: N» (`:971-972`) и «отклонено кодом: N» (`:976-977`), затем путь «Вики» → «Журнал»; нулевая строка не пишется. Молчание — только при обычном исходе без работы: `Analyzed = 0`, исход `completed`, `JudgeCalls = 0`, `JudgeDeferred = 0` и `CodeRejected = 0` (`:1004-1005`, правка QA, замечание b0065470): если судья звал модель, что-то отложил или код что-то отказал, уведомление приходит даже при нуле разобранных чатов — владелец обязан увидеть вердикты и их цену, либо что пакет остался без вердикта или закрылся отказом самого кода. Детали — вид «Решения за ночь» в «Журнале»: их собирает код из пакетов и `log.jsonl`, модель не участвует. Откат — из «Журнала» (по пакету или по источнику).

Той же ночью итог уходит одной структурной строкой в журнал процесса (`LogInformation` после записи файла; при `error`, `open_limit` или отложенных судьёй операциях — повторно `Warning`, чтобы алерт цеплялся по уровню): основа строки — «Ночь вики {OwnerId} {Date}: {Outcome}; чатов {Selected}/{Analyzed}, отказов {Rejected}» (`WikiNightlyService.cs:358`), дальше две условные части и хвост о судье: « (первый: {RejectFirst})» — только при `Rejected > 0` (`:360-364`), «; ступень 2 отказана {Stage2Refused} (первая: {Stage2First})» — только при `Stage2Refused > 0` (`:367-372`), и всегда — «; пакетов {Applied}, на судье {JudgeApplied}/{JudgeRejected}/{JudgeDeferred}, отклонено кодом {CodeRejected}; вход {InputTokens} ток; судья {JudgeCalls} выз. ${JudgeCost}; ручной {Manual}» (`:375-376`). Нулевой «первый» в строке не печатается: «отказов 0 (первый: )» читалось бы недописанным полем. Текста знаний в строке нет — ни утверждений, ни цитат, ни названий страниц: журнал процесса уезжает в SigNoz.

## Сбой применения решения человека возвращает окно в разбор

Пакет, который человек решил во «Входящих», но который не применился («apply_failed» или «stale»), не теряет своё окно: точка окончания решения (`WikiPackagesController.AfterDecision`) возвращает курсор разбора каждого чата-источника пакета («session:{id}#m{a}-{b}») на «a−1» («WikiChatIngestService.ReturnWindowAsync»): дельта «a…N» разбирается заново, её попыткой станет новый пакет. Возврат идёт в фоне, после формы ответа решения (T-A3): при идущем разборе этого чата откат ждёт его конца, но ответ человека из-за этого не висит — форма и контракт ответа от возврата не зависят. Возвращается только решённый пакет: авто-путь без решения человека курсора не трогает; проигравший гонку вызов (409 или код «wiki_apply_claim»/«wiki_apply_status») окна не возвращает; несессионные источники не трогаются (ключ — origin, а не форма ссылки). Ограничение: ночь берёт чат только при дельте не меньше «MinHumanDelta = 3» реплик человека после курсора («WikiNightlyService.cs:103») — возвращённое окно меньше этого ночь не возьёт вовсе, его переразбирает только кнопка «Разобрать».

## Чистка и перезапуск разбора (ADR-039, решение 10)

Одноразовая операция человека: убрать то, что написала ИИ, и начать разбор с нуля. Запускает её кнопка «Начать вики заново» в «Вики» → «Настройки»: сначала предпросмотр (`dryRun` — числа по разделам и классам, список путей; ни списка, ни архива, ни изменённой страницы на диск не пишется), затем подтверждение. Одно исключение: сам вход в раздел под его замком дёргает ленивый бэкфилл основ, и при первом входе в раздел он ставит служебный маркер `keeper/baselines-backfilled/*` и дописывает основы существующих страниц (`WikiKeeper.cs:596-599`, `WikiBaselines.cs:71-97`) — к составу чистки это отношения не имеет. Ручка `POST /api/wiki/purge?dryRun=true|false`, `[Authorize]`, сервисному токену отказ, только свой корень (`WikiController.cs:656`); MCP-инструмента нет — это разрушающая системная операция, как откат.

- **Что удаляется** — по авторству сноскам (`WikiProjections.PageAuthorship`), а не по дате и не по виду страницы: страницы `ai`, не приёмыши, `chronicle`, карточки `source`, на которые не ссылается ни одна оставшаяся страница, и **смешанные `together`** (решение Андрея 12.11, №2). Человеческая строка журнала (`actor=user`) страницу авторства `ai` не защищает: предикат — авторство и приём как есть, такая страница чистка удаляет и она уходит в zip (там же, №2: содержимое сохранено в архиве, разбор соберёт страницу заново; `WikiKeeper.cs:268-283`). Человеческое, приёмыши и проекции `_*` не трогаются; принятые как есть (`op=adopt` в журнале) — не удаляются ни при каком делении по типам, включая карточки-сироты: «приём как есть» сильнее сиротства (`WikiKeeper.cs:272-275, 306-310`).
- **Всё уходит в zip:** перед удалением — архив `pages/` + `keeper/` в `keeper/archive/purge-{ts}.zip` (не индексируется, но входит в бэкап `data`). Архив не создан — операции нет.
- **Заодно с чисткой:** открытые ИИ-пакеты переходят в `stale` с причиной «чистка вики {дата операции}» — дату подставляет код запуска чистки (`yyyy-MM-dd`, `WikiKeeper.cs:412`), курсоры разбора обнуляются (пометки человека и ступень 1 сохраняются), включается флаг бэклога на 15 дней (`WikiKeeper.PurgeBacklogDays` = 14 — последний день = день чистки +14, включительно, `today ≤ until`; `WikiBacklogFlag`) — на этот срок лимит новых страниц на раздел поднимается до 15. Документы исчезнувших страниц убирает из Dify существующий синк, отдельного каскада нет.
- **Порядок выката:** кнопку нажимают после выката судьи (J0–J4). Иначе первая ночь бэклога снова набьёт 20 открытых пакетов без судьи и встанет на `open_limit`.
- **Фронт.** Блок «Начать вики заново» — в «Вики» → «Настройки»: предпросмотр и диалог подтверждения.
