# Живой прогон 2026-09-23: Кузьма, карта сторожей проекта

Первый прогон боевой конфигурации целиком: прунинг выводов, тел Write/Edit и размышлений
(первая ступень 60k, порог контекста 150k, ступень 121k, хвост 48k), бюджет размышлений 1024,
автосжатие через MiniMax-M3. Задача настоящая: прочитать 25 файлов сторожей и написать
`docs/architecture/guards.md` (задача трекера c43a03d7, worktree `exp/kuzma-guards`, итог —
документ 124 КБ, 43 раздела, коммит `365bff37`). Сырые данные: транскрипт чата исполнения
7817d8b9 в профиле `local-qwen`, журнал прокси с `PRUNE_DEBUG=on`, лог монитора
`/tmp/kuzma-run/monitor.jsonl` (149 срезов по 20 с).

## Что подтвердилось

- **Прунинг держит usage ниже порога сжатия при сырой истории вдвое больше порога.** На 21-й
  минуте сырая история перевалила за 232k при usage 131k; без прунинга сжатие пришло бы на
  20 минут раньше, а на 336k сырых локальная модель не сжала бы вовсе (окно 262k).
- **Граница стабильна, кэш после сдвига восстанавливается за один запрос**: 98–99 % из кэша
  на 174 запросах из 191.
- **Первая ступень 60k сработала там, где задумано**: первый запрос выше порога 150k (171k по
  мерке) срезал 58k, следующий сдвиг на 198k — до полной ступени. Оба стоили 67–87 с.
- **Маршрут сжатия в облако** сработал на первом же сжатии и был единственным возможным:
  сырое тело 336k > 262k окна локали. 61 с против 20,7 с у замера меры 4 — тело вдвое
  больше, сводка вдвое длиннее (21,8k символов).
- **Сводка MiniMax предметная и честная**: структура CLI, точные имена констант и файлов, список
  своих же ошибок и невыполненных пунктов (см. ниже).

## Что не подтвердилось или открылось

### 1. Прунинг ломает цикл «прочитал всё → пишу»

Хвост 48k защищает два-три последних Read. Кузьма прочитал 25 файлов подряд, потом сел
писать — и к этому моменту 22 из 25 выводов были срезаны. Сводка сжатия фиксирует это
дословно: *«When I wrote sections from memory (after Read results got cleared), I invented
several details that weren't accurate»* — 13 разделов из 25 написаны с выдуманными деталями,
затем перечитаны (*«often via `cat` because Read results got cleared»*) и переписаны. На это
ушла вся вторая половина прогона (25 минут доводки, 90k символов тел Edit) и, вероятно,
именно это довело историю до сжатия.

Серии прямых запросов 22–23.09 этого не показали, потому что мерили срезы, где модель
действует по свежему хвосту (следующий шаг разведки, итоговый отчёт по уже собранным
выводам). Режим «долгое чтение, потом письмо» — другой, и он у исполнителя основной.

Варианты, не решено: постановка задач локальному исполнителю в форме «документируй файл
сразу после чтения»; защита выводов Read дольше хвоста по признаку (файл ещё не упоминался в
Write/Edit); больший хвост ценой более позднего срабатывания. Плейсхолдер уже подсказывает
перечитать — модель так и сделала, но только после того, как сначала написала по памяти.

### 2. Необъяснённые промахи кэша дороже прунинга

Четыре из шести промахов пришлись на неподвижную границу: из кэша бралась ровно системная
часть (13–14k) либо ноль, история расходилась с первого сообщения. Их цена растёт с промптом
(71 с на 106k, 184 с на 193k) и в сумме превышает цену обоих сдвигов границы. Тот же промах
Денис видел на ходе 11 замера меры 4.

Два из четырёх пришли через 100–130 мс после побочного одиночного запроса (95–135 КБ). По
хвосту тела это фоновое действие продукта над содержимым файла, который писал Кузьма
(«# Сторожа проекта…», 23k токенов): индексация или сводка документа идёт через ту же локаль
параллельно с ходом. Число крупных выводов в теле при этом не падало, то есть встроенная
чистка выводов CLI ни при чём. Разбор — задача 9a7aeced (дамп тел после правок прокси плюс
diff соседних запросов).

### 3. Ступень 121k после первой границы

Между 115k и 242k обрезанного usage успел вырасти с 92k до 232k и упёрся в сжатие раньше,
чем набралась вторая полная ступень (обрезаемое вне хвоста к сжатию ≈ 190k). С MiniMax это
стоило одну минуту и не страшно; без облака стоило бы шесть. Если сжатие когда-нибудь
вернётся на локаль, ступень после первой границы придётся уменьшать.

### 4. Тела Write/Edit срезать было нечего

Кузьма писал документ кусками короче 1,5k символов из-за собственной защиты от лимита на
команду; тела Edit к сжатию набрали 90k символов, но по одному — ниже `PRUNE_MIN_CHARS`.
Обрезка `input` на такой задаче не работает, проверка её живьём ещё впереди.
