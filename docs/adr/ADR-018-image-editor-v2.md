# ADR-018: Редактор картинок v2 — чат картинки, генерация агентом, «Сохранить как», правки без ИИ

**Статус:** Черновик, редакция 3 от 2026-09-26: редактор выносится отдельным модулем, бэкенд и
фронт (раздел 10, требование Андрея). Редакция 2 от того же дня: растр на SkiaSharp вместо
ImageSharp (решение Андрея), контракты волны 0 в коде.
**Дата:** 2026-09-26
**Основа:** [ADR-017](ADR-017-image-editor.md) — редактор v1, он в master. Этот ADR его **дополняет**:
разделы 1–7 и 10 ADR-017 остаются в силе, раздел 6 «Обсудить с Claude» **заменяется** разделом 1
здесь, раздел 5 расширяется «Сохранить как…», а тезис «на бэкенде нет библиотеки изображений»
отменяется (раздел 9).
**Входные артефакты:** макет [image-editor-v2.html](../mockups/image-editor-v2.html) и записка
[image-editor-v2-proposal.md](../mockups/image-editor-v2-proposal.md) (коммит `02432d1b`); решения
Андрея от 2026-09-26 (записка, раздел «Решения») и дополнение от того же дня о правках без ИИ и
размерах (раздел 9).
**Исполнители:** Денис (бэкенд), Кира (фронт).

## Контекст

Решения Андрея, которые ADR **не пересматривает**:

1. Слева панель со всем, кроме промпта: пометки, образцы с ролями, персонажи, быстрые действия,
   поставщик и модель, история шагов. Справа сверху поле промпта, под ним полноценный чат с
   нашим композером и лентой. Персона выбирается только в композере.
2. «Обсудить с Claude» удаляется, его заменяет чат.
3. Чат — обычный чат проекта, привязанный к картинке. Он виден в списке чатов и создаётся после
   первого сообщения. При повторном открытии картинки открывается тот же чат, и он идёт за
   редактором через версии файла. Есть кнопка «Новый чат по этой картинке».
4. Снимок холста прикладывается к сообщению, только если холст изменился.
5. Агент в этом чате запускает генерацию сам, без вопроса, и может менять промпт и настройки.
   Второй режим: агент только предлагает промпт.
6. Ручной запуск пишется в ленту тихой строкой «Вы запустили: …».
7. «Сохранить как…» без перезаписи.
8. Правки без ИИ: размер, сжатие, обрезка, поворот, отражение. Автоуменьшение перед моделью и
   возврат размера оригинала (раздел 9).

Что есть в коде сегодня (сверено 2026-09-26 по ветке `feat/image-editor-v2`):

- **Сессия.** В `Session` нет общего поля «к чему привязан чат». Привязки разбросаны по полям:
  `TaskId`, `AutomationRuleId`, `BranchedFromSessionId`, `Context` (закреплённые материалы),
  `DesktopChat`. **`DesktopChat` — прямой прецедент:** тип чата задаётся только при создании, и
  от него зависит состав MCP-серверов хода (`Session.cs:421-441`). Правило «настройка не двигает
  `UpdatedAt`» не централизовано, его держит каждый сеттер `SessionManager` сам (`SetExpiry`,
  `SetArchived`, `SetContextAsync` и другие).
- **Список чатов** получает сам `Session` через `SessionJsonConverter`. Значки на карточке
  рисует `ChatCard.tsx`: `ChatOriginBadge`, `ExpiryBadge`, `ChatTopicIcon`.
- **Переименование файла** (`FilesController.Rename` → `FileService.NotifyMutated(Rename)`)
  переписывает только привязки комментариев и синк Dify. Ссылки из сессий и задач на файл не
  обновляет никто.
- **Записи ленты от бэкенда**: полиморфный `StoredMessage` плюс `SessionManager.AppendStoredAsync`
  (запись в историю и рассылка). Карточки рисует `ChatItemView.tsx`, по `kind` и цепочкой `if`
  по имени инструмента (`widget_show` → `WidgetView`, `tasks_create` → `TaskCreatedView`).
  **`AppendStoredAsync` пишет в нашу `history.json`, а не в транскрипт CLI: модель такие записи
  не видит.**
- **MCP.** Сервер попадает в ход, если `SessionManager.Build*Context` вернул контекст; решение
  принимается по владельцу, персоне, флагам и свойствам сессии, но не по ходу. Сессию-вызыватель
  тулсет берёт из хвоста маршрута и проверяет через `GetOwned` (`WatchToolset.TryResolve`). У
  тулсета нет ни `turnId`, ни сигнала «Стоп». Есть отмена HTTP-запроса и `TurnCompleted` на
  шине. `DelegatedTurnGate.Decide` отказывает на делегированных ходах (fail-closed в тулсетах).
- **Задачи редактора** (`ImageEditJobService`): реестр в памяти по `ownerId + projectId`.
  События `image_edit_*` уходят в `ToOwner`. Трата пишется на владельца при принятии задачи.
  **Поля «из какого чата» у задачи нет.**
- **«Обсудить»**: `ImageDiscussService` (Main) создаёт чат «Картинка: hero.png», кладёт
  размеченную копию в `.cc-attachments`, отправляет сообщение. Ручка `POST …/image-editor/discuss`,
  фронт `components/imageEditor/discuss/*` (DiscussPanel читает ответ через `useSession`).
- **Сохранение**: `IImageEditSaver` → `VersionedImageStore.SaveNextVersion` (`hero.v2.png`,
  `FileMode.CreateNew`) или «Нарисовать» с `-2`, `-3`. Пути проходят через
  `ProjectLinkGuard.ResolveInside`, ссылки отсекаются.
- **Фронт.** `Composer` полностью управляемый: вложения хранит хозяин (страница), `sessionId`
  обязателен (ключ черновика). `ChatPanel` встраивается с `embedded` (так работает «Стена») и
  умеет `pendingMessage`, **но только текстом**. Пути «сначала сообщение, потом чат» нет: чат
  создаётся заранее. Отдельного маршрута у редактора нет, это слой-портал `ImageEditorHost`.

## Решение

### 1. Чат картинки: привязка, поиск, версии

**Связь — новое поле сессии `Session.ImageChat`**, по образцу `DesktopChat`: тип задаётся при
создании и дальше не снимается. Отдельный стор не нужен: привязка — свойство чата, она едет в
бэкапе вместе с `sessions.json` и уходит на фронт в том же `Session`.

```csharp
// null — обычный чат. Не null — чат картинки: тип фиксирован с создания (от него зависит
// MCP-сервер image-editor, раздел 2), путь меняется, когда редактор уходит на новую версию.
public sealed class SessionImageChat
{
    public string CurrentPath { get; set; } = "";   // файл, с которым сейчас связан чат, от корня проекта
    public List<string> Lineage { get; set; } = []; // прежние пути, старые первыми (hero.png, hero.v2.png…)
}
```

Поле аддитивное и nullable, `BackupSchema.Version` не двигается.

**Создание — после первого сообщения.** Новая ручка `POST …/image-editor/chats`
`{ sourcePath, personaId? }` создаёт чат через `SessionManager.CreateAsync(…, imageChat: …)`,
возвращает `Session` и ничего не отправляет. Правило выбора собеседника переносим из
`ImageDiscussService` (руководитель проекта, иначе личный ассистент), но `personaId` из
композера важнее. Имя — «hero.png · правка», задаётся явно, поэтому авто-заголовок его не
переписывает. Порядок на фронте:

1. Пока чата нет, композер рисуется сам (раздел 6). Черновик хранится под псевдоключом
   `image:{projectId}:{path}`, вложения — локальными `File`.
2. «Отправить» → `POST …/chats` → загрузка вложений и снимка обычной ручкой
   `POST api/chats/{id}/files/upload` → монтирование `ChatPanel` с `pendingMessage`, который
   расширяется до `{ text, attachedPaths }`.

Сбой между созданием и отправкой оставит пустой чат картинки. Это приемлемо: такой чат найдётся
при следующем открытии картинки и будет использован, мусор не копится.

**Поиск чата редактором** — `GET …/image-editor/chats?path=images/hero.png` отдаёт:

- `current` — чат, у которого `CurrentPath == path`: самый свежий по `UpdatedAt` среди
  неархивных, иначе самый свежий архивный. Архивный открываем как есть: первое же сообщение
  вернёт его из архива само, по правилу `IsArchived`;
- `continued` — чаты, у которых `path` есть в `Lineage`: «Разговор об этой картинке продолжился
  на hero.v2.png — открыть?». Сами на старый файл не перескакиваем: чат живёт с новой версией.

Поиск — линейный проход по сессиям владельца в памяти `SessionManager`, с фильтром по проекту.
Индекс не заводим: сессий у владельца сотни, не миллионы.

**«Новый чат по этой картинке»** — тот же `POST …/chats` при уже существующем чате. Прежний
остаётся в списке, `current` дальше отдаёт самый свежий.

**Чат идёт за редактором.** В `POST …/save` добавляется необязательный `chatSessionId`. После
успешной записи сервер:

1. проверяет, что чат свой, из этого проекта и это чат картинки;
2. дописывает старый `CurrentPath` в `Lineage` и ставит новый путь. Сеттер
   `SetImageChatPath` **не двигает `UpdatedAt`**: это настройка, а не активность, и она не
   должна поднимать чат наверх и выводить его из архива;
3. пишет в ленту тихую запись `image_file_moved { from, to }` через `AppendStoredAsync`:
   «Сохранено как images/blog/hero-evening.png. Редактор перешёл на этот файл, чат — вместе с
   ним». Это запись в ленте, и она **двигает** `UpdatedAt`, как любая запись в ленту. Так и
   задумано: человек что-то сделал в этом чате.

**Переименование и перемещение файла вне редактора.** Новый подписчик `FileService.OnMutated`
в Main — `ImageChatPathTracker`. На `Rename` файла или папки (префиксом) он переписывает
`CurrentPath` и пути в `Lineage` у чатов картинок этого проекта. `UpdatedAt` не трогает, записи
в ленту не делает. На `Delete` привязка остаётся, редактор при открытии чата показывает «Файл
удалён или перемещён» и предлагает выбрать файл. Переименования мимо `FileService` (агент в ходе
сделал `mv` своим Bash) трекер не видит. Лечится это при открытии: `current` не нашёлся →
редактор предлагает «Привязать чат к этому файлу» (ручка
`PUT …/chats/{sessionId}/path`).

**Список чатов.** `ChatCard` получает значок «картинка» и миниатюру `CurrentPath` через
существующую ручку сырого файла. Клик открывает **редактор** с этим чатом
(`openImageEditor({ path, sessionId })`), а не страницу чата. В полном чате есть кнопка «Открыть
в редакторе». Флаг выключен у владельца — карточка обычная, клик ведёт в обычный чат.

### 2. Инструмент генерации для агента

**Отдельный MCP-сервер `image-editor` по HTTP (ADR-012)**: параметризованный тулсет
`ImageEditorToolset` в Main (`Services/Mcp/Http`). Хвост маршрута — `sessionId` чата, как у
`watch`. Main, а не вертикаль `Images`: тулсету нужны `SessionManager`, `ProjectManager` и
корень проекта, то есть спина. Вертикали он отдаёт уже собранный `ImageEditJobInput` через
существующий шов `IImageEditJobs`.

**Состав `tools/list` не зависит от хода.** Сервер попадает в конфиг, если
`BuildImageEditorContext` вернул контекст. Для этого одновременно нужны:
`Session.ImageChat != null` (тип, фиксирован с создания, как у `DesktopChat`), флаг
`image-editor` у владельца (прецедент — флаг `DossierToolsEnabled` в отпечатке `memory`) и
включённая подсистема `images`. Всё это — свойства сессии и владельца. В обычных чатах сервера
нет вовсе, поэтому соседние чаты не платят токенами за схему инструментов. Сторож —
`McpToolsetStabilityTests`: `BuildImageEditorContext` добавляется в список рубильников без
`_currentTurn`, а `ImageEditorToolset.ToolsFor` — в проверку тел.

Инструменты (имена разводим по смыслу, однокоренных с пересечением нет):

| Инструмент | Что делает |
|---|---|
| `image_state` | текущее состояние: файл и его размеры, промпт, поставщик и модель, число вариантов, образцы с ролями, персонаж, пометки словами (`EditMarksPrompt`), путь последнего снимка, последние задачи и их итог, доступные модели с `caps` |
| `image_generate` | **запускает генерацию сразу**. Параметры все необязательные: `prompt`, `provider`, `model`, `mode`, `count`, `references[]` (пути проекта с ролями), `op` (правка, фон, апскейл, дорисовка), `matchSourceSize`. Что не передано — берётся из состояния редактора. Меняет состояние и возвращает `{ jobId, quote, changes[] }` |
| `image_suggest_prompt` | только предлагает: `{ prompt, count?, model? }`. Ничего не запускает и не меняет, в ленте карточка «✦ Промпт» |
| `image_cancel` | отмена своей задачи этого чата по `jobId` |

**Откуда агент знает состояние редактора.** Состояние живёт **на сервере**, а не только в
браузере. Иначе запуск при закрытом редакторе невозможен.

- `ImageChatStateStore` (Main, файл `data/image-editor/{ownerId}/chats/{sessionId}.json` рядом с
  рабочими папками, тот же TTL-кеш вне бэкапа). В нём лежат: промпт с автором
  (`human | agent`), выбор поставщика, модели, режима и числа, образцы (пути проекта с ролями;
  загруженные с компьютера — копией в рабочей папке), персонаж, `marks.json`, последняя маска,
  `canvasRevision`, текущий шаг, журнал событий «с прошлого хода».
- Редактор шлёт состояние `PUT …/image-editor/chats/{sessionId}/state` с дебаунсом 500 мс. Маска
  едет multipart, только когда сменилась `canvasRevision`. Каждая запись несёт `revision`; запись
  со старой ревизией отвергается `409`, фронт перечитывает состояние.
- **Каждый ход** чата картинки получает компактный блок «Состояние редактора» (файл, промпт,
  модель, число, образцы, пометки словами, «с прошлого сообщения: Вы запустили …; итог: 3
  варианта, $0.24»). Блок нестабильный, поэтому идёт **хвостом хода** по механике
  `RecallInTurnText`, а не системным блоком: иначе он обнулял бы prefix cache всей истории.
  Собирает его подписчик `prompt/assembling` (ADR-013). Подробности — `image_state` по запросу.
- Ручной запуск (строка «Вы запустили: …») агент узнаёт именно из этого блока. Запись
  `image_launch` в ленте модель **не видит** (история, а не транскрипт CLI), поэтому журнал
  событий в состоянии обязателен, а не «на всякий случай».

**Запуск без вопроса.** `image_generate` исполняется сразу. Чтобы CLI не спросил разрешения на
MCP-инструмент, `mcp__image-editor__image_generate` и `…__image_suggest_prompt` добавляются в
разрешённые **при создании** чата картинки. Это `AutoAllowTools` сессии, а не глобальная
настройка. Сторожа дешёвого запуска:

- делегированный ход (субагент персоны) → `DelegatedTurnGate.Decide`, отказ fail-closed:
  тратить деньги может только ход, который видит человек;
- не больше **2 запусков на ход**. У тулсета нет `turnId`, поэтому это счётчик на сессию,
  который сбрасывает подписчик `TurnCompleted` на шине (фильтр по `SessionId`). Плюс существующие потолки 2 задачи на владельца и 4 на инстанс. Цикл «до
  готово» генерацию не размножит: каждый его шаг — ход с тем же потолком;
- котировка и запуск идут ровно тем путём, что и у человека: **сборка входа выносится из
  `ImageEditorController.Start` в общий `ImageEditLaunchAssembler` (Main)**, и им пользуются
  и ручка, и тулсет. Две сборки входа разошлись бы в проверке путей и лимитов.

**Как ход меняет открытый редактор.** Тулсет пишет изменения в `ImageChatStateStore` и
рассылает `image_chat_state { sessionId, projectId, revision, state, changedBy: "agent",
changes: [{ field, from, to }] }` через `ISessionBroadcaster.ToOwner`. Редактор этого чата
применяет состояние: поле промпта подсвечивается, появляется метка «✦ написал Claude», у
изменённых настроек — «✦ модель сменил Claude». Ручная правка снимает метку и пишет
`author = human`. Если человек в этот момент печатает в поле промпта, его несохранённый текст
не теряется: редактор держит его как черновик и показывает «Вернуть мой текст».

**Редактор закрыт.** Всё работает так же: вход собирается из состояния на сервере, исходник —
`CurrentPath` с диска проекта, маска — последняя присланная, если `canvasRevision` совпадает с
текущим файлом. Сменился файл — пометки отбрасываются, и агент видит это в `image_state`.
Варианты ложатся в рабочую папку. Карточка в полном чате даёт «Открыть в редакторе», и тот
открывается сразу на вариантах этой задачи. **Сохранять в проект агент не может**: «Применить»
и «Сохранить как…» — только руками человека. Писать файлы проекта агент и так умеет своими
инструментами, а редактор не должен давать второй, неявный путь.

**Карточки в ленте.**

- `image_generate` — это обычный `tool_use` в истории. `ChatItemView` рисует его
  `ImageLaunchCard` (по образцу `WidgetView`) из `input` и JSON-результата: заголовок «Запущена
  генерация · ≈ $0.10 · 2 варианта», строка «Изменил: …», прогресс, «Отменить». Живой статус —
  события `image_edit_*`. В них и в `ImageEditJobDto` добавляются `SessionId` и
  `Initiator: human | agent`. После перезагрузки статус догоняется через `GET …/jobs/{id}`, после
  рестарта бэкенда — `410 interrupted`.
- `image_suggest_prompt` → `ImagePromptCard` с кнопками «Вставить в промпт» и «Сгенерировать».
  Кнопки работают через React-контекст `ImageEditorBridge`, который даёт редактор. В полном чате
  контекста нет, и кнопка одна — «Открыть в редакторе с этим промптом».
- Ручной запуск: `POST …/jobs` принимает необязательный `chatSessionId`. После старта сервер
  пишет `image_launch { by: "human", prompt, provider, model, count, estimate, jobId }` через
  `AppendStoredAsync`, в ленте это тихая строка «Вы запустили: «…» · FLUX Fill · ≈ $0.10 ·
  2 варианта».

**Траты и изоляция.** Ничего нового по деньгам: трату пишет `ImageEditJobService` на
**владельца чата** (`GetOwned` в тулсете, тот же `ownerId`, что и у ручек). Никогда не на
`AdminOwnerId` Higgsfield и не на персону. В `SpendRecord` добавляются `SessionId` и
`Initiator`, чтобы в «Модели и расход» было видно, сколько потратил агент. Изоляция держится на
том, что тулсет видит только свою сессию: чужой `sessionId` в хвосте → пустой `tools/list`, чужой
`jobId` в `image_cancel` → «задача не найдена».

**Отмена.** Кнопка «Отменить» в карточке и под полем промпта — это `DELETE …/jobs/{id}`, та же
ручка, что в v1, с проверкой владельца. Поведение `charged` честное, как в ADR-017 §7.
**Кнопка «Стоп» хода генерацию не отменяет**: задача живёт отдельно от хода, человек мог
остановить разговор и ждать картинки. Отмена генерации — только явная. Настройки, которые
поменял агент, при отмене не откатываются: промпт остаётся в поле, так в тексте карточки.

### 3. Снимок холста в сообщении

- **Признак «холст изменился»** — `canvasRevision`: хеш от `CurrentPath`, id текущего шага
  истории и канонического `marks.json`. Фронт хранит `lastSentRevision` чата (он же лежит в
  состоянии на сервере — переживает перезагрузку). Не совпало — в композере чип
  «hero.png · 3 пометки» с пунктирной рамкой, совпало — бледный «hero.png · без изменений».
  Крестик снимает снимок, меню «+» возвращает.
- **Механизм вложений существующий**: снимок — PNG размеченной копии (`exportAnnotated`, без
  пометок — сама картинка; это нынешний `discuss/snapshot.ts`, переезжает в
  `chat/snapshot.ts`). Он грузится `POST api/chats/{id}/files/upload` в `.cc-attachments/{guid}/`
  и уходит в `attachedPaths`. Дальше `ClaudeSession` сам превращает картинку в image-блок.
  Снимок ужимается до 1568 px по длинной стороне: больше модели не нужно, а лишние мегабайты
  base64 оседают в транскрипте на каждый `--resume`.
- **Подпись «холст не менялся — снимок не приложен».** `SendMessage` хаба меняться не будет.
  Добавляется метод хаба `SendImageChatMessage(sessionId, text, attachedPaths, mode, snapshot:
  { revision, attached })`: он зовёт тот же `SendMessageAsync` и пишет в `StoredUserMessage`
  новое поле `ImageSnapshot`. По нему `ChatItemView` рисует подпись. Модели подпись не нужна:
  изменения она видит из блока состояния.

### 5. «Сохранить как…»

- `ImageEditSaveRequest` получает `Mode: "next-version" | "as"`. Прежнее поведение (`hero.v2.png`,
  «Нарисовать» с `-2`) остаётся под `next-version`. **Флага перезаписи нет по-прежнему.**
- `"as"`: `Folder` + `FileName`. Имя проходит `Path.GetFileName` (обязано совпасть с вводом:
  «a/b.png» → 400), без ведущей точки и запрещённых символов. Расширение сервер ставит **сам по
  фактическому формату** (или по выбранному кодированию, раздел 9). Вписанное руками `.png`
  срезается, а не удваивается. Папка — `ProjectLinkGuard.ResolveInside` (внутри корня, без
  ссылок) и обязана существовать; папки из диалога не создаём.
- Запись — `FileMode.CreateNew` в `IImageEditSaver.SaveAs`. **Занятое имя — `409 name_taken` с
  `suggestion`** (следующий свободный номер `hero.v3.png`), а не тихий переход на следующий
  номер: имя человек выбрал явно, подменять его без клика нельзя. Гонка двух сохранений даёт тот
  же `409`.
- Проверка на лету — `GET …/image-editor/save/check?folder=&name=&format=` → `{ path, taken,
  suggestion }`. Ничего не пишет. Дебаунс 300 мс, окончательное решение всё равно за `CreateNew`.
- Источник сохранения — вариант задачи (`jobId + variant`) **или шаг истории** (`stepId`,
  раздел 9). Иначе нельзя сохранить обрезку или сжатие без генерации.
- После записи: `NotifyMutated`, перенос чата (раздел 1, `chatSessionId`), тост «Показать в
  дереве».

### 7. Инварианты под угрозой и сторожа

| Инвариант | Угроза | Сторож / тест |
|---|---|---|
| `tools/list` не зависит от хода | подмешать в `BuildImageEditorContext` или `ToolsFor` признак хода («редактор открыт», «идёт генерация») | `McpToolsetStabilityTests`: новый рубильник и тулсет в списках проверок; тест «чат картинки — сервер есть, обычный чат — нет, флаг выкл — нет» |
| `UpdatedAt` не двигают настройки | `SetImageChatPath`, `PUT state`, трекер переименований поднимают чат наверх и выводят из архива | тесты: смена пути, запись состояния и rename файла не меняют `UpdatedAt`; мутация «двигать» краснеет; запись `image_file_moved` в ленту двигает |
| Изоляция владельцев | чужой `sessionId` в `chats/{id}/state`, `save.chatSessionId`, хвосте MCP; чужой `jobId` в `image_cancel` | тест на каждую точку: чужое → 404 или пустой состав, неотличимо от несуществующего |
| Трата на владельца чата | запись на персону, на `AdminOwnerId` Higgsfield или пропуск записи при запуске агентом | тест: агент в чате владельца B запускает Higgsfield → одна запись `OwnerId = B`, `Initiator = agent`, `SessionId` чата |
| Нет запуска без человека в ходе | субагент персоны или фоновый ход тратит деньги | тест: `image_generate` на делегированном ходу → отказ, задачи нет |
| Потолок запусков агентом | цикл тратит кредиты | тест: третий `image_generate` за ход → отказ с текстом, задачи нет |
| Один путь сборки входа | тулсет собирает вход сам, мимо проверок путей и лимитов | вход агента и ручки идёт через `ImageEditLaunchAssembler`; тест: путь образца через символическую ссылку отвергается и из тулсета |
| Выбор поставщика не подменяется | агент меняет поставщика «сам себе» при отказе | агент может выбрать поставщика явно (это решение Андрея), но `retryQuote` роутер сам не исполняет; тест прежний, плюс «отказ → в результате инструмента `retryQuote`, второго вызова драйвера нет» |
| Перезаписи нет | `SaveAs` на занятое имя | тест: занятое имя → `409` + `suggestion`, байты существующего файла не изменились; мутация `CreateNew` → `Create` краснеет |
| Path traversal | имя и папка «Сохранить как», `PUT …/path`, образцы агента | тесты `../`, абсолютный путь, `a/b.png` в имени, ссылка наружу |
| Состояние не затирается гонкой | агент и человек пишут одновременно | тест: запись со старой `revision` → `409` |
| Модель не видит записей ленты | «Вы запустили» только в `history.json` | тест сборки хвоста: ручной запуск попадает в блок состояния следующего хода |
| Стабильность prefix cache | блок состояния в системной части промпта | блок только хвостом хода; тест: системный блок чата картинки не меняется между ходами |
| Флаг гейтит сервер | ручки и MCP при выключенном флаге | тест: флаг выкл → 404 на новых ручках, сервера нет в конфиге хода |
| Разбор заборов один | остаток `image-prompt`-разбора | удаляется вместе с `discussText.ts` |

**Фич-флаг — один, `image-editor`.** Отдельный флаг на чат не заводим. v1 не выходил из dark
launch, и держать две раскладки ради флага — двойная работа без пользы. Чат картинки
существует только внутри редактора, а MCP-сервер есть только в таком чате, так что внешний
контур флаг гейтит целиком. Если Андрею нужен выключатель именно «агент тратит сам», то это
настройка инстанса `ImageEditor:AgentLaunch` (по умолчанию `true`), а не второй флаг. При `false`
остаётся только `image_suggest_prompt`. Это решение по составу инстанса, а не по ходу, поэтому
стабильности не ломает.

### 9. Правки без ИИ и размеры

**Решение: растр делает сервер на SkiaSharp, фронт — только предпросмотр.** Тезис ADR-017 «на
бэкенде нет библиотеки изображений, и заводить её не нужно» отменяется. Причина — запуск
агентом при закрытом редакторе: автоуменьшение (п. 3) и возврат размера (п. 4) обязаны работать
без браузера. Раз библиотека нужна серверу всё равно, второй реализации ресайза на canvas не
заводим: иначе один и тот же шаг давал бы разное качество в зависимости от того, кто его сделал.

Почему одного canvas мало (проверено 2026-09-26):

- **WebP.** iOS Safari не кодирует WebP в `canvas.toBlob`, тихо отдаёт PNG. Сжатие в WebP на
  iPhone было бы враньём.
- **Большие файлы на телефоне.** У iOS Safari потолок площади canvas зависит от устройства и
  памяти. Фото 48 Мп с iPhone в полный размер туда не влезает, и маска размером с исходник
  (ADR-017 §3) на таком фото тоже падает.
- **Качество ресайза.** `drawImage` с `imageSmoothingQuality: high` при сильном уменьшении даёт
  алиасинг, нужны ступенчатые проходы. На сервере они делаются один раз и одинаково для всех
  точек запуска.
- **Метаданные.** Перекодирование через canvas теряет ICC-профиль: фото Display P3 с телефона
  «блёкнет». EXIF-ориентацию браузеры уже учитывают при отрисовке, но саму метку не сбрасывают, и
  после сохранения её ещё надо чинить.
- **Автоуменьшение и возврат размера** в браузере невозможны, когда агент запускает генерацию
  при закрытом редакторе.

**Библиотека — SkiaSharp (MIT)**, решение Андрея от 2026-09-26: `SkiaSharp` плюс
`SkiaSharp.NativeAssets.Linux.NoDependencies`, `PackageReference` только в
`ClaudeHomeServer.Images`. Core остаётся без пакетов. ImageSharp рассматривался первым (код
полностью управляемый), но его Six Labors Split License требует коммерческой лицензии выше порога
выручки. Magick.NET и NetVips тоже нативные и тяжелее.

Проверено пробным проектом (SkiaSharp 3.119.2, net10.0, Linux x64): ресайз 4000×3000 → 1024×768
и кодирование PNG/JPEG/WebP с качеством работают; `ldd libSkiaSharp.so` чистый, fontconfig
вариант `NoDependencies` не требует (текст мы не рисуем). На Windows нативку тянет
`SkiaSharp.NativeAssets.Win32`, в CI на ubuntu она берётся из `runtimes/linux-x64/native` пакета.

**Чем SkiaSharp отличается от того, что обещал ImageSharp**, и как это закрываем:

- **Lanczos3 нет** в `SKSamplingOptions`. Ресайз — `SKCubicResampler.Mitchell`, при уменьшении
  больше чем в 2 раза — ступенчатые проходы по 2×, иначе алиасинг;
- **`MemoryAllocator` нет.** Потолок 100 Мп проверяется по `SKCodec.Info` **до** декодирования
  (заголовок, без пикселей), а не после;
- **`AutoOrient` делаем сами** по `SKCodec.EncodedOrigin`;
- **EXIF энкодеры Skia не пишут вовсе**: геометка пропадает сама, но это держится тестом, а не
  верой;
- **ICC-профиль**: `SKCodec.Info.ColorSpace` переносится в `SKImageInfo` результата, энкодер пишет
  профиль. Держится тестом «фото Display P3 → профиль в результате есть»;
- **маска** масштабируется с `SKSamplingOptions(SKFilterMode.Nearest, SKMipmapMode.None)`,
  бинарность держится тестом из таблицы ниже;
- **размер публикации.** Без RID `dotnet publish` кладёт в `runtimes/` нативку под все платформы,
  около 0,4 ГБ. Все точки публикации (`backend/ClaudeHomeServer/Dockerfile`,
  `scripts/ops/publish-linux.sh`, `deploy80.ps1`, `scripts/ops/deploy-agent.ps1`) получают
  `-r linux-x64 --self-contained false` (Windows — `-r win-x64`). Критерий — размер `runtimes/`
  до и после.

Устройство:

- **`IImageRaster`** (Images, `Services.Images.Editing.Raster`): `Probe` (формат, размеры,
  ориентация, вес), `Apply(ops)` с операциями `AutoOrient`, `Crop(rect в долях)`,
  `Rotate(90|180|270)`, `Flip(h|v)`, `Resize(w, h | percent, lockAspect)`, `Encode(format,
  quality)`. Потолки: вход до 100 Мп по заголовку файла, до декодирования (иначе 400 «картинка
  слишком большая»), одновременно не
  больше 2 операций на инстанс (семафор в сервисе). Пиковая память на 48 Мп — около 0,4 ГБ,
  поэтому очереди нет: сверх потолка — 429, как у задач.
- **Шаги истории — на сервере**, в рабочей папке сеанса (`data/image-editor/{ownerId}/{editId}/
  steps/`). Правки без ИИ и применённые варианты — шаги одной ленты с `parent`. Ручка
  `POST …/image-editor/transform { base: { path | stepId }, ops[], encode? }` → `{ stepId,
  width, height, bytes }`. Бесплатно, без поставщика и без котировки, трат не пишет.
- **Мгновенность** даёт фронт: рамка обрезки, поворот и отражение показываются сразу
  (CSS-трансформ или canvas на экранном разрешении). Сервер фиксирует шаг за 100–300 мс. Пока
  шаг в полёте, следующая операция ставится в цепочку, а не теряется.
- **Размер и сжатие.** Поля px/%, замок пропорций, пресеты (1920, 1280, 1080, 512 по длинной
  стороне; 50 %). Формат PNG/JPG/WebP, качество 40–100. Вес «2,4 МБ → 310 КБ» считает
  `POST …/transform?dryRun=true`: кодирует в память, шаг не пишет, возвращает только `bytes`.
  Дебаунс 300 мс.
- **Тяжёлый файл при сохранении**: если результат больше `ImageEditor:HeavyFileMb` (по
  умолчанию 5), в диалоге сохранения показываем «Файл 8,4 МБ — тяжёлый. Сжать в WebP ≈ 900 КБ?» и
  кнопку, которая подставляет кодирование. Блокировки нет.
- **Автоуменьшение перед моделью (п. 3).** В `ImageEditCaps` модели добавляются `MaxInputSide`,
  `MaxInputMegapixels`, `MaxInputMb`, в каталоге они курируемые, как остальные `caps`.
  `InputFitter` в `ImageEditJobService` перед вызовом драйвера ужимает исходник, образцы и
  размеченную копию под лимит модели. **Маска масштабируется до тех же размеров, что и
  исходник, методом nearest-neighbour**: так она остаётся бинарной, и совпадение размеров
  (ADR-017 §3) держится после ужатия. Оригинал в проекте не трогаем. Точка одна для всех
  запусков — ручка, агент, быстрые действия — поэтому закрытый редактор ничего не меняет.
- **Маска на телефоне.** Фронт экспортирует маску в разрешении предпросмотра (до 2048 px), а
  сервер растягивает её до размера исходника тем же nearest-neighbour. Этим закрывается потолок
  canvas на 48 Мп.
- **Возврат размера оригинала (п. 4).** `MatchSourceSize` в запуске и в состоянии чата, по
  умолчанию `true`, тумблер в «Чем рисовать» и параметр `image_generate`. После скачивания
  варианты приводятся к размерам исходника, **если пропорции совпадают с точностью до 2 %**.
  Не совпадают (модель выбрала свой кадр) — размер результата не трогаем и честно пишем
  «Размер не приведён: другие пропорции». Для «Дорисовать за края» и «Улучшить качество»
  возврата нет по смыслу операции.
- **EXIF и профиль.** На входе в любой конвейер — `AutoOrient`. На выходе ориентация
  сбрасывается в «нормальную», а ICC-профиль исходника сохраняется. Остальные EXIF-поля
  (геометка!) при сохранении **удаляются**: картинка из редактора уходит в сайт или репозиторий.

Сторожа раздела:

| Инвариант | Тест |
|---|---|
| маска после ужатия совпадает с исходником и остаётся бинарной | ужатие 6000×4000 → лимит 2048: размеры маски и исходника равны, в маске только 0 и 255 |
| оригинал не меняется | `transform` и автоуменьшение не пишут в проект; хеш файла до и после равен |
| возврат размера только при тех же пропорциях | 1:1 → 1024², 16:9 → свой размер + пометка |
| геометка не утекает | сохранение JPEG с GPS в EXIF → в результате GPS нет |
| потолок памяти | вход больше 100 Мп → 400 по заголовку, пиксели не декодируются, без исключения наружу |
| ICC-профиль сохраняется | фото Display P3 → в результате профиль есть |
| граница зависимостей | SkiaSharp только в `Images`: `SubsystemBoundaryTests` зелёные плюс **новый** тест «в `ClaudeHomeServer.Core.csproj` нет `PackageReference`» — сейчас это правило держит только ревью |

Объём раздела заложен в волну 1 таблицы раздела 8: бэкенд ~700–900 строк и ~450 строк тестов,
фронт (обрезка, поворот, отражение, размер, сжатие, вес) ~700–900 строк из общих 2 600–3 100.

### 10. Редактор — отдельный модуль (редакция 3)

**Требование Андрея от 2026-09-26:** редактор картинок должен быть отдельным модулем. На
бэкенде он живёт в своём проекте, фронт встраивается отдельно. Сейчас это не так (сверено по
ветке после шагов 1–4 плана):

- логика и драйверы лежат в `ClaudeHomeServer.Images/Services/ImageEditor` (~3 300 строк), в
  одной вертикали с генерацией аватаров;
- контракты лежат в `ClaudeHomeServer.Core/Services/ImageEditor` (~800 строк, с `Versioning`);
- в Main лежат `ImageEditorController` (~460 строк), `Services/ImageEditor/Discuss` и схемы
  `ImageEditorToolset.Schemas.cs`. Это против курса ADR-014 «в Main не остаётся папок вертикалей»;
- фронт вшит в основной бандл: `components/imageEditor` (~3 000 строк) и `api/imageEditor.ts`
  (~820 строк).

Раздел **заменяет** места прежних разделов, где что-то было положено в Main: тулсет и
`BuildImageEditorContext` из §2, `ImageChatStateStore` и `ImageEditLaunchAssembler` из §2,
`ImageChatPathTracker` из §1, раскладку по слоям из §8. Смысл решений §1–§9 не меняется,
меняется только адрес кода.

#### 10.1. Бэкенд: динамический модуль `ClaudeHomeServer.ImageEditor`

**Форма — динамический модуль (сценарий Б), как Notes и Spend**, а не обычная вертикаль на
`ProjectReference`:

- Main ссылается на проект с `ReferenceOutputAssembly="false"`. Типов модуля Main не видит, это
  гарантирует компилятор, а не ревью;
- dll копируется в `modules/image-editor/` **двумя целями MSBuild, `Build` и `Publish`**. Это
  грабли Notes из ADR-014: при одной цели `dotnet publish -o` молча терял dll, и прод падал на
  старте;
- `ModuleLoader` грузит сборку по записи `DynamicModules` (`Key`, `Backend.AssemblyPath`,
  `Frontend.RemoteUrl`) и подключает её контроллеры своим `AssemblyPart`.

Проект — `Microsoft.NET.Sdk.Web`, `OutputType=Library`, единственный `ProjectReference` — на
Core, плюс `JwtBearer` (ради claim `sub`, как у Notes и Spend). `ImageEditorSubsystem : IAppSubsystem`
с `Key = "imageeditor"`: гейт читает `Subsystems:ImageEditor:Enabled`, ключи конфигурации без учёта
регистра. Ключ `image-editor` через дефис дал бы секцию `Subsystems:image-editor`, поэтому не он.
Фич-флаг владельца остаётся `image-editor`. Ключ записи `DynamicModules` при переносе (П1) —
`imageeditor`, как у подсистемы: по нему `ModuleLoader` читает гейт, а фронт сверяет `ActiveKeys`
и id remote. Каталог dll и путь remote остаются `image-editor`.

**Выключить модуль можно двумя способами**, оба уже работают у Notes:

- `DynamicModules[imageeditor].Enabled=false` — dll не грузится вовсе;
- `Subsystems:ImageEditor:Enabled=false` — `ModuleLoader` отказывает до загрузки.

В обоих случаях ручки редактора отвечают `404`: контроллеров нет в составе MVC. Это лучше, чем у
статических Web-вертикалей: у них выключение гейтом даёт `500` (`Program.cs`, комментарий про
`ApplicationPart`).

**Почему не обычная вертикаль.** Андрей просил, чтобы модуль встраивался отдельно. Динамический
модуль подключается и выключается записью конфига, а его dll лежит отдельным файлом. Обычная
вертикаль этого не даёт, а ещё отвечает `500` при выключенном гейте.

**Жёсткое ограничение формы: у динамического модуля не может быть своих NuGet-пакетов.**
`ModuleLoader` грузит сборку в `AssemblyLoadContext.Default`, зависимости резолвятся по
`deps.json` Main. Пакета, которого нет в замыкании Main, в рантайме просто не будет. Отдельный
контекст загрузки ADR-014 отверг. Отсюда разрез по растру ниже и новый сторож: **каждый
`PackageReference` модуля обязан быть в замыкании пакетов Main** (сейчас у Notes и Spend так
только по совпадению).

**Что остаётся в `Images`:**

| Остаётся в `Images` | Почему |
|---|---|
| генерация аватаров: `IImageGenerator`, драйверы fal/glif, `ImageGenerationService`, `ImageBackfillService` | другая фича, редактор её не использует |
| `ImageGenerationSettingsStore` и `ImagePlaces` (включая место `image-editor`) | выбор поставщика по месту — функция админки генерации, общая для мест |
| **`SkiaImageRaster` и пакеты SkiaSharp** | модуль не может нести нативный пакет (см. выше). Растр — общая инфраструктура картинок, ресайз аватаров станет вторым потребителем |

**Что переезжает в модуль** — всё остальное из `Images/Services/ImageEditor`: `Jobs`

`IImageEditor`, а генерация аватаров ими не пользуется. У `FalImageEditor` с аватарами общие
только именованный клиент `"fal"` (его регистрирует Main) и ключ `Fal:ApiKey` из конфигурации.
Типов обеих вертикалей здесь нет, поэтому шов не нужен.

#### 10.2. MCP-сервер `image-editor`

**Тулсет живёт в модуле**, по прецеденту `NotesToolset`: `ImageEditorToolset :
IMcpParameterizedToolset` регистрируется в `ImageEditorSubsystem.Register`, в `Program.cs` его
нет. Схемы (`ImageEditorToolset.Schemas.cs`, шаг 1) переезжают из Main вместе с ним. Маршрут
общий, `POST /mcp/image-editor/{sessionId}`, `McpToolsetRegistry` находит тулсет среди
`IEnumerable<IMcpToolset>`. Main тулсет не тянет.

**Решение «ехать ли серверу в ход» остаётся в Main.** Шва «вертикаль сама добавляет сервер в
конфиг хода» нет ни у кого: у каждого сервера свой record в `LlmSessionContext` и свой
`Build*Context` в `SessionManager`, и Notes, чей тулсет уже в модуле, устроен так же. Заводить
общий контрибьютор MCP-серверов ради второго потребителя не стоит, это отдельное решение по
ADR-012. `BuildImageEditorContext` проверяет `Session.ImageChat != null`, флаг `image-editor` у
владельца **и наличие тулсета `image-editor` в `McpToolsetRegistry`**. Последнее — новое. Если
модуль не загружен, а контекст собран, CLI получит сервер, который отвечает `404`, и в ход
приедет «fetch failed». Наличие тулсета — свойство процесса, а не хода, поэтому
`McpToolsetStabilityTests` не страдают. Проверку «подсистема `images` включена» из §2 заменяет
именно эта.

#### 10.3. Фронт: MF-модуль `frontend/modules/image-editor`

**Форма — как у `notes` и `spend`.** Код фичи переезжает в `src/features/imageEditor/`
(компоненты, `api`, хуки). В `frontend/modules/image-editor/` лежит только MF-обёртка:

- `vite.config.ts` с `name: 'aihome_image_editor'`, `exposes: { './subsystem' }`,
  `remotes: { aihome_shell }`, shared `react`/`react-dom` singleton;
- `subsystem.tsx` с **async boundary**: сначала `await import('aihome_shell/kit')`, потом
  манифест. Иначе редактор молча не зарегистрируется, как было у `spend`;
- `package.json`, dev-порт 5176, прокси `/image-editor-remote` в `vite.config.ts` хоста,
  `build:image-editor` в цепочке `npm run build`, запись `Frontend.RemoteUrl:
  "/image-editor-remote/remoteEntry.js"` в `DynamicModules`.

Ядро редактор получает **только через `aihome_shell/kit`** — широкий неверсионируемый кит
внутренних подсистем. `design-kit` для внешних модулей тут не подходит: он узкий, в нём нет `api`,
`nav`, `signalr` и сторов. В кит добавляется то, чего в нём нет и что редактор уже использует:

- `useMe`;
- `useFeature`/`FLAGS`;
- `NAV_CHANGE_EVENT`;
- низкоуровневый `request` из `lib/offline` (или `api/imageEditor.ts` переписывается на `api`).

`onMessage` и `onReconnected` в ките уже есть.

`ModelsSpendModal` — это код **другой подсистемы** (`spend`). Модуль не может импортировать
модуль, поэтому «Модели и расход» открывается навигацией на раздел или action-слотом, который
вкладывает `spend`.

**Главное правило модуля: ни одного относительного импорта из ядра.** Всё, что импортировано из
`src/components`, `src/hooks`, `src/lib` мимо кита, соберётся **второй копией** внутрь remote. Для
`ChatPanel` это второе SignalR-соединение (`let connection` в `signalr.ts` — синглтон модуля) и
вторые сторы черновиков, персон и сессий. Сторож — правило `no-restricted-imports` в eslint для
`src/features/imageEditor/**`: разрешены кит, собственная папка и `types`. Мутация: импорт
`hooks/useSession` краснеет.

**Встраивание чата — ядро отдаёт модулю слот, а не `ChatPanel` через кит.**

Варианты:

| Вариант | Один инстанс чата | Контракт между модулем и ядром | Решение |
|---|---|---|---|
| А. `ChatPanel` в бандле модуля | нет: вторая копия SignalR и сторов | — | отвергнут |
| Б. `ChatPanel` экспортируется через `aihome_shell/kit` | да (общий ESM-граф) | все пропсы `ChatPanel` (3 000 строк, 74 импорта) плюс `Composer` и черновики для заглушки до создания чата | отвергнут |

Устройство варианта В:

- **Кто рендерит редактор.** Каркас больше не импортирует `ImageEditorHost` в `App.tsx`. Он рисует
  render-слот `app-overlay`, и модуль вкладывает туда свой хост редактора.
- **Как чат попадает в модуль.** Контекст слота несёт `{ ImageChat: ComponentType<ImageChatSlotProps> }`.
  Прецедент — `QuickActionNoteCtx { ActionButton }`: ядро передаёт компонент в render-функцию
  подсистемы.
- **Где живёт `ImageChatSlot`.** В ядре: `src/features/chat/imageChat/ImageChatSlot.tsx`. Внутри
  `ChatPanel` с `embedded` и `hideHeader`, заглушка `ImageChatComposerStub` до создания чата и
  переход «заглушка → `ChatPanel` с `pendingMessage`».
- **Пропсы `ImageChatSlotProps`** (тип объявлен в `registryCore.ts`, как остальные контексты
  слотов):
  - `projectId`, `sourcePath`;
  - `sessionId: string | null`;
  - `draftKey` (псевдоключ `image:{projectId}:{path}`);
  - `leadIn: ReactNode` (первая строка «Чат привязан к…» с кнопками);
  - `prepareSend(text, paths) → { text, paths, snapshot }`;

- **Что меняется в `ChatPanel`.** Пропсы из §6 (`hideHeader`, `prepareSend`, `pendingMessage`
  объектом, `leadIn`) — правки **ядра**, модулю они не видны.
- **Карточки ленты** — обычное направление «модуль вкладывает в слот ядра». В `ChatItemView`
  появляется слот `chat-item-tool` с ключом по имени инструмента (`mcp__image-editor__*`) и по
  `kind` записи (`image_launch`, `image_file_moved`). Модуль вкладывает `ImageLaunchCard`,
  `ImagePromptCard` и тихие строки. Прямых веток `if` по именам инструментов редактора в ядре
  нет.
- **`ImageEditorBridge`** — React-контекст **модуля**. Редактор оборачивает им `<ImageChat>`, и
  карточки внутри `ChatPanel` его видят: контекст проходит сквозь компоненты ядра, а провайдер и
  потребитель — один инстанс модуля. В полном чате провайдера нет, и кнопка одна — «Открыть в
  редакторе».
- **`ChatCard`.** Значок и миниатюра — render-слот `chat-card-badge`. Клик «открыть в редакторе» —
  через action-слот (ниже).

**Вход из дерева файлов остаётся.** `FileExplorer` и `FileViewer` перестают импортировать
`isEditableImage`/`openImageEditor`/`ImageEditorEntryButton`. Вместо этого:

- action-слот `image-editor` с `ImageEditorOpenerApi { isEditable(path), open(target) }`, по
  прецеденту `AiNoteOpenerApi`. Пункты «Редактировать картинку» и «Нарисовать картинку»
  показываются, если есть вклад и включён флаг;

Стор `openImageEditor` (module-level `listeners`) переезжает в модуль целиком. Ядро зовёт его
только через `action`, поэтому инстанс один.

**Деградация.** Если remote не загрузился, раздела и пунктов меню нет, а оболочка работает
(`loadSubsystemRemotes`). Карточки `mcp__image-editor__*` рисуются общей карточкой `tool_use`,
чаты картинок открываются как обычные — так же, как при выключенном флаге.

#### 10.5. Риски и объём

1. **Вторая копия чата внутри remote (MF × чат ядра) — главный риск.** Один случайный
   относительный импорт из ядра, и в бандле модуля окажется своя копия `signalr.ts` и сторов. Лента
   будет молчать или дублировать события, а видно это только на живом стенде. Защита тройная:
   чат приходит слотом (10.3), eslint-сторож в модуле и проверка чанков в шаге 18.
2. **Контекст React через границу MF.** `ImageEditorBridge` работает, потому что его провайдер и
   потребители — один инстанс модуля. Контексты ядра (`ChatProjectContext` и другие) модуль
   обязан брать **из кита**, иначе получит другой объект контекста и `undefined` без ошибки. Это
   ловит тот же eslint-сторож.
3. **Async boundary.** Без `await import('aihome_shell/kit')` в `subsystem.tsx` модуль молча не
   регистрируется: грабли `spend`, описаны в его `subsystem.tsx`.
4. **Динамический модуль без своих пакетов.** Если редактору когда-нибудь понадобится пакет, он
   ляжет в `Images` или в Main, но не в модуль. Сторож «пакеты модуля ⊂ Main» делает это правило
   видимым.
5. **Цели копирования dll.** Одна цель вместо двух — прод не стартует после `publish -o`.
   Проверка в П1 — публикацией во временный каталог.
6. **Столкновение namespace** `Services.Images.Editing` с корнем `Images` — сторож молча принял
   бы код модуля за код `Images`. Лечится переименованием в П1.
7. **Конфликты с шагами 5–6.** П1 и П2 стартуют только после коммитов 5 и 6, в окно переноса
   других исполнителей в ветке нет. `git mv` отдельным коммитом сохраняет историю для ревью Глеба.
8. **Мёртвый MCP-сервер.** Контекст собран, а модуля нет → «fetch failed» у всех инструментов
   хода. Закрыто гейтом «тулсет в реестре» (10.2) и тестом.
9. **Задержка первого открытия.** Remote грузится на старте вместе с остальными
   (`loadSubsystemRemotes` в `App.tsx`), первое открытие редактора не ждёт сети. Если Андрей
   заметит, что старт стал медленнее, remote можно грузить лениво при первом входе, но не раньше
   замера.

**Объём.** Перенос — **~3,5–4,5 дня работы**: П1 1,5–2 дня, П2 2–2,5 дня. Добавки к шагам 10, 13,
14 и 15 за швы и слоты — ещё **~1,5–2 дня**. По календарю П1 и П2 идут параллельно, добавки
раскладываются по окнам 5–7 плана. Итог — **+~3–4 календарных дня** к ~3,5 неделям из §8. Узким
местом остаётся фронт.

## Последствия

- В продукте появляется второй «типизированный» чат после десктопного: `Session.ImageChat` и
  MCP-сервер, который есть только в нём. Следующему такому типу стоит завести общее
  `Session.Kind`, но не раньше третьего потребителя.
- Агент впервые тратит деньги сам, без подтверждения. Защита — цена в карточке, отмена,
  потолок 2 запуска на ход, отказ на делегированных ходах и учёт трат с `Initiator = agent`.
  Лимиты по деньгам остаются волной 2 ADR-017.
- Состояние редактора переезжает на сервер. Это цена запуска при закрытом редакторе, зато
  заодно появляется «продолжить правку» на другом устройстве.
- В решении появляется первая библиотека изображений — SkiaSharp (MIT) в `Images`, с нативной
  сборкой под платформу. Цена — RID в каждой точке публикации (иначе +0,4 ГБ нативки на выкладку)
  и собственные `AutoOrient` и ступенчатый ресайз, которых у Skia нет из коробки.
- «Обсудить с Claude» и блок `image-prompt` исчезают. ADR-017 §6 остаётся как история решения.
- Редактор становится третьим динамическим модулем после Notes и Spend (раздел 10) и первым,
  которому ядро отдаёт свой чат через слот. Цена — ~3,5–4,5 дня переноса и новые швы в Core
  (`IImageChatSessions`, `IImagePlaceSettings`, `IDelegatedTurnGate`, перенос `IImageRaster`).
  Выигрыш — редактор выключается записью конфига, Main его типов не видит, основной бандл фронта
  его кода не несёт.
