# КТ0 · Ворота волны 4: четыре свойства живого CLI в детской песочнице

Протокол проверок на живом CLI до начала кода волны 4. Источник: ADR-041 ред. 5 (решения 48–59, И8), разрез Александра §11.3 «КТ0». Задача трекера: 8a89b1bb.

## Вердикт

**КТ0: 1 — держит; 2 — держит (с важным уточнением про `blocked_path`); 3 — держит (с оговорками про синтаксис allow и trust); 4 — держит.** Блокера нет: граница на `can_use_tool` на живом CLI 2.1.325 работает, волна 4 может идти с планом «один `cc-sandbox`, граница через `ChildPermissionDecision`».

## Условия прогонов

- Контейнер: живой `cc-sandbox` (тот же, что у продукта), `docker exec`, uid=1000(app).
- Бинарник: `/opt/claude-host/versions/2.1.325` — ровно тот путь, который сервер резолвит для контейнерных прогонов (`DockerProcessRunner.ResolveClaudeCommand`, `backend/ClaudeHomeServer.Execution/Services/Execution/DockerProcessRunner.cs:46-55`, по цели симлинка хоста `~/.local/bin/claude` → `…/versions/2.1.325`).
- **Версия CLI (критерий c2):** `docker exec cc-sandbox claude --version` → `2.1.325 (Claude Code)`. Значение конфига сервера: запись `claude-cli-update.json` в данных сервера — `"current": "2.1.325"` (latest 2.1.327 ещё не ставилась). Совпадает.
- Аргументы (как в постановке): `--print --verbose --output-format stream-json --input-format stream-json --permission-prompt-tool stdio --permission-mode default --tools Read,Glob,Grep,Write,Edit`.
- cwd прогона: `/projects/kt0_20261119/A`; рядом `/projects/kt0_20261119/B/secret.txt` (содержимое `SECRET-CONTENT-KT0`).
- Авторизация модели: через шлюз LLM сервера токеном живой сессии-оператора (`ANTHROPIC_BASE_URL=http://host.docker.internal:80/gw/t/<turnId>/llm` + `X-Turn-Token` в `ANTHROPIC_CUSTOM_HEADERS`) — тот же механизм, что у продуктовых ходов (`ClaudeSession.BindGatewayTurn`, `backend/ClaudeHomeServer.Llm/Claude/ClaudeSession.cs:1285-1292`); имя хоста `host.docker.internal` — как у продукта (`SandboxManager.cs:16,191`; оно же в `AllowedHosts` сервера). Модель — qwen3.8-flash-500k (маршрут сессии-оператора). Логика прав `can_use_tool` — на стороне CLI, от модели не зависит.
- Драйвер: `docs/research/kt0-driver.mjs` (эмулятор сервера: шлёт user-сообщение, ловит `control_request/can_use_tool`, отвечает `control_response` allow/deny, пишет поток дословно). Обёртка одного прогона: `docs/research/kt0-run.sh` (env берёт из сессии вызывающего). Полные стрим-логи: `docs/research/kt0-logs/*.jsonl` (в репозитории `.jsonl`: `*.log` гитигнорен, `.gitignore:88`).
- Подготовка: `.claude.json` контейнера получил `projects["/projects/kt0_20261119/A"].hasTrustDialogAccepted: true` (способ, который сам CLI предлагает в своём предупреждении) — иначе `permissions.allow` из project-settings игнорируется (см. «Наблюдения»).

Команды прогона (пример полной, для всех случаев меняется prompt/флаги):

```bash
bash docs/research/kt0-run.sh r1a 'Используй только инструмент Read. Прочитай файл ../B/secret.txt (относительный путь) и дословно скажи его содержимое.'
```

## П.1. Read/Glob/Grep за пределами cwd — спрашивает ли до чтения

Шесть прогонов (инструмент × относительный/абсолютный путь), политика драйвера — allow. Все шесть получили `control_request can_use_tool` ДО `tool_result` (критерий c3):

| # | прогон | инструмент | путь в запросе пользователя | `can_use_tool` | `tool_name` в запросе |
|---|--------|-----------|---------------------------|----------------|----------------------|
| 1 | r1a | Read | `../B/secret.txt` | есть (1) | Read |
| 2 | r1b | Read | `/projects/kt0_20261119/B/secret.txt` | есть (1) | Read |
| 3 | r1c | Glob | `../B` (pattern `secret.txt`) | есть (1) | Glob |
| 4 | r1d | Glob | `/projects/kt0_20261119/B` (pattern `**/secret.txt`) | есть (1) | Glob |
| 5 | r1e | Grep | `../B` (pattern `SECRET-CONTENT-KT0`) | есть (1) | Grep |
| 6 | r1f | Grep | `/projects/kt0_20261119/B` (тот же pattern) | есть (1) | Grep |

Дословный фрагмент r1a.log (control_request — до любого tool_result):

```json
{"type":"control_request","request_id":"5fcc59e3-…","request":{"subtype":"can_use_tool","tool_name":"Read","display_name":"Read","input":{"file_path":"/projects/kt0_20261119/B/secret.txt"},"description":"/projects/kt0_20261119/B/secret.txt","permission_suggestions":[{"type":"addRules","rules":[{"toolName":"Read","ruleContent":"//projects/kt0_20261119/B/**"}],"behavior":"allow","destination":"session"}],"decision_reason":"Path is outside allowed working directories","decision_reason_type":"workingDir","server_policy_ask_only":true,"tool_use_id":"call_283830ebb15d4cdcaa99cd5d"}
```

После нашего `control_response` allow в том же потоке:

```json
{"type":"user","message":{"role":"user","content":[{"tool_use_id":"call_283830ebb15d4cdcaa99cd5d","type":"tool_result","content":"1\tSECRET-CONTENT-KT0\n2\t"}]}, …}
```

**Отказ читает молча (r1g, политика deny):** `tool_result` вернулся ошибкой с нашим сообщением, содержимое файла в поток не попало (`grep -c SECRET-CONTENT-KT0 r1g.log` → 0):

```json
"tool_result","content":"КТ0: отказ по политике протокола","is_error":true,"tool_use_id":"call_404d4038bc4f461597461d52" … "tool_result_meta":[{"id":"call_…","non_execution_kind":"permission-rule", …}]
```

Модель после отказа повторила Read (второй `can_use_tool` в r1g) — тоже отклонён. CLI сам объясняет причину запроса: `"decision_reason":"Path is outside allowed working directories"`, `"decision_reason_type":"workingDir"`.

**Вердикт п.1: держит.** Выход за cwd спрашивается для всех трёх инструментов, относительный и абсолютный путь одинаково; без разрешения файл не читается.

## П.2. Символические ссылки

Структура: `A/link -> ../B/secret.txt` (файл), `A/dirlink -> ../B` (каталог).

| # | прогон | вызов | `can_use_tool` | `input.file_path` | `blocked_path` |
|---|--------|-------|----------------|-------------------|----------------|
| 1 | r2a | `Read ./link` | есть (1) | `/projects/kt0_20261119/A/link` | `/projects/kt0_20261119/B/secret.txt` |
| 2 | r2b | `Read ./dirlink/secret.txt` | есть (1) | `/projects/kt0_20261119/A/dirlink/secret.txt` | `/projects/kt0_20261119/B/secret.txt` |
| 3 | r2c | `Glob **/secret.txt` в `./dirlink` | есть (2) | pattern+`path: ./dirlink` | `/projects/kt0_20261119/B` |

Дословный фрагмент r2a.log:

```json
"subtype":"can_use_tool","tool_name":"Read","display_name":"Read","input":{"file_path":"/projects/kt0_20261119/A/link"},"description":"link","blocked_path":"/projects/kt0_20261119/B/secret.txt", …
```

**Вердикт п.2: держит.** Симлинк не читает молча — ни на файл, ни через каталог; Glob через симлинк тоже спрашивает.

**Уточнение, важное для Б10:** при симлинке `input.file_path` — путь ссылки ВНУТРИ cwd, а наружу указывает отдельное поле `blocked_path` (разрешённая цель ссылки). Если `ChildPermissionDecision` будет судить по `input.file_path`, симлинк на чужую папку ошибочно пройдёт как «внутри cwd». У Glob в этом прогоне `input.path` — относительный (`./dirlink`, r2c): относительные значения в `input` бывают (см. наблюдение 7). Требование к Б10: **ни одному пути в `control_request.input` (`file_path`, `path`) не доверяем как абсолютному — резолвить каждый такой путь против cwd ХОДА; при `blocked_path` решение принимается по нему.**

## П.3. Project-settings: хук, allow, агент — с `--setting-sources user` и без

В `A/.claude/settings.json`: хук `PreToolUse` (matcher `*`, команда `touch /projects/kt0_20261119/A/hook-fired.marker`) и `permissions.allow`. В `A/.claude/agents/x.md` — агент `x`.

Прогоны (маркер удалялся перед каждым):

| # | флаги | allow в settings | маркер хука | `can_use_tool` на Read вне cwd | агент `x` в `init.agents` |
|---|-------|------------------|-------------|-------------------------------|--------------------------|
| r3a | без | `["Read(/**)"]` | **есть** | есть (1) | есть |
| r3b | `--setting-sources user` | `["Read(/**)"]` | **нет** | есть (1) | нет |
| r3c | без | `["Read(//projects/**)"]` | **есть** | **нет** (прочитал напрямую) | есть |
| r3d | `--setting-sources user` | `["Read(//projects/**)"]` | **нет** | есть (1) | нет |

- Критерий c4 (маркер-файл): r3c/r3d — две записи одного сценария, без флага маркер появляется (`-rw-r--r-- 1 … hook-fired.marker`), с флагом — нет. Подтверждено и на r3a/r3b.
- `init.agents` без флага содержит `"x"` (r3a/r3c: `"agents":[…,"x"]`); с флагом — `["claude","Explore","general-purpose","Plan","statusline-setup"]` (r3b).
- allow: без флага и с корректным синтаксисом абсолютного пути (`Read(//projects/**)`) CLI **не спрашивает** (r3c: `can_use_tool=0`, содержимое прочитано); с `--setting-sources user` — спрашивает (r3d). То есть флаг гасит project-settings целиком: и хуки, и allow, и агентов.
- Оговорка синтаксиса: `Read(/**)` из карточки задачи абсолютные пути НЕ покрывает (r3a спросил, хотя allow был в файле и workspace trusted). Для абсолютных путей в Claude Code двойной слэш: `Read(//…)`.

**Вердикт п.3: держит.** С `--setting-sources user` хук не срабатывает, allow не действует, агент не виден. Дополнительное требование к конфигурации детской песочницы: собственные allow-правила ребёнка в его папке не сработают без trust workspace (см. «Наблюдения») и без корректного синтаксиса путей.

## П.4. `.mcp.json` против `--strict-mcp-config`

В `A/.mcp.json` stdio-сервер `kt0-dot-mcp` (`node /projects/kt0_20261119/kt0-mcp.mjs`); в `--mcp-config` (отдельный файл `kt0-mcp-config.json`) — сервер `kt0-cli-mcp` (тот же скрипт).

Контроль (без `--strict-mcp-config`, прогон r3c, init-событие):

```json
"mcp_servers":[{"name":"kt0-dot-mcp","status":"connected","source":"project"}]
```

r4b (`--strict-mcp-config --mcp-config /projects/kt0_20261119/kt0-mcp-config.json`):

```json
"mcp_servers":[{"name":"kt0-cli-mcp","status":"connected","source":"dynamic"}]
```

`kt0-dot-mcp` в init нет — сервер из `.mcp.json` не поднялся.

**Вердикт п.4: держит.** С `--strict-mcp-config` поднимается только то, что передал сервер (`source:"dynamic"`); project-`.mcp.json` игнорируется.

## П.5. Вспомогательное для Б10: Write/Edit внутри cwd в режиме default

| прогон | вызов | `can_use_tool` |
|--------|-------|----------------|
| smoke2 | `Read ./hello.txt` | **нет** — прочитал сразу |
| r5a | `Write ./new.txt` | **есть** (`"input":{"file_path":"/projects/kt0_20261119/A/new.txt","content":"kt0-new"}`) |
| r5b | `Edit ./hello.txt` | **есть** (`"input":{"file_path":"/projects/kt0_20261119/A/hello.txt","old_string":"hello kt0","new_string":"hello kt0 edited",…}`) |

Фиксация как есть: в `--permission-mode default` чтение внутри cwd разрешения не спрашивает, запись/правка внутри cwd — спрашивает на каждый вызов. Для Б10 это означает: `ChildPermissionDecision` будет получать запросы и на записи внутри папки предмета — политика «allow всё внутри cwd» нужна и для Write/Edit, иначе каждый ход ребёнка будет стоять на двух подтверждениях.

## Наблюдения, выходящие за вопросы протокола (но важные для волны)

1. **`blocked_path`** — при симлинках именно он указывает наружный путь (см. п.2). Требование к Б10: ни одному пути в `control_request.input` (`file_path`, `path`) не доверяем как абсолютному; резолвить каждый такой путь против **cwd хода**; при `blocked_path` решение принимается по нему.
2. **Trust workspace.** До установки `hasTrustDialogAccepted` CLI писал в stderr: `Ignoring 1 permissions.allow entry from .claude/settings.json: this workspace has not been trusted.` Т.е. даже без `--setting-sources user` allow-правила из папки предмета молча игнорируются, пока workspace не принят. С `--setting-sources user` это неважно (их всё равно нет), но для любых будущих «разрешений самого ребёнка» — блокирует.
3. **CLI подсказывает правила:** в каждом `can_use_tool` есть `permission_suggestions` (addRules вида `//projects/…/B/**`) — их не надо применять, но видно, что CLI считает «правильным» разрешением.
4. **Причина запроса в самом запросе:** `decision_reason`/`decision_reason_type:"workingDir"` — сервер может логику границ не дублировать, а верифицировать.
5. **Отказанное исполнение помечено:** `tool_result_meta[].non_execution_kind:"permission-rule"` — инструмент не исполнился, это различимо в потоке.
6. **Версионная зависимость:** changelog 2.1.327 (ещё не поставлена: `"latest": "2.1.327"`) содержит «Changed path checks to refuse some symbolic links» и «Changed what counts as inside a working directory, so some paths now ask for permission» — поведение п.1/п.2 может измениться на следующей версии; автообновление CLI хоста (`ClaudeCliAutoUpdateOps`) поднимет симлинк, и контейнерные прогоны уйдут на новую версию. Протокол снят на 2.1.325 — версии продукта на сегодня.
7. **Ни один путь в `control_request.input` не гарантирован абсолютным — ни `file_path`, ни `path`.** Read: в r1a абсолютный путь `/projects/kt0_20261119/B/secret.txt` записала сама модель в `tool_use` (в логе `tool_use.input.file_path` и `control_request.input.file_path` — одинаковые), а относительного `file_path` нет ни в одном из 19 логов: «CLI абсолютизирует `file_path` у Read» нашими прогонами не доказано и гарантией не считается. Glob/Grep несут `path` дословно, как его записала модель: r1c — Glob, `input.path = "../B"`; r1e — Grep, `input.path = "../B"`; r2c — Glob, `input.path = "./dirlink"`; абсолютные значения у них ровно там, где их записала модель (r1d, r1f). Требование к Б10: **ни одному пути в `control_request.input` (`file_path`, `path`) не доверяем как абсолютному — резолвить каждый такой путь против cwd ХОДА (не cwd сервера); при `blocked_path` решение принимается по нему.**
