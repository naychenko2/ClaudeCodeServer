# Канал к живому браузеру пользователя (для ADR-008)

**Дата:** 2026-08-19
**Связанный ADR:** [ADR-008 Десктопный агент](../adr/ADR-008-desktop-agent.md)
**Статус:** проверка фактов проведена, прототип не делался
**Источник:** проверка по документации Chrome, исходникам Chromium и issue-трекерам

> Зачем: спайк UIA показал, что браузер — худший класс окон для UIA-снапшота (Chromium
> строится до 17.4 с, 12.6 % коллизий на безымянных `Pane`, ленивая материализация дерева).
> При этом браузер — самый частый сценарий автоматизации. Проверяли, есть ли путь лучше.

## Что уже есть в продукте

Плагин `playwright@claude-plugins-official` (`ClaudeRuntimeSettings`), 24 инструмента
`browser_*`, гейт по tool-ключу `browser` персоны, по умолчанию выдан только тестировщику.
Он поднимает **свой** инстанс браузера с чистым профилем.

Отсюда граница, которая и определяет всю задачу:

| | Браузер агента (есть) | Браузер пользователя (нет) |
|---|---|---|
| Профиль | чистый, свой | живой, с вкладками и SSO |
| Логины | агент логинится сам | уже залогинен человек |
| Сценарий | проверка UI, публичные сайты | «посмотри в моём CRM», «заполни, я уже вошёл» |

Playwright второй столбец не закрывает и закрыть не может: профиль живого Chrome занят.

## Проверенные факты

**CDP к обычному Chrome на дефолтном профиле — закрыт.** С Chrome 136 (март 2025)
`--remote-debugging-port` и `--remote-debugging-pipe` игнорируются, если каталог профиля
дефолтный; мотивация — кражи кук после включения App-Bound Encryption. Проверка живёт в
`remote_debugging_server.cc` под `BUILDFLAG(GOOGLE_CHROME_BRANDING)`, то есть касается
branded-сборок Chrome (Chromium и Chrome for Testing не затронуты). Флага-разрешителя нет,
политика `RemoteDebuggingAllowed` умеет только запрещать. Копирование профиля не спасает:
App-Bound Encryption привязан к исходному каталогу.

**Санкционированный путь к живому профилю появился в Chrome 144** (декабрь 2025):
`chrome://inspect#remote-debugging`, пользователь включает приём отладочных подключений,
на каждое подключение — диалог с фокусом по умолчанию на отказе, разрешение не запоминается,
сверху висит баннер «Chrome is being controlled by automated test software». Обходит запрет
дефолтного каталога (approval-режим не проходит через `IsRemoteDebuggingAllowed`).

**Расширение MV3 даёт полный CDP.** `chrome.debugger` открывает домены `Accessibility`,
`DOMSnapshot`, `DOM`, `Input` и прочие — то есть AX-дерево и ввод доступны напрямую, без UIA.
Плашка «расширение выполняет отладку» снимается только двумя способами: запуск Chrome с
`--silent-debugger-extension-api` (правка всех ярлыков) либо установка расширения политикой
(`Manifest::IsPolicyLocation`). Запрос на «доверенные ID» висит в трекере с 2022 года.

**Service worker MV3 засыпает** через 30 с бездействия; `chrome.runtime.connectNative()`
держит его живым (Chrome 105+), но продукты с этой же схемой штатно имеют кнопку
«переподключить» — на разрыв надо закладываться как на норму.

**Native messaging на Windows:** регистрация в `HKCU` (права администратора не нужны),
манифест с явным списком `allowed_origins` (wildcards запрещены, значит ID расширения должен
быть детерминированным), формат «32-битная длина + UTF-8 JSON». Лимиты: сообщение **к хосту —
64 МиБ**, ответ **от хоста — 1 МБ**. Для нас это удачное направление: снапшот едет от
расширения к хосту (64 МиБ), а команды обратно крошечные. Chrome **сам запускает хост** как
дочерний процесс — значит наш WPF-клиент хостом быть не может, нужен тонкий шим, проксирующий
stdio в клиент по локальному IPC. Манифест читается при старте браузера — после установки
Chrome требует перезапуска.

**Недоступно расширению в принципе:** `chrome://`, Chrome Web Store (отдельный хардкод),
страницы других расширений, встроенный PDF-viewer. Cross-origin iframes требуют сборки через
messaging. Корпоративная политика `runtime_blocked_hosts` закрывает и content scripts, и CDP.

**Дистрибуция — самое узкое место.** `--load-extension` удалён из branded-сборок в Chrome 137,
внешняя установка self-hosted CRX через реестр закрыта ещё в Chrome 33, force-install политикой
требует (по справке Chrome Enterprise, эмпирически не проверено) присоединения машины к домену.
Остаётся: ручная загрузка распакованного расширения через режим разработчика — либо публикация
в Chrome Web Store, в том числе непубличным листингом.

**Как делают другие.** Claude in Chrome — расширение из Web Store + `chrome.debugger` + native
messaging к десктопному клиенту, то есть ровно предлагаемая схема; принятые ими ограничения —
вечная плашка отладки, засыпающий service worker, ручной reconnect. Chrome DevTools MCP от
самой команды Chrome по умолчанию работает с отдельным профилем, а к живому браузеру идёт
только через approval-режим 144. Browser-use и вся Playwright-школа — свой профиль.

## Следствия для ADR-008

1. **Путь — расширение MV3 + native messaging.** Approval-режим Chrome 144 даёт живой профиль
   дешевле, но открывает порт 9222 **любому локальному процессу**: это прямо противоречит
   модели, ради которой мы вводим capability-токены и физическое подтверждение. Как основной
   механизм не годится; как опциональный «турбо-режим» за флагом — приемлемо.
2. **Драйвер прозрачен для модели** (решение владельца): `desktop_ui` и `desktop_act`
   работают и в браузере, просто снапшот берётся из DOM/AX, а не из UIA. Второй набор
   инструментов рядом с 24 `browser_*` от playwright не заводим — правило именования.
   Playwright остаётся изолированным браузером тестировщика под своим tool-ключом.
3. **PDF остаётся за UIA.** Встроенный viewer расширению недоступен, значит вкладка с PDF
   обслуживается кадром и распознаванием — ещё один аргумент за единый набор инструментов
   с выбором драйвера на стороне клиента.
4. **Плашка отладки снимается только политикой или ярлыком** — то есть в обычной установке
   она будет всегда. Для нашей модели согласия это скорее плюс (видимый индикатор, который
   агент не может убрать), но в текстах интерфейса это надо объяснить заранее, иначе будет
   восприниматься как поломка.
5. **Дистрибуция становится сроком, а не деталью.** Установка без режима разработчика
   означает публикацию в Chrome Web Store и внешнее ревью, которым мы не управляем. Если
   браузерный канал попадает в релиз — процесс публикации надо начинать заранее.
6. **Разрыв соединения с расширением — штатное состояние**, а не авария: нужен явный исход
   инструмента и понятная человеку кнопка переподключения.

## Что проверить прототипом (спайк не делался)

- Время снятия AX-дерева и `DOMSnapshot` через `chrome.debugger` на тех же страницах, где
  UIA дал 17.4 с — сравнение теми же метриками, что в [спайке UIA](uia-snapshot-spike.md).
- Стабильность идентификаторов элементов после скролла и переключения вкладки.
- Объём среза страницы и сколько из него реально нужно модели.
- Поведение service worker под нагрузкой и реальную частоту разрывов.
- Два непроверенных места из справки: требование доменного присоединения для force-install
  и содержимое `DOMSnapshot` на cross-origin iframe.
