# Кнопка «Собрать архитектуру»: все уровни, галочка «С агентом», пометка «нет в коде»

Тип: research · Статус: **план, ждёт одобрения Григория** · Дата: 2026-09-27
Постановка — задача `8fcae39e` (решение Григория 2026-09-27). Предпосылки: серия Viaduct
([ADR-016](../adr/ADR-016-viaduct-architecture-section.md),
[architecture-section.md](../features/architecture-section.md)) в дереве, но не закоммичена;
реализация стартует только после её коммита.

## Решение Григория (рамка)

Кнопку «Собрать из кода» убрать; вместо неё одна кнопка **«Собрать архитектуру»**, строящая
L1–L3 (L4-код не строим — для этого «Граф»):

1. **Проход 1, детерминированный** (всегда): нынешний генератор L2/L3 + дешёвые кандидаты L1
   из конфига, стек-нейтрально, с шумоподавлением.
2. **Проход 2, агентный** — по галочке «С агентом» (по умолчанию выключена): задача
   персоне-архитектору проекта со своим чатом исполнения; агент через `arch_*` выверяет
   кандидатов, заводит людей и внешние системы, подписывает связи, заполняет описания.
3. Элементы «из кода», пропавшие из кода, помечаются «нет в коде» (тег + строка в сводке),
   не удаляются. Ручные элементы и правки не трогаются никогда.

- Конвейер прохода 1 целиком живёт в вертикали `backend/ClaudeHomeServer.Architecture`

- Поля элемента модели: `id, name, type, position, connections[{targetId,label}],

## 1. Проход 1: детерминированный (бэк)

### 1.1 Где живёт

Всё — внутри вертикали Architecture, без новых зависимостей:

- **Новый сканер `ArchitectureExternalScanner`** рядом с `ArchitectureSourceScanner`:
  обходит дерево проекта (те же фильтры каталогов и потолок 20 000) и собирает кандидатов L1.
- **`ArchitectureInputs`** дополняется записью кандидата (см. 1.2), `ArchitectureInput`
  получает `IReadOnlyList<ExternalCandidate>`.
- **`ArchitectureModelBuilder`** строит из кандидатов внешние системы уровня L1
  (`external: true`, тег `кандидат`) и связи «система проекта → кандидат» с подписью
  из источника; потолок `MaxExternalSystems = 20` (по уверенности, см. 1.3).
- **`ArchitectureModelMerger`** не меняет инвариантов: кандидаты едут тем же слиянием со
  стабильными id `gen-system-{hash("system|external:" + имя)}`; найденный элемент не
  перезаписывается, дописываются только пустые поля.
- **`ArchitectureModelGenerator`** дополняется работой с картой происхождения (см. 1.4)
  и merge-сохранением meta (перестаёт терять `updatedAt`/`updatedBy` — попутный фикс).

### 1.2 Формат кандидата

```csharp
// ArchitectureInputs.cs
public sealed record ExternalCandidate(
    string Name,          // имя секции/сервиса/клиента: "Dify", "Perplexity", "signoz"
    string? Technology,   // эвристика: "HTTP API", "docker-сервис", null
    string Source,        // человекочитаемый источник: "appsettings.json: секция Dify"
    int Confidence);      // 0..100 — для сортировки и отсечки по потолку
```

**В модель не попадает ни один адрес, ключ или значение конфига** — только имена и
источник (`Source` уходит в `description`, обрезка до 120 симв. как у тулсета). Поэтому
сканировать безопасно и `appsettings.Local.json` (имена секций не секретны), см. открытый
вопрос №3.

### 1.3 Источники и шумоподавление (стек-нейтрально)

Каждый источник — отдельная дешёвая эвристика; применяется, если файл-маркер есть в дереве:

| Источник | Что берём | Шумоподавление |
|---|---|---|
| `appsettings*.json` | секции верхнего уровня, внутри которых есть ключ-адрес (`Url`, `BaseUrl`, `Endpoint`, `*ApiUrl`) | +уверенность за соседний `ApiKey`/`Token`/`Secret`; секции из чёрного списка каркаса (`Logging`, `Kestrel`, `AllowedHosts`, `ConnectionStrings` без внешнего хоста…) — вон |
| `*.cs`: `AddHttpClient("имя")` / `AddQuietHttpClient("имя")` | имя клиента (текстовый скан, не Roslyn) | безымянные/типизированные регистрации без строкового имени пропускаем |
| `docker-compose*.yml` | имена сервисов | сервис самого приложения (`build:` на текущее дерево) — вон |
| `package.json` | **волна 2, не сейчас**: зависимости-SDK слишком шумны | — |

Дедупликация по нормализованному имени (казус «Dify в appsettings и dify в compose» — один
кандидат, уверенность складывается). Всё, что ниже порога уверенности или сверх потолка 20, —
только строка в сводке результата, не элемент.

### 1.4 Происхождение элементов и «нет в коде»

**Где хранить.** Не в модели (редактор затрёт чужие поля), а в
`model.viaduct.meta.json` — новый блок:

```json
"elements": {
  "<elementId>": {
    "origin": "code",                    // code | agent (нет записи = вручную)
    "missingSince": "2026-10-02T…",      // origin=code, пропал из свежей генерации
    "userDeletedAt": "2026-10-02T…"      // origin=code, удалён из модели человеком
  }
}
```

- Пишут блок двое: **генератор** (`origin: "code"` для каждого созданного им элемента) и
  **тулсет `arch_create_element`** (`origin: "agent"`). Элементы редактора записи не имеют —
  это и есть «вручную». Оба пишут через хранилище (`ArchitectureModelStore` получает метод
  дозаписи в meta под тем же `ArchitectureFileGate`).
- **«нет в коде»**: при прогоне генератор сравнивает элементы `origin=code` в модели со
  свежесгенерированным набором. Пропал из набора → тег `нет в коде` в модель +
  `missingSince` в meta + строка в сводке. Вернулся → тег снимается, `missingSince`
  очищается. Теги трогаются ТОЛЬКО у `origin=code`-элементов, и только эти два тега
  (`кандидат` генератор ставит при создании и больше не трогает — снять его дело агента
  или человека). Если у элемента уже 3 тега и все чужие — тег не ставим, факт остаётся
  в сводке (честное ограничение Viaduct).
- **Удалено человеком ≠ пересоздать**: элемент есть в `elements` с `origin=code`, в модели
  его нет, а свежая генерация его снова нашла → это осознанное удаление; ставим
  `userDeletedAt` и НЕ пересоздаём. Побочно закрывается сегодняшняя дырка: пересборка
  воскрешала удалённый руками сгенерированный контейнер.
- **Существующие модели без меток** — ленивая миграция при первом прогоне: id с префиксом
  `gen-` считаются `origin=code` (генератор всегда давал этот префикс), UUID — «вручную».
  Ничего заранее не переписываем.
- **Идемпотентность**: два прогона подряд без изменений кода не меняют ни модель, ни meta
  (кроме `generatedAt`); тег «нет в коде» не дублируется; сводка (`Added/Matched/…`)
  дополняется полями `Candidates`, `MarkedMissing`, `Unmarked`, `SkippedDeleted`.

Параллельные прогоны прохода 1 остаются как есть: `ArchitectureFileGate` сериализует
«прочитал→слил→записал», слияние идемпотентно — второй прогон просто повторит работу.
Отдельный замок не заводим.

## 2. Проход 2: агентный (галочка «С агентом»)

### 2.1 Контракт запуска

- `POST /api/projects/{id}/architecture/generate` получает тело `{ "withAgent": true|false }`
  (совместимо: пустое тело = false). Ответ дополняется `agentTaskId` при запуске агента.
- Порядок: проход 1 всегда выполняется первым и синхронно (как сейчас); только при его
  успехе запускается агент. Ошибка запуска агента не откатывает проход 1 — ответ несёт
  `agentError` с кодом, кнопка честно показывает «модель собрана, агент не стартовал».

### 2.2 Шов (вертикальные границы)

Architecture не может ссылаться на Tasks/Personas — заводим один узкий Core-шов по образцу
`INoteTaskBridge`/`IArchitectureCodeSource`:

```csharp
// Core/Services/Architecture/IArchitectureAgentLauncher.cs
public interface IArchitectureAgentLauncher
{
    // Создаёт задачу персоне-архитектору проекта и запускает исполнителя.
    Task<ArchitectureAgentLaunch> LaunchAsync(
        string projectId, string ownerId, ArchitectureAgentBrief brief, CancellationToken ct);
}
public sealed record ArchitectureAgentBrief(string Title, string Description, string[] Labels);
public sealed record ArchitectureAgentLaunch(string? TaskId, string? Error); // Error: no_architect | build_in_progress | tasks_unavailable
```

- **Адаптер в Main** (`Services/Composition/ArchitectureAgentLauncherAdapter.cs`, регистрация
  в `Program.cs` рядом с `TaskExecutorAdapter`): резолвит персону, зовёт
  `TaskManager.Create(...)` (`ModelTier: strong`, `Labels: ["viaduct","arch-build"]`,
  `SourceSessionId: null`) → рассылает `task_changed` → `TaskExecutionService.ExecuteAsync(task,
  auto: true)` — ровно путь `TeamWaveService`, новых механизмов нет.
- В вертикали зависимость **необязательная** (`IArchitectureAgentLauncher? launcher = null`,
  как `IArchitectureCodeSource` в контроллере): нет реализации / Tasks выключены → на
  `withAgent: true` честный `503 agent_unavailable`, проход 1 при этом отработал.
- Записи `Boundaries` не меняются: вертикаль по-прежнему видит только Core; адаптер живёт
  в Main, где `TaskManager`/`TaskExecutionService` уже разрешены.

### 2.3 Выбор персоны-архитектора

- Отдельной специальности «архитектор» в `PersonaSpecialty` нет и заводить её не надо:
  ищем по образцу `TeamPlanningService.ResolvePlanner` —
  `GetForContext(owner, projectId).FirstOrDefault(p => p.Specialty == Planner)`,
  с предпочтением персоны проекта перед глобальной (в CCS это Максим).
- Фолбэка на другие специальности **нет**: Coordinator/Analyst для выверки архитектуры —
  подмена ожиданий. Нет Planner-персоны → `ArchitectureAgentLaunch(null, "no_architect")`,
  UI показывает подсказку «Заведите персону со специальностью „Планировщик“» (без
  автосоздания — открытый вопрос №1).
- Доклад о завершении — штатный путь `TaskExecutionService.TryDeliverCompletionAsync`;
  `SourceSessionId` у задачи пуст (её создала кнопка, не чат), поэтому агент завершится
  уведомлением + итогом в карточке задачи — этого достаточно, сводка живёт в
  `resultMarkdown`.

### 2.4 Постановка задачи агенту (шаблон в вертикали)

Текст собирает вертикаль (она знает контекст сборки), шов получает готовые Title/Description.
Скелет описания (по мотивам задачи `2babc77e`, которую он заменяет):

1. Открой модель через `arch_context`. Кандидаты L1 помечены тегом `кандидат` — каждый
   **проверь по коду** (файл-источник указан в описании элемента): подтверждён → сними тег,
   заполни `technology` и описание, подпиши связи (что происходит: «RAG-поиск», «озвучка
   ответа»); шум → удали элемент.
2. Заведи недостающее для L1: людей (person-типа в Viaduct нет — внешняя система с тегом
   `пользователь`) и внешние системы, которых детерминированный проход не видит.
3. Пройди контейнеры: заполни пустые `description`/`technology`.
4. Элементы с тегом `нет в коде` — проверь: устарел → предложи удаление в сводке (сам НЕ
   удаляй), переименован → скажи об этом.
5. Ручные элементы и правки не трогай. Итог — сводка: что подтвердил/удалил/добавил
   с источником (файл:строка), что отбросил и почему.

### 2.5 Прогресс на холсте и защита от двойной сборки

- **Живая картинка бесплатно**: правки агента через `arch_*` пишут файл модели → push
  `filesChanged` → холст перезагружается (механика дефекта `ccc47ed1`).
- **Статус**: фронт получает `agentTaskId` из ответа генерации, слушает уже приходящий
  `task_changed` и держит плашку «Агент собирает архитектуру…» (ссылка «Открыть чат» на
  `task.linkedSessionId`) до `ClaudeResult`/Done. Никакого нового поллинга и событий.
- **Защита**: адаптер перед созданием ищет незавершённую задачу с меткой `arch-build` в
  этом проекте → `build_in_progress` (409 наружу). Вторая линия — существующие отказы
  `TaskExecutionService` (claim `_launching`, живая сессия). Фронт при известном живом
  `agentTaskId` дизейблит кнопку. Прогон прохода 1 без агента параллельно агентной сборке
  не запрещаем — слияние и `ArchitectureFileGate` это уже держат.

## 3. UI (реализация — после макета Веры)

Три точки, где сейчас «Собрать из кода», меняются на «Собрать архитектуру»:

| Место | Сейчас | Станет |
|---|---|---|
| Пустое состояние документа (`ArchitectureDocument.tsx:175`) | primary «Собрать из кода» | primary «Собрать архитектуру» + чекбокс «С агентом» (выключен) с подписью |
| Overflow-меню документа (`:78`) | «Пересобрать из кода» | «Пересобрать архитектуру» (галочка — в том же меню или диалоге, решает Вера) |
| Панель рельсы (`ArchitecturePanel.tsx:74`) | «Собрать из кода» | «Собрать архитектуру» (без галочки — компактный вызов = без агента) |

Тексты (черновик, Вера правит):
- Подпись галочки: «Персона-архитектор проверит кандидатов и дополнит модель — создаётся
  задача со своим чатом».
- Плашка: «Агент собирает архитектуру… · Открыть чат»; по завершении — «Агент закончил —
  сводка в задаче».
- Отказ `no_architect`: «Нет персоны-архитектора. Заведите персону со специальностью
  „Планировщик“ в этом проекте».
- Тултипы тегов `кандидат` / `нет в коде` — на холсте это обычные теги Viaduct, своей
  подсветки не делаем (волна 2, если понадобится).

Состояние галочки — в localStorage страницы (как `viaduct-prefs:{projectId}`), в модель
и на сервер не едет.

## 4. Место модели

**Новое место в `LocalActionCatalog` не нужно.** Сессия исполнителя задачи всегда идёт
местом `tasks-executor` (`SessionManager.UsageKeyFor`), а модель определяется
`TaskItem.ModelTier` (ставим `strong` — сборка редкая и тяжёлая) и матрицами персоны.
Проход 1 модель не использует вовсе. Отдельное место имело бы смысл только для one-shot
через `CheapTextRunner` — его в этой фиче нет.
