## Метод и его границы

* **Полная память вкладки — RSS процесса рендерера**, а не только JS heap. PID берётся из `SystemInfo.getProcessInfo` (браузерная CDP-сессия) — суммировать по `ps` нельзя: на машине одновременно живут чужие chromium. Снимаются **две цифры**: `VmRSS` (вся память процесса, включая разделяемые отображения) и `RssAnon` (приватная часть). Плюс `Runtime.getHeapUsage` (JS heap) и `Memory.getDOMCounters` (узлы/слушатели).
* **`performance.measureUserAgentSpecificMemory()` на стенде недоступен**: нет cross-origin isolation (`crossOriginIsolated = false`, метода нет в сборке). Это осознанная замена, а не пропуск — см. «Что не проверено».
* **Счётчик blob-URL**: перехват `URL.createObjectURL` / `URL.revokeObjectURL` через `addInitScript` (до загрузки страницы). Считаются создания, освобождения и **живые байты** (`blob.size`).
* **Живой ход**: фейковый Anthropic-совместимый движок на `127.0.0.1:18031` (python, SSE `message_start → content_block_start → пауза → 120 порций текста по 1 с`), провайдер `local-qwen` стенда переключён на него, чат создаётся с моделью `qwen3.8-27b` (`POST /api/chats`), тиры моделей владельца — на `qwen3.8-27b`. Ход реально доходит до движка (проверено по журналу юнита).
* **Стор IndexedDB в сценарии 5 не читался ни разу** — ни `getAll`, ни `openCursor`, ни `getAllKeys`. Значит, любая цепочка через `IDBCursorWithValue` в снимке принадлежит приложению.
* **Все сценарии — в одной вкладке, документ не перезагружался** (`navigation entries = 1` в снимках).

## c2 — Гонка blob в истории медиа: подтверждена

**Механика (код, `frontend/src/features/localModel/MediaHistoryCard.tsx:294-324`):**

```ts
fetch(historyFileUrl(record.id, variant, 'full'))
  .then(async res => {
    if (cancelled) return;              // ← проверка ДО чтения тела
    ...
    } else if (res.ok) {
      const blob = await res.blob();    // ← асинхронный разрыв
      objectUrl = URL.createObjectURL(blob);   // ← создаётся, даже если карточка уже умерла
      setPreview({ phase: 'ready', url: objectUrl });
    }
  });
return () => { cancelled = true; if (objectUrl) URL.revokeObjectURL(objectUrl); };  // cleanup
```

Если карточка умерла между `if (cancelled)` и `await res.blob()`, то в cleanup `objectUrl` ещё `null` → отзывать нечего, а `createObjectURL` сработает позже — на уже размонтированном компоненте.

**Прямое воспроизведение (хронология из сценария race-close, мс):**

```
fetch-start → fetch-resolved → blob-call → [карточка закрыта] → blob-resolved → createObjectURL
                                                     33105                    37468
```

`revokeObjectURL` после этого — **нет**. Счётчик: создано 1 → 2, освобождено 1 → 1, живые байты 0 → **3,69 МБ**.

Сценарий «←/→» даёт хуже: перезапуск эффекта (`[record.id, variant, record.status]`) → cleanup старого эффекта (пустой `objectUrl`) → **два** blob'а без отзыва: живые байты 3,69 → **10,81 МБ**.

**Как воспроизводилось окно.** Окно «тело пришло, `await res.blob()` ещё ждёт» делается двумя способами, оба — без правок кода приложения:
* **медленная сеть**: `Network.emulateNetworkConditions` (150 кБ/с) — тело файла едет ~26 с; в первом прогоне карточка закрывалась на +1,5 с, blob появился на +33 с ( уже после закрытия) — утечка тоже есть, просто счётчик снимали слишком рано;
* **задержка `Response.prototype.blob()`** (перехват в странице, только для файлов истории) — окно детерминированное: `blob()` виснет заданное число мс, карточка закрывается внутри этого окна.

**Control (правильный путь):** карточка открылась, файл догрузился, карточка закрыта → `create 1 / revoke 1 / живых 0` — штатный путь освобождает blob корректно.

**Дефект заведён:** «История медиа: blob-URL файла результата не освобождается при закрытии/перелистывании карточки во время загрузки».

## c3 — Живые ходы и прогрев по наведению: что держит

**Живой ход идёт** (фейковый движок, ответ 40 320 символов = 120 порций по 336 символов). Пока ход шёл, а на чат никто не смотрел:

* дельты копились — по серверной истории чата ответ записан целиком (40 320 символов), в ленте при возврате — **1 440 повторов** фразы;
* **сессия с ходом не вытесняется по LRU.** Открыто 4–13 чужих чатов, список догружал 12–16 чужих историй (потолок `useSession._store` = 8) — при возврате в чат с ходом **запрос его истории НЕ ушёл (0)**, а дельты уже были в ленте. Ровно то поведение, которое задаёт `useSession.ts:163-186`: сессия с `isWaiting` из «холодных» не считается и не вытесняется;
* прямого счётчика записей `_store` с `isWaiting:true` снять **не удалось**: стор `useSession` наружу не выставлен, а съёмка Map-ов по heap-снимку (`mapSurvey`) не классифицировала `_store` — все найденные Map-ы получили форму «прочее». Поэтому вывод о невытеснении — **поведенческий** (0 перезапросов истории при возврате), а не счётчик из кучи.

**Что реально держит память в сценарии чатов:**

| что | сколько | комментарий |
|---|---|---|
| список чатов (784–865 карточек) | RSS до 991 МБ, heap до 202 МБ (пик на 15-й секунде), потом спад до ~757/116 | список тянет десятки историй подряд; `…/history?after=-1` в полёте — не больше 2 одновременно |

| живой ход | дельты копятся в сторе сессии, пока на чат не смотрят; сессия не вытесняется | потолка по объёму у накопленных дельт нет — ограничение только «не вытеснять», но и «не выпускать» |

## c4 — Дефект 5f107f90 перепроверен без своих курсоров

**Метод:** скрипт **ни разу** не открывал курсор чтения стора (никаких `getAll`/`openCursor`/`getAllKeys`). Снимок A — сразу после выхода из чата; снимок B — через 90 с.

| | снимок A (сразу после выхода) | снимок B (+90 с) |
|---|---|---|
| JS heap used | 100,5 МБ | **50,1 МБ** |
| base64-строки | **2 PDF = 11 109 340 Б (10,6 МБ)** + прочее 0,39 МБ | PDF **нет**, прочее 0,39 МБ |
| узлов `IDBCursorWithValue` | 4 | 3 |
| узлов `IDBRequest` | 8 | 3 |

**Цепочка удержания PDF (снимок A):**

```
string 'JVBERi0xLjQKJdPr6eEKMSAwIG9iago8PC9Qcm9k' (10,45 МиБ)
  object Object (48 Б) ← base64
  object Object (28 Б) ← data
  object system / Context (24 Б) ← t
  closure (?) (28 Б) ← context
  object system / Context (28 Б) ← n
  …
```

**Выводы:**

1. **`IDBCursorWithValue` — это код приложения, а не артефакт замера.** Мой скрипт не создавал ни одного курсора → все узлы-курсоры в снимке принадлежат приложению: это его собственный проход по стору `idbRangeStamps` (`frontend/src/lib/idb.ts:113-130`), который читает **значения целиком** (`c.value`), то есть протаскивает через курсор и base64 вложений. Курсор в этом прогоне **не держит PDF** — цепочка PDF идёт через асинхронный контекст, а не через `IDBCursorWithValue`.
2. **Удержание транзиторное.** Через 90 с вложений в куче нет, heap упал со 100,5 до 50,1 МБ. То есть утверждение дефекта «**без потолка**» **не подтверждается**: наблюдается пик ~10,6 МБ сразу после выхода из чата, который рассасывается сам. Накопление возможно только если открывать чаты с вложениями быстрее, чем рассасывается (замер QA6 открывал 5–14 чатов за несколько минут — там Δheap +10…+37 МБ за прогон согласуется с этой моделью).
3. **Что делать с карточкой:** механизм «курсор» снимать из описания, оставить «незавершённая асинхронная обработка вложения» + «транзиторно, но без потолка по скорости открытия чатов». Правку (`cancelled` после `await`, отмена по размонтированию, потолок по весу в `_imageCache` — `MarkdownContent.tsx:52-59`) — по коду приложения, не в этой задаче.

**Вывод записан в карточку `5f107f90` (обновлены repro/actual/verification).**
