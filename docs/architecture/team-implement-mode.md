# Практика «Командная реализация» → режим чата

Продуктовый план. Софья (продакт-аналитик), 2026-07-28.
Статус: фича собрана целиком — планирование, раздача, волны, автономный цикл с эскалациями
и непрерывный контур. Флаг — `team-implement-mode`. Поверхности и файлы реализации —
[features.md](features.md), раздел «Командная реализация».
Э8 «Интервью и перепланирование» реализован (ветка `feature/team-implement-interview`),
ревью Глеба пройдено — вердикт APPROVE; живая приёмка (Вера) — после мержа.

## Зачем

Сегодня практика — одноразовый workflow-ход: субагенты внутри одного хода, результат
виден только в конце, прогресс не отслеживается, персоны раздаются по кругу без учёта
компетенции. Цель — превратить её в **режим чата**: чат становится штабом фичи, работа
идёт задачами на персон-исполнителей, дочерние чаты исполнения висят в иерархии под
штабом, доклады возвращаются в штаб и двигают процесс дальше.

Польза одним предложением: **крупную фичу можно поручить команде и вести её целиком из
одного чата — с планом, задачами, докладами и проверкой.**

Два принципа, из которых выведено всё остальное:

1. **Согласование — при каждом изменении плана, а не при каждой волне** (уточнено в Э8;
   до него читалось «один раз»). Человек утверждает план на входе в итерацию и каждую
   его новую версию; волны по неизменному плану идут без вопросов — защитой от разгона
   служит не согласование, а бюджет.
2. **Режим не заканчивается вместе с планом.** Пока режим включён, чат остаётся штабом:
   любая новая вводная от человека проходит тот же цикл — декомпозиция, подбор
   исполнителей, задачи, контроль исполнения.

## Решения по развилкам (согласовано с владельцем)

1. **Волны запускает координатор автоматически, под бюджетом.** Гейт
   `DenyOnDelegatedTurn(AlsoWhenExecutorSuppressed)` для чатов в режиме практики
   заменяется квотой, а не снимается «вообще».
2. **Исполнителя подбирает планировщик (LLM) по карточкам персон**, пользователь правит
   назначение в карточке плана.
3. **Подтверждение первоначального плана — карточка в ленте чата.** Волны после этого
   не согласовываются (при включённых авто-волнах).
4. **Оба режима живут:** «Командная реализация» — режим чата (эта фича),
   «Командный спринт» — нынешний быстрый workflow (переименование, см. ниже).
5. **Авто-волны — тумблер, по умолчанию включён.** Доступен при запуске и на ходу.
6. **Провал в авто-режиме: одна перевыдача, потом стоп** с вопросом и сводкой.
7. **Состав команды опционален.** По умолчанию — вся команда проекта.
8. **Режим — непрерывный контур.** Новая вводная в чате → новая волна. Работа идёт в
   волну, вопрос получает ответ без задач; границу проводит координатор.
9. **Бюджет считается на вводную** и сбрасывается с каждой новой.
10. **Эскалация — по остаточному принципу:** координатор сначала пробует справиться сам,
    зовёт человека, только когда не может.

## Сценарий пользователя

1. В композере выбирает «Командная реализация» и пишет задачу. Участников выбирать не
   обязательно — по умолчанию доступна вся команда проекта. Тумблер «Авто-волны» включён.
2. Чат помечается: бейдж в композере «Командная реализация · интервью», такой же
   маркер — в списке чатов.
3. Координатор проводит **интервью** (Э8, протокол механики «Интервью»): вопросы приходят
   карточкой с кнопками-вариантами (механизм ASK — `AskUserQuestion`), рекомендуемый
   вариант помечен, свободный ответ — через «Другое». Постановка ясна — «вопросов нет»,
   допущения уедут в карточку плана. На время интервью и планирования чат работает в
   режиме «план» — селектор в композере это показывает.
4. Координатор изучает репозиторий и публикует **карточку плана**: под-задачи, у каждой —
   исполнитель с обоснованием, файлы, волна; при Э8 — блок «Допущения».
5. Пользователь правит исполнителей прямо в карточке и жмёт «Запустить». **Согласований
   в итерации больше не будет, пока не изменится сам план.**
6. Бэкенд создаёт задачи и стартует первую волну. Дочерние чаты исполнения появляются
   под штабом в дереве.
7. Исполнители работают, закрывают задачи через `tasks_complete`, докладывают в штаб.
8. Координатор, собрав доклады, публикует сводку и **сам запускает следующую волну**.
   Если он не знает, как действовать дальше, — возврат в интервью: волны на паузе,
   вопросы, обновлённый план vN на подтверждение (Э8).
9. Волны кончились → проверка (сборка/тесты) → итоговый отчёт. **Режим не выключается:**
   бейдж переходит в «ожидание», чат готов принять следующую вводную.
10. Пользователь пишет «теперь добавь экспорт в CSV» → координатор декомпозирует, назначает
    исполнителей, ставит задачи, гоняет новую волну. Бюджет при этом обнуляется. Интервью
    на добавочной вводной — только если у планировщика есть реальные вопросы (Э8).
11. Практика завершается только когда человек выключает режим в бейдже.

## Схема

```
   композер: практика [+ участники] [+ авто] + задача
                 |
                 v
     [ЧАТ-ШТАБ помечен бейджем режима]
                 |
      координатор проводит интервью
      (вопросы -> ответы | допущения)
                 |
        координатор планирует
                 |
                 v
      КАРТОЧКА ПЛАНА в ленте
      под-задачи | исполнитель | файлы
      [Запустить] [Изменить] [Отмена]
                 |
                 v  <- единственное согласование
   бэкенд создаёт задачи и стартует волну
                 |
     +-----------+-----------+
     v           v           v
  задача A    задача B    задача C
  чат-испол.  чат-испол.  чат-испол.  <- дети штаба
     |           |           |
     +-----> доклады в штаб <+
                 |
        координатор: сводка волны
                 |
      справился сам? --нет--> ЭСКАЛАЦИЯ
            |                 карточка + push
            да                     |
            |                 ответ человека
            v                      |
      следующая волна <------------+
      (авто: без человека)
                 |
                 v
        проверка (сборка/тесты)
                 |
                 v
      +--> ОЖИДАНИЕ ВВОДНОЙ (режим жив)
      |          |
      |     человек пишет в чат
      |          |
      |    работа? --нет--> просто ответ
      |          да

```

## Непрерывный контур

Режим живёт, пока его не выключили. Стадии: `интервью → планирование → волны →
проверка → ожидание → (новая вводная) → интервью …` (стадия «интервью» — Э8; на
добавочной вводной без вопросов она схлопывается).

**Что происходит с сообщением человека в режиме.** Координатор разделяет по одному
признаку — *нужно ли для этого менять файлы*:

- **Работа** («добавь экспорт», «почини сортировку», «покрой тестами») → декомпозиция,
  подбор исполнителей, задачи, волна. Бюджет обнуляется, счётчик волн стартует заново.
- **Разговор** («почему выбрали Киру?», «что сейчас в работе?», «покажи план») →
  обычный ответ координатора, без задач и трат.

Спорный случай трактуется как разговор с уточняющим вопросом — дешевле переспросить,
чем развернуть волну на пустом месте.

**Подтверждение добавочных волн.** Первоначальный план утверждается всегда, даже при
включённом авто: это вход в итерацию. Добавочная волна (после вводной в уже идущем
режиме) публикует карточку состава, но при авто **не ждёт клика** — работа стартует
сразу, карточка информационная, с кнопкой «Остановить». Логика простая: сама вводная
человека и есть точка контроля. **Буквально человека** (M7, волна 2): агентская вводная
(`chats_send` в штаб), классифицированная координатором как работа, публикует план
неподтверждённым — он ждёт клика, как первоначальный.

## Авто-волны

**Тумблер «Авто-волны»** — в настройках механики при запуске и в бейдже режима на ходу.
По умолчанию включён. При включённом авто **волны не согласовываются вообще**: карточки
«запустить следующую?» между волнами не появляются.

- **Выключен:** после каждой волны карточка «Волна 1 закрыта. Запустить волну 2?» с
  кнопками «Запустить» / «Изменить остаток плана» / «Завершить итерацию».
- **Переключение на ходу:** снял авто во время волны — текущая доигрывает, следующая
  ждёт подтверждения. Включил, когда практика ждёт — стартует сразу.

## Эскалация и остановки

В автономном режиме худший сценарий — практика встала, а человек не знает, ждёт она его
или умерла. Поэтому **любая остановка = карточка в ленте с причиной и кнопками**, плюс
системное уведомление и web push, если человека нет в этом чате. Молчаливых пауз не бывает.

**Порядок действий координатора при проблеме:** сначала пробует сам (перевыдать задачу,
уточнить у исполнителя, пересобрать волну, откатить неудачный кусок) — в пределах
бюджета. Зовёт человека, только когда своими силами не выходит.

| Триггер | Что видит человек |
|---|---|
| Исполнитель сообщил о блокере (нет доступа, требования неясны, конфликт с чужим кодом) | «Исполнитель застрял: …» + текст блокера → «Ответить» / «Отдать другому» / «Снять задачу» |
| Задача провалилась дважды | «Задача „…" не удалась дважды» + причина → «Отдать другому» / «Пропустить» / «Завершить» |
| Расхождение с планом (нужны файлы вне владения, объём вырос) | «Работа выходит за план: …» → «Разрешить» / «Оставить в плане» / «Пересобрать волну» |
| Проверка красная после попыток починки | «Сборка/тесты не проходят: …» → «Чинить дальше» / «Завершить с замечаниями» |
| Нужно продуктовое решение (два рабочих варианта) | Вопрос координатора с вариантами |
| Планировщик не построил план по вводной (сбой или таймаут) | «План … не построился» + честная причина: у таймаута — «планировщик не уложился во время», без претензий к постановке человека → «Повторить планирование» одной кнопкой по той же вводной, без повторного интервью |
| Планировщик не знает, как действовать дальше (требования неясны) | «Нужны уточнения — волны на паузе» + вопросы интервью → после ответов план vN на подтверждение (Э8) |
| Исчерпан бюджет итерации | «Израсходовано: N задач, M волн» → «Добавить бюджет» / «Завершить итерацию» |
| Волна не двигается дольше таймаута | «Волна не двигается: задача „…" молчит» → «Перезапустить» / «Снять» / «Завершить» |
| Пользователь нажал «Остановить» | Текущие исполнители дорабатывают, новые не стартуют |

Кроме восьми остановок тем же типом карточки идут два **не-тревожных** события, и в ленте
они отличаются тоном — иначе рядовой ход событий кричал бы как сбой:

| Событие | Что видит человек |
|---|---|
| Волна закрыта, авто-волны сняты | «Волна N закрыта. Запустить следующую?» → «Запустить» / «Изменить остаток плана» / «Завершить итерацию» |
| Новая вводная ушла в работу (авто-волны включены) | «Новая вводная в работе: …» + состав списком → одна кнопка «Остановить». Работа уже идёт, решения не ждёт |

**Ответ человека — обычным сообщением в чат.** Никаких особых форм: написал, что делать,
координатор учёл и пошёл дальше с того же места. Кнопки карточки — быстрый путь для
типовых решений.

**Эскалация снизу.** У исполнителей есть `chats_report_up` — доклад в вышестоящий чат,
который по построению **не запускает там ход**. Для блокеров этого мало: в авто-режиме
доклад «я застрял» пролежал бы незамеченным до конца волны. Поэтому доклад с пометкой
блокера будит координатора и сразу даёт карточку человеку — под квотой пробуждений, чтобы
этим каналом нельзя было обойти бюджет.

**Провал задачи (авто включён):** координатор один раз перевыдаёт работу — тому же
исполнителю с учётом причины либо другому, если причина в компетенции. Второй провал той
же под-задачи — эскалация. Перевыдачи считаются отдельным потолком бюджета.

## Состав команды

Выбор участников **опционален**.

- **Проектный чат без явного выбора** — доступна вся команда проекта; планировщик
  выбирает из неё по компетенциям. В карточке плана видно, кого он взял и почему.
- **Явный выбор** сужает круг: планировщик обязан раздать работу только этим персонам.
  Нужно, когда часть команды занята или человек хочет конкретных исполнителей.
- **Глобальный чат (вне проекта)** — команды нет, поэтому участников нужно выбрать явно;
  без выбора практика не стартует и объясняет почему.

## Бюджет

Считается **на итерацию** (одна вводная человека + все волны по ней) и обнуляется с
каждой новой вводной. Логика: сообщение человека и есть точка контроля, значит сброс
безопасен, а режим может жить неделями и не упираться в потолок от первого прогона.

Дефолты (настраиваемые): **12 задач**, **4 волны**, **20 запусков исполнителей**,
**3 перевыдачи**, **10 пробуждений штаба**. Счётчики живут на `Session.TeamImplement`,
инкремент — в точке запуска на бэкенде, а не в модели.

**Ответ человека на вопросы интервью вводной не является** (Э8): бюджет не сбрасывает,
задач не разворачивает — иначе цикл «вопрос-ответ» обнулял бы потолки. Сброс — только
по вводной, которую координатор классифицировал как новую работу.

Пятая квота — **пробуждения штаба агентом** — появилась по итогам ревью: без неё бюджет
обходился соседним инструментом (доклад-блокер и `chats_send` будили координатора в обход
счётчика запусков). Расширить любой потолок может только человек кнопкой «Добавить бюджет»;
у агента такого пути нет. Волна стартует, только если помещается в остаток целиком —
иначе не стартует вовсе и даёт карточку «Бюджет исчерпан».

## Что уже готово и переиспользуется

- Атрибуция задач: `TaskItem.CreatedByPersonaId`, `SourceSessionId`, `DelegationDepth`.
- Иерархия: `Session.ParentSessionId` вычисляется из `Task.SourceSessionId` — дочерние
  чаты прикрепляются к штабу без единой новой строки.
- Доклад исполнителя в чат-источник + авто-ход постановщика (ADR-001, модель Z, CT-8).
- `chats_report_up` — промежуточные доклады снизу вверх (для блокеров нужна доработка,
  см. «Эскалация»).
- Образец режима с бейджем: `Session.WorkLoop` + `PUT /chats/{id}/loop` + бейдж в композере.
- Образец карточки-с-кнопками в ленте: `plan_review` (`StoredPlanReviewMessage`,
  `SessionHub.RespondPlan`) — тот же паттерн request/ответ, но у нас план структурный.
- Уведомления и web push — для эскалации, когда человека нет в чате.
- Дисциплина исполнителя уже в промпте `TaskExecutionService`: «НЕТ СВИДЕТЕЛЬСТВ = НЕ
  ГОТОВО», обязательный `tasks_complete` с `resultMarkdown` и `linkedFiles`.

## Переименование: «Командный спринт»

Нынешняя быстрая механика (workflow `claude-defaults/workflows/team-implement.js`:
субагенты внутри одного хода, без задач, докладов и иерархии) называется **«Командный
спринт»**. Название «Командная реализация» освобождается под режим чата.

- **Карточки в группе «Сделать» стоят рядом** и должны читаться как разные инструменты:
  у реализации — «Штаб фичи: план, задачи, исполнители», у спринта — «Быстро разбить и
  раздать субагентам».
- **Историю в лентах не ломаем.** Отправленные ходы `/team-implement {JSON}` лежат в
  истории дословно, и карточка механики рисуется по этому префиксу. Детектор держит оба
  префикса: старый маппится на «Командный спринт». Иначе прошлые прогоны превратятся в
  сырой JSON.

## Этапы

Порядок, которым фича собиралась. Работа по Э0–Э6 закрыта, Э7 — живая приёмка,
Э8 — реализован и прошёл ревью (Глеб, APPROVE); живая приёмка Веры — после мержа в master.

### Э0. Спека и макеты (Майя)
Карточка плана, карточки эскалаций, бейдж режима с тумблером «Авто» и стадиями (десктоп +
мобила, обе темы). Состояния бейджа: планирование / ждёт подтверждения / волна N /
ждёт решения / проверка / ожидание вводной. Плюс две карточки механик в группе «Сделать».

### Э1. Режим на сессии (Денис + Кира)
- `Session.TeamImplement` по образцу `SessionWorkLoop`: наличие объекта = режим активен.
  Поля: стадия, номер волны, флаг авто, id координатора и планировщика, состав
  исполнителей (пустой = вся команда), бюджет итерации, id карточки плана.
- API включения/выключения и переключения авто по образцу `/chats/{id}/loop`.
- Бейдж в композере с тумблером «Авто» и маркер в списке чатов. Выключение режима — из
  бейджа, с подтверждением.
- Критерий: режим, стадия и флаг авто переживают рестарт сервера и переключение чатов.

### Э2. Планирование по компетенциям
- Координатор = собеседник чата; чат без персоны — пикер при включении режима.
  **Гард на входе:** `PUT /chats/{id}/team-implement` отклоняет включение без координатора
  или без состава исполнителей — 400 с машинным `code`
  (`team_implement_no_coordinator` / `team_implement_no_executors`) плюс текст человеку.
  Отказ обязан приходить ДО первого хода интервью: раньше он всплывал только на построении
  плана, и целый раунд интервью (десятки минут и токены) уходил впустую.
- Планировщик подбирается по `Persona.Specialty` (Planner → Coordinator → Analyst),
  пользователь может указать явно.
- В промпт планировщика уходят **карточки кандидатов** (вся команда проекта либо явно
  выбранные): имя, роль, описание, специальность, привязки к папкам/знаниям. У каждой
  под-задачи — исполнитель и одна строка обоснования.
- Результат — карточка плана в ленте (новый тип сообщения + WS + метод хаба).
- Критерий: бэкендовая под-задача уходит бэкендеру, фронтовая — фронтендеру; обоснование
  видно в карточке.

### Э3. Раздача и волны
- «Запустить» → бэкенд создаёт задачи (`personaId` = исполнитель, `SourceSessionId` =
  штаб, `CreatedByPersonaId` = координатор) и **пакетно стартует задачи волны**.
- В описание каждой задачи: что сделать, файлы во владении, критерий готовности и — если
  штаб работает в worktree — обязательное указание рабочего дерева.
- Прогресс волны виден в ленте штаба и в дереве чатов.
- Критерий: ни одной работы вне задачи; на каждую под-задачу есть карточка задачи и
  дочерний чат.

### Э4. Автономный цикл и эскалация (самый рискованный)
- Исключение из гейта: на реакционном ходу координатора запуск исполнителя разрешён,
  **если** сессия в режиме практики и бюджет итерации не исчерпан. Иначе — прежний 403.
- Логика авто-волн; бюджет на итерацию со сбросом по вводной.
- **Блокер-доклад будит координатора** (доработка `chats_report_up`: пометка «нужна
  помощь» запускает ход в штабе).
- Все триггеры эскалации из таблицы: карточка + уведомление + push.
- Таймаут волны — страховка от молчаливого зависания.
- Обязательно к ревью Глебом: он уже ловил две лавинные дыры в этой механике.

### Э5. Непрерывный контур
- Стадия «ожидание вводной»: режим не выключается после проверки.
- Классификация сообщения человека (работа / разговор) в промпте координатора.
- Добавочная волна: карточка состава без блокировки при авто; сброс бюджета.
- Критерий: после завершённой фичи фраза «теперь добавь X» разворачивает новую волну без
  повторного включения режима.

### Э6. Переименование, тексты, «Что нового», документация
Переименование в «Командный спринт» с обратной совместимостью детектора; тексты ниже;
раздел в `docs/features.md` + пометка в `docs/personas.md`.

### Э7. Живая приёмка (Вера, Playwright)
- Основной прогон: задача на 3 под-задачи в двух волнах, состав по умолчанию (вся
  команда), одна правка исполнителя руками, **до конца без единого клика после
  подтверждения плана**.
- Продолжение: после итога — вводная «добавь ещё X» → новая волна без включения режима.
- Разговорное сообщение в режиме → ответ без задач.
- Намеренный провал исполнителя: одна перевыдача, остановка после второго.
- Блокер от исполнителя: карточка эскалации приходит немедленно, а не в конце волны.
- Исчерпание бюджета, снятие авто на ходу.
- Сначала dev, потом прод. Отдельно — прогон «Командного спринта», ни разу не гонявшегося
  вживую.

### Э8. Интервью и перепланирование (реализовано 2026-07-30, ревью Глеба — APPROVE)

Вход в итерацию становится разговором, а тупик в волне перестаёт быть гаданием:
координатор сначала спрашивает, потом планирует — и возвращается к вопросам, когда
не знает, как действовать дальше.

```
интервью -> планирование -> согласование -> волны
    ^                                         |
    +-------- «нужны уточнения» --------------+
     (волны на паузе, план vN -> согласование)
```

**Решения по развилкам (согласовано с владельцем):**

1. **Первая вводная итерации проходит интервью всегда.** Добавочные вводные в живом
   контуре — только при реальных вопросах планировщика, иначе контур станет вязким.
2. **Путь «вопросов нет»:** постановка ясна — планировщик декларирует допущения, они
   утверждаются вместе с планом (блок «Допущения» в карточке). Фейковых вопросов ради
   обязательности стадии не бывает.
3. **Протокол — тот же, что у механики «Интервью»** (скилл `oh-my-claudecode:deep-interview`),
   **канал — штатный ASK** (дополнение 2026-07-29): вопросы задаются инструментом
   `AskUserQuestion` и приходят интерактивной карточкой с кнопками-вариантами
   (готовый механизм: `AskQuestionMessage` → `AskQuestionView`, ответ уходит в ход).
   До 4 вопросов на раунд, у каждого 2–4 варианта, рекомендуемый помечен; свободный
   ответ — через вариант «Другое». Глубина standard. Своих карточек вопросов не
   заводим — переиспользуем ASK; текстовых вопросов-простыней в интервью не бывает.
4. **Перепланирование:** тупик в волне → стадия интервью (волны на паузе) → план vN →
   подтверждение карточкой **обязательно даже при включённых авто-волнах** — авто
   покрывает волны по неизменному плану, но не смену самого плана.
5. **Интервью и планирование идут в план-режиме чата** (дополнение 2026-07-29):
   на этих стадиях штаб работает в настоящем `--permission-mode plan` — правки
   запрещены на уровне permission-механики CLI, а не только списком инструментов;
   пользователь видит в композере привычный режим «план». Интервью отдельного режима
   не имеет — обе стадии живут в одном непрерывном план-режиме.

**Что делается:**

- Стадия `interview` в машине состояний режима (`TeamImplementStage`), переживает
  рестарт. Таймаут волны в ней не тикает — ожидание человека не зависание; но карточка
  «Нужны уточнения — волны на паузе» + уведомление + push обязательны (правило
  «молчаливых пауз не бывает»).
- **План-режим на стадиях интервью и планирования.** На входе в `interview` сервер
  запоминает текущий `Session.Mode` пользователя и ставит `Plan` (живому процессу —
  через `set_permission_mode`); на переходе `Confirming → Wave` (клик «Запустить»)
  возвращает сохранённый. Возврат в интервью из волны — тот же цикл. Выбор пользователя
  не затирается: после планирования чат работает в том режиме, в котором был.
- **Штатная карточка `plan_review` в штабе не используется:** `ExitPlanMode` координатору
  запрещён (тем же механизмом, что и `CoordinatorNoCode` — свойство сессии, состав
  инструментов от хода не зависит). Планирование завершается ТОЛЬКО командной карточкой
  плана — иначе пользователь получал бы два согласования подряд (штатное и наше).
- **Селектор режима в композере** на стадиях интервью/планирования показывает «план» и
  заблокирован — с тултипом «Штаб планирует. Режим вернётся после согласования плана».
- **Карточки — от лица персоны, а не от системы** (дополнение 2026-07-29). Координатор
  штаба — всегда персона, и всё, что штаб говорит человеку, должно выглядеть как её
  речь: аватар и имя в шапке каждой карточки. Автор пишется в карточку **в момент
  публикации** (`PersonaId` в `TeamPlanMessage`/`TeamEscalationMessage` и в их
  stored-слое — история переживает рестарт и смену координатора: старые карточки
  сохраняют исходного автора). Карточка плана — от планировщика, эскалации/сводки/
  бюджет — от координатора (обычно это одна персона). ASK-карточки интервью и
  текстовые ходы уже идут в чате персоны — проверить, что аватар там на месте.
  Уведомления и push эскалаций — тоже от имени персоны: «{Имя}: нужно ваше решение»,
  «{Имя} ждёт ответов по задаче» вместо обезличенного «Команда ждёт…».
- Версия плана на состоянии режима; карточка плана vN — блоки «Что изменилось» и
  «Допущения»; волна стартует только по подтверждённой последней версии.
- Правило бюджета: ответ на интервью — не вводная (без сброса потолков и без задач),
  см. раздел «Бюджет».
- **Выход из интервью без работы (M6, волна 2):** сообщение человека оказалось разговором —
  координатор завершает ход маркером `<team:talk/>`, и интервью закрывается без плана:
  свежая «итерация» возвращается в ожидание первой вводной, прерванное clarify-интервью —
  обратно в волну. Маркер, а не «просто ответь»: по голому тексту бэкенд не отличит честный
  ответ от молчаливого тупика (stall-гард). Сброс бюджета и план-режим привязаны к
  классификации (маркер `<team:work>`), а не к приёму сообщения: разговор в ожидании ничего
  не стоит и не лочит селектор.
- Протокол в промпте координатора: максимум 2 раунда вопросов на вводную; вопрос обязан
  закрывать развилку — всё остальное оформляется допущением. **Вопросы — только
  инструментом `AskUserQuestion`, не текстом** (формулировка правила уже обкатана в
  автоматизациях персон — `PersonaAutomationService`). Уведомление «Ждёт ответа» +
  push при отсутствии человека — как у permission-запросов.
- Правка критерия приёмки: «без единого клика после подтверждения плана» действует,
  **пока план не менялся**.

**Уточнения по факту реализации** (появились по ходу кода, в согласованный текст выше не входили):

- **Маркер `<escalate:clarify>`** — координатор помечает им тупик в волне (симметрично
  `<team:work>`, который закрывает интервью). Маркер переводит `TeamImplementStage` в
  `Interview` и заводит `TeamEscalation` с `Kind = NeedsClarification`.
- **Карточка `needsClarification` — без кнопок.** В отличие от остальных эскалаций из
  таблицы «Эскалация и остановки», решение по ней не кликается: ответ уходит через сами
  вопросы интервью (`AskUserQuestion`), а не через `Actions` карточки — `TeamEscalationActions`
  для этого вида пустой намеренно.
- **`PUT /chats/{id}/mode` отклоняется, пока штаб планирует.** `SessionManager.SetMode`
  бросает ошибку «Штаб планирует. Режим вернётся после согласования плана», пока у режима
  есть `SavedMode` (признак — именно `SavedMode`, а не стадия: у провайдера без поддержки
  план-режима штаб ничего не навязывает, блокировать нечего). Событие `team_implement`
  несёт это наружу полем `modeLocked` — им кормится заблокированный селектор в композере.
- **`acceptEdits`/`bypassPermissions` при включении режима поднимаются до `auto`.** Гард
  «координатор не пишет код» проверяет команду в момент permission-запроса, а в этих двух
  режимах CLI разрешения не спрашивает вовсе — запись файла через shell (heredoc, `tee`,
  `sed -i`) прошла бы мимо гарда. Поэтому и при включении режима, и при возврате режима
  после планирования (`RestoreUserMode`) `acceptEdits`/`bypassPermissions` заменяются на
  `Auto`; `Plan` и прочие режимы не трогаются (`GuardCompatibleMode`).
- **Обратная совместимость на нулевых версиях плана.** `PlanVersion`/`ApprovedPlanVersion`
  равны нулю у чатов, начатых до Э8; гард версии плана в момент старта волны при нулях
  выключен — обновление сервера не подвешивает уже идущую практику.
- **Гейт интерактивности общего ASK-правила** (отдельная задача e167a383, свой коммит):
  правило «вопрос с 2–4 осмысленными вариантами → `AskUserQuestion`, открытый вопрос —
  текстом» добавлено в системную подсказку интерактивных ходов вообще (не только штаба),
  но переиспользует уже существующий признак «есть кому ответить» — не исполнитель задачи,
  не ход автоматизации, не делегированный ход. В фоновые и агентные ходы правило не уходит,
  иначе агент ждал бы клика, которого не будет.
- **Гард молчаливого тупика расширен на интервью** (фикс ревью, коммит `d19d93df`). Тот же
  класс проблемы, что чинил Э7-фикс (координатор закончил ход, ни разу не дойдя до волны, и
  без маркера — практика висла бы без следа), проявился и на новой стадии: условие в
  `HandleTeamTurnEndAsync` расширено с `Stage == Planning` на `Stage is Interview or Planning`
  (обе — при `WaveNumber == 0`). Легитимный интервью-ход под гард не попадает: `AskUserQuestion`
  блокирует ход через `control_response`, и `result` (единственный триггер гарда) до ответа
  человека просто не приходит.

**Критерии приёмки Э8:**

- Первая вводная всегда проходит интервью; кристальная задача даёт «вопросов нет» +
  допущения в карточке плана, без фейковых вопросов.
- Вопросы приходят ASK-карточками с кнопками (рекомендуемый вариант помечен, «Другое»
  принимает свободный текст); текстовых вопросов-простыней нет; больше двух раундов
  на вводную не бывает.
- Тупик в волне: карточка + push немедленно, волны стоят; после ответов — план vN с
  «Что изменилось»; работа продолжается только после «Запустить», даже при авто.
- Ответ на интервью не обнуляет бюджет и не создаёт задач.
- Рестарт сервера в стадии интервью ничего не теряет: стадия, вопросы в ленте, версия
  плана и план-режим на месте.
- Добавочная вводная без вопросов идёт по-старому: карточка состава без блокировки.
- В стадиях интервью/планирования чат реально в план-режиме: селектор показывает «план»
  и заблокирован, попытка правки файла упирается в permission-механику, штатная карточка
  `plan_review` не появляется ни разу.
- После «Запустить» селектор разблокирован и показывает прежний режим пользователя
  (в т.ч. после рестарта сервера посреди планирования).
- Карточка плана и карточки эскалаций показывают аватар и имя персоны-автора; после
  смены координатора старые карточки сохраняют исходного автора; push эскалации
  приходит от имени персоны («{Имя}: нужно ваше решение»).

**Тексты Э8:**

- Бейдж: короткая форма «КР · вопросы», полная подпись «Командная реализация · интервью» —
  в тултипе (решение владельца 2026-08-02, см. раздел «Тексты»).
- Старт интервью (реплика перед ASK-карточкой): «Пара вопросов перед планом. Выберите
  варианты — или „Другое", чтобы ответить своими словами».
- Тупик в волне: «Нужны уточнения — волны на паузе».
- Push-заголовок: «Команда ждёт ответов по задаче».
- Карточка плана: «План v2 · обновлён после уточнений», блоки «Что изменилось»,
  «Допущения». Кнопки прежние: «Запустить», «Изменить план», «Отменить».
- Тултип заблокированного селектора режима: «Штаб планирует. Режим вернётся после
  согласования плана».
- Push и уведомления эскалаций — от имени персоны: «{Имя}: нужно ваше решение»,
  «{Имя} ждёт ответов по задаче» (вместо обезличенного «Команда ждёт вашего решения»
  из раздела «Тексты» — тот текст остаётся фолбэком, если персоны у штаба вдруг нет).
- «Что нового»: «Командная реализация теперь начинается с разговора: команда сначала
  задаёт вопросы по задаче и только потом показывает план. Если по ходу работы что-то
  окажется неясным, она не будет гадать — снова спросит и покажет обновлённый план на
  подтверждение».

## Замысел в карточке и полный план файлом (решение владельца 2026-08-02)

**Проблема.** Карточка плана показывает распределение работ — кто, над чем, в каких файлах,
в какой волне, — но не показывает замысла. Человек утверждает состав, не видя, как команда
поняла задачу: если планировщик понял неверно, по строке «notes.md · Кира · фронтовая часть»
этого не заметить, расхождение всплывёт уже на верификации. При этом «что сделать» (`Goal`)
и «критерий готовности» (`DoneCriteria`) у под-задач **уже есть в модели** — они просто
уезжают в описание задачи исполнителя и в ленте не видны.

**Решение — два уровня вместо одного.**

1. **В карточке — блок «Замысел»:** 3–5 строк от планировщика: к чему идём, ключевые решения,
   что осознанно не делаем. Новое поле `TeamImplementPlan.Intent`.
2. **Полный план — отдельным файлом** `docs/plans/team/{слаг чата}/iter{N}/plan-v{M}.md`, ссылка
   на него — строкой в карточке («Полный план — `plan-v1.md`»). Клик открывает файл в правой
   панели предпросмотра — тем же механизмом, которым из чата открываются любые файлы проекта
   (`onOpenFile`, уже используется в `MarkdownContent`, `PersonaTaskView`, `TaskCreatedView`).

**Что внутри файла:** замысел и подход, под-задачи с `Goal` и `DoneCriteria`, файлы во владении,
исполнители с обоснованием, волны, допущения, а с версии v2 — блок «Что изменилось».

**Инварианты:**

- **Файл пишет сервер, а не модель.** Планировщик и так отдаёт структуру плана; сервер рендерит
  из неё markdown при публикации карточки. Поручать запись модели нельзя: координатору запрещено
  писать файлы (`CoordinatorWriteGuard`, правило «любая работа — через задачу»), и попытка
  упёрлась бы в гард. Побочная польза — файл гарантированно соответствует плану, а не тому,
  что модель решила написать.
- **Версия = отдельный файл.** Перепланирование (Э8) не перезаписывает `plan-v1.md`, а кладёт
  рядом `plan-v2.md`; карточка каждой версии ссылается на свой файл. История решений остаётся.
- **Вводная = отдельная подпапка (`iterN`).** Слаг папки строится из имени чата, а то ставится
  по первой вводной и дальше не меняется — вторая (и последующие) вводные того же чата иначе
  писали бы в тот же `plan-v1.md`, что и первая (прод 2026-08-03, находка Веры). Счётчик —
  `SessionTeamImplement.IterationNumber`, растёт на каждой новой вводной (не на перепланировании
  внутри неё — там растёт версия).
- **Путь — через `SafeJoin`**, слаг чата нормализуется: имя чата приходит от человека и в путь
  напрямую не годится.
- **Глобальный чат без проекта** — файла негде хранить: карточка показывает «Замысел», строки
  со ссылкой нет. Практика при этом работает как раньше.
- **Побочный эффект `docs/`:** планы попадают в панель «Документация» и в синк базы знаний
  проекта (дефолтная область — `docs/**`). Это осознанно: план отвечает на вопрос «почему так
  решили» и полезен в поиске. Если начнут забивать выдачу — исключить `docs/plans/` из синка.

**Тексты:**

- Заголовок блока в карточке: «Замысел».
- Строка-ссылка: «Полный план — `plan-v1.md`» (у поздних версий — соответственно `plan-v2.md`).
- «Что нового»: «В плане команды теперь виден замысел — как она поняла задачу и что решила
  сделать. Полный план лежит файлом рядом с проектом: открывается по ссылке из карточки,
  со всеми деталями по каждой части работы».

## Правило «любая работа — через задачу»

1. **Промпт координатора**: «Ни одна работа не выполняется без задачи. Всё, что делает
   команда, оформляется задачей с исполнителем и критерием готовности».
2. **Гард**: в режиме практики координатор по умолчанию не правит файлы сам (настройка
   «Координатор не пишет код», включена) — иначе он срежет углы и сделает всё сам.
3. **Проверка на закрытии волны**: правки файлов вне задач — оформить задачей задним
   числом либо объяснить в сводке.

## Тексты

**Карточки механик (группа «Сделать»):**
- «Командная реализация» — «Штаб фичи: план, задачи, исполнители».
  Плейсхолдер: «Что реализовать командой?…»
- «Командный спринт» — «Быстро разбить и раздать субагентам».
  Плейсхолдер: «Что сделать спринтом?…»

**Состав:** «Исполнители (по умолчанию — вся команда проекта)».
Подпись: «Оставьте пустым, и планировщик подберёт людей под каждую часть работы сам».

**Тумблер:** «Авто-волны — не спрашивать после каждой волны».
Подпись: «План согласуете один раз. Дальше команда работает сама, пока хватает бюджета».

**Бейдж в композере:** короткая форма `КР · вопросы` / `· планирует` / `· волна 2 из 3` /
`· решение` / `· проверка` / `· ожидает`; полная подпись («Командная реализация · интервью»
и т.д.) — в тултипе. Решение владельца 2026-08-02: сокращения остаются везде — и в бейдже,
и в маркере списка чатов; полные формы жили бы только в тултипе и на мобиле были бы
недоступны, поэтому городить адаптивную ветку не стали. Чип «Авто» рядом, кликом переключается.
Тултип: «Чат работает как штаб: задачи ставятся исполнителям, их чаты видны под этим в
списке. Напишите, что ещё нужно сделать — команда возьмёт в работу».

**Карточка плана:** заголовок «План командной реализации», подзаголовок «5 под-задач ·
2 волны · 3 исполнителя». Кнопки: «Запустить», «Изменить план», «Отменить».
Строка под-задачи: название · чип исполнителя (кликабельный) · файлы · серым —
обоснование выбора. При авто под кнопками: «После запуска волны пойдут одна за другой —
вмешаемся только при проблеме или исчерпании бюджета».

**Сводка волны (авто):** «Волна 1 закрыта: 3 из 3. Запускаю волну 2».

**Стадия ожидания:** «Итерация завершена. Напишите, что делать дальше — команда возьмёт
в работу». Режим при этом остаётся включённым.

**Эскалации:** тексты — в таблице раздела «Эскалация и остановки».
Push-заголовок: «Команда ждёт вашего решения», тело — суть проблемы одной строкой.

**Глобальный чат без состава:** «Выберите исполнителей — вне проекта команды нет, и
подбирать не из кого».

**Итоговый отчёт:** «Итерация завершена: 5 задач, 3 исполнителя, проверка пройдена».
При красной проверке: «…проверка не прошла: осталось 2 замечания».

**«Что нового»:** «Командная реализация стала режимом чата. Выбираете практику — чат
становится штабом: план с исполнителями под каждую часть, задачи, чаты исполнения прямо
под штабом и проверка в конце. Согласовываете план один раз, дальше команда работает
сама и зовёт вас, только если застряла. Нужны доработки — просто напишите в тот же чат,
команда возьмёт их в работу. Прежний быстрый вариант никуда не делся — он теперь
называется „Командный спринт"».

## Фич-флаг

`team-implement-mode`, по умолчанию выключен. Снимаем после: живой приёмки на проде, двух
реальных фич, доведённых **без вмешательства после подтверждения плана**, одной итерации
с продолжением («добавь ещё X») и подтверждения, что бюджет ни разу не пробит.

## Риски

| Риск | Что делаем |
|---|---|
| Лавина запусков (уже ловили) | Бюджет вместо запрета, счётчики на бэкенде, ревью Глеба |
| Сброс бюджета по вводной = обход потолка | Сброс только по сообщению человека (не агента); при подозрительной частоте — сводка расхода в ленте |
| Авто-режим жжёт бюджет впустую | Потолок перевыдач, стоп после второго провала, сводка волны в ленте |
| Блокер лежит незамеченным до конца волны | Доклад с пометкой блокера будит координатора (Э4) |
| Человек не у экрана, а практика ждёт | Уведомление + web push на каждую эскалацию |
| Координатор делает всё сам | Настройка «Координатор не пишет код» + проверка на закрытии волны |
| Разговорное сообщение развернуло волну | Классификация по признаку «нужно менять файлы»; спорное — переспросить |
| Вся команда по умолчанию = случайные исполнители | Обоснование выбора в карточке плана + правка исполнителя до запуска |
| История прошлых прогонов ломается переименованием | Детектор держит оба префикса |
| Долгий прогон рвётся при рестарте | Состояние на сессии, а не в ходе |
| Интервью превращается в допрос (Э8) | Пачка вопросов с дефолтами, максимум 2 раунда, «не развилка → допущение» |
| Ответы на интервью обходят бюджет (Э8) | Ответ на интервью — не вводная: потолки не сбрасываются, задачи не создаются |

## Критерии приёмки

- Чат помечен режимом на всех стадиях; после рестарта пометка, стадия и флаг авто на месте.
- Практика стартует без явного выбора участников в проектном чате.
- План публикуется карточкой, исполнителя можно сменить до запуска.
- Каждая под-задача = задача в системе + дочерний чат под штабом в дереве.
- **При включённом авто итерация доходит до конца без единого клика после подтверждения
  плана — пока план не менялся; новая версия плана (Э8) требует подтверждения всегда.**
- Между волнами не появляется ни одной карточки согласования при включённом авто.
- Новая вводная в завершённой итерации разворачивает новую волну; бюджет обнуляется.
- Вопрос в режиме получает ответ и не создаёт задач.
- Каждая эскалация — карточка с причиной, кнопками и push; молчаливых зависаний нет.
- Блокер исполнителя доходит до человека в момент возникновения, а не в конце волны.
- Провал: одна перевыдача, второй — эскалация с внятной сводкой.
- Старые ходы `/team-implement` в лентах по-прежнему рисуются карточкой («Командный спринт»).
