# Локальная модель как CLI-провайдер (Qwen3.8-27B на vLLM)

Постановка на адаптер локальной модели по образцу GLM / Kimi / MiniMax.
Разведка проведена 04.09.2026 на живом стенде, все утверждения ниже —
результаты фактических запросов, а не паспортов.

## 1. Главный вывод разведки: транслятор протоколов не нужен

Первоначальная гипотеза была «написать прокси Anthropic ↔ OpenAI, потому что
vLLM отдаёт OpenAI-совместимый API». Гипотеза **неверна**: vLLM 0.28 отдаёт
`POST /v1/messages` и `POST /v1/messages/count_tokens` нативно, то есть говорит
на том же протоколе, что и наши облачные CLI-провайдеры.

Проверено живыми запросами к `http://127.0.0.1:18020`:

| Что | Результат |
|---|---|
| Непотоковый ответ | `type: message`, `role: assistant`, `stop_reason: end_turn`, `usage.input_tokens/output_tokens` |
| Блок размышления | `{"type":"thinking","thinking":"…","signature":"…"}` — с подписью, как у Anthropic |
| Потоковая отдача | `event: message_start` → `content_block_start` → `content_block_delta` (`thinking_delta`) |
| Вызов инструмента | `stop_reason: tool_use`, блок `{"type":"tool_use","name":"get_weather","input":{"city":"Москва"}}` |
| Поля кэша в usage | `cache_creation_input_tokens`, `cache_read_input_tokens` присутствуют |

Значит **работа сводится к заведению провайдера конфигом** — ровно как заводились
`glm`, `kimi`, `minimax`, — плюс небольшой список доработок из §3, вызванных тем,
что провайдер локальный, а не облачный.

Запуск сервера уже включает всё нужное: `enable_auto_tool_choice: true`,
`tool_call_parser: qwen3_coder`, `reasoning_parser: qwen3`.

## 2. Что это за модель и где она живёт

- Модель: `Qwen3.8-27B`, квант W4A16 AutoRound + переквантованные `lm_head`,
  embeddings и MTP-модуль (репозиторий `syv-ai/qwen38-27b-rtx3090`).
- Движок: vLLM 0.28.0 в контейнере, ~30 патчей репозитория, спекулятивное
  декодирование DFlash2 (15 черновых токенов за проход).
- Адрес: `http://127.0.0.1:18020`, id модели — `qwen3.8-27b`.
- Железо: одна RTX 3090 24 ГБ, `gpu_memory_utilization = 0.93`.
- Проект стенда: `C:\llm\qwen-serving`, переключатель карты `C:\llm\use-gpu.ps1`.

Замеренная производительность (наш бенчмарк `C:\llm\bench-compare.ps1`,
10 задач с автопроверкой):

| Показатель | Значение |
|---|---|
| Средняя генерация | 127.6 ток/с |
| Пик (генерация кода) | 183.9 ток/с |
| Свободный диалог | 33–46 ток/с |
| Доля принятых черновых токенов | 32% (2.2 из 7 за шаг) |
| Время до первого токена | 1.59 с |
| Проверяемых задач верно | 8 из 9 |

Разброс скорости объясняется спекулятивным декодированием: на предсказуемом
тексте (код, JSON) черновик угадывает часто, на живом диалоге — редко.
**Заявленные автором 120–130 ток/с относятся к предсказуемому тексту, а не к
разговору.**

## 3. Чем локальный провайдер отличается от GLM / Kimi / MiniMax

Механика подключения одна и та же (`LlmProviderRegistry.BuildCliEnv` ставит
`ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_MODEL`, изолированный
`CLAUDE_CONFIG_DIR`), но пять мест ведут себя иначе.

### 3.1. Провайдер считается выключенным без ApiKey

```csharp
// Models/LlmProviderConfig.cs
public bool Enabled =>
    !string.IsNullOrWhiteSpace(ApiKey) && !string.IsNullOrWhiteSpace(AnthropicBaseUrl);
```

У локального сервера ключа нет. Варианты:

- **дёшево:** прописать в конфиге любую непустую строку (`"ApiKey": "local"`) —
  vLLM её игнорирует, `Enabled` становится true, код не трогаем;
- **честно:** ввести признак `RequiresApiKey = false` (или `IsLocal = true`) и
  учесть его в `Enabled`.

Рекомендация — второй путь: фиктивный ключ в конфиге читается как «забыли
настроить» и будет сбивать с толку при разборе инцидентов.

### 3.2. Баланса и квот нет

`Balance`, `BalanceUrl`, `ConsoleCookie` не нужны: денег не тратится.
`ProviderBalanceService` не трогаем, в UI у провайдера не должно быть блока
остатка — вместо него полезнее показывать состояние сервера (поднят / карта
занята другим движком).

### 3.3. `QueryModelsApi` — false

`GET /v1/models` у vLLM есть, но отдаёт ровно одну запись — ту, что поднята.
Каталог задаём статически, как у `kimi` и `minimax`.

### 3.4. Провайдер может быть физически недоступен

Принципиальное отличие от облака: **локальная модель занимает ту же карту, что и
llama.cpp**, и одновременно они не живут (19.5 ГБ + 15.7 ГБ при 24 ГБ VRAM).
Сейчас переключение ручное (`use-gpu.ps1 llama|vllm`), и на время работы vLLM
локальный роутер `:8080` остановлен, то есть RAG-эмбеддер и фоновые действия
через `LocalLlm` недоступны.

Отсюда требование: **перед ходом проверять живость эндпоинта** и давать
человеческую ошибку вместо `Unreachable`. Заготовка в коде есть —
`ProviderHealthRegistry` и классификатор `TurnErrorClassifier`; нужен отдельный
класс ошибки вида «локальная модель не запущена», чтобы фолбэк не тратил на неё
шаги цепочки (по аналогии с `EgressDown`, см. `TurnFailureText`).

### 3.5. Контекст мал, а системный промпт Claude Code огромен

Замер живым запуском `claude --print` против локального эндпоинта:

```
API Error: 400 This model's maximum context length is 57344 tokens.
However, you requested 32000 output tokens and your prompt contains
at least 25345 input tokens, for a total of at least 57345 tokens.
```

**Системный промпт Claude Code — 25 345 токенов**, плюс CLI резервирует 32 000
под ответ. В режиме `CTX=fast` (57 344) не хватает одного токена, агентный режим
не стартует в принципе. Нужен режим `CTX=long` (int8 KV, ~128k) — он же снижает
скорость примерно вдвое и добавляет потери точности на длинном контексте.

> **Устарело (см. §7б, §7в, пересмотрено 2026-09-05).** В `start_qwen.sh` есть
> третий режим — `CTX=huge` (KVarN 4/2-bit KV), который даёт 245 760 токенов
> контекста при 48 ток/с агентного цикла. Эта правка снимает проблему выше
> целиком: 25 345 + 32 000 < 245 760 с большим запасом. Актуальное окно и
> конфигурация — в §7б; сводка по приёмам и вывод по железу — в §7в.

Вывод для каталога: `ContextWindow` ставим по фактическому `max_model_len`
поднятого режима и обязательно прокидываем в `CLAUDE_CODE_MAX_CONTEXT_TOKENS`
(механика уже есть в `BuildCliEnv`) — иначе CLI считает окно равным 200k и
не сжимает контекст вовремя.

## 4. Две несовместимости, которые надо закрыть

Обе найдены живым запуском, обе воспроизводимы.

### 4.1. `unrecognized_model` — предупреждение, не блокер

```
[claude-code:unrecognized_model] {"model":"qwen3.8-27b","query_source":"sdk"}
```

CLI не знает id и предполагает окно 200k. Лечится тем же
`CLAUDE_CODE_MAX_CONTEXT_TOKENS`, который мы и так ставим. Отдельной работы не
требует, но в логах будет мелькать — стоит упомянуть в документации, чтобы не
принимали за поломку.

### 4.2. `reasoning effort high` — реальный блокер

```
API Error: 400 Unexpected reasoning effort high.
Supported types are xhigh (default), medium, and low.
```

Claude Code шлёт усилие рассуждений `high`, реализация Anthropic-API в vLLM
принимает только `xhigh` / `medium` / `low`. Обходится флагом `--effort medium`,
но у нас усилие задаётся per-персона и приезжает из настроек, значит нужно одно
из двух:

- **при сборке хода** подменять `high` на поддерживаемое значение для этого
  провайдера (точка — `ClaudeSession`, где формируются аргументы CLI);
- **либо** поставить перед vLLM тонкий прокси, переписывающий поле.

Первый путь предпочтительнее: прокси — лишний процесс в контуре, который придётся
поднимать, сторожить и чинить. Разумно ввести в конфиг провайдера поле-карту
допустимых уровней усилия (например `EffortMap: { "high": "medium" }`), чтобы
подмена была декларативной и не размазывалась по коду.

## 4.3. Первая живая проверка: связка работает, но медленно (устарело, см. 7б)

> **Цифры этого раздела — историческая отправная точка.** После настройки кэша,
> размышлений и набора инструментов ход занимает 2.8 с, а не 341. Итоговая
> конфигурация и замеры — в §7б; ниже описано, с чего мы начинали и почему.

После подъёма контекста до 98 304 токенов `claude --print --effort medium
--model qwen3.8-27b` **отработал успешно**: в логах vLLM четыре
`POST /v1/messages?beta=true → 200 OK`, ответ содержательный и верный
(«12×12 = 144»).

**Время ответа — 341.6 секунды.** Почти шесть минут на арифметику уровня
таблицы умножения. Причины складываются:

- системный промпт CLI (25 345 токенов) обрабатывается на каждом ходе;
- агентный цикл делает несколько запросов на один вопрос пользователя;
- `CTX=long` (int8 KV) примерно вдвое медленнее `CTX=fast`;
- спекулятивное декодирование на служебном тексте почти не срабатывает
  (приёмка 32% даже на обычном диалоге).

**Вывод для планирования.** Технически провайдер реализуем и требует немного
работы (§5). Но продуктовый сценарий «локальная модель как рабочая лошадка
агентных чатов» на этом железе не выигрывается: минуты на простой ход. Реальные
ниши — работа без интернета, приватные задачи, которые нельзя отдавать наружу,
и фон, где время ответа не критично. Ожидания по скорости надо ставить заранее,
иначе фича будет выглядеть сломанной.

## 4.4. Грабля конфигурации: `MAX_LEN` не работает при `SPEC=dflash2`

Переменная `MAX_LEN` в `.env` молча игнорируется, когда включено спекулятивное
декодирование: `single-user/start_qwen.sh:341` перетирает её значением
`DFLASH_MAX_LEN` (дефолт 131072 для `CTX=long`). Симптом — движок падает на
старте с `ValueError: ... max seq len (131072) ... available KV cache memory`,
сколько бы ни правили `MAX_LEN`. Задавать надо **`DFLASH_MAX_LEN`**.

Там же выяснился и потолок железа: 128k KV-кэша в int8 в 24 ГБ **не помещаются**,
vLLM сам называет максимум — 114 224 токена. Рабочее значение стенда — 98 304.

## 4.5. llama.cpp тоже говорит на Anthropic API, но с Claude Code не работает

Проверено 05.09.2026 на сборке **b10816**: llama.cpp отдаёт `POST /v1/messages`
в том же формате, что и vLLM, — с блоками `thinking`, потоковыми событиями и
вызовом инструментов (`stop_reason: tool_use`, блок `tool_use` с `name`/`input`).
То есть **выбор движка для этой задачи открыт**, и первоначальная ставка на
vLLM не обязательна.

Замеры одного и того же набора задач на одной карте:

| | vLLM W4A16 (патченый) | llama.cpp b10816 + DFlash2 |
|---|---|---|
| Скорость генерации | 127.6 ток/с | 54.5 ток/с |
| Качество (наш набор) | 8 из 9 | 8 из 9 |
| Anthropic API, инструменты | да | да |
| Холодный старт | ~5 минут | ~30 секунд |
| Роутер, эмбеддер, сторож | нет | **есть, уже в контуре** |
| Основа | ~10 000 строк сторонних патчей | штатный апстрим |
| Известные риски | Xid 31 примерно раз в 40 часов на `CTX=long` | нет |

**ВНИМАНИЕ, эта рекомендация опровергнута практикой.** По протоколу llama.cpp
совместим, но на настоящем клиенте падает:

```
Error: Jinja Exception: System message must be at the beginning.
```

Чат-шаблон Qwen3.8 требует системное сообщение строго первым, а Claude Code
присылает их иначе. Обойти можно только правкой шаблона (убрать `raise_exception`
и рендерить системный блок как обычный) — то есть держать и сопровождать
собственную копию шаблона. Хрупко.

**Итоговая рекомендация: vLLM** (`http://127.0.0.1:18020`, модель `qwen3.8-27b`).
Он проверен полным агентным циклом, вдвое быстрее и не требует правки шаблонов.
llama.cpp остаётся для чата, фоновых действий и RAG-эмбеддера — там, где клиент
наш собственный.

Качество между сборками не различалось ни разу за шесть конфигураций — выбор
делается по эксплуатационным свойствам, а не по «уму» модели.

### Настройки llama.cpp, которыми получены эти цифры

В пресете `[qwen38-27b]` файла `C:\llm\models.ini`:

```ini
spec-type = draft-dflash
spec-draft-model = C:/llm/models/Qwen3.8-27B-DFlash2-Q4_K_M.gguf
spec-draft-n-max = 2
```

Три грабли, каждая стоила отдельного замера:

1. **Сборка не старше b10816.** На прежней 10666 драфтер не грузился вовсе —
   `invalid vector subscript`, слот падал с `exited with status 1`. Нужный PR
   (#27342, DFlash2) влит 27.08.2026, но работоспособным стал позже.
2. **KV-кэш не квантовать.** `cache-type-k/v = q8_0` режет скорость вдвое
   (34.2 → 15.5 ток/с) и не экономит ни мегабайта: модель гибридная, у слоёв
   Gated DeltaNet состояние фиксированного размера. Совет из статей, который
   для этой архитектуры вреден.
3. **MTP-спекулятивка не подходит этому кванту.** `UD-Q4_K_M` не содержит
   MTP-головы, включение дало 13.6 ток/с — вдвое хуже базы, при том что сам
   драфт угадывал на 72%. Нужен либо драфтер DFlash2 (наш случай), либо квант
   со встроенной головой (`UD-Q4_K_XL`).

### Эксплуатационная грабля: 27B и 9B в карту вместе не помещаются

27B с драфтером просит ~16.5 ГБ плюс KV, рабочая связка `qwen35-9b` + эмбеддер
занимает 6.8 ГБ. В 24 ГБ это не складывается, а роутер llama.cpp **не сообщает
об ошибке**: он поднимает слот и молча кладёт модель на CPU. Симптом —
`status: loaded` при почти пустой видеопамяти и скорость 2.8 ток/с вместо 54.5.
Ровно тот же класс тихого отката, что ловит сторож у самого сервера.

Ручки выгрузки у роутера нет (`/models/unload` отвечает 500). Поэтому режимы
взаимоисключающие:

- **прод-режим:** `qwen35-9b` + `nomic-embed-text` — фоновые действия и RAG;
- **режим 27B:** роутер поднимается с `--models-max 1`, либо 9B гасится вручную.

Для интеграции с Claude Code это значит то же ограничение, что и у vLLM, только
дешевле по времени: переключение занимает секунды, а не пять минут холодного
старта.

### Ограничение размышлений — обязательная часть настройки

Без него ход идёт минуты: живой замер `claude --print` дал **341.6 с** на вопрос
«сколько будет 12×12». С `MAX_THINKING_TOKENS=5000` и усилием `low` — **155.7 с**,
то есть вдвое быстрее при том же правильном ответе. Модель по умолчанию
переразмышляет; это подтверждают и внешние источники (случай с 21-минутным
рассуждением над одним SVG). Ограничение бюджета должно ставиться в коде
провайдера, а не оставаться на совести пользователя.

## 4.6. КРИТИЧНО: `mamba-cache-mode align` убивает кэш промпта (замедление в 12 раз)

Самая дорогая находка всей разведки. Скрипт репозитория запускает vLLM с
`--mamba-cache-mode align`, и в этом режиме префиксный кэш у гибридных Qwen
**даёт 0% попаданий** — известный баг vLLM
([issue #42317](https://github.com/vllm-project/vllm/issues/42317), там же
замеры: `align` — 0%, `all` — 54.4%).

Для обычной генерации это почти незаметно. Для Claude Code — катастрофа: он шлёт
25 345 токенов системного промпта на КАЖДОМ обращении, и без кэша они каждый раз
считаются заново.

Замер на нашем стенде, один и тот же вопрос через `claude --print`:

| Режим | Первый вызов | Второй вызов | Hit rate |
|---|---|---|---|
| `align` (дефолт репозитория) | ~180 с | ~180 с | 0% |
| **`all`** | 186.9 с | **15.0 с** | **48.4%** |

**Лечение — одна строка в `.env` стенда:**

```
EXTRA_ARGS=--mamba-cache-mode all
```

`EXTRA_ARGS` раскрывается после собственных аргументов скрипта, поэтому
перебивает его `align`.

**Что это значит для продукта.** Первый ход после подъёма сервера остаётся
долгим — кэш пустой. Дальше системный промпт берётся готовым, и ход укладывается
в ~15 секунд. То есть локальный провайдер пригоден для работы, но «прогрев»
надо учитывать: первый запрос после старта нельзя показывать пользователю как
образец скорости.

Побочные находки того же разбора, которые проверять НЕ надо (у нас уже закрыты):

- `CLAUDE_CODE_ATTRIBUTION_HEADER=0` — меняющийся заголовок Claude Code тоже
  ломает кэш, но vLLM новее 0.17.1 обрабатывает это сам; наш замер с этой
  переменной и без неё дал одинаковые 180 с. В скрипт добавлено на всякий случай.
- Известный баг с той же симптоматикой на Qwen 27B —
  [issue #40630](https://github.com/vllm-project/vllm/issues/40630).

## 5. Что делать (объём работ)

### 5.1. Конфигурация — секция `LlmProviders`

```jsonc
"local-qwen": {
  "DisplayName": "Локальная Qwen3.8-27B",
  "AnthropicBaseUrl": "http://127.0.0.1:18020",   // CLI сам допишет /v1/messages
  "ApiBaseUrl": "http://127.0.0.1:18020/v1",
  "ApiKey": "local",                               // до появления RequiresApiKey
  "MediumModel": "qwen3.8-27b",
  "SmallModel": "qwen3.8-27b",
  "QueryModelsApi": false,
  "SupportsImages": false,                         // language_model_only: true при запуске
  "TierStrong": "qwen3.8-27b",
  "TierMedium": "qwen3.8-27b",
  "TierWeak": "qwen3.8-27b",
  "Models": [
    {
      "Id": "qwen3.8-27b",
      "DisplayName": "Qwen3.8-27B (локальная)",
      "Description": "27B на своей RTX 3090 · бесплатно, без интернета",
      "ContextWindow": 131072                      // по факту режима CTX=long
    }
  ]
}
```

Цены не указываем сознательно: `PriceIn*/PriceOut*` отсутствуют, расход должен
считаться нулевым. **Проверить, что счётчик трат не ломается на провайдере без
цен** — иначе в «Использовании» появятся нули или пустые строки.

Ключ провайдера (`local-qwen`) участвует в резолве по префиксу модели
(`ResolveByModel` → `EffectiveModelPrefixes`). Id `qwen3.8-27b` с ключом не
совпадает, поэтому резолв пойдёт по точному совпадению с каталогом — этого
достаточно, но стоит задать `ModelPrefixes: ["qwen3.8"]` на случай появления
второй локальной модели.

### 5.2. Код

1. `LlmProviderConfig`: признак локального провайдера (`RequiresApiKey` / `IsLocal`)

2. Подмена уровня усилия рассуждений для провайдера (см. §4.2).
3. Проба живости эндпоинта перед ходом + отдельный текст ошибки «локальная модель

5. Проверить нулевую тарификацию в `SpendRecord` / вкладке «Использование».

## 7. Риски и честные ограничения

- **Скорость.** 33–46 ток/с на живом диалоге. Агентный ход Claude Code — это
  десятки тысяч токенов служебного контекста на каждый шаг; работа будет заметно
  медленнее облака.
- **Контекст.** Даже 128k против 200k–1M у облачных провайдеров. При этом 25k
  съедает системный промпт CLI ещё до первого сообщения.
- **Качество.** Квант агрессивный: помимо 4-битных весов дожаты выходной слой и
  эмбеддинги, KV-кэш в режиме `CTX=long` уходит в int8. На нашем бенчмарке
  27B дала 8 из 9 — столько же, сколько локальная 9B, — но набор из десяти задач
  не заменяет длительной эксплуатации.
- **Монополия на карту.** Пока работает vLLM, недоступны llama.cpp-роутер и
  RAG-эмбеддер. Для продуктового использования это означает выбор: либо агентная
  локальная модель, либо локальные фоновые действия и знания — вместе не выходит.
- **Патчи.** Сборка держится на ~10 000 строк сторонних патчей к vLLM. Обновление
  vLLM их сломает; фиксировать версию образа обязательно.
- **Инвариант проекта.** Ограничение «агентным местам локаль недоступна»
  (`LocalActionCatalog`, `Agentic: true`) относится к ветке `LocalLlm` — прямым
  HTTP-вызовам мимо CLI. Здесь модель подключается как **CLI-провайдер**, то есть
  ограничение формально не нарушается. Это стоит проговорить явно при ревью,
  иначе выглядит как обход инварианта.

Скрипт сам выставляет окружение, проверяет живость сервера и внятно сообщает,

### Замеренное время ответа

| Сценарий | Время |
|---|---|
| Простой вопрос, кэш прогрет | **2.8–3.1 с** |
| Первый вопрос после старта сервера | ~20 с |

| Генерация | **60–63 ток/с** |
| Попаданий в кэш промпта | 75–80% |

Первый ход всегда долгий — строится кэш системного промпта. Это не поломка.

### Конфигурация сервера (`C:\llm\qwen-serving\.env`)

```
PORT=18020
SPEC=dflash2                          # спекулятивное декодирование драфтером
PREFIX_CACHE=1                        # кэш промпта — обязателен
VLLM_WSL2_ENABLE_PIN_MEMORY=1         # обязателен под WSL2
MODELS_DIR=qwen-models
CTX=huge                              # KVarN 4/2-bit KV: 245 760 контекста
DFLASH_TOKENS=2                       # ГЛАВНЫЙ рычаг скорости, см. ниже
DFLASH_MAX_LEN=245760                 # окно; при SPEC=dflash2 перетирает MAX_LEN
GPU_UTIL=0.94                         # потолок: на 0.95 движок не стартует
EXTRA_ARGS=--mamba-cache-mode all     # перебивает align, который ставит скрипт
```

Каждая строка получена замером, а не подобрана по документации:

- **`CTX=huge` вместо `fast`/`long`** — режим есть в `start_qwen.sh`, но до 2026-09-05 отсутствовал в этом документе, из-за чего 98k считались потолком железа. Даёт `max_model_len` 245 760 при пуле 278 321 токен. Проверено живым подъёмом; требует `kvarn/install.sh` (в образе уже применён — самопроверка печатает `KV=kvarn / CTX=huge available`).
- **`DFLASH_TOKENS=2` вместо 5** — ускорение **в 1.9 раза** в агентном цикле (25 → 48 ток/с). Пятёрка — настройка для RTX 6000; на 3090 драфтер захлёбывается верификацией. Источник — https://github.com/jonidimo/qwen38-3090-benchmark, подтверждено нашим замером. **Цена правки: ~5 минут перекомпиляции** — меняется сигнатура графов, кэш `torch.compile` инвалидируется.
- **`--mamba-cache-mode all`** обязателен: `start_qwen.sh:447` сам добавляет `align`, который по §4.6 убивает кэш промпта. Наш флаг идёт последним и перебивает его (в логе `WARNING: Found duplicate keys` — это норма).

### Четыре грабли, каждая стоила отдельного разбора

1. **Прокси съедает локальные запросы.** С `HTTP_PROXY` в окружении CLI тащит
   туда даже `127.0.0.1` и падает с `Connection refused — a firewall or proxy
   may be blocking it`. Лечится `NO_PROXY`.
2. **`--effort high` не принимается** — сервер отвечает 400 (поддерживаются
   `xhigh`/`medium`/`low`), а на `medium` модель уходит в многоминутные
   размышления. Нужен `low` плюс бюджет размышлений.
3. **Системный промпт — 25 345 токенов, и 81% из них — описания инструментов.**
   Отключение MCP-серверов сократило ход с 9.7 до 4.5 с. В продукте так урезать
   нельзя (инструменты и есть смысл агента) — там время будет выше.
4. **`unrecognized_model` в stderr — норма.** CLI не знает id модели, окно
   контекста мы задаём явно.

## 7в. Что перепробовано ради контекста и чем закончилось

Все приёмы проверены замерами на этом стенде 05.09.2026. Сводка нужна, чтобы
не проходить этот путь заново.

| Приём | Контекст | Ход (прогретый) | Вердикт |
|---|---|---|---|
| **KVarN 4/2, `CTX=huge`** | **245 760** | 48 ток/с (агентный цикл) | **рабочий эталон** |
| bf16-кэш, `CTX=fast` | 65 536 | 2.1–2.7 с | быстрый prefill, мало контекста |
| int8-кэш, `CTX=long` | 98 304 | 4.5 с | промежуточный |
| Выгрузка 2 ГБ весов в ОЗУ | 90 112 | 5.4–6.6 с | **не окупается** |
| Квантование KV в `q8_0` (llama.cpp) | — | вдвое медленнее | вредно на гибридной модели |
| `gpu_memory_utilization` 0.95 | — | не стартует | графика держит 1.24 ГБ |
| Компактный квант GGUF | — | — | vLLM не читает GGUF |
| FP8-кэш | — | — | нужен Hopper, у Ampere нет |

**Выгрузка весов проиграла квантованию кэша по обоим параметрам** — контекста
меньше, ходы медленнее. Разбираться с ней стоит только там, где квантование
кэша недоступно.

### Две находки, без которых остальное не работает

1. **Пул кэша прибит константой.** `single-user/start_qwen.sh` задаёт
   `KV_MEM=${KV_MEM-5583457484}` — 5.2 ГБ, вычисленные под одну карту. Пул
   **не растёт**, сколько бы памяти ни освободили: выгрузка 2 ГБ весов сначала
   не дала ничего именно поэтому. Снимается пустым значением: `KV_MEM=` в
   `.env`, тогда размер считается от `GPU_UTIL`. Автор сам описывает это как
   проблему — но чинил только для многокарточного случая (issue #40).
2. **Потолок `gpu_memory_utilization` — 0.94.** На 0.95 движок не стартует:
   `Free memory on device cuda:0 (22.76/24.0 GiB) is less than desired`. Полтора
   гигабайта держит Windows под рабочий стол и браузеры, перенести вывод некуда
   — встроенного видео в системе нет.

### Вывод по железу (пересмотрен 2026-09-05)

Прежний вывод — «мы у потолка: 65k при 2 с либо 98k вдвое медленнее» — **был
неверен**: он опирался на два режима из трёх. Третий, `CTX=huge`, всё это время
лежал в `start_qwen.sh`.

Фактический потолок одной RTX 3090: **245 760 токенов контекста при 48 ток/с**
в реальной агентной работе, с сохранённым спекулятивным декодированием. Это в
3.75 раза больше контекста и вдвое выше скорость, чем считалось.

Вторая карта по-прежнему даёт рост (issue #40: пул со 137 до 302 тысяч токенов,
+16–35% к генерации, параллельные запросы), но **как оптимизация, а не как
необходимость**. Покупать её ради контекста, не включив `CTX=huge`, — деньги
на ветер.

### Как мерить скорость, чтобы не обмануться

Три ловушки, каждая поймана на этом стенде:

1. **Синтетика ≠ работа.** Замер на промпте в 41 токен даёт 60–70 ток/с; тот же
   стенд в агентном цикле с промптом 57k+ — 48. Сравнивать можно только
   однородные замеры.
2. **Разброс между запусками 7–11%.** Одиночный замер не доказывает ничего.
   Нужно 5+ повторов **с чередованием конфигураций** (A,B,C,D → A,B,C,D…),
   иначе нагрев карты припишется той настройке, что мерялась последней.
3. **Базовая скорость дрейфует вниз** от прогона к прогону по мере нагрева:
   одна и та же конфигурация давала 66.2 → 61.3 → 60.5. Абсолютные числа
   между сессиями несравнимы, только внутри одной.

Результаты по 20 замерам (5 повторов × 4 конфигурации, чередование):

| Рычаг | Эффект | Применим? |
|---|---|---|
| `DFLASH_TOKENS` 5→2 | **+90%** | да, главный |
| `temperature` 0.7 | +4…8% (значимо) | **нет** — CLI шлёт своё значение, перебивая `--override-generation-config` |
| `--reasoning off` | не даёт скорости (3 прогона) | нет; сокращает объём генерации, но рискует качеством |

### Грабля: KV гибридной модели считается не по attention-слоям

Наивный расчёт «слои внимания × KV-головы × head_dim × 2 × 2 байта» для
гибридных моделей (Mamba/linear attention) **занижает расход в разы**.

Пример: Nemotron-3-Nano-30B-A3B, 52 слоя = 6 attention + 23 Mamba + 23 MoE,
2 KV-головы, head_dim 128. Расчёт даёт 6 КБ/токен и обещает 262k контекста при
18 ГБ. Факт — **30 КБ/токен и 131k**, впятеро хуже.

Причина видна в логе vLLM:

    Setting attention block size to 1152 tokens to ensure that attention page
       size is >= mamba page size.
    Padding mamba page size by 8.68% to ensure that mamba page size and
       attention page size are exactly equal.

vLLM выравнивает страницы: attention-блок раздувается до размера состояния
Mamba (1152 токенов вместо обычных 16), и память резервируется под все слои с
состоянием, а не под одни attention. **Оценивать окно гибрида расчётом нельзя —
только подъёмом движка**, он сам напечатает `Available KV cache memory`,
`GPU KV cache size` и оценку максимальной длины при отказе.

### Грабли на стороне CCS

1. **Каталожный `ContextWindow` отстаёт от стенда — и решает первый ход.**
   `BuildCliEnv` берёт живое окно из кэша `LocalEndpointProbe`, но после
   рестарта бэкенда кэш пуст, и первый ход получает значение из
   `LlmProviders:local-qwen:Models[].ContextWindow`. Если там реликт (было
   71 680 от режима `fast`), первый ход после каждого рестарта падает
   «Prompt is too long», а последующие идут нормально — диагностируется плохо.
   **Правило: меняя режим стенда, правь и каталог.**

2. **Прод читает конфиг из своей папки.** Правка
   `backend/ClaudeHomeServer/appsettings.Local.json` на опубликованный
   инстанс (`C:\ClaudeServer\prod\`) не влияет вовсе.

3. **`TrimMcpServers` на окне 245k больше не нужен.** Бюджет сходится:
   57 345 (промпт исполнителя) + 26 557 (набор MCP) + 8 192 (резерв ответа)
   = 92 094 из 245 760, остаётся 153 666 на работу. Проверено: с
   `TrimMcpServers: false` локальный исполнитель впервые закрыл задачу сам
   через `tasks_complete`. Признак остаётся в коде для стендов с малым окном.
