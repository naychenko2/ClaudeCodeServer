# Manual checklist: ассистент по умолчанию и знакомство

Ручная проверка фичи под флагом `default-personas-onboarding` **после снятия обязательных
гейтов**: полноэкранных экранов знакомства больше нет, ассистент заводится сам, приглашение
живёт в трёх тихих метках. Что именно должно происходить — [onboarding-intro.md](../architecture/onboarding-intro.md).

Сценарии M1–M13 взяты из плана `.omc/plans/onboarding-optional-consensus.md` (§8.4),
критерии приёмки — §6 того же плана (папка `.omc/` в `.gitignore`, в репозитории её нет).
Сценарий E (мост в командные механики) остался
от прежнего прогона и актуален как есть.

**Диалоговые сценарии требуют залогиненного Claude CLI** — без OAuth любой ход
заканчивается «Not logged in · Please run /login». Это не баг фичи.

---

## Подготовка окружения

1. **OAuth CLI в контейнере** (блокер для M3, M4, M6, M7, E):

   ```bash
   docker exec -it claude-server claude login            # через браузер и claude.ai
   # или быстрее, если есть токен:
   # в .env на хосте добавь CLAUDE_CODE_OAUTH_TOKEN=<токен из «claude setup-token»>
   docker compose -f docker-compose.claude.yml up -d --build claude-server
   docker exec -it claude-server sh -c 'cat /home/app/.claude/.credentials.json | head -5'
   # ожидание: не пусто, есть поле "claudeAiOauth"
   ```

2. **Контейнер собран из worktree** (там, где фича):

   ```bash
   docker compose -f docker-compose.claude.yml build claude-server
   docker compose -f docker-compose.claude.yml up -d claude-server
   ```

3. **Реальная последовательность dark-launch:** логин → включить флаг «Персоны по умолчанию
   и онбординг» в «Экспериментальных функциях» → в этот момент рождается ассистент и
   появляются метки. У нового пользователя флаг по умолчанию выключен, поэтому «просто
   завести юзера» ассистента не создаёт — это ожидаемо.

## M1 — миграция существующего пользователя (главный)

**Что проверяем:** человек, прошедший знакомство до релиза, не видит ни меток, ни изменений.

| Шаг | Действие | Ожидаемо |
|---|---|---|
| 1 | Взять копию реального `users.json` с заполненным `DefaultPersonaId` | — |
| 2 | Включить флаг, стартовать сервер, войти | `IntroCompletedAt` проставлен, `AssistantPersonaId` пуст |
| 3 | Пройтись по разделу «Персоны», кнопке AI-хаба, настройкам проекта | Ни одной метки-приглашения |
| 4 | Сверить `data/personas.json` | Число персон не изменилось, новых не создано |

## M1б — отложенное знакомство переживает рестарт

Новый пользователь получил заготовку и знакомство не проходил. Перезапустить сервер, войти.
**Ожидание:** метки на месте, `IntroCompletedAt` по-прежнему пуст. (Это сторож: миграция
не должна гасить приглашение тем, кто отложил знакомство.)

## M2 — новый пользователь

| Шаг | Действие | Ожидаемо |
|---|---|---|
| 1 | Логин → «Эксперименты» → флаг ON | **Без перезагрузки**: в разделе «Персоны» появилась карточка «Ваш ассистент пока стандартный» и персона «Ассистент» с аватаром-инициалами |
| 2 | Посмотреть на кнопку AI-хаба (FAB) | У аватара точка 8px без анимации; доступное имя кнопки — «AI-действия (Ctrl/⌘ + K) · знакомство с ассистентом не пройдено» |
| 3 | `GET /api/auth/me` | `defaultPersonaId` непустой, `needsOnboarding: true` |
| 4 | `GET /api/personas/{defaultPersonaId}` | `specialty: "coordinator"`, `access: "full"`, привязки содержат `personas-manage`, `tasks`, `notes` |
| 5 | Создать чат из любой точки «Новый чат» | Сессия с `personaId == defaultPersonaId`; лицо в ленте — аватар «Ассистента» |
| 6 | Полноэкранный экран знакомства | **Не появляется ни разу** |

## M3 — полное знакомство

| Шаг | Действие | Ожидаемо |
|---|---|---|
| 1 | «Познакомиться» на карточке | Открывается чат-интервью страницей (не оверлеем), есть выход «Позже» |
| 2 | Пройти 3–5 ходов, подтвердить | Та же персона получила имя, роль, характер и фото |
| 3 | Сверить `data/personas.json` | Глобальная персона по-прежнему **одна**; `defaultPersonaId` не изменился; `AssistantPersonaId` обнулён |
| 4 | Вернуться в продукт | Метки погасли **без перезагрузки** во всех трёх местах |
| 5 | Открыть чат, начатый до знакомства | В нём новое имя ассистента |

## M4 — прервано и возобновлено

Прервать интервью кнопкой «Позже». **Ожидание:** метки на месте, чат «Настройка системы»
в списке; повторное «Познакомиться» открывает **ту же** сессию, kickoff не задвоился.

## M5 — чат знакомства удалён

Удалить чат знакомства и нажать «Познакомиться». **Ожидание:** создаётся новая сессия
с приветствием, ошибки нет.

## M6 — «Применить итоги разговора»

Поговорить, но не доводить интервью до финала, затем нажать «Применить итоги разговора».
**Ожидание:** диалог подтверждения; та же заготовка получила новые поля; метки погасли;
вторая персона не создана.

## M7 — проект без руководителя

| Шаг | Действие | Ожидаемо |
|---|---|---|
| 1 | Создать проект и открыть его | Оверлея знакомства **нет**, рабочее пространство доступно сразу |
| 2 | Настройки проекта | Строка «У проекта нет руководителя. Пока чаты ведёт ваш личный ассистент — без командных механик.» с кнопками «Познакомиться с проектом» и «Назначить руководителя»; обе сначала закрывают диалог |
| 3 | Панель «Команда» | Та же фраза и **одна** кнопка «Познакомиться с проектом» под существующей строкой «Руководитель проекта: не назначен» |
| 4 | Создать чат в проекте | Чат с личным ассистентом (`personaId == me.defaultPersonaId`) |
| 5 | Посмотреть на этот чат | Командных механик нет, и это не выглядит поломкой: пустых блоков и неработающих кнопок не появилось |
| 6 | «Познакомиться с проектом» → пройти интервью | Создан руководитель проекта, назначен дефолтом проекта; строка в настройках исчезла |
| 7 | Создать **новый** чат с руководителем | Механики появились. В уже открытом чате ассистента их не будет — это ожидаемо |

## M8 — флаг выключен

**Ожидание:** ни меток, ни провижна; чаты создаются прежним путём и дают прежние 400 без
`personaId`; `needsOnboarding: false`; маршрут `#/intro` уводит на главную. Персона и поля
в `users.json` при этом сохраняются.

## M9 — две вкладки

Включить флаг одновременно в двух вкладках. **Ожидание:** в `personas.json` ровно один
«Ассистент».

## M10 — ручной выбор другого дефолта

Назначить дефолтом свою персону, не проходя интервью. **Ожидание:** метки погасли,
интервью больше не предлагается.

## M10б — ручная доработка заготовки

Открыть «Ассистента» в «Персонах», задать имя, роль, характер, сохранить.
**Ожидание:** метки погасли; «Познакомиться» не предлагается; правки не перезаписаны.

## M11 — удаление заготовки

Удалить «Ассистента», когда он единственная глобальная персона. **Ожидание:** удаление
проходит (преемник не требуется), оба поля обнулены; следующий «Новый чат» заводит нового
ассистента.

## M12 — мобиль

M2 и M7 в мобильном вьюпорте. **Ожидание:** карточка-приглашение **видна и кликабельна**
в разделе «Персоны» (не «не ломает вёрстку», а именно присутствует); строка настроек
проекта достижима; знакомство открывается страницей/шторкой, а не обрезанным оверлеем.

## M13 — дизайн-ревью

Перед коммитом предложить прогон субагента `designer` по
[docs/design/guidelines.md](../design/guidelines.md) и дождаться ответа — сам не запускать.

## Сценарий E — механика OmO в чате с руководителем проекта

**Что проверяем:** в чате с персоной-руководителем, когда пользователь формулирует
задачу-план («спланируй фичу X», «составь план …»), руководитель предлагает механику
с кнопкой «Запустить»; отказ НЕ должен вызывать повторное предложение в том же чате.

**Предусловие:** M7 пройден — у проекта есть руководитель, открыт **новый** чат с ним
(в чате с личным ассистентом механик нет по решению фичи, это не баг).

| Шаг | Действие | Ожидаемо |
|---|---|---|
| 1 | Открыть чат с руководителем проекта | В шапке аватар персоны, режим работы = Auto |
| 2 | Написать «спланируй фичу X — список задач для онбординга новых клиентов» | Руководитель ведёт диалог, уточняет контекст |
| 3 | После 1–2 уточнений выдаётся карточка-предложение с заголовком механики и кнопкой «Запустить» | Карточка в ленте, иконка механики, кнопка активна |
| 4 | Нажать «Запустить» | В чат уходит `/oh-my-claudecode:ralplan …` (точное имя из каталога OmO), механика запускается |
| 5 | Дождаться завершения механики | Обычный результат работы механики в ленте |

**Краевые случаи — отказ от механики:**

| Шаг | Действие | Ожидаемо |
|---|---|---|
| 6 | Отказаться словами («не надо consensus, реши задачу сам») **ИЛИ** закрыть карточку крестиком | Оба способа эквивалентны: дальше руководитель решает задачу сам |
| 7 | В том же чате поставить ещё одну похожую задачу-план | Диалог как обычно, **БЕЗ** карточки; ни в тексте, ни в DOM нет `<team-mechanic …/>` и упоминаний ralplan/спор/консенсус |
| 8 | Проверить содержательность ответа | Он справляется сам или задаёт уточняющие вопросы |
| 9 | Третья похожая задача подряд в том же чате | Та же картина: содержательный ответ, без карточки и маркера |
| 10 | Открыть **новый** чат с тем же руководителем, поставить нетривиальную задачу-план | Карточка снова появляется — decline живёт в разговоре, а не в персоне |

**Что считать багом:**
- Карточка предлагается повторно **в том же чате** после отказа.
- После отказа в тексте упоминаются «консенсус», «ralplan», «спор с критиком», «прогнать план через …».
- В DOM остаётся сырой текст `<team-mechanic id="…" topic="…"/>` (не сработала стрижка `stripTeamMechanicMarkers`).
- В новом чате с той же персоной карточка **не появляется** на нетривиальной задаче после decline.
- Кнопка «Запустить» отправляет не `/oh-my-claudecode:ralplan …`, а другой формат.
- Механика не запускается (CLI валится) после клика.
- Маркер `<team-mechanic …/>` внутри fenced-блока ``` … ``` или inline-`кода` рисует карточку
  (парсер обязан игнорировать код — `splitByCode` в `frontend/src/features/team/TeamMechanicOffer.tsx`).

**Проверено вручную (Playwright, 2026-08-07, чат `cfa31bd2-…` с Марком QA Lead):**
- decline словами → 3 похожие задачи подряд — все ответы без карточки, без `<team-mechanic>`
  в DOM, без упоминаний механик в тексте.
- Decline **не** привязан к персоне: в новом чате `baff879b-…` с тем же Марком карточка
  «Консенсус-план» снова появилась.
- Маркер не парсится внутри кода — подтверждено по коду (`TeamMechanicOffer.tsx`).

## Что уже автоматизировано (НЕ дублировать руками)

Покрыто юнит-/интеграционными тестами:

- идемпотентность провижна (`DefaultAssistantProvisionerTests`): параллельные вызовы дают
  одну персону, обрыв между созданием и досевом не плодит дубль, выключенный флаг → `null`;
- миграция `IntroCompletedAt` и её сторож «отложенное знакомство переживает рестарт»
  (`UserStoreIntroMigrationTests`);
- `GET /api/auth/me` не создаёт персон и остаётся синхронным; формула `needsOnboarding`;
- точки провижна (стартовый проход, хук включения флага, создание пользователя, рубеж
  в `ChatsController`/`SessionsController`);
- ручная правка заготовки обнуляет `AssistantPersonaId`, правка постороннего поля — нет;
- `POST /api/onboarding/user/apply-transcript`: 404 без живой сессии, 404 без живой
  заготовки, 200 с закрытыми полями;
- промпты знакомства: нет `personas_create`, есть резолвленный `assistantPersonaId`,
  нет «пропустить нельзя»; серверный предохранитель на создание персоны;
- удаление заготовки (в том числе не-дефолтной) обнуляет `AssistantPersonaId`;
- идемпотентность `POST /api/onboarding/user/start`, права `OnboardingController`,
  сериализация полей `User` и восстановление бэкапа с ними.
