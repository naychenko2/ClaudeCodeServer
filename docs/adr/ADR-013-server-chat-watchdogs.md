## Контекст

Инструменты ожидания харнесса — Monitor, `run_in_background`, `CronCreate` — живут **внутри
процесса claude CLI**. В CCS процесс запускается в `--print` и завершается сам (exit=0)
вскоре после хода-продолжения. Фактура из логов 31.08 (чат проекта nga-learning): **четыре
смерти монитора за вечер, каждая через 13–18 секунд после continuation-result**, при живом
интервале опроса 45–60 с — то есть монитор умирал, не успев опросить условие ни разу.
Подмен моделей в тот вечер не было, CCS процессы не Kill'ил: процесс CLI заканчивается сам.

Промптовое лечение («не используй Monitor для долгого ожидания») пробивается насквозь:
хук харнесса, блокируя Sleep-цепочки, буквально инструктирует модель
«use Monitor with an until-loop» — рекомендация хука сильнее секции системного промпта.
`run_in_background` и `CronCreate` — жители того же процесса, их ждёт та же смерть.
Переживает процесс только серверная механика CCS.

Итог: нужен механизм ожидания, живущий в бэкенде, — а не ещё одно правило для модели.

## Решение

**Серверный сторож (watchdog):** модель одним инструментом декларирует «дожидайся условия
и разбуди этот чат». Цикл опроса крутит `WatchdogService` (BackgroundService, тик 5 с),
переживая ходы, рестарты бэкенда и смерть процесса CLI.

**Декларативный poll.** Условие — shell-команда `poll_command`: `exit 0` = дождались,
любой другой код = «ещё нет» (штатная итерация, НЕ терминал). Семантика исходов одного
запуска разведена намеренно (`PollOutcome`):

- `ExitCode 0` → терминал **fired**;
- `ExitCode != 0` → «ещё нет»; упавшая один раз команда сторожа не убивает;
- запуск не состоялся (процесс не стартовал / рабочий каталог исчез / песочница
  недоступна) → счётчик `ConsecutiveLaunchFailures`; **3 подряд → терминал
  launch_failed**; любой состоявшийся запуск счётчик обнуляет;
- истёк таймаут одного запуска → kill, «ещё нет» (запуск СОСТОЯЛСЯ, счётчик сбоев
  обнуляется — иначе зависающая команда за 3 круга гасила бы живой сторож);
- истёк потолок жизни `TimeoutMinutes` → терминал **timed_out**.

**Терминальный будильник.** Промежуточных событий нет — «ещё нет» не несёт информации,
а будильник это ход и токены. Ровно один системный ход по терминалу через
`SessionMessagingService` (`WatchdogAlarm`): `preempt: false` — живой ход получателя не
рвём, будильник встаёт в «честную очередь»; `wait: none`; `callerSessionId: null` — квота
пробуждения штаба не тратится. Потеря единственного терминального события закрыта ретраями
(3 попытки с шагом интервала сторожа, попытка k — в `FiredAt + k·интервал`) и флагом
недоставки `DeliveredAt = null` у терминальной записи — отдельный статус `undelivered`
НЕ заводится, он затирал бы исход. Статус по инициативе модели спрашивается `watch_list`.

**Исполнение — в среде владельца.** Запуск только через `ILauncherFactory.ForOwner(ownerId)`:
local → `cmd.exe /s /c` с СЫРОЙ строкой команды (`ProcessSpec.RawArguments`), container →
`bash -lc` (логин-шелл — PATH профильного окружения, без него `py`/nvm в песочнице не видны).
Сырая строка — следствие инцидента 01.09: .NET `ArgumentList` экранирует внутренние `"` как
`\"`, а cmd живёт не по правилам `CommandLineToArgvW` — poll-команда с вложенными кавычками
(`powershell -NoProfile -Command "…"` от модели) разваливалась в строковый литерал, powershell
ЭХНУЛ тело команды в stdout и вернул exit 0 = ложный fired трёх сторожей за полсекунды.
`/s` заставляет cmd снять только внешние кавычки, внутренние доходят до команды как есть;
промпт-секция дополнительно диктует poll-команду в синтаксисе оболочки БЕЗ powershell-обёрток.
`WorkingDirectory` резолвится ЖИВОЙ на каждый опрос
(rootPath проекта по `ProjectId`; чат вне проектов — домашняя папка владельца через
`UserHomeResolver`): проект могут удалить или переклеить за жизнь сторожа.

**Тулсет `watch`** — по форме ADR-012, волна 2: `POST /mcp/watch/{sessionId}`, хвост несёт
сессию-вызватель, по ней тулсет живьём резолвит владельца, проект и будимый чат; право на
чат и флаг проверяются на КАЖДЫЙ вызов и `tools/list` (`GetOwned` + `WatchMcpEnabled`).
Имя — сознательно не «monitor»: правило именования запрещает однокоренные имена с
пересекающейся семантикой (Monitor CLI уже есть в том же tools/list).
`DelegatedTurnGate` НЕ ставится: гейт в образце (tasks) висит только на туле, запускающем
ход (`tasks_run_executor`); `watch_start` ход не запускает, а гейт отрезал бы полезный кейс
«агент-исполнитель задачи сторожит своё условие».

**Гашение.** Удаление чата гасит сторожей мгновенно (подписка на `SessionManager.
OnSessionDeleted`); архивация и исчезновение чата ловятся тиком (`FindChat` → null или
`IsArchived` → cancelled, БЕЗ будильника — архивный чат будильник оживать не должен).

**Подключение в ход.** `ClaudeSession.BuildTurnMcpConfig` объявляет узел `servers["watch"]`
(http, `alwaysLoad`, токен фабрикой на каждую сборку) на едином условии `WatchHttpOn()` —
схема адреса допускает http И рубильник `Mcp:HttpTransport` включён. На ТОМ ЖЕ условии
клеится секция промпта `mcp-watch` (`WatchPrompts.SectionText`: «долгое ожидание →
watch_start», короткие ожидания в пределах хода — Monitor'у): рассинхрон обучал бы модель
звать тул, которого в ходе нет, — «No such tool available».

**Хранение** — `data/watchdogs.json` (`WatchdogStore`: in-memory + атомарная запись,
повреждённый файл уезжает в `.corrupt-*.bak`, стартуем пустыми); в архив бэкапа попадает
автоматически (всё в `data/`). Отработавшие записи убирает `PruneDelivered`: доставленный
или отменённый терминальный сторож старше суток не нужен никому.

## Рассмотренные варианты

| Параметр | A. Промпт-правило | B. Задачи-напоминания | C. Все события ходом | D. Серверный сторож (принято) |
|---|---|---|---|---|
| Сложность | низкая | низкая | средняя | средняя |
| Стоимость | ноль | ноль | высокая (токены на каждый опрос) | один ход на терминал |
| Переживает смерть CLI | нет | да (но будит человека) | нет | **да** |
| Условие, а не время | — | нет | да | **да** |
| Пробиваемость | хук харнесса перебивает | — | — | — |

**A. Промпт-правило «долгое ожидание — не Monitor».** Отвергнуто: хук харнесса,
блокируя Sleep-цепочки, сам рекомендует «use Monitor with an until-loop» — системный
промпт сессии проигрывает инструкции хука, что и показала фактура 31.08. Лечит симптом,
а не причину: процесс умирал бы и с правильной привычкой модели.

**B. Задачи-напоминания** (`tasks_create` с `dueDate` + `reminderMinutes`). Отвергнуто:
напоминание будит человека уведомлением, а не чат ходом; момент известен заранее, а не
вычисляется условием; нет poll-команды — условие («файл появился», «очередь CI освободилась»)
пришлось бы человеку проверять самому.

**C. Все события ходом** (промежуточное событие каждым опросом). Отвергнуто по цене:
каждое «ещё нет» — это ход и токены без информации; при интервале 30–60 с и потолке жизни
4 часа это десятки пустых ходов на один сторож.

**D. Держать процесс CLI живым.** Отвергнуто: ломит семантику `--print` чужого харнесса,
находится вне нашего контроля и тянет за собой семейство новых проблем (зомби-процессы,
кто гасит, что с реконнектом).

## Анализ компромиссов

- **Терминальный-only против потока событий** — информативность обменяна на стоимость:
  модель узнаёт о промежуточных опросах только по собственной инициативе (`watch_list`).
- **Недоставка — флаг, а не статус**: терминальный исход единственный, его потеря
  недопустима молча, но затирать исход «недоставкой» нельзя — `fired` с недоставленным
  будильником остаётся `fired` с `DeliveredAt = null`.
- **`watch_cancel` только активного**: отмена завершённого сторожа с недоставленным
  будильником отняла бы у него ретраи доставки.
- **Попытка запуска ест интервал** (`LastPollAt`): иначе три несостоявшихся запуска
  пролетали бы за три тика (15 с), не оставляя системе шанса поправиться.
- **Guard после poll + kill по снятию**: пока команда работала, сторож могли снять —
  исход опроса не имеет права перезаписать терминал; идущий poll при снятии убивается
  немедленно (стор эмитит событие, сервис отменяет per-сторож токен, раннер Kill'ит
  процесс) — без этого отменённый poll жил бы сиротой до per-poll таймаута.
- **Оболочка по платформе ЦЕЛЕВОЙ среды владельца** (`TargetIsWindows`), а не хоста:
  песочница всегда Linux — оттуда `bash -lc`; Windows-ветка — `cmd /s /c` с сырой строкой
  (см. «Исполнение» выше: экранирование ArgumentList ломало вложенные кавычки).

## Отсутствие stdio-ветки отката (осознанно)

У старых тулсетов ADR-012 замороженные `mcp/*-server/index.js` — ветки отката на случай
`Mcp:HttpTransport=false`. У `watch` node-сервера **никогда не существовало**, откатывать
нечего: при выключенном рубильнике или негодной для http схеме адреса тулсет ходу не
объявляется вовсе (и секция промпта не клеится). Следствие: владелец с включённым флагом,
но выключенным рубильником транспорта фичу не получит — принятая цена, случай
конфигурационный и редкий.

## Последствия

- Долгие ожидания переживают ходы, рестарты бэкенда и смерть процесса CLI; стоимость —
  один ход на терминал; короткие ожидания в пределах хода остаются за Monitor (разделение
  зафиксировано в секции `mcp-watch`).
- В бэкенде появился постоянный hosted-цикл с исполнением команд, живущим дольше хода.
  Это НЕ новая поверхность атаки (Bash/PowerShell в чате исполняются от того же владельца),
  но время жизни ограничено потолками: TTL ≤ 1440 мин, интервал 30–600 с, per-poll
  ≤ 60 с с kill, ≤ 5 активных на чат и ≤ 20 на владельца, вывод будильника ≤ 10 строк.
- Состав `tools/list` зависит только от свойств сессии/владельца (флаг) — инвариант
  ADR-012 соблюдён; фактические сторожа инварианта у watch — `WatchHttpToolsetTests`
  (флаг/чужой токен → ни состава, ни вызова) и `ClaudeSessionWatchPromptTests`
  (единое условие `WatchHttpOn()` для узла и промпт-секции на все три состояния).
- Ко второй итерации (осознанно не в первой): UI-панель сторожей и отмена из ленты,
  «тихие» карточки без хода, шедулинг-выражения (cron) — сейчас только «дождись условия»,
  будильник чужому чату (сторож будит только чат-постановщика).
