# Хуки oh-my-claudecode: возвращать или нет (разбор, 2026-08-03)

Разбор развилки «вернуть хуки плагина ради фазовой машины Автопилота» против «оставить
`disableAllHooks` и держать механику на своём цикле «до готово». Код читан на версии
плагина в `~/.claude/plugins/marketplaces/omc`.

**Рекомендация: не возвращать (вариант Б).** Ниже — почему, и что вместо этого.

## 1. Откуда окна консоли

Механизм: наши точки запуска ставят `CreateNoWindow = true`
([LocalProcessRunner.cs:39](../../backend/ClaudeHomeServer/Services/Execution/LocalProcessRunner.cs)),
то есть `claude.exe` стартует БЕЗ консоли. На Windows у процесса без консоли каждый
дочерний консольный процесс, запущенный без явного `CREATE_NO_WINDOW`, получает
**свою новую консоль** — то самое мелькающее окно. Наследовать нечего.

```
CCS (служба, есть консоль/нет)
 └─ claude.exe   CreateNoWindow=true  → консоли НЕТ
     ├─ bash.exe / cmd  (инструмент Bash модели)   ─┐
     ├─ rg.exe          (Grep/Glob)                 ├─ без CREATE_NO_WINDOW
     ├─ git.exe         (контекст самого CLI)       │   = НОВОЕ ОКНО каждый раз
     ├─ node            (MCP-серверы)              ─┘
     └─ node run.cjs    (хуки плагина) ──> node <hook>.mjs ──> git rev-parse
                                              ^ здесь windowsHide: true везде
```

Что даёт код плагина: **все** хук-скрипты, реально подключённые в
`hooks/hooks.json`, ставят `windowsHide: true` на своих дочерних вызовах —
`run.cjs:169` (spawnSync), `persistent-mode.mjs:217`, `pre-tool-enforcer.mjs:484,520,530`,
`post-tool-verifier.mjs:87,388,396`, `context-guard-stop.mjs:87`, `code-simplifier.mjs:54`,
`session-start.mjs:279`. Скрипты без `windowsHide` (`plugin-setup`, `status`, `build-*`,
`eval-*`) в `hooks.json` не подключены.

Вывод: **внуки хуков окон не дают**. Окна может давать только сам процесс хука
(`node run.cjs …`) — если его запускает CLI без `CREATE_NO_WINDOW`; но тем же
механизмом и в тех же условиях окна даёт всё остальное, что запускает CLI: Bash,
ripgrep, git, MCP-серверы. Отсюда наблюдение владельца («окна не делись при
выключенных хуках») сходится: остаток — не хуки.

Важно для цены возврата: `PreToolUse` + `PostToolUse` в `hooks.json` навешаны на
матчер `*` — это **1 + 3 = 4 запуска хука на каждый вызов любого инструмента**, каждый
из них = 2 процесса node (`run.cjs` → целевой скрипт). Ход из 30 вызовов инструментов
= ~240 процессов node. Если окна порождают именно процессы хуков, возврат сделает
картину кратно хуже, а не лучше.

### Что измерить (заказ Марку)

1. Живой ход в local-среде при текущем (выключенном) состоянии хуков: снять дерево
   процессов `claude.exe` (`Get-CimInstance Win32_Process` по `ParentProcessId`,
   опрос ~200 мс) и параллельно список окон верхнего уровня (`EnumWindows` /
   `Get-Process | ? MainWindowHandle -ne 0`). Нужен ответ: **у какого именно процесса
   появляется окно** — bash/cmd, rg, git, node.
2. Тот же замер на ходу, где модель точно вызывает `Bash` 10+ раз, и на ходу вообще
   без `Bash` (только Read/Edit). Разница в числе окон = вклад инструмента `Bash`.
3. Контрольный замер: запустить `claude.exe` вручную из консоли (у процесса ЕСТЬ
   консоль) с теми же аргументами и повторить п.2. Если окна пропали — гипотеза
   «нет консоли у родителя» подтверждена, и лечение — дать `claude.exe` скрытую
   консоль (`CreateProcess` с `CREATE_NEW_CONSOLE` + `STARTUPINFO.wShowWindow = SW_HIDE`
   через P/Invoke), а не возиться с хуками.

## 2. Выборочное включение хуков

`--settings` — это **оверлей**, а не замена: наш файл добавляет ключи поверх остальных
слоёв (доказательство — плагины при `disableAllHooks` остаются загружены, скиллы
работают). Значит секция `hooks` в нашем файле хуки плагина только **дополнит** —
убрать чужой хук через settings нельзя. То же про
`LlmProviderRegistry.MergeSettingsInto` (LlmProviderRegistry.cs:335) — это тот же
слой настроек профиля. `disableAllHooks` булев и остаётся единственным рубильником.

Реальный рычаг выборочности лежит не в settings, а в **env самого плагина**:
`DISABLE_OMC=1` и `OMC_SKIP_HOOKS=<список>`. Поддержанные ключи (по коду):
`keyword-detector`, `persistent-mode` / `stop-continuation`, `pre-tool-use`,
`post-tool-use`, `post-tool-use-failure`, `subagent-tracker`, `workflow-drift-guard`.

Но рычаг работает **не в ту сторону**. Ни один из этих скриптов env не читает:

```
session-start.mjs          skill-injector.mjs        permission-handler.mjs
project-memory-session     project-memory-posttool   project-memory-precompact
wiki-session-start         wiki-session-end          wiki-pre-compact
context-guard-stop.mjs     code-simplifier.mjs       pre-compact.mjs
session-end.mjs            verify-deliverables.mjs
```

Итог: точечно **отключить** можно ровно те два хука, которые мы хотели бы вернуть;
точечно **включить** только их — нельзя. Возврат = получить и остальные 14.

## 3. Конфликт двух механизмов принуждения

`persistent-mode.mjs:1295-1333` на `Stop` отдаёт `{"decision":"block"}`, пока
`autopilot-state.json.phase != "complete"`, до 20 раз (`newCount <= 20`).
Наш `SessionManager.ContinueWorkLoopAsync` (SessionManager.cs:4958) шлёт новую
итерацию по `result` хода, лимит `Loop:MaxIterations` (дефолт 20, SessionManager.cs:3111).

Механизмы работают на **разных уровнях** и не отменяют друг друга, а перемножаются:

```
наш цикл: до 20 итераций  ──┐
                            ├─ до 20 × 20 = 400 ходов CLI на одно нажатие
хук: до 20 блоков Stop  ────┘   (и наш UI видит только 20)
```

Три конкретных расхождения:

- **Разные источники истины о завершении.** Мы завершаем по маркеру
  `<promise>ГОТОВО</promise>` (`ContainsPromiseMarker`, SessionManager.cs:5014), хук —
  по полю `phase` в своём state-файле. Модель пишет маркер → мы уходим в `verifying` →
  хук всё равно блокирует Stop, потому что фазу никто не перевёл в `complete`.
  И наоборот: хук отпустил на 21-м блоке — наш цикл продолжает как ни в чём не бывало.
- **Потеря наблюдаемости.** Блоки хука для UI невидимы: `WorkLoopMessage`
  (ServerMessage.cs:270) показывает только наш счётчик. Пользователь видит «итерация
  3/20», а ходов CLI прошло тридцать.
- **Залипания хода не будет, но не благодаря нам.** Спасают собственные гарды
  плагина: `stop_hook_active === true` → безусловный `continue`
  (persistent-mode.mjs:1048), плюс safety-timeout 8.5 с (строка 33), плюс потолок 20.

**Interrupt останется рабочим.** `ClaudeSession.Interrupt` (ClaudeSession.cs:1380–1382)
убивает процесс через `_launcher.Kill` — Stop-хук в мёртвом процессе не исполняется
физически. Это единственная хорошая новость в пункте.

## 4. `OmcKeywordRouting` — оставить, гарды дописать

Настоящий `keyword-detector.mjs` имеет то, чего у нас нет:

| Гард хука | Где | Что делает |
|---|---|---|
| `looksLikeSystemEcho` / `stripSystemEchoes` | ~строка 430 | снимает эхо собственного вывода (наш блок `[МАГИЧЕСКОЕ СЛОВО: …]` — ровно такой случай) |
| `isInformationalKeywordContext` | ~750 | глушит вопрос/объяснение/сравнение/документацию в ±80 символах |
| `hasExplicitWorkflowInvocationContext` | ~944 | требует явного глагола активации рядом со словом |
| гард цитируемых спанов | ~764–800 | слово в кавычках без команды рядом не активирует |
| санитайзер git diff блоков | ~380 | слово внутри диффа не считается |

Но **наш блокер они не закрывают**: списки `INFORMATIONAL_INTENT_PATTERNS`,
`REFERENCE_META_PATTERNS`, глаголы активации — англо/корейско/японско/китайско-тайские.
Русского там нет. Для нашего пользователя, который пишет по-русски и упоминает
латинское `autopilot` в обсуждении, настоящий хук сработает так же ложно, как наша
инъекция. Живое доказательство: постановка ЭТОЙ задачи (обсуждение автопилота на
русском) получила инъекцию «немедленно запусти скилл».

Значит `keyword-detector` возвращать незачем: он делает то же, что
`OmcKeywordRouting.BuildKeywordHint` (OmcKeywordRouting.cs:54), плюс пишет
`autopilot-state.json`, который без `persistent-mode` читать некому.

Что вместо этого — перенести в `OmcKeywordRouting` три гарда (порядок по отдаче):

1. **Эхо-гард.** Если текст содержит наш собственный блок `[МАГИЧЕСКОЕ СЛОВО: …]`
   или `[МАГИЧЕСКИЕ СЛОВА: …]` — вырезать его перед матчингом. Закрывает
   самоподдерживающуюся петлю (постановка задачи → инъекция → цитирование → инъекция).
2. **Требование директивы.** Активировать только когда рядом (±80 символов) есть
   глагол запуска — русский И английский: `запусти|включи|активируй|стартуй|погнали|
   run|start|use|enable|activate|launch`. Без него — упоминание, не команда.
3. **Гард обсуждения.** Глушить при вопросительном знаке в предложении и при маркерах
   разбора: `обсуди|стоит ли|разбери|сравни|почему|что такое|нужно ли|документац|
   статья|vs`.

Плюс исключение кода/цитат: слово внутри ``` … ```, `` ` `` или кавычек не считается —
у нас для маркера промиса такой стриппер уже есть (`ContainsPromiseMarker`,
SessionManager.cs:5014), можно переиспользовать подход.

## 5. Что оживёт вместе с двумя нужными

Из `hooks/hooks.json` — полный состав, который вернётся при снятии `disableAllHooks`:

| Событие | Хук | Что меняется в ОБЫЧНОМ чате |
|---|---|---|
| UserPromptSubmit | `skill-injector` | дописывает «выученные скиллы» плагина в каждый промпт — конкурирует с нашим слоем персоны и recall памяти |
| PreToolUse `*` | `pre-tool-enforcer` | напоминание перед КАЖДЫМ вызовом инструмента + может форсить делегирование агенту; +1 процесс на вызов |
| PostToolUse `*` | `post-tool-verifier`, `project-memory-posttool`, `post-tool-rules-injector` | +3 процесса на каждый вызов инструмента, инъекции правил в контекст |
| PostToolUseFailure | `post-tool-use-failure` | своя логика ретраев поверх нашей |
| PermissionRequest `Bash` | `permission-handler` | **решает разрешения на Bash сам** — у нас permission-поток идёт через `--permission-prompt-tool stdio` в UI; хук вклинивается в него до пользователя |
| Stop | `context-guard-stop`, `workflow-drift-guard`, `code-simplifier`, `persistent-mode` | четыре независимых источника `decision:block` на конце каждого хода |
| SessionStart / SessionEnd | `session-start`, `session-end`, `project-memory-session`, `wiki-*` | срабатывают на КАЖДОМ запуске CLI — включая фоновые one-shot (`OneShotClaudeRunner.cs:140`, `ModelCatalogService.cs:227`, `SubscriptionUsageWarmupService.cs:131`): теги, сводки, память, changelog |
| SubagentStart / SubagentStop | `subagent-tracker`, `verify-deliverables` | трекинг сабагентов в свой стор поверх нашего |
| PreCompact | `pre-compact`, `project-memory-precompact`, `wiki-pre-compact` | своя логика компакта |

Отдельно про фоновые one-shot: им механика Автопилота не нужна вовсе, а
SessionStart/SessionEnd они получат на каждый вызов. Если возврат всё же делать —
делать его ТОЛЬКО в интерактивном `ClaudeSession`, оставив `HooksOffArgs` как есть
в трёх фоновых точках.

## Риски варианта Б (не возвращаем)

- Механика «Автопилот» в продукте — это наш цикл «до готово», а не фазовая машина
  автора плагина. Карточку нужно переписать честно (уже стоит в задаче у Киры),
  иначе продукт обещает не то, что делает.
- `OmcKeywordRouting` остаётся дублем чужого хука и требует поддержки при апдейтах
  плагина (список скиллов). Цена низкая: 78 строк, тест есть
  (`OmcKeywordRoutingTests.cs`).
- Окна консоли остаются нерешёнными — но они и сейчас не решены; отключение хуков
  их не лечило. Лечится отдельно, по п. 1.

## Риски варианта А (возвращаем)

- Нельзя вернуть только нужное (п. 2) — приедут 14 хуков, отключаемых только целиком.
- Перемножение двух enforcement'ов (п. 3) — до 400 ходов CLI на одно нажатие,
  невидимых в UI и оплачиваемых по счётчику токенов.
- `permission-handler` вклинивается в наш поток разрешений — это уже не UX, а граница
  доверия: решение по Bash должно оставаться за пользователем в UI.
- +4 запуска хука на каждый вызов инструмента — латентность каждого хода и
  вероятное ухудшение ровно той проблемы (окна), ради которой всё затевалось.
- В песочнице `--settings` не передаётся вообще (`HooksOffArgs` → `[]` при
  `IsSandboxed`), поэтому статус хуков там определяется смерженным
  `~/.claude/settings.json` владельца — то есть в контейнере хуки, возможно, УЖЕ
  активны, и поведение двух сред разъезжается независимо от нашего решения.
  Это надо проверить (Денис отметил как непроверенное) — вне зависимости от развилки.

## Если владелец всё-таки выбирает А

Порядок шагов, каждый проверяем отдельно:

1. Сначала п. 1 (замер Марка). Если окна дают Bash/rg/git — вопрос хуков к окнам
   отношения не имеет, и решение принимается уже без этой мотивации.
2. Возврат — только в `ClaudeSession` (ClaudeSession.cs:1447), фоновые точки
   оставить с `HooksOffArgs`.
3. Возврат — за фич-флагом и НЕ вместе с нашим циклом: запретить одновременную
   активность `Session.WorkLoop` и autopilot-хука (иначе п. 3). Технически: при
   активном `WorkLoop` продолжать передавать `disableAllHooks`.
4. `OMC_SKIP_HOOKS` в env хода — заглушить всё, что читает env, кроме
   `keyword-detector` и `persistent-mode`; остальные 14 принять как данность.
5. Проверить перед живым инстансом: (а) permission-запрос на Bash по-прежнему
   доходит до UI и ждёт человека; (б) `Interrupt` гасит ход с активной фазой
   автопилота; (в) счётчик ходов CLI за одно нажатие Автопилота; (г) поведение
   в песочнице не разъехалось.
