# Процессы фичи — разрез: шаблоны workflow и наследование специальностей

Разрез к эпику «Процессы фичи» (`a149e308`), задача `781bafc0` (role=cut). Источник решений — интервью Андрея 12.11 в описании эпика; фон — `docs/research/ai-fabrika-review-2026-11.md`.

## 0. Главное до деталей

1. **Слой «профиль специальности» уже есть**: `SpecialtySettingsStore` (`backend/ClaudeHomeServer.Llm/SpecialtySettingsStore.cs`, файл `data/specialty-settings.json`, v5, один глобальный слой, пишет только админ через `PUT /api/specialties/settings/global`). В рантайме уже наследуются:
   - матрица моделей: пустая ячейка `Persona.TierX` → ячейка специальности → слоты (`ModelAssignmentResolver.PersonaMatricesFor` → `UserModelTierResolver`);
   - `DefaultTier` специальности;
   - секции промпта (`PromptSectionsContributor` → `EffectivePromptSections` по `Persona.Specialty`).
   
   **Копируются в персону** и потом живут отдельно ровно две вещи:
   - группа прав `Access/Tools/DisallowedTools` (`SpecialtyTemplatesService.Apply`, при создании и смене специальности);
   - типовые умения `DefaultBindings` (`PersonasCrudService.MaterializeDefaultBindingsAsync`, комментарий «модель копия при создании»). **Решение Андрея 12.11 отменяет это прежнее решение** — отмечаю явно.
   
   Значит, наследование — это доводка двух копирующих путей, а не новый слой.
2. **Шаблон не становится вторым рантаймом.** Конвейер по-прежнему ведёт оркестратор (Софья) карточками `TaskRoles`. Шаблон — конфигурация, её читают ровно в трёх точках: создание задачи фичи (`TaskManager.Create`), запуск исполнителя (`TaskExecutionService.ExecuteAsync`) и проекция (`FeatureProjector`).
3. **Этап шаблона = роль задачи из закрытого набора `TaskRoles`.** Новых видов работ шаблон не вводит.

## 1. Модель данных

Новый стор `data/workflow-templates.json` (Core-модели плюс стор в вертикали `ClaudeHomeServer.Tasks`). Попадает в бэкап по умолчанию.

```
WorkflowTemplateFile { Version; Global: List<WorkflowTemplate>; Projects: Dict<projectId, List<WorkflowTemplate>> }

WorkflowTemplate
  Id, Name, Description            // описание читает рекомендатель
  Version: int                     // +1 при каждом сохранении; старые версии НЕ храним (см. §4)
  BuiltInKey?: "full-cycle" | "fast-track"   // встроенный пресет; удалить нельзя, сбросить к коду можно
  BasedOn?: { TemplateId, Version } // у проектного шаблона: от какого глобального форкнут
  Stages: List<WorkflowStage>       // порядок = порядок маршрута

WorkflowStage
  Role: string                     // ∈ {cut, design, plan, step, review, qa, final, merge}; rework берёт этап step
  Presence: "on" | "optional" | "off"  // см. «Пропуск» ниже
  Specialty?: PersonaSpecialty     // кого звать (подсказка оркестратору, предзаполнение personaId)
  PersonaId?: string               // или конкретная персона; взаимоисключимо со Specialty
  Prompt?: string                  // доп. текст этапа, ≤ 4000 символов, только ДОБАВЛЯЕТСЯ (см. §6)
  TierStrong?/TierMedium?/TierWeak?: string   // ячейки той же лексики ADR-007: id модели | "preset:{id}"
  DefaultTier?: ModelTier
  DisallowedTools?: List<string>   // только СУЖЕНИЕ поверх прав персоны
  McpAllow?: List<string>          // подмножество ключей MCP, уже выданных персоне; null — без сужения
  StallMinutes?: int               // [5..240], null — Tasks:ExecutorStaleMinutes
  StallPolicy?: "nudge-alert" | "alert" | "stop-alert"   // строки, а не enum (урок McpCatalogRef)
```

**Пропуск шага** выражен полем `Presence` этапа, а не отсутствием этапа:
- `on` — этап в маршруте всегда;
- `optional` — по умолчанию в маршруте, человек или рекомендатель может снять;
- `off` — этапа в этом шаблоне нет (фаст-трек: `design=off`, `qa=off`).

Несъёмные роли зашиты в коде (`WorkflowRules.NonSkippable`): `step`, `merge` и, по моей рекомендации, `final`. Финал — единственная проверка решения целиком, а скрытый в графе пропуск — уже названный риск эпика. **Вопрос Андрею: `final` несъёмный?** Валидатор шаблона отказывает в `Presence=off` у несъёмной роли.

**На эпике** (`TaskItem`, аддитивные nullable-поля, только у `role=feature`, `BackupSchema.Version` не растёт — прецедент `Hold`/`Note`):

```
WorkflowProposal? { TemplateId, Scope: "global"|"project", Skipped: List<role>, Rationale, ProposedAt, Model }
Workflow?         { TemplateId, Scope, Route: List<role>, Skipped: List<role>,
                    ConfirmedVersion, ConfirmedAt, ConfirmedByUser: true }
```

**На задаче фичи** (любая роль, кроме `feature`/`consult`):

```
Stage? : StageSnapshot { TemplateId, TemplateVersion, Role, <все поля WorkflowStage после резолва> }
```

## 2. Наследование специальностей

Профиль специальности — существующий `SpecialtyTemplateSettings` (+ дефолты кода в `SpecialtyCatalog`/`SpecialtyPromptPresets`). Новый слой не заводим. Доводим три группы.

| Группа | Сейчас | Станет | Резолв (одна точка) |
|---|---|---|---|
| Матрица моделей, `DefaultTier` | наследуется (пустая ячейка) | без изменений | `ModelAssignmentResolver` → `UserModelTierResolver.ModelFor` |
| Секции промпта | наследуются | без изменений; персонального override не заводим (персонализация — контракт персоны) | `PromptSectionsContributor` |
| Права `Access/Tools/DisallowedTools` | копия при создании и смене специальности | **наследуются группой целиком**; override персоны — тоже группой | новый `PersonaManager.Hydrate` |
| Типовые умения (Skill) | копия в `Persona.Bindings` | Skill-умения специальности наследуются в рантайме; персона гасит своё умение привязкой `Mode=Off` с тем же `SkillName` | `PersonaBindingsService` (эффективный список) |
| Умения, подбираемые ИИ (Knowledge/Project/…) | копия | остаются копией: они проектные, наследовать нечего | — |

**Права — группой и флагом, без перекройки полей.** Persona получает одно аддитивное поле `InheritsAccess: bool`.
- `true`: при КАЖДОМ чтении `PersonaManager` (Get/GetByOwner — единственная граница выдачи персоны) перезаписывает `Access/Tools/DisallowedTools` эффективным шаблоном специальности. Специальность `None` — дефолт кода (Full, без ограничений).
- `false`: поля персоны — её override.

Почему не сделать `Access` nullable: его читают напрямую 17 файлов, от `PersonaAccessPolicy` и `ClaudeSession` до `ExternalMcpContexts` и `PersonaConsultantToolset`, а `Tools == null` уже занято значением «без ограничений». Гидратация на границе выдачи оставляет их нетронутыми.

Персистентные `Access/Tools/DisallowedTools` продолжаем писать материализованными. Тогда откат кода на версию без флага видит последнее значение, а не дефолт Full. При сохранении специальности `SpecialtiesController` перематериализует персоны этой специальности, чтобы снимок для отката не протухал.

**Форма персоны (фронт):** у каждой группы два состояния — «как у специальности» (значения показаны серым, ссылка на роль) и «своё». Переключение в «своё» копирует текущие эффективные значения, возврат «как у специальности» выкидывает override.

### Миграция `data/personas.json`

На проде 288 персон:
- все `Access=full`, `Tools` задан у 1, `DisallowedTools` — у 0;
- ячейки моделей у 51;
- специальность у 196, `None` у 92.

Разовая миграция при загрузке стора, идемпотентная, с маркером в файле. Порядок:
1. **Сухой прогон** — админская ручка `POST /api/personas/migrations/specialty-inheritance?dryRun=true`, отчёт по каждой персоне: что станет наследуемым, что останется override. Андрей смотрит отчёт ДО включения.
2. **Права.** Если группа персоны совпадает с эффективным шаблоном специальности на момент миграции → `InheritsAccess=true`; иначе `false` (override сохраняет текущее поведение байт в байт). У `Specialty=None` → `true` только при Full/без ограничений.
3. **Ячейки моделей.** Ячейка персоны, равная эффективной ячейке специальности, очищается: поведение то же, но правка специальности теперь дойдёт. Отличающиеся остаются override. **Вопрос Андрею:** вариант «очищать равные» рискует снять намеренную «закрепку того же значения» (пример — подобранный руками `tierWeak` Веры). Отчёт сухого прогона поимённо покажет, что очищается.
4. **Умения.** `Bindings` с `Type=Skill`, совпавшие с профилем специальности по `SkillName`, удаляются: теперь наследуются. Несовпавшие остаются. AI-привязки не трогаем.
5. Персоны с `TemplateKey` (пантеон OmO) мигрируют по тем же правилам: регламент их шаблона и права специальности — разные оси.
6. В бэкап новая форма уезжает аддитивно. `BackupSchema.Version` не растёт: поля аддитивные, и откат читает материализованные значения.

## 4. Версионирование

Решение: **эпик помнит маршрут и номер версии при подтверждении, каждая задача — полный слепок своего этапа.** Нужно и то, и другое, но слепок — на задаче, а не на эпике.

- «Правка применяется со следующего шага» = следующей **созданной** задачи: `TaskManager.Create` берёт текущую версию. Уже созданные задачи (в том числе ещё не запущенные) работают по своему слепку. Доработка (`rework`) — новая задача, она получает текущую версию. Это следует из решения, но озвучить стоит.
- **Состав маршрута** (какие этапы есть) фиксируется подтверждением человека и правкой шаблона сам не меняется: QA, тихо исчезнувший или появившийся посреди фичи, — сюрприз. Новая версия с другим составом даёт в шапке фичи «шаблон изменился: v3 → v4, обновить маршрут?», и обновление — снова подтверждение человека.
- Старые версии шаблона не храним: истина для исполнения — слепок на задаче, для показа хватает номера и `BasedOn`. Удалённый шаблон не ломает идущие фичи.

## 5. Рекомендация моделью

- **Шов:** новое место фонового действия `feature-workflow-recommend` в реестре `LocalActionRouter` (исполнителя выбирает админ, как у остальных мест), сервис `WorkflowRecommender` в `ClaudeHomeServer.Tasks`, вызов через `CheapTextRunner`.
- **Вход:** `Title` и `Description` эпика плюс каталог доступных шаблонов (глобальные и проекта: id, имя, описание, этапы с `Presence`).
- **Выход:** `{ templateId, skipped: [role], rationale }`. Сервер валидирует: `templateId` из каталога, `skipped` ⊂ этапов с `Presence=optional`. Мусор отбрасывается, сбой — предложения просто нет.
- **Запуск:** при создании эпика (best-effort, не роняет создание) и кнопкой «Подобрать маршрут». Результат пишется в `epic.WorkflowProposal`.
- **Подтверждение:** только человек, REST `POST /api/tasks/{id}/workflow/confirm` (под `[Authorize]`, проверка владения эпиком через `FeatureOwnerGate`/`IProjectAccess`). Человек может сменить шаблон и пропуски перед подтверждением. MCP-инструмента подтверждения **нет**: агент может только запросить предложение.
- **Без подтверждения:** при `WorkflowProposal != null && Workflow == null` `ExecuteAsync` отказывает любой задаче фичи, кроме `consult`, с текстом «маршрут фичи не подтверждён». Эпик без того и другого — легаси-маршрут, гейт не действует: старые фичи не ломаем.

## 6. Инварианты, пути входа, сторожа

**И1. Профиль специальности меняет только админ, и никакой путь правки персоны его не пишет.**

| Путь записи | Закрытие |
|---|---|
| `PUT /api/specialties/settings/global`, `settings/fallback/global`, `settings/reset/global`, `settings/reset/owner` | уже `[Authorize(Roles="admin")]` |
| `SpecialtySettingsStore.RemapModels`, `ResetModelSettings`, миграции стора, `PresetStore` | системные пути, без изменений |
| `PUT /api/personas/{id}`, `POST /api/personas`, `pantheon/connect`, `ai/quick-create`, `ai/team` | пишут только поля персоны и `InheritsAccess` |
| MCP `personas_create`, `personas_update`, `personas_bindings_set`, `personas_mcp_grant` | то же |
| `bindings/apply-defaults` | пишет только `Persona.Bindings` |

Сторож — IL/рефлексия: методы записи `SpecialtySettingsStore` (`SetGlobal/SetOwner/SetUser/ResetModelSettings/RemapModels`) вызываются только из allow-list (`SpecialtiesController`, миграции, `PresetStore`). Тест: правка персоны через REST и MCP не меняет хеш `specialty-settings.json`.

**И2. Наследование живое:** правка специальности меняет эффективные права и модель персоны с `InheritsAccess=true` / пустой ячейкой без правки персоны; override переживает правку специальности.

| Путь чтения прав | Закрытие |
|---|---|
| `PersonaManager.Get/GetByOwner/All` | `Hydrate` |
| `PersonaAgentFileGenerator` / per-run `--agents` | берут персону из `PersonaManager` — проверить |
| `Session`-снимки персоны, если есть (`Core/Models/Session.cs` читает `Access`) | проверить, не кэширует ли сессия персону мимо менеджера |
| бэкап/restore | персистентные поля материализованы |

Тесты: правка специальности → `PersonaAccessPolicy` даёт новый набор запрещённых; персона с override — старый.

**И3. Таймаут этапа обойти нельзя.**
- `StallMinutes` клампится в [5..240]: 0/null/мусор — дефолт конфига, а не «бесконечно».
- `StallPolicy` — белый список.
- Слепок `task.Stage` пишет только `TaskManager.Create`: `TasksController` PUT, MCP `tasks_update` и `tasks_complete` поле игнорируют (не принимают в DTO).

Сторож: тест на каждый путь обновления задачи — `Stage` неизменен. Мутацией проверить, что тест краснеет, если `Update` начнёт копировать поле.

**И4. Шаблон не применяется задним числом.**

| Путь | Закрытие |
|---|---|
| `TaskManager.Create` | единственный писатель `Stage` |
| `ExecuteAsync`, `ClassifyStall`, `BuildPersonaPrompt`, резолв модели | читают только `task.Stage` |
| сохранение шаблона | не трогает `tasks.json` |

Сторож — тест «сохранили шаблон v2 → задача, созданная при v1 и запущенная после, исполняется по v1»; плюс IL-сторож «`TaskExecutionService` не ссылается на стор шаблонов».

**И5. Этап только сужает права и никогда не расширяет.** `DisallowedTools` и `McpAllow` пересекаются с правами персоны в `PersonaAccessPolicy`. `McpAllow` с ключом, не выданным персоне, молча отбрасывается. Тест: этап с чужим MCP не даёт его исполнителю.

**И6. Промпт этапа не вытесняет правила.** Только секция `## ЭТАП`, лимит длины, показ на экране этапа в блоке «Вход». Тест: постановка с промптом этапа содержит `ПРАВИЛА` байт в байт (расширение сторожа `RulesTemplate_СовпадаетСВстроеннымФолбэком`).

**И7. Маршрут подтверждает только человек.**

| Путь записи `epic.Workflow` | Закрытие |
|---|---|
| `POST /api/tasks/{id}/workflow/confirm` | единственный |
| `TasksController` PUT, MCP `tasks_update` | поле не принимают |
| рекомендатель | пишет только `WorkflowProposal` |

**И8. Изоляция проектных шаблонов.** Читает и пишет их только тот, у кого есть доступ к проекту через `IProjectAccess`. Писать может только владелец проекта: участники общих проектов не меняют чужим агентам промпт и инструменты. Глобальные шаблоны пишет только админ. Новые ручки — под `[Authorize]`, сторож `AnonymousEndpointsGuardTests` их подхватит.

Плюс стандарт: строка новой сборки/типов в сторожах границ, если стор живёт в `ClaudeHomeServer.Tasks`.

## 7. Что НЕ делаем

- Движок, сам двигающий фичу по этапам (автосоздание карточек, автозапуск следующего этапа): конвейер ведёт оркестратор.
- Новые роли и виды работ сверх `TaskRoles`.
- Ветвления и условия в маршруте («если бэк — то…»): маршрут линеен, `Lane` остаётся у шагов плана.
- Персональный override секций промпта специальности.
- Наследование `Effort`, `Contract`, характера, голоса, AI-подобранных привязок.
- Историю версий шаблона и дифф версий шаблона (дифф — только у артефактов этапа).
- Жёсткий wall-clock-лимит хода: таймаут — порог молчания и политика.
- Показ пропущенных этапов в графе (решение Андрея). Данные о пропуске хранятся (`Workflow.Skipped`), возврат к показу — после прототипа.
- Применение шаблона к уже идущим фичам без подтверждения.
- Возвращение per-owner слоёв специальностей (сняты в v5 осознанно).
