# ADR-012: Продуктовые MCP-серверы переезжают со stdio на HTTP внутри Kestrel

**Статус:** Принято (фаза 1 — каркас и один сервер)
**Дата:** 2026-08-26
**Принимающие решение:** Андрей (владелец продукта), Александр (архитектор)
**Реализация:** Денис (бэкенд); разведка транспорта — Денис и Марк (фаза 0)
**Связанные артефакты:**
[McpTransportController](../../backend/ClaudeHomeServer/Controllers/McpTransportController.cs),
[Services/Mcp/Http](../../backend/ClaudeHomeServer/Services/Mcp/Http),
[ClaudeSession.BuildTurnMcpConfig](../../backend/ClaudeHomeServer/Services/Llm/Claude/ClaudeSession.cs),
[docs/architecture/mcp-servers.md](../architecture/mcp-servers.md)

## Контекст

Каждый продуктовый MCP-сервер — файл `mcp/{имя}-server/index.js`, который CLI поднимает
**отдельным процессом node** на каждый ход. Процессов ровно столько, сколько серверов
объявлено в конфиге хода: у чата с персонами это встроенные серверы плюс по `pmem_*` на
каждого консультанта.

Ключевой факт, установленный отдельным стендом 15.08.2026 (claude CLI 2.1.229) и записанный
в [mcp-servers.md](../architecture/mcp-servers.md): **`alwaysLoad` управляет видимостью
инструментов, а не моментом запуска процесса.** Сервер без `alwaysLoad`, никем не вызванный,
всё равно поднимается при старте CLI. Отсюда вывод той доки: «уменьшить можно только числом
объявленных серверов; осознанно оставлено как есть».

Этот вывод верен, но **только внутри допущения, что транспорт — stdio**. Оно и есть предмет
решения: цена платится не за инструмент и не за объявление сервера как такового, а за то, что
объявленный сервер — это команда запуска процесса. Продуктовые серверы почти все устроены
одинаково: тонкий JSON-RPC-фасад, который ходит в НАШ ЖЕ бэкенд сервисным JWT владельца. Для
такого фасада процесс node — чистый посредник.

Замер этой ветки (три хода в одном процессе CLI, конфиг из двух серверов, счёт node-процессов
в дереве CLI):

| Конфиг хода | node-процессов в дереве |
|---|---|
| `widgets` stdio + `notifications` stdio | 5 |
| `widgets` **http** + `notifications` stdio | 4 |

Разница ровно единица на перенесённый сервер, инструмент при этом работал на всех трёх ходах.
В пересчёте на полный состав: **12 объявленных stdio-серверов = 12 процессов node; 3 сервера
на http = 0 процессов.** На боевом это те самые ~610 МБ на 14 персон, и так на каждый ход.

## Решение

Продуктовые MCP-серверы переводятся на **MCP-over-HTTP внутри Kestrel**: `POST /mcp/{name}`,
JSON-RPC 2.0 в теле, реестр тулсетов (`IMcpToolset` + `McpToolsetRegistry`), общий контроллер
на все серверы. Новый сервер добавляется описанием схем и одной регистрацией в DI, а не
копией контроллера.

Фаза 1 (этот ADR) — каркас и **ровно один** сервер: `widgets` (148 строк, ни одного вызова
API, потеря при провале нулевая). Остальные восемь остаются на stdio до фазы 2.

### Условия транспорта (разведка фазы 0, не подлежат смягчению)

- **Только `http`.** По `https` с боевым сертификатом CLI упирается в
  `ERR_TLS_CERT_ALTNAME_INVALID` и **молча** прячет инструмент от модели — ни ошибки в ленте,
  ни записи в логе. Поэтому схема адреса — гейт: не `http` ⇒ сервер объявляется по-старому,
  через stdio, плюс WARN (fail-closed, см. ниже).
- **Адрес — только из `SessionManager.ResolveTasksApiUrl(ownerId)`** плюс `/mcp/<name>`.
  Резолвер уже умеет песочницу (`McpApiUrlOverride` → `host.docker.internal`), явный
  `McpTasksApiUrl` и адреса Kestrel с предпочтением http. Второго правила про порт заводить
  нельзя: на бою Kestrel слушает `:80`/`:443`, порта 5000 там нет вовсе.
- **SSE не реализуем.** Клиент пробует `GET` на транспорт, получает `405` и спокойно живёт
  дальше (проверено живым CLI).
- **`server/discover`** — нестандартный метод, которым CLI зондирует сервер ДО `initialize`:
  отвечаем `-32601`, на работу не влияет (в живом прогоне виден первым запросом).
- **`notifications/initialized` приходит без `id`.** На запрос без `id` — `202` с пустым
  телом; ответ-объект с `id: null` — нарушение протокола.
- **`alwaysLoad: true` при `type: http` работает** и сохранён: без него первый вызов в ходе
  падает «No such tool available» (claude-code#19282). Проверено ходом, где `widget_show` был
  первым действием модели.

### Авторизация

Эндпоинт под `[Authorize]`, владелец — **только из claim `sub`** сервисного JWT; ни URL, ни
тело, ни заголовки на владельца не влияют. Это не формальность: на бою Kestrel слушает
`0.0.0.0:80` и `0.0.0.0:443` с публичным доменом, то есть `/mcp/*` торчит в интернет. Для
`widgets` анонимный доступ был бы безобиден, но в фазе 2 сюда переедет `tasks`, и анонимный
`POST /mcp/tasks` с `tools/call: tasks_list` читал бы чужие задачи. Токен уезжает в конфиг
хода обычным заголовком `Authorization`, как у `fal-ai`/`glif`.

### NO_PROXY — теперь обязательное условие работы, а не удобство

Раньше в бэкенд по локальному адресу ходил node-процесс сервера со своим окружением. Теперь
туда идёт **сам CLI**, и его http-клиент уважает `HTTP_PROXY`: непокрытый `NO_PROXY` локальный
адрес уезжает в прокси и возвращает 503 `CLIENT_HTTP_NOT_IMPLEMENTED` — снова молчаливое
исчезновение инструмента. Воспроизведено живым прогоном: с пустым `NO_PROXY` модель отвечает
«нет инструмента», с выставленным — вызывает его.

Поэтому `ClaudeSession` ставит переменную сам на каждый ход
([LoopbackProxyBypass](../../backend/ClaudeHomeServer/Services/Mcp/Http/LoopbackProxyBypass.cs)):

- **обе формы** (`NO_PROXY` и `no_proxy`) — как это делает `SandboxManager` для песочницы;
- **дополняет унаследованное, а не затирает**: `HTTP_PROXY` на машине бывает единственным
  маршрутом до провайдеров, его исключения ломать нельзя;
- хост берётся **из фактического адреса эндпоинта** плюс базовый список: сопоставление идёт
  по имени, и `localhost` не покрывает `127.0.0.1`;
- значение **детерминированно** (фиксированный порядок, дедупликация): env-оверрайды входят в
  сигнатуру запуска, а мерцание сигнатуры перезапускает процесс CLI со всеми MCP-серверами —
  ровно то, с чем мы боремся.

### Fail-closed и рубильник отката

Транспорт зашит в код, поэтому у него есть конфиг-ключ `Mcp:HttpTransport` (дефолт — включён).
Выключенный ключ и негодная схема адреса дают один и тот же исход: сервер объявляется
**прежним stdio-способом**, инструмент у модели остаётся, причина уходит в лог. Поэтому
`mcp/widgets-server/index.js` не удалён — это путь отката (и заодно живая фикстура
`McpProbeServiceTests`).

Значение транспорта входит в отпечаток состава (`shapes["widgets"]` = `t:http` | `t:stdio`) и
через него — в сигнатуру запуска. Без этого переключение рубильника не пробило бы живой
процесс доживания и применилось бы «когда-нибудь потом», то есть не сработало бы ровно тогда,
когда понадобится.

### Заголовки контекста и журнал вызовов

При stdio заголовки к бэкенду ставит наш же код сервера; при http их шлёт CLI, и доедет
только то, что статикой лежит в `headers` конфига. Поэтому:

- `X-Caller-Session-Id` = `Info.Id` кладётся в `headers` (id чата постоянен в рамках сессии, в
  сигнатуру не входит). На этом заголовке держатся `[DenyOnDelegatedTurn]` (при отсутствии он
  **fail-open**) и ветвление `McpCallLogMiddleware`. В фазе 2 его потеря вернула бы платный
  цикл «доклад → запуск → доклад», ради которого гейт и писали.
- Имя инструмента при http лежит в ТЕЛЕ JSON-RPC, а журнал читает заголовок `X-Mcp-Tool` —
  контроллер достаёт имя из тела и кладёт его во входящий заголовок. Запись делает та же
  `McpCallLogMiddleware`: вторая точка записи дала бы двойной счёт. Служебные методы
  протокола попадают в таблицу как `widgets/initialize`, `widgets/tools/list` и т.п.
- Штатный `GET` (проба SSE) помечается `McpCallLog.SkipItemKey` и в статистику не идёт —
  иначе каждый ход давал бы ложный «отказ MCP» в `GET /api/mcp/calls` и в алерте
  `04-mcp-errors`.

### Роут вне `/api` — проверенные следствия

Уйти под `/api/mcp/{name}` нельзя: там уже живёт `/api/mcp/calls`. Отсюда три следствия:

1. **`AllowedHosts`.** В проде список содержит `localhost` и `host.docker.internal`, то есть
   обе формы обращения к транспорту проходят. В чужом `appsettings.Local.json` их может не
   быть — тогда запрос отобьётся 400 «на пустом месте».
2. **SPA-fallback.** Опечатка в имени сервера (`/mcp/widgetz`) даёт наш 404 — маршрут
   `mcp/{name}` матчится и без известного тулсета (проверено живым стендом). Путь из двух
   сегментов (`/mcp/a/b`) наш маршрут не ловит, и там инстанс с собранным фронтом отдаст
   `index.html` со статусом 200.
3. **Инспекционная копия** режет все не-GET запросы вне `/api/auth` 403-м, значит MCP-вызовы
   в ней не работают — это защита, а не дефект: живые инструменты в копии означали бы правки
   боевых данных.

## Отвергнутые варианты

**B. Node-мультиплексор — один процесс на все серверы.** Один `index.js`, который поднимает
все фасады внутри себя и мультиплексирует stdio. Отвергнут: экономит процессы, но оставляет
всю прежнюю цену — второй рантайм (node) рядом с бэкендом, дублирование схем и валидации на
двух языках, свой цикл живучести stdio, и главное — CLI всё равно объявляет N серверов, то
есть мультиплексор пришлось бы прятать за N записей конфига, каждая со своим процессом.
Настоящий выигрыш здесь только у транспорта, который вообще не требует процесса.

**C. Схлопнуть `pmem_*` в один сервер** с инструментами вида `memory_recall_<handle>`.
Отвергнут дважды. Во-первых, это лечит симптом у одной группы серверов (память консультантов),
а расход на остальные девять остаётся. Во-вторых, ломает правило именования из
`CLAUDE.md`: набор однокоренных имён с пересекающейся семантикой — ровно то, на чём модель
путается, и число инструментов в контексте хода при этом растёт линейно по персонам, тогда
как сейчас растёт число процессов, а состав tools/list у каждого `pmem_*` одинаковый.

## Известное ограничение: `dify`

`dify` — тоже наш сервер (`mcp-dify/`, TypeScript со сборкой, единственный с внешней
зависимостью), но в конфиг хода он приходит **не** из `BuildTurnMcpConfig`, а из внешнего
базового конфига `McpConfigPath` — машинно-специфичного файла вне репозитория. Правкой сборки
конфига его не мигрировать: нужно либо менять содержимое чужого файла, либо перекрывать запись
одноимённым ключом, а это отдельное решение. В фазе 2 он идёт последним и отдельной подзадачей.

## Последствия

- Раздел «`alwaysLoad` управляет видимостью…» в
  [mcp-servers.md](../architecture/mcp-servers.md) больше не заканчивается выводом «уменьшить
  можно только числом объявленных серверов»: теперь есть второй способ — сменить транспорт.
  Правка внесена этим же изменением.
- Утверждение `CLAUDE.md` «каждый MCP-сервер продукта — один файл `mcp/{имя}-server/index.js`,
  чистый Node, stdio JSON-RPC» перестало быть полным — поправлено там же.
- Сторож `McpToolsetStabilityTests` остаётся нетронутым: он стережёт тело
  `BuildTurnMcpConfig`, где живут восемь непереехавших stdio-серверов, а гейт `widgets` как был
  в `SessionManager.BuildWidgetsContext`, так и остался. Инвариант «состав `tools/list` не
  зависит от хода» на новой поверхности держат отдельные тесты
  (`McpHttpTransportTests`, `McpHttpTransportConfigTests`, `McpHttpOwnerIsolationTests`).
- Фаза 2 переносит остальные серверы по одному; у каждого, в отличие от `widgets`, есть вызовы
  API и per-owner данные, поэтому гейты по сессии и журнал вызовов должны переезжать вместе с
  сервером, а не после него.
