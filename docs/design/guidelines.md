# Дизайн-гайдлайны ClaudeCodeServer

Конвенция для ВСЕХ изменений UI — общая канва разработки: новый код обязан ей
следовать, старый подтягивается по мере касания (правило бойскаута). Документ описывает
то, что уже реализовано в коде; источник правды по значениям —
[design.ts](../../frontend/src/lib/design.ts) и [theme.css](../../frontend/src/lib/theme.css).

## Принципы

1. **Тёплая «бумажная» гамма** в духе Claude/Anthropic: кремовые фоны, тёплые нейтрали,
   один оранжевый акцент. Никаких холодных серых и чистого чёрного.
2. **Острова** (стиль Rider Islands): экран — это скруглённые карточки с зазорами на общем
   фоне-холсте с дудл-паттерном, а не сплошные панели встык с 1px-границами.
3. **Accent-дисциплина**: оранжевый `C.accent` — только главное действие и активные
   состояния. Если на экране много оранжевого — это дефект. Отдельные гаммы существуют
   не просто так: план — индиго (`C.plan*`), хаб-навигация — «чернильная» (`C.navInk`),
   статусы — свои (`success/warning/danger/info`).
4. **Воздух**: 4px-сетка (`SP`), щедрые отступы, зазоры между островами вместо границ.
5. **Три шрифта, три роли**: PT Serif — заголовки страниц и hero-тексты, Hanken Grotesk —
   весь UI, JetBrains Mono — код/пути/технические значения. Другие не подключаем.
6. **Тёмная тема бесплатна**, пока цвета берутся из токенов: `C.*` — это CSS-переменные,
   обе темы живут в theme.css. Захардкоженный hex ломает тёмную тему молча.
7. **Меньше нового кода**: перед новым компонентом/токеном — поищи готовый
   (existence-first). Дубль существующего решения — дефект, даже если работает.

## Железные правила

Нарушение любого из них в новом коде — дефект, который чинится до коммита.
Правило про цвета проверяется автоматически — см. «Линт-щиток» ниже.

- **Цвета — только из `C`** (lib/design.ts). Сырой hex/rgb в `.tsx` запрещён.
  Легальные исключения: theme.css (там живут значения), темы сторонних
  редакторов/вьюверов (CodeMirror, Mermaid, OnlyOffice, xterm), `GROUP_COLORS`.
  - Текст поверх заливки **токеном** (`C.accent`, `C.plan`, `C.danger`, `C.success`) —
    это `C.onAccent`: в тёмной теме заливка ярче, а текст на ней темнеет, так задумано.
  - Текст поверх подложки, **не зависящей от темы** (цвет из палитры, надпись на фото,
    лайтбокс) — это `C.onDark`: он белый в обеих темах, иначе надпись пропала бы.
- **Размеры — из шкал**: шрифты `FS`, отступы `SP`, радиусы `R`, тени `SHADOW`,
  z-index `Z`, ширины модалок `MODAL_W`. Magic numbers вида `fontSize: 13.5` не заводим.
- **Контролы — только из [components/ui/](../../frontend/src/components/ui)** (и общих
  компонентов уровнем выше — Toolbar, EmptyState). Свою кнопку/поле/модалку/тумблер
  из div собирать нельзя — если примитива не хватает, расширь его пропом или заведи
  новый в `ui/` (см. «Как расширять систему»).
- **Стили — inline-objects**. Без Tailwind, CSS-модулей и styled-components.
  Глобальный CSS — только theme.css и index.css (анимации, шрифты).
- **Иконки — lucide-react**, размеры из `ICON_SIZE` ([ui/icons.ts](../../frontend/src/components/ui/icons.ts)).
  Инлайновые SVG — только когда в lucide нет подходящей.
- **Каждый экран работает на мобиле**: `useIsMobile()` (lib/breakpoints), у примитивов
  есть `isMobile`-пропы, модалки на мобиле — шторкой (это уже умеет Modal). Конкретные
  ширины, по которым проверяем, — [target-devices.md](target-devices.md).
- **Persistence UI-состояния** (ширины сайдбаров, режимы панелей) — в localStorage
  с префиксом `cc_`.

## Контролы в шапке панели

Шапку панели рисует `PanelShell`, и слоты в ней распределены жёстко (слева
направо): иконка → заголовок → бейдж → **контролы панели** → системные кнопки
(`headerActions`, по умолчанию крестик из `onClose`). Геометрия задана
оболочкой — высота `ISLAND.headerH`, свои паддинги и высоты не выдумываем.

**Кнопки, переключатели и фильтры панель кладёт в шапку сама** — через
`PanelHeaderSlot` у себя в JSX. Владелец экрана в этом не участвует: ни пропов
с готовым `ReactNode`, ни колбэков «отдай мне свой тулбар», ни `window`-событий
на нажатие.

```tsx
function MyPanel() {
  const [view, setView] = useState<'list' | 'tree'>('list');
  const inHeader = useHasPanelHeader();
  return (
    <>
      {inHeader && (
        <PanelHeaderSlot>
          <IconButton size="sm" title="Обновить" onClick={reload}>
            <RefreshCw size={ICON_SIZE.sm} strokeWidth={ICON_STROKE} />
          </IconButton>
          <PillViewSwitcher compact value={view} options={…} onChange={setView} />
        </PanelHeaderSlot>
      )}
      …контент…
    </>
  );
}
```

Правила:

- **Один `PanelHeaderSlot` на панель.** Несколько встанут в порядке
  монтирования — порядок неочевиден.
- **Порядок контролов: сначала вспомогательные, главное действие — последним.**
  Фильтр и переключатель видов идут нейтральными иконками, действие — кнопкой
  с подписью (`Button variant="primary" size="xs"`) в конце ряда. Переключатели —
  `IconSegmented`: цвет иконок в нём не меняется, выбор показывает белая
  плашка, иначе рядом с оранжевой кнопкой возникает второй «активный» акцент.
- **Высота контролов шапки — 24** (`Button size="xs"`, `IconButton size="xs"`,
  `IconSegmented`), чтобы ряд читался одной линией.
- **Только примитивы из `ui/`** (`IconButton`, `PillViewSwitcher`, `Menu`…).
  Самодельная кнопка из `div` — дефект, как и везде.
- **Шапки может не быть** (мобильный стек, сайдбар без `PanelShell`).
  `useHasPanelHeader()` отвечает на это синхронно, в первом же рендере —
  панель с двумя раскладками (иконки в шапке / полноразмерная строка в теле)
  выбирает по нему, не моргая. Эталон — [TasksPanel](../frontend/src/features/tasks/TasksPanel.tsx).
- **Слот ищет ближайший `PanelShell` вверх по дереву.** Панель, вложенная в
  контент другой панели, попадёт в шапку внешней — это нужное поведение
  `bare`-режима, но во вложенных виджетах слот использовать не стоит.
- **`headerActions` — не для контролов панели.** Это системные кнопки
  оболочки; передашь свои — потеряешь автоматический крестик закрытия.

## Подсказки кнопок рельсы

В 40px-полосе рельсы подписей нет, поэтому имя кнопки живёт в плашке сбоку
(`RailFlyout`) — она же носит кнопки-действия, которым в самой рельсе места нет
(«убрать в ящик», «перенести панель на другую сторону», «настройки проекта»).
Нативный `title` для этого не годится: он приходит с задержкой браузера, выглядит
инородно и кнопку в себе не носит.

- **Кнопки рельсы — только `RailIconButton`.** Он собирает сэндвич «иконка +
  плашка» и решает, когда её показывать. Свою пару из `IconButton` и абсолютного
  div собирать нельзя.
- **Действия — массивом `actions`** (иконка + `title` + `onClick`). Плашка сама
  разворачивает их порядок у правой рельсы, чтобы кнопки были одинаково удалены
  от иконки.
- **На таче плашку поднимает ДОЛГОЕ НАЖАТИЕ** (~500мс, общий `useLongPress`), а не
  наведение: пальцем наведения не бывает вовсе, эмулированный `mouseenter` приходит
  без парного `mouseleave` и плашка залипала бы до следующего тапа. Короткий тап
  остаётся обычным кликом, плашку гасит тап мимо. Из этого следует правило: **любое
  действие, живущее только в плашке, на таче доступно лишь так** — если оно
  обязательное, у него должен быть второй вход (пункт контекстного меню, кнопка
  в ящике «…»).
- **Кнопки в плашке на таче — 40px** (`IconButton size="lg"`), плашка под них выше:
  тач-цель меньше 40 в чек-лист не проходит.
- **Долгое нажатие обязано быть закрыто щитом `TOUCH_CALLOUT_GUARD`** (lib/pointer)
  плюс `onContextMenu` с `preventDefault`. Иначе поверх нашей плашки встаёт МЕНЮ
  БРАУЗЕРА: Chrome на Android по удержанию считает кнопку с `<svg>` внутри картинкой
  и предлагает её скачать, iOS показывает callout с выделением. Правило общее для
  любой иконочной кнопки в тач-достижимом месте, не только для рельсы.

## Рецепт нового раздела (хаб-страницы)

Эталоны — [KnowledgePage](../../frontend/src/features/knowledge/KnowledgePage.tsx),
NotesPage, PersonasPage. Скелет desktop-ветки:

```tsx
<CanvasBackdrop>                        {/* дудл-холст страницы */}
  <HubHeader ... />                     {/* общая шапка с хаб-табами */}
  <IslandScaffold
    sidebarOpen={...} sidebarWidth={width} sidebarDragging={dragging}
    onSidebarDrag={startDrag} onSidebarCollapse={...}
    sidebar={/* контролы + список; свои паддинги несёт контент */}
    center={/* карточка/просмотр выбранного элемента */}
  />
</CanvasBackdrop>
```

Обязательные части раздела:

- **Сайдбар**: режим pinned/collapsed в localStorage (`cc_<раздел>_sidebar_mode`),
  ширина через `useSidebarDrag` (общий ключ `cc_sidebar_width`).
- **Мобила**: два вида `list | item`, переключение выбором элемента и `BackButton`.
- **Диплинки**: hash-навигация через `lib/nav` (`parseHash`/`navPush`/`navReplace`),
  обработка popstate.
- **Пустые состояния**: раздел без данных и «ничего не найдено» — через `EmptyState`,
  с полезным действием (создать/подключить), а не голым текстом.
- **Realtime**: изменения с других устройств приходят событием в группу `user_*` —
  стор на `useSyncExternalStore` в `lib/` (образцы: lib/knowledge.ts, lib/notes.ts).

## Линт-щиток

Правило про цвета не держится на честном слове — его проверяет ESLint:

```bash
cd frontend; npm run lint:design
```

Момент прогона — **перед коммитом** (пункт 0 чек-листа ниже), а не после каждой правки:
щиток судит ровно цвета, и на раскладке, логике или замене одного токена на другой ему
ловить нечего. Гонять его чаще стоит только когда правка сама про цвет — новая плашка,
новый стиль, значение цвета в коде. По ходу работы достаточно `npx tsc -b`.

Прогон обязан быть **зелёным**; он гоняет только дизайн-правила, поэтому в нём не тонут
замечания (общий `npm run lint` сейчас несёт сотни замечаний легаси-долга по react-hooks
и типам — это отдельная история). Само правило —
[frontend/eslint-rules/no-raw-color.js](../../frontend/eslint-rules/no-raw-color.js), список
файлов-исключений — `RAW_COLOR_ALLOWED` в [eslint.config.js](../../frontend/eslint.config.js).

Что делать, когда правило сработало:

1. **Обычный случай** — замени литерал на токен `C.*` (см. правило про onAccent/onDark выше).
2. **Нужного цвета нет в системе** — заведи переменную в theme.css В ОБЕ темы и ключ в `C`.
3. **Файл по природе вне системы** (тема стороннего редактора, палитра-данные, canvas) —
   добавь его в `RAW_COLOR_ALLOWED` с комментарием, почему.
4. **Разовое осознанное отклонение** — построчная директива, где **последняя** строка
   комментария содержит саму директиву (иначе она погасит комментарий, а не код):

```tsx
// Нейтральный подклад под кадрируемое фото: от темы не зависит
// eslint-disable-next-line design/no-raw-color
background: '#111',
```

## Как расширять систему

- **Новый цвет**: переменная в theme.css В ОБЕ темы (светлую и тёмную) + ключ в `C`
  с комментарием о роли. Не заводи близнеца существующего тона — сначала проверь палитру.
- **Новый повторяющийся паттерн** (встретился второй раз — уже паттерн): выноси
  в `ui/` и добавляй в реэкспорт [ui/index.ts](../../frontend/src/components/ui/index.ts).
- **Вариант примитива**: расширяй пропом существующий компонент (как `ButtonVariant`),
  а не форкай копию рядом.
- **Отклонение от гайда осознанно нужно** (особый экран, эксперимент): оставь комментарий
  у кода, почему, — иначе следующий (человек или Claude) «починит» обратно.

## Чек-лист перед коммитом UI

0. `cd frontend; npm run lint:design` — зелёный (щиток по цветам).
1. Цвета/размеры — из токенов, ни одного нового hex и magic number в `.tsx`.
2. Контролы — из `ui/` и общих компонентов, ничего самодельного.
3. Переключил тёмную тему — ничего не «выпало» (нечитаемый текст, белые пятна).
4. Сузил окно до мобильной ширины — экран живой, тач-цели не меньше 40px. Нижний
   ориентир — 360 CSS ([target-devices.md](target-devices.md)).
5. Пустые состояния и длинный контент (overflow, ellipsis) обработаны.
6. Новые строки интерфейса — по-русски, в стиле проекта (с буквой «ё»).
7. Для заметных изменений — перед коммитом **спросить**, нужен ли прогон через
   субагента `designer` (ревью соответствия этому гайду), и запускать только по
   явному согласию. Ревью полезно, но стоит времени и токенов, поэтому решение —
   за автором изменений, а не автоматическое.
