# ADR-028: подстановка персонажей на лица картинки

- **Статус:** принято 2026-10-13. Разрез — Александр (задача `bfde7fef`), план — Егор (`a288d9ad`). Решения Андрея В1–В5 записаны как принятые и здесь не пересматриваются.
- **Флаг:** `character-face-swap` (dark launch, тот же у всех трёх этапов; отдельного флага у этапа 3 нет).
- **Связано:** [ADR-017](ADR-017-image-editor.md) (персонажи, нити), [ADR-023](ADR-023-turn-context.md) (контекст хода), [ADR-026](ADR-026-character-lora-training.md) (LoRA, `VisibleTo`), [ADR-027](ADR-027-character-smart-photos.md) (подбор фото), [ADR-014](ADR-014-internal-subsystems.md) (границы).
- **Охват:** весь путь «подстановка на лицо»: этап 1 (правка по маске со склейкой вне маски), этап 2 (один персонаж на одно лицо), этап 3 (несколько персонажей одним запросом). Код этапа 2 ссылался на «ADR-027, §4, этап 2» ошибочно: §4 ADR-027 — шов `IImageLabeler`. Ссылки переводятся на этот ADR отдельным коммитом (шаг 1 плана этапа 3).

## Контекст

Этап 2 ставит одного персонажа на одно лицо. Сервер находит лица и строит маску-эллипс по bbox минус bbox соседей с запасом 30 px (`FaceMaskBuilder`). Потом правит версию локальной моделью, а вне маски возвращает исходник (`ImageCompositeMasked`, результат ровно размером холста). Контекст чата при этом игнорируется целиком. Этап 3 добавляет сценарий «Мария слева, Иван справа» одним запросом.

## Решения Андрея (вход, не пересматриваются)

- **В1. Частичный результат сохраняется.** Упал проход 2 или пришла отмена после прохода 1 — версия сохраняется с выходом прохода 1: лицо 1 `done`, лицо 2 `failed` или `cancelled`. Отмена во время прохода 1 — версии нет.
- **В2. Лимит:** `MaxFacePasses = 2` лица за запрос.
- **В3. Один персонаж на два лица запрещён.** Каждому лицу — свой персонаж. Отказ `invalid_request` на котировке, на запуске и в MCP; в интерфейсе персонаж, уже стоящий на лице, недоступен для другого. Разрез рекомендовал разрешить — рекомендация отклонена.
- **В4. Одна версия на запрос.** «Проход k из N» — только стадия прогресса, промежуточных версий нет.
- **В5. MCP `faces` в первом срезе:** аргумент `faces: [{face, character}]` у `image_generate`, один запуск в счёт `MaxLaunchesPerTurn`, несовместим с `face`/`character`.

## Решения

1. **Одна цель вместо пары «лицо + персонаж».** `FaceTarget(VersionId, FacesKey, Faces: [FaceAssignment(Face, CharacterSlug)])`. Этапы 1–2 на прод не выкатывались, поэтому контракт меняем сейчас, без слоя совместимости в HTTP и MCP. Верхнеуровневый `CharacterSlug` запроса при подстановке на лицо не используется: персонаж живёт в элементе `Faces`. Этап 2 — случай `Faces.Count == 1`. Правила запроса — одна чистая функция `FaceTargetRules.Validate`, её зовут котировка, сборщик запуска и MCP:
   - `1 ≤ Faces.Count ≤ MaxFacePasses` (= 2), иначе «Не больше 2 лиц за раз»;
   - номер лица не повторяется, иначе «Лицо 1 указано дважды»;
   - персонаж не повторяется (В3), иначе «Каждому лицу — свой персонаж: «Мария» уже стоит на лице 1».
   Все три отказа — `invalid_request`, HTTP 400.
2. **Детекция одна, по базовой версии; все маски строятся до постановки в очередь.** Проход k+1 не перезапускает детекцию на выходе прохода k: номера лиц могли бы перетасоваться, а `facesKey` — поменяться. Геометрия между проходами не меняется: выход ровно размером холста, вне маски — пиксели исходника. Любой отказ маски (`faces_too_close`, `face_out_of_frame`, мелкое лицо) приходит до траты GPU и называет номер лица.
3. **Цепочка проходов — в задаче (`ImageEditJobService.RunAsync`), а не в драйвере.** Запрос прохода собирается тем же путём, что одиночный запуск: вход прохода — `ImageEditJobInput.ForPass` (единственная точка подстановки полей прохода, ею же собран и одиночный запуск на одно лицо), запрос — `PrepareAsync` (`InputFitter` + `EditRequestComposer`); все проходы готовятся до постановки в очередь. Цепочка меняет в запросе только исходник (выход прохода k−1). У каждого прохода своя маска и свой персонаж (фото, LoRA, эталон сходства). Драйвер остаётся однопроходным. Проходы идут по возрастанию номера лица.
4. **Одна задача, одна котировка, одна карточка, одна версия (В4).** Промежуточные выходы версиями не становятся: обёртка прогресса гасит `Ready` у непоследних проходов. Стадия показывает «проход k из N».
   - **Котировка помнит N** (`ImageEditQuoteInfo.FacePasses`). Цена local — `free`, ETA = N × ETA правки.
   - **Вариантов при N > 1 — ровно 1:** котировка сама ставит `Count = 1` (без отказа — у MCP число вариантов по умолчанию берётся из выбора человека). При N = 1 — как в этапе 2.
   - **N запуска не совпал с N котировки** — отказ `quote_not_found`, HTTP 404, текст «Котировка посчитана на другое число лиц — цена пересчитается автоматически». Котировка при этом не расходуется. Новый код не заводим: клиент на него делает то же, что на устаревшую котировку, — пересчитывает её; MCP котирует и запускает в одном вызове и в этот отказ не попадает.
5. **Изоляция образцов — по построению.** Запрос каждого прохода собирается заново из `CharacterStore.ForRequest(slug)` своего персонажа, поэтому `VisibleTo` проверяется на каждом слаге. Фото, LoRA и эталоны сходства от прохода к проходу не переносятся. `CharacterPicker` у проходов не работает (`null`), подбор фото на проход — следующим этапом. Маска прохода k исключает bbox+30 px всех остальных лиц, поэтому пиксели уже подставленного лица на следующих проходах совпадают побайтно.
6. **Контекст чата игнорируется целиком, ADR-023 не меняется.** Персонажи — аргументы запроса, а не референсы контекста. Основной объект — по-прежнему нить и версия, агент его не меняет. Два персонажа в контексте не нужны.
7. **MCP (В5).** У `image_generate` статичный аргумент `faces: [{face, character}]`; вместе с `face` или `character` — отказ на вызове. Правила — тот же `FaceTargetRules`, отказ возвращается агенту текстом. Один вызов — один `TryReserveLaunch`. Через два вызова `face` сценарий не собрать: второму нужна версия, которой ещё нет. Состав `tools/list` от хода не зависит.
8. **Частичный результат (В1).** Выход прохода 1 становится вариантом 1 задачи, а значит — единственной версией запуска. Статусы:

   | Что случилось | Задача (`ImageEditJobStatus`) | Событие задачи | Запуск нити (`ImageThreadLaunchStatus`) | Версия | Лица |
   |---|---|---|---|---|---|
   | Все проходы прошли | `Completed` | `ImageEditCompletedMessage` | `done` | выход прохода N | все `done` |
   | Упал проход 2 | `Completed`, `Outcome = Ok` | `ImageEditCompletedMessage` (`Variants = [1]`) | `done` | выход прохода 1 | 1 `done`, 2 `failed` |
   | Отмена после прохода 1 | `Cancelled` | `ImageEditFailedMessage` (`Outcome = Cancelled`) | `cancelled` | выход прохода 1 | 1 `done`, 2 `cancelled` |
   | Упал проход 1 | `Failed` | `ImageEditFailedMessage` | `failed` | нет | 1 `failed`, 2 `cancelled` |
   | Отмена во время прохода 1 | `Cancelled` | `ImageEditFailedMessage` (`Outcome = Cancelled`) | `cancelled` | нет | все `cancelled` |
   | Сервер перезапущен посреди цепочки | задача потеряна (реестр в памяти) | нет | `interrupted` (`ImageThreadRecovery`) | нет — выход прохода 1 жил только в памяти как удержанный `Ready` | статусов нет |

   - **Сбой прохода** — исключение драйвера ИЛИ результат с `Outcome ≠ Ok` либо без картинок: драйверы (Local, fal, Higgsfield) сообщают сбой результатом, а не исключением, и обе формы идут одной веткой «проход упал». `Outcome = Cancelled` без отмены задачи (прервали снаружи, например на узле) — сбой, а не отмена: человек ничего не отменял.

   - **Падение прохода 2 — не ошибка задачи.** Пользователь получил версию, а `Failed` с версией дал бы карточку ошибки и предложение «Повторить через …». Частичность видна только в нити — по статусам лиц в `FaceTargets[]`; карточка показывает ✓ и ✗ у лица. Текст ошибки прохода 2 кладётся в `Error` задачи и в лог.
   - **Отмена после прохода 1 повторяет нынешнее правило «отмена оставляет готовое»:** запуск `cancelled` с версией — так уже бывает у многовариантной задачи.
   - **Грабли для исполнителя:** `FailAsync` хвост `ImageEditResult.Images` не сохраняет — версиями становятся только варианты, отданные по ходу через `Ready`. Поэтому на отмене выход прохода 1 обязан уйти погашенным ранее `Ready` до финала задачи, а не лечь в `Images` отменённого результата.
9. **Статусы лица** — `done | failed | cancelled` (строки, как у `ImageThreadLaunchStatus`):
   - `done` — проход лица прошёл, его выход вошёл в версию;
   - `failed` — проход лица начался и упал: исключение или результат с `Outcome ≠ Ok` либо без картинок; `Outcome = Cancelled` без отмены задачи — тоже `failed` (§8);
   - `cancelled` — проход лица отменён на ходу или не начинался, потому что цепочку оборвали отмена или падение раньше.
   Пока задача идёт, статусов нет: запуск нити в это время `running`, статусы лиц пишутся при финале запуска. Лицо `done` есть у версии всегда: версии без хотя бы одного `done` не бывает.
   - **Оговорка о данных (как есть, без перевода в `cancelled`).** У запуска, прерванного перезапуском, статусов лиц нет вовсе: `ImageThreadRecovery` меняет только статус запуска. А одиночное `faceTarget` этапа 2 при чтении получает статус запуска целиком (§10, `ImageThreadStore.NormalizeLaunch`), поэтому в старых нитях у лица может лежать `running` или `interrupted`. Отображения это не ломает: строки результата по лицам рисуются только при N ≥ 2 и только когда статус есть у всех лиц, а прерванный запуск подписывается своей строкой «Прервано перезапуском сервера». Значит, читатель `Status` лица обязан терпеть значения вне `done | failed | cancelled`.
10. **Форма на проводе и запись в нить.**
    - Провод (котировка и запуск): `faceTarget: { versionId, facesKey, faces: [{ face, characterSlug }] }`, `face` — номер с 1. В multipart-запуске — та же JSON-строка в поле `faceTarget`.
    - Нить: `ImageThreadLaunch.FaceTargets: ImageThreadFaceTarget[]`, элемент — `(N, BBox, CharacterSlug, Similarity?, Status)`, BBox — `[x1, y1, x2, y2]` в пикселях базовой версии. Поле аддитивное, `WhenWritingDefault`; `BackupSchema.Version` не трогаем.
    - Старые данные: одиночное `"faceTarget": {…}` этапа 2 (`ImageThreadFaceTarget(N, BBox, CharacterSlug)`) из дев-нитей читается как `FaceTargets` из одного элемента со статусом по статусу запуска (`done` у запуска `done`, иначе статус запуска) и без `Similarity`. Пишется только новое поле.
11. **Сходство** меряется на каждом проходе внутри его маски (`CcsFaceSimilarity` с `mask`, узел уже умеет) по эталонам персонажа этого прохода и пишется в элемент `FaceTargets`. Общее «сходство версии» (`ImageThreadVersion.Similarity`) при N > 1 не выводим — оно было бы средним разных людей.
12. **Кроп вокруг цели и вуаль.** Qwen-Image перерисовывает белую маску-образец буквально (белые полосы на месте правки), поэтому маску модели не показываем: подстановка на лицо показывает кроп, кисть — вуаль.
    - **Кроп** (`FaceMaskBuilder.ComputeCrop`, `LocalImageCrop`): рамка эллипса маски плюс поле `margin = max(64, round(0,15 · max(w, h)))` с каждой стороны (`CropMarginPx` = 64, `CropMarginShare` = 0,15; `w`, `h` — рамка эллипса, обрезанная холстом), всё обрезано холстом. Поле — доля рамки, а не фиксированные 64 px: на крупном лице (4000×3000) 64 px давали узкий кадр без окружения, и сходство падало; по A/B Артёма доля держит отношение кроп/лицо ≈ 1,3 на любом разрешении, сходство 0,819 против 0,723 у 64 px (карточки 71effdcf-8593-4df9-965d-2f11a1d36a1d и 2e1b97b3-cab4-47d4-b321-85eb854879ec). X и Y — вниз до кратного 8; правая и нижняя граница внутри холста — тоже, а прижатая к правому или нижнему краю холста не округляется: округление срезало бы саму маску у края. Нижняя граница 64 px перекрывает шов склейки (≈ 23 px) и запас соседа 30 px даже после потери до 7 px на округлении.
    - **Размер для модели:** кроп приводится к рабочему размеру модели ≈ 1,05 Мп (`CropTargetPixels`) в обе стороны — мелкий увеличивается, крупный уменьшается; стороны кратны 16, пропорции сохраняются. Лимит входа модели — страховка поверх, а не правило размера.
    - **Исходник с кропом по размеру не ужимается** (в ревью — Д5): маска и кроп посчитаны в пикселях исходника, а нужный размер модели даёт сам кроп. По весу он тоже не ужимается до потолка холста 90 МБ (`MaxCanvasMb` у `qwen-image-2.1` в `ImageEditCatalog` — зеркало `LocalMediaService.MaxMediaInputBytes`, потолка загрузки узла; адаптер принимает холст с кропом до него, остальные входы — по-прежнему до 30 МБ): модель видит кроп, а не холст. `InputFitter` берёт потолок `MaxCanvasMb ?? MaxInputMb`, размеры не меняет. Так же, до того же потолка и без смены размеров, обрабатывается выход прохода k перед проходом k+1.
    - **Осознанный остаток:** холст тяжелее 90 МБ (PNG с зерном ≳ 60–70 Мп) получает прежнюю лестницу JPEG, и вне кропа результат несёт её деградацию. Это известная деградация, а не дефект; понадобится — вариант «клеить на сервере» только для этого хвоста. Склейка при этом остаётся единственной, в графе.
    - **Склейка:** выход модели возвращается в рамку кропа и клеится по `KeepMask` (явный канал «вне маски — исходник», не образец) с чистым холстом, шов — `GrowMask 8` + размытие. Модель видит только кроп, промпт прохода называет персонажа и лицо «в центре первой картинки».
    - **Вуаль** (кисть у local, `MaskSupport.Veil`): место правки закрашивается серым 128 с α 0,6 на отдельной копии холста (`IImageRaster.VeilMasked`); модель получает копию, склейка «вне маски — исходник» идёт по чистому холсту, текст человека оборачивается в «Что сделать с этим местом: …». Вуаль не включается при `FaceCrop` (в ревью — Д3: модель видит кроп, текста о заливке нет) и на пути с размеченной копией (не проверена — маска уходит образцом, как раньше).
    - **Вуаль — изменение обычной кисти local у всех пользователей, вне флага `character-face-swap`.** Основание — замеры Артёма (задачи `de52fb1b`, `b8321f4e`, `8e52864d`, `d32afcf3`): из вариантов против белых полос лучший — вуаль с α 0,6.
    - Запрос прохода с кропом собирается общим путём из §3, отдельной сборки у кропа нет.

## Что не меняется

- Только local, флаг тот же.
- `MaxJobsPerOwner` считает цепочку одной задачей.
- Кэш лиц и коды ошибок этапа 2 остаются прежними; новых кодов в `ImageEditErrorCodes` этап 3 не заводит.

## Последствия

- **Плюсы:** драйверы не трогаем; облако позже встанет в ту же цепочку — с оговоркой: fal и Higgsfield `Ready` не шлют, их выход приходит только в `result.Images`. Удержание выхода прохода k (§8, В1) для них должно брать его из результата прохода, а не из погашенного `Ready`, иначе частичный результат молча потеряется.
- **Ограничения:** прозрачность не переживает подстановку — исходник (`img1`) грузится в граф как RGB, PNG с альфой выходит без неё. Так было и в этапе 2.
- **Минусы:** задача держит слот владельца в N раз дольше, а между проходами в очередь GPU встают чужие задачи — ETA здесь оценка, а не обещание.
- **За скобками:** N > 2, варианты при N > 1, облачные поставщики, подбор фото на проход, автопривязка «слева/справа» по тексту промпта.
