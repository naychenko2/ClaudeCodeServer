# LLM-wiki: «Ночной разбор» чатов

Срез Ф2 эпика LLM-wiki ([ADR-035](../adr/ADR-035-llm-wiki-single-writer.md), §12ж; макет — [llm-wiki-v2.html](../mockups/llm-wiki-v2.html), режим «Срез Ф2 02.11»). Сверено с кодом ветки `fix/wiki-night-busy` 06.11.2026 (волна WN). Судья спорных операций и чистка — [ADR-039](../adr/ADR-039-wiki-new-setup.md), решения 9 и 10; сверено с кодом `feat/wiki-judge` 12.11.2026 (шаги J0–J5, P1–P2). Несколько локальных исполнителей ночи — там же, решение 11; сверено с кодом `feat/wiki-night-executors` 13.11.2026 (шаги W1a–W8b). Укрупнение и связи (каталог и кандидаты промпта, снятие ссылок, «Связанные», подгруппы дерева) — там же, решение 12; сверено с кодом `feat/wiki-queue1` 17.11.2026 (шаги S1–S8).

## Что делает

В окне, которое владелец задал в настройках, служба `WikiNightlyService` проходит по его чатам и разбирает те, где накопилось новое (не меньше 3 реплик человека после курсора), — тем же разбором, что кнопка «Разобрать этот чат», но с местом `wiki-nightly`. Порядок: чаты с пометкой «важный», затем по свежести. Серые чаты проверяет ступень 2 (`wiki-triage`), только когда очередь дошла до чата. Чаты исполнения задач и чаты с пометкой «не разбирать» не берутся. Тумблер по умолчанию **выключен**. Ночь работает без облака: при локальном маршруте места — только локальная модель, без финального claude-шага (отказ модели — если не применено ни одного окна: чат не разобран, курсор не двигается; отказ позднего окна — частичный исход: применённые окна остаются, хроника пишется, курсор встаёт на конец последнего завершившегося без отказа окна; нет маршрута — ночь прерывается с `error`); явный облачный выбор админа для `wiki-nightly` не исполняется: `WikiIngestService.CallModelAsync` отказывает окно до вызова («ночной разбор только локальной моделью», `WikiIngestService.cs:636-647`, ADR-039 §6). Облако допускает только кнопка «Разобрать» (`wiki-ingest`). Занятость локального движка ходом исполнителя ночь не останавливает: облачного шага нет, пропуск был бы потерей вызова, — запрос идёт в занятый движок; не пустивший слот (`TryEnter` без ожидания) и есть отказ окна (исключение режима — [llm-providers](../architecture/llm-providers.md)).

## Новая постановка (ADR-039, волна С2)

Синтез — один локальный вызов на окно, сверено с кодом 11.11.2026:

- **claim и quotes.** Операция несёт утверждение `claim` (≈600 символов) и 1–3 цитаты (`quotes`); дословность проверяет код по цитатам, `Text` заполняется текстом `claim`. Синтез создаёт только `create`, `append`, `conflict`, `link` (`WikiPlanValidator.cs:514`); `rewrite`, `rename`, `merge` — волны С4/С7.
- **Причины спора.** Операция, которую решает не код, попадает в пакет с текстом причины и машинным `ReasonCode`, например «число не подтверждено цитатой: …» → `number_unconfirmed` (`WikiPlanValidator.cs:414`): каждое число `claim` обязано стоять в цитате. Кто решает спор по коду — судья или человек, см. ниже.
- **Поштучный приём.** Негодная операция отказывается сама (`Rejected`, с индексом и причиной), годные остальные идут в пакет — план целиком не отвергается.
- **Зоны чата.** `awaiting_human` — в пакете есть операции «на решении», применённых нет; `rejected_skipped` — окно пропущено курсором после отказов (`WikiChatIngestService.cs:116-125`).
- **Пропуск окна.** После трёх отказов подряд при ответившей модели (`RejectSkipAfter = 3`) курсор переходит через окно, зона `rejected_skipped` с причиной последнего отказа; отказ до модели (облако ночью, движок занят) серию не наращивает. Вручную чат разбирается пунктом меню.
- **Хроника.** Без модели: код дописывает «Что выяснили» утверждениями и цитатами из применённых операций (`WikiChatIngestService.cs:600`); проекция журнала — волна. С 17.11 каждая `[[…]]`-ссылка claim попадает в хронику только разрешённой для раздела дома хроники и его цепочки вверх — неразрешимая снимается до видимого текста (`AppendChronicleAsync`, `WikiChatIngestService.cs:860-865`).

## Укрупнение и связи (ADR-039, решение 12)

Ночной разбор и кнопка «Разобрать» после очереди 1 (сверено с кодом `feat/wiki-queue1` 17.11.2026, шаги S1–S8). Ничего не меняет схему ответа модели и не добавляет операций: каталог, кандидаты, «Связанные» и статус пакета считает код.

- **Структура промпта.** Статичные правила → каталог раздела назначения и цепочки вверх → полные тексты страниц-кандидатов → окно источника (`WikiKeeperPrompts.cs:197-203`). Правила статичны и идут первыми — префикс кэшируется; append переносит страницу в конец её блока каталога (файл переписывается Хранителем — время рождения обновляется), префикс сохраняется только между окнами без применений.
- **Каталог раздела.** Строится из того же снимка страниц раздела под шлюзом, что и кандидатов, — второй точки правды о состоянии раздела в окне нет (`WikiIngestService.cs:365-377`). Строка `- [[Заголовок]] — вид — сводка`; сводка — проекция: `summary` из шапки, иначе первые ~150 символов раздела «Сводки» страницы (сноски сняты, `[[x|y]]` → видимый текст, одна строка, обрезка по слову; `WikiProjections.cs:207-232`); модель поля не пишет. **Потолок** — 14 000 символов (`PromptCatalogMaxChars`, `WikiIngestService.cs:111`): сначала голый скелет строк («Заголовок — вид») — новые страницы гарантированы, при упоре первыми выпадают старые; освободившийся бюджет идёт на сводки по порядку строк, хвост остаётся голым (`BuildSectionIndex`, `:689-776`). **Порядок** — по времени последней записи файла, при равенстве по пути (`:715-720`): Хранитель пишет страницу через temp + `File.Move`, append даёт файлу новое время рождения — страница уходит в конец блока; кэш выигрывает только между окнами без применений. Поля `created` в шапке нет; брать ли время из шапки/журнала вместо свежести диска — открытый вопрос (ADR-039, р.12). Известное ограничение: после восстановления из бэкапа время рождения всех файлов — время восстановления, порядок вырождается в сортировку по пути и префиксный кэш ломается. Символы каталога — часть входа: ночь прибавляет их /4 к оценке расхода (`WikiNightlyService.Pass.cs:250`). `_index.md` человека — полный и по пути, без потолка.
- **Кандидаты.** `WikiCandidates` — чистая функция над тем же снимком: значимые слова (подряд букв от 4, нормализация, стоп-список, основа — первые 6 символов, для слова от 5 букв без последней), оценка — пересечение с заголовком (×2), сводкой и алиасами, дословное совпадение заголовка/алиаса — первой очереди; оценка 0 и карточки `source` — не кандидаты. Top-5 (`TopN`, внешний потолок `MaxCandidatePages` = 5). Кандидатов и каталог собирает код: облака в синтезе нет (решение 6).
- **Append-first.** Правило 6 промпта: сначала append к странице того же предмета из каталога; `create` — только предмету, у которого страницы ещё нет; прежняя квота «Usually 4–10 pages per window» убрана; заголовок create — существительное-предмет, не предложение (`WikiKeeperPrompts.cs:142-145,152-154`).
- **Ссылки в claim.** Промпт разрешает `[[Заголовок]]` дословно по каталогу — без «— вид», без префикса раздела, без алиаса `|`. Неразрешимую ссылку **снимает до текста валидатор**, до проверки чисел и до записи `Text`: она заменяется видимым текстом (алиасом, иначе заголовком без префикса) и становится обычным текстом утверждения (`WikiPlanValidator.cs:304-306`, `WikiGate.StripUnresolvedLinks`). Цель резолвится целиком, вместе с алиасом: `[[x|y]]` снимается всегда, даже если страница `x` существует (промпт алиас в claim запрещает). Резолвер у валидатора, хроники и гейта один — `WikiGate.ResolveLink`, те же правила видимости, что у всего гейта; у «Связанных» — своя копия тех же правил (`WikiRelated.cs:252-270`), ошибка там даёт лишний/недостающий пункт проекции, не запись на диск; **гейт остаётся строгим** (цель операции `link` и правки человека — как раньше). Числа: текст уцелевших ссылок в проверку не входит, текст снятой — считается (`WikiClaimNumbers`, поправка ADR-039 р.2).
- **Счётчик снятых ссылок.** Число снятых ссылок операции — поле `Operation.StrippedLinks` в JSON принятого пакета (`WikiPackage.cs:255`); сумма по окну — `IngestResult.StrippedLinks` (`WikiIngestService.cs:149-151`). **В итог ночи пока не выводится**: у `NightResult` такого поля нет, строка итога и уведомление его не печатают. Мера точности модели для проверки ниже.
- **Статус пакета со смешанными вердиктами (D0).** Пока есть нерешённая спорная — `proposed`; все спорные приняты — `accepted`; ни одна не принята и авто-операций нет — `rejected`; иначе — `partially_accepted`: отказ по спорным не выбрасывает авто-операции из применения (`StatusAfterDecisions`, `WikiPackageStore.cs:399-411`). Одно правило для решения человека и вердикта судьи; 51 ранее отклонённый пакет задним числом не пересчитывается — рекомендация разреза (вариант а), решение за Андреем (ADR-039, решение 12).
- **Блок «Связанные».** Новое поле `related` существующего GET `/api/wiki/page` (`WikiController.cs:263-278`): чистая проекция при показе (`WikiRelated`), в файл страницы ничего не пишется. Область — раздел и цепочка вверх (то же множество, что `allowed` у гейта); группы по приоритету: общий источник в сносках → хроника того же чата → упоминают эту страницу → упомянуты здесь → обратные ссылки; потолок 8 на группу, дубль остаётся только в старшей группе, карточки `source` и проекции `_*` исключены из групп упоминаний. Чтение соседей фоновое и в учёт чтений не входит (поправка ADR-039 р.7, строка сторожа `WikiController.Page.related`). Фронт рисует блок под текстом страницы (`WikiPageView.tsx`), пустые группы не рисуются. Переход по ссылке `[[…]]` из текста страницы — не в очереди 1 (очередь 2 или отдельный шаг): в тексте она рисуется простым текстом, и пока ссылки видны в тексте, переходы — через блок «Связанные».
- **Подгруппы дерева по видам.** Внутри узла раздела страницы раскладываются по 7 подгруппам в фиксированном порядке: решения → правила → термины → состояния → хроники → «Прочее» (старые виды и без типа) → «Мои заметки» (`WikiUnifiedTree.tsx:56-64`). Счётчик подгруппы — число строк после фильтра и поиска, пустые подгруппы не показываются; свёртка переживает перечитку: ключ localStorage `cc_wiki_tree_folds`, запись «ключ раздела#вид» (`:48,67`).

## Проверка постановки на одном разделе

Кнопка «Разобрать» на подготовленном разделе; ночь не останавливается, свои пакеты отличаются по месту (`wiki-ingest`) и созданы не раньше T0. Предусловия: D0 уже на бою (иначе отказ судьи снова выбросит авто-операции и исказит долю append); маршрут `wiki-ingest` на время теста — тот же локальный движок, что у ночи; раздел средний (20–40 страниц знаний), без страниц авторства человека.

Замер — скрипт на чтение по `keeper/packages/*.json` и `pages/` раздела: `.cc-attachments/wiki-test-queue1/measure.py` (описание запуска и метрик — `README.md` там же). **Файлы `.cc-attachments/` вне git** (`.gitignore`): скрипт нигде не коммитится, живёт в рабочем дереве. Критерии:

| Критерий | Порог |
|---|---|
| новых страниц знаний на окно | ≤ 3 |
| доля append `append/(create+append)` | ≥ 30 % |
| средняя степень связей «тема ↔ тема» в страницах раздела | > 0 |

Рядом, чтобы не обмануться: доля `page_duplicate` (ориентир 10 % от create), вызовы судьи и их цена, отказы окна по лимиту новых страниц, снятые ссылки относительно поставленных, и выборочно глазами ~10 append — в страницу ли того же предмета. Решение за Андреем: проходит → «Начать вики заново» и ночь на новом синтезе; не проходит → правка правила 6 и потолка каталога, повтор на том же разделе.

## Судья спорных операций (ADR-039, решение 9)

Спорные операции ИИ-пакетов решает не только человек: отдельный идемпотентный проход `WikiJudgeSweep` — облачная модель по новому месту `wiki-judge`, выбранному админом в «Поставщиках моделей». Точки запуска: ночь (тик или кнопка «Запустить сейчас») — ровно один полный проход в конце ночного прохода, его числа идут в итог ночи (`WikiNightlyService.cs:812-833`); ночная заявка посреди ночи судью не зовёт (guard по `actionKey`, `WikiIngestService.cs:272-273`); дневная заявка («Разобрать», `wiki_ingest`, `wiki_add_fact`) — сразу после заявки, кончившейся `awaiting_human` (`:262-285`). Вердикт один: apply / reject с причиной; «переписать» судья не выносит, почти верную операцию он отклоняет — следующая ночь переформулирует её сама. Ночной синтез при этом остаётся локальным: облако в ночи — только этот проход.

- **Кого судья касается.** Только нерешённые `inbox`-операции пакетов автора `ai`, и только по машинному коду причины: `number_unconfirmed`, `page_duplicate`, `section_new_pages_limit`, `after_model_repair`, `no_history_section`, `class_disabled`, `target_disputed`, `overrides_human`, `revert_quarantine`, `personal_to_common` (`WikiApplyPolicy.JudgeAdmitted`, `WikiApplyPolicy.cs:62`). `origin_url`, `unknown_op`, `no_class`, `bad_class`, `no_page` отклоняются кодом без вызова модели; пакет без кода (старый) не допущен; отброшенное валидатором судье не даётся вовсе. «Только для человека» — перенос «Личное → Общее», замена утверждения человека, правка поперёк карантина отката, выключенный класс — теперь тоже решает судья (решение Андрея 12.11, №1).
- **Ручной режим — тем же тумблером.** «Применять без ревью» (`AutoApplyEnabled`, по умолчанию включён) выключен → прохода нет вовсе, ни одного вызова, «Входящие» решает человек прежними кнопками. Нового тумблера нет.
- **«Входящие» как ручная очередь уходят.** При включённом тумблере очередь становится «очередью судьи» (лимит открытых 20 — он же), а её показ — видом «Решения судьи»: только чтение (операция, вердикт, почему, ссылка на страницу). Решать заново то, что уже решил судья, человек не может (`CodeAlreadyDecided`); его действие — откат пакета — только в «Журнале» → «Решения за ночь» и только у применённых пакетов.
- **3 попытки.** Битый или отсутствующий вердикт и отказ вызова — попытка по операции; на третьей отказ выносит код («судья не вынес решения за 3 попытки»): пакет не висит в очереди бесконечно. Отмена прохода попыток не карает. Этот отказ по попыткам — тот же счётчик, что и отказы по коду причины: та же метка `JudgeModelCode` и тот же «отклонено кодом» (`CodeRejected`) в карточке итога, в строке журнала и в теле уведомления (`WikiJudgeSweep.cs:350, 371-375`); «отклонил» судьи считает только вердикты модели.
- **Потолка вызовов за ночь нет** (решение Андрея 12.11, №3): их держит только лимит открытых пакетов — при упоре ночь заканчивается исходом `open_limit`, а не завалом непроверенного. Цена каждого вызова (`OneShotUsage.CostUsd`, делится на операции одного вызова) идёт в итог ночи.
- **«Личное» судье отдаётся без отдельного согласия** владельца (там же, №4).
- **Фронт.** При включённом тумблере «Входящие» показываются видом «Решения судьи» (только чтение: операция, вердикт, почему, ссылка на страницу); при выключенном — прежние «Входящие». Вид «Решения за ночь» — в «Журнале» (утренняя сводка); откат пакета — только там и только у применённых пакетов. Их данные на бэке: решения в файле пакета, `actor = "judge"` в `log.jsonl`.

## Несколько исполнителей (ADR-039, решение 11)

Ночь может делаться не одной локальной моделью: админ назначает место `wiki-nightly` нескольким локальным движкам, и тело прохода становится координатором, который раздаёт чаты по их слотам. Главное, что это даёт, — **запасной исполнитель**: гаснет один, разбор доходит до конца на другом; прирост скорости вторичен (оценка ×1,3–1,8, не ×2 — сродство с разделом и шлюз раздела, решение 11). Пустой список исполнителей — прежняя ночь по маршруту места, без изменений.

- **Настройка — в «Поставщиках моделей» (админ), не в настройках вики.** В строке места «Ночной разбор вики» под выбором маршрута — блок «Исполнители ночи» (`NightExecutorsEditor.tsx`, встроен в `ApplyTab.tsx`): выбор локальных движков, их параллельность и общий потолок слотов места (1–4). Запись — `PUT /api/admin/local-actions/{key}/executors` (весь контроллер под `[Authorize(Roles = "admin")]`, `LocalActionsAdminController.cs:17,124`); валидирует сам стор: годятся только `local` и имена `LocalEngines:*`, `tier:` / `preset:` / `direct:` / id модели — 400 с названной причиной, `parallel` — до потолка своего движка (`LocalActionExecutorsStore.cs:139–156`). Порядок списка — приоритет: свободный слот первого получает чат раньше. Файл `data/local-action-executors.json` входит в бэкап `data` как остальное `data/`; миграции прежних настроек нет, массовые пресеты («Применить пресет») список не трогают. Пустой список = снять ключ: `wiki-nightly` идёт по своему маршруту, как до фичи (`Pass.cs:331–350`).
- **Что видит владелец.** В «Вики» → «Настройки» → блок ночи — только чтение: «Исполнители: … (назначает администратор)» и разбивка последней ночи по движкам (`WikiNightlyBlock.tsx:574`). Своих рычагов по числу исполнителей у него нет: лимиты ночи и раздела, бюджет и окно — прежние, в `keeper/settings.json`, их держит координатор.
- **Координатор и сродство с разделом.** Слотов — сумма параллельности исполнителей, урезанная швом до `maxTotal` места раунд-робином (`CheapTextRunner.cs:635–648`). Свободный слот получает первый чат очереди, чей раздел сейчас не в работе: сродство — двух чатов одного раздела одновременно нет, порядок внутри раздела прежний, очередь под занятым разделом не переставляется (`WikiNightlyService.Pass.cs:486–489`, `:560–562`). Счётчики и бюджет меняет только координатор, слот лишь зовёт разбор на своём движке (`:437–438`). `CheckStop` и лимиты проверяются перед каждой выдачей; при упоре выдача останавливается, чаты в полёте доигрываются. **Список исполнителей читается один раз на проход** — он же порядок разбивки и тот же, что видит драйвер; `CheckStop` перечитывает стора перед каждой выдачей (свежий PUT виден следующему чату), но это решение «идти дальше или нет», к итогу оно не относится (`:318–326`).
- **Проба готовности — на каждый обход выдачи, до взятия чата.** Именованный движок: GET на `ReadyUrl` (2xx = готов), результат кэшируется на 1 с; движок без `ReadyUrl` считается готовым — решит сам вызов (`NamedLocalEngines.cs:86–101`). Основная локаль: «не настроена» или «занята ходом исполнителя» (`LocalBlockedByTurn`) — без HTTP (`CheapTextRunner.cs:684–690`). **«Готов» ≠ «вызов пойдёт»**: проба решает лишь, давать ли чату этот движок, занятость решает сам вызов. Неготовый исполнитель пропускается — чата не сжигает и сам не выбывает, вернётся, когда станет готов; сбой самой пробы читается как «не готов» и координатор не роняет (`Pass.cs:494–515`).
- **Выбывание: 3 отказа подряд «модель недоступна» у этого исполнителя.** Нулевой вход + причина «локальная модель недоступна» (`IsLocalDownRejection`, `:633–634`); ряд свой у каждого движка, `LocalDownBreakAfter = 3` (`:26`, `:54–62`) — исполнитель выбыл до конца прохода, его слоты чатов больше не получают, время запомнено. **Ряд обнуляется любым исходом того же исполнителя, кроме этого отказа** — состоявшимся разбором, отказом плана (модель отвечала) или отказом занятого слота; отказ чужого исполнителя его не трогает вовсе (`:64–68`). Путь без названных исполнителей ведёт тот же выключатель под ключом `RouteKey = ""` — его выбывание даёт прежний итог `error` (`:33`, `:44`).
- **«Слот движка занят» — отказ, не выбывание.** Формулировка «занят: слота не дождались» с нулевым входом (`IsSlotRefusalRejection`, `:636–644`): движок занят, а не мёртв, — в ряд он не входит и исполнитель не выбывает. Но чат с таким отказом не ждёт следующей ночи: координатор отдаёт его **один раз** другому исполнителю (тот же лимит повтора).
- **Повтор чата ≤ 1, только при нулевом входе.** Чат, отказанный «моделью недоступна» или «занятым слотом» и без единого применённого окна, возвращается в голову очереди ровно один раз за проход; отказавший его исполнитель его не получает — иначе мёртвый движок взял бы его снова (`:582–589`, `:512`). Курсор чата не двигался, повтор не резервирует бюджет второй раз и не считается новым выбранным чатом. **Ступень 2 при повторе не зовётся**: первая выдача её уже спросила, второй вызов был бы вторым решением по одному чату и удвоил бы оценку и вход ступени 2 (`:175`). Частичный исход и отказ плана не повторяются. Чат, которому сейчас некому (его движок занят или он ему уже отказан), очередь не держит — уходит в её конец (`:527–534`).
- **Пост-проверка: все выбыли → итог `error`.** `CheckStop` перед выдачей требует живого исполнителя (`:679–684`); «ни живого, ни готового, в полёте никого» — тот же итог (`:516–526`); если третий отказ пришёлся последним чатом очереди, предохранитель после обоих драйверов называет `error` и там (`:356–364`). `error` дату не закрывает — следующий тик пробует снова; раньше названный упор (`budget`, `open_limit`, `window_closed`, `disabled_midway`) держит свой итог. Наличие маршрута места проверяется только пути без названных исполнителей: при списке, а не при нём (`:670–675`).
- **Единственная локаль занята живым ходом — ночь останавливается сразу.** Проба готовности основной локали — «локальная модель настроена и не занята ходом исполнителя» (`LocalBlockedByTurn`); если такая локаль — единственный исполнитель списка, то на первом же обходе выдачи очереди некому дать ни одного чата и в полёте никого: проход называет `error`, ни один чат не разобран, исполнитель не выбыл (его ряд не тронут). `error` дату не закрывает — следующий тик окна пробует снова, когда ход освободит локаль; запасного исполнителя при одном в списке нет.
- **Разбивка: `analyzed` по движку — ПОПЫТКИ.** Поле `NightResult.Executors` (`{engine, analyzed, rejected, inputTokens, withdrawnAt}`, `WikiNightlyService.cs:176,184–185`): порядок — как список стора, движок, которому ни одного чата не досталось, — с нулями, вход ступени 2 к движку не относится (`Pass.cs:414–428`). Отказанный одним чат может быть добран другим, поэтому строка журнала называет число честно — «чатов N, попыток M» (`WikiNightlyService.cs:370–379`); **итог по чатам (`Selected`) от повтора не удваивается**, путь без названных исполнителей остаётся прежней парой «чатов N/M». Хвост строки — «исполнители local 3/3 выбыл 04:00; gemma 4/0» (`:410–415`, `:455–466`), в уведомлении — по одному предложению о каждом выбывшем («Модель … сделала N попыток, выбыла в HH:mm, разбор продолжила …») (`:770–800`). Всё это — в той же единственной строке итога, в файле `nightly-last.json` и в DTO `lastNight`: текста знаний и причин по исполнителю там нет (прежнее правило J-O1/J-J4).
- **Исполнитель — только локальный движок, без страховки.** Вызов идёт `RunOnLocalEngineDetailedAsync`: ни шага «выбранная модель», ни `FallbackRoute` этого движка, ни финального claude-шага — до облака путь не доходит никогда; неизвестный, выключенный, не готовый или не ответивший движок — отказ окна без подмены (`CheapTextRunner.cs:692–704`). Пустой или пробельный `engine` маршруту места не отдаётся: отвергается до всякого вызова с той же причиной (`WikiIngestService.cs:723–742`).
- **Ограничение.** Возврат выбывшего исполнителя в пределах прохода не делается: состояние отказов живёт до конца прохода и снятия выбывания не имеет (`Pass.cs:42–79`) — его вернёт следующий тик окна, если дата не закрыта. Внутри прохода возвращается только чат, а не исполнитель.

## Где настраивается

«Вики» → «Настройки» → «Ночной разбор»: тумблер «Разбирать по ночам», окно (часы сервера, по умолчанию 03–06), бюджет входа (700 000 токенов), пакетов за ночь (20) и на раздел (6). Пометки «Важный» / «Не разбирать» — в меню чата; список отбора — «Отбор чатов». Исполнителей ночи (сколько локальных движков и с какой параллельностью) здесь нет — их назначает админ в «Поставщиках моделей», см. «Несколько исполнителей».

## Ручной запуск

Кнопка «Запустить сейчас» — рядом с заголовком «Прошлая ночь» (WN-5, WN-6b); при выключенном тумблере неактивна с подписью «Ночной разбор выключен». Диалог подтверждения с лимитом пакетов за проход, затем `POST /api/wiki/settings/nightly/run` → 202 `{started:true}`; работа идёт в фоне службы, состояние кнопки («Идёт разбор…») — по `nightlyRunning` в GET. Это тот же проход, что у тика, и под тем же замком владельца: с тиком или другим ручным запуском параллельно он не идёт. Окно при ручном не проверяется, отметка «за дату уже пройдено» не мешает; сам проход дату не закрывает — ночной тик той же даты проходит ночь заново (в итоге поле `manual`). Отказы — 409 со своим кодом до любого состояния прохода: функция выключена (`wiki_llm_wiki_off`), ночь выключена (`wiki_nightly_disabled`), этот владелец уже проходит (`wiki_nightly_running`), настройки нечитаемы (`wiki_settings_invalid`); сервисному токену — 403, службы нет в этом составе — 503. Настроек действие не меняет.

## Итог ночи

Карточка в том же блоке по файлу `keeper/nightly-last.json`: выбрано, разобрано, применено пакетов, решения судьи (принято / отклонено / ждут / отклонено кодом), число его вызовов и их стоимость, оценка токенов, исход (`completed`, `budget`, `open_limit`, `window_closed`, `disabled_midway`, `error`). При названных исполнителях — и разбивка по ним (попытка/отказ на движок, время выбывания): см. «Несколько исполнителей».

Отказанные разборы (WN-2) считаются и называются: `rejected` — их число среди analyzed, `firstRejectReason` — причина первого из них; на каждый отказ — строка в журнал сервера, в карточке — «отказано N» пятой метрикой (только при N > 0). Когда отказаны все разобранные чаты и ни один токен не дошёл до модели, исход — `error`, а не `completed`: `error` дату не закрывает, следующий тик окна пробует снова (тот же `error` той же даты владельцу второй раз не сообщается).

Фактический вход `InputTokens` (сумма входа разобранных чатов и ступени 2) пишется в тот же файл — это мера нагрузки на GPU локали, а не деньги; бюджет ночь решает по оценке `EstTokens`, заранее, до вызова. Карточка и API фактического не показывают.

После записи итога приходит одно уведомление прохода (для ночного тика — утром), с 12.11 — новой формы: заголовок «Ночной разбор: применено N; судья принял K, отклонил L; ждут M; $X» (`WikiNightlyService.cs:837-838`). В теле — по одной сводной строке на каждую непустую меру: «Во «Входящих» N пакет ждёт решения» (`:752-753`), «судья недоступен — ждут решения: N» (`:756-757`) и «отклонено кодом: N» (`:761-762`) — и, при названных исполнителях, по одному предложению о каждом выбывшем (`:765`, `:770-800`, см. «Несколько исполнителей»), затем путь «Вики» → «Журнал»; нулевая строка не пишется. Молчание — только при обычном исходе без работы: `Analyzed = 0`, исход `completed`, `JudgeCalls = 0`, `JudgeDeferred = 0` и `CodeRejected = 0` (`:811-825`, правка QA, замечание b0065470): если судья звал модель, что-то отложил или код что-то отказал, уведомление приходит даже при нуле разобранных чатов — владелец обязан увидеть вердикты и их цену, либо что пакет остался без вердикта или закрылся отказом самого кода. Детали — вид «Решения за ночь» в «Журнале»: их собирает код из пакетов и `log.jsonl`, модель не участвует. Откат — из «Журнала» (по пакету или по источнику).

Той же ночью итог уходит одной структурной строкой в журнал процесса (`LogInformation` после записи файла; при `error`, `open_limit` или отложенных судьёй операциях — повторно `Warning`, чтобы алерт цеплялся по уровню): основа строки — «Ночь вики {OwnerId} {Date}: {Outcome}; чатов {Selected}/{Analyzed}, отказов {Rejected}» (`WikiNightlyService.cs:376-379`; при названных исполнителях вторая часть называется честно о попытках — «чатов {Selected}, попыток {Analyzed}», см. «Несколько исполнителей»), дальше две условные части и хвост о судье: « (первый: {RejectFirst})» — только при `Rejected > 0` (`:381-385`), «; ступень 2 отказана {Stage2Refused} (первая: {Stage2First})» — только при `Stage2Refused > 0` (`:388-393`), и всегда — «; пакетов {Applied}, на судье {JudgeApplied}/{JudgeRejected}/{JudgeDeferred}, отклонено кодом {CodeRejected}; вход {InputTokens} ток; судья {JudgeCalls} выз. ${JudgeCost}; ручной {Manual}» (`:396-397`), и при названных исполнителях — хвост «; исполнители …» (`:410-415`). Нулевой «первый» в строке не печатается: «отказов 0 (первый: )» читалось бы недописанным полем. Текста знаний в строке нет — ни утверждений, ни цитат, ни названий страниц: журнал процесса уезжает в SigNoz.

## Сбой применения решения человека возвращает окно в разбор

Пакет, который человек решил во «Входящих», но который не применился («apply_failed» или «stale»), не теряет своё окно: точка окончания решения (`WikiPackagesController.AfterDecision`) возвращает курсор разбора каждого чата-источника пакета («session:{id}#m{a}-{b}») на «a−1» («WikiChatIngestService.ReturnWindowAsync»): дельта «a…N» разбирается заново, её попыткой станет новый пакет. Возврат идёт в фоне, после формы ответа решения (T-A3): при идущем разборе этого чата откат ждёт его конца, но ответ человека из-за этого не висит — форма и контракт ответа от возврата не зависят. Возвращается только решённый пакет: авто-путь без решения человека курсора не трогает; проигравший гонку вызов (409 или код «wiki_apply_claim»/«wiki_apply_status») окна не возвращает; несессионные источники не трогаются (ключ — origin, а не форма ссылки). Ограничение: ночь берёт чат только при дельте не меньше «MinHumanDelta = 3» реплик человека после курсора («WikiNightlyService.cs:103») — возвращённое окно меньше этого ночь не возьёт вовсе, его переразбирает только кнопка «Разобрать».

## Чистка и перезапуск разбора (ADR-039, решение 10)

Одноразовая операция человека: убрать то, что написала ИИ, и начать разбор с нуля. Запускает её кнопка «Начать вики заново» в «Вики» → «Настройки»: сначала предпросмотр (`dryRun` — числа по разделам и классам, список путей; ни списка, ни архива, ни изменённой страницы на диск не пишется), затем подтверждение. Одно исключение: сам вход в раздел под его замком дёргает ленивый бэкфилл основ, и при первом входе в раздел он ставит служебный маркер `keeper/baselines-backfilled/*` и дописывает основы существующих страниц (`WikiKeeper.cs:596-599`, `WikiBaselines.cs:71-97`) — к составу чистки это отношения не имеет. Ручка `POST /api/wiki/purge?dryRun=true|false`, `[Authorize]`, сервисному токену отказ, только свой корень (`WikiController.cs:656`); MCP-инструмента нет — это разрушающая системная операция, как откат.

- **Что удаляется** — по авторству сноскам (`WikiProjections.PageAuthorship`), а не по дате и не по виду страницы: страницы `ai`, не приёмыши, `chronicle`, карточки `source`, на которые не ссылается ни одна оставшаяся страница, и **смешанные `together`** (решение Андрея 12.11, №2). Человеческая строка журнала (`actor=user`) страницу авторства `ai` не защищает: предикат — авторство и приём как есть, такая страница чистка удаляет и она уходит в zip (там же, №2: содержимое сохранено в архиве, разбор соберёт страницу заново; `WikiKeeper.cs:268-283`). Человеческое, приёмыши и проекции `_*` не трогаются; принятые как есть (`op=adopt` в журнале) — не удаляются ни при каком делении по типам, включая карточки-сироты: «приём как есть» сильнее сиротства (`WikiKeeper.cs:272-275, 306-310`).
- **Всё уходит в zip:** перед удалением — архив `pages/` + `keeper/` в `keeper/archive/purge-{ts}.zip` (не индексируется, но входит в бэкап `data`). Архив не создан — операции нет.
- **Заодно с чисткой:** открытые ИИ-пакеты переходят в `stale` с причиной «чистка вики {дата операции}» — дату подставляет код запуска чистки (`yyyy-MM-dd`, `WikiKeeper.cs:412`), курсоры разбора обнуляются (пометки человека и ступень 1 сохраняются), включается флаг бэклога на 15 дней (`WikiKeeper.PurgeBacklogDays` = 14 — последний день = день чистки +14, включительно, `today ≤ until`; `WikiBacklogFlag`) — на этот срок лимит новых страниц на раздел поднимается до 15. Документы исчезнувших страниц убирает из Dify существующий синк, отдельного каскада нет.
- **Порядок выката:** кнопку нажимают после выката судьи (J0–J4). Иначе первая ночь бэклога снова набьёт 20 открытых пакетов без судьи и встанет на `open_limit`.
- **Фронт.** Блок «Начать вики заново» — в «Вики» → «Настройки»: предпросмотр и диалог подтверждения.
