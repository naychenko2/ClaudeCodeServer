# План переделки доступа MCP-серверов на allow-list

> Статус: план работ (август 2026), решение владельца зафиксировано — модель доступа
> разворачивается с deny-list на allow-list. Здесь — что менять, в каком порядке, чем
> рискуем, как мигрировать. Автор — Александр (тимлид). Исполнители: Денис (бэкенд),
> Кира (фронт, совместно с задачей 41fb305d по UI новой модели).
> Базовая дока — [mcp-registry.md](../architecture/mcp-registry.md).

## Правило доставки (зафиксировано, не переоткрывать)

Сервер попадает в ход, если он включён **в проекте** этого чата ИЛИ выдан **персоне**
этого чата. Оси включения: проект целиком (все чаты проекта), отдельная ось «чаты вне
проектов», персона целиком (все её чаты). Разреза «персона × проект» нет.

```
  запись реестра выключена (record.Enabled == false)?
      да -> мимо                              (ось 0, как сейчас)
      нет
       |
  включён "здесь"?
    чат в проекте:   key в Project.McpServersOn
    чат вне проекта: record.AllowOutsideProjects
       |
      нет --- ИЛИ --- выдан персоне чата?
       |              McpServerGranted(persona, "mcp:"+key)
       |              (нет персоны -> нет)
      оба "нет" -> мимо
       |
  персона ReadOnly и !record.AllowReadOnlyPersonas?
      да -> мимо                              (AND-гейт, как сейчас)
       |
      в ход
```

Все входы условия — свойства владельца/проекта/персоны, ни один не смотрит на ход:
инвариант «состав tools/list не зависит от хода» держится по конструкции.

## 1. Хранение

**Рекомендация.** Три носителя, без нового стора:

| Ось | Было | Станет |
|---|---|---|
| Проект | `Project.McpServersOff` (deny) | `Project.McpServersOn` (allow; null/пусто = ничего не включено) |
| Чаты вне проектов | — (доставлялось всегда) | `McpServerRecord.AllowOutsideProjects` (bool, дефолт `false`) |
| Персона | Off-привязка `mcp:<ключ>` = отнять | Привязка `mcp:<ключ>` с `Mode != Off` = **выдать**; отсутствие или Off = не выдано |

Механизм привязок целиком **не** разворачивать: инверсия — только для `mcp:`-ключей,
отдельным методом (см. п. 2). `ServerToolEnabled` и его deny-семантика для встроенных
серверов (`ServerKeys`: personas/consultants/codegraph/notifications/widgets) не меняются.

**Обоснование.**
- Общий стор выдач (`data/mcp-grants.json`) отвергнут: третья точка истины, новый файл в
  каскаде бэкапа, новый сервис — при том что выдача проекта естественно живёт в проекте
  (рядом с PermissionRules и прочими настройками), выдача персоны — в её привязках, а ось
  «вне проектов» — свойство самой записи сервера (реестр и так per-owner). Наименьшее
  изменение достигает цели.
- Off-привязка после разворота становится эквивалентом отсутствия привязки. Ломать её
  валидацию не нужно: существующие Off-записи безвредны, `PurgeMcpBindings` работает как
  прежде (удаление/переименование сервера подметает привязки любого режима).
- Разворот всего механизма привязок дал бы «Off = выдать» для tasks/notes/web — бессмыслица;
  а отдельный новый тип привязки (не Tool) — лишняя сущность: `Mode != Off` уже выражает
  «включено», и привязка при этом бесплатно попадает в блок «Привязанные знания и правила»
  промпта (строка «применяй инструменты …» — для allow-модели это желаемое поведение).

**Каскад правок хранения (Денис).**
- [Project.cs:82](../../backend/ClaudeHomeServer/Models/Project.cs) — поле `McpServersOn`
  (на этапе флага `McpServersOff` остаётся рядом, удаляется при снятии флага — см. п. 5).
- [ProjectManager.cs:169-175](../../backend/ClaudeHomeServer/Services/ProjectManager.cs) —
  параметр `mcpServersOn` с той же нормализацией (trim, нижний регистр, distinct;
  null = не менять, пустой список = «не включён никто»).
- [ProjectsController.cs:609](../../backend/ClaudeHomeServer/Controllers/ProjectsController.cs) —
  `UpdateProjectRequest.McpServersOn` + поле в DTO списка (строка 35).
- [McpServerRecord.cs](../../backend/ClaudeHomeServer/Models/McpServerRecord.cs) —
  `AllowOutsideProjects` рядом с `AllowReadOnlyPersonas`; протащить в `McpServerDto`,
  draft создания/правки и `McpServerMapper`.
- **Новый каскад-sweep:** `ProjectManager.PurgeMcpKey(ownerId, key)` — убрать ключ из
  `McpServersOn` всех проектов владельца; звать из `McpServersController.Delete`
  (строка 157, рядом с `PurgeMcpBindings`) и из `Update` при смене ключа (строка 129).
  Сегодня протухший deny безвреден; протухший **grant** — хуже: новый сервер под старым
  ключом молча унаследовал бы чужие выдачи, а счётчики UI врали бы.
- **Бэкап:** на этапе флага инкремент `BackupSchema.Version` **не нужен** — только
  добавления полей с дефолтами (правило в
  [BackupSchema.cs](../../backend/ClaudeHomeServer/Services/Backup/BackupSchema.cs): добавление
  не ломающее). Инкремент 5→6 — на этапе зачистки, когда `McpServersOff` удаляется из модели:
  старый код, восстановив новый архив без deny-поля, молча получил бы «доступно везде».
  `BackupPaths` не трогаем: projects.json и mcp-servers.json уже в архиве, новых файлов нет.

**Риски.**
- Пропущенный sweep при смене ключа → выдачи-сироты (см. выше). Закрыть тестом.
- Два поля (`Off` + `On`) сосуществуют весь период флага — путаница у читателя кода.
  Смягчение: комментарий у обоих полей «deny-ветка, умирает со снятием флага mcp-allowlist».

## 2. Доставка в ход

**Рекомендация.** Всё решение — по-прежнему внутри
[SessionManager.BuildExternalMcpProvider:1886](../../backend/ClaudeHomeServer/Services/SessionManager.cs),
ветка по фич-флагу владельца. Логику условия вынести в чистую статическую функцию
(например, `McpDelivery.ShouldDeliver(record, projectServersOn, isProjectChat, personaGranted, readOnly)`)
— OR-правило имеет 6+ значимых комбинаций, их надо гонять юнитами без SessionManager.

В `PersonaBindingsService` — **новый метод**, `ServerToolEnabled` не трогать:

```csharp
// Выдан ли персоне сервер личного реестра (allow-list): выдаёт только явная
// привязка Mode != Off; отсутствие привязки и Off — не выдан. Чат без персоны — не выдан.
public bool McpServerGranted(Persona? persona, string key) =>
    persona is not null && FindToolBinding(persona, key) is { Mode: not PersonaBindingMode.Off };
```

Ось «чаты вне проектов» встаёт ровно туда, где сегодня deny-шаг пропускается
([SessionManager.cs:1906](../../backend/ClaudeHomeServer/Services/SessionManager.cs) —
`projectId is null`): вместо пропуска шага — чтение `record.AllowOutsideProjects`.
`Project.McpServersOn` читается на каждый ход, как сегодня Off-list — правка настроек
проекта применяется со следующего хода без пересоздания адаптера.

Сопутствующее в PersonaBindingsService:
- `GetToolDefaultState` (строка 238): ветка `IsMcpKey` → `(false, null)` — пикер студии
  показывает «по умолчанию выключен» (за флагом; при выключенном — как сейчас).
- `ToolCatalogFor` (строка 76): текст подсказки — «по умолчанию выключен; привязка
  ВКЛЮЧАЕТ сервер этой персоне; условие применения не учитывается» (тоже за флагом:
  текст читает промпт подбора привязок, он обязан совпадать с действующей семантикой).

**Инвариант стабильности состава.** Не ломается: флаг — свойство владельца, `McpServersOn` —
проекта, привязка — персоны, `AllowOutsideProjects` — записи реестра. Текст/глубина/флаги
хода в условие не входят. Сторож
[McpToolsetStabilityTests](../../backend/ClaudeHomeServer.Tests/Services/McpToolsetStabilityTests.cs)
правится так:
- `РубильникиСерверов_ГейтятсяТолькоПоПерсоне` (InlineData `BuildExternalMcpProvider`, `mcp:`) —
  в regex допустимых точек решения добавить `McpServerGranted`.
- `КаскадРеестра_ТриОсиНаМесте` — проверять `McpServersOn`, `AllowOutsideProjects`,
  `McpServerGranted(`. Пока обе ветки живут в методе, строки обеих эпох присутствуют —
  тест проходит на всём периоде флага; при зачистке deny-ветки ассерты на `McpServersOff`/
  `ServerToolEnabled(` уходят вместе с ней.
- `ПрофильReadOnly_РежетСерверЦеликом_АНеЕгоИнструменты` — без изменений.

**Риски.**
- Соблазн «умного» условия (например, авто-включать сервер персоне, у которой есть привязка
  к проекту с этим сервером) — это и есть запрещённый разрез «персона × проект». Не делать.
- Ветка по флагу внутри лямбды провайдера: следить, чтобы флаг читался при построении
  провайдера или по owner на ход — оба варианта детерминированы на сессию; НЕ читать
  никакие свойства хода.

## 3. Профиль «Только чтение» (`AllowReadOnlyPersonas`)

**Рекомендация.** Остаётся отдельным AND-гейтом поверх allow-list, поведение поля не меняется.

**Обоснование.** Смыслы ортогональны: выдача отвечает «кому сервер нужен», а
`AllowReadOnlyPersonas` — «безопасен ли сервер для персоны, которой запрещено писать».
Выдача в проект широковещательна — она накрывает и чаты RO-персон этого проекта; без гейта
RO-персона получала бы произвольные внешние инструменты (в т.ч. пишущие) через проектную
ось. Явная выдача RO-персоне тоже гейт не обходит: имён инструментов чужого сервера мы не
знаем (обоснование в [mcp-registry.md](../architecture/mcp-registry.md), «Каскад доступности»),
решение по-прежнему принимается целиком по серверу.

**Риски.** UX-грабля: владелец выдал сервер RO-персоне привязкой, а сервер не приехал,
потому что на записи нет `AllowReadOnlyPersonas`. Смягчение — подсказка в UI (студия персоны
и/или вкладка «Доступ»): «персона с профилем "Только чтение" получит сервер, только если на
сервере включено разрешение для таких персон». Передать в задачу 41fb305d.

## 4. Миграция

**Рекомендация.** Чистый старт, без автопереноса. Данные `McpServersOff` в On не
конвертируются — при снятии флага поле просто удаляется.

**Обоснование.**
- «Незаметный» перенос технически прост (OR-правило покрывается project-grant во все проекты
  плюс `AllowOutsideProjects = true`, минус бывшие Off-исключения; персонные привязки не
  нужны — проектная ось накрывает чаты персон), но он **материализует декартово произведение**,
  ради ухода от которого разворот и затевался: 38 явных выдач на сервер с первого дня,
  навсегда неотличимых от осознанных. И «как раньше» всё равно не получится: новый проект
  после переноса сервер уже не получит — расхождение с ожиданием заложено в саму модель.
- Масштаб прода: 1 свой сервер, 0 исключений, владелец — постановщик этой задачи. Повторная
  выдача руками — минуты. Выгода автопереноса нулевая, стоимость (скрипт + замусоренные
  данные) — постоянная.
- Флаг (п. 5) делает момент разворота явным и обратимым: включил — серверы замолчали —
  включаешь их точечно там, где нужны.

**Смягчение «тихого замолкания».** На карточке сервера при включённом флаге — состояние
«не включён нигде: ни в одном проекте, ни вне проектов, ни у персон» (главный экран задачи
41fb305d). Отдельный механизм уведомлений не городить.

**Риски.** Появившийся второй пользователь включит флаг и удивится тишине — но флаг
per-user и включается им самим; состояние «не включён нигде» на карточке отвечает на вопрос
до того, как он задан.

## 5. Фич-флаг

**Рекомендация.** Да, катить за флагом: `mcp-allowlist` («Allow-list доступа MCP-серверов»,
`Default: false`, stage experimental). Три шага по CLAUDE.md: строка в `FeatureFlagCatalog.All`,
ключ в `FLAGS` (`lib/featureFlags.ts`), ветвления в `BuildExternalMcpProvider` /
`GetToolDefaultState` / `ToolCatalogFor` (бэк) и вкладке «Доступ» + `McpProjectSection` (фронт).

**Обоснование.** Это dark-launch-конвенция проекта, и здесь она дёшева: старая матрица и
deny-ветка уже существуют (при выключенном флаге работа — ноль), новый UI строится по задаче
41fb305d в любом случае. Семантический разворот доступа — ровно тот случай, когда нужна
кнопка отката без git revert.

**Критерий снятия флага (все три):**
1. UI новой модели (41fb305d) принят QA (Вера, сценарии из п. 6).
2. Владелец прожил на новой модели ≥2 недель на проде без возвратов к deny.
3. Выполнена зачистка: удалены `Project.McpServersOff`, deny-ветка провайдера, старая
   матрица `McpAccessMatrix`, старые тексты каталога; инкремент `BackupSchema.Version` 5→6;
   обновлены `McpToolsetStabilityTests`, [mcp-registry.md](../architecture/mcp-registry.md)
   (раздел «Каскад доступности» переписывается под allow) и выжимка в CLAUDE.md.

**Риски.** Период двух семантик: настройки, сделанные в allow-режиме, не действуют при
откате флага (и наоборот). Приемлемо — данные не теряются, действует ровно одна модель
в каждый момент; в UI обе поверхности честно подписаны.

## 6. Порядок работ

```
Денис В1: модель + DTO + sweep          <- контракт (стык)
   |                 \
Денис В2: доставка    Кира: UI (после согласования JSON-полей)
+ тесты бэка          - типы/api.ts
   |                  - McpProjectSection (allow, за флагом)
   |                  - вкладка «Доступ» (задача 41fb305d)
    \                /
     Вера: приёмка по сценариям
```

**Денис, волна 1 — контракт (блокирует Киру только именами JSON-полей):**
1. `Project.McpServersOn`, `McpServerRecord.AllowOutsideProjects`, флаг в каталоге.
2. `ProjectManager.Update` (+нормализация), `UpdateProjectRequest`/DTO проекта,
   `McpServerDto`/draft/mapper.
3. `ProjectManager.PurgeMcpKey` + вызовы из `McpServersController.Delete`/`Update`.

**Денис, волна 2 — доставка и тесты:**
4. `PersonaBindingsService.McpServerGranted`, правки `GetToolDefaultState`/`ToolCatalogFor`
   (за флагом).
5. `BuildExternalMcpProvider`: ветка по флагу, чистая функция условия.
6. Тесты: см. ниже.

**Кира (параллельно волне 2; стык — JSON-контракт):**
- `types/index.ts`: `mcpServersOn?: string[] | null` у проекта, `allowOutsideProjects` у
  сервера, `FLAGS.mcpAllowlist`.
- `api.ts`: `projects.update` + запросы реестра.
- `useMcpData`: `setProjectOn` (сегодня `setProjectOff`, строка 324), счётчики «включён в N
  проектах / у M персон» вместо Off-счётчиков.
- `McpProjectSection` (настройки проекта) — allow-семантика за флагом.
- Вкладка «Доступ» — по задаче 41fb305d. **Внимание:** существующий макет
  `docs/mockups/mcp-access-v1.html` + proposal написаны под deny-модель («где сервер
  выключен», кнопка «Выключить в проекте»). Каркас (карточка сервера, список строк, пикер
  проектов с поиском) переиспользуется, но тексты и смысл инвертируются («где сервер
  включён», «Включить в проекте», строка-тумблер «Чаты вне проектов», пустое состояние =
  «не включён нигде» — теперь это не норма, а призыв к действию). Ревизия макета — Майя.

**Тесты (добавить/переписать):**

| Набор | Что |
|---|---|
| `ProjectManagerTests` | нормализация `McpServersOn` (регистр/trim/distinct, null vs пусто); `PurgeMcpKey` чистит все проекты владельца |
| `PersonaBindingsServiceTests` | `McpServerGranted`: нет привязки → false, Off → false, Auto/Always → true, persona null → false; `GetToolDefaultState(mcp:)` за флагом → (false, null) |
| Новый (чистая функция условия) | OR-матрица: проектный чат ± grant проекта ± grant персоны; внепроектный чат ± `AllowOutsideProjects` ± grant персоны; RO-персона ± `AllowReadOnlyPersonas` |
| `McpToolsetStabilityTests` | правки из п. 2 |
| `ProjectsControllerTests` | `McpServersOn` в DTO и Update |
| Каскад контроллера | Delete/смена ключа зовут sweep проектов (по образцу теста на `PurgeMcpBindings`, если он есть; иначе — юнит на связку) |

**Сценарии приёмки (Вера, при включённом флаге):**
1. Сервер без выдач → нет ни в одном чате (проектном, внепроектном, персонном).
2. Включён в проекте A → есть во всех чатах A (и у персон A), нет в проекте B и вне проектов.
3. `AllowOutsideProjects` → есть в чате вне проекта без персоны; в проектах — нет.
4. Привязка персоне → есть во всех чатах персоны (в т.ч. в проекте без выдачи), у других
   персон и в обычных чатах — нет.
5. RO-персона с привязкой, `AllowReadOnlyPersonas=false` → сервера нет; `=true` → есть.
6. Удаление/переименование сервера → выдачи в проектах и привязки персон подметены.
7. Выключение флага → поведение деградирует к deny-модели без потери данных.
