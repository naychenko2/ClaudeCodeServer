## 2. Три грабли — без них приёмка споткнётся

1. **Маршрут `ui_probe` — в `path` вместе с «#».** Правильный вызов:
   `ui_probe url=http://127.0.0.1:5000 path="/#/project/fedfe8c3-eaab-48ae-a5bd-1661bb68f7cc/feature/8d33d18b-c6f6-4311-8ddb-e5a627f38fb2" viewports=[360,1280]`.
   Если положить маршрут в `url` без «#» — проба молчит на домашнем экране и даёт `totals=0` впустую.
2. **Перед любой пробой — свежая сборка фронта в worktree:** `cd /home/an/Sources/ClaudeCodeServer-feature-gantt-c/frontend && npm run build`. Стенд раздаёт `frontend/dist`; в worktree он не собран — без сборки проба меряет старый или пустый билд.
3. **Флаг `features-overview` у admin.** В сгенерированном `data/users.json` среза он включён (`"features-overview": true`) — без него страница фичи не показывается, и вся приёмка упирается в «фичи нет». **Осторожно:** `make-slice.py` пишет `FeatureFlags: {}` — после любого перезапуска скрипта флаг надо вернуть вручную.

## 3. Что на стенде НЕ является дефектом

- **Стадия prod у смерженной фичи остаётся active с тоном «идёт»** при наличии хвостов — намеренное поведение, зафиксированное тестами бэка (`FeaturePostMergeTailsTests`). Хвосты при этом не держат «ждёт вас» (L2).
- **Интервал за правым краем оси.** Бэк отдаёт интервалы без клиппинга; обрезку по окну делает фронт (`FeatureLaneModel.test.ts` › «обрезка по границе окна»). Интервал, целиком за окном, не рисуется — это норма.
- **`intervalsByStage = null` vs пустой словарь.** `null` — только режим approx (журнала нет); пустой словарь — «журнал полный, ходов не было» («этапа не было»). На тестовой фиче журнал полный — пустых словарей быть не должно.
- **Состояния «идёт» и «стоит» на тестовой фиче не видны вживую:** фича смержена, `attention` при хвостах обнулён, живых интервалов нет. Их приёмка — только автотестами (C1, C2). На стенде видны «смержена», паузы-пунктиры между интервалами и хвосты.

## 6. Расхождения с формулировками карточек (решение — за Софьей)

Инструмент поиска задач в сессии составления этого документа отсутствовал, поэтому карточка GC-QA в трекере не видна — но это НЕ значит, что её нет: по договорённости команды («шаги фичи заводятся в трекере сразу после разбора плана») она, скорее всего, заведена, и её критерии, вероятно, взяты из план-заметки. Сверка ниже — по карточке GC-QA план-заметки. Если формулировки карточки в трекере отличаются — прислать её, сверю.

1. **Порог размеров.** Макет: «целей меньше 28 px нет, считая интервалы с зоной касания ±15 px». Карточки (GC-F5c п.3, GC-QA п.1): «`ui_probe` → `totals=0`» при стандартном пороге 40 px. Это разные проверки. **Предлагаю:** держать плановый вариант (`ui_probe` default 40, зона касания — внутри размера элемента, как в «зона касания 40 px — на самой кнопке; видимая капсула 20 px»); 28 px — макетный замер, в приёмке не использовать.
2. **`ui_probe` «Статистики» (GC-QA п.1)** — невыполним plain-proбой по path (вкладка не в URL, N3). **Предлагаю:** заменить в карточке на «замер „Статистики“ через Playwright (клик вкладки)» или снять требование.
3. **Состояния «идёт»/«стоит» (GC-QA: «фича с полным журналом»)** — на срезе фича смержена: живых интервалов и `attention.stopped` нет, состояния проверяемы только автотестами. **Предлагаю:** в карточке прямо указать, что на стенде проверяются «смержена + хвосты + паузы», а «идёт/стоит» — по автотестам; либо просить Марка добавить в срез несмерженную фичу с живым журналом (решение за Софьей/Марком).
4. **Числа ходов.** В карточках шагов встречалось «30 ходов» — неверно (в ответе такого счётчика нет). Живой контракт: 256 событий журнала, 228 ходов в интервалах (см. §1). Везде, где приёмка ссылается на число ходов, брать числа §1.
5. **Повторность возврата (3 из 3, GC-QA п.3)** — строже макета (тот не требует повторности). Оставить как есть: это требование устойчивости, не расхождение.
