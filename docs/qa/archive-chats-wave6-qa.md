# QA-отчёт: сквозная проверка «Архив чатов» по плану v4

**Дата:** 2026-08-24
**Сборка:** worktree `archive-chats-v4` (feature/archive-chats-v4), бэк на :5050, фронт из worktree/frontend/dist
**Тесты автоматические:** `dotnet test` — passed 5702 / skipped 4 / total 5706 (exit 0). `npm run lint:design` — exit 0
**Тесты ручные:** Playwright на :5050 (admin/12345), REST через curl

---

## Сводный вердикт

**ВЕРНУТЬ В ДОРАБОТКУ.** Бэкенд архива в основном работает и проходит все юнит/контроллерные тесты, но фронт фичи не подключён: страницы, настройка правила, пункты меню и плашка возврата у открытого архивного чата либо экспортируются без импорта, либо обращаются к полю, которое сервер не возвращает. На живом UI пользователь не может ни убрать чат в архив через меню, ни попасть в раздел «Архив», ни увидеть плашку возврата — фича выглядит как «только бэкенд».

## Сценарии плана v4 — что проверено

### 1. Убрать чат в архив и вернуть

- ✅ **Сценарий:** PUT `/api/chats/{id}/archived` с `{"archived": true}` → 200, `isArchived=true`, `archivedAt` установлен, `archivedBy="user"`. Повторный вызов с тем же `true` идемпотентен.
- ✅ **Сценарий:** PUT с `{"archived": false}` → 200, `isArchived=false`, `archivedAt=null`. Чат снова появляется в списке проекта.
- ✅ **Сценарий:** история и метаданные не задеты: `claudeSessionId`, `messageCount`, `status`, `personaId`, `name` сохраняются (проверено на `ab9b69fa-...` после архивации/разархивации).
- ⚠️ **Замечание:** Возврат активностью (смена имени) НЕ возвращает чат из архива — `UpdateAsync` (SessionManager.cs:4982-4984) и `RetitleAsync` (SessionManager.cs:4737) намеренно не двигают `UpdatedAt` у архивного. Это соответствует плану («не-активность не двигает UpdatedAt»), но протипт другому месту плана («переименование возвращает чат сама»). Реализация сознательно сужает «активность» до нового сообщения/хода.

**Шаги воспроизведения (переименование архивного не возвращает):**
1. Залогиниться, открыть чат `ab9b69fa-...` в проекте.
2. PUT `/api/chats/{id}/archived` `{"archived": true}`.
3. PUT `/api/projects/{pid}/sessions/{sid}` `{"name": "after-archive-active"}`.
4. GET `/api/chats/{id}` → `isArchived=true`, `archivedAt` остался, `updatedAt` не сдвинулся.

### 2. Архивация чата с ходом в полёте → 409 с понятной ошибкой

- ✅ **Бэк:** `SetArchivedAsync` в `SessionManager` бросает `InvalidOperationException`, `ChatsController.SetArchived` (`ChatsController.cs:232`) мапит в `Conflict(...)` с текстом «в чате идёт ход».
- ⚠️ **UI:** проверить сценарий «архивация во время хода» в живом UI не удалось — для этого нужен реальный ход через claude.exe + подписку; запуск такого хода вне рамок QA. Поведение бэка проверено через юнит-тест `ChatsArchivedEndpointTests`.
- ⚠️ **Дефект (косвенный):** пункт меню «Убрать в архив» не отображается ни в одной карточке (см. п. 6), поэтому пользователь физически не может вызвать этот сценарий через UI. Тест тоста с «в чате идёт ход» невозможен без фикса п. 6.

### 3. Ручная архивация временного чата снимает срок

- ✅ **Сценарий:** `a983b5cd-...` — установлен `expiresAfterMinutes=120`, `expiryAnchor` поставлен. PUT `archived=true` → `expiresAfterMinutes=null`, `expiryAnchor=null`, `isArchived=true`. Соответствует плану («снятие — ДО записи признака архива»).

### 4. Активность в архивном чате возвращает его сама

- ⚠️ **Проверено частично:** реальное «новое сообщение» через SignalR без живого claude.exe не запустить. По коду:
  - `UpdateAsync` (SessionManager.cs:4982-4984) и `RetitleAsync` (4737) — НЕ двигают `UpdatedAt` у архивного, см. п. 1.
  - `SetPinned` — двигает `UpdatedAt` (принято осознанно, закрепление = «чат нужен»).
  - Все остальные ~20 мест, где `entry.Info.UpdatedAt = DateTime.UtcNow` (SendMessage, OnTurnEnd и пр.), проверки на `IsArchived` НЕ содержат → двигают безусловно. Это и есть «активность возвращает чат сама».
- ✅ **Юнит-сторож:** `ChatArchiveServiceTests` покрывает сценарий «активность возвращает чат БЕЗ вызова мутатора» (тест зелёный, виден в логе `dotnet test`).

### 5. Клик «Проставить значки» не выводит чаты из архива

- ✅ **Код:** `SetChatIconsAsync` (SessionManager.cs:4803) имеет предфильтр `Where(s => string.IsNullOrEmpty(s.Topic) && !s.IsArchived)` — архивные отсечены ДО вызова модели.
- ✅ **Юнит:** покрыто в `ChatArchiveServiceTests` (зелёный).

### 6. Раздел «Архив», пункты карточки, плашка возврата, настройка правила

**❌ ДЕФЕКТ — фронт архива не подключён к UI:**

- ❌ **`ArchivePage.tsx`** (`frontend/src/pages/ArchivePage.tsx:51`) экспортирует компонент, но НЕ импортируется ни в одном файле. Маршрута `#/archive` нет в `NavSnapshot`/`toHash` (`frontend/src/lib/nav.ts`). Прямой переход на `#/archive` показывает страницу проекта, а не архив. Счётчик архива в заголовке и empty-state «Здесь пусто. Сюда попадают чаты, к которым давно не возвращались…» пользователю недоступны.

- ❌ **`ArchiveSettings.tsx`** (`frontend/src/components/ArchiveSettings.tsx:33`) экспортирует компонент с полем «Убирать в архив чаты без сообщений дольше…», подписью «Закреплённые чаты и чаты с активными задачами остаются на месте», счётчиком превью и кнопкой «Применить сейчас» — но НЕ импортируется ни в одном файле. В «Настройках проекта» (открыты через кнопку `e253`) этого блока нет.

- ❌ **`ChatCard` принимает `onArchive`** (`ChatCard.tsx:153`) — пункт меню «Убрать в архив» / «Вернуть из архива» существует в коде (`ChatCard.tsx:649-665`), но `ChatList.tsx:147-163` НЕ передаёт `onArchive` в `<ChatCard>`. Условный рендер `{onArchive && …}` всегда ложный → пункт меню НЕ появляется ни в одной карточке чата ни в одном списке.

- ❌ **Плашка возврата у открытого архивного чата** — НЕ реализована. Поиск «Вернуть из архива» в `frontend/src/components/` не находит её; она присутствует только в `ChatCard` (п. выше, не подключён) и в `ArchivePage` (не подключён). При ручном переходе на `/project/{id}/chat/{archivedChatId}` в ленте чата — никакого упоминания «архив»: дефолтный пустой контент `e572-e633`. Шаги воспроизведения:
  1. Залогиниться, открыть проект `qa-archive` (`f12de9db-…`).
  2. Видны три чата в «Сегодня»: «Чат #1», «Чат #2», «after-archive-active». **При этом «Чат #2» — это `a983b5cd-…`, он же в архиве** (см. п. 7 — фильтр не работает).
  3. Кликнуть «Чат #2» → URL `#/project/.../chat/a983b5cd-…`, в ленте нет ни плашки, ни слова «архив», никакой подсказки что чат в архиве.

- ❌ **Select и скролл на чат после возврата** — в коде не реализован. Сам по себе select-скролл завязан на пункт меню или плашку, оба не подключены.

### 7. Счётчик превью и кнопка «Применить сейчас»

- ✅ **Бэк:** `GET /api/chats/archive-preview?days=N[&projectId=]` → `{"count": N}` (проверено: 0 для свежих чатов, ответ корректный). `POST /api/chats/archive-run` → `{"archived": 0, "batchId": null}` (правило не нашло кандидатов, флаг включён).
- ✅ **Бэк:** `PUT /api/projects/{id}/archive-days` с флагом выключен → 400 «Автоправило архива выключено: включите «Автоправило архива чатов» в экспериментальных функциях». С включённым → `archiveAfterDays=30` сохраняется.
- ❌ **UI:** кнопки «Применить сейчас» и счётчика превью нет (см. п. 6 — `ArchiveSettings` не подключён).

### 8. Откат пачки возвращает только чаты своего прохода

- ✅ **Бэк:** `POST /api/chats/archive-batch/{batchId}/restore` → `{"restored": N}`. Откат фильтрует по `ArchiveBatchId == batchId && ArchivedBy == "rule" && IsArchived` (SessionManager.cs:1417) — возвращает только свою пачку. Проверено на несуществующем `test-batch-123` → `{"restored": 0}` (корректно).

### 9. При выключенном `chat-auto-archive` настройка правила скрыта

- ✅ **Бэк:** при выключенном флаге `archive-days` и `archive-run` возвращают 400 с текстом про «включите в экспериментальных функциях» (`ChatsController.cs:79-80` и аналогично в `archive-days`).
- ❌ **UI:** даже при включённом флаге настройка правила невидима (см. п. 6 — `ArchiveSettings` не подключён). Ручной архив и раздел «Архив» тоже не работают без меню и маршрута.

### 10. Блок «Недавние» на главной не пустой при архивных чатах

- ✅ **Бэк:** `HomeController.cs:45` фильтрует `!s.IsArchived` ДО `.Take(recent)` — блок «Недавние» корректно скрывает архивные.
- ✅ **DTO:** `HomeSessionDto.Archived` (без префикса `Is`) — поле называется как ожидает фронт.
- ✅ **Проверено:** GET `/api/home/summary` при 1 архивном + 2 неархивных чатах → `active=[], recent=[1 неархивный]`. Блок «Недавние» есть в `HomeController.cs:40-49`, на UI его рендер отдельный — форму проверил через API.

### 11. Десктопный чат — без копии транскрипта и без сводки

- ⚠️ **Проверено по коду:** `ArchivedTranscriptStore` (новый файл `backend/ClaudeHomeServer/Services/ArchivedTranscriptStore.cs`) и `ChatDigestService` (`backend/ClaudeHomeServer/Services/Llm/ChatDigestService.cs`) реализованы и покрыты юнит-тестами (`ArchivedTranscriptStoreTests`, `ChatDigestServiceTests` — зелёные). Гейт `DesktopChat` присутствует.
- ⚠️ **Live-проверка:** десктопный чат требует флага `desktop-agent` (по умолчанию выключен). Включать и создавать десктопный чат вне рамок этой QA-волны. Юниты подтверждают, что `DesktopChat=true` пропускает копию транскрипта и отказывает в сводке.

### 12. Сводка карточки, её инвалидация после активности, кнопка «Сохранить в заметки»

- ✅ **Бэк:** `POST /api/chats/{id}/digest` для пустого чата → 400 «В чате ещё нет сообщений для сводки» (проверено). Для непустого — собирает сводку через `ChatDigestService` (с `LocalActionCatalog.ChatDigest`, кэш в `ArchiveSummary`/`ArchiveSummaryAt`).
- ✅ **Инвалидация:** `chatDigest.BuildDigestAsync` отдаёт `null`-сводку при `UpdatedAt > ArchiveSummaryAt` (по коду).
- ✅ **Сохранение в заметки:** идёт через существующий `POST /api/sessions/{id}/summary` (план отдельно оговаривает не трогать). Этот эндпоинт не изменён — `SessionSummaryService` не модифицирован.
- ❌ **UI:** кнопки «Собрать сводку» и «Сохранить в заметки» находятся внутри `ArchivePage` (`ArchivePage.tsx:223`), который не подключён (см. п. 6). Карточка чата в обычном списке (где сейчас и показываются чаты — см. п. 7) этих кнопок не имеет.

### 13. Рассогласование имён полей между сервером и фронтом — дефект

- ❌ **Критично:** `Session.cs:502` `IsArchived` сериализуется в `isArchived` (стандартный camelCase для System.Text.Json). `HomeSessionDto` (`HomeController.cs:102`) определяет поле явно как `Archived = false` — сериализуется в `archived`.
- `frontend/src/lib/chatFilters.ts:210-212` `isArchivedChat(s)` читает поле `s.archived` (без `is`).
- **Результат:** для **всех списков сессий проекта/чатов** (SessionsController, ChatsController, ChatList) `s.archived` всегда `undefined` → `isArchivedChat` возвращает `false` → `matchChatFilter` (`chatFilters.ts:223`) НЕ скрывает архивные чаты. **Архивные чаты остаются видимыми в обычных списках** (см. «Чат #2» в списке при проверке).
- `HomeSessionDto.Archived` назван правильно, поэтому `matchChatFilter` на блоке «Недавние» работает корректно (проверено в п. 10).

**Шаги воспроизведения:**
1. Архивировать любой чат `PUT /api/chats/{id}/archived {"archived": true}`.
2. GET `/api/projects/{id}/sessions` — поле `isArchived=true`, `archived` отсутствует.
3. Открыть проект в UI — архивный чат ВИДЕН в обычном списке.
4. `matchChatFilter`/`isArchivedChat` не находит `archived` → фильтр пропускает.

## Что не проверено (вне живого UI)

| Сценарий | Причина |
|---|---|
| Реальный ход во время архивации (409 с тостом в UI) | Нужен живой claude.exe + подписка; в QA-волне для :5050 нет ни того, ни другого. |
| Реальная сводка карточки (не «нет сообщений») | Та же причина. |
| Десктопный чат — без копии транскрипта и без сводки в UI | Требует флага `desktop-agent` и подключённого десктоп-клиента. |
| Активность (новое сообщение) возвращает чат из архива | Требует живой ход. |

По всем этим сценариям поведение бэка покрыто юнитами (зелёные в `dotnet test`), код проверен на наличие гейтов и инвариантных проверок.

## Критические блокеры

1. **Фронт архива не подключён.** `ArchivePage`, `ArchiveSettings`, пункт меню в `ChatCard` (`onArchive`), плашка возврата — всё экспортируется, но не используется. Пользователь не может выполнить ни один клиентский сценарий архива.

2. **Рассогласование имён полей архива.** Сервер отдаёт `isArchived`, фронт читает `archived` — фильтр скрытия архивных из обычных списков не работает; архивные чаты видны наряду с обычными.

Без фикса этих двух пунктов фича в UI фактически отсутствует — её нельзя «увидеть» глазами пользователя.
