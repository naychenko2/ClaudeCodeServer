# ADR-031: фича как сквозное измерение чатов

- **Статус:** принято 2026-10-18, ветка `feat/features-overview`, волна 1 «Обзор фич» (эпик `f9eb511b`). Разрез и контракт — Александр (шаг С0, заметка «Контракт индекса фич — утверждён (Александр, 18.10)»), план — Егор («План «Обзор фич» — Егор, 18.10»), бэк Б1–Б3 — Денис, фронт — Кира. Макеты — [features-overview-proposal.md](../mockups/features-overview-proposal.md), [html](../mockups/features-overview.html).
- **Опирается на** режим «Исполнение фичи»: агрегат `FeatureRun` и порядок `OrderRuns` ([turn-plan-feature-mode.md](../features/turn-plan-feature-mode.md)). Индекс их не дублирует, а переиспользует.
- **Связано:** [ADR-001](ADR-001-task-and-chat-origin.md) (происхождение задачи и чата: `SourceSessionId`, `ExecutorLaunchedBySessionId`), [ADR-014](ADR-014-internal-subsystems.md) (вертикаль `Tasks`, честный 503 у выключенной подсистемы).
- **Контракт для людей:** [turn-plan-feature-mode.md](../features/turn-plan-feature-mode.md), раздел «Контракт `GET /api/tasks/features/index?projectId=`».

## Контекст

Фичу команда ведёт задачами трекера: эпик (`role=feature`) и дочерние задачи с `FeatureId`. Чатов у фичи много: куратор, создавший эпик; оркестратор, запускающий исполнителей; чат каждого исполнителя. В списке сессий они разбросаны по дереву «кто кого породил», и по нему не видно, какие фичи сейчас ведутся и где их чаты.

Нужно второе измерение списка — «по фичам», — не ломая первое (дерево) и не заводя новое хранимое состояние, которое пришлось бы синхронизировать с трекером.

## Решения

### 1. Членство «чат → фича» вычисляется, а не хранится

- **Хранимого поля нет.** Ни у `Session`, ни у `TaskItem` не появилось поля «фича чата». Членство — чистая функция задач владельца и узкого снимка его сессий: `FeatureProjector.BuildIndexCore` ([FeatureProjector.cs](../../backend/ClaudeHomeServer.Tasks/Projector/FeatureProjector.cs)).
- **`Session` на wire не расширяется.** Членство едет отдельным ответом `GET /api/tasks/features/index`, а не полем каждой сессии в `sessions.json` и SignalR-событиях. Причина: членство меняется от событий трекера (`task_changed`), а не сессии; поле в `Session` пришлось бы пересчитывать и рассылать при каждом изменении задачи — вторая точка правды.
- **Виды связи** (сила по убыванию; на пару «чат × фича» одна запись с сильнейшим видом):
  - `curator` — `epic.SourceSessionId == чат` (чат завёл эпик);
  - `orchestrator` — `ExecutorLaunchedBySessionId` эпика или дочерней задачи фичи `== чат`;
  - `executor` — `Session.TaskId` указывает на задачу с `FeatureId == F` или на сам эпик F. `LinkedSessionId` источником не берётся: при перезапуске он перезаписывается, и старые чаты-исполнители выпали бы.
- **`SourceSessionId` дочерних задач — не членство.** Чат, создавший шаг, в фичу не «входит». Иначе оркестраторский чат, который заводит задачи всем фичам, оказался бы членом каждой с видом сильнее, чем есть на деле.
- Вид `key` в словаре силы зарезервирован (`KindStrength`), но в `chats` **пока не отдаётся**: ключевой чат фича несёт полем строки `keySessionId` (п. 2). Контракт С0 предполагал, что ключевой чат всегда есть в `chats` с видом `key`; в Б3 это не реализовано, фронт берёт ключевой чат из строки.
- **Порядок фич у чата** (волна 3): фича, чья задача — `Session.TaskId` чата, первой в списке; далее — по силе связи и bucket (§5, «Порядок фич у чата в нескольких фичах»).

### 2. Ключевой чат — цепочка, первое живое звено

Цепочка (`FeatureProjector.KeyChain`): `epic.SourceSessionId` → `epic.ExecutorLaunchedBySessionId` → самый частый `ExecutorLaunchedBySessionId` среди дочерних задач → `null`. Дубли звеньев схлопываются; при равной частоте берётся лексикографически меньший id — ради детерминизма (контракт С0 предлагал «самую позднюю задачу», реализовано проще; детерминизм держит тест `Мутация_КлючевойЧат_РавенствоЧастот_МеньшийId`).

Живость (`KeySession`):

- **удалённый или чужой чат** — звено пропускается, берётся следующее: живым считается только id из снимка сессий владельца;
- **архивный чат** остаётся ключевым, строка помечает его `keyArchived = true`;
- **чат из другого проекта** остаётся ключевым, его проект — в `keyProjectId`;
- живых звеньев нет — `keySessionId = null`.

### 3. Шов контроллер ↔ проектор

Вертикаль `Tasks` не видит `SessionManager` (ADR-014). Контроллер ([TasksController.GetFeaturesIndex](../../backend/ClaudeHomeServer/Controllers/TasksController.cs)) делает ровно это: 503 при выключенной подсистеме → `sessions.GetAllOwnedBy(UserId)` → маппинг в узкий снимок `FeatureIndexSession(Id, TaskId, ProjectId, Archived)` ([FeatureIndex.cs](../../backend/ClaudeHomeServer.Tasks/Projector/FeatureIndex.cs)) → `features.BuildIndex(UserId, snapshot, projectId)` → `Ok`.

Почему снимок всех сессий, а не пары `(sessionId, taskId)`:

1. Куратор и оркестратор берутся из полей задач — это id чатов, которых в парах нет; фильтр владельца иначе расползся бы на две вертикали.
2. Живость, архив, проект и чужой чат проверяются тестами чистой функции в `Tasks.Tests` ([FeatureIndexMembershipTests.cs](../../backend/ClaudeHomeServer.Tasks.Tests/FeatureIndexMembershipTests.cs), [FeatureIndexRowTests.cs](../../backend/ClaudeHomeServer.Tasks.Tests/FeatureIndexRowTests.cs)), без подъёма `SessionManager`.
3. **Изоляция fail-closed по построению:** задачи — `GetByOwner(ownerId)`, наружу уходит только id чата, который есть во входном снимке владельца. Сквозные тесты (503, чужой чат не попал в `chats` и не стал ключевым, удалённый/архивный/другой проект у ключевого чата, область `projectId`) — в [TasksControllerTests.cs](../../backend/ClaudeHomeServer.Tests/Controllers/TasksControllerTests.cs).
4. Направление ссылок `Main → Tasks` не меняется, `SubsystemBoundaryTests` не задеты.

`TaskItem` в DTO индекса не кладётся: смысл эндпоинта — уйти от тяжёлого `ProjectAll` (полные задачи всех фич) к компактной строке.

### 4. Бэк считает, фронт показывает

`bucket`, `chips`, рельса, тревога, порядок `features[]` (`OrderRuns`) и членство считает проектор; значения строки берутся из `FeatureRun`, а не пересчитываются рядом. `bucket` и порядок — одна точка правды (`Bucket`). Фронт ([featuresIndex.ts](../../frontend/src/lib/featuresIndex.ts), [chatGroups.ts](../../frontend/src/lib/chatGroups.ts)) не пересортировывает и не пересчитывает; обновление — по существующему `task_changed` с дебаунсом, нового SignalR-события нет.

### 5. «Одна строка — одна группа» и правило дерева в «Фичах»

В режиме «Фичи» (`groupByFeatures`) каждый чат стоит **ровно в одной** группе, дублей строк нет:

1. группа чата — первая фича из `chats[id]` (список уже упорядочен по силе связи);
2. у чата без фичи — группа его родителя по `parentSessionId`, рекурсивно; корень без фичи уходит в «Без фичи»;
3. ребро «родитель → ребёнок» живёт, только если оба в одной группе; иначе ребёнок всплывает корнем своей группы (тот же приём, что у висячего родителя);
4. `ParentOverrideId` отдельно не обрабатывается: он уже входит в `parentSessionId` и подчиняется п. 3;
5. мультифичевый чат стоит в группе первой фичи.

**Отвергнуто: «группу задаёт корень дерева».** Родитель исполнителя — чат, который завёл задачу (`SourceSessionId`), а по конвейеру задачи всех фич заводит один оркестраторский чат. При группировке по корню все исполнители всех фич уехали бы в группу первой фичи.

Порядок групп — порядок `features[]` бэка; закрытые фичи уже в его конце, «Без фичи» — после них. Висячий `featureId` (строки фичи нет) уходит в «Без фичи», а не теряется. `Session` не мутируется: в группы уходят копии с эффективным `parentSessionId`.

**Порядок фич у чата в нескольких фичах** (волна 3, Б-ord): если чат — исполнитель задачи фичи (`Session.TaskId` → задача с `FeatureId` или сам эпик), эта фича стоит **первой** в списке чата (`chats[id]` и `ProjectForSession`), независимо от силы связи и bucket. Оба маршрута используют один сортировщик (`FeatureProjector.PreferFirst`), порядок не дублируется. Чат без `TaskId` задачи фичи (оркестратор/куратор) — прежний порядок (сила связи, bucket, давность). **Осознанное изменение:** группа мультифичевого чата в «Фичах» теперь определяется его собственной фичой (а не сильнейшей связью), т.к. группа = первая фича из `chats[id]`.

### 6. Флаги

- **`features-overview`** — фасет «Фичи» в списке сессий (`featureGroupByOptions`, только внутри проекта) и загрузка индекса на фронте. Dark launch, `Default: false`.
- **`turn-plan-feature-mode`** — плашка фичи в чатах фичи: это та же поверхность чата, что режим «Исполнение фичи», поэтому отдельного флага у неё нет.
- Флагами закрыт только UI: эндпоинт `features/index` от флагов не зависит, при выключенных флагах список сессий работает как раньше.

## Волна 2: ручка одной фичи и лента событий

Волна 1 (индекс «чат → фичи», §1–§5) даёт список фич; волна 2 добавляет ручку **одной** фичи по id —
для страницы фичи (макет [features-overview-2-proposal.md](../mockups/features-overview-2-proposal.md) п. 2).
Ручку разрешил Андрей; контракт — Александр (разрез §1).

### Ручка `GET /api/tasks/features/{featureId}`

Эндпоинт — [TasksController.GetFeature](../../backend/ClaudeHomeServer/Controllers/TasksController.cs).
`[Authorize]`, владелец из claim (не из маршрута); от фич-флагов не зависит. Подсистема `Tasks`
выключена (`features == null`) → честный `503` (ADR-014, как у `GetFeatures`/`GetFeaturesIndex`).

**Ответ — обёртка** `{ run, events, eventsTotal }` (контракт — [turn-plan-feature-mode.md](../features/turn-plan-feature-mode.md),
«Контракт `GET /api/tasks/features/{featureId}`»):

- `run` — агрегат: существующий `FeatureProjector.Project(featureId, ownerId)`, новой арифметики нет.
  Обёртка, а не поле в `FeatureRun`: тот же агрегат отдаёт `GET features?sessionId` (плашка чата),
  а лента его раздула бы.
- `events` — лента: `FeatureProjector.BuildEvents(run, снимок сессий)`, порядок как отдаёт функция
  (`At desc`, при равенстве — `taskId`). `?eventsLimit=`: не задан → `100`; `all`/`0` → все;
  `N` (целое > 0) → `N`; прочее → `100`.
- `eventsTotal` — число событий **до** обрезки.

**Коды:** нет эпика / чужой / удалён → один `404` (не отличаем: это же состояние «Фичу удалили» на
фронте); подсистема выключена → `503`.

### Шов: `InternalsVisibleTo` на Main

`BuildEvents` — `internal static` (как `BuildIndexCore`). Контроллер (Main) зовёт его напрямую, поэтому
в [ClaudeHomeServer.Tasks.csproj](../../backend/ClaudeHomeServer.Tasks/ClaudeHomeServer.Tasks.csproj) добавлен
третий `InternalsVisibleTo("ClaudeHomeServer")` (к существующим `ClaudeHomeServer.Tests`/`ClaudeHomeServer.Tasks.Tests`).
Направление `Main → Tasks` не меняется (Main уже ссылается на `FeatureProjector`), `SubsystemBoundaryTests`
не задеты.

### Ручка `POST /api/tasks/features/{featureId}/merge`

Эндпоинт — [TasksController.MergeFeature](../../backend/ClaudeHomeServer/Controllers/TasksController.cs).
`[Authorize]`, `[DenyOnDelegatedTurn]` (анти-рекурсия, как у `Execute`); от фич-флагов не зависит.
Составная операция: создаёт задачу `role=merge` и запускает исполнителя штатным путём
(`TaskExecutionService.ExecuteAsync`), прямого git в бэкенде нет.

**Контракт:**

| Код | Условие |
|-----|---------|
| `503` | подсистема `Tasks` выключена (`features == null`) |
| `404` | эпик не найден / чужой / удалён; тело `{ error: "Фича не найдена" }` — то же, что у `GET` |
| `409` | фича уже смержена (`State == merged`: merge `Done` ∧ (финал принят ∨ эпик `Done`)) или закрыта (`State == closed`, эпик `Done`) — проверяется ПЕРЕД «финал не принят»; частичный мерж (merge `Done`, финал не принят) → не «смержена», а «финал не принят» |
| `409` | финал не принят (`!run.Ready`): `final` не `Done` или вердикт не `accepted`/`accepted_with_remarks` |
| `409` | worktree фичи непригоден: путь или ветка пусты, путь не на диске, или путь не числится в `git worktree list` проекта (тот же предикат, что `AttachWorktreeAsync`) — иначе исполнитель тихо стартовал бы в корне проекта; текст 409 не несёт абсолютного пути хоста |
| `409` | `0` или `>1` персоны с `Specialty=DevopsExecutor`, допустимых в проекте эпика |
| `200` | задача `role=merge` создана (или существующая открытая возвращена) и исполнитель запущен (ответ — задача после запуска, `ClaudeStartedAt` стоит) |

**Осознанные 409 (добивка ревью, волна 2):**

- **Проект не git-репозиторий** — фича в нём **не мержится** (`409`): гард требует, чтобы worktree числился в `git worktree list` проекта, а без git-репо списка нет. Осознанно: мерж «в основную ветку» без git не имеет смысла, поэтому не деградируем в тихий старт в корне.
- **Worktree совпадает с корнем проекта** (`WorktreePath = RootPath`) — `409` «worktree фичи совпадает с корнем проекта»: гард иначе принял бы корень как worktree, и «мерж в основную ветку» происходил бы в том же дереве, что и исход.
- **Подсистема Git выключена** — честный `503` (как у `Tasks`), а не `409` «worktree не найден»: без Git проверить `git worktree list` нечем.
- **Сбой `git worktree list`** — `409` с честной причиной (не `500`), тот же приём, что `AttachWorktreeAsync`.

**Гард записи `role=merge`** ([TaskManager.ValidateFeatureFields](../../backend/ClaudeHomeServer.Tasks/TaskManager.cs),
действует для REST и MCP одинаково, ошибка → `400`):

- задача получает `role=merge` (создание или смена роли на merge) только если фича `Ready` — финал принят
  (`final` `Done` ∧ вердикт `accepted`/`accepted_with_remarks`); иначе «Фича ещё не готова к мержу: финал не принят»;
- **перенос merge-задачи в другую фичу запрещён** (смена `featureId` у `role=merge`) — в Ready-фичу
  Done-merge из A объявил бы B смерженной чужой задачей (`MergedAt` чужой, собственный мерж B потом `409`),
  в смерженную — тихо открыл бы её (`merged → merge_pending`); отвязка (`featureId:""`) тоже `400`;
- update merge-задачи без смены роли и фичи, перенос НЕ-merge задач и создание merge в Ready-фиче — как раньше;
- частичный мерж или выкатка куска — **задача без роли** с `featureId` эпика; полный мерж без финала
  человек оформляет закрытием эпика. Флага обхода гард не имеет.

**Идемпотентность:** если задача `role=merge` уже существует — вернуть её в той же форме, что и ветка
создания (если она `Todo` — сначала запустить исполнителя, ответ — актуальная задача с `ClaudeStartedAt`);
если она уже закрыта (`Status == Done`) — `409` (верхний гард «Фича уже смержена» срабатывает по
`State == merged`, а не по голому `Merge Done`; если `Done` стало в окне между снимком и гейтом —
«Фича смержена во время мержа»: дубль не проходит, гейт лишь сериализует создание, запись из
`MergeGates` не снимается — один семафор на фичу живёт до рестарта процесса).

**Исполнитель:** выбирается динамически через `PersonaSpecialty.DevopsExecutor`
([PersonaContract.cs](../../backend/ClaudeHomeServer.Core/Models/PersonaContract.cs)):
`personas.GetByOwner(ownerId)` → фильтр по `Specialty` → валидация `TaskPersonaValidator.Error`
(зона `PersonaZone`). Имя персоны в код не зашито.

**Поля задачи:** `FeatureId` = id эпика, `Role` = `merge`, `ProjectId`/`WorktreePath`/`WorktreeBranch`
— из эпика, `PersonaId` — выбранный исполнитель, `Assignee` = `Claude`.
`Description` — самодостаточный шаблон постановки (`BuildMergeDescription`): смержить ветку фичи
(`WorktreeBranch` эпика) в основную ветку проекта (имя — текущая ветка корня по git; если неизвестна —
«обычно master», без жёсткого имени) в основном дереве проекта (worktree эпика — источник),
предусловие «финал принят», **push не делать**, при конфликте — доложить (не разрешать молча),
после мержа проверить `git log`/сборку и закрыть эпик, worktree/ветки не удалять.

### Ограничения ленты (честные, без журнала)

Лента — чистая проекция `FeatureRun`/`TaskItem`, хранилища событий нет. Поэтому:

- **Видна последняя пара старт/стоп** задачи: `TaskItem` держит одно `ClaudeStartedAt`/`ExecutorStoppedAt`,
  перезапуск перезаписывает их — журнал не заводим.
- **Нет снятого «ждёт вас»**: `waiting`-событие есть, пока `AwaitingHumanSince` стоит; сняли (→ `null`) —
  события «снято» нет.
- **Нет переносов**: смена исполнителя/персоны отдельного события не даёт.
- **Нет автора кнопки**: кто запустил/снял — не атрибутируется (только `personaId` задачи, если есть).

## Волна 3: макеты фичи

Макет фичи — прототип `docs/mockups/*.html` с запиской-шапкой `*.md` рядом. Связь макета
с фичей — **шапка записки** (единый формат, своего парсера нет) + запасной путь через
`linkedFiles` задач фичи.

### Формат шапки записки

Записка `docs/mockups/<имя>.md` несёт шапку `**Ключ:** значение` сразу за H1 (тот же формат,
что ADR и `DocProperties`):

- `**Фича:** <guid эпика>` — связь с фичей (через запятую — несколько guid, если записка общая);
- `**Статус:** черновик | утверждён | отклонён` — статус макета (меняет Майя/Софья по слову
  Андрея, отдельным коммитом; git показывает, кто и когда утвердил);
- `**Файлы:** a.html, b.html` — прототипы макета (относительные пути — от папки записки).

Html не разбираем вовсе: прототип идёт в «Файлы» записки. Один парсер, одна точка правды,
ноль регулярок по html.

### Склейка в контроллере, не в проекторе

`FeatureProjector` (Tasks) файлов **не касается** (ADR-014: швы по фактической потребности).
Склейку делает `TasksController.GetFeature` (Main): ссылки `Main → Docs` и `Main → Tasks`
разрешены, `SubsystemBoundaryTests` не задеты. Порядок (fail-closed, сторож G10):

1. эпик → `epic.ProjectId` → проект владельца (`GetByOwner`); чужой/нет → `mockups: []`;
2. локальный проект (`ProjectCapabilities.FilesOnServer=false`) → `mockups: []` +

### Фиксированная область, проверенное дерево, `exists`

  может сузить «Доки», и макеты пропали бы. Отдельный слот кеша `DocsIndexService` (ключится
  корнем + областью) — не мешает и не дёргает область проекта.
- **Проверенное дерево эпика** (волна 4, W4-5): «master-only» отменён — каталог и читалка
  файлов резолвят проверенное worktree эпика (`epic.WorktreePath`, сверка с
  `git worktree list` проекта): запись `tree="feature"` побеждает master по относительному
  пути, макет из ветки виден до мержа. Нет проверенного дерева — основной checkout, как

## Волна 3: состояние, журнал, статистика, расход, прогресс

Решения — Александр: разрез волны 3 (карточка `0fefe39c`), архитектурное ревью журнала и
машины состояний (`25ec27ec`), финальное ревью «честного прогресса» Б-pr2 (`621b2e5a`),
финальное ревью деления общего расхода Б9c (`29af360f`). Разбивка на шаги — Егор
(`d097f474`). Ниже — что решено, что отвергнуто и какой инвариант это держит. Описание
для человека — [features-overview.md](../features/features-overview.md).

### 1. Состояние фичи: одна функция, `bucket` из неё

- **Решено:** девять состояний (`merged → closed → stopped → waiting → merging →
  merge_pending → running → not_started → idle`), первый совпавший побеждает —
  `FeatureProjector.ComputeState`. `bucket` строки индекса и порядок `OrderRuns`
  выводятся из `state`; отдельного расчёта группы нет. Тревога `kind=merge` остаётся
  только при `merge_pending` (merge-задачи нет); при `merging` тревоги нет — идущий
  мерж больше не выглядит как «ждёт вас».
- **Отвергнуто:** тревога «мерж» по условию «merge-задача не `Done`» — она держала
  тревогу, пока мерж идёт (баг, который чинит Б1).
- **Инвариант:** одна точка правды состояния. `state` явно копируется в `SlimRun` —
  каждое новое поле `FeatureRun` с тестом сериализации, иначе оно теряется молча.
  **Совместимость:** изменение несовместимо со старым клиентом (читатели `kind==='wait'`
  с причиной «мерж»), поэтому Б1b и фронтовый Ф-mk — один пакет; по отдельности в master
  не вливать.

### 2. Честный прогресс: одна правда о принятии

- **Решено:** единица учёта — шаг (`stepRef`; без него — id задачи). Один проход
  `FeatureStepAccounting.Build` даёт и цепочки, и корзины, и линии: расхождения по
  построению нет. `total = accepted + review + work + notCreated`; `withdrawn` и
  `unlinkedReworks` — вне знаменателя. `StepsOpen = total − accepted`. Последний виток
  определяется **по завершению**: `(CompletedAt ?? +∞, TaskStart)` — идущий виток
  становится последним, поэтому шаг с открытым возвратом честно числится «на ревью».
  Снятая доработка шаг не снимает: шаг снят, только если последний виток `withdrawn`
  или снята сама задача-шаг. Ключи шагов сравнивает один `StringComparer.OrdinalIgnoreCase`
  (+ `Trim` для старых данных) — и в проекторе, и в гарде дублей плана. «План не
  разобран» — честное состояние до заполнения `planSteps` (отдельная задача после
  выкатки, П-pr): `notCreated = 0`, и мерж этим не блокируется. `tasks_get` в ветке
  волны отдаёт `planSteps` — аддитивное поле, отдельного слова Андрея не потребовалось.
- **Отвергнуто:** формула `total − accepted − withdrawn` (ошибка разреза «момент
  закрытия», §1 — заменена формулой выше); порядок витков по старту (решение 2); «снять любой
  виток цепочки = снять шаг» (асимметрия `ordered.Any`); отдельный Core-хелпер для
  принятия — `TaskManager` живёт в той же сборке `Tasks`, шва Main → Tasks нет, а хелпер
  «впрок» против ADR-014; отдельное поле «сумма записей чата и выданных долей».
- **Инвариант:** `IsAcceptance`/`IsFinalAccepted` — единственная точка решения о
  принятии (`Ready`, `merge_pending`/`merged`, гард `role=merge`, шаг). Сторож —
  мутация «`accepted_with_remarks` → возврат»: в прогоне Глеба краснеют три теста.

### 3. Журнал событий: append-only файл в вертикали `Tasks`

- **Решено:** хранилище `data/feature-journal/{ownerId}/{featureId}.jsonl`, путь через
  `SafePath.Join`, белый список id **и при записи, и при чтении**. Формат строки `v:1`
  (`kind, at, taskId, reason, from, to, verdict, sessionId, turnSeq, startedAt, endedAt,
  outcome, errorClass, model`) утверждён и годится как контракт для timeline и
  разрезов: работа — интервалы `turn`, ошибка — `turn.outcome = error`, ожидание —
  `waiting…waiting_cleared`, простой — остаток; модель пишется на каждый ход, поэтому
  смена модели внутри задачи видна. Переходы пишутся во всех мутаторах `TaskManager`
  сравнением снимка «до/после», а не на `SaveNow`; ходы — подписчик `TurnCompleted`
  на шине (ADR-013), который ищет задачу через `GetBySession` своей вертикали и швов
  не добавляет. Ошибки записи глотаются, мутацию не роняют. Потолок 20 000 строк:
  при переполнении перестают писаться только `turn`-записи, `truncated = lines ≥ MaxLines`.
  «Полный журнал» — начинается с `created` и не обрезан; только тогда `source = journal`.
  Фичи до выкатки журнала — целиком «≈», гибрида нет. `BackupSchema.Version` не поднят:
  появился новый каталог в `data/`, формат существующих данных не менялся.
- **Отвергнуто** (блокеры ревью, закрыты доработкой): каскад удаления журнала по
  `task.FeatureId` при удалении **любой** дочерней задачи — каскад только для эпика
  (`Role == feature`); проверка id в `Read` «закомментированная мутацией» — без неё
  `../<чужой>/<id>` читал бы журнал чужого владельца; молчащий `ClearAwaitingHuman` —
  ожидание в проде не снималось никогда, поэтому `waiting_cleared` не писалась и
  интервал «ожидание» не закрывался. Решено: снятие ожидания происходит в точках
  ответа человека — при запуске исполнителя и при переходе в `Done` (через публичный
  `ClearAwaitingHuman`). Отдельного хранилища событий и нового SignalR-события нет.
- **Инвариант:** изоляция по пути владельца и снимку сессий (fail-closed); новых
  MCP-инструментов и ручек записи нет, поэтому `[DenyOnDelegatedTurn]` не затронут;
  при выключенной `Tasks` не регистрируются ни журнал, ни подписчик, контроллер
  отдаёт 503. Сироты подметаются только у владельцев с задачами — осознанный fail-safe:
  каталог владельца без задач не чистится никогда.
- **Не зафиксировано в карточках:** ретенция сверх потолка (в карточке только оценка
  «~200 Б на событие»); автор кнопки «кто запустил/снял» — не атрибутируется; `verdict` без
  `from` — в формате сознательная дыра, не дефект.

### 4. Статистика и расход: ничего нового не хранится

- **Решено:** записи расхода хода уже несут `TaskId/SessionId/PersonaId/Model/CostUsd`
  (`Services/SpendMapping.cs`, `RecordTurnSpend`), дневные свёртки сохраняют `TaskId` —
  нужен только шов чтения: `ISpendFeatureReader` в Core, реализация в `Spend`. Шов
  **опциональный**: `null` → `stats.spend = null`, а не 0. Атрибуция: задачи фичи плюс
  ключевой чат, если он состоит только в этой фиче; ось исключения (общие чаты)
  **главнее** обеих осей. Цена ненадёжна — один предикат `SpendCostReliability`
  (список из конфига `Spend:UnreliableCostModels`, дефолт `deepseek`, `glm`); такие
  модели не входят в сумму, токены остаются: `costPartial`, `hiddenCostModels`.
  `Source = free` — надёжный 0, проверяется раньше «ненадёжно». Токены — «вход+выход»
  крупно, кэш отдельно (решение Андрея, 20.10). `stats` живёт только в
  `GET features/{id}`: `FeatureRun` остаётся лёгким.
- **Отвергнуто:** отдельное хранилище расхода по фичам; приписывать расход общего
  оркестратора каждой фиче целиком (двойной счёт); делить общий чат «на все фичи
  запроса» — знаменатель **состава конкретного чата** `M[c]`, а не объединение
  участниц (проба: `c1 = {F,G}`, `c2 = {F,H}`, ход 90 токенов → 75, тест красный);
  метка `method` по фиче — она **по чату**; «≈» как «источник неточный» — метка
  означает точность доли, а не источник интервалов.
- **Инвариант (главный сторож):** сумма долей равна расходу чата ровно. Каждый ход
  делится отдельно и полностью: активные фичи этого чата упорядочиваются по id,
  `base = x / N`, `r = x % N`, первые `r` получают `base + 1` (метод наибольшего
  остатка); деньги — `decimal`, проверка сохранения с допуском 1e-9. Ход без активных
  фич не распределяется. Активность фичи строит **один** модуль
  (`FeatureActivityBuilder`), half-open `[from, to)`; «остановка главнее работы» из
  `ComputeState` в историю не переносится — активность означает «над фичей работают
  или её ждут», а не статус в интерфейсе. `journal.Read` — один раз на запрос
  (словарь по `featureId`), глобального кэша нет.
- **Не зафиксировано в карточках:** «нераспределённый расход» (ход/сутки без активных
  фич) как число в ответе — аддитивное поле, ждёт слова Андрея; место ему в сводке
  расходов владельца, а не в `stats.spend` фиче. Точный режим для старых фич,
  «кто нажал», сравнение с типичной фичей, остановка/запуск, очередь, перезапуск шага,
  закрытие без мержа — отложены (разрез §5).

### 5. Хвосты волны (тех. долг, мерж не держат)

- Журнальная ветка `FeatureTimeline` держит свою копию правила активности
  (`stopped ?? done`, `StartedAt` вместо `At`) — свести к `FeatureActivityBuilder`.
- `AllTasks(run)` продублирован в `FeatureActivity` и `FeatureTimeline` — одна функция.
- Пять inline-копий «вернули» (`Returned or AcceptedWithRemarks`) в `FeatureProjector`
  — ось петель, заменить на `IsReturn`.

**К «Последствиям» волны 1:** волна 3 добавляет один каталог в `data/`
(`data/feature-journal/`) — он попадает в бэкап по умолчанию, `BackupSchema.Version`

### 2. Три часа: работа, очередь, состояние

- **`elapsedMinutes` — рабочее время, а не время с момента постановки.** Это
  `WorkWallMinutes` — работа по часам стены: объединение work-интервалов, параллельные
  не складываются ([FeatureTimeline.cs:64-65](../../backend/ClaudeHomeServer.Tasks/Projector/FeatureTimeline.cs)).
  Сводка берёт готовое число из того же экземпляра `timeline`, что пошёл в `stats`
  ([TasksController.cs:866-868](../../backend/ClaudeHomeServer/Controllers/TasksController.cs));
  второго счёта нет (FeatureBrief.cs:128).
- **`queueWaitMinutes` — время в очереди.** Только у `kind = queued`: от момента
  постановки удержания (`FeatureHold.Since`, [TaskItem.cs:204](../../backend/ClaudeHomeServer.Core/Models/TaskItem.cs))
  до `now` (FeatureBrief.cs:156-161). Отдельное поле, потому что у фичи в очереди
  work-интервалов нет: `elapsedMinutes = 0`, и подпись «в очереди N мин» иначе была бы
  недостижима (MAJOR-1 ревью R-F8). При пере-постановке в очередь — время ТЕКУЩЕГО
  стояния, прошлые интервалы очереди не суммируются (:154-155).
- **`updatedAt` — время последнего записанного события состояния**, а не касания записи: максимум
  событий состояния задач фичи (`CreatedAt`, `ClaudeStartedAt`, `ExecutorStoppedAt`,
  `CompletedAt`, `AwaitingHumanSince`, `Hold.Since` эпика) (FeatureBrief.cs:287-306). Снятие паузы
  (`ClearHold`, TaskManager.cs:1421) и снятие ожидания (`ClearAwaitingHuman`, :1357) состояние меняют,
  но события не создают: вклад отметки исчезает из максимума, значение может уменьшиться —
  откатывается к предыдущему событию (финал принят 10:00, пауза 12:00, снята 12:05 → снова 10:00;
  характеризующий тест FeatureBriefTests.UpdatedAt_СнятиеПаузыИОжиданияНеСоздаётСобытияЗначениеОткатывается).
  **Отвергнуто:** `TaskItem.UpdatedAt` (двигается настройками задачи — состояние от них
  не меняется) и `LastActivityAt` (в нём только завершение/старт — «исполнитель встал»
  и «ждёт вас» в нём не видны) (:281-283). `computedAt` остаётся отдельным полем:
  он отвечает на «насколько свеж снимок», `updatedAt` — на «насколько old показано» (:17-19).

### 3. Оценка: история проекта, ничего не хранится

`estimate.remainingMinutes ≈ stepMinutes × (Work + NotCreated + 0.5 × Review) + tailMinutes`,
где `Work/NotCreated/Review` — корзины шагов `run.StepProgress`, а `stepMinutes`/`tailMinutes` —
медианы выборки (FeatureBrief.cs:225-231). Коэффициент «на ревью» — именованная константа
`ReviewCoefficient = 0.5`, не настройка (:45). `p25`/`p75` — та же формула по тем же
квантилям выборки: `p25 ≤ remaining ≤ p75` по построению (:205-207). `source` один:
`"history"` (:48).

Выборка — расширение существующей `FeatureTypical` («типичная фича» волны 5), того же
её кэша: `StepMinutes` — медиана по смерженной фиче от средней длины её принятых цепочек,
`TailMinutes` — от принятия последнего шага до мержа
([FeatureTypical.cs:65-72](../../backend/ClaudeHomeServer.Tasks/Projector/FeatureTypical.cs),
:229-236). Длительности берутся из `run.StepChains`, которые проектор посчитал для этой
же фичи: нового прохода по журналам и нового хранилища нет (:24-33). Считаются только

### 4. «Голос оркестратора» — `TaskItem.Note`

Хранимое поле только у эпика ([TaskItem.cs:151-154](../../backend/ClaudeHomeServer.Core/Models/TaskItem.cs)),
запись `FeatureNote` (:211-215): текст ≤ 600 (`MaxTextLength`, :214), `At`, чат автора,
`ByUser`, стадия и категория на момент записи. Пишет `TaskManager.SetFeatureNote`
([TaskManager.cs:1442-1456](../../backend/ClaudeHomeServer.Tasks/TaskManager.cs)):
обрезка и усечение на сервере, пустой текст снимает голос (:1450-1452). `At` — момент
записи, `StageAtWrite`/`StateAtWrite` штампует сервер из проекции, агент и клиент их не
передают. Стадия — активная стадия конвейера по той же функции `FeatureBrief.ActiveStageOf`,
с которой сверяет `StaleOf` (единая база штампа и проверки; `Now[0]` для штампа не используется:
на «ждёт вас» / паузе / idle он пуст, и голос там был бы устаревшим с первой секунды —
возврат FIN 74722f13) (FeatureBrief.cs:165-172,
[TasksController.cs:1029-1030](../../backend/ClaudeHomeServer/Controllers/TasksController.cs),
[TasksToolset.cs:482-483](../../backend/ClaudeHomeServer/Services/Mcp/Http/TasksToolset.cs)).
**Категория на момент записи — та же величина, что `brief.kind`** (`FeatureBrief.KindAtWriteOf`,
та же функция `KindOf`, что считает категорию фичи; B15, дефект 415c1c80): у фичи в очереди
состояние проекции — «paused» (причина удержания не хранится), а категория — «queued». Штамп
состоянием давал «голос устарел с первой секунды» в очереди; именем поля и JSON-контракт
не трогаем — `StateAtWrite` теперь хранит категорию, а голоса, записанные до B15, хранят
СОСТОЯНИЕ и достраиваются до категории таблицей `FeatureBrief.KindByState` (fail-closed для
неизвестного значения), миграция данных не нужна.

**Кто вправе.** Человек — `PUT features/{featureId}/note`, тело только `text`; сервисный
токен — 403 (:1010-1014), не-эпик — 400 (:1022-1023). Агент — параметр `featureNote` у
`tasks_update`: право только у `curator` или `orchestrator` фичи, исполнитель
(`executor`) получает отказ «Голос фичи пишет оркестратор или человек»
([TasksToolset.cs:313-328](../../backend/ClaudeHomeServer/Services/Mcp/Http/TasksToolset.cs)).
**Обе точки проверяют одно правило `FeatureChatMembership`, локальной копии правила
членства не заводим** (риск 6 разреза — блокер ревью). Когда писать — процессное правило
(конвейер Софьи: на переходах этапа, на «ждёт вас», на паузе); серверной автоматики нет.

**Что наружу не отдаётся.** `bySessionId` — чат автора живёт в `tasks.json`, с wire его
снимает конвертер типа на границе сериализации — во всех четырёх выходных опциях
(REST-списки и карточка, ответы PUT/POST, `task_changed`, MCP)
([FeatureNoteJsonConverter.cs:25](../../backend/ClaudeHomeServer/Services/FeatureNoteJsonConverter.cs));
из модели поле не удалено: это след автора, из него в будущем заполняется `byPersonaId`
— аддитивная правка модели, не проектора (FeatureBrief.cs:238-239). `StateAtWrite`
служит только признаку устаревания, наружу не уходит (FeatureBrief.cs:66-69).

**Когда голос устаревший** (`brief.note.stale`): `StageAtWrite` ≠ текущей активной
стадии конвейера ИЛИ категория (`brief.kind`) сменилась с момента записи
(FeatureBrief.cs:264-270); тесты — [FeatureBriefTests.cs:508](../../backend/ClaudeHomeServer.Tasks.Tests/FeatureBriefTests.cs),
:519, :531. Текст устаревшего голоса не прячем — это последнее слово ведущего; голоса
нет — строки нет совсем (:240-241). Голос, записанный в очереди, свежий до смены категории
(очередь → пауза человека / работа) — штамп и сравнение берут одну величину (B15, дефект
415c1c80); прежнее ограничение («причина удержания на момент записи не хранится») снято.

## Что вынесено за волну

Выкатку не блокирует ничего: флаги выключены, каждый пункт честно деградирует.

- **Панель «Фичи»** — отдельная поверхность обзора; в волне 1 только фасет списка сессий.
- **Хранимый `KeySessionId`** у эпика (ручное назначение ключевого чата) — пока ключевой чат только вычисляется цепочкой п. 2.
- **Фильтр «Задач» по фиче** — трекер по `featureId` не фильтрует.
- **Ручная привязка чата к фиче** — членство только вычисляемое; ручная привязка потребовала бы хранимого поля и правил его согласования с трекером.

## Последствия

- Новых хранимых полей, файлов в `data/` и SignalR-событий нет — бэкап, миграции и `BackupSchema.Version` не затронуты.
- Членство меняется вместе с задачами: перезапуск исполнителя из другого чата переносит `orchestrator`-связь, удаление эпика убирает фичу из индекса целиком (висячий `FeatureId` дочерних её не поднимает).
- Цена: каждый запрос индекса проходит все задачи и сессии владельца. Задачи группируются по `FeatureId` один раз, поэтому стоимость линейная; кеша нет, пока не понадобится.
