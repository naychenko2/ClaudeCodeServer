# Разбор раскладки PanelZone: путь панели «История решений» и гипотеза двойного монтирования

Дата: 2026-08-21. Автор: Кира (frontend). Правок кода не делалось — только чтение.

## 1. Путь элемента от WorkspacePage до карточки

1. `frontend/src/pages/WorkspacePage.tsx:1746` — элемент создаётся один раз в литерале
   `panels={{ … dossiers: <DossierHistoryPanel … /> … }}`. Объект `panels` не мемоизирован
   (в отличие от `WallPage.tsx:175`, где стоит `useMemo`), то есть пересоздаётся на каждый
   рендер страницы — но тип узла стабилен, реконсиляция перемонтажа не даёт.
2. `frontend/src/pages/workspace/DesktopWorkspace.tsx:240` — тот же объект кладётся в
   `zonePanels` и передаётся **обеим** зонам: `PanelZone side="left"` (`:333`) и
   `PanelZone side="right"` (`:480`). Один и тот же React-элемент в двух пропсах — не проблема
   сам по себе: элемент это описание, а не инстанс; два монтирования будут только если
   **обе зоны реально его отрендерят**.
3. `PanelZone.tsx:188` — `content(k)` достаёт `panels[k]`; `:184` `keyAvailable` проверяет
   только `allowedKeys` и наличие контента, **зону не проверяет**.
4. Дальше — три взаимоисключающие ветки рендера:
   - десктоп: `zoneBody` → `renderPanel` на `PanelZone.tsx:1205`;
   - компакт (планшет), inline и drawer: `compactBody` → `renderPanel` на `PanelZone.tsx:1255`;
   - «Стена» (floating): `zoneBody` внутри ранн­его return `PanelZone.tsx:1310–1322`.
5. Выбор ветки — `PanelZone.tsx:1299`: `const body = compact ? compactBody : (…)`,
   и `:1335` `return isLeft ? <>{rail}{body}</> : <>{body}{rail}{zoneProbe}</>`.

## 2. Вычисляется ли `compactBody` безусловно

Да, IIFE на `PanelZone.tsx:1236` выполняется каждый рендер, **но** первой же строкой
(`:1237`) отдаёт `null` при `!compact`, а `columns` на `:199` в компакте пустой массив
(`compact ? [] : layout…`). То есть:

- вне компакта `compactBody === null` — drawer/оверлей ничего не монтирует;
- в компакте `zoneBody` не попадает в дерево вовсе (`:1299`), а floating-ветка закрыта
  условием `if (floating && !compact)` (`:1310`).

Порталов ни у drawer'а, ни у бэкдропа нет: `PanelZone.tsx:1268–1283` — обычные
`position: absolute` внутри зоны. Попап-превью (`peekCard`, `:922`, второе место с
`content(k)` на `:944`) выключен флагом `PEEK_ENABLED = false` (`:70`) и дополнительно
отсечён `!openKeys.includes(peeked.key)` (`:646`).

**Вывод по постановке:** одновременного монтирования «десктоп + compact/drawer» в коде
`PanelZone` нет — ветки строго взаимоисключающие. Гипотеза «`compactBody` смонтирован
параллельно десктопной раскладке» не подтверждается.

Межзонный дубль (обе `PanelZone` рендерят `dossiers`) тоже закрыт на уровне стора:
`panelStackState.ts:378` `zoneOf` держит панель ровно в одной зоне, `openPanelIn` (`:620`)
сначала зовёт `closePanel`, а загруженное из localStorage состояние проходит
`enforceZoneInvariant` внутри `sanitizeZones` (`panelStackState.ts:421–447`) — «панель ровно
в одном месте».

## 3. Что действительно найдено: два источника истины об открытости

Реальный дефект в этой области — не одновременный, а **последовательный** двойной монтаж
из-за двух параллельных источников открытости:

- store-раскладка зоны — `PanelZone.tsx:118` (`layout` из `zoneState`);
- эфемерный локальный стек — `PanelZone.tsx:162` `const [tabletPanels, setTabletPanels] = useState<PanelKey[]>([])`.

Развилка источников — `PanelZone.tsx:206–212`:

```
const tabletKeys = compact
  ? (compactOverlay ? tabletPanels.filter(keyAvailable)   // узкий планшет
                    : layout.flat().filter(keyAvailable)) // широкий планшет inline
  : [];
```

и то же дублирование в `openZoneOf` (`:316–318`). Порог между ветками — `tabletInline`
(`PanelZone.tsx:168–170`), он считается **по ширине окна и ширине зоны**
(`windowWidth >= width / PANEL_INLINE_MAX_SHARE`).

Отсюда два наблюдаемых эффекта, которые снаружи выглядят как «панель смонтирована дважды»:

1. **Панель числится открытой в двух местах.** `placeHere` при `compactOverlay`
   (`PanelZone.tsx:389–395`) кладёт ключ в `tabletPanels` и **не трогает store-раскладку**.
   Если панель уже лежала в `layout` (открыта на десктопе, потом окно сузили — тогда она
   исчезает с экрана, потому что `columns = []`), клик по иконке рельсы добавит её ещё и в
   `tabletPanels`. Никакого выселения из `layout` при этом нет.
2. **Перемонтаж на границе порога.** Пересечение `tabletInline`/`compact` меняет ветку
   дерева (`:1205` ↔ `:1255` ↔ `:1299`), а вместе с ней — позицию и тип узлов вокруг
   `DossierHistoryPanel`. React в этом случае размонтирует и смонтирует панель заново:
   сбрасывается её состояние, повторно уходят запросы, повторно инициализируются диалоги
   `DossierExportDialog`/`DossierImportDialog`, живущие внутри самой панели. При ресайзе окна
   рядом с порогом это происходит пачками.

Плюс к этому `reveal` (`panelStackState.ts:1185–1189`) судит об открытости строго по
`zoneOf`, то есть по store-раскладке, и в `compactOverlay` отвечает «уже открыта» про
панель, которой на экране нет.

## 4. Какой коммит это принёс

- **8a6b509d** (`feat(tablet): адаптивный UI планшета…`, 16.08) — да, это он. Диффом
  `tabletInline` из простого `windowWidth >= TABLET_INLINE_MIN` превратился в составное
  правило с шириной зоны, и появилась развилка drawer/inline внутри `compactBody`. Сам
  эфемерный `tabletPanels` старше (введён `e696e46b`, единая зона панелей), но именно
  8a6b509d сделал границу между «эфемерным» и «store» источником подвижной и зависящей от
  ширины зоны.
- **0bddcd9f** (21.08) — трогает только `multiInCol` в `compactBody` (`PanelZone.tsx:1244`),
  то есть растягивание одиночной панели по высоте. К монтированию отношения не имеет.
- **73f5b9ff** (21.08) — трогает только геометрию drawer'а (`top: GAP` + `maxHeight`,
  `PanelZone.tsx:1268–1275`) ради тени. К монтированию отношения не имеет.

## 5. Что стоит проверить в браузере (для волны с живой проверкой)

Гипотеза «панель в дереве дважды одновременно» проверяется за один шаг: открыть «Историю
решений», в DevTools → Elements поискать заголовок панели / корень `DossierHistoryPanel`
и убедиться, что совпадение одно. Если совпадений два — значит источник дубля **вне**
`PanelZone` (например, второй экземпляр `WorkspacePage`/`DesktopWorkspace` в дереве), и
искать надо там, а не в ветках раскладки.

Если совпадение одно, а симптом (двойные модалки, дублирующиеся запросы) есть — это
сценарий из §3: ловится счётчиком монтирований в `DossierHistoryPanel` при медленном
ресайзе окна через ~1000px и при переключении «узкий планшет ↔ широкий планшет».

## 6. Итог

- Постановочная гипотеза (compact смонтирован параллельно десктопу, в т.ч. через порталы)
  **не подтверждается**: `PanelZone.tsx:1299` делает ветки взаимоисключающими, порталов нет,
  peek выключен, межзонный дубль снимает `enforceZoneInvariant`.
- Подтверждается другая: **два источника истины об открытости** (`layout` vs `tabletPanels`,
  `PanelZone.tsx:206–212`, `:316–318`, `:389–395`) и **смена ветки дерева на пороге
  `tabletInline`** (`:168–170`, `:1205`/`:1255`/`:1299`) дают повторные монтирования панели
  и рассинхрон «открыта/не видна». Принёс это **8a6b509d**; 0bddcd9f и 73f5b9ff здесь ни при чём.
- Подстраховка «единственный экземпляр модалок фичи», заложенная в план команды, лечит
  симптом и в этом сценарии тоже — но корень в раскладке, а не в диалогах.
