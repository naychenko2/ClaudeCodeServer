# Выбор генератора картинок (иконка проекта, аватар персоны)

**Статус:** реализовано, без фич-флага. Настройка не меняет поведение чистой установки —
до первого выбора админа работает режим «Автоматически».
**Источник правды по поведению — код:**
[backend/ClaudeHomeServer/Services/Images/](../../backend/ClaudeHomeServer/Services/Images/),
[FalImageService.cs](../../backend/ClaudeHomeServer/Services/FalImageService.cs),
[ImageGenerationController.cs](../../backend/ClaudeHomeServer/Controllers/ImageGenerationController.cs).
**Смежные документы:**
- [ADR-008](../adr/ADR-008-project-background-generation.md) — фон проекта; догоняющая
  генерация здесь повторяет его паттерн (`ProjectBackgroundBackfill`);
- [../architecture/features.md](../architecture/features.md), раздел «Генерация медиа
  (fal.ai, glif)» — медиа из **ходов чата** и карточки использования (это другая поверхность:
  там генерирует модель через MCP, здесь — сервер сам);
- [model-presets-and-tiers.md](model-presets-and-tiers.md) и
  [ADR-007](../adr/ADR-007-model-preset-chains.md) §4 — та же логика выбора, что у текстовых
  моделей: подмена только по явно заданному порядку, автоподбора нет.

---

## 1. Зачем

Иконку проекта и аватар персоны рисовал единственный жёстко зашитый драйвер fal.ai с моделью
из `Fal:ImageModel`. Из этого следовали три проблемы:

- **нет ключа fal — нет картинок вообще**, хотя у инстанса может быть подключён glif
  (его токен уже есть для MCP-инструментов чата);
- **выбор сервиса и модели зашит в конфиг машины** — админ не мог поменять его из интерфейса;
- **неудачная генерация теряла картинку навсегда**: проект или персона оставались на
  инициалах, и вернуться к этому было нечем, кроме ручного повтора.

Фича закрывает все три: слой драйверов с общим контрактом, выбор сервиса и модели в разделе
«Модели и расход», очередь догоняющей генерации.

## 2. Как устроено

```
ImageGenerationController ──┐
ProjectsController          ├─► ImageGenerationService ──► IImageGenerator
PersonasController          │      (роутер: режим,          ├─ FalImageService  (fal, синхронный)
OnboardingController        │       порядок, модель)        └─ GlifImageGenerator (glif, с опросом)
        │                   │              ▲
        │ картинки нет      │              │ настройка инстанса
        ▼                   │      ImageGenerationSettingsStore
ImageBackfillService ───────┘        (data/image-generation.json → секция Images → auto)
   (очередь data/image-backfill.json, прогон, SignalR image_backfilled)
```

### 2.1. Драйвер: `IImageGenerator`

[IImageGenerator.cs](../../backend/ClaudeHomeServer/Services/Images/IImageGenerator.cs) —
контракт из пяти членов: `Key` (`fal` | `glif`), `DisplayName`, `Enabled` (есть ключ/токен),
`Models` (курируемый каталог для пикера) и
`GenerateManyAsync(prompt, count, model, ct)`. Общие типы — `GeneratedImage(Bytes, ContentType)`
и `ImageModelInfo(Id, DisplayName, Description?)`.

**Отказ драйвера — пустой список, а не исключение.** На этом договоре стоят и роутер (он
понимает «не смог» без разбора ошибок), и вызывающие контроллеры (внятный отказ вместо 500).

Регистрация — одна строка `AddImageDriver<T>()` в
[ImageGenerationRegistration.cs](../../backend/ClaudeHomeServer/Services/Images/ImageGenerationRegistration.cs):
драйвер отдаётся и по своему типу, и в набор `IEnumerable<IImageGenerator>`, который получает
роутер. Новый провайдер = новый класс + одна строка регистрации.

### 2.2. Драйвер fal.ai (синхронный)

[FalImageService.cs](../../backend/ClaudeHomeServer/Services/FalImageService.cs) — прежний
сервис под общим контрактом, поверхность сохранена (старые перегрузки `GenerateAsync`/
`GenerateManyAsync` без модели на месте).

- Транспорт: `POST https://fal.run/{model}`, заголовок `Authorization: Key {Fal:ApiKey}`,
  тело `{ prompt, image_size: "square", num_images: count }`; `count` клампится в 1…4.
  Именованный HttpClient `"fal"` (под ним висит тихий логгер, см. `AddQuietHttpClient`),
  таймаут 180 с. Картинка приходит ссылкой в `images[]` — скачивается в байты (обычный URL и
  `data:`-URL).
- `Enabled` = задан `Fal:ApiKey` (или переменная окружения `FAL_KEY`).
- Каталог моделей: `fal-ai/flux/schnell` (дефолт), `fal-ai/flux/dev` плюс модель из
  `Fal:ImageModel`, если админ вписал в конфиг что-то своё (иначе её нельзя было бы выбрать
  в интерфейсе).

### 2.3. Драйвер glif (асинхронный, с опросом)

[GlifImageGenerator.cs](../../backend/ClaudeHomeServer/Services/Images/GlifImageGenerator.cs) —
серверный путь без участия CLI-хода; транспорт тот же, что у `GlifAccountService`: JSON-RPC
`tools/call` на `https://glif.app/api/mcp`, `Bearer {Glif:McpToken}`, endpoint stateless (без
`initialize`), ответ приходит SSE-кадром либо чистым JSON.

- `compose_project { prompt, output_preference: "image", intelligence? }` сразу возвращает
  `jobId` и `pollIntervalSeconds`; готовое медиа забирается опросом `get_job_status { job_id }`.
- Интервал опроса — из ответа, с клампом 2…15 с (дефолт 5 с) и переопределением по ходу опроса;
  общий бюджет генерации — **180 с**, дальше отказ (на том конце ждёт человек).
- Схема `compose_project` — `additionalProperties: false`, лишних полей слать нельзя;
  параметра «сколько вариантов» у неё нет, поэтому при `count > 1` просьба о вариациях
  дописывается в текст промпта, а сколько реально пришло — покажет медиа готовой джобы.
- «Модель» у glif — **уровень агента** `intelligence`: `lite` / `smart` / `genius`. Саму
  модель под задачу glif подбирает сам, это его штатный режим.
- `Enabled` = задан `Glif:McpToken`.

Ответы разбирает
[GlifJobParser.cs](../../backend/ClaudeHomeServer/Services/Images/GlifJobParser.cs) — чистая
защитная функция: достаёт полезное из `structuredContent`, `_meta.glif`, JSON внутри
text-блоков и самого `result`; ссылки на медиа собирает из `media[]` и блоков
`resource_link`/`resource` с дедупом. Состояния сводит к четырём (`Unknown` / `Working` /
`Completed` / `Failed`); **незнакомый статус считается «ещё считается», а не провалом** —
полный словарь статусов glif не зафиксирован.

### 2.4. Роутер `ImageGenerationService`

[ImageGenerationService.cs](../../backend/ClaudeHomeServer/Services/Images/ImageGenerationService.cs) —
единственная точка входа генерации; прямой привязки к конкретному драйверу у вызывающих больше нет.

- **Порядок драйверов фиксирует сам роутер** (`ImageGenerationOptions.ProviderOrder` =
  `glif` → `fal`), а не порядок регистрации в DI. Glif впереди намеренно: в режиме
  «Автоматически» человек делегировал выбор модели, а подбор модели под смысл — штатный
  режим glif, тогда как fal идёт на одну модель из настройки.
- `Resolve(place)` строит цепочку исполнения **по месту**: **явный выбор → ровно один провайдер**
  (и только если он `Enabled`); **`auto` → все включённые в порядке `ProviderOrder`**, где второй и
  дальше — подстраховка на случай, когда предыдущий вернул пусто. Выключенные провайдеры в
  цепочку не попадают.
- `GenerateManyAsync` идёт по цепочке до первого непустого результата; параметры `provider` /
  `model` — разовое переопределение настройки (в продуктовом коде сейчас не используется —
  места генерации зовут роутер без них).
- Полезное для UI: `Mode`, `ActiveProvider` (кто пойдёт следующим запросом; `null` — генерация
  недоступна), `Enabled`, `ModelFor(key)`, `Providers`.
- `UpdateSettings` валидирует ключ провайдера и модель (только роутер знает состав драйверов) и
  возвращает текст ошибки либо `null`. Модель сверяется с каталогом драйвера; если каталог пуст,
  принимается любой id.

### 2.5. Настройка и её слои

[ImageGenerationSettingsStore.cs](../../backend/ClaudeHomeServer/Services/Images/ImageGenerationSettingsStore.cs)
— `data/image-generation.json`, `FormatVersion = 1`, снимок неизменяемый, запись целиком под
локом (образец — `FallbackSettingsStore`).

```
выбор админа (data/image-generation.json)
        ↓  пусто
секция конфига Images (appsettings*.json)
        ↓  пусто
auto  /  модель = дефолт самого драйвера
```

- **Патч-семантика** (как у `PUT /api/settings`): поле не прислали — оставить прежним,
  прислали `""` — сброс к слою ниже.
- Чтение файла регистронезависимо по именам свойств: стор пишет PascalCase, а руками файл
  правят в camelCase (ловушка `FallbackSettingsStore`).
- Файл с версией новее поддерживаемой (восстановленный из свежего бэкапа) не применяется —
  стартуем с дефолтов.
- Секретов файл не содержит: ключи провайдеров живут только в `appsettings.Local.json`.
  В бэкап попадает по общему правилу `BackupPaths.ShouldInclude`, исключений не требует.

### 2.6. Догоняющая генерация

Картинка появляется не мгновенно (у glif это принципиально: джоба опрашивается), а генератора
может не быть вовсе. Поэтому место живёт на инициалах, пока результат не придёт, — тот же
паттерн, что у фона проекта (ADR-008).

Файлы:
[ImageBackfillStore.cs](../../backend/ClaudeHomeServer/Services/Images/ImageBackfillStore.cs) ·
[ImageBackfillService.cs](../../backend/ClaudeHomeServer/Services/Images/ImageBackfillService.cs) ·
[ImageBackfillHostedService.cs](../../backend/ClaudeHomeServer/Services/Images/ImageBackfillHostedService.cs).

- **Очередь** — `data/image-backfill.json` (`FormatVersion = 1`). Заявка:
  `Kind` (`project-icon` | `persona-avatar`), `EntityId`, `OwnerId`, `Prompt?`, `Attempts`,
  `LastFailReason`, `CreatedAt`. Постановка идемпотентна: повтор на ту же сущность дубля не
  создаёт (обновляет промпт, если прислали новый).
- **Кто ставит заявки:** `ProjectsController` (иконка проекта), `PersonasController` и
  `OnboardingController` (аватар персоны) — в момент, когда генератор выключен или вернул
  отказ. У иконки нового проекта, которого ещё нет (`POST /api/projects/icon/generate-preview`),
  заявку ставить не на что — только честный отказ.
- **Идемпотентность прогона** держится на самой очереди: заявка снимается, как только у
  сущности появилась картинка, — неважно, сгенерировали её мы, человек выбрал кандидата или
  загрузил свою. Повторный прогон — no-op, генератор не дёргается.
- **Потолки:** не больше 2 генераций одновременно на инстанс (залп упёрся бы в rate limit
  провайдера), один владелец = один прогон, внутри прогона заявки идут последовательно.
  Повтор в рамках прогона — до 2 попыток с паузой 5 с, пожизненный потолок заявки — 5 попыток.
  Повторяются только транзиентные отказы: `no-image`, `network`, `io`.
- **Генератор выключен — заявки не трогаются вовсе:** сжечь на выключенном генераторе потолок
  попыток значит потерять картинку навсегда, а очередь заведена ровно ради этого случая.
- **Сохранение** идёт тем же путём, что ручной выбор кандидата: файл в каталоге ассетов
  сущности с cache-busting-именем (`icon-{guid}` / `avatar-{guid}`) + перевод иконки/аватара в
  режим картинки (`SetIconImage` / `SetAvatarImage`).
- **Фронту** уходит SignalR-событие `image_backfilled { kind, entityId }` в группу владельца;
  персонам вдобавок штатное `personas_changed` — раздел «Персоны» уже умеет его слушать.
  Иконку проекта фронт подхватывает без перезагрузки: разбор события — `lib/imageBackfill.ts`,
  форс-рефетч общего кэша проектов — `onProjectIconBackfilled` в `useAllProjects`, дальше сами
  обновляются список, открытое рабочее пространство и диалог иконки. Cache-busting держится на
  перечитывании DTO: у нового файла `icon-{guid}` другой `src`, старую картинку браузер не отдаст.
- **Триггеры по времени** (`ImageBackfillHostedService`): отложенный прогон через 30 с после
  старта сервера и тик каждые 10 минут. В среде `Testing` фоновый цикл не крутится (гейт
  `Testing:EnableHostedServices`). Программный триггер — `ImageBackfillService.KickOff(ownerId?)`.
- Промпты по умолчанию (для заявок, пришедших без своего) держатся в одной формулировке с
  ручной генерацией: `ProjectsController.BuildIconPrompt` / `PersonasController.BuildAvatarPrompt`.

## 3. Настройка в интерфейсе

**Где:** раздел «Модели и расход» → вкладка «Применение» → секция **«Картинки»**
([ImageGenSection.tsx](../../frontend/src/features/modelsSpend/ImageGenSection.tsx),
встроена в [ApplyTab.tsx](../../frontend/src/features/modelsSpend/ApplyTab.tsx)).

**Кто:** настройка задаётся **по местам** — отдельно «Иконка проекта», отдельно «Аватар персоны»
(ключи `ImagePlaces.All`: `project-icon`, `persona-avatar`). Требования к картинке у мест разные —
иконке нужна плоская эмблема, аватару портрет, — поэтому человек чинит то, что его не устроило,
не ломая второе. Внутри места настройка общая для инстанса, как остальные места вкладки
«Применение», — меняет её только админ. Читают все: диалоги иконки и аватара подписывают, кто и какой моделью
нарисует картинку, и без чтения подпись не отрисовать. Не-админ видит ту же секцию в режиме
чтения с пояснением «Генератор картинок общий для всех — его выбирает администратор».

**Что видно:** две строки настройки, по одной на место, с заголовками из `title` бэка
(«Иконка проекта», «Аватар персоны»). В каждой строке:

- три карточки выбора — **Автоматически** · **fal.ai** · **glif**. У «Автоматически» подпись
  «Сейчас пойдёт {провайдер}» либо «Ни один сервис не настроен»; у провайдера — его модель либо
  подсказка «Не настроен — впишите `Fal:ApiKey` / `Glif:McpToken` в appsettings.Local.json».
  Ненастроенный провайдер выбрать нельзя (карточка недоступна, сервер тоже отвечает 400);
- селект модели, активный **только при явно выбранном fal.ai**; первый пункт «По умолчанию» =
  дефолт драйвера. При «Автоматически» и glif селект неактивен с подписью «Генератор подберёт
  модель сам» — модель там выбирает сам генератор;
- если не настроен ни один сервис — «Генерация картинок недоступна: ни один сервис не
  настроен. Иконки и аватары придётся загружать вручную».

Сохранение оптимистичное: снимок пересчитывается на клиенте той же логикой, что `Resolve` на
бэке, и заменяется ответом сервера (`GET` и `PUT` возвращают одну и ту же форму, перечитывать
после записи не нужно).

**Подпись в местах генерации.** Кто именно нарисует картинку, видно там, где человек нажимает
«сгенерировать»: общий компонент
[ImageGenNote.tsx](../../frontend/src/components/ImageGenNote.tsx) (секция иконки проекта, форма
персоны, мастер создания персоны) читает ту же настройку и показывает «Рисует {сервис · модель}»
либо «Генератор выбирается автоматически — сейчас {сервис}», а при выключенной генерации —
«Генерация картинок выключена — добавьте ключ fal.ai или токен glif в настройках». Он же несёт
состояние ожидания («Иконка/Аватар рисуется — появится сам(а), можно продолжать») и отказ
«{Генератор} не ответил, картинка осталась прежней» с текстом ошибки от бэкенда и кнопкой
«Попробовать снова»: причину отказа фронт не придумывает. Пока настройка грузится, подпись
молчит — иначе мигало бы «выключена».

**Цену за картинку заранее не показываем.** Прайса в проекте нет, стоимость известна только по
факту: у fal она приходит в billing-событиях (`unit_price`), у glif — из ответа инструмента
(`GlifCostParser`). Фактический расход виден в карточках «Использование»
(`GET /api/fal/account` — баланс в USD и разбивка по моделям и дням; `GET /api/glif/account` —
план, баланс в кредитах, окна 24 ч / 7 д / 30 д).

## 4. Конфигурация

| Ключ | Где | Что задаёт |
|---|---|---|
| `Fal:ApiKey` | `appsettings.Local.json` | ключ fal.ai; пусто (и нет `FAL_KEY`) — драйвер выключен |
| `Fal:ImageModel` | конфиг | дефолтная модель fal (дефолт `fal-ai/flux/schnell`); попадает и в пикер |
| `Glif:McpToken` | `appsettings.Local.json` | токен glif; пусто — драйвер выключен |
| `Images:Provider` | конфиг | стартовый режим машины: `auto` (дефолт) \| `fal` \| `glif` |
| `Images:Models:{key}` | конфиг | модель по умолчанию у провайдера; пусто — дефолт драйвера |

Секция `Images` есть в отслеживаемом
[appsettings.json](../../backend/ClaudeHomeServer/appsettings.json) (общие дефолты) и в образце
[appsettings.Local.example.json](../../backend/ClaudeHomeServer/appsettings.Local.example.json).
Ключи провайдеров в секцию `Images` **не дублируются** — они остаются в `Fal` и `Glif`.
Значения секции — дефолты чистой установки: выбор админа в интерфейсе живёт в
`data/image-generation.json` и перебивает конфиг.

**Хранилища фичи:** `data/image-generation.json` (настройка) и `data/image-backfill.json`
(очередь). Оба едут в бэкап по общему правилу; ломающее изменение структуры любого из них =
инкремент его `FormatVersion` (правило `BackupSchema`).

## 5. Инварианты

1. **Явно выбранного провайдера подменять нельзя.** Не ответил выбранный glif — честный отказ,
   а не тихий переход на fal со счётом. Переход на другого провайдера возможен **только** в
   режиме «Автоматически» (`ImageGenerationService.Resolve`). Это та же логика, что принята для
   текстовых моделей: фолбэк по явно заданному порядку, автоподбора нет.
2. **Ненастроенный провайдер нельзя выбрать явно** — `PUT /api/image-generation` отвечает 400
   на входе, а не при первой попытке нарисовать иконку: фолбэка у явного выбора нет, и такая
   настройка означала бы молча неработающую генерацию.
3. **Настройка задаётся по местам, персонального слоя нет** — у каждого места (`project-icon`,
   `persona-avatar`) свой провайдер и своя модель, но внутри места выбор общий на инстанс, как
   у остальных мест вкладки «Применение». Патч трогает только присланные места; запрос без мест
   отвечает 400, а не сбрасывает настройку.
4. **Отказ драйвера — пустой список.** Исключения наружу не летят (кроме отмены снаружи);
   вызывающий сам решает, что показать человеку и ставить ли заявку в очередь.
5. **Картинка не теряется:** не получилось сейчас — сущность встаёт в очередь и получает
   картинку позже. Заявка снимается только по появлению картинки, исчезновению сущности или
   исчерпанию потолка попыток; на выключенном генераторе попытки не тратятся.
6. **Поле `generate` в ответах `icon/caps` и `avatar/caps` не переименовывать** — на него
   завязаны формы проекта и персоны на фронте.
7. **Секреты — только в `appsettings.Local.json`.** Ни настройка, ни очередь ключей не хранят.

## 6. Известные ограничения

- **Пресетов моделей под назначение нет.** Раздельный выбор по местам есть, но если у обоих
  мест выбран fal, разница между иконкой и аватаром держится только на промптах (плоская
  векторная эмблема против фотопортрета), которые собирают сами контроллеры.
- **Порядок режима «Автоматически» — `glif` → `fal`**, зашит в
  `ImageGenerationOptions.ProviderOrder`; настройкой не меняется.
- **Уровни агента glif (`lite` / `smart` / `genius`) в интерфейсе недоступны** — селект модели
  работает только для fal, у glif подбор отдан самому генератору. Драйвер их отдаёт, так что
  открыть выбор — правка одного пикера.
- **Признака «картинка ещё едет» у фронта нет:** заявки `ImageBackfillStore` наружу не отдаются,
  поэтому состояние «рисуется» в диалоге живёт только пока запрос в полёте. Закрыл и открыл
  диалог — увидишь результат лишь когда он придёт событием.
- **Окно гонки на обновлении иконки:** если запрос списка проектов уже был в полёте в момент
  события, форс-рефетч переиспользует его ответ, снятый до записи файла, — иконка догонит
  следующей загрузкой списка. Окно — доли секунды.
- **Число вариантов у glif — просьба, а не параметр:** сколько картинок вернёт джоба, заранее
  не известно (у fal `num_images` соблюдается точно).
- **Полный словарь статусов `get_job_status` не проверен** — точно встречались `working` и
  `completed`; неизвестный статус трактуется как «ещё считается», поэтому мёртвая джоба будет
  опрашиваться до общего бюджета 180 с.
- **Расход серверной генерации не попадает в `SpendStore`.** Учёт по `request_id` (`FalCostService`)
  и `GlifCostParser` работают на медиа, сгенерированные **в ходе чата** через MCP; иконки и
  аватары, нарисованные сервером, видны только в балансе и расходе аккаунта провайдера.
- **Догоняющая генерация не различает вид сущности при выборе провайдера** — идёт текущей
  настройкой инстанса на момент прогона, а не на момент постановки заявки.
