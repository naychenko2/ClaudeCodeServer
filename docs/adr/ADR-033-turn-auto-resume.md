# ADR-033: Авто-возобновление ходов после перезапуска сервера

**Статус:** Принято (D1 — документ; реализация — отдельной волной после ревью)
**Дата:** 2026-10-19
**Принимающие решение:** Андрей (владелец продукта), Александр (архитектор)
**Автор:** Софья (продакт-аналитик / оркестратор)
**Связанные артефакты:**
[SessionManager.cs](../../backend/ClaudeHomeServer/Services/SessionManager.cs)
(`TakeRestartResumeCandidates`, интеграция `KillAllProcesses`,
`AppendTurnAbortedAsync`), `TurnAutoResumeService` (новый —
`Services/Turn/TurnAutoResumeService.cs`), новый промпт в `ClaudeHomeServer.Prompts`,
[work_loop_stopped](../../frontend/src/components/chat/ChatItemView.tsx) (ветвь
`work_loop_stopped` инфо-пилюли)

## Контекст

Текущий запуск на ветке `master` валится и поднимается регулярно: выкатка
ADR-010, OOM под нагрузкой, питание машины, обновление CLI. Каждое падение
оставляет активный чат в статусе `Working` без живого CLI-процесса. После
старта пользователь видит в ленте инфо-пилюлю про «прерванный ход» и должен
сам нажать «Продолжить» — то есть ход, который шёл сам, без явного клика, и
оборвался по внешней причине, требует реакции человека. Это дефект опыта
пользователя и источник «потерянных» ходов после рестарта.

Дополнительный сигнал — инциденты 21–22.09: цикл выкатки и OOM, посреди
которых активный ход обрывался на середине инструмента (`Bash`, `Edit`,
`Write`). Транскрипт `~/.claude/{csid}.jsonl` в этих случаях цел, потому что
CLI пишет его инкрементально по каждому сообщению, и `--resume <csid>`
поднимает процесс с того же места; мы этим уже пользуемся для ручного
«Продолжить». Задача фичи — поднять ту же операцию автоматически для ходов
без явного визита пользователя.

Точка приложения — замена ручного триггера «Продолжить» на фоновую
проверку при старте сервера. Делать её нужно осторожно: автозапуск LLM
без явного действия пользователя с возможностью повтора неидемпотентных
действий требует жёсткого сторожа crash-loop и узкого набора исключений.

## Решение

### Сервис `TurnAutoResumeService : BackgroundService`

`TurnAutoResumeService` заводится как фоновый hosted-сервис. Его `ExecuteAsync`
стартует **после `ApplicationStarted`** и **после паузы прогрева**
`TurnAutoResume:WarmupSeconds` (по умолчанию 15 секунд, чтобы дать
`SessionManager` завершить десериализацию `sessions.json` и сторожам чатов —
`ADR-013` — закрепиться). После прогрева сервис берёт у `SessionManager`
снимок кандидатов через `TakeRestartResumeCandidates()` (одноразово,
очищается при выдаче) и обходит их с паузой `TurnAutoResume:GapSeconds`
(по умолчанию 5 секунд) между отправками. Потолок за один старт —
`TurnAutoResume:MaxPerBoot` (по умолчанию 10), остальные остаются в списке
до следующего рестарта либо ждут ручного «Продолжить».

Для каждого кандидата сервис шлёт «Продолжи» через штатный
`SendMessageAsync(auto, DeliveryCause.ServerRestartResume)` — путь
`--resume <ClaudeSessionId>` поднимается в `EnsureProcess` заново.
`DeliveryCause.ServerRestartResume` нужен, чтобы лог хода и причины
`isMeta` ясно показывали, что ход пошёл автоматически, а не по клику
пользователя; используем существующий `enum` причин доставки, не заводя
новый.

### Источник истины «оборван рестартом»

Реестр кандидатов на возобновление — **список в памяти текущего старта
сервера**, не новый файл состояния. Две развилки правды и так дают
расхождения, третья (`bootId`/`server-state.json`) нам не нужна.

Снимок собирает `SessionManager.LoadSessions` по правилу:

```
кандидат := (Working ИЛИ Working ∪ ShutdownInterruptedAt)
            И НЕ подходит ни под одно исключение v1 (см. ниже)
```

Конкретные правила:

- **Базовое множество** — все сессии с `Status == Working` из `sessions.json`.
- **Добавка** — сессии с `Session.ShutdownInterruptedAt != null` (этот снимок
  гасит `KillAllProcesses`, см. ниже).
- **Снимок `ShutdownInterruptedAt` ставит `KillAllProcesses` ТОЛЬКО для
  `Status == Working`**, не для `Starting` и не для `Waiting`. Иначе мы бы
  ловили в снимок чаты, которые сейчас поднимаются, и своими же руками
  ставили бы их в очередь на возобновление — конфликт с реально идущим
  `EnsureProcess`.
- **Снимок гасится сразу после захвата.** Иначе повторный старт (например,
  повторный OOM после первой попытки) оставил бы старых сирот в списке.
  На диск пишется тот же `SaveSessions()`, что уже вызывается из
  `KillAllProcesses`.
- **Наружу список выдаётся через `TakeRestartResumeCandidates()`** — метод
  одноразовый, очищается при выдаче. Повторный вызов тем же процессом
  отдаёт пустой массив.

### Гонка с маркером обрыва `AppendTurnAbortedAsync`

Сейчас `AppendTurnAbortedAsync` пишет маркер прерывания в транскрипт через
`_ = Task.Run(...)` — fire-and-forget. В авто-возобновлении это создаёт
гонку: авто-отправка «Продолжи» может уйти раньше маркера, и тогда в
истории окажется:

```
[user]: Продолжи (авто)
[assistant]: ...
[user]: [server_restart] ход был прерван
```

— то есть маркер приехал позже «продолжающего» сообщения и разрушил
контекст. Лечение — изменить контракт:

```csharp
public Task AbortMarkersWritten { get; }
public Task AppendTurnAbortedAsync(...);   // возвращает Task, не fire-and-forget
```

`TurnAutoResumeService.ExecuteAsync` обязан `await AbortMarkersWritten`
**до первого `SendMessageAsync`**. Для ходов с уже завершённой записью
маркера это no-op (`Task.CompletedTask`); для свежеоборванных это точка
синхронизации.

Это контрактное изменение, не новая сущность: существующие вызовы
`AppendTurnAbortedAsync` будут `await`-нуты в местах, где раньше
игнорировались (то есть всегда — fire-and-forget просто становится
`await`). Поведение продукта не меняется, кроме гонки выше.

### Сторож crash-loop

`Session.RestartResumeAttempts` — счётчик авто-запусков на сессии:

- **+1 при авто-отправке** (`TurnAutoResumeService` видит текущее значение,
  увеличивает, отдаёт в `SaveSessions`).
- **Сбрасывается в 0 на result любого хода** — нормальный финиш
  (`finished`/`error`/любой исход из `FallbackLlmSessionAdapter.ResolveNextTarget`)
  обнуляет счётчик. Сюда же входит финальный `turnOutcome` (`success`/
  `failed`/`crashed`/...).
- **Автоотправки нет, если ≥1 к моменту следующего старта** — в
  `Eligibility` для сессии стоит блок «`RestartResumeAttempts >= 1` →
  исключаем, остаётся баннер». Это лечит ход, валящий сервер сам
  (OOM посреди хода, рекурсивный crash-loop): первый старт отправил
  авто-ход, тот снова уронил сервер, второй старт видит счётчик ≥ 1 и
  не трогает сессию — пользователь должен разобраться руками.

### UX-карточка

Переиспользуем существующий `AddWorkLoopStoppedNoticeAsync(reason="server_restart", text=...)`.
`reason="server_restart"` — новое значение уже существующего `enum`
причин остановки рабочей петли. Канал доставки до пользователя —
инфо-пилюля в ленте чата через существующую ветку `case 'work_loop_stopped'`
в `ChatItemView.tsx:1988` (контракт с бэком стабильный, новых событий
не требуется).

Текст карточки — короткий, одна строка:

> «Сервер был перезапущен. Ход продолжен автоматически; если что-то пошло
> не так — нажмите «Продолжить» ещё раз.»

Гидратация аккумулятора `ChatContext` до вызова
`AddWorkLoopStoppedNoticeAsync` обязательна: метод молча выходит,
если контекст пуст, и без него карточка не покажется. Зависимость
от того, что контекст уже засеян после `ApplicationStarted` —
разумная, она совпадает с моментом, в котором `TurnAutoResumeService`
тоже начинает работать.

### Фич-флаг

Новый ключ `turn-auto-resume` в `FeatureFlagCatalog.All`, `default false`,
per-owner в `data/users.json`. Default false сознательно: это **автозапуск
LLM без явного клика пользователя** с возможным повтором неидемпотентных
действий — флаг первым обкатаем на себе, включая проверку, что карточка
видна и понятна.

Содержимое `FeatureFlag.Title`/`Description` — нейтральное, без обещаний
«волшебного спасения»:

> Автоматически продолжать ходы, прерванные перезапуском сервера. Включайте,
> только если понимаете риск повтора необратимых действий.

### Конфиг

```json
{
  "TurnAutoResume": {
    "Enabled": null,
    "MaxPerBoot": 10,
    "WarmupSeconds": 15,
    "GapSeconds": 5
  }
}
```

- `Enabled` — по умолчанию выключено; флаг `turn-auto-resume` берёт
  приоритет над конфигом (см. поведение per-owner в `FeatureFlag`).
- `MaxPerBoot = 10` — потолок автоотправок за один старт. OOM-инциденты
  21–22.09 показали: N одновременных CLI на старте — пик памяти
  (стартовая загрузка vLLM-слоя плюс мульти-CLI concurrency). Потолок и
  последовательная отправка обязательны.
- `WarmupSeconds = 15` — пауза после `ApplicationStarted` для прогрева
  `SessionManager` и сторожей чатов. Уменьшение — отдельная правка с
  замером.
- `GapSeconds = 5` — пауза между автоотправками. Смягчает одновременный
  разогрев нескольких CLI при N=10.

### Исключения v1 (сознательные)

Не возобновляем (одно общее правило `Eligibility.Reason` для метрик и
диагностики):

- **`Waiting`** — мы не выбираем за человека, чат ждёт явного ввода.
- **`TeamImplement != null`** (штаб «Командной реализации») — у него свой
  сторож волн, двойной перезапуск после падения волны даст несогласованное
  состояние штаба.
- **Групповые чаты** — v1 не трогаем, у них свой rejoin-цикл по членам
  группы.
- **Локальный проект при офлайн-устройстве** (`project.IsLocal && !deviceOnline`)
  — не возобновлять и не ставить в ожидание устройства: чат остаётся
  `Orphaned`. Если устройство онлайн — возобновляем как обычно. Инлайновых
  `if (IsLocal)` не заводим — единственная точка правды
  `ProjectCapabilities`.
- **Последний `tool_use` без result** — `deploy_start` / `deploy_rollback`
  (петля выкатки). Возобновлять запрещено: возобновлённый агент снова
  выкатит, и так по кругу. Условие проверяется на снимке транскрипта
  через существующий `TranscriptProbe.IsTailIntact` либо его аналог — хвост
  считается «битый», если последняя запись — `tool_use` без
  следующего `tool_result`.
- **`Starting`** — процесс ещё поднимается, снимок не ставится (`Status` не
  `Working`), не возобновляется.

### Промпт продолжения

В `ClaudeHomeServer.Prompts` — отдельная секция для причины
`ServerRestartResume` (например, `case "server_restart_resume"` в
общем промпт-конфиге). Текст:

> Сервер был перезапущен посреди твоего хода, транскрипт цел. Сначала проверь
> результат последнего действия — не повторяй вслепую то, что могло уже
> выполниться; затем продолжи задачу.

Это НЕ приказ «возобнови любой ценой» — это явное напоминание свериться
с состоянием. Иначе агент повторит `Write`/`Bash`/`deploy_start` вслепую,
и мы получим race-condition «было частично, потом стало дважды».

### Сценарии отказа и реакция

1. **Ход валит сервер сам.** OOM посреди хода или рекурсивный падеж. Сторож
   `RestartResumeAttempts >= 1` отбивает повтор на втором старте, чат
   остаётся в `Working` без автоотправки, пользователь видит баннер
   и жмёт «Продолжить» руками.
2. **Хвост с `deploy_start`** — последний `tool_use` без `tool_result`.
   `Eligibility.Reason = last_tool_use_unresulted_v1_excluded`,
   баннер остаётся.
3. **Битый транскрипт** — `TranscriptProbe.IsTailIntact` отказывает до
   отправки; баннер остаётся с явной причиной `transcript_corrupt`.
4. **Офлайн-устройство локального проекта** — `Eligibility.Reason =
   device_offline_v1_excluded`, баннер остаётся; не встаём в очередь
   на устройство.
5. **Resume упал по сети/модели** — фолбэк-цепочка ADR-007 → `error`;
   чат не зависает в `Working`. Сторож `RestartResumeAttempts` уже сброшен
   на этот момент, так что следующий старт снова сможет попробовать.

## Отвергнутые варианты

- **`bootId` и `data/server-state.json`** — вторая точка правды поверх
  `Status` и снимка. Конфликты записи при concurrent-стартах двух
  реплик (когда будем масштабировать), ничего не даёт на одну реплику.
  Статуса и `ShutdownInterruptedAt` достаточно.
- **Отдельный `ServerMessage` для авто-возобновления** — переиспользуем
  существующий `work_loop_stopped` с `reason="server_restart"`. Канал
  стабильный, фронт уже умеет, новых правил на `client.ts` не появляется.
- **`systemDirective`-доставка** — обходит `DeviceWaitGate` и ручной
  триггер пользователя в локальных проектах. Не используем: первое
  нарушает «человек разрешает запуск», второе — «устройство должно быть
  онлайн», и обход этих гейтов именно для авто-возобновления неуместен.
- **Возобновление `Waiting`** — мы не выбираем за человека; чат ждёт
  явного ввода не из-за рестарта, а по дизайну.
- **`MaxPerBoot = 0` / без потолка** — на инциденте 22.09 одновременный
  старт 8–10 CLI дал пик RSS > 16 ГБ. Потолок обязателен.
- **Сброс `RestartResumeAttempts` по таймеру, а не на result** — маскирует
  crash-loop, разрешает повторный авто-запуск того же валящегося хода
  через час. Не используем.

## Последствия (что НЕ решено)

- **Неидемпотентные действия при авто-возобновлении** — пользователь
  обязан понимать через карточку, что ход мог выполнить что-то, чего
  он не видел (например, `Bash` с `rm -rf` или `git push` мог отработать
  до того, как сервер упал). Это явная зона продакт-аналитики — текст
  карточки должен быть коротким и недвусмысленным.
- **Поведение зависит от `appsettings.Local.json`** (потолок `MaxPerBoot`).
  При больших N пауза растёт линейно: 100 чатов = 100 × `GapSeconds`.
  Это сознательно (OOM-инцидент), но требует документирования в
  on-call чек-листе.
- **Стоимость токенов** — автозапуск LLM без явного клика. Флаг
  `turn-auto-resume` обязателен, потому что иначе платный LLM стартует
  без явного сигнала «да, я оплачу этот прогон».
- **Сторож `MaxPerBoot` — на инстанс, не на чат.** Один зависающий
  ход занимает слот в `MaxPerBoot`, остальные ждут следующего старта.
  Это компромисс: снимать со счётчика мы не можем, потому что иначе
  неконтролируемо накопим CLI-процессы.
- **Не покрывает восстановление `deploy_start`** как мы и описали выше.
  Если пользователь поймал «хвост упал посреди выкатки», он жмёт
  «Продолжить» руками и руками же решает, что делать с полу-выкатанным
  состоянием.
