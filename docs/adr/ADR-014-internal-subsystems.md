# ADR-014: Внутренние подсистемы

**Статус:** Принято (этап 0 — контракт `IAppSubsystem` и пилот `VideoSubsystem`;
этап 1 — сторож `SubsystemBoundaryTests`; этап 2 — следующие вертикали
по готовности швов).
**Дата:** 2026-09-01
**Принимающие решение:** Андрей (владелец продукта), Александр (архитектор)
**Реализация:** Денис (бэкенд)
**Связанные артефакты:**
[IAppSubsystem.cs](../../backend/ClaudeHomeServer.Core/Services/Composition/IAppSubsystem.cs),
[VideoSubsystem.cs](../../backend/ClaudeHomeServer/Services/Video/VideoSubsystem.cs),
[SubsystemBoundaryTests.cs](../../backend/ClaudeHomeServer.Tests/Services/SubsystemBoundaryTests.cs)
(новый — рефлексия границ вертикалей)

## Контекст

`Program.cs` уже на старте этапа весил **1616 строк / 246 регистраций** в
Microsoft DI (на `master`). Это не «большой файл» — это симптом: одна точка
входа, в которой оказываются все разделы продукта (Video, Backup, Desktop,
Telemetry, Knowledge, Images, Tts, PersonAs, Tasks, Modules, …), и каждая
фича льёт туда новую порцию сервисов, hosted-сервисов и HttpClient'ов.
Три реальных проблемы из этого:

1. **Слабый сигнал «где граница».** Сейчас граница между разделами — комментарий
   `// === Раздел «Видео» ===` и порядок строк в файле. Через полгода никто не
   вспомнит, что именно «Видео» считается отдельным разделом и где его границы
   проходят.
2. **Расползание зависимостей.** Без явного контракта «вертикаль X зависит
   от Y» ссылка на чужой сервис появляется как один `using`, и обратное
   `using` тянется за ней — типичный сценарий: видео оказывается в зависимости
   от десктопа через общего соседа. Ловится это только регрессией.
3. **Стоимость добавления новой фичи.** Средняя новая фича трогает
   `Program.cs` + 3-5 файлов раздела + 1-2 контроллера + 1 миграцию `users.json`,
   и каждый шаг требует держать в голове «а ещё эту регистрацию надо добавить
   в Program.cs». Тяжело и легко пропустить.

Термин уже занят: «модуль» в проекте — это **внешний** модуль за YARP
(`Services/Modules`, манифест `module.json`, `ModuleRegistry`/`IModule`,
контракт в `docs/modules/integration-contract.md`): отдельный процесс за
реверс-прокси, своя регистрация, свой реестр. Внутренние границы — другое:
это регистрация ВНУТРИ Microsoft DI, без выгрузки, без hot-plug, без отдельного
процесса. Разделять эти два смысла одним словом нельзя: через полгода никто не
разберёт, о чём речь в тикете «вынести модуль в отдельную сборку».

Цель — завести отдельный термин **«подсистема»** (`IAppSubsystem`,
`Services/Composition/`), зафиксировать контракт и правило зависимостей
вертикалей, провести пилот на разделе «Видео» (где границы уже сложились)
и оставить дорожную карту для Desktop (настоящая цель, требует рефакторинга
трёх god-объектов) и отказ от Backup (там не вертикаль — срез поперёк).

## Решение

### Терминология

| Слово | Что значит | Где живёт |
|---|---|---|
| **Модуль** | Внешний процесс за YARP | `Services/Modules`, `docs/modules/integration-contract.md` |
| **Подсистема** | Внутренняя регистрация в Microsoft DI | `Services/Composition/IAppSubsystem` |
| **Вертикаль** | Раздел продукта (Video, Desktop, Telemetry, …) — логическая граница | Папка `Services/{Vertical}/`, контроллер(ы), свои модели |
| **Спина** | Общий слой, от которого зависят все вертикали: Microsoft DI, `McpSecretStore`, `Configuration`, модели в `Models/`, утилиты из `Services/Http/` и `Services/Security/` | — |
| **Шов** | Явный интерфейс на границе вертикали (например, `IDesktopChatDirectory`), через который она открывает другим вертикалям доступ к своему состоянию | `Services/{Vertical}/...I{Name}.cs` |

«Модуль» и «подсистема» — НЕ синонимы. В тикете, коммите и коде выбирается
одно из двух; смешение — дефект ревью.

### Контракт `IAppSubsystem`

```csharp
public interface IAppSubsystem
{
    string Key { get; }      // латиница, нижний регистр, уникально в процессе
    string Title { get; }    // человекочитаемое имя (логи, диагностика)
    void Register(IServiceCollection services, IConfiguration config);
}
```

Регистрация — через `IServiceCollection.AddSubsystems(config, params IAppSubsystem[])`:

- **Порядок важен.** Подсистемы более низкого слоя идут первыми, верхние —
  позже. Это та же модель, что `AddSingleton`/`AddHostedService` в самом
  Microsoft DI: кто первый, тот и «спина».
- **Дубликат `Key` — ошибка конфигурации.** `Telemetry:Backends` и
  `Telemetry:Alerts` не должны оказаться конкурентами за одну секцию;
  `AddSubsystems` бросает `ArgumentException` с понятным сообщением, а не
  проглатывает.
- **Пустой или null `Key` — ошибка регистрации.** `HashSet.Add(null)` упал бы
  с неинформативным NRE изнутри таблицы, а две подсистемы с пустым ключом
  дали бы тот же «дубликат», не отличая смысловой конфликт от недозаполненности.
- **`Register` вызывается один раз** при сборке контейнера. Подписчиков
  на события жизненного цикла у подсистемы нет: всё, что нужно
  сконфигурировать (`AddSingleton`/`AddHostedService`/`AddHttpClient`),
  делается в `Register`. После `Build()` подсистема как объект
  выбрасывается — она НЕ singleton-сервис.

Контракт жёсткий, расширение через дополнительные методы — отдельный вопрос
(пока не нужен: один раз зарегистрироваться достаточно).

### Контракт v1.1 — что добавилось при выделении следующих подсистем

Версия 1.0 (этап 0) закрыла один интерфейс и один сторож. К моменту массового
выделения (этап 2+) разведка по 15 вертикалям 2026-09-02 выявила четыре общих
элемента, которые нужны ДО того, как переносить следующую подсистему. Они
оформлены как аддитивное расширение v1.0 — без поломки контракта этапа 0.

1. **Хелпер hosted с Testing-гейтом** —
   `SubsystemHostingExtensions.AddGatedHostedService<T>` /
   `.AddGatedHostedFrom<T>`. Семантика скопирована 1-в-1 из локальных функций
   `AddHosted<T>` / `AddHostedFrom<T>` в Program.cs:121-130: в Testing-среде без
   явного `Testing:EnableHostedServices=true` hosted НЕ регистрируется.
   Это та же логика, что в `Services/Images/ImageBackfillHostedService.cs:20-24`
   (там её копировали вручную — после v1.1 копия не нужна, и подсистема просто
   зовёт `AddGatedHostedService` из `Register`). В Program.cs локальные функции
   удалены: те же 25+ регистраций теперь идут через extension-метод, поведение
   продукта не меняется.

2. **Общая форма резолва каталога данных** —
   `SubsystemHostingExtensions.ResolveDataDir(IConfiguration, params string[])`.
   До этого три вертикали (`Services/CodeGraph/GraphPersistence.cs`,
   `Services/Dossiers/DossierStore.cs`, `Services/Knowledge/WorkspaceKnowledgeStore.cs`)
   дублировали один и тот же сниппет `Path.GetDirectoryName(Path.GetFullPath(
   config["DataPath"] ?? …))`, плюс он встречался в двух местах Program.cs
   (пост-билд и handle-migration). В этой задаче хелпер только СОЗДАН; три
   существующих места не переписываются — миграция пойдёт по мере выделения
   их подсистем, иначе правка dataDir-логики смешалась бы с выделением.

3. **Опциональная app-фаза** — отдельный интерфейс
   `IAppPhaseSubsystem : IAppSubsystem { void ConfigureApp(WebApplication); }`,
   плюс `AddSubsystems` дополнительно регистрирует каждый инстанс как
   `services.AddSingleton<IAppSubsystem>(s)` (чтобы набор был доступен после
   `Build()`), и метод `SubsystemRegistration.UseSubsystems(this WebApplication)`
   зовёт `ConfigureApp(app)` в порядке регистрации для тех, кто реализует
   `IAppPhaseSubsystem`. В `Program.cs` после `var app = builder.Build()` и ДО
   всех прочих пост-билд инициализаций добавлен `app.UseSubsystems()` —
   подсистемы получают шанс сделать свою работу раньше, чем её увидят
   пост-билд шаги (например, Knowledge MigrateFromProjects).
   Отдельный интерфейс (а не DIM на `IAppSubsystem`) — потому что DIM в
   проекте уже ломал Moq (см. комментарии в `ILlmSessionAdapter.cs`).
   Подсистемы без `IAppPhaseSubsystem` продолжают работать как раньше: их
   `Register` отрабатывает, фаза их не трогает.

4. **Сторож границ на много вертикалей** —
   `SubsystemBoundaryTests` перестроен из захардкоженного Video-теста в
   табличную форму. Запись `VerticalBoundary(VerticalName, NamespaceRoot,
   AllowedNamespacePrefixes)` и `IEnumerable<object[]> Boundaries` с одной
   записью (Video — белый список перенесён как есть). Новые подсистемы
   добавляют ОДНУ строку в таблицу. `[Theory]` + `[MemberData]` прогоняет
   все записи одинаковым набором рефлексии.

Ссылка на заметку разведки: «Матрица подсистем — разведка 15 вертикалей
(2026-09-02)» в `notes/` проекта.

### Уточнение оценки Desktop

Разведка 2026-09-02 показала, что оценка этапа 0 («рефакторинг трёх
god-объектов») была завышена. Реальный объём:

- **Врастание Desktop в SessionManager — 1 тип / 3 строки**:
  `Services/SessionManager.cs:564` сам делает
  `new Desktop.DesktopCapabilityTokenService(jwt)` в конструкторе. Достать —
  зарегистрировать `DesktopCapabilityTokenService` в DI и принимать его в
  SessionManager через конструктор. Это не рефакторинг god-объекта, это
  переход от `new` к DI, ~3 строки диффа.
- **Готовый шов найден**: `IDesktopTurnGate`
  (`Services/Llm/DesktopServerLocator.cs:25-39`) — контракт «десктопный ли
  чат + выпуск capability-токена на ход». Реализация не зарегистрирована,
  но сам контракт лежит рядом с рантаймом ходов, и именно через него
  SessionManager сможет узнать «десктопный ли чат» без знания про Desktop.
  Это убирает прямой импорт `Services/Desktop` из `Services/Llm`.
- **JwtService всё ещё знает про `DesktopCaller`** (этап 0 фиксировал),
  и ClaudeSession всё ещё инъектит desktop-MCP-сервер. Эти два врастания
  остаются, но на фоне найденного шва IDesktopTurnGate они выглядят
  меньше: первый рефакторинг убирает 1 импорт + добавляет конструктор,
  второй переезжает на `IDesktopMcpContribution` (отдельная задача).

Desktop по-прежнему не блокирует остальные подсистемы — следующая волна
выделения (Images / Tts / Telemetry / Dossiers) идёт независимо.

### Правило зависимостей вертикалей

**Вертикаль зависит от спины и швов, но НИКОГДА от другой вертикали.**

- **Спина** (`Microsoft.*`, `System.*`, `ClaudeHomeServer.Models`,
  `ClaudeHomeServer.Services.Http`, `ClaudeHomeServer.Services.Security`,
  общие утилиты) — общий слой, от которого зависят все. Зависимость на спину
  в обе стороны безобидна: это контракт проекта, а не граница.
- **Шов** (`IDesktopChatDirectory`, `IVideoProvider`, `IKnowledgeCatalogService`…)
  — явный интерфейс, через который вертикаль открывает другим доступ
  к своему состоянию. Зависимость на шов — это и есть разрешённая связь.
- **Другая вертикаль напрямую** — запрещена. `Services/Video` не имеет права
  импортировать тип из `Services/Desktop`, и наоборот. Нужна связь — два пути:
  1. **Событие шины** (`TurnEventBus`, [ADR-013](ADR-013-turn-event-bus.md)).
     Подходит для фактов и для правок по ходу (`turn/completed`,
     `prompt/assembling` и т.п.) — там, где подписчик не обязан блокировать
     вызывающего.
  2. **Явный шов.** Подходит для синхронного запроса состояния
     (`IDesktopChatDirectory.CanHands(sessionId)`). Шов регистрируется в той
     вертикали, которой принадлежит состояние, и импортируется той, которая
     его читает.

Удерживается тестом `SubsystemBoundaryTests`
([`Services/SubsystemBoundaryTests.cs`](../../backend/ClaudeHomeServer.Tests/Services/SubsystemBoundaryTests.cs)) —
рефлексия по сборке, проверяет что типы из `Services/Video` не ссылаются
на типы из `Services.Desktop`, `Services.Backup`, `Services.Knowledge`,
`Services.Personas`. Источник правды — сборка, а не текст: один из существующих
стражей (`McpToolsetStabilityTests` через `FindSource` и `MethodBody`) сломался
на прошлом этапе от простого переименования метода, и пришлось чинить отдельной
задачей. Рефлексия полей/конструкторов/свойств/методов (declared-only + public)
с раскрытием generic-аргументов и `Nullable<T>` ловит оба направления:
«не вызывай чужой сервис» и «не держи поле чужого типа».

Тест осознанно не проверяет **интерфейсы и базовые классы** за пределами
четырёх мест ниже. Расширение (новые пары вертикалей, проверки унаследованных
членов) — отдельный шаг.

### Решение НЕ переходить на сборки и `AssemblyLoadContext`

Соблазн «разделить подсистемы по сборкам» понятен — DeepSeek Harness держит
50 пакетов, выглядит как образец модульности. Три причины не делать этого
в нашем стеке:

1. **Microsoft DI не выгружает контейнер по конструкции.** `AssemblyLoadContext`
   умеет выгружать сборки, но DI-контейнер — единый объект на процесс, и
   выгрузка одной его части означала бы выгрузку всего. Сборки без выгрузки —
   это и есть текущая ситуация, только в ней появляется лишний indirection
   (отдельный проект, отдельный `.csproj`, отдельная публикация NuGet
   in-tree пакета) без выигрыша.
2. **Отдельные сборки ломают сторожей границ, опирающиеся на одну
   сборку.** Пилот `feature/csproj-pilot` это подтвердил: три страж-теста
   (`SubsystemBoundaryTests`, `RootSubsystemBoundaryTests`,
   `SubsystemBoundaryCoverageTests`) читали `typeof(VideoSubsystem).Assembly`
   и после выноса вертикалей сканировали только Video — для остальных
   вертикалей нарушения перестали ловиться молча, тесты оставались
   зелёными. Пришлось переводить их на перебор
   `AppDomain.CurrentDomain.GetAssemblies()`. Прежняя формулировка пункта
   («`InternalsVisibleTo`, на котором стоят все тесты») — фактически
   неверная: атрибут используется точечно (`FileLog`, `FileWatcherService`),
   пилот его почти не задел, и каждый test-project в .NET имеет
   собственный `InternalsVisibleTo` — это стандартная практика, а не
   проблема. Реальная цена разноса — именно в страж-тестах, которые
   завязаны на «всё в одной сборке».
3. **У DeepSeek Harness 50 пакетов потому, что в pnpm-монорепе пакет ничего
   не стоит** — это структурная папка с `package.json` и `tsconfig.json`,
   она не линкуется, не подписывается, не собирается отдельно. В .NET
   сборка — это артефакт со своей версией, своим NuGet-манифестом, своей
   подписью и своим местом в `bin/`. Каждая такая граница съедает
   5–15 секунд сборки и 1–2 МБ в `bin/`, и за пять подсистем мы получим
   замедление `dotnet build` без выигрыша в изоляции (см. п. 1).

Когда (если) потребуется реальная изоляция — отдельные процессы через
**внешние модули YARP** (`Services/Modules`, `IModule`/`ModuleRegistry`).
Это та точка, где «модуль» оправдан; внутренние подсистемы — нет.

### Пилот физической изоляции (2026-09, ветка `feature/csproj-pilot`)

Контракт `IAppSubsystem` оставляет вертикали в одной сборке, но
соблазн вынести их в отдельные `.csproj` остаётся — пилот должен был
проверить, есть ли реальный выигрыш на инкрементальной сборке, и при
каких условиях он окупается. Ветка `feature/csproj-pilot` (worktree
`wt-csproj-pilot`, коммиты `803f9aee`…`90182517`) жива как артефакт
исследования, в `master` не мержена.

#### Что мерили

Пилот вынес Video/Yandex/Reader и их юнит-тесты в отдельные `.csproj`.
Потребовалось выделить `ClaudeHomeServer.Core` (контракт `IAppSubsystem`,
Http-утилиты, `SsrfGuard`, `McpSecretStore`, `JsonFileStore`) — иначе
вертикали не компилировались, цикл разрешён как Main → Vertical → Core.
Полный реестр перенесённого — в
`docs/research/csproj-pilot-measurements.md` (ветка пилота).

#### Первый замер был ошибочным

Первичные цифры `B2`/`B3`/`B4` оказались замаскированными no-op сборками:
правка файла в исходном протоколе не приводила к перекомпиляции. На это
указывала аномалия **B2 (1.59) ≈ B3 (1.69) ≈ B6 no-op (1.71)** — три
разных сценария не могут стоить одинаково в монолите, где любая правка
`.cs` инвалидирует всю `ClaudeHomeServer.dll`. Baseline `B4 = 2.57с`
невоспроизводим в принципе: нижний предел этой команды (запуск без
единой правки, всё актуально) — **5.12с**. Именно на этом числе
держался ложный вывод «B4b даёт +105%, изоляция не окупается».

Методическая мораль зафиксирована для следующих замеров: фиксировать
факт перекомпиляции (timestamp `obj/**/*.dll`), чередовать замеры
base/pilot в одном worktree-сеансе (дрейф загрузки машины иначе
съедает разницу), гонять **5 прогонов** вместо 3.

#### Корректные цифры (перезамер чередованием, 5 прогонов, медиана)

| Сценарий | Baseline | Пилот | Δ |
|---|---|---|---|
| Правка вертикали → build | 5.09 | 2.52 | **−50%** |
| Правка вертикали → её тесты | 8.94 | 5.52 | **−38%** (−57% после снятия `Video.Tests → main`) |
| Правка спины → build | 5.20 | 5.93 | +14% |
| Полный билд с нуля | 10.91 | 11.81 | +8% |
| No-op сборка | 1.70 | 2.51 | +0.8с |

**Изоляция работает.** По timestamp артефактов правка вертикали
пересобирает только `ClaudeHomeServer.Video.dll`, `ClaudeHomeServer.dll`
не трогается; правка спины — наоборот, только main. Главный цикл
разработчика «правка вертикали → её тесты» стал быстрее в 1.6 раза
(8.94 → 5.52с), а после снятия ссылки `Video.Tests → main` (нужна
одному файлу — `VideoFavoritesTests.cs` использует `UserStore` как
фикстуру) — в 2.4 раза, ~3.8с.

#### Почему всё равно не раскатываем — профиль правок

Изоляция на уровне компиляции работает, но это ещё не ответ на вопрос
«раскатывать ли». Ответ даёт профиль правок. По git-истории за три
месяца (1324 коммита с правками `backend/`):

- **2.6%** (35 коммитов) трогают исключительно вертикали — это и есть
  сценарий, где изоляция даёт −50%.
- **10.9%** (144 коммита) трогают вертикали вообще (вместе со спиной
  или только вертикали).
- Остальные **89.1%** правят только спину — здесь изоляция даёт
  +14% на инкременте и +8% на полном билде.

Если коммит трогает и вертикаль, и спину, выигрыш пропадает
(пересобирается main, тянет за собой вертикали). Матожидание по
профилю — **≈ +12% замедления**, а не ускорения: штраф платится на
каждом коммите, приз — только на 35 из 1324.

#### Решение и условие пересмотра

Волну 4 (раскатку изоляции на остальные 12 вертикалей) **не проводим**.
Решение привязано к условию, а не абсолютное: **порог окупаемости
≈ 25–30% правок в вертикалях** при текущих Δ. Пересмотреть, если:

- (а) профиль изменится — рост доли «вертикальных» коммитов,
  например, при выделении Desktop и его фич в самостоятельную ветку
  разработки;
- (б) спина будет расщеплена и перестанет быть единственной горячей
  зоной — например, после выделения `Llm.SessionManager` и `ClaudeSession`
  в отдельные сборки, доля «вертикальных» правок относительно горячих
  зон спины вырастет.

**Настоящая цель ускорения — расщепление `SessionManager`/`ClaudeSession`/
`Llm`** (три god-объекта спины), а не вынос вертикалей. Это и есть
Desktop-цепочка, которая остаётся отдельным треком.

#### Неденежная цена

Цена реальна, хотя и не в секундах:

- **`Core` рискует стать «кухней»** — в него переехали `IAppSubsystem`,
  `QuietHttpLogger`, `SsrfGuard`, `McpSecretStore`, `JsonFileStore` и
  слой `Services.Http`. Через Core вертикали видят половину инфраструктуры
  главного проекта, и граница «Core = минимум для вертикалей» уже
  размыта. Дальнейшее вынесение вертикалей потребует более жёсткого
  отбора, иначе Core станет свалкой.
- **Три сторожа границ** (`SubsystemBoundaryTests`,
  `RootSubsystemBoundaryTests`, `SubsystemBoundaryCoverageTests`) **сломались
  молча**: все три опирались на `typeof(VideoSubsystem).Assembly` и после
  выноса сканировали только Video-сборку. Для остальных вертикалей
  нарушения перестали ловиться, тесты оставались зелёными. Правка —
  переход на `AppDomain.CurrentDomain.GetAssemblies()` с исключением
  тестовой сборки (`ClaudeHomeServer.Tests`). Это та самая проблема,
  которая делает пункт 2 раздела «Решение НЕ переходить на сборки»
  содержательным — и на которой прежняя формулировка этого пункта
  фактически ошибалась.
- **Тестовые хелперы дублируются**: `TestConfig` × 3 (`Video`/`Yandex`/
  `Reader`-тесты), `FakeHostEnvironment` × 1. Мелкая цена обслуживания,
  но цена.
- **`Video.Tests → main`** (для `UserStore`) — тест-проект видит часть
  главной инфраструктуры, что отчасти смазывает выигрыш от изоляции
  (замерено: 1.49с на главном цикле, из них ~0.39с — сами UserStore-тесты,
  остальное — оценка графа main и копирование его замыкания в `bin`
  тест-проекта). Дёшево снимается переносом тестов `UserStore` в общий
  `Tests` — но это уже отдельная правка, не часть решения по волне 4.
- **`UnhandledExceptionHandlerTests.Callsite_*`** стали flaky после
  переноса `UnhandledExceptionHandler` в Core: JIT-инлайнинг
  чувствителен к расположению метода в сборке, и кадр `PiiRules.ComputeHash`
  в стек-трейсе сменился на `System.ArgumentNullException.Throw`.
  Известная категория stack-trace-зависимых флейков, не от архитектуры
  как таковой.

### Курс после пилота (2026-09-03)

Пилот закрыл вопрос «выносить ли существующие вертикали в отдельные
сборки»: ответ — нет (см. «Почему всё равно не раскатываем — профиль
правок» выше). Но это решение про **ретроспективный** перенос уже
существующих 15 вертикалей: профиль правок против (2.6% коммитов
трогают только вертикали, 89% — только спину, выигрыш Δ −50%
применяется только к этим 35 коммитам из 1324).

Экономика **проспективного** случая другая. Пока подсистема активно
разрабатывается, почти 100% её коммитов идут в неё саму — правка
контракта, тесты, регистрация. Если она рождается отдельным проектом,
−50% сборка и −38…57% цикл «правка → её тесты» применяются к КАЖДОЙ
такой итерации, а не к 35 из 1324. Плюс граница держится компилятором,
а не рефлексионным сторожем — это другая надёжность.

Решение пилота не противоречит этому: оно привязано к профилю правок
уже существующего кода. Новые подсистемы стартуют с другого профиля.
**Изоляция работает на проспективном случае — её просто невыгодно
применять к ретроспективному.**

#### Разделение решений

Решение по итогам пилота — это про ретро-перенос существующих
вертикалей, не про архитектурный курс в целом. Курс после пилота
складывается из двух встречных правил:

- **Существующие 15 вертикалей — не переносим.** Профиль правок
  против (см. таблицу Δ выше), и ретро-перенос требует вложений
  (швы, миграция тестов, обновление allow-list сторожей) без
  пропорционального выигрыша по времени разработки.
- **Новые подсистемы — рождаются отдельными проектами.** Каждая
  итерация попадает в «горячую фазу», где почти все правки внутри
  подсистемы — то есть именно тот сценарий, в котором Δ −50%
  сборка и −38…57% цикл «правка → тесты» окупаются с первого
  коммита.

Это не противоречие: экономика проспективного и ретроспективного
случаев разная, разница именно в доле правок, попадающих в вертикаль
за время её активной разработки.

#### Прецедент: разрез цикла `Llm ⇄ Execution` (2026-09-04, волна 4)

В волне 4 между двумя вертикалями (`Services.Llm` и `Services.Execution`)
вырос зависимый цикл, который не закрывался правилом зависимостей
напрямую, а только через allow-list сторожа. Цикл порождался реестром
корней транскриптов (`WorkflowAgentParser.TranscriptRoots`):
наполняли его `Llm`, `Execution` и константа, а читал `WorkflowController`.
Через один шов в спине `Llm ⇄ Execution` вытащить было нельзя — реестр
должны были знать и писатель, и читатель, а вертикали по правилу
не должны зависеть друг от друга.

Разрез пошёл по правилу: реестр, который наполняют разные слои, а
читает REST-гейт, кладётся в спину. Новый `Services/TranscriptRoots.cs`
(волна 4, коммит `451f59f3`) живёт в корне `Services/` именно потому,
что из `Llm` и `Execution` нужна только запись, а из контроллера —
только чтение; в подсистему ни одна из сторон реестр не забирала,
и позволить забрать — означало бы выбрать чью-то сторону. Заодно
`ClaudeCliLocator` уехал в `Services.Llm` (читался из `Execution`,
но по факту был инфраструктурой провайдера).

Лекарство от цикла между вертикалями — **разрез**, а не **запись
в allow-list**: запись легитимизировала бы зависимость, и следующая
правая сторож сломался бы снова на этой же паре. Разрез оставляет
правило в силе.

#### `Execution` — горизонтальный слой, не вертикаль

`Services.Execution` при разборе цикла был опознан как **горизонтальный
слой в низу стека**: у него 14 потребителей вне `Llm` (Git, Deploy,
Reader, Knowledge, …), и обращаться к нему через шару вертикалей =
ставить его в один ряд с Yandex/Video/Reader — неправда. Подсистемная
форма `Execution` (если когда-то потребуется) должна жить не в
`SubsystemBoundaryTests.Boundaries` как обычная вертикаль, а как
отдельный горизонтальный шов спины.

#### Core — что уже есть

Под новые подсистемы заложен общий слой. По коммиту `14e474de`
(волна 3, шаг 1) в репо добавлен проект
[`ClaudeHomeServer.Core`](../../backend/ClaudeHomeServer.Core/) — общая
инфраструктура, от которой зависят все вертикали. Состав по факту:

- **Контракт подсистем** и хелперы регистрации:
  [`IAppSubsystem.cs`](../../backend/ClaudeHomeServer.Core/Services/Composition/IAppSubsystem.cs)
  (`IAppSubsystem`, `IAppPhaseSubsystem`, `SubsystemRegistration.AddSubsystems` /
  `UseSubsystems`),
  [`SubsystemHostingExtensions.cs`](../../backend/ClaudeHomeServer.Core/Services/Composition/SubsystemHostingExtensions.cs)
  (хелпер hosted с Testing-гейтом, общая форма резолва data-каталога).
  Контракт v1.1 — аддитивное расширение v1.0, без поломки видевших
  вертикалей.
- **HTTP-утилиты**:
  [`QuietHttpLogger.cs`](../../backend/ClaudeHomeServer.Core/Services/Http/QuietHttpLogger.cs).
  Дефолтный логгер печатает каждый провал внешнего HTTP как Error
  со стектрейсом и забивает консоль — подсистемы сразу получают тихую
  форму через `AddQuietHttpClient`.
- **JSON-стор общего назначения**:
  [`JsonFileStore.cs`](../../backend/ClaudeHomeServer.Core/Services/JsonFileStore.cs).
- **Секрет-стор MCP**:
  [`McpSecretStore.cs`](../../backend/ClaudeHomeServer.Core/Services/Mcp/McpSecretStore.cs).
- **SSRF-гард** для исходящих запросов:
  [`SsrfGuard.cs`](../../backend/ClaudeHomeServer.Core/Services/SsrfGuard.cs)

Ноль `PackageReference`, `<OutputType>Library</OutputType>`,
`<EnableDefaultContentItems>false</EnableDefaultContentItems>`. Швы
(`ISessionDirectory`, `IUserDirectory` и т.п.) пока НЕ заведены —
добавляются по фактической потребности конкретной подсистемы, а не
впрок. Это и есть режим «сначала швы, потом рождение»: если новая
подсистема нуждается в шве, шов сначала появляется в Core (или в
спине, если ему нужна она), и только потом вертикаль выделяется
в проект.

#### Направление ссылок

`Main → Vertical → Core`. `Core` не ссылается ни на кого — нулевой
`PackageReference` это и держит (зависимости только на BCL/ASP.NET
через неявные global usings Web SDK).

`Main` видит проект подсистемы ради явного `new XSubsystem()` в
`AddSubsystems` — **сканирование сборок сознательно НЕ используем**
по двум причинам:

- **Потеря явности.** Без явного списка `new VideoSubsystem()` в
  `Program.cs` следующий разработчик не найдёт, где подсистема
  подключается, и не сможет быстро отключить одну вертикаль для
  отладки. Явный список — карта раздела.
- **Plugin-хрупкость.** Забытая DLL = молча отсутствующая
  подсистема, и сторож `SubsystemBoundaryCoverageTests` это не
  поймает без явного allow-list (как сегодня он ловит забытую
  строку в `Boundaries` для уже существующих реализаций).

`Vertical → Core` — вертикаль ссылается на инфраструктуру Core.
`Vertical → Vertical` — нарушение (default-deny в
`SubsystemBoundaryTests`).

#### Критерий «положен ли новой подсистеме свой проект»

Зависит от того, закрываются ли потребности подсистемы от спины
**существующими швами `Core` плюс максимум 1–2 новыми узкими
интерфейсами**.

- **ДА → рождается отдельным проектом.** Пример: подсистема хранит
  свой стор (`JsonFileStore` уже в Core), шлёт событие по шине
  (`TurnEventBus`, [ADR-013](ADR-013-turn-event-bus.md)), иногда
  дёргает `ICheapTextRunner` для одного фонового хода. Всё уже
  закрыто Core, или добавляется как один новый интерфейс в Core.
  Тогда — отдельный `.csproj` с первого коммита.
- **НЕТ → рождается в Main как раньше.** Если ей нужна половина
  спины (`SessionManager`, `ClaudeSession`, десяток менеджеров) —
  это честный сигнал, что фича на самом деле про спину, а не про
  отдельную вертикаль. Изолировать её преждевременно = тащить
  `Main → Vertical → Core → Main` стрелку обратной зависимости и
  убивать весь смысл изоляции.

Сам критерий давит в сторону проектирования узких швов: если
«нужна половина спины» — автор сначала заводит швы (`IDirectory`,
`IStore`, `INotifier`), а уже потом думает о выделении. Это и есть
тот же режим «сначала швы, потом переезд», который для ретро-переноса
зафиксирован ниже, в подразделе «Ретро-перенос существующей вертикали
как исключение» («Условие то же: сначала швы, потом переезд»).

#### Ретро-перенос существующей вертикали как исключение

Волну 4 (раскатку изоляции на остальные вертикали) **не проводим** —
это и есть вывод пилота, и он остаётся в силе. Но решение привязано
к профилю правок, а не абсолютное. Ретро-перенос **отдельной**
вертикали возможен, если она стала горячей.

Ориентир из разведки 2026-09-02 — поле «трогает только вертикаль,
без спины», последние 3 месяца:

| Вертикаль | Коммитов | Решение по умолчанию |
|---|---|---|
| Git | 39 | кандидат на ретро-перенос (тёплая) |
| Dossiers | 30 | кандидат (тёплая) |
| CodeGraph | 15 | пограничная (тёплая) |
| Video, Yandex, Reader, Images, Tts, Deploy, Backgrounds, ProjectIcons, Spend, Knowledge, Memory | <15 | остаются в Main до смены профиля |
| Watchdog | 3 | холодная, не кандидат |

Условие переноса — то же, что и для новой подсистемы: сначала швы
(в Core или в спине, если им нужна спина), потом выделение `.csproj`.
Горячая вертикаль, которой нужна половина спины, тоже остаётся в
Main — критерий швов общий.

#### Сторожа границ после Core

`SubsystemBoundaryTests` (коммит `14e474de`) и
`SubsystemBoundaryCoverageTests` (коммит `709190ae`) перестроены
из захардкоженного `typeof(VideoSubsystem).Assembly` (который до
выделения Core возвращал единственную `ClaudeHomeServer.dll` и тем
самым скрытно загружал Main) на перебор
`AppDomain.CurrentDomain.GetAssemblies()` с фильтром:

- `name == "ClaudeHomeServer"` — главная сборка (этапы 0/1 ещё не
  выносили вертикали);
- `name.StartsWith("ClaudeHomeServer.")` — Core и будущие вертикальные
  сборки;
- минус `ClaudeHomeServer.Tests` и `ClaudeHomeServer.Tests.*`
  (тестовые сборки, где живут `StubSubsystem`/`FakeSubsystem` —
  стабы `IAppSubsystem` в реестр продовых вертикалей не входят).

Это была реальная дыра. До multi-assembly-фикса сторож зависел от
порядка загрузки: если ни один тест в testhost до этого не тронул
Main, она не загружена, и сторож проходит **вакуумно** — выборка по
любой вертикали в Main будет пустой. Доказано мутацией в ревью
коммита пилота: **17/17 зелёных при нулевом наборе типов**. Статический
конструктор `SubsystemBoundaryTests` (`_ = typeof(VideoSubsystem).Assembly`)
форсирует загрузку Main и снимает гонку, но одной дисциплиной
тестов это не закрыть — нужны явные ассерты.

После фикса оба теста защищены:

```csharp
assemblies.Should().HaveCountGreaterThanOrEqualTo(2,
    "сторож должен видеть минимум ClaudeHomeServer и ClaudeHomeServer.Core");
allTypes.Should().NotBeEmpty(
    "сборки должны отдавать типы (ориентир замера — ~4230) — иначе " +
    "проверка полноты таблицы Boundaries ничего не проверяет");
```

и для каждой записи в `Boundaries`:

```csharp
types.Should().NotBeEmpty(
    $"вертикаль {boundary.VerticalName} ({boundary.NamespaceRoot}) " +
    "обязана иметь хотя бы один тип — иначе она исчезла/переименована, " +
    "а проверка границ ничего не проверяет");
```

Если фильтр сборок или порядок загрузки снова сломаются — оба теста
**упадут**, а не пройдут вакуумно. Это и есть гейт, который не даёт
«расширение до Core» в будущем молча сломать сторожей.

#### Video — пилот ✅

Самый чистый раздел: вертикаль уже сложилась, оставалось её только оформить.

- **1 исходящая зависимость:** `YouTubeOAuthService` принимает `McpSecretStore`
  (`Services/Video/YouTubeOAuthService.cs:21`). Это спина (`Services.Mcp`), не
  другая вертикаль — правило выполняется.
- **1 входящая мягкая:** поле `FavoriteVideoChannels` в `Models/User.cs:93`.
  Осознанная граница: вынос в собственный стор подсистемы сменил бы формат
  `users.json` и потребовал бы инкремента `BackupSchema.Version` — это
  отдельное решение, не часть пилота. Зафиксировано в шапке
  `VideoSubsystem.cs` как сознательный компромисс.
- **1 контроллер:** `Controllers/VideoController.cs`. Вынос тривиален.
- **0 `HostedService`:** фоновых задач у Video нет, миграция на `IAppSubsystem`
  не требует переноса циклов.
- **2 HttpClient'а с разными egress-настройками:** `SmotrimProvider`
  (`.WithoutEgressProxy()` — российский сервис) и `YouTubeOAuthService`
  (с прокси — YouTube за DPI). Их регистрация живёт рядом с самой подсистемой,
  и риск перепутать инвариант («СМОТРИМ без прокси, YouTube через прокси»)
  при следующей правке становится заметно ниже — комментарий в одном файле
  с обеими регистрациями.

  **Что НЕ покрывает текущий сторож** (`VideoSubsystemRegistrationTests`):
  он проверяет регистрацию двух `QuietHttpLogger` с разными `Category`
  (`ClaudeHomeServer.Video.Smotrim` / `.YouTube`) — это доказывает, что
  оба клиента зарегистрированы и не перетёрлись. Сам факт вызова
  `WithoutEgressProxy()` на нужном профиле сторож сейчас НЕ проверяет:
  рефлексия по `IHttpClientBuilder` не различает вызовы расширений,
  и для физической проверки прокси-флага нужен либо парсинг `Program.cs`/
  `VideoSubsystem.cs` на конкретный вызов (хрупко), либо отдельный тест,
  который собирает клиента и смотрит на его handler. Это отдельная задача.

Пилот оформлен в `Services/Video/VideoSubsystem.cs` и регистрируется в
`Program.cs` одной строкой `builder.Services.AddSubsystems(builder.Configuration,
new VideoSubsystem())`. После выноса Video подсистема сама делает **6 регистраций**
внутри (`AddMemoryCache` + 5 сервисных) — это и есть наблюдаемый вычет
из `Program.cs`. Конкретные цифры — в разделе «Метрика успеха».

#### Desktop — отложен, но это настоящая цель ⏳

Самая большая вертикаль проекта и самая запутанная. Три god-объекта, которые
держат её в собранном виде, делают выделение нетривиальным.

- **Объём:** ~3378 строк в `Services/Desktop/`, `Protocol/DesktopProtocol.cs`,
  `Hubs/SessionHub.cs` (часть про устройства) и **4 контроллера**
  (`DesktopAgentController`, `DeviceCallsController`, `DeviceSessionsController`,
  `DevicesController`). Не 3100 — цифра выросла с момента оценки.
- **God-объект 1: `SessionManager` сам делает
  `new Desktop.DesktopCapabilityTokenService(jwt)`** —
  `Services/SessionManager.cs:564`. `SessionManager` — это реестр сессий,
  и в нём не должно быть знания про capability-токены десктопа. Достать
  эту строку — рефакторинг `SessionManager` с переносом в
  `DesktopCapabilityTokenService` статической инициализации в DI.
- **God-объект 2: `JwtService` знает про `DesktopCaller`** —
  `Services/JwtService.cs:251,266`. Выдача и проверка capability-токенов
  живёт в общем сервисе JWT, и любая правка формата токена — это правка
  `JwtService`. Достать — отдельный `DesktopTokenIssuer`/`DesktopTokenValidator`,
  `JwtService` сократится до user-JWT.
- **God-объект 3: `ClaudeSession` инъектит MCP-сервер `desktop` в конфиг CLI** —
  `Services/Llm/Claude/ClaudeSession.cs:1498`, `servers["desktop"] = new JsonObject(...)`.
  `ClaudeSession` — общий рантайм всех ходов, и то, что он знает про
  десктоп-тулсет, означает: выключение desktop-флага в проекте не отзовёт
  сервер из конфига (см. CLAUDE.md, раздел «Десктопный агент», инвариант
  «`CancelForProjectAsync` обязателен»). Достать — делегирование
  регистрации desktop-MCP через шов `IDesktopMcpContribution`.
- **Готовые швы уже есть:** `IDesktopChatDirectory`,
  `IDesktopDeviceDirectory`, `IDesktopHandsNotifier`, `IDesktopCallCanceller`
  (`Services/Desktop/DesktopAccessGate.cs`, `DesktopHandsSessionService.cs`).
  Эти четыре интерфейса — точки, через которые Desktop открывает своё
  состояние другим вертикалям. За них и тянуть: вынести подсистему,
  оставить швы на месте, переписать три god-объекта на использование швов
  вместо прямого импорта.

Desktop выделяется **отдельной цепочкой задач** (не одной): сперва god-объекты,
потом `DesktopSubsystem.cs`, потом перерегистрация. Оценка — 4–6 задач-исполнителей
в общем дереве.

#### Backup — вычеркнут, не вертикаль ❌

Внутренняя проверка показала: Backup — не вертикаль, а **инфраструктурный срез
поперёк всех**. Изолировать его как подсистему = менять всю систему, а не бэкап.

- **`BackupValidation` десериализует 6 чужих моделей:** `Project`, `Session`,
  `Persona`, `TaskItem`, `ProjectGroup`, `DesktopDevice`. Это намеренно:
  бэкап проверяет целостность ВСЕХ сторов, а не своего подмножества.
- **`BackupPaths` ссылается на константы четырёх чужих сервисов** —
  имена файлов сторов (`data/projects.json`, `data/sessions.json`,
  `data/personas.json`, `data/devices.json`) он знает по константам, потому
  что хранилища эти имена объявляют сами.
- **`BackupSchema.Version` — глобальный счётчик формата ВСЕХ данных:**
  инкремент при изменении формата любого стора требует bump `BackupSchema.Version`,
  даже если Backup как код не менялся. Это by design: версия нужна, чтобы
  restore знал, что зеркало старого формата надо пересобрать.
- **`BackupCli.TryHandle(args)` и `InstanceLock.TryAcquireInstance` работают
  в `Program.cs` ДО построения DI** — `Program.cs:40` (`BackupCli.TryHandle`)
  и `Program.cs:84` (`InstanceLock.TryAcquireInstance`). Backup-режим
  (`--backup`/`--restore`/`--inspect`) обходит обычный запуск продукта:
  он не требует Kestrel, не регистрирует контроллеры, не открывает
  hosted-сервисы. Это естественная точка выхода из Program.cs, а не
  «ещё одна регистрация в `AddSubsystems`».

Изолировать = менять всю систему (вынести шесть моделей в отдельный «слой
сериализации», придумать как Backup узнаёт их формат без импорта типов,
завести отдельный счётчик версии на каждую вертикаль, переписать CLI-режимы).
Это не задача выделения подсистемы — это задача переустройства хранения.
Вердикт: **Backup остаётся как есть**, инвариант — если когда-нибудь
понадобится его подсистемная форма, начинать с хранилищ, а не с `Backup*`.

### Метрика успеха

Два измерения. Ни одно не «выполнено» в абсолюте — оба трекаются по
каждой новой подсистеме и по среднему диффу.

1. **`Program.cs` худеет.** Считается двумя способами, чтобы отделить
   вычет от пилота от вычета между пилотами:

   - **Строки файла:** `wc -l backend/ClaudeHomeServer/Program.cs`.
   - **Регистрации:** `grep -c 'builder\.Services\.Add' backend/ClaudeHomeServer/Program.cs`
     — каждая такая строка это отдельный вызов `Add*` (`AddSingleton`,
     `AddScoped`, `AddTransient`, `AddHostedService`, `AddHttpClient`,
     `AddMemoryCache`, `AddQuietHttpClient`, `AddSubsystems`, …).
     Паттерн пойман по префиксу `builder.Services.Add`, что совпадает
     с фактической формой всех регистраций в файле (у `Program.cs` это
     единственное место; чужой `services.Add*` за пределами подсистем
     не встречается).

   Базы — две разные точки; при сравнении важно понимать, какая из них
   имеется в виду:

   | База | | Строк | Регистраций | Когда мерить |
   |---|---|---|---|---|
   | **`master`** (до пилота Video) | | 1616 | 246 | когда сравниваем «общий прогресс» с момента заведения подсистем |
   | **Непосредственная база пилота** (`6f862b1f`) | | 1629 | 248 | когда сравниваем «вычет конкретно пилота Video» |

   На текущем `HEAD` (`feature/turn-event-bus-etap0`):

   - **vs `master`:** 1605 строк / 241 регистрация (Δ −11 строк, −5 регистраций).
     Разница в строках — это и пилот, и пара промежуточных правок
     (`AddPromptSectionContributors` и т.п.); Δ в регистрациях выглядит
     скромно, потому что пилот заменил 7 «внешних» регистраций
     на 1 вызов `AddSubsystems`, а 5 регистраций остались жить внутри
     `VideoSubsystem.Register`.
   - **vs базы пилота (`6f862b1f`):** Δ −24 строки, −6 регистраций от
     непосредственной базы пилота — это и есть чистый вычет самого
     пилота по `Program.cs`. VideoSubsystem сам делает 6 регистраций
     внутри (`AddMemoryCache` + 5 сервисных: `VideoOptions`,
     `YouTubeOAuthService`, два `IVideoProvider`, `VideoProviderRegistry`).
     Дополнительно отдельным MINOR-фиксом `AddMemoryCache` переехал
     в `VideoSubsystem.Register`, и общий счёт `Program.cs` стал ещё
     на единицу меньше (242 → 241 от базы пилота).

   **Цель** — уход под 1000 строк и 150 регистраций по мере выделения
   следующих вертикалей (Desktop даст ещё ~25 регистраций,
   Telemetry/Images/Tts — ещё ~40).
2. **Среднее число файлов, которое трогает новая фича.** Базовое значение
   сейчас: фича = 1 правка в Program.cs + 3–5 файлов раздела + 1–2
   контроллера + иногда миграция `users.json`. С подсистемами — фича = 0 правок
   в Program.cs + 1 файл подсистемы + файлы раздела. Цель — устойчиво ниже
   3 файлов на среднюю фичу в подсистемной вертикали (Video сегодня уже
   достигает: правки каталога идут в `Services/Video/`, `Program.cs`
   не трогается).

3. **Корень `Services/*.cs` (верхний уровень) — замер без цели.** Ряд
   с пунктом 1, но цели нет и в ближайшее время не предвидится (см.
   ниже). Считается так:
   `find backend/ClaudeHomeServer/Services -maxdepth 1 -name '*.cs' | wc -l`
   для числа файлов и
   `find backend/ClaudeHomeServer/Services -maxdepth 1 -name '*.cs' | xargs wc -l | tail -1`
   для строк. Снято с этапа 1, см. решение ниже.

### Решение: цель «корень `Services` < 15k строк» снята с этапа 1

Цель держалась в `research/services-root` (инвентарь + вердикт архитектора)
и в этот ADR не входила. Решение добавляется сюда, чтобы цели и их снятия
жили в одном месте.

**Что произошло:** разведка и разбор корня `Services/` (`bd03ef01`,
`497e38f1`) показали, что метрика меряет не ту величину. 69% корня — это
`SessionManager`, и догон «корня под 15k строк» ради абсолютной цифры
требует выносить его (или другие крупные god-объекты спины) — то есть
выводить код из-под сторожей границ, потому что god-объекты по определению
лезут в несколько вертикалей сразу.

**Решение.** Цель «корень `Services` < 15k строк» снимается с этапа 1.
Переносится на этап 4 — после того как будут расщеплены god-объекты
спины (`SessionManager`, `ClaudeSession`, `Llm`), которые сейчас и
составляют основную массу корня. До этапа 4 замер корня фиксируется
в `CLAUDE.md` без цели, как наблюдаемая метрика (рядом с `Program.cs`).

**Когда пересмотреть.** Если god-объекты спины будут расщеплены раньше —
этап 4 можно начать с их измерения против порога 15k. Если профиль
правок изменится (см. «Разделение решений» выше) так, что корень
начнёт расти от новых фич — порог может быть снят как нерелевантный
(метрика не отличает «кода в спине» от «спине место в подсистеме»).

Метрики не выносятся в Grafana/дашборд: тренд виден по `git log --stat` и
по размеру `Program.cs` (`wc -l backend/ClaudeHomeServer/Program.cs`).
Если кто-то хочет численную верификацию — `git log --oneline -- Program.cs |
wc -l` показывает количество коммитов, трогавших точку входа; цель —
уменьшение этого числа со временем.

### Практика коммитов в цепочке задач-исполнителей

Не архитектурное решение системы, но именно этот этап (четыре задачи подряд
с ручным выделением подсистемы) породил инцидент 2026-09-01, зафиксированный
правкой CLAUDE.md «Коммиты»: локальный коммит внутри worktree-задачи —
**часть критерия готовности задачи**, а не отдельная просьба пользователя.
Без него следующий исполнитель в цепочке стартует на грязном дереве,
и его дифф включает чужие правки — а это уже отдельный класс регрессий,
которые сторож `SubsystemBoundaryTests` не ловит. Закреплено письменно
рядом с архитектурным решением для удобства чтения, потому что здесь эта
практика возникла и здесь она проверяется.
