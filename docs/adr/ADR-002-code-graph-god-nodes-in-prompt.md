# ADR-002: God-nodes Code Graph в системный промпт хода

**Статус:** Принято
**Дата:** 2026-07-27
**Принимающие решение:** Андрей (владелец продукта), Александр (архитектор)
**Реализация:** backend — Денис
**Связанные артефакты:** задача `88801c80` (Code Graph: god-nodes в системный промпт),
[CodeGraphService](../../backend/ClaudeHomeServer/Services/CodeGraph/CodeGraphService.cs),
[CodeGraphPromptProvider](../../backend/ClaudeHomeServer/Services/CodeGraph/CodeGraphPromptProvider.cs)

## Контекст

В проекте уже строится граф зависимостей кода (CodeGraph, Wave 1/2: узлы — типы, рёбра —
Calls/Implements/References; REST `GET /api/projects/{id}/code-graph` + панель «Граф»). Но этот
граф **невидим Claude CLI** во время хода: процессу достаются только файлы проекта и системный
промпт. В результате на «холодном старте» понимания кода модель каждый раз заново открывает
файлы вслепую, не зная, какие типы — настоящие хабы связности (god-nodes), с которых логично
начать разбор. Граф уже посчитан, но его польза доходит до пользователя только через отдельную
панель, а не до самого рассуждения модели.

Силы и ограничения:

- **Инвариант состава `tools/list`** — MCP-инструменты входят в сигнатуру запуска CLI; их состав
  не должен зависеть от хода, иначе процесс перезапускается со всеми MCP-серверами
  («Stream closed», «No such tool available»).
- **Инвариант per-owner изоляции** — граф ключуется по `Project.RootPath`, принадлежащему
  владельцу сессии; межвладельческих утечек быть не должно.
- **Граф перестраивается с дебаунсом 15с** (`CodeGraphService`), поэтому дёргать построение на
  каждый ход нельзя — нужен кэш slice.
- **Существующий паттерн per-ход провайдеров** — `LlmSessionContext` уже склеивает в
  `combinedPrompt` блоки `RecallProvider`/`BindingsProvider`/`PersonaRecallProvider`
  (`ClaudeSession`, `--append-system-prompt`); добавить ещё один — наименьшее изменение.

## Решение

**Вариант A — per-ход slice в системный промпт.** Ввести в `LlmSessionContext` per-ход провайдер
`CodeGraphProvider: Func<string?, Task<string?>>` (по образцу `BindingsProvider`), который
возвращает compact-блок top-10 god-nodes для `--append-system-prompt`, или null. Источник данных —
`CodeGraphService.GetSnapshotAsync(rootPath)` (тот же, что у REST). Реализация —
`CodeGraphPromptProvider` (`Services/CodeGraph/`), регистрируется в `SessionManager` при создании
сессии (замыкая `rootPath`); per-owner получается автоматически — по корню проекта владельца.

```
## Структура кода проекта (Code Graph)
Базовые хабы по связности (top-10):
• ClaudeSession (Services/Llm/Claude/ClaudeSession.cs) — 87 связей
• LlmProviderRegistry (Services/Llm/LlmProviderRegistry.cs) — 29
• ...
Полный граф и поиск: панель «Граф» или GET /api/projects/{id}/code-graph.
[может быть устаревшим — файлы изменились]   ← только при isStale=true
```

**Кэш slice по сигнатуре builtAt.** graph.json переписывается (атомарно) только при перестроении
графа, поэтому его mtime 1:1 отражает смену `BuiltAt` — `GraphPersistence.GetCacheSignature`
возвращает этот mtime дёшево (без загрузки графа). Пока сигнатура та же, slice переиспользуется из
кэша `CodeGraphPromptProvider` без вызова `GetSnapshotAsync`; `isStale` досчитывается дешёвым
mtime-чеком (`CodeGraphService.IsStaleFor`) на каждый ход и добавляет soft-пометку, даже если граф
ещё не перестроен. Cap top-N = 10; формат — FQN + sourceFile + degree.

## Альтернативы

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| **A. Per-ход slice** (выбран) | compact top-10 в `--append-system-prompt` | виден модели **гарантированно**; наименьшее изменение (паттерн провайдеров есть); решает холодный старт «из коробки» | ~300 токенов на ход; slice фиксирован (не отвечает на конкретный вопрос) |
| B. MCP query/explain (lazy) | MCP-сервер графа с инструментом «объясни/найди» | модель зовёт точечно, ровно под вопрос; 0 токенов, если не нужно | LLM может **не позвать** (холодный старт не закрывается); +новый MCP-сервер/точка отказа; ломает инвариант `tools/list` (состав начинает зависеть от того, есть ли граф) |
| C. Гибрид (A + B) | slice + точечный query | максимум покрытия | заметно больше работы; A даёт ~80% пользы |

**Почему A:** гарантированно доходит до модели (не зависит от того, догадается ли она позвать
инструмент), закрывает именно холодный старт, минимально по изменению. B/C оставлены на Wave 3 —
если slice окажется маловат для конкретных задач.

## Последствия

- **+~300 токенов на каждый ход** проектной сессии с построенным графом (cap top-10; compоактная
  строка на узел). Стоимость сознательно принята ради закрытия холодного старта.
- **Per-owner** — автоматически через `rootPath` проекта владельца; для worktree-сессий (корень
  отличается от `project.RootPath`) граф может не найтись → провайдер вернёт null → блок молча
  пропускается (safe degradation).
- **Stale soft-пометка** — slice не блокирует ход и не врёт «актуально»: при изменённых .cs
  выводится `[может быть устаревшим — файлы изменились]`.
- **Кэш по builtAt** — граф не грузится на каждый ход; перестроение (debounce 15с) инвалидирует
  slice само (смена сигнатуры).
- **Отключаемо** — `CodeGraphProvider = null` (нет rootPath / провайдер не injecting в тестах) →
  блока нет; ошибки внутри провайдера → тихо null, ход идёт без блока.

## Follow-ups

- Измерить реальную помощь холодному старту (сокращение числа «вслепую» открытых файлов /
  времени до первого осмысленного действия).
- Wave 3: добавить MCP query/explain (вариант B), если slice top-10 недостаточен для точечных
  вопросов — держать инвариант `tools/list` (состав от хода не зависит).
- Мониторить рост стоимости/latency на репо >1000 файлов: граф больше, slice — тот же (cap top-10),
  но `GetSnapshotAsync` дорожает (переход на потоковую загрузку графа при необходимости).
- Порог god-узлов (`Core.CodeGraph.GodNodes`, minDegree=10) — при слишком «тощих» проектах slice
  не формируется; рассмотреть адаптивный порог, если это окажется частым.
