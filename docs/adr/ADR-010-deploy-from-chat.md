# ADR-010: Пересборка и переопубликация прода из чата

Статус: предложено · 2026-08-18 · автор: Александр (тимлид/архитектор)

## Контекст

Прод — хостовая публикация Windows: `deploy80.ps1` собирает фронт и бэк и кладёт всё в
`C:\deploy\claude`, сервер живёт под трей-супервизором `ClaudeHomeServer.Tray.exe`
(либо под внешним Runner `ClaudeServerTray.exe`). Выкатка сегодня — ручной запуск скрипта
на боевой машине. Хочется запускать её из чата самого прода и не остаться без прода,
если публикация не удалась.

Четыре факта определяют дизайн:

1. **Откатывать нечем.** `dotnet publish` пишет поверх `C:\deploy\claude`, прошлые
   бинарники не сохраняются. Снимок снимается только для `data` (`exe --backup`,
   шаг 0.5 скрипта). Неудачная публикация сегодня необратима.
2. **Сервер гасится раньше сборки.** Шаг 1 скрипта убивает процессы, шаги 2–3 собирают
   фронт и бэк. Ошибка компиляции = прод лежит всё время разбирательства.
3. **Чат прода — потомок сервера.** Чат работает через `claude.exe`, дочерний процесс
   `ClaudeHomeServer.exe`; трей при остановке делает `Kill(entireProcessTree: true)`.
   Деплой, запущенный прямо из чата, убивает собственного предка и обрывается на середине.
4. **Трей публикуется в ту же папку** (шаг 5 скрипта) — исполнителем деплоя быть не может,
   залочит собственный exe.

## Решение

**Сервер не деплоит себя.** Он проверяет права, пишет заявку и будит агента, который
не состоит с ним в родстве. Тяжёлая работа идёт при живом сервере, переключение —
короткое окно, здоровье проверяется автоматом, при провале агент сам возвращает прошлый
релиз. Результат новый инстанс подбирает из журнала на диске.

```
чат прода                ХОСТ (вне publish)
   |
   | POST /api/deploy   +-----------------------+
   +-----------------> | заявка + schtasks /run |
                       +----------+-------------+
                                  | (нет родства с сервером)
                          +-------v--------+
                          |  deploy-agent  |
                          +-------+--------+
  ФАЗА 1 (сервер ЖИВ):            |
    git-guard, npm build,         |
    dotnet publish -> staging,    |
    docker build sandbox          |
  ФАЗА 2 (окно 10-20 c):          |
    exe --backup (данные)         |
    stop tray + server            |
    bin -> releases\<stamp>       |
    staging -> C:\deploy\claude   |
    start tray                    |
  ФАЗА 3 (гейт):                  |
    health 3 раза / 90 с --ok--> готово
             |
             нет -> вернуть releases\<stamp>
                    -> start -> health
                    -> уведомление + пост в чат
```

### Компоненты

| Что | Где живёт | Зачем |
|---|---|---|
| `DeployController` | `Controllers/DeployController.cs` | приём заявки, статус, ручной откат; admin-only |
| MCP-инструменты `deploy_start` / `deploy_status` / `deploy_rollback` | `mcp/workspace-server` | поверхность для чата |
| `deploy-agent.ps1` | `C:\deploy\ccs-deploy\` — **вне** `PublishDir` | исполняет выкатку, переживает смерть сервера |
| Задача планировщика `CCS-Deploy` | Task Scheduler | разрывает родство процессов |
| Журнал `deploy-state.json` | `C:\deploy\claude.releases\` | единственная точка истины о ходе выкатки |
| Снимки релизов | `C:\deploy\claude.releases\<utc>\` | материал для отката |

### Почему именно так

- **Task Scheduler, а не detached-процесс.** `Kill(entireProcessTree: true)` строит дерево
  по `ParentProcessId`; процесс, порождённый планировщиком, потомок `svchost`, к серверу
  отношения не имеет. Трюк с промежуточным `cmd`, который «сразу умирает», держится на
  гонке — снимок дерева может успеть увидеть связь.
- **Копия релиза рядом, а не blue-green через junction.** Путь `C:\deploy\claude` зашит
  в `DockerPathMapper` (`{PublishDir}/mcp-dify`), ярлык автозапуска, `tray.json`, а рядом
  с бинарниками лежат `data`, `certs`, `appsettings.Local.json`. Переезд на схему
  `current -> releases\N` стоит дороже пользы; копирование каталога — секунды.
- **Сборка в staging до остановки.** Единственное изменение, которое убирает целый класс
  аварий: «не собралось» перестаёт быть инцидентом прода, а окно недоступности падает
  с минут до секунд.

## Контур Linux

Windows-контур остаётся прежним (см. выше). На Linux — отдельные путь и договорённости:
платформа другая, итого — другой exec, лок, формат побудки; логика, формат журнала и
грабли фаз те же. Детали скриптов — [scripts/ops/README.md](../../scripts/ops/README.md),
раздел «Linux: выкатка через deploy_start»; ниже — только то, что отличает контур и
почему он такой.

**Побудка — `systemd-run --user`, не `schtasks` и не `nohup`/`setsid`.**
Сервер запускает one-shot юнит и сразу возвращается:

```
systemd-run --user --collect --quiet --unit=ccs-deploy-<id> \
  -p ManagedOOMPreference=avoid \
  --setenv=CCS_RELEASES_DIR=<ReleasesDir> \
  <AgentDir>/scripts/ops/deploy-linux.sh
```

argv фиксированный: ни одного параметра заявки, никаких полей `current.request` в
командной строке — заявка целиком лежит в журнале. `<id>` — UTC-штамп вида
`YYYYMMDD-HHMMSS[-(N)]`, проверяется белым списком `^[A-Za-z0-9_-]{1,128}$`
(`DeployValidation.IsValidBuildId`) до подстановки в имя юнита, иначе CR/LF
стал бы инъекцией.

**Почему НЕ `setsid`/`nohup`.** Инцидент 2026-09-28 08:59 (лог 085902): `setsid`
сменил сессию, но не cgroup; оркестратор жил в scope `ccs-agents.slice` и умер на
шаге `stop ccs.service` (бэкенд при остановке гасит весь slice, а вместе с ним —
все идущие ходы). Switch остался посреди `stop`, прод лёг, никто не откатил.
Инцидент повторился 12.10. `systemd-run --user --collect` поднимает процесс в
СВОЁМ юните (по сути — `ccs-deploy-<id>.service`), к `ccs-agents.slice` он не
привязан: ccs.service останавливается, а юнит выкатки живёт дальше и доводит
swap до конца.

**`ManagedOOMPreference=avoid`** — вытащить сборку из-под `systemd-oomd`:
на той же машине рядом крутится vLLM, и при пиковой сборке фреймворка нельзя
быть первой жертвой нехватки памяти. У `ccs.service` стоит `omit`, что тоже
значимо (он первым не падает). На общий потолок `ccs-agents.slice` не
опираемся — оркестратор вне slice, лимиты cgroup его не действуют.

**Лок — файловый `flock -x`, не именованный мьютекс.** Один файл
`<ReleasesDir>/deploy.lock` держит оркестратор всё время работы; ручной запуск
`switch-release.sh` и `deploy_start` из чата сериализуются на нём. `flock`
реентерабелен через fork, но bash при `exec 9>file` на уже открытый fd считает
redirect noop'ом (тот же OFD уже залочен оркестратором) и второй `flock -n`
получает EAGAIN — поэтому номер fd передаётся в `switch-release.sh` через
переменную `CCS_DEPLOY_LOCK_FD`, и тот не переоткрывает лок.

Сервер ловит занятость на той же стороне через `IDeployAgentLock.TryAcquireDeploy`:
на Linux это `FileShare.None` на том же `deploy.lock`, .NET под капотом делает
`flock(LOCK_EX|LOCK_NB)` и EWOULDBLOCK превращается в исключение с HResult
`0x0000000B` — единственный случай, который `DeployAgentLockAdapter` маскирует
как «агент жив»; остальные IOException (нет прав, нет каталога, ENOSPC) и
`UnauthorizedAccessException` пробрасываются, чтобы `DeployService` ответил
честным отказом (`DeployStartStatus.LaunchFailed`), а не «другая выкатка идёт».

**Формат шагов и фаз.** Журнал `<ReleasesDir>/deploy-state.json` ведётся по
общему контракту ADR-010: фазы `queued → building → switching → verifying →
succeeded | rolled_back | failed`, шаги `build / snapshot / stop / swap /
start / health`, каждый шаг несёт длительность в мс (`DeployStep.Ms`). Имена
camelCase, история — 30 записей, `releases` отдельно, `current.request` агент
НЕ трогает.

**Один писатель журнала — `deploy-journal.py`.** Со стороны оркестратора
журнал правит ТОЛЬКО этот хелпер (атомарный `tmp + os.replace`), вызывается
через явный `python3 -I deploy-journal.py …` (на Linux `/usr/bin/env python3`
не пробрасывает флаги в shebang, поэтому env shebang — лазейка для
site-packages/user-site). Команды: `set-phase`, `set-step <name> <status> [ms]`,
`set-sha`, `set-rollback-target`, `finalize <status> [message] [releaseId]`.
Сервер пишет только заявку (`current` до побудки); отметка «доложено» — на
Linux хранится отдельным файлом `reported-<deployId>` в `ReleasesDir` по той же
причине, что и на Windows (общая запись двух процессов в `deploy-state.json`
теряется: переписывание журнала оркестратором во время `finalize` либо
затирало бы `result` агента, либо затирало бы отметку доклада).

**Отказ отката из чата — `Unsupported`.** `deploy_rollback` на Linux сознательно
не сделан: снимки живут в `/opt/ccs/releases/<метка>/`, автооткат внутри
`switch-release.sh` уже работает (ветка `health fail` возвращает предыдущий
снимок), а ручной кейс проще выполнить скриптом с явной меткой, чем тащить
состояние в чат. `DeployService.RollbackAsync` на `IsLinux=true` отвечает
`DeployStartStatus.Unsupported` («Откат из чата на Linux пока не поддержан —
откат вручную из /opt/ccs/releases (автооткат внутри switch-release.sh работает)»)
ДО записи в журнал — иначе карточка хода осталась бы «идущей» без агента.
Когда появится — раздел «Откат» ниже дополнится отдельным разделом.

## Что сознательно вынесено за рамки Linux-контура

- **Откат из чата на Linux.** См. предыдущий раздел: `DeployStartStatus.Unsupported`
  до записи в журнал; автооткат внутри `switch-release.sh` остаётся штатным.
- **Детализация шагов сборки внутри `publish-linux.sh`.** Скрипт сборки-в-staging
  отдельный (BUILD_FRONTEND/PUBLISH_DIR), оркестратор его зовёт одной строкой
  и пишет шаг `build` с ms; что именно `publish-linux.sh` делает (deps, фронт,
  бэк, mcp-dify, релиз агента устройства) — отдельный документ, и его шаги в
  журнал не лезут.
- **Сериализация отметки «доложено» на уровне ОС.** Файл-маркер — общая схема
  для Windows и Linux; кросс-процессная синхронизация через flock уже даёт
  нужное «один писатель» для самого журнала, отметка живёт рядом и пишется
  сервером, а не оркестратором — коллизий нет.
- **Полигон.** Тестовый контур есть (песочница с шимами `systemctl`/`systemd-run`),
  но в этой версии ещё не оформлен отдельным deploy-linux-test.md — пока живёт
  в [scripts/ops/README.md](../../scripts/ops/README.md).

## Контракт

### REST (все — `[Authorize]` + admin)

```
POST /api/deploy/start
  { ref?: string, skipFrontend?: bool, skipSandbox?: bool, allowDirty?: bool }
  -> 202 { deployId }
  -> 409 если выкатка уже идёт
  -> 400 если дерево грязное и allowDirty не задан (в теле — список файлов)

GET  /api/deploy/status  -> { current, history[], releases[] }
POST /api/deploy/rollback { releaseId? }  -> 202 { deployId }   // по умолчанию предыдущий
```

Права — политика `admin-by-store` (`AdminByStoreRequirement`), а не `[Authorize(Roles =
"admin")]`: заявка приходит из чата сервисным токеном MCP, а он выдаётся с ролью `user`
всегда — поднять его до `admin` нельзя, это открыло бы весь admin-периметр каждому
MCP-инструменту разом. Роль владельца токена проверяется по `UserStore` (он же источник
истины: роль в токене — слепок на срок его жизни).

`ref` — не переключение ветки: агент собирает рабочее дерево как есть и чужой `ref`
отклоняет. Валидируется белым списком `^[A-Za-z0-9._/-]{1,100}$`. Никакие другие поля запроса
в командную строку агента не попадают: набор флагов фиксирован. Эндпоинт исполняет код на
хосте под учёткой владельца — это граница привилегий, а не просто ручка.

### Признак «поднялся именно новый»

`GET /api/health` остаётся анонимным и отдаёт `204` (его пингует фронт — контракт не
трогаем), но получает заголовок `X-Build: <deployId>`. Проверка живого процесса по файлу
на диске не годится: файл лежит там независимо от того, какой exe сейчас запущен.

### Журнал `deploy-state.json`

```json
{
  "current": {
    "id": "20260818-141230",
    "phase": "verifying",
    "ref": "master", "sha": "4dc7ddab", "dirty": false,
    "initiatedBy": { "userId": "...", "sessionId": "..." },
    "steps": [ { "name": "frontend", "status": "ok", "ms": 41200 } ],
    "result": null, "reported": false
  },
  "history": [ ],
  "releases": [ { "id": "20260818-135500", "sha": "8e28cba9", "path": "..." } ]
}
```

Фазы: `queued -> building -> switching -> verifying -> succeeded | rolled_back | failed`.

**Отчёт о результате.** Чат-инициатор умирает вместе с сервером, поэтому докладывает уже
новый инстанс: читает журнал и при `result != null` и отсутствии отметки шлёт уведомление
(`NotificationService`) и сообщение в `sessionId`. Без этого «публикация не прошла» узнаётся
по молчащему сайту. Три уточнения, без которых доклад не доходит:

- **Поллинг, а не одно чтение на старте.** Агент ставит `result` ПОСЛЕ того, как поднял новый
  сервер (старт → health-гейт до 90 с → ротация снимков → запись итога), поэтому на старте
  итога в журнале ещё нет. Новый инстанс перечитывает журнал каждые 5 с в течение ~5 мин.
- **Отметка «доложено» — отдельный файл** `{ReleasesDir}/reported-{deployId}`, а не поле
  журнала: журнал целиком переписывает агент из своей копии в памяти, и общая запись двух
  процессов теряется (отметка затирается — доклад повторяется; либо затирается `result`).
  Поле `reported` в журнале остаётся только для заявок, закрытых самим сервером.
- **Срок годности итога — сутки.** Журнал живёт на диске месяцами; без предела рестарт через
  месяц отчитался бы о позавчерашней выкатке как о новости.

## Guard'ы

- **Грязное дерево** — `git status --porcelain` не пуст → отказ без `allowDirty`. HEAD sha
  и список файлов пишутся в журнал. (На 18.08.2026 в рабочем дереве лежат чужие
  незакоммиченные правки — ровно этот сценарий.)
- **Один деплой за раз** — мьютекс `Global\ccs-deploy`, по аналогии с `InstanceLock`. Он же —
  единственное доказательство «агента больше нет»: сервер берёт его, когда правит журнал после
  старта агента (свободен = писать безопасно).
- **TTL заявки** (`Deploy:StaleQueuedMinutes`, дефолт 15) — агент мог не приступить вовсе
  (задача планировщика не стартовала, сработал его guard), и запись навсегда осталась бы в
  `queued` = «выкатка идёт» = 409 на всё следующее. Просроченная и не сдвинутая с `queued`
  заявка закрывается как `failed` (под мьютексом) и следующая едет.
- **Живой Runner** — та же проверка, что в `deploy80.ps1`: два супервизора на порту 80
  ломают выкатку дважды.
- **Свободное место** — staging + `KeepReleases` снимков; проверять до начала, а не на
  середине копирования.

## Откат

**Код откатывается автоматом.** Не сошёлся health-гейт (3 успешных ответа за 90 с) →
агент гасит сервер, возвращает снимок релиза поверх `PublishDir`, стартует трей, проверяет
health ещё раз, пишет `rolled_back`. Не удалось и это — `failed` с явным текстом: дальше
нужен человек.

**Данные не откатываются никогда автоматически.** За минуты жизни новой версии в сторы уже
записались ходы пользователей и фоновые сервисы, а формат мог мигрировать — автоматический
`--restore` уничтожил бы свежие данные ради отката кода. Снимок `exe --backup` перед
выкаткой остаётся страховкой, восстановление — явное решение человека через меню трея.

## Что сознательно не делаем

- **Дренаж активных ходов.** Переключение режет идущие ходы. Правильно — перестать
  принимать новые и дождаться текущих, но это отдельная работа; в первой версии
  предупреждаем в ответе на `deploy_start`, сколько ходов сейчас активно.
- **Blue-green и нулевой downtime.** Окно в 10–20 секунд для домашнего инстанса дешевле,
  чем разнос путей и переезд `data`.
- **Выкатка контейнерного инстанса.** Механизм про хостовой прод; docker-путь живёт своей
  жизнью (`docker-compose.claude.prod.yml`).
- **Самообновление агента на лету.** Агент копируется из репы в свой каталог шагом 0 и
  запускается уже копией — скрипт не переписывает сам себя во время работы.

## Критерии проверки

1. Ошибка компиляции фронта — прод остаётся живым, статус `failed`, ни одна секунда
   недоступности не зафиксирована.
2. Новая версия стартует, но падает на старте — автооткат возвращает прошлый релиз,
   `X-Build` соответствует откаченному, в чат приходит отчёт.
3. Смерть сервера в момент фазы 2 **не убивает агента** — проверять явно, замером PID
   и дерева, а не «вроде отвязали».
4. Повторный `deploy_start` при идущей выкатке — 409, второй агент не стартует.
5. Грязное дерево — 400 со списком файлов; с `allowDirty` едет и пишет sha+dirty в журнал.
6. Ручной `rollback` на N-1 релиз поднимает прод и докладывает в чат.
