## Базовые возможности

- Auth: реальная аутентификация по API-ключу — `[Authorize]` на всех API + хабе.
  Ключ из `Auth:ApiKey` (env/config) или автоген в `data/auth-key.txt` (печатается в консоль).
  Клиент: `Authorization: Bearer` (REST), `?access_token=` (WS); 401 → авто-логаут.
  Удалённый доступ (Tailscale + HTTPS): [remote-access.md](../operations/remote-access.md)
- Проекты: CRUD, редактирование, выход
- Сессии: создание с именем/режимом/моделью, редактирование названия и модели (шапка чата + список), статусы (starting/active/waiting/finished/error)
- Чат: Composer (вложения, режим ⚡/📋/❓, голосовой ввод, стоп, «Claude печатает…»)
- Сообщения: text, thinking, tool_use (spinner), permission_request, file_changed, result, error+retry
- Empty states: нет сессий, пустой чат с подсказками, пустая папка, нет результатов поиска
- Файловый менеджер: дерево, поиск, просмотр/редактирование, diff/revert, бинарные, изображения, loading
- Несохранённые изменения: диалог при закрытии файла
- Экран не гаснет, пока идёт ход: планшет с открытым чатом засыпал посреди ответа, и
  человек возвращался к погасшему экрану вместо ленты. Блокировку
  ([wakeLock.ts](../../frontend/src/lib/wakeLock.ts), владелец `turn`) берёт реестр сессий
  по тому же признаку, что и poll реконсиляции — ход идёт **И** чат кто-то смотрит
  (`syncWaitPoll`), поэтому фоновые чаты экран не жгут, а стена и воркспейс покрыты одним
  условием (оба живут через `ChatPanel` → `useSession`). Ограничение самого API: держит
  только вкладку на переднем плане — уход в другое приложение планшет усыпит.
  Потолка по времени нет: зависший ход светит экраном, пока не кончится
- Непрочитанность чатов — гибрид: localStorage как optimistic-кеш (мгновенное гашение
  метки) + серверная отметка `Session.lastReadAt` (`PUT /api/chats/{id}/read`) для синка
  между устройствами; серверное значение приезжает обычным поллингом списков (5с).
  Чат непрочитан, если `updatedAt > max(локальная отметка, lastReadAt, baseline устройства)`.
  Отметка не двигает `updatedAt`; отправка на бэк затроттлена (leading + trailing, окно 5с),
  на бэке идемпотентна (`LastReadAt >= UpdatedAt` → без перезаписи файла).
  Логика — `frontend/src/lib/chatReadState.ts`, `SessionManager.MarkRead`

## Архив чатов

Мягкая альтернатива удалению: чат уходит из списка, но остаётся целым — история,
транскрипт claude CLI, теги и настройки на месте. Источник истины — `Session.ArchivedAt`
(момент архивации, не флаг): от него считается опциональная ретенция, а «когда убрал» —
единственный вопрос, который к архивному чату задают.

**Где кнопка.** Действие `archive` живёт в общем каталоге
[chatActions.ts](../../frontend/src/lib/chatActions.ts), поэтому появляется сразу во всех
местах, где чат вообще чем-то управляют: меню плитки в списке (`ChatCard`), шапка открытого
чата (`ChatHeaderBar`), колонка «Стены». По умолчанию спрятано в «⋯» и вытаскивается кнопкой
через глазик, как остальные действия. В каноническом порядке стоит **перед** «Удалить»
намеренно: дотянувшийся до края меню человек должен увидеть мягкий вариант раньше
необратимого.

**Где смотреть.** Кнопка `Archive` в шапке панели чатов (`ChatListToolbar`, все три ступени
+ мобильная) переключает список в архивный вид: там только архивные, над ними строка действий
[ArchiveNotice](../../frontend/src/components/ArchiveNotice.tsx) — «К списку» и «Очистить»
(удаление всего архива, с подтверждением). Пояснительного текста в строке нет намеренно: где
человек находится, видно по вдавленной кнопке в шапке, а подпись отъедала бы место у списка.
Непустой архив кнопка показывает серым кружком-счётчиком ([CountBadge](../../frontend/src/components/ui/CountBadge.tsx),
общий примитив с рельсой панелей; тон `muted`, потому что лежащие в архиве чаты ничего не
требуют). Сама кнопка видна всегда, даже при пустом архиве, — иначе про него нельзя узнать,
ни разу им не воспользовавшись. Архивный вид — **ось вида** в `ChatFilters` (`archived`), а не
чип фильтра: «Сбросить всё» его не трогает, иначе сброс фильтров молча выкидывал бы человека
из архива.

**Видимость самого действия.** «В архив» по умолчанию спрятано в «⋯» во всех трёх точках
(плитка списка, шапка чата, колонка «Стены») и вытаскивается кнопкой через глазик, как
остальные действия. Исключение одно: **у архивного чата «Вернуть из архива» стоит кнопкой
всегда**, на своём каноническом месте — прямо перед «Удалить», а глазика у этой строки нет
вовсе. На карточке оно идёт СВЕРХ потолка в три быстрые кнопки: вытеснять ради него «Удалить»
(соседа по смыслу) нельзя, а архивный список — редкий режим, где четвёртая кнопка ряд не ломает.
Иначе выход из архива пришлось бы искать по одному чату через «⋮» — притом что действие
спрятано по умолчанию.

**Инварианты:**

- **Архивация не двигает `UpdatedAt`** — по нему идут сортировка, секции дерева и
  непрочитанность. Иначе возврат из архива выбрасывал бы чат наверх списка непрочитанным,
  будто в нём только что был ход.
- **Повторная архивация не переставляет `ArchivedAt`** — от него считается ретенция, и
  «поархивировал ещё раз» не должно продлевать срок хранения.
- **Сообщение человека возвращает чат из архива** (`SessionManager.SendMessageAsync`): раз
  пишут — разговор снова живой. Только сообщение ЧЕЛОВЕКА: авто-ход (цикл «до готово»,
  автоматизация, исполнитель задачи) архив не отменяет, иначе убранный чат всплывал бы сам.
- **Архив глушит уведомления и непрочитанное.** Гасится доставка (`ChatPanel`), а не
  настройка чата: `notificationsMuted` переживает архивацию и вернётся вместе с чатом.
  Из счётчика непрочитанного архивные выброшены (`countUnreadChats`), из сводки главной —
  на сервере (`HomeController`), а вместе с ней и из точки активности проекта.
- **В архивном виде не применяется фильтр статусов.** Дефолт прячет срез «Готово» (чаты
  выполненных задач), а в архив как раз их и убирают — иначе человек открывал бы архив и
  видел «пусто» при трёх лежащих там чатах.

**Ретенция — настройка человека, по умолчанию выключена.** Срок хранения выбирается кнопкой
«Хранить» в той же строке действий (пресеты: всегда / 1 / 15 / 30 / 90 дней / полгода / год)
и живёт в `User.ArchiveRetentionDays` (`PUT /api/auth/archive-retention`, значение приезжает в
`GET /api/auth/me`). Настройка **личная и общая для всех областей**: архив у каждого свой, а
срок хранения — привычка владельца, не свойство проекта. `null`/0 — не удалять никогда.
Убирает [ChatExpiryService](../../backend/ClaudeHomeServer/Services/ChatExpiryService.cs) — тот
же, что чистит временные чаты: отсчёт от `ArchivedAt`, чат с идущим ходом защищён, срок берётся
по ВЛАДЕЛЬЦУ чата (`ResolveOwnerId`, с кешем «владелец → срок» на проход). Не резолвится
владелец — уборка выключена: удалять то, чей хозяин неизвестен, опаснее, чем не удалить.
Ключ `Session:ArchiveRetentionDays` остался **дефолтом инстанса** для тех, кто настройку не
трогал (личное значение его перебивает), и читается на каждом тике — рестарт не нужен.
Дефолт «не удалять» осознанный: человек убирает чат в архив именно чтобы сохранить его, и
молчаливая уборка превратила бы кнопку «В архив» в отложенное «Удалить». Для сравнения, у
claude CLI архива нет вовсе — там только retention локальных транскриптов
(`cleanupPeriodDays`, 30 дней по умолчанию).

Массового API удаления нет намеренно: «Очистить архив» шлёт обычные `DELETE` по одному —
удаление чата уносит и транскрипт claude CLI, и дублировать этот каскад пачкой ради одной
кнопки незачем. Упавшие удаления просто остаются в архиве.

## Очередь сообщений занятого чата («честная очередь»)

Сообщение, отправленное пока идёт ход, встаёт в видимую серверную очередь
(`SessionEntry.Pending`, событие `pending_messages`, карточка-конверт в конце ленты) и
уходит в работу по концу хода. **Идущий ход при этом не убивается** — отправка ≠ остановка,
как в claude CLI: kill посреди хода выбрасывал сделанную работу и оплаченные токены, оставлял
`tool_use` без `tool_result` в транскрипте и рваные правки в проекте, а пользователь обычно
дописывает уточнение, а не просит остановиться.

Прерывание осталось там, где ждать конца хода бессмысленно или так решено отдельно:

| Случай | Что делает | Почему |
|---|---|---|
| Обычный ход (`Working`) | ждёт `result` | ход доживёт сам |
| Ход ждёт человека (`Waiting`) | прерывает | стоит на карточке разрешения/вопроса и сам не кончится |
| Активен цикл «до готово» | прерывает | сообщение становится следующей итерацией (решение владельца 2026-08-08) |
| Агентское `chats_send` | прерывает обычный ход | ждущий агент иначе упрётся в таймаут |
| Кнопка «Прервать и отправить» | прерывает | явный перебой человеком |

Разбор очереди идёт по трём событиям: штатный `result`/`error`; `exited` прогона с меткой
`DrainOnExitedRun` (его прервали ради очереди); `exited` **своего** прогона без живого хода
(`Process is not { HasLiveTurn: true }`) — смерть процесса, ватчдог, «Стоп» — иначе сообщение
висело бы призраком до следующей отправки. Замороженную «Стопом» очередь (`QueueFrozen`) не
разбирает ни один из путей: её размораживает только новое сообщение пользователя.

Третий гейт смотрит именно на живой прогон, а **не** на статус чата и не на `Busy()`: статус
`exited` успевает сбросить сам (`Working→Active`), а `Busy` включает `OrchestrationActive`, и
боевой адаптер — всегда обёртка `FallbackLlmSessionAdapter`, которая отдаёт придержанный
`exited` вниз из `SettleAsync`, а `_turn` обнуляет лишь в `finally` — то есть уже после
`SessionManager`. Оба варианта гейта молча не срабатывали бы никогда. Если разбор всё же
попадёт в окно живой оркестрации, доставка не теряется: `SendMessageAsync` обёртки вернёт ход
в `Pending` через `EnqueueBypass`, а её `finally` добьёт разбор сигналом `_orchestrationDone`.

Явный перебой — `POST /api/sessions/{id}/pending/preempt` (`SessionManager.PreemptForPending`),
кнопка на карточке головы очереди. В отличие от «Стоп» очередь **не** морозится: прерывание
здесь и есть требование доставить ждущее сейчас. Отказ (409) — если ход уже кончился, очередь
пуста или заморожена, живого прогона нет (чат залип в `Working` — такой реанимирует «Стоп»;
либо идёт ротация фолбэка, где `Interrupt` бесполезен) либо **идёт компакция**: `/compact` —
обычный ход, но обёртка фолбэка его не оркеструет и `exited` убитой компакции глотает, так что
перебой оставил бы чат в вечном `Working` с застрявшей очередью (метка
`SessionEntry.CompactInFlight`).
Исход отправки `queued-preempted` (хаб `SendMessage`) говорит клиенту отметить ход прерванным —
иначе голый `exited` убитого прогона нарисовал бы ложную аварию «AI завершился неожиданно».

## Тема чата (значок у названия)

У чата есть тема — **имя компонента lucide-react** в PascalCase (`Cat`, `Bug`, `User`,
`MousePointerClick`…), по которому фронт рисует монохромную иконку рядом с именем: в списке
чатов предмет узнаётся быстрее, чем читается текст. Хранится отдельным полем `Session.Topic`,
само имя остаётся чистым текстом (поиск по названию значок не задевает).

**Свободный выбор, без каталога тем.** Модель подбирает любую из ~1700 иконок lucide-react
под предмет разговора (кошка → `Cat`, собака → `Dog`, баг → `Bug`, человек → `User`).
Каталога тем с белым списком нет: бэк доверяет модели и хранит имя как строку, фронт
рендерит `icons[topic]` ([lucideIcon.ts](../../frontend/src/lib/lucideIcon.ts)) — незнакомое
имя (модель промахнулась) молча не рисуется, чат не ломается. Это даёт максимальную
различимость: каждый предмет — свой значок, а не общая категория-свалка.

**Как проставляется.** Значок определяет то же фоновое действие `chat-title`, что уточняет
авто-заголовок нового чата (`RefineChatTitleAsync`, ответ `{title, iconName}`); промпт
просит модель выбрать имя lucide-компонента, бэк sanity-проверяет PascalCase без белого
списка. Существующим чатам значки проставляются пакетно действием AI-палитры «Проставить
значки тем» → `POST /api/chats/icon-batch` (`SetChatIconsAsync`): чаты со значком
отсеиваются ДО вызова модели, каждый оставшийся — отдельный вызов, поэтому на десятках чатов
прогон занимает десятки секунд. `RetitleAsync` («Обновить название») значок не трогает.

**Бандл.** `import { icons }` в [lucideIcon.ts](../../frontend/src/lib/lucideIcon.ts)
тащит весь lucide-react (~1700 иконок). Для внутреннего продукта CCS это приемлемый обмен за
максимальную различимость; per-icon lazy-импорт невозможен (пакет в одном файле).

**Миграция.** Прежние реализации клеили значок эмодзи прямо в имя («🐛 Правка») и хранили
ключ темы из каталога (`bug`, `code`…). `ChatTopicMigration.Apply` на старте (`LoadSessions`)
чистит имена от ведущих эмодзи и обнуляет устаревшие ключевые `Topic` (они не PascalCase);
идемпотентна (флаг версии не нужен), чаты с `NameLocked` не трогает. Значки проставятся
заново lucide-именами при batch-прогоне.

## Генерация медиа (fal.ai, glif)

Медиа из результатов MCP-инструментов генерации рендерятся прямо в ленте чата —
[MediaBlock.tsx](../../frontend/src/components/chat/MediaBlock.tsx) (изображение/видео/аудио-плеер,
футер с метой, кнопки «Скачать» и «Добавить в проект» через `/api/proxy`). Парсинг устойчивый
(точные форматы вендоров не зафиксированы), `extractMediaFromResult`:

- **fal.ai**: массивы `images`/`videos`/`audio_files`/`audios` в корне/`result`/`data`/`output`,
  одиночные `video`/`audio`/`image`; классификация по `content_type`/расширению, `fal.media`/`fal.run`
  без типа → изображение. Точная стоимость приходит с backend (billing-events по `request_id` →
  `FalCostContext`), пока не пришла — «считается…» (снимается через 30 с).
- **glif**: MCP-блоки `resource_link`/`resource` в `content` (uri + mimeType), `assets` из
  `get_project` (uri, `type`, `metadata.{format,width,height}`), JSON внутри text-блоков;
  хосты `glifusercontent.com` / `res.cloudinary.com` без типа → изображение. Дедуп по URL
  (один файл из assets и resource_link показывается раз). Футер помечается «glif» (+ `outputType`
  из `_meta.glif`). Backend распознаёт completed-генерацию по `tool_result` и эмитит
  `glif_cost` → история (`StoredGlifCostMessage`) + SignalR + `SpendStore` (`SpendSources.Glif`).
  Fenced-блоки ` ```ui ` (Gallery-разметка glif) остаются обычными код-блоками.
- Домены обоих генераторов — в `PROXY_ALLOWED_HOSTS`/`MEDIA_HOSTS`
  ([MarkdownContent.tsx](../../frontend/src/components/chat/MarkdownContent.tsx), синхронизировать
  с `AllowedHosts` прокси-контроллера); src медиа-доменов в markdown блокируется — показан в MediaBlock.

**Карточки использования** — экран «Использование» ([UsageScreen.tsx](../../frontend/src/components/UsageScreen.tsx))
и виджет на главной ([UsageWidget.tsx](../../frontend/src/features/home/UsageWidget.tsx)):
fal — `GET /api/fal/account` (баланс USD + расход по моделям/дням); glif — `GET /api/glif/account`
(план, баланс КРЕДИТОВ — не USD, расход окнами 24 ч/7 д/30 д; без ключа — empty-state как у fal).

## Выбор генератора картинок (иконка проекта, аватар персоны)

Картинки, которые рисует **сам сервер** (а не модель в ходе чата), идут через слой драйверов
`Services/Images`: контракт `IImageGenerator`, драйверы `FalImageService` (fal.ai, синхронный
`fal.run`) и `GlifImageGenerator` (glif.app, `compose_project` + опрос `get_job_status`), роутер
`ImageGenerationService`. Провайдера и модель админ выбирает **отдельно для каждого места**
(`ImagePlaces`: иконка проекта, аватар персоны) — секция «Картинки» на
вкладке «Применение» диалога «Модели и расход» (`GET/PUT /api/image-generation`, чтение всем,
запись админам); настройка живёт в `data/image-generation.json` поверх секции конфига `Images`.
Модель выбирается только у fal.ai; в «Автоматически» и у glif её подбирает сам генератор.
Режимы: **Автоматически** (первый включённый в порядке `glif` → `fal`, следующий подстраховывает)
| **fal.ai** | **glif**; **явный выбор фолбэка не даёт** — не ответил выбранный сервис, значит
честный отказ, а не тихий переход на другой со счётом. Не получилось нарисовать сейчас (сервис
не настроен, отказ, сбой) — сущность встаёт в очередь `data/image-backfill.json`, живёт на
инициалах и получает картинку догоняющей генерацией (`ImageBackfillService`, старт +30 с и тик
10 мин, событие `image_backfilled`) — паттерн фона проекта ([ADR-008](../adr/ADR-008-project-background-generation.md)).

## Виджеты в чате

Штатная фича, без флага: модель показывает интерактивные HTML-виджеты (дашборды, графики,
калькуляторы) через `mcp__widgets__widget_show` — [mcp/widgets-server/index.js](../../mcp/widgets-server/index.js)
(без зависимостей, в API не ходит: валидирует input, лимит html 64 КБ). Фронт рендерит
`input.html` в sandbox-iframe ([WidgetView.tsx](../../frontend/src/components/chat/WidgetView.tsx) +
чистое ядро [lib/widgetHtml.ts](../../frontend/src/lib/widgetHtml.ts)): `sandbox="allow-scripts
allow-forms allow-modals"` (без same-origin/popups), строгая CSP-мета в обёртке (default-src
'none' — никакой сети), тема через CSS-переменные `--cc-*` (смена темы = ремаунт iframe),
авто-высота postMessage `cc-widget-height` (фильтр по `e.source`, кламп 120–800/560-мобила),
защитный cap рендера 256 КБ. Карточка виджета «пришпилена» в ленте (`isWidgetEntry` в ChatPanel) —
не прячется в свёртку «N действий», как медиа fal.ai; виджет переживает F5 (input в history.json).
Подсказка модели — widgetsHint в ClaudeSession (только при подключённом сервере); сервер
регистрируется в BuildTurnMcpConfig с `alwaysLoad` и работает у всех CLI-провайдеров.
Дискаверабилити: действие `chat.widget` в AI-палитре (контекстные промпты по разделам) +
rule-based подсказка в календаре при 5+ активных задачах. Для docker-песочницы сервер
копируется в образ (`/app/mcp/widgets-server`) — при обновлении нужна пересборка sandbox-образа.

## Быстрые фразы композера

Готовые сообщения, уходящие в чат одним нажатием: кнопка слева от микрофона
([Composer.tsx](../../frontend/src/components/Composer.tsx), `phrasesButton`) открывает попап
со списком ([QuickPhrases.tsx](../../frontend/src/components/QuickPhrases.tsx)), клик по фразе
= обычная отправка. Черновик в поле при этом НЕ трогается: фраза уходит через
`handleSend(overrideText)` — тем же путём, что и буфер режима разговора, — поэтому недописанное
сообщение переживает выбор фразы. Вложения, если они прикреплены, уезжают вместе с фразой
(их чистит ChatPanel, как при любой отправке).

**Два уровня.** У фразы есть необязательная группа: без неё пункт лежит в корне попапа, с
ней — прячется под именем группы («ГИТ → закоммить»). Группа раскрывается В ТОЙ ЖЕ карточке
(клик по имени — вход, клик по шапке со стрелкой — возврат), а не вложенным подменю сбоку:
на узком экране открывать его некуда. Порядок групп — по первому появлению их фразы в наборе,
сортировки по алфавиту нет: строки расставлены руками, и переставлять их за человека нельзя
(`groupQuickPhrases`). Фразы одной группы собираются вместе, даже если лежат в наборе вразнобой.

**Форма правки ведёт список СЕКЦИЯМИ, а не плоско** (`toSections` / `flattenSections`), и это не
про вид, а про правду: попап двухуровневый, поэтому в плоском списке стрелки порядка врали бы —
перестановка строки через границу группы в попапе не изменила бы ничего. Секция «Без группы»
всегда первая (она же приёмник для фраз без группы), её заголовок показывается только когда есть
группы. Имя группы правится ОДИН раз в заголовке секции, а не полем у каждой строки: общее,
размазанное по N полям, расходится опечаткой. Пустое имя = не группа, поэтому очистка имени
разгруппировывает секцию. Перенос фразы, дальние прыжки («В начало», «В конец») и удаление живут
в меню строки — в самой строке остаётся поле и три компактные кнопки, на мобиле уезжающие под
поле отдельной линией. Непустая строка и непустая группа удаляются только через `ConfirmDialog`:
кнопка стоит рядом со стрелкой порядка, а в строке до 500 символов. Enter в поле добавляет
СЛЕДУЮЩУЮ строку (отправлять форму из любого из двух десятков полей — ловушка), строки черновика
несут стабильные id, иначе при перестановке фокус и каретка прыгают на соседнюю.

Набор **per-user и один на все чаты** — привязки к проекту сознательно нет: «продолжай»,
«покажи дифф», «закоммить» одинаковы везде. Хранение — `User.QuickPhrases` в users.json через
UserStore, ресурс `GET/PUT /api/me/quick-phrases`
([MyQuickPhrasesController](../../backend/ClaudeHomeServer/Controllers/MyQuickPhrasesController.cs),
конвенция per-user настроек — как `/api/me/wall`). Валидация PUT молчаливая: обрезка пробелов →
отброс пустых → дедуп **пары «группа + фраза»** (одинаковый текст в разных группах — разные
пункты) → потолки (24 фразы, 500 символов текста, 40 — имени группы). Итог сервера и
становится набором — форма показывает то, что реально сохранено. Наборы, заведённые до
появления групп, лежат в users.json списком голых строк — их читает `QuickPhraseJsonConverter`
(конвертер висит на самом типе: users.json, бэкапы и API-ответы сериализуются разными
опциями и разъехаться не должны).

Список тянется **лениво, при первом открытии попапа** ([lib/quickPhrases.ts](../../frontend/src/lib/quickPhrases.ts)):
монтирование композера в каждом чате не должно порождать запрос. Провал загрузки не роняет
композер и не выдаётся за «фраз нет» — попап отличает пустой набор от отсутствия связи
(`quickPhrasesFailed`), иначе офлайн звал бы заводить фразы заново поверх уже существующих.

## Голосовой режим чата

Разговор с CCS, когда ответ **слушают, а не читают** (телефон, прогулка): надиктовал вопрос
голосовым вводом — ответ пришёл коротким и прочитался вслух. Штатная фича, без флага;
per-чат, по умолчанию выключена. Управление — **одна кнопка** (иконка `AudioLines`,
[Composer.tsx](../../frontend/src/components/Composer.tsx), `voiceButton`), занимающая место
«Отправить» при пустом поле; отдельного тумблера озвучки (`Volume2`/`VolumeX`) больше нет.
Три состояния читаются цветом: выключено — нейтральная плашка, режим включён без петли —
`C.accentLight`, петля разговора идёт — заливка `C.accent`. Состояние — `Session.VoiceMode`
(`SetVoiceMode`, **не двигает `UpdatedAt`**, как и прочие настройки чата); PUT обоих путей —
`/api/chats/{id}` и `/api/projects/{pid}/sessions/{sid}`, sentinel-семантика (нет поля = не менять).

**Формат ответа — ДВЕ точки влияния на промпт**, и обе обязательны
([VoicePrompts.cs](../../backend/ClaudeHomeServer/Services/Prompts/VoicePrompts.cs)):

1. секция `voice-mode` в системном промпте хода (`ClaudeSession`) — коротко, без
   таблиц/кода/списков/схем/эмодзи; явно отменяет встроенное правило «схемы рисуй Mermaid-кодом»
   из `ProjectManager.BuiltInSystemPrompt`. Там же — просьба брать инструменты только по
   необходимости: каждый вызов это round-trip `tool_use → tool_result → новый запрос`, то есть
   пауза-тишина в разговоре. **Спрос режется промптом, а не запретом:** состав
   `--disallowedTools` входит в сигнатуру прогона, и зависимость его от свойств хода
   перезапускала бы процесс со всеми MCP-серверами («Stream closed») — те же грабли, что у
   снятого `WriteIntentGate`;
2. оговорка `PersonaOverride` **последним блоком слоя персоны** (`PersonaPromptBuilder.BuildCore`).
   Без неё правило проигрывает: слой персоны склеивается ПОСЛЕ всех секций
   (`TurnPromptAssembler.Combine`), и слот «Формат ответов» персоны перебивает голосовой формат.
   Сабагентный `.md` (`BuildForSubagent`) и `persona_ask` оговорку не получают осознанно.

Известное ограничение: включение режима посреди идущего прогона применяется со следующего
процесса CLI — same-process ход системный промпт не пересобирает.

### Стиль озвучки: разговор и выжимка

У озвучки два стиля — `Session.VoiceStyle` ([VoiceStyles.cs](../../backend/ClaudeHomeServer/Models/VoiceStyles.cs)):

- **`talk`** (дефолт, всё описанное выше) — ответ короткий целиком, читается вслух по мере
  набора, работает петля разговора. Пусто/мусор в поле = `talk`, поэтому старые чаты ведут
  себя как раньше и миграция стора не нужна.
- **`digest`** — человек СМОТРИТ на экран и слушает: ответ обычный и полный (код, таблицы,
  схемы), а вслух идёт только выжимка из блока `<voice>…</voice>` в его конце
  (`VoicePrompts.DigestSectionText` + `DigestPersonaOverride`). Отмена ASCII-схем сюда не
  переносится — на экране схемы нужны. Петли, микрофона, стриминга и barge-in в `digest` нет.

**Выжимка стоит в КОНЦЕ ответа, и это не вкусовщина.** Модель генерирует авторегрессионно и
не может переписать сказанное: выжимка первым блоком — это ответ до рассуждения, который
не столько разойдётся с ответом, сколько **потянет ответ за собой** (модель подгоняет
остальное под собственные первые фразы), а в агентном ходу вдобавок пишется до чтения файлов.
Плата за конец — озвучка стартует на `result`, стриминга по предложениям нет; для работы за
компьютером это терпимо, ответ виден на экране.

**Стиль НЕ настраивается — он выводится из ширины экрана**
([lib/voiceStyle.ts](../../frontend/src/lib/voiceStyle.ts), `voiceStyleFor`): узкий экран —
телефон в руке, `talk`; широкий — экран перед глазами, `digest`. Переключателя нет вовсе, и
это осознанно: два сценария различаются не вкусом, а тем, видит ли человек экран, а ширина
отвечает на этот вопрос точнее, чем тумблер, который пришлось бы дёргать при каждой смене
устройства. Один и тот же чат, открытый с компа и с телефона, получает верный формат сам.
Значение реактивно (повернул планшет — следующий ход придёт в другом формате) и нигде не
хранится: `localStorage` не нужен.

**Стиль не влияет на разговор без рук.** Петля работает на любом устройстве; от стиля зависит
только длина ответа и что читается вслух. Кнопка наушников осталась единообразной — путать её
поведение по устройствам было бы хуже, чем не иметь второго стиля вовсе.

Сервер хранит последнее выставленное значение — оно нужно ему, чтобы выбрать секцию промпта;
`voiceStyle` приезжает в тех же PUT и **без `voiceMode`** (второе устройство выправляет чужой
стиль), поэтому сеттер принимает оба поля как nullable и трогает только присланные.
Синхронизация — по расхождению и только при `voiceMode === true`, один PUT на открытие чата
плюс по факту смены стиля, ответ игнорируется: иначе `digest` на широком экране слал бы PUT
(то есть перезапись всего `sessions.json`) на открытие каждого чата, а поздний ответ,
разошедшийся с тапом по кнопке, перевернул бы её состояние.

**Маркер `<voice>` вырезается безусловно** — и в санитайзере речи (`stripVoiceMarker`), и на
рендере ленты, по одному правилу: всё от первого вхождения `<voice` до конца текста, включая
оборванный на стриме префикс. В сохранённой истории и транскрипте CLI маркер ОСТАЁТСЯ (без
него `--resume` вернул бы контекст без примера формата), поэтому модель может повторить его и
после выключения стиля, а HTML-подобные теги санитайзер иначе не трогает вовсе. Содержимое
показывается плашкой «Коротко» ([VoiceDigestNote.tsx](../../frontend/src/components/chat/VoiceDigestNote.tsx))
— она же TL;DR ответа для глаз.

**Выдержка живёт и БЕЗ озвучки.** Секция `LongAnswerSectionText` просит блок `<voice>` у
любого длинного ответа — человек написал вопрос руками, получил простыню и хочет видеть суть
плашкой «Коротко», не вычитывая её; прочитать вслух можно кнопкой-динамиком на самой плашке
(разовое чтение, режим не включается и микрофон не трогается). Отличие от `DigestSectionText`:
там блок обязателен ВСЕГДА (иначе озвучивать нечего), здесь — только когда ответ реально
длинный, короткий ответ сам себе выдержка.

**Форма выдержки без озвучки — тезисная:** первая строка блока это вывод одной фразой, под ней
2–4 пункта с дефиса. Этот блок читают ГЛАЗАМИ, а глаз снимает суть со списка быстрее, чем со
сплошного абзаца; у `DigestSectionText` выжимка осознанно осталась связной речью — рваные
пункты на слух звучат хуже фразы. Маркер пункта именно дефис, потому что `sanitizeForSpeech`
срезает в начале строки только `-`, `*` и `+`, а тире зачитал бы вслух: кнопка чтения на плашке
никуда не делась. Разбирает выдержку на «вывод + тезисы» `splitVoiceDigest`
([turnSpeechStream.ts](../../frontend/src/lib/turnSpeechStream.ts)) — плашка рисует простой
текст, и без разбора переносы схлопнулись бы в строку с дефисами посередине; выжимка сплошным
абзацем (старая история, стиль `digest`) целиком уходит в вывод и выглядит как раньше.

Выбор секции — одна точка `VoicePrompts.SectionFor(voiceMode, digest, heard, longAnswerDigest)`
(вынесена из `ClaudeSession` ради шва под тест). `heard` — есть кому слушать или читать: не
исполнитель задачи, не правило автоматизации, не делегированный ход. Оговорка персоны идёт тем же правилом
(`SessionManager` отсекает два признака из трёх, третий добирает секция) — иначе модель
получила бы «пиши блок `<voice>`» без формата и без слушателя, и маркер засорил бы транскрипт.
Локальный собеседник на Ollama в `digest` выключен гейтом `ShouldRunLocalVoice` (болталка не
умеет ни инструменты, ни маркер); сигнал «нужно решение» не пищит — карточку видно глазами.
Модель забыла маркер — фолбэком читаются первые ТРИ ПРЕДЛОЖЕНИЯ (не первая строка: ответ одним
абзацем уехал бы в синтез целиком), промахи считает `talkDiag`.

**Строка состояния** (`VoiceStatusRow`) обязательна в обоих стилях и меняет только текст:
режим переживает F5 и смену чата, а без напоминания единственным признаком включённой озвучки
остаётся оттенок кнопки — включил утром, вернулся вечером, ответ заговорил.

**Озвучка.** Фронт после каждого завершённого хода собирает текст ответа (все `text`-элементы
без `parentToolUseId` — реплики сабагентов не читаем — появившиеся после предыдущего `result`),
прогоняет через санитайзер, режет на предложения и **пакует их в запросы**
([lib/tts.ts](../../frontend/src/lib/tts.ts), `packSentences`), затем шлёт пакеты на
`POST /api/tts` очередью (следующий синтезируется, пока играет текущий).
Бэкенд ([YandexTtsService](../../backend/ClaudeHomeServer/Services/Tts/YandexTtsService.cs))
синтезирует через Yandex SpeechKit **API v3** (`tts/v3/utteranceSynthesis`, JSON, ответ —
строки с base64 внутри, склеиваются в mp3). Сервисному аккаунту нужна роль
**`ai.speechkit-tts.user`** — со STT-ролями рабочий ключ отвечает 403 (в лог идёт отдельная
понятная строка). Конфиг — `Yandex:SpeechKit` в `appsettings.Local.json`; незнакомое имя
голоса не глушит озвучку, а заменяется дефолтным с предупреждением в лог
(`TtsVoiceCatalog` — белый список из 16 голосов и карта их амплуа).

**Чей голос — решает [VoiceResolver](../../backend/ClaudeHomeServer/Services/Tts/VoiceResolver.cs),
единственная точка склейки** (образец — `UserModelTierResolver.ModelFor`): голос персоны →
голос инстанса из конфига. Фронт шлёт `personaId` в теле `POST /api/tts`, владельца
проверяет сервер (`PersonaManager.Get`). **Отказов здесь не бывает по устройству**: чужой или
удалённый `personaId`, незнакомый голос, амплуа, которого у голоса нет, темп вне 0.1–3.0 —
всё молча вырождается в дефолт. Причина не в снисходительности: 400 или 502 уводят на голос
браузера ОСТАТОК фразы, то есть одна устаревшая вкладка стоила бы человеку куска озвучки.
Строгая валидация (с 400) живёт на другом конце — в `PUT /api/personas/{id}/voice`, где
ошибку надо показать в форме.

**Ход читается одним голосом.** Персона берётся из последней реплики хода, иначе из
собеседника чата (`turnVoicePersonaId`), и захватывается ОДИН раз на ход: пакеты уходят на
синтез заранее (prefetch), и смена голоса посреди хода выбросила бы уже оплаченный пакет.
В групповом чате это значит, что реплики разных персон в одном ходу прочтёт один голос —
нарезка озвучки по говорящему сюда не входит. Тем же голосом петля разговора произносит
реплики о себе («Слушаю.», «Выключаю разговор») — иначе в одном разговоре звучали бы два
разных голоса.

**Видно, кто говорит.** Пока звучит ответ, у аватара её реплики в ленте расходятся кольца
цветом персоны, и тем же цветом светится aurora над композером. Источник ОДИН —
`activeSpeaker` в `ChatPanel`: захваченная на ход персона (ровно та, что дала голос) плюс
индекс её реплики (`turnVoiceItemIndex`); лента получает его контекстом
`SpeakingItemContext`, композер — пропом `auroraColorHex`. Гейт — фаза озвучки, а не сама
захваченная персона: та переживает конец чтения, и без гейта свет горел бы после того, как
смолкло. Подсвечивается только реплика ГОВОРЯЩЕЙ персоны — в групповом чате последним мог
ответить кто-то другой, и кольцо на его аватаре соврало бы про голос; персона не резолвится
(голос инстанса, чат без персоны) — эффекта нет вовсе, цвета взять неоткуда. Размах колец
мельче, чем у индикатора ожидания (`.cc-echo-ring--tight`): аватар сидит лидом ВНУТРИ пузыря
с `overflow: hidden`, и полный размах срезало бы кромкой. При `prefers-reduced-motion` колец
нет вовсе — от них осталась бы статичная обводка вокруг лица на всё время чтения.

**Почему пакеты, а не предложения.** v3 берёт деньги за ЗАПРОС (0,1626 ₽ до 249 символов), а
не за символы, поэтому точка безубыточности против v1 — 121 символ
([speechkit-pricing.md](../research/speechkit-pricing.md) §4), а средняя фраза короче.
Без упаковки v3 выходит **вдвое дороже v1** (замер: ответ на 353 символа — 6 запросов
против 3 пакетов), с упаковкой — дешевле v1 процентов на двадцать на длинных ответах и
вровень на коротких. Так что упаковка тут не оптимизация, а условие: главный смысл перехода —
голоса, и упаковка нужна, чтобы он не стоил денег. При этом ПЕРВЫЙ кусок уходит в одиночку —
звук обязан пойти сразу; и в стриме копилка сбрасывается, как только очередь пуста, иначе
экономия выродится в ту самую паузу, ради которой стриминг писался. Пакеты не набиваются под
завязку намеренно: предложения не режутся пополам, поэтому 600 символов едут четырьмя
запросами, а не тремя. Лимит запроса v3 — 249 символов (замерено),
нарезка в сервисе (`SplitForSynthesis`, рез по границе слова) остаётся страховкой на случай
длинного текста от другого потребителя.

Основной путь — `HTMLAudioElement` с mp3, а не `speechSynthesis`: mp3 продолжает играть при
погашенном экране телефона, а браузерный синтез глохнет — для сценария прогулки это решающее.

**Коды ответа `/api/tts` — контракт фолбэка**, менять осознанно:
`503 {reason:"not_configured"}` — ключа нет (постоянно: фронт запоминает и уходит на
`speechSynthesis`, показав один тост; флаг сбрасывается при возврате связи в `online`, потому
что 503 отдаёт и реверс-прокси при рестарте инстанса); `502 {reason:"upstream"}` — Яндекс
отказал или молчит (временно, фронт не запоминает); `400` — пустой текст или длиннее 3000
символов. `OfflineError`/`RequestTimeoutError` (без `status`) — молчим: связи нет.

Прочие решения: при активном цикле «до готово» не озвучиваем вовсе (отличить финальный `result`
от промежуточного в момент события нельзя); расход на синтез в `SpendStore` не учитываем
(ограничители — короткий ответ по промпту, лимит 3000 в контроллере, обрезка ~1500 в
санитайзере); рейт-лимита на эндпоинте нет (он под `[Authorize]`, пользователь — владелец
инстанса). Прайминг аудио делается дважды — в обработчике тумблера и при отправке сообщения:
политика autoplay пускает звук только после пользовательского жеста, а режим переживает
перезагрузку («включил вчера — надиктовал сегодня»).

### Режим разговора (hands-free)

Петля без касаний: сказал → пауза со звуковым сигналом и окном отмены → отправка → ход →
озвучка ответа → снова слушаю. Целиком на фронте, бэкенд не участвует. Автомат —
[useHandsFree.ts](../../frontend/src/hooks/useHandsFree.ts): **чистый редьюсер**
`handsFreeReducer` (под юнит-тестами `hooks/__tests__/handsFree.test.ts`) плюс обёртка с
эффектами (таймеры, микрофон, wake lock, сигнал, реплики). Режим персистится
(`Session.VoiceMode`), сама петля — нет: после F5 она спит, для старта нужен жест.

Грамматика полосы ввода:

```
режим выключен, поле пустое   ->  [+][скрепка] .. [микрофон] [AudioLines]
режим выключен, есть текст    ->  [+][скрепка] .. [микрофон] [    ^     ]
идёт генерация (поле пусто)   ->  ..                         [   стоп   ]
ручная запись микрофоном      ->  [красная точка|таймер|волна]  [X] [V]

петля активна (своя ветка):
  слушаю   -> [волна + «слушаю» + скажите «стоп» — выключу] [ остановить ]
  отсчёт   -> [распознанный текст + «2…1…»]     [ остановить ]
  думает   -> [«думает…» + фоновая пульсация]   [ остановить ]
  говорит  -> [«отвечает…»]                     [ остановить ]

режим включён, петля спит (пауза):
            -> [.VolumeX «Разговор на паузе — …»] [ Продолжить ]
```

**В петле кнопка одна и всегда означает «прекрати»** (решение владельца): один тап глушит
чтение, прерывает идущий ход и выходит из режима. Прерывание идёт **по фазе петли**
(`sending`/`waiting`), а не по `isGenerating`: между отправкой и статусом «идёт ответ» есть
окно в секунду-две, и клик в него оставлял ход живым — модель договаривала уже после выхода
из разговора. Фазу видно по подписи в полосе ввода, а не
по кнопке: разбираться на ходу, что означает значок именно сейчас, человек с телефоном в
кармане не может. Прежний вариант — «Стоп» прерывает ход, оставаясь в разговоре — отменён:
он требовал двух разных тапов в зависимости от фазы.

**Голосовой выход из разговора:** фраза «стоп» (синонимы: «хватит», «отбой», «конец связи»,
«выключись», «выключи разговор», «достаточно», «прекрати», «хватит говорить») в микрофонных
фазах (`listening`/`pending`) гасит петлю **без касаний**: буфер умирает вместе с петлёй
(в чат не уходит), звучит «Выключаю разговор», композер доделывает хвост тапа — страховочное
прерывание хода и `PUT voiceMode=false` (Р3). Распознавание — **точное совпадение всего
чанка** после нормализации регистра/пунктуации (`isStopCommand`): «стоп, а теперь расскажи…»
и «хватит денег» — обычная речь, уходит в чат как сообщение. Ограничение честное: во время
хода и озвучки команда не работает — микрофон тогда закрыт (эхо-защита), сказать «стоп»
физически некуда; выход в тех фазах — только кнопка. Барж-ином дыра закрыта наполовину: перебивание глушит озвучку и возвращает петлю слушать, и «стоп»,
сказанное следом, распознаётся уже штатно.

**Звуки петли** (`lib/beep.ts`; референсы, по которым их выбирали, — в
`.cc-attachments/sounds/` вместе с генератором `gen-sounds.js`):

- *слушаю* (`startListening`) — двойной тик 520→700 Гц при открытии микрофона и **повтор
  каждые 5.5 с**, пока фаза `listening`: одного сигнала мало, на ходу не помнишь, слушают
  тебя сейчас или ответ ещё читается. Тиканье прекращается само при первом распознанном
  слове (фаза уходит в окно отправки). Возврат из окна отмены (человек продолжил говорить)
  повтор заводит, но первый тик не играет — он лёг бы прямо на речь. Двойной намеренно:
  одиночный писк занят отправкой, события должны различаться на слух;
- *отправка* — короткий писк 880 Гц: речь распозналась, пошло окно отмены;
- *ожидание ответа* (`startThinking`, фазы `sending`/`waiting`) — тихая высокая нота
  1320 Гц раз в 4 с («дальний маячок»). На прогулке экран не виден, и молчащая пауза в
  полминуты неотличима от «связь отвалилась»; редкий негромкий сигнал подтверждает работу
  и не лезет в уши всё ожидание. Первый тик идёт сразу — подтверждение, что вопрос принят.
  В фазе `speaking` не звучит: эффект привязан к фазе и гаснет сам;
- *нужно твоё решение* (`needAnswer`) — тройной пинг 780 Гц. Звучит один раз, когда модель
  задала вопрос или просит разрешение; следом (через 560 мс, чтобы сигнал не лёг на первое
  слово) идёт голосовая фраза, и петля выходит из режима. Только в петле: вне разговора о
  таких событиях сообщают браузерные уведомления.

Фазы автомата: `off | listening | pending | sending | waiting | speaking`. Ключевые решения:

- **Микрофон принадлежит человеку, пока петля выключена.** Гасить его хук вправе только
  пока петля активна (эхо-защита) и один раз на выходе из неё. Раньше условие смотрело
  только на фазу, и выключенная петля душила обычную диктовку: человек жал микрофон, эффект
  видел «фаза не `listening`, а микрофон открыт» и тут же его закрывал — кнопка выглядела
  сломанной. Сторож — e2e «после выхода из разговора обычная диктовка снова пишет в поле».
- **Эхо — дефект №1.** Микрофон открыт ровно в `listening`/`pending`; фаза озвучки ведётся
  в `ChatPanel` (`speechPhase`) **с токеном вызова**: новый `speak` внутри себя зовёт
  `stopSpeaking()`, и `finally` предыдущего иначе сбросил бы фазу уже начавшейся озвучки.
  `speak()` резолвится по реальному концу звука — **включая браузерный фолбэк** (резолв по
  `onend`/`onerror`), это самый частый путь отказа и был прямым каналом эха.
- **Барж-ин (P1 среза voice-mode-benchmark).** Под озвучку
  ответа слушает ОТДЕЛЬНЫЙ VAD-канал (`lib/bargeVad.ts`: getUserMedia с браузерным AEC +
  Silero VAD v5 в аудио-ворклете, `@ricky0123/vad-web`). Решение принимает СВОЙ детектор
  (`lib/bargeDetect.ts`, чистая логика под юнитами) по сырым кадрам, и оно
  **двухступенчатое**: речь ~300 мс → озвучка приглушается до 20% (обратимо, автомат об
  этом не знает — фаза остаётся `speaking`); речь дожила до ~550 мс → прерывание хода
  (как кнопка «Стоп»), глушение и возврат петли в `listening` (событие `bargeIn`); смолкла
  раньше → громкость возвращается. Плюс гейт громкости (втрое выше скользящего фона и выше
  абсолютного минимума RMS) — дальние источники вроде телевизора за стеной не перебивают
  вовсе. Так цена ложной тревоги падает с «ответ потерян» до «полсекунды тише». Возврат подтверждается **словом** «Слушаю»
  (реплика петли `bargeAck`, механика та же, что у «Ты ещё здесь?»): оборванная на
  полуслове озвучка иначе неотличима от обрыва связи. Тик «микрофон открыт» при этом
  молчит — два сигнала об одном событии; под реплики самой петли VAD-канал не
  открывается вовсе, иначе она перебивала бы сама себя. Инвариант эха при этом сужается честно:
  «РАСПОЗНАВАНИЕ и озвучка не пересекаются» — VAD-канал живёт РОВНО в фазе `speaking`
  (трек отпускается синхронно в момент перебивания, до открытия Web Speech), на
  WebKit/iOS канал выключен гейтом `isAmpUnsafePlatform` (второй захват там убивает
  SpeechRecognition). `ChatPanel` держит флаг подавления озвучки перебитого хода
  (обе точки — пересоздание стрима на проскочившей дельте и одиночный `speak()` на
  `result`), снимается на границе следующего хода. Ассеты (модель, ворклет, WASM) — со
  своего хоста из `/vad/`, деградация тихая: канал не поднялся → петля живёт как раньше.
  Дочитки перебитого ответа нет — осознанно. Тексты и критерии снятия флага —
  [docs/features/voice-barge-in.md](../features/voice-barge-in.md).
- **Прямого перехода «ход кончился → слушаю» НЕТ**: эффекты композера идут раньше
  родительского эффекта озвучки, и в том кадре `willSpeak` физически ещё не выставлен.
  Выход из `waiting` — только по озвучке либо по страховке 1.5 с после снятия `isGenerating`.
- **Страховки считают бездействие, а не длительность фазы**: ход с инструментами идёт
  минутами, озвучка 1500 символов — больше полутора. Глобальный сторож — 60 с без хода,
  звука и прогресса, затем голосовое «выключаю разговор».
- **Выход по вопросу модели** (`awaitingResponse` — `permission_request`/`ask_question`,
  НЕ `isWaiting`): реплика «нужно твоё решение» и выход; если вопрос пришёл посреди озвучки,
  ответ дочитывается, и только потом выход.
- **Бесплодный цикл считается один раз — по `cycleEnded`**: движок на пустом цикле шлёт
  `onerror('no-speech')` И следом `onend`, и по двум событиям счётчик рос бы вдвое. 3 цикла
  подряд → «ты ещё здесь?», ещё 2 → выключение. Сама реплика произносится в фазе `speaking`
  (микрофон закрыт — иначе синтез слышит себя и петля разговаривает сама с собой), но
  счётчик и отметку «уже предупредили» переживает: возврат из неё идёт по флагу
  `noticeSpeech`, а не как из озвучки ответа. Перезапуск распознавания — не чаще раза в
  1.5 с (иначе горячий цикл start→error→start), тосты ошибок демпфируются до раза в 30 с,
  `no-speech` в петле молчит.
- **Окно отмены адаптивное** (`pendingDelayFor`, чистая функция под юнитами): 1.0 с, если
  мысль дозрела (4+ слов без висячего хвоста, короткий самодостаточный ответ вроде «да»,
  либо терминальная пунктуация), 2.8 с, если фраза оборвана (последнее слово — союз,
  предлог, филлер «ну»/«э», либо сказано одно-два слова), 2.0 с в неясном случае. Это
  дешёвая замена semantic VAD: на пунктуацию полагаться нельзя — Web Speech для ru-RU её
  почти не ставит, поэтому решает ХВОСТ фразы. Речь, продолжившаяся в окне, по-прежнему
  возвращает петлю в `listening` и дописывает буфер.
- **Тайминги круга пишутся в диагностику**: `talkMark` (`lib/talkDiag.ts`) размечает
  `speech-end → send → turn-start → first-audio`, дамп разговора печатает сводку по кругам
  и средние. Первый звук отмечает сам проигрыватель (`onplaying` / `utter.onstart`), а не
  фаза `speaking`: между ними лежит синтез первого куска.
- **Буфер петли отдельный от поля ввода**: текст в поле сделал бы из кнопки режима
  «Отправить» и намусорил в черновике. Отправка идёт `handleSend(overrideText)` без
  `resetInput()` — недописанный черновик пользователя остаётся на месте.
- **Гейты старта**: есть Web Speech и не включён клавиатурный фолбэк, не идёт цикл «до
  готово», не взведена командная механика, нет неотвеченного вопроса, не идёт ход (во время
  хода кнопка режима уступает место «Стоп» — стартовав петлю, из неё было бы не выйти). Офлайн выключает петлю
  совсем (композер в офлайне подменяется заглушкой — выключить её было бы нечем), поэтому
  хук объявлен выше раннего return. Мёртвый движок (watchdog, синтетический код `mic-dead`)
  — немедленный выход с сообщением.
- **Тап по кнопке**: петля спит → **обрыв играющей озвучки** (`onStopSpeech`), затем старт
  синхронно в жесте (`primeAudio`, `primeBeep`, `startMic`; PUT `voiceMode` уходит следом,
  его провал гасит петлю с тостом); петля активна → выключение режима, а в фазе ожидания
  заодно прерывание хода. Обрыв обязателен: режим персистится, ответ читается вслух и без
  петли, и микрофон открылся бы под собственный голос модели. Слать ли обратный PUT,
  решает **ref запрошенного значения**, а не проп: между двумя быстрыми тапами ответ
  первого PUT ещё не пришёл, и по пропу режим остался бы включённым на сервере. Этот ref —
  **единственный** источник правды: `onToggleVoiceMode(next)` принимает явное значение, и
  `ChatPanel` ничего не вычисляет сам (второй ref после провала PUT или смены чата с тем же
  значением режима инвертировал бы его — петля крутилась бы молча).
- **Осознанный компромисс с обрывом озвучки:** `speechSynthesis.cancel()` в ряде движков
  отрабатывает не мгновенно, а `startMic()` идёт следом в том же жесте (гвард `isSpeaking()`
  живёт только в эффекте микрофона). Теоретически хвост браузерного синтеза попадёт в первый
  цикл распознавания. Разрыв жеста ради гварда стоил бы разрешения микрофона и autoplay —
  оставлено как есть.
- **Отправка может не состояться** (механику «Команды» успели взвести уже внутри петли):
  `handleSend` возвращает признак, и петля по `false` возвращается слушать с тостом,
  а не стоит 60 с до сторожа бездействия.
- **Уход из чата честно гасит режим.** Смена чата (Composer стоит с `key` по сессии) или
  уход в другой раздел размонтирует композер вместе с петлёй — раньше режим оставался
  «наполовину живым»: кнопка подсвечена, озвучка ходит, а слушает никто. Теперь cleanup
  размонтирования при активной петле шлёт `PUT voiceMode=false` (`quietExitTalk`). Гасится
  ТОЛЬКО живая петля — режим, включённый без петли (только озвучка), человек не выключал.
  **Ход при этом НЕ прерывается**: он живёт на сервере и фронта не требует, обычный уход
  из чата его никогда не убивал — прерывание в хвосте выхода оставлено только явным
  «прекрати» (кнопка/голосовое «стоп», `exitTalk`); озвучка «в пустоту» не играет, её
  гейтит живой чат. Воскресить петлю без жеста нельзя (autoplay/микрофон), поэтому возврат
  в чат честно показывает плашку «Разговор на паузе» с кнопкой «Продолжить» НАД полем
  ввода (`voiceMode && !петля`; поле остаётся полем); она же — путь быстрого рестарта
  после F5.
- Экран держит [wakeLock.ts](../../frontend/src/lib/wakeLock.ts) (переполучение по
  `visibilitychange`), сигнал окна отмены — [beep.ts](../../frontend/src/lib/beep.ts)
  (тон WebAudio ~40 мс). Обоих API может не быть — тихая деградация. Зависший ход (фаза
  `waiting` живёт сколько угодно) отпускает блокировку экрана через 5 минут, не выключая
  разговор. Блокировка одна на вкладку, а просят её двое (петля и идущий ход, см.
  «Базовые возможности»), поэтому у неё **набор владельцев**: жива, пока хочет хоть один —
  иначе конец хода гасил бы экран посреди разговора. Пока петля жива, она объявляет себя
  **эксклюзивным** владельцем (`setWakeLockExclusive`): чужие заявки не учитываются вовсе,
  иначе владелец `turn` отменял бы пятиминутный отпуск экрана выше.
- **Известное ограничение:** `tts`, `beep` и `wakeLock` — модульные синглтоны, поэтому две
  одновременно смонтированные панели чата делили бы одну озвучку и одну блокировку экрана
  (вторая петля обрывала бы звук первой). Конфигурация редкая — в продукте панель чата
  одна; лечение (инстансы на панель) дороже проблемы, оставлено осознанно. Смягчение:
  при размонтировании `releaseWakeLock`/`closeBeep` зовёт **только тот экземпляр, который
  петлю и включал** — иначе закрытие соседнего чата обесточило бы живую петлю.

Сравнение петли с голосовыми режимами ChatGPT и Claude (барж-ин, semantic VAD, бюджеты
задержки) и план улучшений — срез [research/voice-mode-benchmark.md](../research/voice-mode-benchmark.md)
(август 2026, не поддерживается).

### Локальный исполнитель разговора (Ollama)

Админ может назначить разговору локальную модель: место **`chat-voice`** («Голосовой чат
(разговор)», группа «Чаты и персоны» диалога «Поставщики моделей») → «Локальная». После этого
ходы разговора идут **прямым HTTP-вызовом Ollama** (`OllamaClient.ChatTurnAsync`) мимо claude
CLI: ответ за 1–3 с вместо старта подпроцесса, бесплатно (`SpendRecord` с provider `ollama`,
cost 0). Это единственное чатовое место без `Agentic` — инструментов разговору не нужно.

- **Гейт** — `SessionManager.ShouldRunLocalVoice`: `Session.VoiceMode` + local-маршрут места
  + ход человека без вложений, без цикла «до готово» и штаба. Авто-ходы, доклады
  автоматизаций и агентские отправки — через CLI как раньше. Персона не блокирует: её
  характер (`Contract.Character`/`Tone`) подмешивается в system-промпт собеседника
  (`VoicePrompts.LocalCompanionSection`) сокращённо, без слоя памяти/привязок.
- **Конвейер общий**: ветка шлёт синтетические `session_started → text_delta… → result →
  exited` через `OnMessageAsync` — аккумулятор, статусы, «честная очередь» и бродкаст
  работают как у CLI-хода. Фронт ничего не знает об исполнителе.
- **Ход идёт потоком** (`stream: true`, NDJSON): куски ответа уходят в ленту по мере
  генерации, и озвучка первого предложения начинается, не дожидаясь конца хода. Куски
  копятся до границы предложения (или 40 символов) — фронт режет речь по предложениям, а
  слать каждый токен отдельным SignalR-событием незачем. Счётчики токенов берутся из
  финального чанка `done: true`; хвост без терминальной пунктуации досылается последним
  куском. Потолок времени хода держит связанный CTS: при потоке `HttpClient.Timeout`
  покрывает только заголовки ответа. Ответ целиком (`TextDeltaMessage` одним куском)
  шлётся лишь как страховка, если поток не дал ни куска.
- **История едина**: до первого CLI-хода (нет `ClaudeSessionId`) разговор пишется в
  `data/sessions/{id чата}/history.json`, затем — в общий транскрипт. При возврате на CLI
  ходу дописывается сводка разговора (`BuildCliTurnText`): транскрипт CLI реплик локали
  не знает. Сводка одноразовая (`LocalTurnsSinceCli`), рестарт сервера её теряет — редкий
  кейс, лента при этом целá.
- **Сбой без фолбэка**: пустой ответ/ошибка Ollama — честная ошибка в ленте (тихий
  15-секундный старт CLI в разговоре хуже видимой ошибки). «Стоп» отменяет HTTP-вызов по
  CTS (`SessionEntry.LocalVoiceCts`) — exited ветки сам возвращает чат в Active и разбирает
  очередь.

### Деньги Яндекса: расход на озвучку и остаток на счёте

Озвучка — единственная платная часть голосового режима (распознавание идёт Web Speech
браузера и бесплатно), и учёт у неё **свой**: Billing API Yandex Cloud отдаёт баланс, прайс и
список услуг, но на вопрос «сколько ушло на SpeechKit за неделю» не отвечает вовсе —
детализация живёт только в CSV-выгрузке (разовой или в бакет Object Storage, с задержкой).
Зато считать самим здесь **точнее**, чем у Яндекса: v3 тарифицируется ЗА ЗАПРОС, а запросы
отправляет сам сервер.

**Счётчик.** `YandexTtsService.SynthesizeAsync` возвращает `TtsResult` — аудио плюс число
запросов, которые Яндекс **принял** (ответил 2xx), и их цену по
`Yandex:SpeechKit:RubPerRequest` (дефолт 0,1626 ₽, прайс — в конфиге, не в коде). Считаются и
запросы неудавшегося синтеза: оборвались на третьем куске — первые два оплачены, и молчать о
них значит занижать счёт. Не считаются отказы (400/403/5xx) и обрывы связи — про них
неизвестно, а гадать хуже, чем недосчитать единицу.

Отмена клиентом (закрыли вкладку, нажали «Стоп») наружу уходит обычным отказом, а не
исключением: иначе контроллер не успел бы записать расход и оплаченные запросы исчезли бы
из учёта.

**Запись.** Трату пишет `TtsController` (`SpendSources.Tts`, provider `yandex`, модель = голос,
`Generations` = запросы, `CostRub` = рубли). Разрезы проект/задача/персона берутся из чата — его
id фронт шлёт в `TtsRequest.SessionId`. Id передаётся **параметром** `speak`/`startStreamSpeak`
(в плашке «Коротко» — из `ChatSessionContext`), а не модульной переменной `lib/tts.ts`: панелей
чата на экране бывает несколько (колонки «Стены», два чата рядом), и общее значение приписало
бы траты чужому чату. Чужой или протухший id просто оставляет трату без разрезов, а `PersonaId`
из запроса для учёта не используется вовсе — он не проверен на владельца, и чужая персона в
отчёте о своих деньгах хуже пропущенного разреза. Реплики автомата разговора и прослушивание
голоса в карточке персоны чата не имеют — их траты ложатся на владельца без разрезов.

**Валюты не складываются.** `SpendRecord.CostRub` живёт отдельно от `CostUsd`: пересчёт по
выдуманному курсу врал бы тем сильнее, чем старше запись. В обзоре расхода рубли идут
отдельной плиткой «озвучка», в анализе — строкой рядом с вызовами без токенов. Источник `tts`
входит в `SpendSources.IsTokenless`, и это признак не только для рейтинга «дорогих ходов»
(там сортировка по токенам, которых у него нет): такие записи **не считаются ходами** в
счётчиках обзора, виджета и бейджа чата и не попадают в «последний ход». Иначе один
озвученный ответ добавлял бы 5–10 «ходов», а бейдж показывал бы «0 ткн · озвучка» вместо
настоящего ответа.

**Остаток на счёте** — `GET /api/yandex/account` (`YandexAccountService`, кэш 60 с, плашка
«Yandex Cloud» в виджете использования рядом с fal и glif). Billing API принимает **только
IAM-токен**, поэтому рядом живёт `YandexIamTokenProvider`: подписывает JWT (PS256) ключом
сервисного аккаунта и меняет его на токен, кэшируя до истечения. Настройка — секция
`Yandex:Billing` (id аккаунта, id ключа, PEM); аккаунту нужна роль **`billing.accounts.viewer`
на биллинг-аккаунте**, а не на облаке — иначе Яндекс не отказывает, а молча отдаёт пустой
список, и сервис подсказывает про роль именно в этом случае. Баланс — кошелёк инстанса,
поэтому его видит только админ (то же правило «по умолчанию закрыто», что у балансов
LLM-провайдеров); расход каждый видит свой. Без ключа раздел просто выключен — на озвучку и
её учёт это не влияет.

## Снимок промпта хода («какой промпт ушёл»)

Кнопка в панели под каждым постом ленты (иконка свитка) открывает шторку с тем, что CCS
собрал и передал claude CLI на этом ходу. Штатная фича, без флага.

**Сборка.** Системный промпт хода собирается в `ClaudeSession` из списка секций
(`PromptSectionDto`), а текст для `--append-system-prompt` склеивает
[TurnPromptAssembler.Combine](../../backend/ClaudeHomeServer/Services/Llm/Claude/TurnPromptAssembler.cs).
Это **единственный** путь сборки: показанное человеку и отправленное модели идут из одного
списка и разойтись не могут (сторож — `TurnPromptAssemblerTests`). Секции с `Kind = "turn"`
(текст сообщения с обвязками `SessionManager.BuildCliTurnText`) в склейку не входят — они
уходят в stdin и показываются отдельным блоком.

**Хранилище** — [PromptSnapshotStore](../../backend/ClaudeHomeServer/Services/PromptSnapshotStore.cs):
`data/prompt-snapshots/{sessionId}/{unixMs}-{seq}.json.gz`, последние 50 ходов на чат.
Ключ — `Session.Id`, а НЕ `ClaudeSessionId`: на первом ходу второго ещё нет, а чаты с общим
транскриптом (`resumeSessionId`) перемешивали бы снимки и вытесняли чужие. Отсюда же
удаление отдельной строкой в `SessionManager.DeleteAsync` — без гейта общего разговора.
Суффикс имени — возрастающий счётчик, а не случайный: ретеншн сортирует по имени.
Корень `prompt-snapshots` исключён из бэкапа (`BackupPaths`) — это диагностический лог.

**Применён / унаследован.** Промпт пересобирается каждый ход, но уходит модели только когда
ход стартует новым процессом. Ход, доигранный в живом процессе (совпала сигнатура прогона),
пишет снимок с `applied: false` и ссылкой `inheritedFromId` на снимок старта прогона
(`CliRun.PromptSnapshotId`) — UI это показывает прямо. Поэтому публикация в ДВУХ точках
`RunTurnAsync`: в ветке same-process — до `await TurnTcs` (иначе `TurnAccumulator.FlushAsync`
успеет унести ход, и id некуда прицепить), в ветке нового процесса — до `_launcher.Start`.

**Привязка к посту.** Событие `prompt_snapshot` (только id, текст по SignalR не гоняем) →
`TurnAccumulator.SetPromptSnapshot` кладёт id в `StoredUserMessage.PromptSnapshotId`. У постов
ассистента своего id нет: `ChatPanel` разносит его по ленте скользящим окном. Кнопки нет у
постов сабагентов, у ходов без нового сообщения (продолжение цикла «до готово») и у истории
до появления поля; на делегированном ходу она появляется только после перезагрузки страницы.

**Слой CLI** (`CliLayerDto`) собирается по окружению ЭТОГО хода: имена инструментов и статусы
MCP-серверов из события `system/init` (дописываются в готовый файл через `AttachCliLayer`),
`CLAUDE.md` рабочей папки и профиля CLI с раскрытыми `@`-импортами
([ClaudeMdExpander](../../backend/ClaudeHomeServer/Services/Llm/Claude/ClaudeMdExpander.cs)),
каталог скиллов профиля, вес транскрипта `--resume`. Раскрытие импортов — НАША реконструкция:
`@~/…`, абсолютные пути и цепочка родительских `CLAUDE.md` не собираются, о чём сказано в UI.
Недоступны совсем: текст встроенного промпта Anthropic и описания инструментов. Файловая
часть дедуплицируется по хешу (`cliLayerFrom`) — `CLAUDE.md` весит десятки КБ и меняется редко.

**Разбор промпта** — кнопка «Проанализировать»: место `prompt-audit` в `LocalActionCatalog`
(группа «Чаты»), один вызов через `CheapTextRunner`, не больше одного разбора на сессию (409).
**Приватность:** по умолчанию исполнителю уходят только метаданные секций (ключи, размеры,
доли); фрагменты текста — по явной галочке, потому что в секциях лежат recall личных заметок
и долгая память персоны, а место может быть назначено на OpenRouter или Ollama. Сторож —
`PromptAuditPromptTests`.

**API:** `GET /api/sessions/{id}/prompt/{snapshotId}` (404 — снимок вытеснен ретеншном, UI
говорит об этом прямо), `POST …/analyze`.

## Артефакты сессии

За фич-флагом `session-artifacts`: панель справа от чата с вкладками — план (ExitPlanMode),
задачи (Todo/Task), агенты (субагенты Task/Agent + workflow-группы с раскрытием деталей:
промпт, лента вызовов, результат), изменённые/упомянутые файлы, ссылки. Всё derived из ленты
чата ([useSessionArtifacts.ts](../../frontend/src/hooks/useSessionArtifacts.ts)), без участия бэкенда.

### Какие Task-инструменты где живут

Имён три класса, и путать их дорого:

| Инструмент | Что это | Где доступен |
|---|---|---|
| `Task` (без суффикса) | запуск СУБАГЕНТА (делегирование) | всегда, блокировать нельзя |
| `TaskGet` / `TaskList` | чтение трекера аккаунта claude.ai — у нас там пусто | закрыты, пока подключён tasks-server |
| `TaskCreate` / `TaskUpdate` | план ТЕКУЩЕГО хода (преемник `TodoWrite`, которого CLI 2.1.226 уже не отдаёт) | закрыты только у сессий-исполнителей задач |
| `mcp__tasks__*` | продуктовые задачи (канбан, календарь) | по правам персоны / у исполнителя форсированно |

Сборка запретов — конструктор [ClaudeSession](../../backend/ClaudeHomeServer/Services/Llm/Claude/ClaudeSession.cs)
(`BuiltInTaskReadTools` / `BuiltInTaskPlanTools`), сторож — `BuiltInTaskToolsPolicyTests`.

План хода закрыт исполнителю намеренно: у него на руках задача трекера, и «закрытие» её
через `TaskUpdate` вместо `tasks_complete` оставило бы задачу висеть в `inProgress` — успешный
ход без закрытия продукт сейчас никак не досматривает. Обратная сторона: регламенты пантеона
OmO требуют вести todo, поэтому в переводах стоит оговорка «если инструменты доступны».

Чек-лист в ленте (`TodoPlanView`) собирается из плана хода; задачи `mcp__tasks__*`
подмешиваются в тот же список только когда плана хода в ленте нет (фолбэк для исполнителей
и старых транскриптов) — иначе два разных смысла слиплись бы в одной карточке.

Где план виден — **две поверхности, и обе бесплатны по месту**:

- карточка чек-листа в ленте (`TodoPlanView`) — «что запланировано», рисуется один раз, на
  последнем task-вызове ленты;
- подпись под индикатором ожидания (`planHint` → проп `hint` у `WaitingIndicator`) —
  «на каком я шаге»: `2/7 · Гоняю тесты`. Берётся `activeForm` пункта (в схеме `TaskCreate`
  он описан ровно как строка для спиннера), при его отсутствии — заголовок.

Отдельной ПАНЕЛИ под план хода нет и не планируется: `SESSION_KEYS` — это `plan`, `agents`,
`context`, а зона над композером в проектном чате занята git-баром, и список из 7–15 пунктов
съел бы там самую ценную полосу экрана (на мобиле — тем более). Панель «Задачи» в рельсе — это
канбан задач ПРОЕКТА, к плану хода отношения не имеет.

Рудименты старой `ArtifactsPanel` вычищены 2026-08-21: мёртвые ветки `panelBadge`
(`todos`/`notes`/`comments`/`files`/`links`), реестр `PANEL_META` на восемь категорий,
`countFiles` и кнопка «Артефакты сессии» в шапке чата, которая не рендерилась ни на одном
экране (её проп-триггер `onToggleArtifacts` не передавал ни один родитель).

## Контекст чата (флаг `chat-context`)

Материалы, закреплённые за чатом ЯВНОЙ кнопкой «в контекст чата»: файл проекта (включая
проектные заметки `notes/**.md`), ссылка ридера, задача проекта. Идея пересажена из ADR-0018
репозитория gpb-event-assistant, но механика другая: правая половина сплита — не «один
временно открытый объект», а список вкладок, живущий на сервере в `Session.Context`
(`data/sessions.json`, потолок 50 записей) и переживающий закрытие окна, переключение чата
и рестарт бэкенда. Обычный клик по файлу/ссылке/задаче остаётся просмотром и контекст
не трогает — попала в него вещь или нет, решает только человек (preview-механики VS Code,
где открытый файл сам едет в контекст, здесь нет).

**Отличия от исходного ADR-0018** (кроме явной кнопки вместо preview): состояния «половина
без чата» нет — полоса вкладок живёт над правой половиной сплита, а когда чат один в центре
или правая половина закрыта, те же материалы стоят чипами в шапке чата; отдельного projectId
у записи нет — контекст живёт только в проектных чатах, и адреса `file`/`task` читаются
внутри проекта сессии.

**Три списка материалов у чата — три разные вещи:**

| Список | Что это | Кто наполняет |
|---|---|---|
| Вложения композера | одноразовая передача файла в ближайший ход | человек, «прикрепить к чату» |
| Артефакты сессии | производный список того, что чат трогал | сам чат (derived из ленты) |
| Контекст чата | постоянные материалы разговора | человек, «в контекст чата» |

### Серверный контур

- Модель — `SessionContextEntry` (`Type`/`Id`/`Title`; значения `file`/`url`/`task` —
  единая точка `SessionContextTypes`, тех же строк на фронте). Аддитивное поле с дефолтом:
  старые `sessions.json` читаются штатно, `BackupSchema.Version` не двигается.
- REST: `GET/PUT /api/projects/{id}/sessions/{id}/context` — PUT идемпотентно меняет состав
  ЦЕЛИКОМ (валидация: белый список типов, непустой `Id`, потолок 50); событие
  `context_updated` с полным снимком уходит в группы session/project/user, поэтому вторая
  вкладка браузера видит замену без перезагрузки.
- **Признак «не найден» считает одна точка** — [SessionContextResolver.cs](../../backend/ClaudeHomeServer/Services/SessionContextResolver.cs):
  file — `SafeJoin` от корня проекта + `File.Exists`, task — резолв в том же проекте у того же
  владельца, url — не проверяется. GET отдаёт запись с `missing: true`, тул такую запись
  моделью не раскрывает (строка-предупреждение «скажи пользователю: запись устарела»), фронт
  рисует вкладку с предупреждением и меню «убрать/указать заново». Молча не чистим: состав
  меняется только PUT, а запись описывает желание человека, а не состояние файловой системы.
- Агентская сторона — MCP-тул `mcp__wsp__context_list` (первый житель `BASE_TOOLS`
  workspace-сервера: инструменты, живущие при любом наборе секций). Сессию определяет
  бэкенд по `X-Caller-Session-Id` — параметра у тула нет намеренно, иначе модель спросила бы
  состав чужого чата; `GET /api/mcp/session-context` сверяет владельца с sub токена (403 на
  чужого). Выдача: projectId сессии, записи с подсказкой, чем раскрыть (`files_read` /
  `tasks_get` / «открой у себя, если доступен WebFetch»).
- Подсказка хода — секция «Что приложено к этому чату»
  ([ChatContextPrompts.cs](../../backend/ClaudeHomeServer/Services/Prompts/ChatContextPrompts.cs)),
  появляется только при непустом контексте: «начни ход с `mcp__wsp__context_list` … и
  сверяйся с материалами». Состав берётся ЖИВЫМ `Func`-провайдером на каждом ходу — материал,
  добавленный кнопкой в идущем разговоре, попадает в промпт следующего хода без
  пересоздания адаптера (обычные поля контекста мид-сессию не живут).

### Инварианты

- **Состав `tools/list` от контекста не зависит** — `context_list` гейтится флагом ВЛАДЕЛЬЦА
  `chat-context` (env `WORKSPACE_CHAT_CONTEXT`, входит в отпечаток `shapes` wsp), а не
  непустотой контекста и не свойствами хода: иначе добавление материала мид-сессию меняло бы
  сигнатуру MCP и перезапускало CLI со всеми серверами. От содержимого контекста зависит
  только текст подсказки (она в сигнатуру не входит). Сторож — `McpToolsetStabilityTests`.
- **Правка контекста не двигает `UpdatedAt`** — как у `SetArchived`/`SetExpiry`: по `UpdatedAt`
  идут сортировка, секции дерева и непрочитанность.
- **Известное ограничение: персона с выключенными всеми wsp-секциями видит вкладки, а тул
  позвать не может.** У такой персоны `BuildWorkspaceContext` возвращает null — wsp-сервер
  не монтируется вовсе, и `context_list` в составе нет. Монтировать сервер по непустоте
  контекста нельзя (см. инвариант выше), поэтому подсказка хода в этом случае тоже НЕ
  добавляется — не обещать модель недоступное. Осознанное ограничение v1.
- Чаты вне проекта в v1 контекста не имеют вовсе (полоса/кнопки не рисуются); хостовые файлы
  (путь вне проекта) кнопкой не кладутся — запись адресуется путём от корня проекта, чужой
  сервер пометил бы её «не найден».

### Фронт

Полоса ([ChatContextBar.tsx](../../frontend/src/features/chatContext/ChatContextBar.tsx),
два варианта — вкладки и чипы) — тонкий слой НАД существующей маршрутизацией: клик по
материалу ведёт ровно тем же путём, что клик по нему в панели (open-file / ридер /
задача-aside), собственной маршрутизации нет; активная вкладка ВЫЧИСЛЯЕТСЯ из состояния
центра. Кеш состава — модульный стор [chatContext.ts](../../frontend/src/lib/chatContext.ts)
(по образцу `useExternalPreviewLinks`): его читают и полоса, и кнопки «в контекст», а пишут
его REST и событие `context_updated` из любого окна. GET состава ходит с `live: true` —
офлайн-кэш после переключения чата подставил бы чужой состав. Кнопки («в контекст чата»)
стоят в контекстном меню строки FileExplorer, в шапках FileViewer / ридера / карточки
задачи; гейт — флаг + открытый чат, повторное нажатие переключается на «Убрать» (идемпотентно,
индикация акцентом). Общая механика кнопок — [useContextButton.ts](../../frontend/src/features/chatContext/useContextButton.ts):
одно место, чтобы четыре поверхности не разъехались. Закрытие вкладки = удаление из
контекста без undo — возврат материала одна кнопка; тоста с действием в системе нет,
примитив ради этого не заводили.

### Критерии снятия флага

- Агент реально пользуется: `GET /api/mcp/calls` показывает стабильные вызовы
  `context_list` за срез, и люди не жалуются «модель игнорирует приложенные материалы»
  (тихий агент — риск слабых моделей цепочки фолбэка, смягчение — подсказка хода).
- Составы не гниют: записи `missing` исправляются или убираются, а не копятся.
- Три списка материалов (вложения/артефакты/контекст) не путаются — иначе вернуться
  к текстам и разведению подписей до снятия.

## Панель «Изменения» — «Также меняли» (какие ещё чаты трогали файл)

В панели «Изменения» (git status рабочего дерева) строка каждого изменённого файла несёт
тихий бейдж — число ЕЩЁ чатов проекта, менявших этот файл, с тултипом-именами на десктопе;
шапка diff-просмотра файла показывает тот же список кликабельными именами («Также меняли:
…») — клик открывает чужой чат. Источник — обратный индекс `ProjectFileSessionsIndex`
(бэкенд): `SessionChangedPaths.Extract` разбирает историю каждого чата проекта
(`file_changed` + `tool_use` из write-инструментов; правки вне заявленного хода попадают
со флагом `external=true`) и кеширует пути per-чат по `LastWriteUtc` его `history.json` —
лента перечитывается только когда реально изменилась. Эндпоинт
`POST /api/projects/{id}/files/changed-by` отдаёт для присланных путей список
`{sessionId, name, external}`; фронт (`lib/git.ts`, `applyChangedByFilter` — единственная
точка фильтрации) раскладывает ответ на две поверхности: в бейджи идут только записи с
`external=false` без активного чата (не быть «другим» самому себе), а пути активного чата
(включая `external=true`) собираются в `myChangedPaths` — серверный источник фильтра
«кто менял файл» (фронтовый дубль по живой ленте снесён).

Тем же двум множествам подчинён **фильтр списка** — кнопка в шапке панели открывает меню
из пяти взаимоисключающих режимов со счётчиками: все изменения · только этот чат ·
другие чаты · несколько чатов · правки вне чатов. Каждому режиму отвечает СВОЙ значок
бейджа строки, чтобы фильтр и список говорили одним языком: `MessageSquareDot` (мой),
`MessageSquare` (чужой, начиная с одного), `MessagesSquare` (2+ чатов — файл, за который
«дерутся»: там вероятны конфликты и затирание чужих правок), `User` (мимо чатов); у «всех
изменений» значок нейтральный (`ListFilter`), иначе с кнопки не прочитать, включён фильтр
или нет. Счётчик каждого пункта считается по ПОЛНОМУ рабочему
дереву (отвечает «сколько получу, если нажму») и от текущего выбора не зависит; корзины —
не разбиение: файл, который трогали и активный чат, и чужой, попадает и в «этот чат», и в
«другие чаты», и в «несколько чатов». Классификация и счётчики — чистые функции `fileMatchesChatFilter` /
`countChatFilter` рядом с `fileChatBadge` ([lib/gitFormat.ts](../../frontend/src/lib/gitFormat.ts)),
поэтому фильтр и бейдж строки не могут разойтись в трактовке. Инвариант: фильтр — ЧИСТО
отображение. Стейджинг, «Отменить все», guard переключения ветки и форма фиксации ходят по
полному `workingFiles`, а в самой форме фильтр не действует вовсе — иначе «Зафиксировать»
расходилось бы с видимым списком. Режим виден без открытия меню: иконка кнопки, полоса
состояния над списком («Другие чаты · 5 из 42», крестик сбрасывает) и пустое состояние
говорят одним и тем же языком. Меню доступно только при активном чате и в скоупе
«Не зафиксировано» — в скоупах коммита и стэша `changedBy` не про эти файлы.

Атрибуция не врёт после коммита: у чата хранится `Session.CommittedFilePaths` — пути,
чьи правки уже зафиксированы в git; актуальная атрибуция = пути из истории МИНУС это
множество (вычитание — после кеша, на каждый запрос). Коммит ловит
`CommitAttributionService` по сдвигу HEAD на пути `GET git/status` (`branch.oid` уже есть
в статусе; работает и для коммитов мимо продукта — Bash в чате, терминал): пути диапазона
(`git diff --name-only old new`) пересекаются с множествами чатов, совпавшие помечаются
одной пачкой (`MarkFilesCommitted`, один `SaveSessions`). Новая правка файла чатом
(tool_use write-инструмента или file_changed, кроме ходов в чужом worktree) пометку
снимает — файл снова числится за чатом. Принятые ограничения: сдвиги HEAD при погашенном
сервере не засчитываются (маркер в памяти); reset/откат коммита пометки не снимает;
правка в окне «коммит → пометка» теряет атрибуцию до следующей правки; снятие пометки —
по заявке tool_use, а не по успешному результату.

Ограничения (осознанные, не баги):
- в бейджи «Также меняли» правки вне заявленного хода (`external=true` — Bash/скрипты
  модели или человек в IDE) не попадают — бейдж отвечает на вопрос «что менял ИМЕННО этот
  чат своим ходом»; режим фильтра «только этот чат» их учитывает;
- чаты в отдельном git worktree и ходы, ушедшие в чужое дерево (`TurnWorktree`), из индекса
  исключены — их правки живут не в `rootPath` проекта;
- пока панель смотрит worktree активного чата (свой git-контекст), `changedBy` не грузится —
  пути status относятся к другому дереву, индексу они не знакомы;
- правки живого хода соседнего чата видны с лагом до его снапшота в историю (после хода/тула);
- на мобиле тултипа с именами нет (`title` не работает по тапу) — только счётчик бейджа;
- папки и переименования, которых git status не разложил на файлы, индекс не находит —
  пустой список у такой строки норма, а не сбой;
- частые запросы эндпоинта при живом ходе чата приняты осознанно: ответ ограничен присланными
  `paths`, а кеш per-чат не даёт перечитывать нетронутые истории.

### Значок «правки не зафиксированы» в списке чатов

Тот же ответ `changed-by` даёт **третью** поверхность: в списке чатов проекта
([SessionList](../../frontend/src/components/SessionList.tsx)) чат, за которым числятся
незафиксированные правки, несёт тихий значок `GitCommitVertical` с тултипом «Правки этого
чата не зафиксированы в git». Множество (`dirtySessionIds` в `lib/git.ts`) выводится
БЕЗ единого запроса к серверу: `changed-by` спрашивают ровно по грязным путям git status,
а сервер уже вычел `CommittedFilePaths` — значит любой `sessionId` в ответе и есть чат с
незакоммиченным. Снятие значка после коммита получается даром той же цепочкой
`git_status_changed → status → changed-by`: закоммиченный файл уходит из статуса.

От `changedBy` отличается ровно одним: **активный чат не исключается** — свой значок он
носит наравне с прочими. А вот `external=true` отбрасывается так же, и это принципиально.
Пока в чате идёт ход, файловый вотчер пишет в его историю КАЖДУЮ правку файлов репы, в том
числе чужую — человека в IDE или соседнего чата; она оседает как `external`. Для
пер-файлового бейджа это терпимо, а вот значок агрегирует: замер на боевых данных
(21 чат, 23 грязных пути) дал **48 совпадений «файл-чат», из которых 39 — только внешние**,
и горело 9 чатов вместо двух настоящих. Чат про CSS шапки оказывался помечен правками
`PreviewController`/`DevServerService`, которых не видел. С отсечением `external`
остаются ровно те чаты, что правили файл сами.

**Признак наследуется вверх по ветке** (`withAncestors` в
[lib/chatTree.ts](../../frontend/src/lib/chatTree.ts)): чат с незафиксированными правками
зажигает значок и у всех своих предков — иначе свёрнутая ветка (а равно просто длинная)
прятала бы работу, и родитель выглядел бы чистым. Обход идёт по тому же
`parentSessionId`, по которому строится дерево, поэтому значок не может разойтись с
нарисованной иерархией, и считается по ПОЛНОМУ списку чатов проекта: предок, скрытый
фильтром, остаётся звеном цепочки к видимому прародителю. Наследование работает во всех
режимах списка — иерархия лежит в данных и без включённого режима «Иерархия».

Свои правки и унаследованные разведены ТОЛЬКО текстом подсказки («Правки этого чата не
зафиксированы в git» против «Не зафиксированы правки во вложенных чатах»): два оттенка
серого на иконке 13 px не различить, а молчаливый значок у родителя врал бы, что тот
правил файлы сам. Совпало и своё, и потомков — показывается своё.

Трёхзначность как у `myChangedPaths`, но опора другая — достоверность данных, а не наличие
активного чата: пустой git status = пустой `Set` («ни у кого»), worktree-контекст и ошибка
`changed-by` = `undefined` (значков нет), а падение самого `git status` (офлайн) последнее
известное множество НЕ гасит — сетевой сбой ничего не сообщает о фиксации правок.

Значок наследует все ограничения атрибуции, но агрегация делает их заметнее — пер-файловый
бейдж врал точечно, значок врёт про весь чат:

- коммит при погашенном сервере не засчитан (маркер HEAD в памяти) — значок останется, и
  любая последующая грязь на «его» файле будет его поддерживать;
- файл, который чат когда-то правил САМ, испачкал кто-то другой — помечен всё равно чат
  (отсечение `external` снимает обратный случай, а этот остаётся);
- созданный чатом untracked-файл, который никогда не закоммитят, держит значок вечно;
- чаты в отдельном worktree значка не получают вовсе (из индекса исключены), а пока
  активный чат смотрит в своё дерево, значки гаснут у всех чатов проекта;
- в глобальном списке «Чаты» (вне проектов) значка нет — там чаты без `rootPath`;
- на мобиле тултип по тапу не всплывает, значок остаётся без пояснения.

## Панель «Документация»

Документация проекта (`README.md` + настраиваемые папки, по умолчанию `docs/**`) как связный корпус, а не список файлов:
дерево документов, превью с оглавлением, поиск по заголовкам и телу, переходы по
относительным ссылкам между документами, обратные ссылки («кто сюда ссылается») и передача
в чат. Панель живёт в правой рельсе рядом с «Файлами»; открывается README на всю панель (домашний вид, крестик уводит к списку)
([DocsPanel.tsx](../../frontend/src/pages/workspace/DocsPanel.tsx)).

Чем отличается от соседей: «Файлы» — дерево репозитория для работы с кодом, «Заметки» —
личный vault вне репы, «Знания» — семантический поиск через Dify.

Устройство:

- **Индекс** собирает бэкенд ([DocsIndexService](../../backend/ClaudeHomeServer/Services/Docs/DocsIndexService.cs)):
  заголовки со слагами, ссылки (doc / repo / external) и обратные ссылки — разворот
  исходящих, отдельного хранилища нет. Кеш ключуется корнем папки и живёт до изменения
  **отпечатка области** (путь + время правки + размер каждого файла): по «максимальному
  mtime и количеству» замена одного файла другим в ту же секунду прошла бы незамеченной.
- **Область настраивается** (кнопка в шапке панели, диалог
  [DocsScopeDialog.tsx](../../frontend/src/pages/workspace/DocsScopeDialog.tsx)) по трём
  независимым осям — `Project.DocsFolders` / `DocsRootFiles` / `DocsExtensions`, у каждой
  `null` = дефолт, пустой список = «ничего отсюда»:
  - **папки** (дефолт `docs/`) — соглашение в проектах разное: `docs`, `wiki`,
    `documentation`, спеки рядом с кодом. Берутся рекурсивно, поэтому вложенные в диалоге
    показаны как «внутри docs», а не отдельными галками;
  - **файлы корня** (дефолт `README.md`) — поимённо: в корне лежит и код, папкой его не
    выберешь, а `CHANGELOG`/`ROADMAP`/`CLAUDE.md` читают наравне с `docs/`. Выбранный файл
    попадает в область даже с расширением вне списка типов — явный выбор сильнее фильтра;
  - **типы файлов** (дефолт «Markdown») — выбираются **группами**, а не расширениями:
    каталог `DocsIndexService.TypeGroups` перечисляет ровно то, что продукт умеет открыть —
    Markdown, Текст, PDF, Office, Visio, Диаграммы (drawio), Картинки, Аудио, Видео.
    Хранятся ключи групп: расширений три десятка, россыпью они не читаются и в настройке
    не нужны;
  - **исключения** (`excludeFolders`, дефолт — пусто) — подпапки, вычитаемые из выбранных
    папок: рядом с документацией живут рабочие артефакты (`workdir` спайков, `demo-data`,
    песочницы агентов), и глобальный стоп-лист обхода (`node_modules`, `dist`…) их не знает —
    это законные папки репозитория. В диалоге исключение ставится кликом по вложенной строке
    («внутри docs»): перечёркнутая иконка, повторный клик возвращает. Правила: явное
    включение сильнее (запись, совпавшая с выбранной папкой или лежащая вне всех выбранных,
    отбрасывается нормализатором), снятие выбранной папки уносит и её исключения, после
    нормализации ось всегда список. В `.docs` ключ `excludeFolders` пишется только непустым;
    в `PUT /scope` null означает «не трогать» (асимметрия к старым осям: закешированный
    старый бандл фронта не знает оси и не должен стирать исключения своим null), `[]` —
    «убрать все». Отпечаток кеша исключённые папки не считает: их файлы в корпус не
    попадают, и правки внутри исключённого корпус пересобирать не обязаны — область
    въезжает в ключ кеша целиком.

  **Файлы без текста** (`Text: false` у группы — pdf, office, visio, картинки, звук, видео)
  попадают в список, но корпуса у них нет: содержимое не читается вовсе (незачем держать
  в кеше мегабайты байтов), заголовков, ссылок и поиска по телу не будет, а вместо превью
  панель предлагает открыть файл в центре — там уже есть pdf.js, OnlyOffice, drawio и плееры.
  В индексе и в `GET docs/doc` они помечены `binary`.

  Кандидатов считает бэкенд: папки с документами не глубже трёх уровней (без скрытых и
  `node_modules`) и файлы корня. И счётчик папки, и список файлов корня считаются по **всем**
  поддерживаемым типам, а не по выбранным: пока выбор в диалоге редактируется, цифра «43»
  иначе врала бы, а свой же выбранный `NOTES.txt` пропадал бы из списка при сужении типов.
  Есть ручной ввод папки: пустой пока папки в кандидатах нет, а завести область заранее —
  нормальное желание. Корень проекта папкой выбрать нельзя — это был бы обход всего репозитория.
- **Гейт области**: `GET docs/doc` отдаёт только то, что попало в индекс, — и следует за
  настройкой: сузили область, и вчерашний документ отдаваться перестаёт. Без гейта эндпоинт
  стал бы вторым универсальным файл-ридером поверх `files/content`.
- **Порядок списка**: README первым, дальше по папке и **заголовку** (не по имени файла) —
  панель подписывает строки заголовками, и сортировка по пути выглядела бы в ней случайной.
- **Список папок** — оглавление для самого списка: поповер по кнопке либо, кому нужно
  постоянно, закреплённый блок над документами (переживает перезагрузку). У блока своя
  прокрутка и своя высота на хендле — папок бывает два десятка, и без ограничения он
  вытеснил бы сами документы. Текущая папка (та, где выбранный документ) выделена, переход
  подсвечивает секцию миганием — иначе после прыжка непонятно, куда смотреть. Мигание
  запускается **после остановки прокрутки** (`scrollend`, с таймером на случай браузера
  без него): затухание длится 300 мс и вместе со смуз-скроллом отыгрывало вхолостую —
  до места доезжала уже погасшая подпись.
- **Свёрнутые папки**: клик по подписи группы прячет её документы (шеврон + счётчик
  скрытых), состояние хранится по проекту — папки у репозиториев разные. Высота едет
  анимацией `grid-template-rows` от `0fr` к `1fr`, замерять содержимое не нужно;
  `visibility` гасится после анимации, иначе скрытые строки остаются в обходе табом.
  Прыжок в свёрнутую папку из оглавления разворачивает её и прокручивает следующим
  кадром — до перерисовки координаты ещё от свёрнутого списка.
- **Подпись группы** — путь через точку (`docs · architecture`): слеш читается как путь
  к файлу, а здесь это ветка оглавления. Шеврон стоит в колонке бейджей расширений,
  чтобы левый край списка читался одной линией.
- **Кнопки уровней** (в шапке) сворачивают и разворачивают по **одному уровню
  вложенности** за нажатие — от самого глубокого открытого к корню и обратно. «Свернуть
  всё» одним махом прятало бы и то, что нужно было оставить. Кнопка гаснет, когда её
  направление исчерпано.
- **Закреплённые документы**: бейдж расширения под курсором превращается в булавку —
  отдельной кнопке в строке места нет, а место иконки и так занято состоянием документа.
  Закреплённые **дублируются** блоком у нижнего края списка (своя прокрутка, сворачивается
  как папка) и при этом остаются на своих местах в папках, помеченные булавкой. Порядок
  внутри блока задаётся перетаскиванием (`@dnd-kit/sortable`, пороги жеста — общие
  [lib/dnd.ts](../../frontend/src/lib/dnd.ts), как на доске задач), поэтому в хранилище
  лежит **список**, а не множество. Состояние — по проекту.
- **Якоря**: слаг считается от текста заголовка, очищенного от markdown-разметки, одинаково
  на сервере и на клиенте ([docsLinks.ts](../../frontend/src/lib/docsLinks.ts)) — это контракт,
  по которому панель находит раздел. Якорь из ссылки декодируется (кириллица в href приезжает
  процент-энкодингом).
- **HTML в markdown** исполняется, но только после санитайза: `rehype-raw` +
  `rehype-sanitize` со схемой [markdownHtml.ts](../../frontend/src/lib/markdownHtml.ts).
  Без него README выглядел как текст с торчащими `<div align="center">` и `<img>` —
  так центрируют логотип и скриншоты почти в каждом репозитории. Схема расширяет
  `defaultSchema` точечно (align, размеры картинки, `details`/`summary`, внутренние схемы
  ссылок `wikilink:`/`noteatt:`); `script`, `style`, `iframe`, `form`, обработчики `on*`
  и `javascript:`-ссылки остаются вырезанными — тем же рендером идут ответы модели и
  чужие заметки, источник недоверенный всегда. Проверяется тестами
  [markdownHtml.test.ts](../../frontend/src/lib/markdownHtml.test.ts).
- **Картинки документа** грузятся через `files/stream`: путь в `src` относителен документа,
  а не адреса страницы (`resolveDocImage` + `api.files.fileUrl`). Работает и в панели, и в
  центральной области — README там рендерит `DocComments`, и резолв прокинут туда же.
- **Оглавление** снимается с реального DOM после рендера ([useHeadings.ts](../../frontend/src/hooks/useHeadings.ts)),
  тем же хуком пользуется панель «План» — список TOC и цель скролла физически один узел.
  Раскрывается наведением на кнопку (клик оставляет открытым) — тот же жест, что у списка
  папок. Без заголовка, крестика и ряда иконок справа: в узком поповере они забирали больше
  внимания, чем сами заголовки, поэтому «раздел в чат» переехал на правый клик по строке.
- **Выделение следует за показанным документом**, а не за последним кликом: строка выбрана,
  пока документ открыт в превью либо в центральной области. Панель получает `activeFilePath`
  и `onCloseFile` из `WorkspacePage` (как «Изменения») — файл в центре закрывают крестиком
  просмотрщика, мимо панели, и без этой связи строка оставалась выделенной. Повторный клик
  по показанному документу закрывает его — той же строкой, что открыла.
- **В чат** двумя способами: документ целиком уходит **путём-вложением** (Claude прочитает
  файл сам, контекст не раздувается), раздел из оглавления — **цитатой исходного markdown**
  в композер.
- Панель подписана на `filesChanged`: правки `docs/` прямо из чата обновляют дерево, превью
  и обратные ссылки без перезагрузки.

### Типы документов и свойства

У документа бывает **тип** (ADR, спека, runbook), у типа — **свойства**: статус, дата,
ответственные, ссылка на заменяющий документ. Значения правятся из интерфейса: колонка
справа от открытого документа, плашка главного значения в шапке превью панели,
точка-метка в строке дерева.

- **Свойства и комментарии — ОДНА колонка** справа от текста
  ([DocPropsPanel](../../frontend/src/features/docs/DocPropsPanel.tsx)), свойства сверху.
  Панель комментариев уезжает туда порталом (`panelTarget` у `DocCommentedMarkdown`) —
  без этого она рисует собственный сайдбар, и рядом с документом оказывается две колонки.
  Обе секции — общий примитив [SidebarSection](../../frontend/src/components/ui/SidebarSection.tsx):
  один вид заголовка, сворачивание с анимацией (grid 0fr→1fr) и памятью в localStorage.
  **Свойства свёрнуты по умолчанию** — документ открывают читать, а не править поля;
  комментарии раскрыты. Свёрнутая секция занимает ровно строку заголовка: обе закрыты —
  колонка в две строки, без пустоты под ними.
- **Колонка ПЛАВАЮЩАЯ** (`float: right`, контейнер — `flow-root` вместо clearfix), а не
  вторая колонка флекса: свёрнутые секции это две строки заголовков, и в двухколоночной
  раскладке весь текст ниже всё равно жался бы в остаток ширины, оставляя справа пустую
  полосу до конца документа. Обтекание пускает текст под колонку. Цена — колонка не липнет
  при прокрутке (`sticky` с `float` не работает); ради обтекания это принято сознательно.
  Из-за обтекания же панель комментариев внутри `DocCommentedMarkdown` отказывается от
  своей flex-раскладки, когда уезжает порталом: flex-контейнер floats не обтекает.
  **Плата за float — соседи в markdown:** обычный блок обтекается только строками, а его
  бокс уходит ПОД плавающий элемент, поэтому подложка цитаты заезжала под колонку, а
  маркеры списка прятались за ней. Лечится своим BFC у таких блоков — `display: flow-root`
  у `blockquote`/`ul`/`ol` в [MarkdownViewer](../../frontend/src/components/MarkdownViewer.tsx)
  (у `pre` и таблицы он уже есть от `overflow`). Новый блок с фоном или рамкой — добавлять
  туда же.
- **Колонка встаёт сбоку, только если документу остаётся читаемая ширина** (`SIDE_MIN_W`,
  порог по ширине просмотрщика, а не окна). При открытых панелях центр сжимается до трети
  экрана, и колонка в 290px оставляла документу лапшу в одно слово — там она уезжает под
  текст (и в разметке встаёт после него), как на мобиле.
- **Свойства формой:** подпись сверху, контрол под ней, поля даты и текста раскрыты сразу
  (в колонке на это есть место), плашка выбора — по содержимому, а не во всю ширину, иначе
  читается как поле ввода. Показываются все свойства схемы, включая пустые.
- **Габарит контролов задан одним числом** (`useChipHeight`: 26 на десктопе, 40 на тач):
  примитивы приходят разными (плашка 26, кнопка xs 24, поле ввода 40), и без общей высоты
  ряд подскакивал на каждом раскрытии поля.
- **Ключи, которых нет в схеме типа, не показываются.** Править их нечем (вид свойства
  неизвестен), а текст документа не режется — строка `**Основание:** …` видна в нём на
  своём месте. Дублировать её контролом-заглушкой значит спрашивать у читателя «что это».
- **У комментариев нет кнопки «Скрыть»** — в фильтре остались «Все / Откр.», а спрятать
  список целиком можно сворачиванием секции, тем же жестом, что и у соседей по колонке.
- **Данные тянутся лесенкой:** настройка области (в ней схема) → документ → индекс, и
  последний только если у типа есть свойство-ссылка. Просмотрщик открывают на любом файле
  репозитория, платить тремя запросами за каждый `.png` незачем.
- **Строки шапки из текста НЕ вырезаются** — ни в центре, ни в превью. Причина не
  косметическая: комментарии к документу якорятся абсолютными офсетами в тексте файла
  (`DocComments` считает их по тому же тексту), и вырезание блока в середине увело бы все
  якоря ниже шапки. Поэтому значения видны дважды — контролами в полосе и строками в самом
  документе; последние и есть файл.
- **Точка-метка есть и у страницы раздела** (`docs/contract.md` при папке `docs/contract/`).
  Своей строки в дереве такая страница не имеет — её роль играет подпись раздела, поэтому
  метка живёт в её правом хвосте, перед счётчиком скрытых. У папки без парной страницы точки
  нет: читать статус не из чего.

- **Значения живут в самом md**, строками `**Ключ:** значение` в шапке — ровно так уже
  написаны ADR проекта, поэтому формат не вводился, а был описан: миграции нет, файл
  читается в git, на GitHub и в wiki. Разбор — [DocProperties](../../backend/ClaudeHomeServer/Services/Docs/DocProperties.cs).
  Контур шапки строгий: front-matter → H1 → **непрерывный** блок строк свойств до первой
  пустой строки, заголовка или ограды кода. Двоеточие обязано стоять ВНУТРИ `**…**` —
  иначе свойствами стали бы `**ОБЯЗАТЕЛЬНО**: …` из переводов omo и `**OpenTelemetry-based**
  observability … режимами:` из observability, которые стоят ровно на позиции шапки.
  **Оформление строки свободное** — голая строка (так написаны ADR этого репозитория),
  пункт списка (`- **Статус:** Предложено`) или цитата (`> **Статус:** Проектирование`):
  в других проектах пишут именно так, и без этого фича там не работала бы вовсе. Ложных
  срабатываний маркер не добавляет — контур всё равно пускает только блок сразу за H1;
  при записи оформление сохраняется, новое свойство встаёт в том же виде, что соседи.
  **Значение — ровно своя строка:** перенос на следующую в него не входит и не правится.
  Приклеив продолжение, запись схлопнула бы в одну строку целый абзац шапки — а такие
  шапки в проектах есть (`> **Статус:** Концепт.` с описанием на три строки следом).
- **Схема типов — только в `.docs`** репозитория, секцией `docTypes`
  ([DocTypeSchema](../../backend/ClaudeHomeServer/Services/Docs/DocTypeSchema.cs)): тип это
  свойство корпуса, а не предпочтение владельца папки. Тип определяется папками + необязательной
  маской имени (`docs/adr` + `ADR-*.md`), в самом документе не указан. Цвет значения — имя РОЛИ
  (`success`, `danger`…), а не цвета: зелёного в токенах нет, роль кладётся на токен на фронте.
- **Инвариант кеша:** свойства разбираются при сборке корпуса (зависят только от файла), а тип
  проставляется **проекцией на выходе** `GetIndex`. Отпечаток кеша считается по документам, и
  тип, зашитый при сборке, показывался бы старым до перезапуска сервера после правки схемы.
- **Инвариант записи `.docs`:** файл ПРАВИТСЯ через `JsonNode`, а не пересобирается — к
  `WriteScopeFile` ведут пять дорог из контроллера (область, создание документа в корне,
  переезд и удаление «Начала», вынос области в репозиторий), и пересборка означала бы, что
  кнопка «вернуть README в область» стирает схему типов у всей команды. Неразобранный `.docs`
  не перезаписывается вовсе — 409.
- **Запись значения** (`PUT docs/property`) проходит три гейта: область (документ есть в
  индексе), содержимое (только markdown — иначе pdf из типизированной папки был бы прочитан
  как текст и записан обратно испорченным) и схема (ключ описан у типа — иначе это универсальный
  редактор чужих файлов мимо правил `FilesController`). Правится ровно хвост строки после
  `**Ключ:** `, поэтому дифф в git — одна строка; BOM и стиль концов строк сохраняются.
  Значение-ссылка пишется markdown-ссылкой: её чинит существующий `UpdateLinks` при
  переименовании цели, и цель получает обратную ссылку в графе. Свойство-дата с `autoUpdate`
  переписывается той же записью файла и только если значение реально изменилось.

Вне объёма первой версии: переходы по ссылкам в центральной области (там документ
рендерит `DocCommentedMarkdown`), картинки с относительными путями в превью, индикатор
устаревшей документации.

## Панель «Сервисы» (dev-серверы проекта)

Запускает дев-серверы проекта и показывает их страницу в iframe. Вместе с «Терминалом»
образует группу инструментов проекта (`TOOLS_KEYS`) — отдельную группу рельсы. Обе кнопки
по умолчанию лежат в ящике рельсы («…», `defaultTucked` у `wsPanels`): доступны всегда,
но столбец иконок не занимают. Настройки проекта «Инструменты» (`Project.ToolsEnabled`),
гейтившей эту группу, больше нет — видимостью кнопок управляет ящик, а не настройка.
**Ключ панели и все эндпоинты остались `preview`** — переименована только подпись, потому
что ключ лежит в сохранённых раскладках localStorage.

### Откуда берутся сервисы

[ProjectServiceDiscovery](../../backend/ClaudeHomeServer/Services/ProjectServiceDiscovery.cs)
разбирает манифесты и складывает результат с сохранёнными конфигурациями; дубли
схлопываются по сигнатуре «команда + аргументы + cwd», приоритет — у сохранённых, затем у
конфигураций Rider (человек настроил их явно, остальное — догадки разбора):

| Источник | Что читаем |
|---|---|
| `launch.json` | `.claude/launch.json` проекта — редактируемые, формат Claude Desktop |
| `rider` | `.run/*.run.xml` и `.idea/**/runConfigurations/*.xml` |
| `npm` | серверные скрипты `package.json` (`dev`, `start`, `serve`, `watch`, `dev:*`) |
| `dotnet` | профили `Properties/launchSettings.json` с `commandName: Project` |
| `docker-compose` | имена сервисов и первый хостовый порт |
| `procfile` / `makefile` | строки-таргеты с серверными хинтами |

Из конфигураций Rider поддержаны `LaunchSettings`, `js.build_tools.npm`, `docker-deploy` и
составные `multilaunch`. Скриптовые типы (`ShConfigurationType`, `PowerShellRunType`)
пропускаются осознанно: отличить в них сервер от разовой утилиты нечем. Пути с
`$PROJECT_DIR$` резолвятся через `SafeJoin` — конфигурации сплошь ссылаются наружу
(`$PROJECT_DIR$/../frontend`, интерпретатор в System32), и такие мы не берём.

**Составные конфигурации** становятся группой: у неё нет своей команды, есть `Members` —
id участников (ссылки `runConfig:{фабрика}.{имя}` резолвятся по самому длинному совпадению
имени, иначе «Backend» перехватывал бы ссылку на «Telemetry Backend»). Запуск поднимает
участников по очереди, остановка гасит всех, статус производный: `started` — живы все,
`partial` — часть, `error` — упал кто-то. Сигнатура дедупликации у групп своя (по составу):
с общей все группы проекта выглядели бы одинаково «пустой командой» и осталась бы одна.

### Запуск и готовность

[DevServerService](../../backend/ClaudeHomeServer/Services/DevServerService.cs) держит по
процессу на `projectId:serviceId` и отдельно — «активный для превью» сервис, на порт
которого смотрит iframe. Ключевое: **`started` ставится только когда порт реально принимает
TCP-соединение** (поллинг до 30 с), иначе iframe грузился в мёртвый порт. Порт прокидывается
в окружение (`PORT`, `ASPNETCORE_URLS`) либо ловится из вывода регуляркой. В песочнице порт
берётся из опубликованного пула `Sandbox:PortRange*` — случайный хостовый не проброшен наружу
и до него не достучится прокси. Убивает процесс только launcher, который его запустил:
`Process.Kill` на docker-клиенте не трогает процесс внутри контейнера.

### Сервисы, запущенные снаружи

Порты сервисов с известным `SuggestedPort` пробуются на слух (`IsPortListeningAsync`): порт
отвечает, а процесс не наш → статус `external`, кнопка «Показать страницу» вместо «Старт»,
ни остановки, ни логов (процесс чужой). Скана слушающих портов машины при этом нет — щупаем
только свои. Провал старта с занятым портом объясняется словами, а не хвостом лога.

**Инвариант:** порт для внешнего превью выбирает сервер по конфигурации сервиса
(`POST /preview/active-external` принимает только `serviceId`). Приняв порт от клиента,
эндпоинт стал бы туннелем на любой localhost-порт хоста под авторизацией владельца проекта.

### Логи

Вывод копится в `OutputRingBuffer` (общий примитив с терминалами, 200k символов, обрезка с
запасом в четверть — сдвиг буфера иначе шёл бы на каждой строке). Рассылается тиком раз в
100 мс одним куском: `dotnet build` и `vite` печатают тысячами строк, и поштучная отправка
означала бы столько же сообщений SignalR и вызовов `term.write`. Группа — на конкретный
сервис (`DevServerService.LogGroup`), иначе вывод сыпался бы во все вкладки пользователя.

Подписка `JoinPreviewLog` **возвращает** накопленный буфер, а не рассылает его сообщением:
адресная рассылка приходит в соединение, а не в конкретный вьюер, и при пере-монтировании
(в dev его гарантирует StrictMode) лог показывался дважды. Снимок берётся до входа в группу
— строка в этот зазор потеряется, но не задвоится.

В UI — вкладка «Логи» рядом со «Страницей», read-only xterm (Vite и dotnet печатают ANSI,
в `<pre>` они стали бы мусором). Переключатель «Этот | Все» показывает логи всех живых
сервисов вперемешку с цветным префиксом `[Имя]`, как docker compose; у группы «свой» лог —
это логи её участников. Упавший сервис логов не имеет: его инстанс удалён из реестра вместе
с буфером, причина остаётся в `service.error`.

### Прокси

Middleware в [Program.cs](../../backend/ClaudeHomeServer/Program.cs) форвардит
`/preview/{projectId}/**` на `http://127.0.0.1:{порт активного}`. Стоит до endpoint routing,
поэтому `[Authorize]` там не работает: токен берётся из cookie `cc_preview` (её ставит фронт
перед загрузкой iframe — уходит и с сабресурсами) либо из `?access_token`/`Bearer`, дальше
сверяется владелец проекта. Префикс срезается вручную: `HttpTransformer.Default` дописывает
путь к базовому адресу, и `/preview/{id}` уезжал на дев-сервер дважды.

## Продуктовая история «Что нового»

Основной функционал, кнопка в шапке: AI-сводка изменений **по всем проектам сразу** — что
нового и чем полезно пользователю (не код, не diff).
[ChangelogService](../../backend/ClaudeHomeServer/Services/ChangelogService.cs) собирает git-коммиты
из репы продукта — путь в `Changelog:SourceRepoPath` (машинно-специфичный, в
`appsettings.Local.json`; без него раздел показывает «не настроено»), имя —
`Changelog:SourceProjectName` (дефолт = имя папки). Дальше группирует по дням и суммирует
каждый день **одним вызовом** через общий
[OneShotClaudeRunner](../../backend/ClaudeHomeServer/Services/Llm/OneShotClaudeRunner.cs) (модель
`Changelog:Model`, дефолт haiku; лениво, продуктовый промпт — польза, а не техника; таймаут
`Changelog:TimeoutMs`, дефолт 480с). Промпт просит не более 12 пунктов на день (агрессивная
группировка) и короткий `scoreReason`. Области выравниваются между днями подсказкой частых
`area` из кеша (`KnownAreas`) + канонизацией `NormalizeAreas` (схлопывает «Чат»/«чат»/«ЧАТ»).
Fallback без LLM (`FallbackItems`, при недоступном claude) кладёт `area` по типу коммита
(feature→«Новое», fix→«Исправления», improvement→«Улучшения», иначе «Прочее») и честный
`scoreReason` «сводку собрать не вышло». **Дробить день на параллельные чанки пробовали —
отказались**: старт CLI (~15с) платится за каждый вызов, а чанки не видят друг друга и дробят
смысл (замер на 59 коммитах: один вызов — 141с/13 пунктов, три чанка — 182с/29 пунктов).
Каждый пункт: `type` (feature/improvement/fix/other), `area` (раздел продукта — Claude
определяет сам), `emoji`, `title`, `benefit`, `authors`, `projects`. Результат кешируется на
уровне продукта в `data/changelog/product.json` (ключ дня = хеш sha-набора всех проектов —
сводка одна для всех и перегенерируется только при новых коммитах дня). Алиасы авторов —
`Changelog:AuthorAliases` (email → имя). Эндпоинты — глобальный
[HistoryController](../../backend/ClaudeHomeServer/Controllers/HistoryController.cs) (`api/history/*`).
Фронт: [ProductHistory.tsx](../../frontend/src/components/ProductHistory.tsx) — полноэкранная лента
по дням (Сегодня/Вчера/дата). Внутри дня пункты **сгруппированы по области** (`area`), и режим
показа адаптивный (`LIST_MODE_MAX = 12`): мало пунктов — все области идут **секциями списком**
(заголовок `CategoryHeader` + свой таймлайн), много — **вкладки-подчёркивания** `AreaTabs`
с таймлайном активной области. Таймлайн (`GroupTimeline`) — маркеры-кружочки единым
accent-цветом. Иконки авторов — эмодзи-роли (`AUTHOR_EMOJI`: известным авторам сопоставлены
фиксированные эмодзи, новым — из пула детерминированно по имени). Фильтр по исполнителю (чипы,
авторы по алфавиту; режим считается от отфильтрованных пунктов). Навигация по дням —
**календарь** (`DayCalendar`): дни с изменениями кликабельны, сводка генерится лениво только
для выбранного дня. Кнопка «Что нового» в [HubHeader](../../frontend/src/components/HubHeader.tsx)
видна во всех разделах (событие `open-product-history` → overlay в
[App.tsx](../../frontend/src/App.tsx)), бейдж считает новые коммиты с последнего захода
(timestamp в `localStorage`).

## Механики OmO в чатах (флаг `work-loop`)

Тексты — переводы oh-my-openagent ([omo-adoption.md](../omo/adoption.md)); рантайм-константы —
[Services/Prompts/OmoPrompts*.cs](../../backend/ClaudeHomeServer/Services/Prompts/OmoPrompts.cs)
(Categories генерируются скриптом docs/omo/gen-omo-prompts.ps1 из переводов).

- Своя вставка «магического слова ultrawork» УДАЛЕНА: слова `ultrawork`/`ulw` ловит
  keyword-detector плагина oh-my-claudecode (см. BuildCliTurnText).
- **Цикл «до готово»** (`work-loop`, по мотивам ralph/ulw-loop): тумблер в композере →
  `PUT /api/chats/{id}/loop` → `Session.WorkLoop` {promise=«ГОТОВО», iteration, maxIterations
  (конфиг `Loop:MaxIterations`, дефолт 20), phase working|verifying}. Пока цикл активен, к ходу
  дописывается протокол «выведи `<promise>ГОТОВО</promise>` когда всё сделано»; на `exited`
  штатного хода `ContinueWorkLoopAsync`: маркер не найден → автопродолжение (continuation-сообщение
  видно в ленте как обычное), найден → фаза verifying (один верификационный ход со свидетельствами;
  без рабочего протокола), после — стоп; стоп также по лимиту, ошибке хода и Interrupt (снимается
  синхронно до exited). Событие `work_loop` (active/iteration/max/phase) → бейдж «Цикл: итерация N/M»
  в композере. Текст хода агрегируется в `SessionEntry.LoopTurnText` (поиск маркера). Сообщение
  пользователя в чат с активным циклом НЕ снимает цикл (решение владельца 2026-08-08): оно
  прерывает текущий ход, встаёт в очередь и само становится следующей итерацией (ход из очереди
  несёт протокол цикла); директива продолжения при user-pending не шлётся (арбитраж —
  `LoopTurnInFlight` под `PendingLock` с обеих сторон). Цикл снимают только кнопка цикла,
  «Стоп»/Interrupt и штатные окончания (ГОТОВО+верификация, лимит, ошибка хода). Агентские
  сообщения (`chats_send`) по-прежнему ждут конца всего цикла; выключение цикла форсирует
  разбор их очереди.
- **Квота запусков задач в цикле**: на ходу доклада исполнителя (`SuppressTasksExecute`)
  запрет не снимается, а заменяется квотой (паттерн Э4 из «Командной реализации», чтобы
  «доклад → запуск → доклад» не ушёл в бесконечный платный круг): счётчики
  `SessionWorkLoop.ExecutionsStarted` / `MaxExecutions` (конфиг `Loop:MaxTaskExecutions`,
  дефолт 20), расход через `SessionManager.TryConsumeWorkLoopRun` на ЛЮБОМ неделегированном
  ходу чата с циклом (`DenyOnDelegatedTurnAttribute.AllowInWorkLoop` на
  `TasksController.Execute`), возврат единицы при 4xx/исключении (`RefundWorkLoopRun`),
  при исчерпании 403 «доложи человеку и дождись решения». Квота принадлежит самой сессии
  цикла (вверх по родителям не поднимаемся — в отличие от командной); повторное включение
  цикла обнуляет счётчики (новый объект `SessionWorkLoop`); Guard B4 исключает двойное
  списание командной квотой и квотой цикла в одном чате.
- Справочник категорий делегирования (`OmoPrompts.DelegationCategories`) — секция «ДЕЛЕГИРОВАНИЕ»
  в промпте персоны-исполнителя задач (TaskExecutionService).
- **Sweep-terminus статуса после хода** (P12/P15): `ExitedMessage` прогона приходит лишь со смертью
  процесса, а прогон доживает фоновых агентов (до `Claude:BgLingerMinutes`) — без sweep чат висел в
  `active` бесконечно. `SaveSessions` по истечении `Session:StuckActiveGraceSeconds` (дефолт 15 c)
  доводит `Active`→`Finished`, когда у прогона нет живой фоновой работы (`!HasLiveTurn ||
  !HasPendingBg`); цикл «до готово» и планировщик штаба гейтятся отдельно. Окно калибруется ключом
  — если `finished` мигает на длинных ходах (ретрай/фолбэк затягивают паузу), grace поднимают.

## Командная реализация — режим чата (флаг `team-implement-mode`)

Чат становится штабом фичи: координатор публикует план, работа идёт задачами на
персон-исполнителей, их чаты висят в иерархии под штабом, доклады возвращаются в штаб и
двигают процесс дальше. Продуктовый план (сценарий, тексты, эскалации, бюджет) —
[team-implement-mode.md](team-implement-mode.md).

- **Состояние на сессии** — `Session.TeamImplement` (по образцу `SessionWorkLoop`: наличие
  объекта = режим активен): стадия (`interview | planning | confirming | wave |
  awaitingDecision | checking | idle`), номер волны, **плановое число волн** (`PlannedWaves` — из карточки
  плана; бейдж «волна N из M» берёт M отсюда, а не из потолка бюджета), флаг авто-волн,
  координатор/планировщик, состав исполнителей (пустой = вся команда проекта), бюджет
  итерации, `CoordinatorNoCode` («координатор не пишет код сам» — у штаба отключены
  Edit/Write/NotebookEdit). API: `PUT /api/chats/{id}/team-implement` (вкл/выкл + состав),
  `PUT /api/chats/{id}/team-implement/auto`; событие `team_implement` — при каждом изменении.
- **Карточка плана в ленте** — тип сообщения `team_plan` (`TeamPlanView`): под-задачи по
  волнам, чип исполнителя с поповером смены, обоснование выбора строкой, кнопки
  «Запустить» / «Изменить план» / «Отменить» (метод хаба `RespondTeamPlan`). Переиздаётся
  с тем же `planId` — клиент обновляет карточку на месте (дедуп в `chatReducer`).
- **Раздача и волны** — `TeamWaveService`: «Запустить» создаёт задачи (`personaId` =
  исполнитель, `SourceSessionId` = штаб, `CreatedByPersonaId` = координатор) и пакетно
  стартует волну; дочерние чаты исполнения встают под штаб через вычисляемый
  `Session.ParentSessionId`.
- **Бейдж в композере и маркер в списке чатов** ([TeamImplementBadge.tsx](../../frontend/src/features/team/TeamImplementBadge.tsx),
  подписи — [lib/teamImplement.ts](../../frontend/src/lib/teamImplement.ts)): «Командная
  реализация · <стадия>», тон по тому, чей ход (работает команда / ждёт человека / ждёт
  задачу), чип «Авто» переключается кликом, выключение режима — с подтверждением.
- **Два инструмента в группе «Сделать»** ([teamMechanics.ts](../../frontend/src/features/team/teamMechanics.ts)):
  «Командная реализация» (`implementMode`) включает режим чата REST-вызовом и отправляет
  тему обычным сообщением; «Командный спринт» (`implement`) — прежний быстрый
  workflow-ход `/team-implement {JSON}` (субагенты внутри одного хода, без задач и
  докладов). **Id `implement` менять нельзя:** по префиксу `/team-implement` детектор
  (`detectTeamMechanic`) рисует карточкой старые ходы в лентах — переименование затронуло
  только подпись, история не ломается (сторож — `teamMechanics.test.ts`).

- **Автономный цикл и остановки** — `TeamWaveService` + сторож `TeamWaveWatchdog` (тик раз
  в минуту): следующая волна стартует сама при включённых авто-волнах, провал под-задачи даёт
  одну перевыдачу с причиной, второй провал — карточку человеку. Любая остановка = карточка
  `team_escalation` в ленте + уведомление и web push, если человека нет в чате (блокер
  исполнителя, провал дважды, расхождение с планом, красная проверка, исчерпание бюджета,
  зависшая волна, «Стоп»). **Бюджет итерации** считает бэкенд в точке запуска: волна либо
  помещается в остаток целиком, либо не стартует и даёт карточку с расходом; квота
  расходуется и на ходу координатора (`[DenyOnDelegatedTurn(AllowInTeamImplement)]` вместо
  прежнего запрета), и на запусках из чатов исполнения. Таймаут волны считается от последней
  её активности (`TeamImplement:WaveTimeoutMinutes`, дефолт 90).
- **Непрерывный контур** — после проверки режим уходит в стадию «ожидание вводной», а не
  выключается: следующая фраза человека проходит тот же цикл (маркер `<team:work>` в ответе
  координатора → план → добавочная волна), бюджет обнуляется вводной человека.
- **Интервью и перепланирование (Э8)** — вход в итерацию стал разговором: вводная человека
  открывает стадию `interview`, координатор задаёт вопросы **только `AskUserQuestion`**
  (ASK-карточки с вариантами, максимум 2 раунда на вводную — счёт ведёт бэкенд полем
  `InterviewRounds`), «вопросов нет» = допущения в карточке плана (`Plan.Assumptions`).
  Закрывает интервью тот же маркер `<team:work>`. Тупик в волне — маркер
  `<escalate:clarify>`: волны на паузе, карточка `needsClarification` + push, следом ход с
  просьбой задать вопросы; после ответов идёт план `vN` («Что изменилось» — `Plan.Changes`),
  и **подтверждение обязательно даже при авто-волнах**. Волна стартует только по
  подтверждённой последней версии (`PlanVersion` / `ApprovedPlanVersion`; нули = состояние
  до Э8, гард выключен). Ответ на интервью вводной не считается — бюджет не сбрасывает.
  Таймаут волны в интервью не тикает.
- **План-режим стадий интервью и планирования (Э8)** — на входе в интервью сервер запоминает
  режим прав человека (`SavedMode`) и переводит чат в `Plan`: правки запрещает сама
  permission-механика CLI, а не только список инструментов; живому ходу режим меняется через
  `set_permission_mode`. На «Запустить» (`Confirming → Wave`) режим возвращается (с поправкой
  на гард «координатор не пишет код»), `PUT /chats/{id}/mode` до этого отклоняется
  («Штаб планирует…»), а событие `team_implement` несёт `modeLocked` для блокировки селектора.
  `ExitPlanMode` у чата в режиме запрещён всегда (`TeamImplementPrompts.ModeDisallowed`) —
  иначе штатная карточка `plan_review` дала бы второе согласование поверх карточки плана.
- **Карточки от лица персоны (Э8)** — `team_plan` и `team_escalation` несут `personaId`
  автора, зафиксированного В МОМЕНТ публикации (план — планировщик, эскалации — координатор),
  и он же лежит в stored-слое: смена координатора историю не переписывает. Уведомления и push
  идут от имени персоны («{Имя}: нужно ваше решение», «{Имя} ждёт ответов по задаче» —
  `TeamImplementPrompts.WaitingTitle`), обезличенный текст остаётся фолбэком.

## Задачи v3

Напоминания, регулярные, Claude-исполнитель; исполнение гейтится флагом `personas` для персон:

- Напоминания: `TaskItem.ReminderMinutes` (офсет от срока), `TaskSchedulerService`
  (BackgroundService, тик 30 с) шлёт `NotificationMessage` в группу user_* (тост
  [NotificationToasts.tsx](../../frontend/src/components/NotificationToasts.tsx)) + web push.
  Сроки локальные: `User.TimeZone` (IANA, фронт шлёт при старте), конверсия в UTC —
  [TaskDueCalculator.cs](../../backend/ClaudeHomeServer/Services/TaskDueCalculator.cs), без времени — 09:00
- Web push: VAPID-ключи автогенерация в `data/vapid-keys.json`, подписки в
  `data/push-subscriptions.json` (несколько устройств per-user, авточистка 404/410). SW — свой
  `frontend/src/sw.ts` (vite-plugin-pwa `injectManifest`, отдельный tsconfig.sw.json),
  обработчики push/notificationclick с hash-диплинками
- Регулярные задачи: `TaskRecurrence` + `SeriesId`; при переводе экземпляра в done
  PUT /api/tasks/{id} спавнит следующий
  ([TaskRecurrenceCalculator.cs](../../backend/ClaudeHomeServer/Services/TaskRecurrenceCalculator.cs) —
  отсчёт от срока, не от завершения)
- Claude-исполнитель: [TaskExecutionService.cs](../../backend/ClaudeHomeServer/Services/TaskExecutionService.cs) —
  сессия acceptEdits в проекте задачи (личная — чат вне проекта), промпт с правилами ведения
  статуса через MCP tasks_*; наблюдение через событие `SessionManager.OnSessionMessage`
  (result → отметка + уведомление, permission → «ждёт ответа»); триггеры: кнопка «Выполнить
  с Claude» и автозапуск планировщиком в момент срока (окно 24 ч)
- **Страховка «ход кончился, а задачу не закрыли»** (`ClassifyStall` + `CheckStalledExecutorAsync`,
  зовёт тот же тик планировщика): успешный ход задачу не закрывает — это обязан сделать сам
  исполнитель через `tasks_complete`, а промежуточный ход многошаговой задачи и «исполнитель
  молча забил» на конце хода неразличимы. Поэтому решает не событие, а **тишина** чата-исполнителя
  дольше `Tasks:ExecutorStaleMinutes` (дефолт 15): сперва один автоход-оклик «закрой или эскалируй»
  (в ленте — плашка, не пузырь с промптом), и только если столько же молчания прошло после него —
  уведомление человеку «Задача осталась в работе». Отметки шагов живут на задаче
  (`ExecutorNudgedAt`, `ExecutorStaleAlertedAt`), поэтому оклик и уведомление ровно по одному
  на запуск, переживают рестарт и сбрасываются перезапуском исполнителя (`MarkClaudeStarted`).
  Ветки, где уведомление уже ушло своим путём (провал хода, терминальная остановка, `Waiting`
  на разрешение), страховка не трогает. Оклик ограничен окном свежести (`NudgeWindow`, 24 ч):
  чат молчит дольше — сразу уведомление, без платного хода в позавчерашний разговор (иначе
  первый же тик после обновления разослал бы автоходы во все давно висящие задачи)
- Исполнитель = персона: `TaskItem.PersonaId` — задача выполняется «от лица» персоны
  (6-секционный контракт постановки, уведомления её лицом). Единый пикер «Исполнитель»
  (Я/Claude/персона) в форме и диалоге; вкладка «Задачи» персоны и назначение через REST/MCP —
  см. [personas.md](personas.md). За флагом `personas` (отдельного `task-claude-exec` нет)
- **Уровень модели исполнения**: `TaskItem.ModelTier` (`strong|medium|weak`, пусто — как
  настроено для места `tasks-executor`). Тяжёлую работу отдаём сильной модели, рутину —
  экономной, не меняя настройку на всех. Главный вход — параметр `modelTier` в
  `tasks_create`/`tasks_update` (задачи ставит персона-постановщик), плюс селектор
  «Модель исполнителя» в форме задачи. Постоянный уровень исполнителя — `Persona.ModelTier`,
  задача его перебивает. Резолв и приоритеты — [llm-providers.md](llm-providers.md)
- Постановка задачи (`BuildPersonaPrompt`) несёт таблицу категорий делегирования и правило
  выбора канала (read-only мнение → `Task(персона, model=…)`; работа с правками →
  `tasks_create` + `tasks_run_executor`); полные профили категорий вынесены в файл
  `.claude/delegation-categories.md` (пишет `PersonaAgentFileSync`, абсолютный путь — в промпте),
  чтобы не тащить ~26 КБ в каждый запуск. В ленте карточка постановки свёрнута
  (`CollapsibleMarkdownBody`), разворачивается по клику

## Восстановление знаний после сбоя индексации (Dify)

Документ, упавший на индексации в Dify (провайдер эмбеддингов был недоступен), раньше
пропадал из поиска молча и навсегда: локальный стор хранил хеш содержимого, дифф-синк считал
документ актуальным и не трогал его. Наружу это выглядело как накопительная деградация — recall
персоны слепнет, `knowledge_search` по проекту неполный, ошибки при этом нигде нет.

Фоновый реконсайлер (`Dify:Reconcile:Mode`, дефолт **`off`** — dark launch) обходит датасеты
участников синка, находит документы в статусе `error`, сопоставляет их с записями сторов и
сбрасывает хеши — штатный дифф-синк пересоздаёт документы из источника истины. Тем же
механизмом лечится и накопленный хвост (первый прогон = бэкфилл). Документы без источника у
CCS — сироты и ручные документы «Знаний» — не лечатся, а показываются: текст ошибки Dify
выводится рядом с бейджем статуса в разделе «Знания» и в панели знаний проекта (там у файловых
документов есть и кнопка повтора индексации). Ручной документ лечится только повторной
загрузкой — источника контента у CCS нет.

Метрики (`ccs.dify.error_documents`, `ccs.dify.documents_recovered`) и уведомление владельцу
«часть знаний не проиндексирована» — не чаще раза в сутки, когда ошибки держатся ≥2 обходов
подряд. Устройство, режимы, backoff и карантин «ядовитых» записей —
[knowledge.md](knowledge.md#восстановление-error-документов-dify-реконсайлер).

## Бэкапы и восстановление

Резервные копии каталога `data` (чаты с историей, персоны с памятью, задачи, заметки,
лог событий SQLite). Код — [Services/Backup/](../../backend/ClaudeHomeServer/Services/Backup/).

**Настройка — только руками**, секция `Backup` в `appsettings.Local.json`
(`Enabled`, `Path`, `IntervalHours`, `SecretsPath`; образец с пояснениями —
`appsettings.Local.example.json`). Через UI не правится намеренно: пути машинно-специфичны,
а настройка внутри `data` откатывалась бы вместе с данными при восстановлении — включая
путь к папке собственных архивов.

**Что попадает в архив.** Всё из `data`, кроме: секретов (отдельный архив, см. ниже),
`logs/`, `sandbox-tmp/`, `server-pids.txt` (восстановленный реестр PID заставил бы следующий
старт убить по протухшим номерам всё, что зовётся claude/node), самих папок архивов,
временных и `.corrupt-*` файлов. Из профилей CLI (`claude-profiles/`, `sandbox-profiles/`)
берётся **только подпапка `projects/`** — транскрипты для `--resume`, которые больше
неоткуда восстановить; `.credentials.json` с OAuth-токенами и синканные `plugins` осознанно
за бортом, потому что основной архив уезжает в облако. `project-events.db` снимается
online-backup API SQLite (`BackupDatabase`), а не копированием файла: копия без WAL-хвоста
протухшая. Секреты (`jwt-secret.txt`, `vapid-keys.json`, `module-keys.json`,
`appsettings.Local.json`, `appsettings.{Env}.json`) — **отдельным локальным архивом**
в `SecretsPath` (дефолт `{папка exe}/backups-secrets`, вне `data`, чтобы пережить restore).

**Как снимается.** Расписание интервальное, не календарное: проверка раз в час, снимок —
если с последнего успеха прошло больше `IntervalHours` (машина Windows может спать ночью, и
cron молча пропускал бы окно). Плюс ручной снимок (кнопка виджета, меню трея,
`exe --backup`) и автоматический в `deploy80.ps1` перед выкаткой. Архив пишется сразу в
целевую папку как `.part` и переименовывается **на месте** — иначе `File.Move` между томами
(облачная папка обычно на другом диске) даёт copy+delete, и синхронизатор подхватывает
недописанный файл. Рядом кладётся sidecar-манифест: по нему виджет и трей показывают состав
без вскрытия архива. Инициаторов трое (таймер, трей, деплой), поэтому снимок под именованным
мьютексом; ротация — 7 дневных + 4 недельных + 3 месячных, и **только по своим архивам**
(чужой `instanceId` и нечитаемый sidecar не трогаются: в общей облачной папке лежат
архивы разных инстансов, а OneDrive держит файлы плейсхолдерами).

**Восстановление — вне веб-интерфейса**: `ClaudeHomeServer.exe --restore <архив>
[--secrets <архив>] [--force]` либо пункт меню трея. Причина простая: бэкап нужен ровно
тогда, когда приложение не работает, и механизм внутри сервера в этот момент недоступен.
Четыре гейта, все до того, как каталог сдвинут с места:

1. **сервер не запущен** — признак `Global\ccs-instance-{sha1(dataDir)}`, который сервер
   держит весь uptime ([InstanceLock.cs](../../backend/ClaudeHomeServer/Services/Backup/InstanceLock.cs));
   живой сервер продолжил бы писать в перемещённый каталог;
2. **тот же инстанс** — `instanceId` из `data/instance-id.txt`. Три случая: файла нет
   (чистая машина после смерти диска) → id **усыновляется** из архива; совпал → ок;
   не совпал → отказ, обходится `--force`. Разведение случаев принципиально: без него
   штатный disaster-recovery требовал бы того же флага, что и опасное кросс-инстансное
   восстановление;
3. **версия формата** — `manifest.schemaVersion <= BackupSchema.Version`; архив новее кода
   роняет десериализацию, а `JsonFileStore` на этом молча отдаёт пустой стор;
4. **целостность** — sha256 всех файлов по манифесту + **строгое** чтение сторов
   ([BackupValidation.cs](../../backend/ClaudeHomeServer/Services/Backup/BackupValidation.cs))
   теми же `JsonSerializerOptions`, что у самих сторов. Отдельно от штатной загрузки именно
   потому, что та прощает ошибки: битый файл переименовывается в `.corrupt-*.bak`, стор
   стартует пустым, и «восстановилось» означало бы «всё зелёное, а персон нет».

Дальше: гасится контейнер песочницы (`data/sandbox-*` смонтированы внутрь и держат каталог),
снимается страховочный снапшот, `SqliteConnection.ClearAllPools()` (пул держит `.db` и после
закрытия соединений — каталог иначе не переименовать), `data` → `data.old-{ts}`, распакованное
→ `data`; **любая ошибка распаковки откатывает** `data.old` обратно. Секреты и история
архивов переносятся из `data.old` в новый каталог: их нет в архиве, а каталог заменён целиком —
без переноса обычный откат втихую разлогинивал бы всех (новый jwt-secret) и убивал push-подписки.
Ключ `--secrets` поверх этого восстанавливает архивные.

**Post-restore**: маркер `.post-restore` обрабатывается на старте до подъёма сторов
([PostRestoreHook.cs](../../backend/ClaudeHomeServer/Services/Backup/PostRestoreHook.cs)) —
обнуляются карты документов `workspace-knowledge.json`, чтобы штатный `BootstrapDocsAsync`
пересобрал Dify-слой с натуры. Сторы заметок и памяти персон не трогаются: у них дифф-синк
по хешам, он сойдётся сам. Ограничение v1: restore рассчитан на **тот же Dify** —
документы, созданные в датасетах после снятия снапшота, останутся сиротами.

**Инспекционная копия**: `exe --inspect <архив> [--port 5599]` поднимает временный инстанс
на `127.0.0.1` из архива — посмотреть и перенести данные руками. Копия обезврежена, иначе она
бы **жила**: планировщик выполнял бы просроченные задачи Claude-исполнителем (реальные деньги
и правки файлов), синхронизация знаний «поправляла» бы боевые датасеты Dify под отставшее
состояние, push уходили бы дублями. Поэтому в ней: снимаются регистрации **всех** своих
hosted-сервисов (разом, по сборке — перечень пришлось бы дописывать при каждом новом сервисе),
не запускаются `ProcessRegistry` (его pid-файл лежит рядом с exe и принадлежит боевому серверу),
`PersonaAgentFileSync` (пишет `.claude/agents/*.md` в реальные папки проектов), стартовые
миграции и прогрев моделей; принудительно пустые `Dify:ApiKey` и `Sandbox:ProjectsRoot`;
read-only middleware отбивает все не-GET запросы (стоит до аутентификации и до WebDAV, иначе
`PUT/MKCOL/MOVE` ушли бы на живой диск мимо гейта). Переопределения кладутся **последним**
источником конфигурации — `appsettings.Local.json` грузится поверх командной строки и иначе
вернул бы боевые пути; окружение дочернего процесса — `Inspection`, потому что пустое
означало бы `Production` с его `Kestrel:Endpoints` на `0.0.0.0:80/443`.

**Чего бэкап не покрывает** (осознанно): транскрипты CLI подписки (`~/.claude/projects/**`,
вне `data` — при обычном откате на той же машине они на месте и `--resume` работает, после
смерти диска лента чатов есть, а продолжить разговор нельзя), файлы проектов (это git-репы),
вложения чатов, датасеты Dify (переиндексируются). Снапшот не транзакционен между файлами.

**Виджет** «Бэкап» на главной ([BackupWidget.tsx](../../frontend/src/features/home/BackupWidget.tsx),
только `role=admin`): статус, последние 3 снимка со сводкой состава и кнопка ручного снимка
(скрыта, пока бэкап не включён в конфиге). Данные — из `data/backup-state.json`;
в папку архивов виджет не ходит намеренно: на спящем облаке перечисление файлов подвесило бы
дашборд. API — `GET /api/admin/backup`, `POST /api/admin/backup/run` (оба admin-only).
