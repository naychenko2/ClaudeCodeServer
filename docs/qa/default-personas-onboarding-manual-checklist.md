# Manual checklist: дефолт-персоны и онбординг

**Вердикт QA-прогона Playwright:** фича проверена частично, диалоговые сценарии
требуют OAuth-аутентификации Claude CLI. Этот документ — пошаговая ручная проверка
для человека, у которого есть работающий CLI.

Сценарии взяты из плана
[`docs/architecture/default-personas-onboarding-plan.md`](../architecture/default-personas-onboarding-plan.md),
acceptance criteria — строки 61–85, верификация — 191–195.

---

## Подготовка окружения

1. **OAuth CLI в контейнере** (блокер, без него сценарии A/B/E дальше интервью не
   уедут — будут валиться с «Not logged in · Please run /login»).

   ```bash
   docker exec -it claude-server claude login            # через браузер и claude.ai
   # или быстрее, если есть токен:
   # в .env на хосте добавь CLAUDE_CODE_OAUTH_TOKEN=<токен из «claude setup-token»>
   docker compose -f docker-compose.claude.yml up -d --build claude-server
   docker exec -it claude-server sh -c 'cat /home/app/.claude/.credentials.json | head -5'
   # ожидание: не пусто, есть поле "claudeAiOauth"
   ```

2. **Чистая база пользователей** (для сценария A):

   ```bash
   docker exec claude-server sh -c 'cat /data/users.json'   # запомнить текущий
   # либо через UI: Аватар → Эксперименты → «Дефолт-персоны и онбординг» → OFF
   # удалить /data/users.json нельзя — admin создастся заново при следующем запросе
   ```

3. **Контейнер собран из worktree** (там, где фича):

   ```bash
   docker compose -f docker-compose.claude.yml build claude-server
   docker compose -f docker-compose.claude.yml up -d claude-server
   ```

## Сценарий A — новый пользователь + флаг ON

**Что проверяем:** первое включение фичи создаёт обязательный экран-гейт, после
интервью `User.DefaultPersonaId` записывается в `users.json`, новые чаты открываются
с персоной-ассистентом по умолчанию.

| Шаг | Действие | Ожидаемо |
|---|---|---|
| 1 | Аватар → «Эксперименты» → тумблер «Дефолт-персоны и онбординг» → ON | Тумблер включился без ошибки; в `users.json` `FeatureFlags["default-personas-onboarding"] = true` |
| 2 | Полная перезагрузка страницы (`Ctrl+F5`) | Виден **полноэкранный** гейт «Знакомство» со Sparkles-иконкой, заголовком, подзаголовком «Короткое интервью…» и двумя кнопками в шапке (`Создать персону из разговора`, `Начать заново`). Боковая навигация «Чаты / Проекты / Календарь / Заметки / Персоны» НЕ видна (скрыта под гейтом). |
| 3 | Проверить `users.json` | `OnboardingSessionId != null`, `DefaultPersonaId == null` |
| 4 | Проверить `sessions.json` | У записи `OnboardingKind = "user"`, `PersonaId = null`, `ProjectId = null`, `Name = "Настройка системы"` |
| 5 | В чате написать 2–3 реплики о себе («я фронтенд-разработчик, работаю в основном с React», «делаю фичи для ИИ-дома», «нужен помощник с планированием и проверкой кода») | Мастер ведёт интервью, задаёт уточняющие вопросы, в конце предлагает карточку персоны |
| 6 | Подтвердить предложенную персону («да, подходит» / «всё верно») | Сообщение от Claude, метка `onboarding_completed` в WebSocket (`{ type: "onboarding_completed" }`), затем `result` |
| 7 | В шапке гейта появилась кнопка «Перейти в систему» | Кликнуть → гейт закрывается, виден основной UI |
| 8 | Проверить `users.json` | `DefaultPersonaId` — непустой GUID, отличается от `OnboardingSessionId` |
| 9 | Проверить `data/personas.json` | Появилась персона с этим ID, владелец — admin, scope = global |
| 10 | Создать новый чат | В шапке чата — аватар персоны-ассистента, а не дефолтный юзер-кружок |
| 11 | Открыть «Персоны» | Новая персона есть в разделе «Глобальные», отмечена как default |
| 12 | Перезагрузить страницу | Гейт НЕ показывается; пользователь сразу попадает на `/home` |

**Краевые случаи:**
- Двойной клик «Создать персону из разговора» подряд — бэкенд под `SemaphoreSlim`,
  второй запрос не плодит вторую сессию (`OnboardingController.cs:29–32`).
- Пропасть интернет между шагами 5 и 7 — `onboarding_completed` не придёт, кнопка
  «Перейти в систему» не появится, чат остаётся в гейте; перезапуск страницы возвращает
  на тот же гейт (сессия жива в `OnboardingSessionId`).

## Сценарий B — существующий пользователь + ретро-гейт

**Что проверяем:** включение флага у юзера с уже существующими чатами запускает
тот же гейт; для проекта без `DefaultPersonaId` срабатывает **проектный** гейт.

| Шаг | Действие | Ожидаемо |
|---|---|---|
| 1 | Создать пользователя с 2+ чатами (или взять существующего). `DefaultPersonaId = null` | `users.json` подтверждает |
| 2 | Создать проект, открыть его, сделать 1+ чат. `Project.DefaultPersonaId = null` | `projects.json` подтверждает |
| 3 | Аватар → «Эксперименты» → флаг ON | `FeatureFlags["default-personas-onboarding"] = true` |
| 4 | Выйти, залогиниться заново | Полноэкранный гейт «Знакомство» — тот же, что в сценарии A |
| 5 | Пройти личный онбординг | `User.DefaultPersonaId` записан |
| 6 | Гейт закрылся → на главной. Открыть проект | Появляется **отдельный** гейт «Знакомство с проектом "X"», шапка подписана именем проекта, в чате `OnboardingKind = "project"`, `PersonaId = User.DefaultPersonaId` |
| 7 | Пройти проектный онбординг (короткое интервью про проект) | В WebSocket `onboarding_completed` для **этой** сессии; `Project.DefaultPersonaId` записывается |
| 8 | Создать новый чат в этом проекте | Аватар = персона-руководитель (та, что создана на шаге 7), не глобальная |
| 9 | Создать новый чат **вне проекта** | Аватар = глобальная дефолт-персона (из сценария A) |

**Краевые случаи:**
- Проект без `DefaultPersonaId` у проекта, но у юзера тоже нет — `POST /api/onboarding/project/{id}/start`
  возвращает 400 «Сначала пройдите личный онбординг» (`OnboardingController.cs:81–82`).
- Включить флаг, пройти гейт, выключить флаг, перезагрузиться — гейт НЕ должен
  появиться повторно (порог по `DefaultPersonaId`, не по флагу).
- Удалить созданную персону в разделе «Персоны» → следующий онбординг должен
  сработать (а не зависнуть на старой).

## Сценарий E — механика OmO в чате с дефолт-персоной

**Что проверяем:** в чате с персоной-руководителем, когда пользователь формулирует
задачу-план («спланируй фичу X», «составь план …»), мастер предлагает механику с
кнопкой «Запустить»; отказ от механики НЕ должен вызывать повторное предложение в
том же чате.

**Предусловие:** сценарий A или B завершён, есть `User.DefaultPersonaId`, открыт чат
с персоной-руководителем (или ассистентом — в зависимости от того, какая из них
выбрана default).

| Шаг | Действие | Ожидаемо |
|---|---|---|
| 1 | Открыть чат с дефолтной персоной | В шапке аватар персоны, режим работы = Auto |
| 2 | Написать «спланируй фичу X — список задач для онбординга новых клиентов» | Руководитель ведёт диалог, уточняет контекст |
| 3 | После 1–2 уточнений руководитель выдаёт карточку-предложение с заголовком механики и кнопкой «Запустить» | Карточка в ленте, иконка механики, кнопка активна |
| 4 | Нажать «Запустить» | В чат уходит `/oh-my-claudecode:ralplan …` (или `<agent-name>:ralplan` — точное имя из каталога OmO), запускается соответствующая механика |
| 5 | Дождаться завершения механики | Виден обычный результат работы механики в ленте |

**Краевые случаи — отказ от механики:**

| Шаг | Действие | Ожидаемо |
|---|---|---|
| 6 | Отказаться от механики **словами** («не надо consensus, реши задачу сам») **ИЛИ** закрыть карточку крестиком | Оба способа эквивалентны: дальше руководитель решает задачу сам |
| 7 | В том же чате поставить ещё одну похожую задачу-план | Руководитель ведёт диалог как обычно, **БЕЗ** карточки-предложения (механика не предлагается повторно в этом же разговоре); ни в тексте, ни в DOM нет `<team-mechanic …/>` и упоминаний ralplan/спор/консенсус |
| 8 | Проверить, что ответ руководителя содержательный | Он справляется сам или задаёт уточняющие вопросы |
| 9 | Поставить ещё одну похожую задачу (3-я подряд в том же чате) | Та же картина: содержательный ответ, без карточки, без маркера в DOM |
| 10 | Открыть **новый** чат с тем же руководителем и поставить там нетривиальную задачу-план | Карточка механики снова появляется — decline живёт в разговоре, а не в персоне |

**Что считать багом:**
- Карточка предлагается повторно **в том же чате** после отказа.
- В тексте ответа на похожую задачу после отказа упоминается «консенсус», «ralplan», «спор с критиком», «прогнать план через …».
- В DOM остаётся сырой текст `<team-mechanic id="…" topic="…"/>` (стрижка `stripTeamMechanicMarkers` не сработала).
- В новом чате с той же персоной карточка **не появляется** на нетривиальной задаче после decline (decline ушёл за пределы разговора).
- Кнопка «Запустить» отправляет не `/oh-my-claudecode:ralplan …`, а другой формат.
- Механика не запускается (CLI валится) после клика.
- В чате без дефолт-персоны (например, в «Настройка системы» во время сценария A)
  карточка появляется — её быть не должно до завершения онбординга.
- Маркер `<team-mechanic …/>` внутри fenced-блока ``` … ``` или внутри inline-`кода`
  парсится как предложение и рисует карточку (парсер должен игнорировать код —
  `splitByCode` в `frontend/src/features/team/TeamMechanicOffer.tsx`).

**Проверено вручную (Playwright, 2026-08-07, чат `cfa31bd2-…` с Марком QA Lead):**
- decline словами → 3 похожие задачи подряд (резервное копирование → очистка
  неактивных заметок → теги для заметок) — все ответы без карточки, без
  `<team-mechanic>` в DOM, без упоминаний механик в тексте.
- Decline **не** привязан к персоне: в новом чате `baff879b-…` с тем же Марком
  на нетривиальной задаче («миграция монолита на микросервисы») карточка
  «Консенсус-план» снова появилась.
- Маркер не парсится внутри кода — подтверждено по коду (`TeamMechanicOffer.tsx`,
  `splitByCode` отделяет fenced и inline блоки до `MARKER_RE`).

## Что уже автоматизировано (НЕ дублировать руками)

Эти проверки покрыты юнит-/интеграционными тестами и в данный прогон не входят:

- идемпотентность `POST /api/onboarding/user/start` (SemaphoreSlim)
- сериализация полей `User.DefaultPersonaId` / `OnboardingSessionId` (round-trip)
- контроль прав доступа `OnboardingController` (401 / 403 / 404)
- валидация `ProjectId` в `POST /api/onboarding/project/{id}/start`
- проверка «нет личного дефолта → 400» для проектного онбординга
