# ADR-012: Настройки специальностей — один глобальный слой с admin-only записью

**Статус:** Принято
**Дата:** 2026-08-26
**Принимающие решение:** Андрей (владелец продукта), Александр (архитектор)
**Реализация:** бэкенд — Денис (согласовано 26.08.2026, до правок стора), фронт — Кира
(волна 1 плана «Специальности как персоны»)
**Связанные артефакты:**
[ADR-007](ADR-007-model-preset-chains.md) (пресет как именованная цепочка, матрицы уровней),
[specialties-personalization-review.md](specialties-personalization-review.md) (роль —

[SpecialtySettingsStore.cs](../../backend/ClaudeHomeServer/Services/SpecialtySettingsStore.cs),
[SpecialtiesController.cs](../../backend/ClaudeHomeServer/Controllers/SpecialtiesController.cs)

## Контекст

Настройки специальности (права, матрица моделей по уровням, `DefaultTier`, секции промпта,
типовые умения) и именованные пресеты-цепочки живут в `data/specialty-settings.json` в **трёх**
слоях: `Global` (инстанс) → `Users[userId]` (назначение админом конкретному пользователю, «B9»)
→ `Owners[ownerId]` (личный слой владельца). Резолв идёт снизу вверх, причём **семантик
наследования две**:

```
права + матрицы + DefaultTier      секции промпта + типовые умения
(замена записи ЦЕЛИКОМ)            (посекционно, каждый параметр отдельно)

Owner[X].planner ─┐                Owner: enabled=off ─┐  (enabled)
User[X].planner  ─┼─► первый       User:  —            ┼─► первый ЗАДАННЫЙ
Global.planner   ─┘   заданный     Global:text="…"   ─┘   параметр
код (SpecialtyCatalog)             код (SpecialtyPromptPresets)
```

Что с этим не так:

1. **Роль — контракт инстанса, а не личная настройка.** На ключах специальностей стоит
   оркестрация (роутинг подзадач, планировщик команды, выбор по семейству исполнителя), и
   [прошлый ADR](specialties-personalization-review.md) уже запретил персонализировать подпись
   и состав ролей. Персональные *настройки* той же роли оставляли вторую, невидимую ось: у двух
   пользователей «Планировщик» вёл себя по-разному, хотя оркестратор считает роль общей.
2. **Резолв не удерживается в голове.** Три слоя × две семантики = восемь путей до значения,
   которые UI вынужден объяснять бейджами слоя-источника (`SourceBadge`, `enabledSource`,
   `textSource`). Цена сложности уже оплачена дефектами — в приёмке волны нашли
   `LayerSwitch` с захардкоженным `isAdmin={true}`, показывавший админские слои не-админам.
3. **Слой `Users` (B9) не использован ни разу.** На проде и на деве `Users` — пустой словарь;
   механика назначения настроек чужому пользователю не пригодилась.
4. **Персонализация от снятия слоёв не исчезает.** У пользователя остаются личные слоты
   моделей (`User.ModelTier*`), модель и матрица уровней у его персон, выбор исполнителя мест
   каталога. Личным остаётся то, что и должно быть личным, — персона; роль возвращается в
   инстансный контракт.

Фактическое состояние сторов на 26.08.2026 (проверено чтением файлов):

| Контур | `Version` | `Global` | `Owners` | `Users` |
|---|---|---|---|---|
| prod | 3 | 0 специальностей, 3 пресета | `andrey` (admin): 14 ролей, 7 пресетов, `defaultSpecialty` | `{}` |
| dev | 3 | пусто | `andrey` (admin): 14 ролей, 3 пресета; `admin` (admin): 1 пресет | `{}` |

Отсюда два вывода, определяющие решение: **все живые настройки лежат в owner-слое админа**
(механический переход «оставить только `Global`» стёр бы боевую конфигурацию целиком), и
**владельцев-не-админов со своим слоем нет вовсе** — цена снятия слоёв на реальных данных
равна нулю.

## Решение

Один слой. Резолв любого параметра специальности:

```
Global (data/specialty-settings.json)  →  дефолт кода (SpecialtyCatalog / SpecialtyPromptPresets)
```

- `ownerId` в резолве не участвует: настройки специальностей перестают быть per-owner данными.
- **Запись — только `admin`** (`[Authorize(Roles = "admin")]`), **чтение — любой
  аутентифицированный**. Глобальный слой и раньше отдавался всем в `GET /settings`; секретом он
  не является, а фронту он нужен, чтобы показать роль в режиме «только просмотр».
- Обе семантики наследования схлопываются в одну: значение либо задано в `Global`, либо
  берётся из кода. Посекционное наследование внутри `Global` остаётся ровно в том виде, в
  каком оно нужно: заданная секция перекрывает дефолт кода, незаданная — нет.
- `FormatVersion` 4 → **5**, с разовой миграцией при чтении файла.

### Отвергнутые варианты

- **Оставить два слоя (Global + Owner), убрать только `Users`.** Снимает треть сложности и
  ноль причин: обе главные болячки (роль как личная настройка, бейджи источника в UI) держатся
  именно на owner-слое.
- **Оставить слои, закрыть запись ролью.** Тогда `Owners` остаётся мёртвым кодом с живым
  резолвом — самая дорогая из конфигураций: сложность есть, пользы нет.
- **Стереть `Owners`/`Users` без влития.** Проверено по файлам: снесло бы 14 настроенных ролей
  и 7 пресетов на проде.

## Миграция FormatVersion 4 → 5

```
       ФАЙЛ v≤4                                   ФАЙЛ v5
┌─────────────────────────┐            ┌──────────────────────────────┐
│ Global                  │──базис────►│ Global (слитый)              │
│ Owners[admin₁]          │──поверх───►│                              │
│ Owners[admin₂]          │──поверх───►│  конфликт → выигрывает       │
│ Owners[не-админ]        │──отбросить │  owner; среди админов —      │
│ Users[*]                │──отбросить │  первый по порядку users.json│
└─────────────────────────┘            │ Owners = {}, Users = {}      │
   v1 сначала едет по существующей     │ Version = 5                  │
   ветке v1→v2 (ADR-007 §6)            └──────────────────────────────┘
```

**Инвариант миграции (он же критерий приёмки):** для владельца-админа эффективный резолв по
всем 14 ролям — права, три ячейки уровней, `DefaultTier`, состояние каждой секции промпта,
типовые умения, список пресетов — **до и после миграции совпадает**. Миграция переносит не
слой, а то, что админ видел на экране.

Из этого инварианта следует гранулярность влития — она **не одинакова по полям**, потому что
не одинакова была семантика наследования:

| Что | Как вливается | Почему |
|---|---|---|
| Запись специальности: `Access`, `Tools`, `DisallowedTools`, `TierStrong/Medium/Weak`, `DefaultTier` | owner-запись **заменяет** глобальную целиком | резолв и был «первый заданный слой целиком» |
| `PromptSections` | **посекционно**: owner-секции поверх глобальных, по `id`, отдельно `Enabled` и `Text` | резолв был посекционным; замена записи целиком снесла бы секции, заданные админом глобально |
| `DefaultBindings` | непустой owner-список заменяет глобальный, пустой — не трогает | наследование было «полем», не посекционным |
| `DefaultSpecialty` («любая специальность») | owner-запись заменяет глобальную целиком | та же семантика, что у записи специальности |
| `Presets` | конкатенация: owner-пресеты, затем глобальные; дедуп по `Id` (owner раньше) | пресеты слоёв жили рядом и не переопределяли друг друга (ADR-007 §1) |
| `Owners[не-админ]`, `Users[*]` | отбрасываются | writer'а у этих слоёв больше нет; на боевых данных их не существует |

**Кто такой «админ-источник».** Роль живёт в `UserStore`, поэтому миграции нужен доступ к
нему: рекомендуемая форма — `UserStore` обязательной зависимостью конструктора
`SpecialtySettingsStore` (цикла DI нет: `UserStore` зависит только от конфигурации, среды и
логгера). Правило выбора — **все владельцы с ролью `admin`, в порядке `users.json`, более
ранний выигрывает при конфликте ключа**. Правило «первый админ» без слова «все» отвергнуто по
факту: на проде первый админ в списке (`admin`) слоя не имеет, а вся конфигурация — у второго
(`andrey`); такая миграция потеряла бы всё.

**Страховка.** Перед первой записью v5 миграция кладёт рядом копию исходного файла
(`specialty-settings.v4.bak`) и пишет в лог, чей слой и во что влит. Копия — не про
восстановление одной кнопкой, а про то, чтобы разбор «куда делась настройка» вообще был
возможен: `Owners`/`Users` после прохода в файле не остаются.

**Идемпотентность.** Признак «мигрировано» — `Version == 5`; повторный старт ничего не
переписывает. Marker-файл, как у `GlmModelAliasMigration`, здесь не нужен: версия формата уже
является маркером, а миграция идёт при загрузке, до любой записи.

## Изменения API

Удаляются:

| Метод и маршрут | Что делал |
|---|---|
| `PUT /api/specialties/settings` | запись личного слоя (короткий алиас `settings/owner`) |
| `PUT /api/specialties/settings/owner` | то же, явный маршрут |
| `GET /api/specialties/settings/user/{userId}` | чтение слоя, назначенного пользователю |
| `PUT /api/specialties/settings/user/{userId}` | запись слоя пользователю (B9) |
| `PUT /api/specialties/settings/fallback/owner` | личный потолок подмен цепочки |

Короткий маршрут `PUT /settings` попал в список осознанно: он — синоним `settings/owner`, и
оставленный «для совместимости с фронтом» он стал бы единственной незакрытой ролью точкой
записи per-owner.

Остаются:

| Метод и маршрут | Доступ |
|---|---|
| `GET /api/specialties` | любой аутентифицированный (плюс новые поля `icon`, `color`) |
| `GET /api/specialties/prompt-sections` | любой аутентифицированный |
| `GET /api/specialties/settings` | любой аутентифицированный; отдаёт **один** слой |
| `PUT /api/specialties/settings/global` | `admin` |
| `PUT /api/specialties/settings/fallback/global` | `admin` |
| `GET /api/specialties/settings/reset/global/preview` | любой аутентифицированный (счёт по общему слою секретом не является) |
| `POST /api/specialties/settings/reset/global` | `admin` |
| `GET /api/specialties/settings/reset/owner/preview` | любой аутентифицированный; **сужен до персон вызывающего** |
| `POST /api/specialties/settings/reset/owner` | любой аутентифицированный; **сужен до персон вызывающего** |

Форма ответа `GET /settings`: поля `user` и `owner` уходят, остаются `version`,
`maxSubstitutions`, `global`, `presets`. У пресетов поле `scope` вырождается в единственное
значение `global` — из wire-контракта его в этой волне **не убираем** (см. «Хвосты»).

## Последствия для пользователя без роли admin

- Раздел «Специальности» становится для него **читаемым, но не редактируемым**: он видит
  роль, её модели, секции промпта и типовые умения — ровно те, по которым реально пойдут его
  персоны, — и не может их изменить. Фронт обязан показывать это состоянием интерфейса, а не
  ошибкой после нажатия: серверный отказ — 403.
- **Личные цепочки-пресеты пропадают.** `PresetScope.Owner` перестаёт существовать, значит
  не-админ больше не создаёт, не переименовывает и не удаляет пресеты (`ModelsController`
  отдаст ему `Forbid` на любой пресет — код уже написан так). На боевых данных теряется ноль
  личных пресетов, на деве — один.
- Личные рычаги остаются прежними: слоты моделей `strong/medium/weak` в «Моих моделях»,
  модель и матрица уровней у своих персон, выбор исполнителя мест каталога.

## Точки невозврата

1. **`Owners` и `Users` после миграции в файле отсутствуют.** Возврат — только из архива
   `data` или из `specialty-settings.v4.bak`. Перед выкаткой снять бэкап.
2. **Откат кода на версию с `FormatVersion = 4` опасен.** Стор, увидев формат новее своего,
   **стартует с дефолтами** (это сознательное поведение: незнакомая структура хуже дефолтов) —
   и первая же запись перезапишет файл, потеряв глобальные настройки. Правило отката: сначала
   восстановить файл из бэкапа, потом откатывать код.
3. **`BackupSchema.Version` обязан быть инкрементирован (8 → 9).** Из формата уходят два
   словаря; старый код, восстанавливая новый архив, должен падать с внятной ошибкой, а не
   тихо. Файл `Services/Backup/BackupSchema.cs` — вне владения волны, см. «Хвосты».
4. Пользователи-не-админы, успевшие что-то настроить между выкаткой и миграцией, ничего не
   настроят: запись закрыта ролью раньше, чем миграция что-либо потеряет.

## Хвосты, не входящие в эту волну

Названы явно, чтобы не уехали молча:

- **Сигнатуры с `ownerId` не трогаем.** `TemplateSettings`, `EffectiveTemplate`,
  `SpecialtyMatrices`, `SpecialtyDefaultTier`, `EffectivePromptSections`,
  `EffectiveDefaultBindings`, `EffectivePresets*`, `FindPreset`, `ExpandChain` сохраняют
  параметр, который перестаёт влиять на результат. Их зовут `ModelAssignmentResolver`,
  `PersonaManager`, `SessionManager`, `SpecialtyTemplatesService`, `PersonasController` — файлы
  вне владения волны; чистка сигнатур — отдельная задача после мержа.
- **`PresetScope` и `SpecialtySettingsStore.SectionSource` не сужаем.** Значения `User`/`Owner`
  становятся недостижимыми, но живут в чужих файлах и в wire-контракте фронта; их снятие —
  та же отдельная задача, вместе с бейджами источника в UI.
- **`FallbackSettingsStore.Owners` остаётся жить.** Эндпоинт записи личного потолка подмен
  уходит, а `ResolveMaxSubstitutions` продолжает читать `Owners` из `model-fallback.json`: у
  того, у кого личное значение уже записано, оно залипнет навсегда без способа снять его из
  интерфейса. На проде и деве словарь пуст, поэтому это не блокер волны, но задача нужна:
  либо резолв перестаёт читать `Owners`, либо словарь чистится миграцией того стора (с
  инкрементом его `FormatVersion`).
- **`BackupSchema.Version` 8 → 9** (см. точку невозврата 3) — файл вне владения.
- **Строка в индексе `docs/README.md`** на этот ADR — файл вне владения.

## Частное решение: `reset/owner` остаётся, но только про персон

`POST /settings/reset/owner` делал **две** вещи: чистил уровни в личном слое специальностей
**и** звал `PersonaManager.ResetTierMatrices(ownerId)` — «сбросить уровни у моих персон».
Вторая половина к слоям отношения не имеет: персоны были и остаются per-owner сущностью.
Удаление маршрута целиком забрало бы у пользователя единственную кнопку сброса уровней его
персон.

Поэтому маршрут `POST /api/specialties/settings/reset/owner` и его `preview` **сохраняются,
сужаясь до персон вызывающего**: специальностей они больше не касаются, ответ вырождается в
`{ personas, personaNames }`. Это дешевле, чем заводить под ту же кнопку новый эндпоинт в
разделе персон, и не оставляет функциональной дыры.

Пункт **расходится с буквой постановки** задачи бэкенда («удалить `GET/POST
/settings/reset/owner`») и согласован с её исполнителем 26.08.2026; расхождение вынесено
координатору волны отдельно.
