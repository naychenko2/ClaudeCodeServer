# «Железо» на трёх серверах (worker · ai · video) — предложение v1

Доработка вкладки «Железо» панели «Локальные модели» под новый контур: CCS переехал на серверную
ферму из трёх машин. Задача — видеть железо и движки **всех трёх** узлов в одной панели.

Предыдущая итерация: [спека «Железо»](local-model-hardware-spec.md) · [предложение v1](local-model-hardware-proposal.md) ·
макет [v2](local-model-hardware-v2.html). Эта работа — её развитие, а не замена.

## 1. Что есть сегодня (факты по коду)

| Что | Где | Собственник данных |
|---|---|---|
| Вкладка «Железо» — **один локальный узел** (машина, где работает CCS) | `frontend/src/features/localModel/HardwareTab.tsx`, контракт `GET /api/local-model/hardware` | локально: `nvidia-smi`, `hwmon`, помощник `ccs-gddr6` (root) |
| Карты ComfyUI-узла (утилизация, VRAM, **температура**, мощность) | `IComfyStats` / `ComfyCcsStats` → `GET {ComfyUrl}/ccs/stats` | сам узел ComfyUI (`ComfyUrl` в `appsettings.Local.json`) |
| Метрики vLLM-движка (очередь, KV-кэш, префикс-кэш, токены/с) | `VllmMetricsSource` → `GET {AnthropicBaseUrl}/metrics` | сам движок vLLM |
| Температуры GPU, VRM, дисков, RAM **удалённых** узлов | — | **никто не собирает** |

Вывод: у CCS уже есть два «шва» к удалённым узлам — `/metrics` у vLLM и `/ccs/stats` у ComfyUI.
Оба отдают часть железа (карты — у ComfyUI), но **ни один не отдаёт CPU/RAM/диски/аптайм узла**,
а vLLM не отдаёт температуры карт вовсе.

## 2. Проблема

Сейчас админ видит: «карты локального стенда» + «карты ComfyUI-узла» + «цифры движка» — в трёх
разных вкладках, без общего ответа на вопрос **«вся ли ферма жива и не перегревается?»**.
На новой ферме это перестало быть любопытством: worker, ai и video — разные машины, и падение
или перегрев одного из них бьёт по всем ходам.

## 3. Инвентарь узлов (живой срез 16.11, Артём)

**Главное:** после переезда CCS на worker панель «Железо» **показывает не тот хост**. `GpuSampler`/`HardwareSampler`
читают `nvidia-smi`, `/sys/class/hwmon`, `/proc/meminfo` и `/run/ccs-gddr6/temps.json` на хосте бэкенда — теперь это
worker, где нет ни одной NVIDIA, нет `asus-ec` и нет помощника gddr6. Карты, VRM и вода **ai** из панели пропали,
RAM и CPU в ней теперь от worker. Опрашивать удалённые узлы придётся в любом случае — это не «доделка», а починка.

| | **worker** 192.168.7.117 | **ai** 192.168.7.83 | **video** 192.168.7.208 |
|---|---|---|---|
| Роль | CCS (`ccs.service`), Forgejo, rs-stand | Strata (Qwen3.8-Flash-Next IQ3) :18020, прокси CLI :18021, метрики :18025 | Windows 11 + WSL2 Ubuntu: ComfyUI :8188, HyperQwen vLLM 27B :18020, gpu-arbiter :18031, Dify :8080 |
| CPU | 2× EPYC 7K62, 96 ядер / 192 потока | Ryzen 9 5900X, 12/24 | Ryzen 7 5700X, 8/16 (в WSL 12 потоков) |
| ОЗУ | 64 ГБ (4×16 RDIMM), available 45 ГБ, swap 8 ГБ (5 занято) | 128 ГБ, available 37 ГиБ, shmem 28 ГиБ (KV-тир) | 64 ГБ, но WSL ограничен 40 ГБ (.wslconfig), available 22 |
| GPU | нет | 2× RTX 3090, PL 350 Вт, VRAM 23,1/24 ГБ | 1× RTX 3090, PL 370 Вт, VRAM 24,1/24 ГБ |
| Диски | NVMe 2 ТБ, `/` 26 % (`/srv/ccs` 303 ГБ) | NVMe 1 ТБ `/` **86 %**; NVMe 2 ТБ `/mnt/nvme2t` 49 %; SATA 2×480 ГБ `/mnt/video` **93 %**; HDD 2 ТБ + 3 ТБ | NVMe 2 ТБ: C: **84 %** (VHDX WSL 609 ГБ), D: 10 %; Samsung 256 ГБ как `/mnt/wsl/models` — **100 %**, свободно 1,8 ГБ |
| Плата/вода | VRM/CPU/System/6 вентиляторов — только через IPMI | asus-ec: VRM, чипсет, CPU, плата; вода **не подключена** (−40 °C) | датчиков платы нет нигде (в WSL hwmon пуст, в Windows нужен драйвер) |
| gddr6/hotspot | нет | есть: `ccs-gddr6` стоит на **ai**, файл свежий (mem 60/68, hotspot 62/62) | недоступно: в WSL нет `/dev/mem` карты |

**Доступы с worker:** на ai ssh работает (ключ `worker_ed25519`, sudo NOPASSWD). На video — **отказ**: в
`administrators_authorized_keys` стоит `from="192.168.7.83"`, то есть ключ разрешён только с ai. Брандмауэр .117
уже пускает, мешает только `from=`. Для агента по HTTP это не нужно; если понадобится ssh — решение Андрея.

**Что видно без установок:** worker — CPU/RAM/load/диск/аптайм локально; video — карта по `:8188/ccs/stats`,
состояние арбитра по `:18031/state`, очередь и KV по `:18020/metrics`; ai — очередь/KV/скорость по `:18025/metrics`.
**Что требует агента:** ai — почти всё, что раньше `HardwareSampler` читал локально; worker — root-помощник IPMI
(VRM, вентиляторы, БП); video — расширить `/ccs/stats` полями RAM и дисков (цифры Windows-стороны — через
планировщик Windows, прецедент есть в `CCS-PoolSampler`).

**Следствие для показателей (важно):** полный паритет на всех узлах **невозможен технически** — на video нет
датчиков платы и gddr6, на worker VRM только по IPMI. Значит, панель обязана быть честной: у каждого узла свой
набор показателей, отсутствующее — «датчика нет», а не ноль. Заполненность дисков — самая полезная метрика
из всех: на video модели забиты на 100 %, на ai `/mnt/video` 93 %, корень 86 %.

## 4. Набор показателей

Предлагаю три слоя. Слой 1 — про узел, слой 2 — про железо, слой 3 — про движок.

### Слой 1 · Живость узла (для каждого из трёх)
- отвечает / не отвечает, с какого времени молчит (как сейчас `stale`);
- аптайм и время старта;
- «роль» узла в одной строке: worker · ai · video.

### Слой 2 · Железо узла (паритет с сегодняшней вкладкой, но на каждом узле)
- **Карты**: утилизация, VRAM занято/всего, температура памяти и ядра, горячая точка, мощность/лимит,
  троттлинг (`powerCap` / `thermal`), частота, P-state, вентилятор.
- **Процессор**: Tctl/ядро, загрузка в % (сейчас этого нет даже локально — а это главный признак «упёрлись в CPU»).
- **ОЗУ**: занято/всего, % (сегодня это единственное, что видно по памяти).
- **Диски**: заполненность %, температура (если отдаёт SMART), скорость/IO — по возможности.
- **Сеть** (для worker особенно): сколько трафика уходит на ai и video, есть ли потери. Для ai/video — входящий трафик.

### Слой 3 · Движок на узле
- **ai (vLLM)**: в работе / в очереди, KV-кэш %, префикс-кэш, токены/с, TTFT, вытеснения (preemptions),
  троттлинг и температуры карт (связь «медленно — вот почему»).
- **video (ComfyUI)**: статус, очередь, занятые слоты, загруженные модели, ошибки/длительность; плюс LLM-метрики,
  если на video свой движок.
- **worker (CCS)**: очередь задач, активные ходы, сколько ждут LLM, потребление памяти процессом CCS.

## 5. Как получать данные (три варианта)

**А · Агент-экспортёр на каждом узле.** На ai и video ставится наш же маленький сервис (тот же код, что
`ccs-gddr6`/сборщик hwmon), отдаёт JSON по HTTP; CCS его опрашивает. **Плюс:** полный паритет с локальной
вкладкой на всех узлах, один формат данных, агент не знает про CCS и про панель. **Минус:** ещё один
сервис в проде на каждом узле, нужна его установка и поддержка.

**Б · Расширить существующие швы.** ComfyUI-узел уже отдаёт `/ccs/stats` — дополняем его CPU/RAM/дисками/аптаймом.
Для ai нужен агент на хосте с vLLM: либо свой маршрут рядом с vLLM, либо наш отдельный. **Плюс:** минимум нового;
часть данных (карты video) уже есть. **Минус:** две разные формы данных у разных узлов, ai-узел всё равно требует агента.

**В · SSH-опрос с worker.** CCS заходит по ssh на ai/video и выполняет `nvidia-smi`/`sensors`. **Плюс:** ничего
не ставится на узлы. **Минус:** ssh-ключи и доступ на серверах, пароли/ключи в конфиге, исполнение команд
на удалённой машине — заметный риск безопасности и своя зона ответственности.

**Рекомендация — Б с переходом на общий формат.** Данные с ComfyUI-узла уже текут, формат данных
узлов должен стать один (иначе в панели будет два разных «железа»), а узел без нашего агента (vLLM)
агент получит обязательно. Если Андрею важно «ничего не ставить на узлы» — тогда В, но тогда
надо обсуждать доступы отдельно.

## 6. Как показывать в панели (три варианта — их рисует дизайнер)

| | А · сводка + детализация | Б · вкладка на узел | В · «стены» узлов рядом |
|---|---|---|---|
| Как | одна карточка на узел (светофор, hottest, статус), ниже — раскрытие выбранного узла | переключатель узлов в шапке вкладки, содержимое как сегодня | три колонки, каждая — мини-панель узла |
| Плюс | обзор сразу, детали по клику | привычная структура сегодняшней вкладки | всё видно сразу без кликов |
| Минус | два уровня вложенности | обзор надо переключать | на телефоне нечитаемо, дублирование |

## 6а. Решение по сбору (архитектурный разрез Александра, принято)

**«Тупой агент, умный бэкенд»** — вариант А в узком виде.

- На ai и video ставится read-only агент `ccs-node-stats` (python3 только со стандартной библиотекой,
  systemd-юнит жёсткости `deploy/systemd/ccs-gddr6.service`). Агент **ничего не толкует**: отдаёт сырой
  срез — `/sys/class/hwmon/*`, `/proc/meminfo`, `/proc/uptime`, `/proc/stat`, CSV `nvidia-smi`, файл
  `ccs-gddr6`, statvfs по меткам. Разбор, уровни, пороги и история остаются в CCS.
- **Б отклонён:** сбор железа внутри процесса ComfyUI — узел пропадает целиком именно тогда, когда
  железо и нужно. **В отклонён:** ssh с worker — та же поверхность RCE, что запрещена у пульта
  удалённых команд, плюс ssh-сеанс каждые 2 с и второй парсер `sensors`.
- Код: вертикаль `ClaudeHomeServer.Llm/LocalStats` (рядом с `HardwareSampler`), реестр узлов — новая
  секция `HardwareNodes` в `appsettings.Local.json`; без секции работает как сегодня (узел `worker`).
  Связь узла с движками и медиа — **по именам**, без URL; склейку делает Main (`LocalModelStatsController`).
- Контракт: `GET /api/local-model/hardware?node=…` (тот же `HardwareReport` + `Node`, `UptimeS`,
  `CpuLoadPerc`) и `GET /api/local-model/hardware/farm` — сводка по узлам. Статусы узла: `ok` / `stale`
  (агент присылает `ageMs` — расхождение часов не мешает) / `down` / `incompatible`.
- Инварианты: ответ агента недоверенный (разбор в своём try/catch, потолки тела и числа, ошибка → статус
  узла, а не падение хоста); секретов на узлах нет (без токена, только чтение, allow-list IP); URL агентов
  задаются **только** в машинном конфиге (иначе SSRF из админки); железо видит только админ;
  **одна точка правды по железу узла video** — карты берём у агента, `/ccs/stats` остаётся контекстом
  медиа-панели.

Полный разрез с файлами и рисками — в докладе задачи `6199b268`.

## 7. Решения Андрея (16.11)

1. **Сбор:** ставим агента на ai и video (вариант А). Значит — один формат данных узла, агент отдаёт
   сырой срез, толкует CCS.
2. **Глубина:** «как есть, честно „датчика нет“» — у каждого узла свой набор показателей; там, где датчика
   нет, панель пишет об этом, а не рисует ноль. Заполненность дисков — в состав показателей.
3. **Место:** та же вкладка в панели «Локальные модели», **переименованная в «Стенды»**. Отдельной
   админ-панели не делаем.
4. **Сеть:** в эту фичу не входит — отдельный шаг позже (С1).
5. **Вариант подачи:** **А — сводка + детализация**. Сверху карточка «Ферма» с тремя узлами
   (светофор, hottest, статус), касание узла раскрывает ниже его детали; на 320 узлы идут списком.
   Макет: `local-model-hardware-cluster-v3.html` (варианты А/Б/В переключаются в шапке).

Открытых вопросов не осталось. Следствия для плана:
- Глубина «как есть» → у узла video не будет датчиков платы и gddr6, у worker VRM/вентиляторы только
  через IPMI (это отдельный root-помощник, решается позже); контракт DTO обязан различать «датчика нет»
  и «значение есть».
- Переименование вкладки в «Стенды» — фронтовый шаг, в текстах интерфейса: «Стенды» вместо «Железо»,
  «Стенд не отвечает» → «Узел не отвечает» (узлов теперь три, «стенд» перестал быть один).

## 8. Живой дамп IPMI с worker (16.11) — контракт разбора надо править

Снят реальный `ipmitool sdr elist full` на worker (Supermicro H11DSi-NT, BMC ATEN FW 1.52,
IPMI 2.0): дамп 2690 Б, чтение занимает 1,44…4,50 с. Правила разбора SDR, описанные в ADR-029,
**на этой плате не работают** — три расхождения:

1. **Сокеты.** В `entity 3` четыре записи: `CPU1 Temp`, `CPU2 Temp` **и** вольтажи `P1_VDDCR`
   (3,3 V), `P1_VMEMABCD` (3,4 V). Разбор «entity 3 по возрастанию instance» дал бы четыре сокета.
   Правильно: фильтр по имени `^CPU(\d+) Temp$` (или по единицам `degrees C`), номер сокета — **из
   имени** (нумерация с 1). Сверка одновременным чтением: CPU1 52 °C против Tctl 54,1; CPU2 38 °C
   против 39,3 (между сокетами 15 °C). Соответствие с `k10temp` однозначное: CPU1 ↔ `0000:00:18.3`,
   CPU2 ↔ `0000:00:19.3`; `lscpu` — 2 сокета, NUMA node0 = 0-47,96-143, node1 = 48-95,144-191.
2. **VRM.** Префикса `CPU<n>` нет **ни у одного** VRM — по прежнему правилу все восемь ушли бы в
   «плату». Реальные имена: `VRMCpu<n>`, `VRMSoc<n>`, `VRMP<n>ABCD`, `VRMP<n>EFGH` — на сокет
   четыре VRM (ядро, SoC, две памяти). Entity у VRM прошивка ставит 8 (Memory Module) — не годится.
3. **Плата.** В `entity 7` двенадцать записей, девять из них вольтажи. Правильно: по имени
   `System Temp` (и при необходимости `Peripheral Temp`), не по entity.

**Вывод в контракт:** entity в прошивке Supermicro **ненадёжен** (`P1_VDDCR` на 3, `P2_VDDCR` на 32,
`P2_VMEM` на 7) — держаться за имя и единицы; entity использовать только для вентиляторов (29).
Вентиляторы: 8 записей, `ok` и >0 у пяти (FAN3 600, FAN4 900, FAN5 700, FAN6 900, FANB 900;
FAN1/FAN2/FANA — `ns`), к сокетам не относятся.

**Ещё два факта:**
- **Кристаллов у EPYC 7K62 шесть, а не восемь** — метки `Tccd1, 2, 3, 5, 7, 8`, с дырами в
  нумерации: разбор не должен рассчитывать на сплошную нумерацию.
- **Период помощника — 15 с, а не 10:** чтение SDR бывает 4,5 с, при десятисекундном периоде
  запуски накладываются. `/dev/ipmi0` доступен только root (есть и `/dev/ipmi1` — второй KCS по
  ACPI; `ipmitool` по умолчанию берёт `ipmi0`, проверено `-I open -d 0`), `ipmitool` 1.8.19.

Правка контракта — в ADR-029 (`b332a28d7`), карточка IPMI-шага — по дампу, а не по прежней букве.
