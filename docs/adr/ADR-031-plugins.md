# ADR-031: Плагины — пакет из существующих примитивов, мост панели v1, модель прав

- **Статус:** Предложено, 2026-10-17 (Александр). Принимает Софья до старта пачки C1 (шаги 3.1/3.2).
- **Основа:** разрез «Плагины и build-it-yourself UX» (задача `ab0682be`), план Егора (задача `b5215b40`, риск 5 — «контракт моста только в задаче»), эпик `802bb754`. Связанные решения: [ADR-014](ADR-014-internal-subsystems.md) (подсистемы и сторожа границ), [ADR-015](ADR-015-cli-profile-sync-zones.md) (зоны профилей CLI), [ADR-016](ADR-016-local-projects.md) (локальные проекты, `ProjectCapabilities`), [ADR-012](ADR-012-mcp-over-http-transport.md) (тулсеты MCP), [ADR-016 Viaduct](ADR-016-viaduct-architecture-section.md) (образец моста sandbox-iframe).
- **Флаги:** `plugins-mvp` (установка, skills/команды, панели) и `plugins-build-yourself` (черновики агентом). Оба `Default: false`, заводятся шагом 1.1. Плюс тумблер подсистемы `Subsystems:plugins:Enabled`.
- **Карта фичи:** [docs/architecture/plugins.md](../architecture/plugins.md).

## 1. Контекст и силы

Нужна плагин-система с build-it-yourself UX: пользователь одним промптом просит «добавь работу с Linear», и агент собирает пакет из панели, slash-команды и навыка для персон. Образец — bb (getbb.app), где так устроены GitHub, память агента, расписания.

Силы, которые тянут решение в разные стороны:

- **Недоверенный код.** Пакет пишет агент или чужой автор. Веб-морда торчит наружу: код плагина с доступом к JWT, стору или DOM хоста — это RCE в браузере владельца.
- **Многопользовательность.** bb однопользовательский, у нас изоляция per-owner — первое требование. Профили CLI (`data/claude-profiles/{key}`) и `~/.claude/skills` общие на инстанс и зеркалятся синком (ADR-015): всё, что туда положено, получают все владельцы.
- **У нас уже есть почти всё.** Нативный формат плагина Claude CLI (`skills/`, `commands/`) с доставкой флагом `--plugin-dir` (есть в CLI 2.1.301, повторяемый, действует только на запуск). Sandbox-iframe с мостом `postMessage` (`WidgetView`, `ViaductFrame`). Личный реестр MCP с allow-list. `McpSecretStore`, `SsrfGuard`, `SafePath.Join`, `RecursiveDirectoryWatcher`.
- **Подпись запуска CLI.** Всё, что влияет на аргументы процесса CLI, перезапускает его вместе со всеми MCP-серверами («Stream closed»). Набор зависит только от свойств сессии, не от хода.
- **Правило вертикалей.** Плагину нужны данные Notes и Tasks, но вертикаль не может ссылаться на другую вертикаль (ADR-014).

### Рассмотрено и отвергнуто

| Вариант | Почему нет |
|---|---|
| Панель плагина в основном бандле / Module Federation remote от пользователя | Недоверенный код получает JWT, весь стор и DOM хоста |
| Серверный код плагина: C# через `DynamicModules` или JS-рантайм в бэкенде | Полное доверие, нет выгрузки, упавший плагин гасит хост. Для логики есть MCP |
| Внешний YARP-модуль на плагин | Отдельный процесс на каждый плагин — слишком тяжело для «панель + навык» |
| Своё хранилище навыков и свой механизм команд | Вторая точка правды рядом с CLI. Нативный формат уже умеет namespacing `plugin:skill` |
| Запись навыков в `~/.claude/skills` или в профиль CLI | Утечка между владельцами: каталоги общие на инстанс |
| Один `kind` на плагин (`panel`/`command`/`skill`) | Запрещает главное — «один промпт → панель + команда + навык» |
| Права на каждый навык | Навык — текст для модели, он ничего не исполняет. Права на нём ничего не ограничивают |
| Окно «разрешить?» на каждый вызов | Усталость от согласий: через неделю все жмут «да» |
| HMR и dev-сервер для панелей | Пересобирать нечего: бандлера нет, серверного кода нет |

## 2. Решение

### 2.1. Плагин = пакет из существующих примитивов

Своего рантайма для плагинов не строим. Плагин — пакет под одним манифестом и одним согласием человека:

| Вклад | На чём едет |
|---|---|
| Навык и slash-команда | Нативный формат плагина CLI, доставка `--plugin-dir` из каталога владельца. Команда = навык с `user-invocable`, отдельного механизма команд нет |
| Панель | Sandbox-iframe без `allow-same-origin` с мостом v1 (§3) |
| Логика с внешним миром (Linear, GitHub) | Запись личного реестра MCP (ссылка из манифеста) или серверный прокси по праву `net:{host}` |
| Триггер (после MVP) | Существующие `TriggerSources`, только ссылка |

**Серверного кода плагина в процессе бэкенда нет и не будет.**

### 2.2. Манифест

Манифест `ccs-plugin.json` лежит рядом с нативным `plugin.json` CLI:

```json
{
  "id": "local-3f9a/linear-notes",
  "name": "Linear из заметок",
  "version": "0.1.0",
  "bridge": { "v": 1 },
  "contributes": {
    "skills":   ["skills/linear-sync"],
    "commands": ["commands/linear.md"],
    "panels":   [{ "id": "main", "slot": "sidebar", "entry": "panel/index.html", "title": "Linear" }],
    "requires": {
      "mcp":     ["linear"],
      "secrets": [{ "name": "LINEAR_TOKEN", "required": true }]
    }
  },
  "permissions": {
    "requested": ["notes:read", "net:api.linear.app", "secret:LINEAR_TOKEN"]
  }
}
```

- `id` — глобальный `{publisher}/{slug}`. В MVP publisher = `local-{ownerShort}`, позже — автор каталога.
- `contributes` — набор вкладов: `skills`, `commands`, `panels`. Любой из массивов может быть пуст, хотя бы один вклад обязателен. `requires` вкладом не считается.
- `contributes.requires.secrets` — секреты пакета: имя и признак `required`. Обязательный секрет, не заданный владельцем, блокирует установку.
- `permissions.requested` — **запрошенные** права, потолок. Выдаёт их человек (§4).
- `bridge.v` — версия моста панели, с которой пакет собран (§3.5).
- Неизвестные поля разбор игнорирует (forward-compat). Источник правды схемы — модель `Core/Models/Plugins/PluginManifest.cs`; пример выше обязан с ней совпадать.

**Обоснование выбора формы.** Три поля — объекты, а не скаляры и плоские массивы, чтобы расширять их без ломающего изменения формата:

- `bridge` — объект: версия моста v2 добавится как `{ "v": 2 }` со своими полями рядом, разбор v1-пакетов не меняется.
- `secrets` — объекты: признак `required: true` блокирует установку, пока секрет не задан (решение В2 макетов). Строкой это не выразить.
- `permissions` — объект: сейчас в нём единственное поле `requested`, позже рядом может встать, например, `granted` для предвыданных прав каталога без смены типа поля. Выданные человеком права при этом живут в записи установки (§2.3), не в манифесте.

### 2.3. Хранилище и установка

```
data/plugins/{ownerId}/
  packages/{id}/{version}/   — неизменяемые пакеты
  installed.json             — записи установки
  _drafts/{slug}/            — черновики build-it-yourself
```

- Запись установки ссылается на пакет по **id + version + sha256**, хранит **выданные** права (`granted`), `enabled` и источник.
- **Источник установки — строка, а не enum** (`"draft"`, `"upload"`, позже `"catalog:{ref}"`); неизвестные значения при разборе терпим. Урок `McpCatalogRef`: новое значение enum при откате кода унесло бы файл владельца в `.corrupt`.
- Пакет проходит **валидатор по allow-list файлов**: `plugin.json`, `ccs-plugin.json`, `skills/**/SKILL.md` и вспомогательные `.md`, `commands/*.md`, `panel/**` (статика). Отказ на всё остальное, прежде всего `hooks/`, `.mcp.json`, `bin/`, `settings.json`, `agents/` — это исполнение кода или обход allow-list MCP. Отказ на символические ссылки, выход за корень, превышение размера и числа файлов. Окончательный перечень запрещённого уточняет спайк (шаг 0).
- Каталог пакетов монтируется в песочницу **read-only**.

### 2.4. Вертикаль `ClaudeHomeServer.Plugins`

Одна новая вертикаль (`IAppSubsystem`, ключ `plugins`, тумблер `Subsystems:plugins:Enabled`): хранилище, валидатор, REST установки и согласия, мост панели, прокси `net:`, тулсет `plugins`.

В Core — только модели (`Models/Plugins/`) и два шва:

- `IPluginDirSource` — «каталоги плагинов для запуска (owner, persona, project)». Его читает Llm (`ClaudeSession`) опциональной зависимостью (`?? []`).
- `IPluginCapability` — обработчик операций одного права. Регистрирует **вертикаль-владелец данных**: Notes — `notes:read`, Tasks — `tasks:read`. Направление `Notes → Core ← Plugins`, ссылки вертикаль → вертикаль нет.

Отключаемость по ADR-014: выключенная подсистема не регистрируется; мост и прокси отвечают честным 503 с причиной; обязательный параметр конструктора от Plugins вне вертикали — дефект.

### 2.5. Доставка навыков и команд

- `ClaudeSession` добавляет `--plugin-dir` на каждый включённый пакет владельца из `IPluginDirSource`.
- Набор считается **только от свойств сессии** (владелец, персона, проект), никогда от хода. Установка, удаление и смена версии вступают в силу **со следующего старта процесса CLI**: в новом чате или после «Перезапустить сессию». Посреди чата процесс ради плагина не перезапускаем. Это закрывает риск 2 плана Егора.
- Персоне плагин открывает привязка типа `Skill` с target `plugin:{id}` (новый enum не нужен). Гейт — на уровне всего плагина: `--plugin-dir` грузит пакет целиком, фильтровать навыки внутри — значит переписывать пакет на лету.
- Пакеты не попадают ни в `~/.claude/skills`, ни в `data/claude-profiles/*/plugins`: `LlmProviderRegistry.SyncDirs` синхронизирует папку `plugins` профилей между собой, и туда наши пакеты класть нельзя.
- Плагины профиля CLI (`installed_plugins.json`, которые уже читает `SkillsService`) и плагины владельца — **разные источники**, в API и UI метятся явно.

### 2.6. Build-it-yourself

- Агент пишет **только** в `data/plugins/{owner}/_drafts/{slug}/` и **только** через MCP-тулсет `plugins`: `draft_create`, `draft_write_file`, `draft_validate`, `draft_preview`. Сервер пишет через `SafePath.Join` и прогоняет валидатор. Встроенный Write не годится: у container-владельцев каталог не смонтирован на запись, у local-владельцев Write пишет куда угодно.
- **Инструментов install, approve и grant у агента нет по построению**, это держит сторож на состав тулсета. Принять черновик, выдать права, ввести секрет может только человек кнопкой и только по пользовательскому JWT; сервисный JWT получает 403.
- Всё вне пакета (добавить сервер в реестр MCP, завести токен) агент только **предлагает**, делает человек.
- Состав `tools/list` тулсета `plugins` не зависит ни от флага, ни от хода; флаг проверяется на бэкенде отказом.

## 3. Мост панели v1

### 3.1. Песочница

- Панель монтирует компонент хоста `PluginFrame` в `<iframe sandbox="allow-scripts">` **без `allow-same-origin`**. Origin фрейма непрозрачный: ни куки, ни JWT, ни хранилища хоста.
- Навигация iframe не несёт заголовок `Authorization`, а все ручки у нас под JWT Bearer. Поэтому в MVP хост сам забирает entry панели по REST (с JWT, только из установленного пакета владельца) и монтирует её через `srcdoc` (как `WidgetView`). Перед монтированием хост вставляет CSP: `default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data: blob:; connect-src 'none'; form-action 'none'`, а также шим `plugin-kit` (мост и CSS-токены тем).
- Следствие: **панель MVP — один самодостаточный HTML** (скрипты и стили инлайн, потолок размера задаёт валидатор). Многофайловые панели — открытый вопрос (§7).
- React хоста во фрейм не передаётся. Панель — статический HTML/ESM, при желании со своим vendored preact; `plugin-kit` даёт стили контролов под дизайн-систему.

### 3.2. Приём сообщений

Хост принимает сообщение, только если выполнены **все** условия:

```ts
e.source === frameWindow      // окно СВОЕГО фрейма
&& e.origin === 'null'        // фрейм без allow-same-origin шлёт с непрозрачного origin
&& msg?.source === 'ccs-plugin'
&& msg.v === 1
```

Остальное молча отбрасывается, как в `ViaductFrame`. Хост отправляет во фрейм `postMessage(msg, '*')`: адресат — конкретное окно, а origin непрозрачного фрейма назвать нельзя. Поэтому **в сообщения хоста не кладётся ничего, чего панель не вправе видеть**.

### 3.3. Формат сообщений

Конверт у всех сообщений общий: `{ source, v: 1, type, ... }`. Из фрейма приходит `source: 'ccs-plugin'`, от хоста уходит `source: 'ccs-host'`.

**Фрейм → хост**

| type | Поля | Смысл |
|---|---|---|
| `ready` | — | Шим загрузился, ждёт `init`. Повторный `ready` игнорируется |
| `call` | `id: string`, `op: string`, `args: object` | Вызов операции хоста. Ответ — `result` с тем же `id` |
| `resize` | `height: number` | Желаемая высота; хост зажимает в пределы слота |

**Хост → фрейм**

| type | Поля | Смысл |
|---|---|---|
| `init` | `plugin: {id, version}`, `slot`, `context`, `theme`, `locale`, `granted: string[]` | Ответ на `ready` |
| `result` | `id`, `ok: true, data` или `ok: false, error: {code, message}` | Итог `call` |
| `theme` | `theme` | Смена темы без перемонтирования |
| `context` | `context` | Смена контекста слота (например, другой проект) |

- `theme` — значения CSS-переменных `--cc-*` текущей темы и её имя.
- `context` — только то, что слот явно отдаёт: `projectId` и id выбранного объекта, если он есть. Список чатов, стор, JWT, данные других владельцев во фрейм не попадают никогда.
- `granted` — информационная копия выданных прав, чтобы панель могла прятать недоступное. **Источник правды — сервер**: панель, соврав себе про права, получит `denied`.

### 3.4. Путь вызова

1. Фрейм шлёт `call {id, op, args}`.
2. `PluginFrame` сам добавляет то, что фрейм подделать не может: id и версию **смонтированного** плагина и контекст слота (`projectId`). Затем вызывает `POST /api/plugins/{id}/call` с пользовательским JWT, в теле `{op, args, context}`.
3. Сервер проверяет: подсистема включена (иначе 503), владелец JWT = владелец установки (иначе 404), установка `enabled`, `ProjectCapabilities` проекта контекста допускает плагины, право операции есть в `granted` (иначе 403). Только после этого вызывает `IPluginCapability`.
4. Ответ хост пересылает во фрейм как `result`.

Операции называются `{область}.{глагол}`; каждая требует ровно одного права, сопоставление объявляет её обработчик. MVP:

| op | Право | args |
|---|---|---|
| `notes.search` | `notes:read` | `{query, limit?}` |
| `notes.read` | `notes:read` | `{id}` |
| `tasks.list` | `tasks:read` | `{status?, limit?}` в пределах проекта контекста |
| `net.fetch` | `net:{host}` + `secret:{name}` при `auth` | `{url, method?, headers?, body?, auth?: {secret, header, prefix?}}` |

`net.fetch` выполняет серверный прокси: только точный хост из `granted`, `SsrfGuard`, без редиректа на другой хост, таймаут и потолок размера ответа. Секрет подставляет сервер в заголовок `auth.header`, в ответ и во фрейм он не попадает.

Коды ошибок `error.code`: `denied` (нет права), `not_found` (нет установки или объекта), `invalid` (не тот формат args, неизвестный `op`), `unavailable` (подсистема или фича выключены, локальный проект), `upstream` (сбой внешнего хоста у `net.fetch`), `timeout`, `limit` (превышен потолок размера или числа вызовов в полёте).

Хост ограничивает число одновременных вызовов одного фрейма и размер `args`. Числа фиксирует шаг 3.2 в `CLAUDE.md` вертикали.

### 3.5. Версионирование

- `v` — целая версия протокола. Пакет объявляет `bridge` в манифесте; хост, не поддерживающий эту версию, панель не монтирует, а показывает заглушку «Панель собрана для более новой версии».
- **Внутри v1 разрешены только аддитивные изменения:** новые `type`, новые `op`, новые необязательные поля. Неизвестные `type` и поля обе стороны игнорируют. Неизвестный `op` → `invalid`.
- **Ломающее изменение = v2.** Хост держит v1 и v2 одновременно, пока в установленных пакетах есть `bridge: { "v": 1 }`. Снятие v1 — отдельное решение с миграцией черновиков.
- Ожидаемые аддитивные шаги после MVP: `notes:write:{prefix}`/`tasks:write` (новые `op`), `project-files:read`, открытие ссылки через хост, события «данные изменились» от хоста.

## 4. Модель прав

- **Права крупные и называют поверхности хоста.** MVP: `notes:read`, `tasks:read`, `net:{exact-host}`, `secret:{name}`. Glob'ов по файловой системе нет. `write`-права, `project-files:read`, `notes:write:{prefix}` — после MVP (§7).
- **`requested` ≠ `granted`.** Манифест несёт потолок. Человек выдаёт права в диалоге установки, их подмножество хранится в записи установки. Выдать право, которого нет в `requested`, — 400.
- **Согласие — один раз при установке.** Обновление, которое расширяет `requested`, требует повторного согласия; новые права автоматически не выдаются. Окна «разрешить?» на каждый вызов нет. Исключение — будущие разрушающие операции под существующим флагом `workspace-destructive`.
- **Проверка — на сервере при каждом вызове**, по актуальной записи установки, без кэша: отозвал право — со следующего вызова `denied`.
- **Права защищают мост панели, а не агента.** Агенту права не нужны и ограничить его не могут: возможности агента задают его инструменты (`PersonaAccessPolicy`, allow-list MCP, среда исполнения). Навык плагина меняет поведение агента, но не даёт ему новых возможностей; в UI это пишем прямо. Главная угроза навыка — долговременная prompt-инъекция. Защита: установку делает только человек и видит полный текст навыков, источник помечен, позже добавятся подпись и хеш.
- **Секреты** хранятся per-owner механизмом `McpSecretStore`, имя файла — в `BackupPaths.SecretFileNames`. После сохранения значение не показывается, в UI только «задан» или «не задан».

## 5. Инварианты

1. **Песочница панели.** `sandbox` без `allow-same-origin`, JWT и стор хоста во фрейм не попадают, `connect-src 'none'`, весь выход наружу — только мостом. Приём сообщений — по `e.source === win && e.origin === 'null'` плюс метке протокола.
2. **Per-owner изоляция.** Пакеты, установки, черновики, права и секреты ключуются владельцем. Каждый `{id}`-эндпоинт сверяет владельца установки: чужое — 404. Даже будущее общее хранилище пакетов (`_shared/{sha256}`) не делает общими права и секреты.
3. **Пакеты не попадают в общие каталоги CLI** (`~/.claude/skills`, `data/claude-profiles/*`). Только `--plugin-dir` из каталога владельца.
4. **Набор `--plugin-dir` зависит от сессии, не от хода.** Изменение применяется со следующего старта процесса CLI.
5. **Пара mount ↔ `DockerPathMapper` правится одной правкой.** Расхождение даёт exit=1 и ложный `Unreachable` у каждого container-владельца при зелёных тестах.
6. **Валидатор по allow-list.** Исполняемые части формата CLI-плагина (`hooks/`, `.mcp.json`, `bin/`, `settings.json`, `agents/`) в пакет не попадают.
7. **Агент не устанавливает плагины.** Install, approve и grant — только человеком по пользовательскому JWT.
8. **ADR-016.** В MVP плагины в локальных проектах выключены через `ProjectCapabilities` с текстом причины, без инлайнового `if (project.IsLocal)`. Каталог пакетов и секреты на устройство не едут. Прокси `net:` — серверный выход в сеть вне шлюза `/gw`; это допустимо, потому что работает только для серверных проектов.
9. **Источник установки — строка**, неизвестные значения терпим.
10. **Граница вертикалей.** Plugins не ссылается на Notes и Tasks; обработчики прав приходят через Core-шов `IPluginCapability`.

## 6. Trade-offs

| Выбрали | Против | Цена |
|---|---|---|
| Нативный формат плагина CLI + `--plugin-dir` | Своё хранилище навыков | Зависим от формата CLI, который может дрейфовать между версиями. Нужна проба загрузки тестового плагина при обновлении CLI и строгий allow-list файлов |
| Применение со следующего старта CLI | Мгновенное применение | Установил плагин — в текущем чате он появится только после «Перезапустить сессию». Нужна плашка с кнопкой |
| Iframe с непрозрачным origin, `srcdoc` | Основной бандл | Панель не может использовать React хоста и его контролы. Свой UI через `plugin-kit`, в MVP только один HTML-файл |
| Крупные права, согласие при установке | Тонкие права, согласие на вызов | Право `notes:read` открывает все заметки владельца, а не папку. Сужение — следующими правами, аддитивно |
| Гейт персоны на весь плагин | Гейт на отдельный навык | Нельзя дать персоне половину плагина |
| Навыки едут в системный блок | Подгрузка по требованию | Описания навыков раздувают каждый ход, установка обнуляет prefix cache. Нужен потолок числа и объёма описаний на сессию; по умолчанию плагин включается привязкой |
| Прокси `net:` на сервере | Сеть из фрейма | Сервер делает исходящие запросы за пользователя. Нужны точный хост, `SsrfGuard`, запрет редиректа, лимиты |

## 7. Что осталось открытым

- **Триггеры** (webhook, cron) — после MVP, через существующие `TriggerSources`.
- **Marketplace и шаринг между владельцами** — после MVP. Раскладка готова: общее хранилище `data/plugins/_shared/{sha256}` подключается без миграции записей установки, меняется только резолв пути. Нерешено: подпись пакетов, доверие к publisher, модерация.
- **Плагины в локальных проектах** — после MVP. Нужно решить, как доставлять каталог на устройство и как прокси `net:` уживается со шлюзом `/gw`.
- **`write`-права** (`notes:write:{prefix}`, `tasks:write`) и `project-files:read` — после MVP, аддитивно в мосте v1.
- **Многофайловые панели.** `srcdoc` не умеет относительные ресурсы. Кандидат — короткоживущие билеты на ассеты пакета (как билеты ADR-016). Решаем, когда упрёмся в потолок одного HTML.
- **Потолок контекста от навыков** — конкретные числа (сколько плагинов и сколько байт описаний на сессию) задаёт шаг 2.1 по замеру.
- **Тексты UI для двух видов «плагинов»** (профиля CLI и владельца) — согласует Софья.
- **Пример манифеста в ADR vs фактическая модель.** Первая редакция §2.2 разошлась с `PluginManifest.cs` в трёх полях (`bridge`, `requires.secrets`, `permissions`); исправлено по ревью пачки A. Сторожа, который держит пример §2.2 в синхроне с моделью, нет: дрейф снова поймает только ревью. Кандидат — тест, разбирающий JSON-блок §2.2 моделью и проверяющий `Validate()`.
- **Перечень запрещённых файлов пакета** уточняется по итогам спайка (шаг 0): как CLI ведёт себя с `hooks/` и другими частями формата в local и container.
