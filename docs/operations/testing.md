# Тесты: наборы, шарды, сторожа, пул хостов

Как устроен прогон бэкенд-тестов после фичи «Ускорение тестов» и что из этого обязан знать
каждый, кто пишет или гоняет тесты. Правила написания теста (платформонезависимость, паттерн
«интервал — опция, ожидание — событие», метки категорий) — в
[conventions.md](../architecture/conventions.md), раздел про тесты; здесь — устройство прогона
и обязанности автора теста, которые держат сторожа.

> Документ описывает только то, что есть в коде ветки. Базового списка медленных тестов
> нет и не заводится: он протухает за неделю. Медленное находит профиль и сторож длительности.

## Наборы и метки

Монолит `ClaudeHomeServer.Tests` и остальные тестовые проекты гоняются двумя проходами:

| Проход | Фильтр | Что внутри |
|---|---|---|
| **Fast** | `Category!=Host&Category!=Slow&Category!=Integration&Category!=Node&Category!=Bench` | всё, что не помечено исключаемой категорией |
| Остальное | `(Category=Host\|Category=Slow\|Category=Integration\|Category=Bench)&Category!=Node` | вторым проходом на шарде CI; вместе два прохода дают весь шард |

Fast — **исключение категорий**, а не перечень меток: новый тест без меток попадает в Fast сам.
Отсюда две обязанности автора:

- `[Trait("Category", "Host")]` на **классе**, который поднимает `TestWebApplicationFactory`
  (xUnit v2 не наследует трейты класса, метка нужна на самом классе). Держит сторож `HostCategoryGuardTests`.
- `[Trait("Category", "Slow")]` на **методе** без хоста, который не укладывается в гейт
  длительности. Это временная мера до перевода ожидания на событие; навсегда в Slow — тесты,
  чья стоимость в самой работе (спавн процесса, скан решения), их перечень — в conventions.md.

Категория `Node` исключена и из CI (нужен Node и `frontend/node_modules`); `Dns` в CI гоняется.

Фильтр Fast записан в трёх местах: `FAST_FILTER` в
[test-profile.py](../../scripts/test-profile.py), `FAST` в [ci.yml](../../.github/workflows/ci.yml)
и проверка «быстрые тесты» в секции `Pregate` [appsettings.json](../../backend/ClaudeHomeServer/appsettings.json).
Меняешь набор — правь все три.

## Как гонять

В чате агента тесты — только инструментом `mcp__tests__run_tests` (прогресс, очередь сборок,
«Стоп»), не Bash. Таблица ниже — для голого терминала и для того, что делает сам инструмент.

| Задача | Команда |
|---|---|
| Какие тестовые проекты задела правка | `scripts/tests-affected.sh` (по `git diff` и графу `ProjectReference`; только читает git) |
| Один набор тестов | `dotnet test backend/ClaudeHomeServer.Tests --filter "FullyQualifiedName~SessionManagerTests"` |
| Fast по решению | `dotnet test backend/ClaudeHomeServer.slnx --no-build --filter "Category!=Host&Category!=Slow&Category!=Integration&Category!=Node&Category!=Bench"` |
| Монолит шардами локально | `python3 -I scripts/test-shards.py --run backend/ClaudeHomeServer.Tests -n 3 --results .cc-attachments/test-shards` |
| Fast шардами (как в предгейте) | `python3 -I scripts/test-shards.py --run-fast backend/ClaudeHomeServer.slnx --split backend/ClaudeHomeServer.Tests=3,backend/ClaudeHomeServer.Llm.Tests=2 --filter "<фильтр Fast>" --results .cc-attachments/pregate-fast` |
| Профиль прогона по TRX | `python3 -I scripts/test-profile.py <папка с TRX или .trx>` |
| Сторож длительности | `python3 -I scripts/test-profile.py <папка TRX набора Fast> --check` |
| Тесты самих скриптов | `python3 -I scripts/test_test_profile.py` и `python3 -I scripts/test_test_shards.py` |

Заметки:

- `--run` берёт готовую сборку (`dotnet test --no-build`) — сначала собери. Папка результатов
  получает `shard{i}.log` и TRX каждого шарда; в конце печатаются стена и пик RSS дерева
  процессов (на Linux). Без `--timings` раскладка идёт по хешу имени класса; с профилем —
  `python3 -I scripts/test-profile.py <trx> --json > profile.json` и `--timings profile.json`.
- `--check` гонять **только на TRX набора Fast**: там любой тест дольше порога — нехостовый
  тест без метки Slow. Гейт — 5 с (`--threshold`), тесты от 2 с до порога печатаются блоком
  «цель доводки» без падения. `--latest-run` берёт TRX последнего прогона из общей папки
  (окно 600 с), а не всё накопленное.
- В `xunit.runner.json` монолита `maxParallelThreads` = 6 и `longRunningTestSeconds` = 2;
  у `Llm.Tests` — `maxParallelThreads` = 4, параллель коллекций включена. Потоки не поднимай:
  пик памяти растёт вместе с ними.

## Шарды по классу

Монолит режется **по классам**, а не по пространствам имён (перекос) и не по методам
(классовые фикстуры не делятся).

- **Раскладка.** [test-shards.py](../../scripts/test-shards.py): жадная упаковка классов по
  длительностям из профиля (`test-profile.py --json`); класс, которого в профиле нет, — в шард
  по стабильному хешу полного имени `mod N`. Профиль учитывает, что серийный класс держит один
  поток прохода: оценка стены шарда — `max(самый долгий класс, сумма / 5)` на проход, а не
  голая сумма. Списка шардов в репозитории нет: раскладка считается на каждый прогон из
  `dotnet test --list-tests`.
- **Фильтр шарда.** `python3 -I scripts/test-shards.py --list LIST.txt --shard 2/6 --timings profile.json`
  печатает фильтр VSTest вида `FullyQualifiedName~Класс.|…` (точка не даёт зацепить класс с тем
  же префиксом).
- **Самопроверка** в каждом режиме: каждый тест списка попадает ровно в один шард, иначе exit 1.
  Объединение шардов равно списку тестов — состав не сокращается.
- **CI** ([ci.yml](../../.github/workflows/ci.yml)): сборка один раз, её `bin` едет артефактом
  в матрицу — монолит 6 шардов, `Llm.Tests` 2 шарда по классам, остальные тестовые проекты
  («rest», 3 шарда) — по проектам (`--slnx … --exclude … --shard i/N` печатает slnx шарда).
  Каждый шард гоняет два прохода (Fast, затем остальное) и сторож длительности. Профиль прошлого
  прогона лежит в кэше (job `backend-profile`), его веса и раскладывают следующий прогон.
  Число шардов меняется только в матрице.
- **Порог сторожа в CI — 30 с** (`DURATION_GUARD_THRESHOLD`, единственное место): на 4 vCPU
  раннера стена теста вырастает в разы, там ловятся только грубые регрессии. Локально и в
  предгейте — 5 с.

## `run_tests`: монолит шардами

Монолит без `filter` инструмент гоняет **несколькими процессами `dotnet test` параллельно**
([TestShards.cs](../../backend/ClaudeHomeServer.TestRuns/TestShards.cs)):

- Настройка `TestRuns:MonolithShards` (по умолчанию 3, допустимо 1–6; 1 — прежний один процесс)
  и `TestRuns:MonolithTarget` (`backend/ClaudeHomeServer.Tests`) в `appsettings.json`.
- Шарды включаются, только когда цель — монолит, `filter` не задан и подсчёт тестов
  (`--list-tests`) прошёл; иначе — один процесс, как раньше. Любой `filter` отключает шарды:
  дроби им прогон по-прежнему.
- Все шарды идут под **одним** слотом `BuildConcurrencyGate`: второго семафора нет, счётчик
  единственный на процесс. У каждого шарда свой `TurnId` и свой TRX (`results-shard{i}`);
  оборван любой — оборван прогон, код выхода — первый ненулевой.
- Раскладка — **по числу тестов класса**, а не по секундам: профиля длительностей у сервера
  нет. Самопроверка покрытия та же, что в CI; не сошлась — прогон идёт одним процессом.
- **Потолок прогона прежний — 540 с** вместе с очередью сборок (против 600 с `MCP_TOOL_TIMEOUT`
  хода). Шарды его не меняют: они сокращают стену монолита, а не снимают потолок. Подробности
  потолка и запретов аргументов — [mcp-servers.md](../architecture/mcp-servers.md), раздел
  «Прогон тестов».
- **Цена — память.** Каждый шард — свой testhost: замер 2026-10-29 — N=1 даёт пик RSS 5,5 ГиБ,
  N=3 — 9,5 ГиБ при лимите `ccs-agents.slice` 18 ГиБ. Упёрлись в память — снижай
  `MonolithShards`, а не лимит.

## Сторожа

| Сторож | Что стережёт | Где |
|---|---|---|
| `HostCategoryGuardTests` | класс, поднимающий хост, помечен `Host`; скан по метаданным собранных сборок всех тестовых проектов slnx (после правки тестов собери решение — сторож видит собранное) | `Guards.Tests`, Slow |
| `PooledHostGuardTests` | класс пула не меняет конфиг общего хоста (`ExtraServices`, `ExtraConfig`, `WithWebHostBuilder`) | `Guards.Tests`, Slow |
| `CollectionDefinitionGuard` | определения xunit-коллекций лежат в сборке самих тестов (см. ниже) | вызывается из `Tests` и `Llm.Tests` |
| `test-profile.py --check` | нехостовый тест без `Slow` дольше порога | CI (30 с), предгейт и локально (5 с) |

Предгейт шага (секция `Pregate` в `appsettings.json`) включает «быстрые тесты» (Order 35: Fast без
пересборки, `test-shards.py --run-fast`: монолит 3 шарда и `Llm.Tests` 2 шарда по классам, остальные
тестовые проекты — одним процессом на rest-slnx, всё параллельно; раскладка по профилю TRX прошлого
прогона из той же папки, первый прогон — по хешу класса) и «сторож длительности» (Order 36) после `build`; закрытие задачи они
не блокируют, результат виден ревьюеру.

Оба сканирующих сторожа делят один скан решения (`HostScan.Solution`) и помечены `Slow`:
скан сборок решения — работа, а не ожидание.

## Хост на класс и пул общих хостов

Контроллер-тест, который поднимал `TestWebApplicationFactory` на каждый тест, — главный
пожиратель времени. Две ступени лечения, от простой к сложной:

1. **Хост на класс.** Класс берёт `IClassFixture<…>` с вложенной фикстурой-хостом; всё, что
   тесты меняют в общем хосте или графе сервисов, **явно сбрасывается** в конструкторе класса
   (конструктор xUnit выполняется перед каждым тестом) или изолируется построением — новый
   владелец и свои каталоги на тест. Образцы: коммит `808f8428b` (Projects, AgentDownloads,
   LlmProxy, Hardware: 67,1 с → 17,3 с), `db43e9b44` (граф на класс в `TeamWaveServiceTests` и
   `ChatArchiveServiceTests`, сброс в `ResetTestState`), `62d151050` (там же — снос сессий и
   задач предыдущего теста: класс не зависит от порядка тестов). Сброс проверяй мутацией, как в
   `db43e9b44`: убрал возврат состояния — тест обязан покраснеть.
2. **Пул общих хостов** ([SharedHostPool.cs](../../backend/ClaudeHomeServer.TestKit.Host/SharedHostPool.cs)):
   один хост на ключ конфигурации на процесс тестов; класс подключается
   `IClassFixture<PooledHost>` (образец — `TasksControllerTests.Host`). Каталог — свой на класс,
   владельцы — свои (`NewOwner()`), общих `testuser`/`seconduser` в хосте пула **нет**: случайный
   `CreateAuthenticatedClient()` падает на входе, а не делит данные с соседями. Пул — не
   `ICollectionFixture`: коллекция сериализовала бы классы, а пул их не сериализует.

**В пул нельзя:** классы с `ExtraServices`/`ExtraConfig`/`WithWebHostBuilder` (конфиг общего
хоста не меняется; сторож плюс проверка при каждой выдаче хоста), `*DisabledTests`, честные e2e
и классы, проверяющие «пустое состояние» всего хоста. `SessionManagerTests` вне пула: там
тяжёлый конструктор на каждый тест, а не хост. Нужен свой хост — свой подкласс
`TestWebApplicationFactory` в `IClassFixture`. Расширять пул только по цифре профиля.

## Коллекции xunit

Имена коллекций — константы `TestCollections` в TestKit (`Inotify`, `ProcessGlobalState`).
**Определения `[CollectionDefinition]` живут в каждой тестовой сборке** (`TestCollectionDefinitions.cs`
в `ClaudeHomeServer.Tests` и `ClaudeHomeServer.Llm.Tests`): xunit находит их только в
прогоняемой сборке, из TestKit определения молчали и `[Collection(…)]` становился неявной
коллекцией «по имени» — классы последовательны внутри, но параллельны всему остальному и
упирались в общий бюджет inotify пользователя. В TestKit остаются только константы.

- Сторож `CollectionDefinitionGuard` ([TestKit](../../backend/ClaudeHomeServer.TestKit/CollectionDefinitionGuard.cs),
  коммит `0c29e9d2c`) проверяет: каждое используемое имя имеет определение в своей сборке,
  `Inotify` определён с `DisableParallelization`, в TestKit определений нет. Его зовут
  `CollectionDefinitionGuardTests` в `Tests` и в `Llm.Tests`.
- **Новый тестовый проект с `[Collection(TestCollections.*)]` обязан завести свои определения
  и вызвать сторож сам:** сторож проверяет только те сборки, которые его вызывают, и чужую
  забытую не поймает.
- Семантика одного имени различается по сборкам намеренно: `ProcessGlobalState` в `Llm.Tests` —
  с `DisableParallelization`, в монолите — без него (зафиксировано в обоих файлах определений).

## Ожидания в тестах

Тест, который ждёт тик продукта, платит этим тиком на каждом прогоне. Порядок перевода —
в conventions.md («интервал — опция, ожидание — событие»); коротко:

- интервал продукта — `internal`-поле или опция с **прежним** дефолтом, дефолт держит отдельный
  тест на значение;
- ожидание в тесте — `TaskCompletionSource`/событие продукта с `WaitAsync(потолок)`; таймаут —
  **красный**, `Task.WhenAny(tcs, Delay)` без проверки результата проглатывает его;
- **negative-окно** («за N секунд ничего не случилось») ограничено и выводится из тестовых же
  интервалов продукта, а не из полного таймаута «на всякий случай»;
- проверка мутацией: убери сигнал (`TrySetResult`) — тест обязан покраснеть по таймауту.

Образцы: `08c2fc082` (W1: `ExecutorIdlePollInterval` и сигнал простоя из фейка через
`TaskCompletionSource`, 10,15 с → 0,1 с) и `968a2572a` (W4: пауза-прогрев снята, negative-окна
выведены из интервалов, значения дефолтов закреплены тестами, сумма классов 21,2 → 6,7 с).

## Известные пределы

Это то, что не сделано или не доказано; не считай их решёнными.

- **TeamWave + ChatArchive ≈ 15 с.** Порог 13 с на сумму двух классов не взят: по замеру `62d151050`
  `TeamWaveServiceTests` — 12,15 с, `ChatArchiveServiceTests` — 2,86 с. Остаток — рост сторов
  Projects и Personas: `Save()` пишет стор целиком (`ProjectManager.cs:205`, `PersonaManager.cs:422`),
  и цена мутации растёт с числом уже заведённых записей. Стор сессий не виноват: замером снос
  сессий на время класса не повлиял (11,7 с против 11,9 с).
- **Баланс шардов монолита в CI не идеален:** ×1,20 по времени job и ×1,44 по чистому времени
  тестов (замер штаба 29.10; как посчитан показатель, в репозитории не записано). Раскладка уже
  учитывает серийные классы (`b4d282039`), но равенства по чистому времени не даёт.
- **Inotify-классы монолита идут последовательным хвостом.** Коллекция `Inotify` определена с
  `DisableParallelization`: её классы xunit запускает после параллельной части, по одному. В
  `Llm.Tests` они дополнительно помечены `Slow` и уходят из Fast.
- **Режим `run_tests` — без профиля и без `env`.** Серверная раскладка шардов идёт по числу
  тестов класса, а не по секундам (профиля у сервера нет); параметр `env` инструмента принимает
  только белый список Playwright, для `dotnet` переменные окружения тестов задать нельзя.
- **Windows: прогрев после `Start()` у наблюдателя не проверен.** Пауза-прогрев `Task.Delay(200)`
  в тестах `TurnFileWatcher*` снята в W4, потому что на Linux подписка `InotifyBackend` ставится
  синхронно в `Start()` и запись после него видна сразу. У `FileSystemWatcherBackend`
  (Windows/macOS) такая гарантия не проверялась: всплывёт флак «событие не пришло» на Windows —
  начинать с этого места.

## Новый тестовый проект: чек-лист

1. Имя на `.Tests` и запись в `ClaudeHomeServer.slnx`: «rest» подхватывает проект сам
   (шардирование по проектам), сторожа Host и пула сканируют все `.Tests` из slnx.
2. Использует `TestWebApplicationFactory` — метка `Host` на каждом таком классе; собери решение
   и запусти `HostCategoryGuardTests`.
3. Использует `[Collection(TestCollections.*)]` — свои `[CollectionDefinition]` в сборке проекта
   и вызов `CollectionDefinitionGuard.AssertLocalDefinitions` из его теста.
4. Класс хочет общий хост — `IClassFixture<PooledHost>` и своя изоляция данных; не подходит под
   «в пул нельзя» — свой хост на класс.
5. Перед сдачей: Fast по проекту, `test-profile.py --check` на его TRX, тесты скриптов, если
   правил `scripts/`.
