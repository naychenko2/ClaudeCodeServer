> Опора — запрос Андрея 17.11 (задача 95233318, эпик 45af8178) и его уточнение в чате:
> **предметы и все их настройки — в профиле ребёнка**, отдельного места «Репетитор» нет.
> Номера строк — по `master` 5553af6b6. Код не писал, разрез сделан по чтению кода.

## Что просили

1. Набор предметов настраивается (Лиза хочет «Литературу» и «Окружающий мир»).
2. У каждого предмета свой репетитор — полноценная персона: имя, аватар, голос, промпт.
3. Модель репетитора берётся у любого поставщика: Anthropic по API-ключу, DeepSeek, GLM, локальная.
4. Настраивается в профиле ребёнка (уточнение Андрея поверх постановки «отдельное место»).

## Что есть сейчас (факты из кода)

- **Предметы — чистая косметика фронта.** `CHILD_SUBJECTS` захардкожен в
  `frontend/src/features/childMode/ChildHome.tsx:22`, а связь «чат → предмет» хранится в
  `localStorage` браузера (`ChildWorkspace.tsx:43,60,177`, по умолчанию `'math'`). Сервер про
  предмет не знает: все чаты «Уроков» идут с одним тьютором `ChildProfile.TutorPersonaId`
  (`ChildChatsController.cs:65`, `ChildRulesController.cs:94`).
- **Маршрут хода жёстко Anthropic:** `ChildApiKeyRoute.Resolve` (`ClaudeHomeServer.Llm/ChildApiKeyRoute.cs`)
  принимает только запись пула с `ApiKey` и без `OAuthToken`. Сторонняя модель отказывается явно
  (`ClaudeSession.cs:4748-4751`), валидатор профиля требует запись пула
  (`ChildProfileValidator.cs:38`).
- **Фолбэка у ребёнка нет** — цепочка из одной модели (`ClaudeSession.cs:93-97`).
- **Шлюз `/gw` уже отказывает ребёнку в маршруте по подписке** (`UpstreamSelector.cs:84-87`),
  маршрут к провайдеру (`GatewayUpstreamKind.Provider`) не трогает.
- **child-safety ставится по признаку хода, а не по персоне**: `PersonaLayerContributor.cs:121-129`
  передаёт `childSafety: sessionContext.IsChild`, `PersonaPromptBuilder.cs:66` ставит секцию
  перед слотами, а `:124` — оговорку последним блоком. Любой промпт репетитора её не снимет.
- Детский MCP allow-list пуст (`ChildModeAllowList.Pairs`), встроенных инструментов нет (`--tools ""`).
- Все чаты идут через один адаптер `ClaudeSession` (`LlmSessionAdapterFactory.Create`); прямой
  HTTP-движок «Локальная» чатом не является, агентному месту `local/direct` непригодны
  (`ModelAssignmentResolver.cs:86-93`).

## Главное решение

**Предмет — запись в `ChildProfile`. В ней лежат маршрут модели и ссылка на персону-репетитора.
Характер репетитора (имя, аватар, голос, промпт) живёт в обычной персоне ребёнка, но правится
только из профиля, узкими админскими ручками.**

Почему маршрут в профиле, а не в `Persona.Model`:
- Профиль пишет одна ручка, только админ, с валидатором и `AdminByStore`. Читает его одна
  политика (`IChildModePolicy`, fail-closed). Это готовая единственная точка правды для И2.
- У персоны около 40 путей записи (`PersonasController`: CRUD, `ai/*`, `bindings`, `automation`,
  `voice`, `avatar`; MCP `personas`; `apply-transcript` онбординга). Положи модель в персону —
  и каждый из них станет путём к И2. Ребёнку они закрыты И1, но правило «маршрут меняет только
  админ через проверку» держалось бы на сорока замках вместо одного.
- `Persona.Model` у репетитора остаётся `null`. Сверка И1-бис смотрит на профиль.

Почему персона, а не отдельная сущность «репетитор»:
- Аватары (генерация, загрузка, кроп, фон-догон `ImageBackfillService`), голос
  (`PersonaVoice`, `TtsVoiceCatalog`, `VoiceResolver` по `personaId` в `TtsController`), слой
  промпта и детская оговорка уже работают с персоной. Вторая сущность продублировала бы всё это.
- Владелец репетитора — сам ребёнок, как у тьютора волны 1: `SessionManager` и слой промпта
  резолвят `Session.PersonaId` по владельцу чата. Персона владельца-админа, «расшаренная»
  ребёнку, ломает эти проверки.

## 1. Модель данных

```
ChildProfile {
  ...как в волне 1...
  string TutorPersonaId    // остаётся: «Помощник» онбординга правил и запасной репетитор
  string ProviderKey       // остаётся: маршрут онбординга правил
  string Model             //   (тот же формат маршрута, что у предмета, см. §3)
  List<ChildSubject> Subjects   // НОВОЕ; порядок списка = порядок плиток
}
ChildSubject {
  string Id                // slug [a-z0-9-]{1,32}, стабилен; ключ Session.ChildSubject
  string Label             // «Окружающий мир», 1..40
  string Glyph             // 1..3 символа на плитке («Аа», «×÷»)
  string Color             // КЛЮЧ палитры из белого списка (info/rose/success/...), не hex
  string TutorPersonaId    // персона ребёнка; провижнер создаёт её при добавлении предмета
  string ProviderKey       // маршрут: запись пула (Anthropic API) или ключ LlmProviders
  string Model             // конкретный id модели; tier:*/preset:* запрещены
  DateTime? RouteAcknowledgedAt; string? RouteAcknowledgedBy   // согласие админа на не-Anthropic маршрут
  bool Enabled = true      // выключенный предмет скрыт с главной, его чаты не стартуют
}
Session.ChildSubject : string?   // НОВОЕ, закрепляется при создании чата, как ChildSpace
```

- Поля добавочные, `BackupSchema.Version` не двигается.
- **Миграция**: на старте один раз, идемпотентно. Если у включённого профиля `Subjects` пуст,
  засеиваются три предмета волны 1 (`math`, `russian`, `english`) с `TutorPersonaId`,
  `ProviderKey` и `Model` профиля. Неявного «пусто = три по умолчанию» в политике не заводим:
  это была бы вторая точка правды.
- Старые чаты без `ChildSubject` (их немного, у одного ребёнка) получают `math`, ровно как
  сейчас решает фронт (`subjectOf` → `'math'`). Это делает та же миграция, по `ChildSpace != null`.
- Персона предмета: `Specialty=None`, `TemplateKey=null`, `MemoryEnabled=false`, без
  `Bindings` и `AutomationRules`. Инструменты те же, что у тьютора (`tasks`, `notes`); при
  пустом детском allow-list они и так не доезжают. Один репетитор может вести несколько
  предметов: `TutorPersonaId` у разных предметов может совпадать.
- Удаление предмета не удаляет его чаты. Они остаются в списке «Уроков» только на чтение
  (И1-бис не найдёт предмет — ход не стартует, детский текст «Этот предмет закрыт»).
  Персона удаляется, только если на неё не ссылается ни один предмет и `TutorPersonaId` профиля.

## 3. Маршрут модели и новая редакция И2

### Как модель попадает в ход

**Явная конкретная модель в записи предмета, без `UserModelTierResolver` и без пресетов.**
Причины: пресет — это цепочка с фолбэком, а слот разворачивается по матрицам владельца. Есть и
новая грабля: `ModelAssignmentResolver.Resolve(usageKey, explicitModel)` разворачивает маркеры
`tier:*` и `preset:{id}` даже в **явной** модели (`ModelAssignmentResolver.cs:86-93`). Если
пикер админа отдаст `preset:…`, первый шаг пресета уйдёт в `EffectiveModel` — в том числе на
модель подписки. Валидатор обязан отказывать в маркерах (`400 model_not_concrete`), и
`LaunchMismatch` повторяет ту же проверку на запуске.

Как маршрут раскладывается по видам:

| `ProviderKey` резолвится в | Что требуем | Как идёт ход |
|---|---|---|
| запись `ClaudeSubscriptionPool` | `ApiKey` есть, `OAuthToken` пуст; `ResolveByModel(Model) is null` (модель Anthropic) | как в волне 1: `ChildApiKeyRoute`, `BuildOAuthCliEnv` с ключом |
| запись `LlmProviders`, `IsLocal=false` (DeepSeek, GLM…) | `Enabled`; `ProviderKey(Model) == ProviderKey`; у модели цена > 0 (`LlmModelConfig.PriceIn*/PriceOut*`); согласие админа | env провайдера (`BuildCliEnv`), как у взрослого; через шлюз — если провайдер этого требует (`UseServerGateway`) |
| запись `LlmProviders`, `IsLocal=true` | `Enabled`; модель принадлежит провайдеру; согласие админа | как у взрослого (шлюз при `LocalModelStats`) |
| что-то другое (`claude`, ключ без записи, `local`/`direct`) | — | отказ запуска |

`ChildApiKeyRoute` → `ChildRoute.Resolve(snapshot, subject, pool, providers)` с результатом
«пул» или «провайдер». Ветка в `ClaudeSession.cs:4742-4757` перестаёт отказывать сторонней
модели, но требует, чтобы её провайдер **совпал** с `ProviderKey` предмета. Пул-блок выше
(`:4723-4736`) для ребёнка не применяется вовсе: сейчас его последствия снимает
`Remove("CLAUDE_CODE_OAUTH_TOKEN")`, а надо не входить в блок.

### И2, редакция 2: что не меняется ни при каком поставщике

**И2′. Ход ребёнка никогда не идёт по потребительской подписке и никогда не уходит на модель,
которую админ не назначил предмету явно.**

| Самолечение пары в `LlmSessionAdapterFactory.Create` (`:173-185`, `_subscriptionPool.Pick`) | для ребёнка пара не самолечится. Рассогласование — отказ, как в И1-бис, без подбора подписки | **да** |

Ключ провайдера. Без шлюза ключ DeepSeek/GLM лежит в env процесса CLI в песочнице ребёнка, как у

Поэтому принудительный шлюз для ребёнка в первую пачку не беру, оставляю шагом закалки (Т7).

### Что И2′ не обещает — и что идёт в админку

- **Данные ребёнка уходят поставщику.** У DeepSeek и GLM своя юрисдикция и свои условия
  обработки данных несовершеннолетних. Я их условий не знаю и проверять не брался — это вопрос
  к Андрею, а не к коду.
- **Локальная модель хуже держит системный промпт.** Секция child-safety и оговорка доедут, но
  правило «не решать за ребёнка» и маркер стоп-сигнала модель может не соблюдать. Кнопка
  «Мне неприятно» от модели не зависит и остаётся главным каналом.
- Поэтому не-Anthropic маршрут требует **явного согласия админа**: при сохранении предмета с
  таким маршрутом в запросе обязателен `acknowledgeRouteRisk: true`, иначе 400
  `route_risk_unacknowledged`. Сервер пишет `RouteAcknowledgedAt/By`. В редакторе рядом с
  выбором модели — предупреждение: для облака «переписка уходит поставщику X», для локальной —
  «слабее держит правила безопасности». Согласие сбрасывается при смене `ProviderKey`.

### И3 (бюджет) у сторонней и локальной модели

- Сторонняя: стоимость хода считает `LlmProviderRegistry` по ценам модели (`:1387-1392`). **Цена 0
  у обеих сторон даёт `null`, то есть расход не учитывается, и бюджет молча перестаёт
  ограничивать.** Поэтому валидатор требует цену > 0 у облачной модели (`400 model_unpriced`).
- Локальная: `SpendSources.IsFree` — 0 $. Бюджет её не ограничивает, ограничивают окна и
  дневные минуты. Это честное поведение, его надо показать в редакторе: «бюджет не тратится».
- Подсистема Spend выключена — отказ, как в волне 1, у любого поставщика.

## 5. Админский UI: раздел «Предметы» в профиле ребёнка

Место — `ChildProfileEditor` в «Пользователях» (`frontend/src/features/childMode/ChildProfileEditor.tsx`,
вызывается из `UserManagementModal`), по уточнению Андрея. Профиль уже большой. Предлагаю вкладки:
«Режим и время» (то, что есть) и «Предметы». Поля `providerKey`/`model` профиля переезжают
в «Предметы» строкой «Помощник (правила)», чтобы все маршруты были в одном месте.

Минимальный состав карточки предмета:
- название, глиф, цвет (выбор из ключей палитры), включён, порядок (стрелки вверх/вниз; drag — потом);
- репетитор: имя, аватар (существующие компоненты генерации и загрузки аватара персоны, но
  поверх админских ручек), голос (существующий пикер `GET /api/tts/voices`), промпт характера
  (одно поле `character`, без слотов mustDo/mustNot в первой пачке);
- модель: пикер «поставщик → модель» только из допустимых (записи пула с API-ключом,
  включённые `LlmProviders`, конкретные модели; ни пресетов, ни слотов). Рядом — предупреждение
  и галка согласия для не-Anthropic, пометка «бюджет не тратится» у локальной.

Админские ручки (все — `[Authorize(Roles="admin")]` + `AdminByStore`):

| Ручка | Что |
|---|---|
| `PUT /api/users/{id}/child-profile` | как сейчас плюс `subjects[]` (без `tutorPersonaId` во входе) и `acknowledgeRouteRisk` по предмету |
| `POST /api/users/{id}/child-subjects/{subjectId}/tutor` | провижн персоны предмета (`EnsureSubjectTutorAsync`), идемпотентно |
| `PUT /api/users/{id}/child-tutors/{personaId}` | только `name`, `character`, `greeting`, `voice`, `gender` |
| `POST /api/users/{id}/child-tutors/{personaId}/avatar/{generate,upload,select}` | делегирует `PersonasCrudService` с владельцем персоны = ребёнок и владельцем расхода = админ |

Вариант «повторно использовать `PersonasController` с подменой арендатора» отвергаю: это общий
обход владельца персоны, он годится и для чужих взрослых персон. Тот же класс ошибки, что
«общий админ-доступ к чужим чатам».

## Открытые вопросы к Андрею

1. Условия DeepSeek/GLM о данных несовершеннолетних — проверить до включения маршрута у Лизы (Т5 код не блокирует).

   закреплённые поля чатов предмета при сохранении профиля) — предлагаю так. Межпоставщицкое
   продолжение транскрипта несёт те же грабли, что `migrate-provider` у взрослых; если они
   мешают — вариант «старые чаты только на чтение».
