## Контекст

Харнес (claude CLI) нужен с полным доступом к машине пользователя, при этом все вызовы
наружу — LLM и сервисы платформы — должны идти через сервер. Цель — **секреты не на
клиенте**: токены подписок, ключи провайдеров и сервисный JWT владельца живут только на
сервере. Полный контроль сетевого выхода клиента целью НЕ является: у харнеса Bash с правами
пользователя, `curl` мимо прокси настройками не лечится, а сетевой фильтр ОС на клиенте
сознательно не ставим.

Что проверено по коду и определяет решение:

- **Секреты сейчас едут в env хода.** Токен подписки — `CLAUDE_CODE_OAUTH_TOKEN`
  (`LlmProviderRegistry`), ключи сторонних провайдеров — `ANTHROPIC_AUTH_TOKEN`, сервисный
  JWT владельца (7 дней, неотзываемый) — в конфиг MCP. Запуск CLI на клиенте как есть
  унёс бы их все на машину, где у агента полный доступ.
- **Контракт запуска держит `System.Diagnostics.Process`.** `ClaudeSession` завязан на него
  ~30 местами (stdin/stdout, `Kill`, `ExitCode`, `HasExited`). Прецедент обхода уже есть:
  `DockerProcessRunner` — локальный `docker exec -i` как труба stdio, убийство по `TurnId`.
- **Почти все серверные подсистемы проекта читают хостовую ФС напрямую**: `FileService`
  (41 файл-потребитель, синхронный API, ключ — строка `rootPath`), оба ватчера (inotify),
  `GitService` (плюс прямые `File.Exists(.git)`, `.gitignore`), синк Dify по хешам,
  CodeGraph (Roslyn), досье, Docs и сканер карты, навыки и `PersonaAgentFileSync`, notes
  проекта, вложения, discovery сервисов, WebDAV, транскрипты CLI.
- **MCP по https CLI молча теряет инструмент** — транспорт только `http`.

## Решение

### 1. Ось — проект, а не пользователь

Проект бывает **серверным** и **локальным**. Серверный следует `User.ExecutionEnvironment`
(`local`/`container`) — без изменений. Локальный привязан к устройству (`Project.DeviceId`)
и исполняется только на нём.

- Ключ «одна папка — один проект на владельца» становится парой «устройство + путь»
  (`EnsureRootFree`, датасет Dify): строки пути сервера и клиента могут совпасть.
- Смена привязки проекта при существующих чатах запрещена — по аналогии со сменой среды.
- Устройство — сущность ADR-008 (`DeviceRegistry`, сопряжение, токен устройства, HTTPS с
  пинингом). Второй канал не строим: исполнение — ещё одна возможность устройства.

### 2. Секреты не на клиенте: LLM-шлюз и сайдкар

- **LLM-шлюз на сервере работает на ключах сервера** (решение владельца, 2026-09-24):
  принимает токен хода и подставляет учётные данные сервера — токен подписки из пула
  `ClaudeSubscriptionPool` или Anthropic API-ключ для моделей Claude, ключи
  DeepSeek/MiniMax/GLM для сторонних. Провайдера **и модель** выбирает
  шлюз (фоновые вызовы CLI идут на haiku, у стороннего upstream её нет); для локальных
  проектов отпадают профили CLI и перенос транскрипта при фолбэке. Шлюз сам отвечает на
  `GET /api/hello`, пропускает любой HTTP-метод (MCP streamable HTTP шлёт `GET`).
- **Токены подписок Claude через шлюз — по согласованию Anthropic.** Публичные условия
  запрещают «collect, store, or intermediate» токены подписки (разбор —
  [спайк](../research/local-projects-spike-2026-09.md) §4); владелец продукта получил
  согласование Anthropic на этот сценарий (2026-09-24). Копия согласования хранится вне
  репозитория у владельца; при его отзыве или изменении условий подписки выключаются
  **одним тумблером шлюза** (`LlmGateway:AllowSubscriptions`), а не правкой кода. При
  подстановке токена подписки шлюз пробрасывает `anthropic-beta: oauth-2025-04-20` и
  ведёт учёт пула по заголовкам `anthropic-ratelimit-unified-*` — это та же точка правды
  пула, что `rate_limit_event` у серверных проектов, второго счётчика не заводим.
- **Через шлюз ходят только подписки на `claude setup-token`** (долгоживущий токен, без
  обновления). Аккаунты на интерактивном логине (`.credentials.json`, короткий access-токен)
  шлюз не берёт: их сегодня обновляет сам CLI, запущенный на сервере, а у локального проекта
  серверного CLI нет — через несколько часов шлюз получил бы 401. Собственное обновление
  токенов в шлюзе отвергнуто: это чужой протокол обновления плюс гонка со серверным CLI за
  один refresh-токен. Выбор аккаунта пула для локального хода фильтрует такие аккаунты; нет
  подходящего — честный отказ хода с причиной, а не тихий переход на API-ключ (правило
  «явно выбранного не подменяем»).
- **Учётные данные сервера на клиент не едут никогда** — ни токены подписок, ни ключи, ни
  JWT: «ключи сервера на локальной машине» означает, что ими пользуется харнес на машине
  через шлюз, а не что они там лежат.
- **Сайдкар агента на `127.0.0.1`**: `ANTHROPIC_BASE_URL`, MCP (`http`) и `HTTPS_PROXY`
  собственного трафика CLI смотрят в него; он туннелирует всё в канал устройства и сам
  добавляет авторизацию. Сервисный JWT на клиент не едет. Токен хода знает **только агент**
  (в env CLI его нет, адрес хода несёт `TurnId`); он привязан к владельцу+чату+устройству и
  **живёт столько же, сколько ход, с отзывом по его концу** — TTL «минуты» не выживает у
  многочасовых ходов. Заголовки контекста MCP (`X-Caller-Session-Id`) ставит шлюз по
  привязке токена, хвост маршрута сверяется с чатом токена.
- `HTTPS_PROXY` — маршрутизация, а не граница: трафик Bash харнеса мимо прокси допустим, и
  текст согласия говорит это прямо.

### 3. Процесс: удалённый раннер по образцу docker-раннера

`RemoteProcessRunner : IProcessLauncher` запускает на сервере процесс-ретранслятор stdio
через канал устройства; `Kill` — по `TurnId`. Контракт `Process` и `ClaudeSession` не
меняются; `--permission-prompt-tool stdio` едет тем же потоком. Файлы, которые spec
передаёт путями (рантайм-`--settings`, системный промпт, MCP-конфиг хода), раннер
материализует на клиенте. Обрыв канала посреди хода: CLI продолжает работу, агент
буферизует stdout по `TurnId` и досылает после реконнекта. Агент запускает CLI в своей
группе процессов и убивает группой (у CLI дети — MCP-клиенты, Bash), после убийства
убирает `sessions/<pid>.json` в профиле устройства.

### 4. Один код — две композиции, набор функций задаёт матрица возможностей

Второй версии подсистем нет. Подсистемы трёх групп:

| Группа | Подсистемы | У локального проекта |
|---|---|---|
| Привязаны к файлам | файлы, diff/revert, git, ватчер, терминал, дев-серверы и preview, навыки и `.claude/agents`, вложения | в агенте, **тем же кодом** (другая композиция `IAppSubsystem`) |
| Платформа | ядро чата, история, шлюз, задачи, память, персоны, личные заметки, расходы, TTS | на сервере, без изменений |
| Нужен контент проекта на сервере | знания Dify, CodeGraph, досье, панель документации, уборка карты | выключены |

- **У агента нет долговременного состояния**: метаданные, чаты и история — на сервере; у
  клиента только файлы проекта и транскрипты CLI. Поэтому нет миграций данных — только
  версионирование протокола. Это условие отличает агента от «клиента как второго сервера»,
  отброшенного в ADR-008.
- **Матрица возможностей проекта** — единственная точка правды для фронта и серверных
  guard'ов. Инлайновых `if (project.IsLocal)` не заводим.
- **Guard без обходов**: серверная подсистема файловой группы, вызванная для локального
  проекта, отвечает явным отказом ДО обращения к диску; сквозные функции (MCP
  `files_*`/`WorkspaceToolset`, `search_unified`, привязка персоны «папка проекта», индекс
  «какие чаты трогали файл») — тоже. Тест-сторож краснеет на новом обходе.

### 5. Доступ с других устройств

- **Чат и задачи локального проекта видны отовсюду**; ход идёт, пока устройство онлайн,
  иначе честное «устройство офлайн».
- **Файлы: запись и чтение разведены по путям.**

| Откуда открыт проект | Чтение | Запись |
|---|---|---|
| С самой машины (клиент) | агент по `localhost` | агент по `localhost` |
| С другого устройства | ретранслятор через сервер, только онлайн | нет |

  У ретранслятора в протоколе **нет операций записи вообще**: `list`, `read`, `stat`,
  `search` и git только на чтение (`status`, `diff`, `log`, `show`). Так «редактировать
  только на машине» — физическое свойство, а не политика сервера. Поиск — на агенте.
- **Агент сам ограничивает пути**: только под корнями, явно разрешёнными пользователем на
  этой машине, проверка реального пути (симлинки), потолки размера, отдача потоком.
  Серверной проверке агент не доверяет.
- Остаточный риск, названный прямо: скомпрометированный сервер читает файлы проектов в
  пределах корней, пока устройство онлайн. Не хуже того, что он и так может через харнес.

## Последствия

- **Транскрипты CLI локального проекта живут только на клиенте** и в бэкап сервера не
  попадают; история чата цела (`history.json` собирается на сервере из stream-json), но
  resume после потери машины невозможен.
- `FileService` выносится из Main в вертикаль (он и так в курсе этапа 5 ADR-014); шов —
  async и с ключом «проект», событие `OnMutated` сохраняется.
- Новый периметр поддержки — кроссплатформенный агент (не WPF-клиент ADR-008, тот только
  Windows), версии протокола, автообновление.
- Ватчер в агенте — тот же `RecursiveDirectoryWatcher`; ветку `FileSystemWatcher` на
  Windows/macOS проверить отдельно.

## Отброшенные варианты

| Вариант | Почему отброшен |
|---|---|
| Среда на пользователя (`ExecutionEnvironment = remote`) | Удалённость — свойство проекта: файлы живут на устройстве |
| Двустороннее зеркало проекта на сервере | Вторая точка правды, конфликты правок агента |
| Полная виртуализация ФС для всех серверных подсистем | 15+ подсистем; ровно поэтому ADR-008 отверг схему |
| Вторые версии подсистем для локальных проектов | Удвоенная поддержка, расхождение поведения |
| Секреты в env хода на клиенте | Противоречит цели; ключи доступны харнесу с полным доступом |
| MCP напрямую на сервер по https | CLI молча теряет инструменты |
| Проект виден только на своей машине | Теряется сценарий «задача с телефона»; технически не нужно |
