## Блокирующие находки

### B1 (critical) — вики не включается флагом: в MF-remote «Заметки» своя копия стора флагов

**Шаги воспроизведения**
1. Собрать фронт (`npm run build`) и поднять стенд.
2. Включить флаг `llm-wiki` пользователю (`users.json` → `FeatureFlags: {"llm-wiki": true}`),
   перезапустить стенд.
3. Открыть «Заметки» → переключатель «Заметки | Вики» **виден**.
4. Кликнуть «Вики» → вкладка подсвечена, **центр пуст**, дерева разделов нет.
5. Открыть чат → в шапке **нет** кнопок «Разобрать этот чат» / «Открыть хронику» /
   «Откатить всё из этого чата».
6. В DevTools: запросов `/api/wiki*` — **ноль**.

**Ожидаемое:** при флаге вкл. — экран вики и кнопки в шапке; запросы `/api/wiki/tree` идут.
**Фактическое:** UI вики не рендерится вовсе, ни одного запроса к бэку.

**Причина (подтверждена разбором бандлов)**
- `frontend/src/features/notes/NotesPage.tsx:75` берёт `useFeature` из `aihome_shell/kit`
  (хостовый, общий инстанс) — поэтому переключатель «Вики» виден.
- `frontend/src/features/notes/wiki/WikiTab.tsx:234`, `frontend/src/features/notes/NoteView.tsx:59`,
  `frontend/src/features/notes/WikiChatActions.tsx:108` берут `useFeature` из
  `../../lib/featureFlags` — а это **отдельная копия модуля** внутри remote-сборки
  (`frontend/dist/notes-remote/assets/NoteView-BHZzNmpo.js`: `si={},ci=new Set` — свой стор,
  `setAllFlags` в remote-сборке не встречается ни разу; `setAllFlags` зовёт только хост —
  `frontend/src/App.tsx:497`).
- Итог: в remote-инстансе `_flags` пуст → `getFlag('llm-wiki')` всегда false →
  `WikiTab` (`if (!enabled) return null`, `:293`) и `WikiChatActions` (`:224`) ничего не рисуют
  и не ходят в `/api/wiki*`.
- Сборка это не ловит: `frontend/modules/notes/vite.config.ts` намеренно НЕ ставит алиас
  `aihome_shell/kit` на локальный путь («именно он вернул бы копию»), но и `lib/featureFlags`
  не выведен в shared/kit — модуль тянется напрямую.

**Почему это major/critical:** фича под флагом не включается ни у кого в собранной поставке;
весь вики-UI недоступен. Это не косметика — вся П1 держится на этом экране.

**Обход на стенде (код продукта не трогал):** артефакт сборки
`frontend/dist/notes-remote/assets/NoteView-BHZzNmpo.js` пропатчен — `getFlag('llm-wiki')`
читает `localStorage['qa-llm-wiki']`. Все UI-проверки ниже сделаны с этим обходом; без него
экраны вики не рендерятся.

### B2 (critical) — все REST-вызовы вики из UI идут на `/api/api/wiki/…` → 404

**Шаги воспроизведения**
1. Собрать фронт, поднять стенд, войти.
2. Открыть вкладку «Вики» (или любой экран вики) → в DevTools:
   `GET http://127.0.0.1:5555/api/api/wiki/tree` → **404**.

**Ожидаемое:** `GET /api/wiki/tree` → 200.
**Фактическое:** 404 на `/api/api/wiki/*`; в центре экрана — «Не найдено» с кнопкой «Повторить».

**Причина:** `frontend/src/lib/wiki.ts` строит пути с `/api` (`:295` `wikiHttp('/api/wiki/tree')`,
`:311`, `:323`, `:378`, `:392`, `:406`, `:474`, `:536`, `:624`, `:630`, `:690` и др.), а
`request()` из `frontend/src/lib/offline.ts:31` сам префиксует `BASE = '/api'` (`:1623`
`fetch(BASE + url, …)`). Остальной код фронта так не делает: `src/lib/api.ts` зовёт
`request('/auth/login')`, `'/users'` и т. п. — без `/api`.

**Почему это не поймали тесты:** юнит-тесты мокают `request` на уровне пути и ждут
`'/api/wiki/journal'` (`frontend/src/features/notes/wiki/__tests__/WikiJournal.test.ts:238`) —
то есть они закрепляют **неправильный** путь; двойной префикс появляется только на реальном
`fetch`. Ни один тест не проверяет итоговый URL.

**Обход на стенде:** в том же артефакте сборки заменено `/api/wiki/` → `/wiki/`.

### Прочие находки

**H1 (major) — «Журнал»: число в диалоге отката нечестное.**
Запись журнала показывает «применено · 1 стр.», а диалог «Откатить всё из этого чат?» —
«В журнале с этим источником: 0 применённых записей, 0 стр.» (на фикстуре с applied-пакетом —
«1 применённых записей, 1 стр.»).
Причина: `WikiJournal.tsx:348` считает `entries.filter(e => e.status === 'applied' && …)`,
а бэк в склейке записей берёт статус **пакета** (`WikiJournalReader.cs:270`,
`Status = joined.Count == 1 ? joined[0].Status : null`). У применённых, но позже откатанных
пакетов статус `reverted`, у ещё не откатанных — `proposed`/`accepted`; значения `applied`
в списке записей не бывает. То есть счётчик в диалоге показывает 0 там, где человек видит
применённую запись, и «1 применённых записей» — ещё и не согласовано по числу
(нужно «1 применённая запись»).

**H2 (major) — откат всего из чата не снимает хронику.**
`POST /api/wiki/packages/retract` возвращает `removedChronicles: []`, но файл хроники чата
остаётся на диске со всеми утверждениями и сносками:
`pages/Проекты/…/Хроники/e2acfe8a-….md` — 10 утверждений, 10 сносок на карточку
`QA-чат-3-ba4a0115`. В каталоге вики эта страница видна как обычная.
Причина (по коду): снятие хроники в `WikiRetractService.cs:323` ищет операцию `OpCreate`
с путём в папке «Хроники», а хроника пишется **вне пакета** — `AppendChronicleAsync`
(`WikiChatIngestService.cs:411`) создаёт/пополняет файл напрямую. Операций `create` для
хроники в пакетах нет ⇒ снять её откатом нечем.
Это прямое расхождение с обещанием в UI: «Снимется всё, что Хранитель взял из этого чата:
**хроника** и знания» и с шапкой сценария П1 (п.9).

**H3 (minor) — `metrics.jsonl` не различает разделы и расходится с `_health.md`.**
Две строки (для `personal` и `projects/047a15f0…`) содержат **одни и те же** числа
(`notes:12, orphans:9, unlinkedMentions:4, wikiPages:11`), тогда как `_health.md` разных
разделов содержат 10 и 2 находки. По коду метрики линта считаются **по всей базе**
(`WikiLint.cs:515` `_baseNotes` — весь снимок), а находки — по разделу; в строке метрик
`section` стоит, но цифры к разделу не привязаны. Сверять «метрики после фикса» по
`metrics.jsonl` бессмысленно — они одинаковы для всех разделов.

**H4 (minor) — «Журнал»: «Откатить всё из этого чат» вместо «…из этого чата».**
`WikiJournal.tsx:244` и `:353`: `Откарить всё из этого ${meta?.label ?? 'источника'}`,
где `ORIGIN_META.session.label = 'чат'` (`WikiInbox.tsx:39`) — именительный падеж в
родительном месте. Для `note`/`file`/`url`/`task`/`dossier`/`memory` — та же ошибка
(«из этого заметка»). Пункт 14 П1 требует родительный падеж именно здесь.

**H5 (minor) — «Разобрать в базу» для заметки личного раздела отказывается.**
`POST /api/wiki/ingest/note` для личной заметки → `{"outcome":"rejected","reason":"личный раздел — с Ф2"}`.
Формально задокументировано («target не передаём: „common" для источника вне проекта — отдельное
решение человека, ADR-036 §3»), но в UI это выглядит как отказ без пути решения: человек
нажимает «Разобрать в базу» у личной заметки и получает отказ.

  подсистемы), замер заменён своим сценарием в браузере; числа выше — из него.
