# ADR-005: Серверная часть режима чтения ссылок

**Статус:** Предложено
**Дата:** 2026-08-03
**Принимающие решение:** Андрей (владелец продукта)
**Реализация:** backend — Денис, frontend — Кира, тексты — Софья, ревью — Глеб
**Связанные артефакты:** макет `docs/mockups/link-reader-v1.html`,
спецификация `docs/mockups/link-reader-proposal.md` (Майя)

## Контекст

Ридер — панель воркспейса, которая показывает содержимое внешней страницы рядом с чатом.
Клиент отдаёт серверу URL, сервер идёт по нему сам и возвращает текст статьи. Макет
предъявляет серверу два требования: домен известен до ответа (берётся из URL на клиенте)
и **ошибка приходит с причиной одной строкой**.

Что уже есть в коде и определяет решение:

- **`Services/SsrfGuard.cs`** — резолвит хост и отсекает loopback/приватные/link-local/CGNAT
  диапазоны, fail-closed на пустом резолве. Написан ровно под эту задачу (`save-from-url`).
- **Клиент `safe-download`** (`Program.cs:316`) — `AllowAutoRedirect = false`, чтобы редирект
  на приватный хост не обошёл проверку. Прецедент загрузки произвольного пользовательского URL
  лежит в `FilesController.SaveFromUrl`. **Но прецедент неполный:** там `AllowAutoRedirect=false`
  плюс `EnsureSuccessStatusCode()`, то есть любой 3xx превращается в 502 — редиректы не
  поддерживаются вовсе. Ридеру они нужны (http→https, bare→www, короткие ссылки), поэтому
  самая ответственная часть — ручная цепочка хопов с перепроверкой каждого — пишется с нуля
  и прецедента в коде не имеет.
- **`MarkdownContent.tsx`** — `react-markdown` + `remark-gfm`, **без `rehype-raw`**. Сырой HTML
  в markdown не рендерится в принципе.
- **`Telemetry/PiiRules.cs:57`** — `url.full` и `url.query` намеренно дропаются, а
  `server.address` остаётся в `KeepTags`.
- **`MarkitdownService`** — python-утилита на хосте, при отсутствии молча возвращает `null`.
  Опциональная зависимость, не годится в фундамент фичи.

Главная сила: **приватность важнее полноты**. Ридер не должен добывать содержимое ценой
отправки URL наружу третьей стороне и не должен превращать сервер в разведчик локальной сети.

## Решение

Извлечение — **в процессе бэкенда**, одним NuGet-пакетом `SmartReader` (порт Mozilla
Readability на AngleSharp; 0.11.1, Apache-2.0, обновлён 25.07.2026, netstandard2.0/2.1).
HTTP делаем сами, библиотеке отдаём уже скачанный HTML — её собственный загрузчик не
использовать никогда, иначе он обойдёт SSRF-проверку и политику редиректов.

```
Клиент: кнопка-компаньон у ссылки
  |  POST /api/reader/read  { url }   <- URL в теле, не в query
  v
ReaderController [Authorize] + флаг link-reader
  |
  1. Разбор URL: схема http/https, порт 80/443,
     без userinfo, отбросить #fragment
  2. SsrfGuard.IsPubliclyRoutableAsync  -> local-address
  3. GET через клиент "link-reader":
     AllowAutoRedirect=false, ResponseHeadersRead
     на каждом 3xx (<=5) -> шаги 1 и 2 для нового URL
  4. Content-Type -> html / текст / отказ (not-a-page, pdf)
  5. Чтение тела с потолком 2 МБ ПОСЛЕ распаковки
  6. SmartReader(uri, html) -> Title, Content(HTML), IsReadable
  7. Обход DOM по белому списку тегов -> Markdown
  v
{ title, siteName, byline?, markdown }  |  { error: { code } }
```

**Markdown как формат провода — ключевое решение.** Не «так удобнее», а так исчезает целый
класс работы: `react-markdown` без `rehype-raw` не исполняет HTML, поэтому санитайзер не нужен
ни на сервере, ни на клиенте. Шаг 7 — обход DOM по **белому списку** (`h1`–`h6`, `p`, `ul/ol/li`,
`pre/code`, `blockquote`, `table`, `img`, `a`, `strong/em`, `hr`), всё остальное отбрасывается:
`script`, `style`, `iframe`, `form` не переживают конвертацию физически, а не по чёрному списку.
Это ~150–200 строк, которые мы пишем сами и покрываем тестами.

**Инварианты рендера — три, и они держатся вместе.** Первый снимает исполнение HTML, но два
других закрывают векторы, которые в markdown остаются родными:

1. **`rehype-raw` в рендерере ридера не появляется.** Как только появится — абзац выше
   перестаёт быть правдой и понадобится санитайзер.
2. **`urlTransform` ничего не пропускает мимо `defaultUrlTransform`.** Белый список тегов не
   спасает от `[текст](javascript:…)` и `![](data:text/html;base64,…)` — это markdown, а не HTML,
   и гасит их только трансформер URL. В `MarkdownContent.tsx:173-182` его уже частично обходят
   (`ABS_PATH_RE` возвращает URL как есть, медиа-домены уходят в `proxyUrl`) — ридеру такие
   послабления запрещены.
3. **Ридер рендерит своим экземпляром, без `resolveFileMention`.** В чате резолв упоминаний
   файлов применяется к тексту, который написали мы или модель. В ридере текст пишет чужой сайт,
   и `[конфиг](appsettings.Local.json)` в чужой статье превратился бы в живую ссылку, открывающую
   локальный файл пользователя. Прав это не повышает, но фишинговый примитив внутри панели,
   созданной для показа чужого контента, — ровно то, чего там быть не должно.

Переиспользуется **формат провода и конвейер `react-markdown`**, а не компонент `MarkdownContent`
целиком: у ридера своя карта `components` (типографика колонки чтения по макету Майи) и свой
`urlTransform`.

### 1. Приватность: что уходит, что остаётся

**Уходит на сайт:**

| | Открыть в браузере | Открыть рядом |
|---|---|---|
| IP | пользователя | сервера (напрямую — раздел 2, клиент `link-reader` игнорирует egress-прокси) |
| Куки, вход, сессии | да | **никогда** |
| JS, аналитика, реклама | исполняются | **не исполняются** |
| Fingerprint браузера | да | нет |
| Referer | по политике браузера | **не шлём** |

Заголовки запроса — закрытый список: `User-Agent`, `Accept: text/html,application/xhtml+xml`,
`Accept-Encoding: gzip, deflate`, `Accept-Language` (фиксированное значение из конфига, не язык
пользователя). Никаких `Referer` и `Authorization` — ни при каких условиях, включая редиректы.

**«Никаких кук» — это настройка клиента, а не отсутствие заголовка.** `HttpClientHandler.UseCookies`
по умолчанию `true`, а именованный клиент переиспользует handler между запросами и между
пользователями. Сайт, поставивший `Set-Cookie` на редиректе (там их и ставят), склеил бы чтения
разных людей в одну свою сессию. Инварианты клиента `link-reader`, записанные явно:
`UseCookies = false`, `UseDefaultCredentials = false`, `PreAuthenticate = false`,
`AllowAutoRedirect = false`.

**Потолок размера считается после распаковки.** Раз просим `gzip`, то на хорошо сжимаемых данных
2 МБ ответа разворачиваются примерно в 2 ГБ; счётчик обязан стоять на распакованном потоке, иначе
потолок становится не защитой, а приглашением к zip-бомбе. Кодировку берём из `charset` в `Content-Type`,
при отсутствии — из `<meta charset>`; для рунета без этого получаем кракозябры вместо статьи.

**User-Agent — честный** (`ClaudeCodeServer-Reader/1.0`), а не подделка под Chrome. Обоснование:
Cloudflare и подобные щиты фингерпринтят TLS/JA3, а не строку UA, — маскировка их всё равно не
проходит, зато делает нас неотличимыми от скрапера в глазах тех, кто просто пишет лог. Цена
честности: часть сайтов ответит 403. Это отдельная причина ошибки и кнопка «Открыть в браузере»,
а не повод врать в заголовке.

**Логи.** URL передаём **POST'ом в теле**, а не `GET ?url=` — иначе адрес каждой прочитанной
страницы попадает в стандартный лог запросов ASP.NET и в любой реверс-прокси перед ним. Свои
логи пишем по формуле «домен + исход + длительность»: полный URL и извлечённый текст не логируем
никогда. В `ProjectEventLogService` чтения не пишем вовсе.

**Телеметрия — известная и принятая утечка:** исходящий спан HttpClient сохраняет
`server.address`, то есть **домены прочитанных страниц видны в SigNoz**. `url.full` и `url.query`
санитайзер дропает, так что путь и параметры не уезжают. Оставляем как есть: SigNoz
самохостится, доступен только админу, а метрики латентности и ошибок ридера операционно нужны.
Фиксируем это здесь, чтобы находка не всплыла потом как сюрприз.

**Кеш — не делаем, но по честной причине.** Приватностный довод здесь не работает: перечень
прочитанных доменов и так оседает в наших логах и в SigNoz с retention 30 дней, а кеш с TTL
в пять минут был бы самым недолговечным из трёх следов. Настоящая причина проще — он не нужен:
страницу открывают один раз, «Повторить» в макете и так подразумевает свежий запрос, а отсутствие
кеша — это ноль кода. Если когда-нибудь упрёмся в производительность: только in-memory, per-owner,
TTL ≤ 5 минут, с потолком записей — и никогда на диск.

**Картинки статьи — частичное исключение, назову прямо.** Их грузит браузер пользователя
напрямую с origin, то есть CDN сайта видит IP человека. Проксировать их через себя означает
второй эндпоинт со своей SSRF-проверкой и наш трафик за чужой хостинг; выкинуть картинки —
сломать макет. Решение для v1: рендерим напрямую с `referrerpolicy="no-referrer"` (сайт не
узнает, откуда пришли) и `loading="lazy"` (картинки ниже экрана не запрашиваются вообще).
Если Софья решит, что обещание приватности должно быть абсолютным, — `/api/reader/image` за
тем же `SsrfGuard` добавляется отдельным шагом на ~40 строк.

**Предупреждение при первом использовании — да, нужно.** Модель в голове у человека: «по ссылке
идёт мой браузер». Здесь идёт сервер, и разница невидима, но существенна — это его собственная
машина и его сеть. Форма: однократная плашка **внутри панели** при первом открытии, закрывается
и больше не показывается. Не модалка и не диалог подтверждения: факт информационный, а не
опасный, и ставить подтверждение на каждое чтение — трение без пользы. Текст пишет Софья, в нём
должно быть четыре факта: (1) страницу открывает сервер, а не браузер; (2) сайт увидит адрес
сервера; (3) куки и вход не передаются, поэтому закрытые страницы не откроются; (4) прочитанное
не сохраняется. Признак «показано» — в `localStorage`: на новом устройстве плашка появится снова,
и это скорее правильно, чем нет.

### 2. Локальные адреса

Рубежи, из которых защитой является не первый:

1. **Кнопки нет** (клиент) — схема не `http(s)`; хост `localhost`, `*.localhost`, `*.local`,
   `*.internal`, `home.arpa`; хост — IP-литерал. Это UX, а не безопасность: клику по самой
   ссылке ничего не мешает, и `localhost:5173` откроется в браузере как раньше — то есть
   правильно.
2. **Проверка самого URL** (сервер) — схема только `http`/`https`, **порт только 80/443**,
   userinfo (`http://user:pass@host/`) отклоняем. Без порта в списке ридер становится сканером
   портов интернета от нашего IP: `http://публичный-хост:6379/` проходит проверку адреса
   насквозь, шлёт HTTP-мусор в Redis и показывает ответ человеку.
3. **`SsrfGuard`** (сервер) — после резолва DNS.
4. **Рубежи 2 и 3 на каждом хопе редиректа.** Именно оба: перепроверять только адрес мало —
   `Location: file:///C:/…/appsettings.Local.json` или `gopher://` меняет схему, а не хост,
   и проверка адреса на нём просто бессмысленна. Относительный `Location` разрешаем
   относительно текущего хопа.

Что видит человек, если адрес всё же дошёл до сервера: причина `local-address`, и одной строкой
подсказка про панель «Сервисы» — в чатах этого продукта локальные адреса встречаются постоянно,
и отправить человека в правильное место дешевле, чем объяснять запрет.

**Дыры существующего `SsrfGuard`, которые надо закрыть заодно.** Он не отсекает IPv4-multicast
`224/4`, reserved `240/4`, broadcast `255.255.255.255`, benchmark `198.18/15` и NAT64-префикс
`64:ff9b::/96` (`64:ff9b::7f00:1` — это `127.0.0.1` там, где NAT64 включён). Для `save-from-url`
это академия, для ридера — нет, потому что ответ показывается человеку. Дополняем guard, а не
заводим второй: он общий, и `save-from-url` от этого только выиграет.

**Egress-прокси ломает контроль по адресу — проверено, и решение принято в обратную сторону
от первоначального плана.** `docker-compose.claude.yml:72-77` выставляет `HTTP_PROXY`/`HTTPS_PROXY`
на весь контейнер из `CLAUDE_EGRESS_PROXY`, а `HttpClient` в .NET читает эти переменные по
умолчанию (ради чего в проекте и живёт `WithoutEgressProxy()`). Там, где запрос идёт через прокси,
соединение устанавливается **с прокси**, имя хоста уезжает в `CONNECT`, и резолвит его прокси —
своей DNS-картой и из своей сети. Значит проверенный нами IP и фактически посещённый не связаны
ничем, а `SocketsHttpHandler.ConnectCallback` увидел бы адрес прокси (сам приватный) — то есть
проверка IP «в лоб» завернула бы там все легитимные запросы.

**Проверено дважды — с хоста и из контейнера, оба раза релеит.** Марк проверил с dev-хоста
(`192.168.7.65`, задача `aaba1449`): HTTP forward пропускает приватные IP локальной сети
(`192.168.7.65` → 200 OK, «Server: Kestrel»), режет только loopback; HTTPS CONNECT не фильтрует
**ничего**, включая `127.0.0.1`. Из контейнера `claude-server` (задача SSRF-обхода, 2026-08-03,
`docker exec claude-server curl -x http://192.168.7.208:2080 ...`) — тот же результат: HTTP forward
на `192.168.7.65:5000` и на `127.0.0.1:5000` (loopback уже относительно самого прокси) отдаёт
200 OK с тем же Kestrel; HTTPS CONNECT на `127.0.0.1:5000` устанавливает туннель без единой
проверки (TLS-хендшейк падает уже внутри с «wrong version number» — то есть до цели дошли, просто
там не HTTPS). Посылка «прокси и есть граница сети» не подтвердилась ни разу — рубеж прокси
не держит вообще.

**Решение: ридер идёт мимо прокси.** Третий режим («соединение с прокси, IP цели не виден») закрыт
не тем, что прокси стал фильтровать адреса, а тем, что клиент `link-reader` его больше не
использует: `ReaderHttpHandlerFactory.Create()` ставит `SocketsHttpHandler.UseProxy = false` —
не общий `WithoutEgressProxy()` из `QuietHttpLogger.cs` (тот подменяет весь handler на голый
`HttpClientHandler` и снёс бы `ConnectCallback` с SSRF-фильтром), а флаг прямо на том же
`SocketsHttpHandler`, что несёт `ConnectCallback`. Режим теперь один, а не три:

```
UseProxy = false -> соединение всегда прямое, IP проверяем сами (ConnectCallback ниже)
```

Раз соединение всегда прямое, различать «это прокси или цель» по `context.DnsEndPoint` больше не
нужно — эта ветка убрана из `ConnectAsync`, там остался только резолв + `SsrfGuard`. Цена решения
принята: в сетях без прямого выхода в интернет (egress только через `CLAUDE_EGRESS_PROXY`) ридер
работать не будет — это меньшая потеря, чем SSRF во внутреннюю сеть при включённом флаге.
Регрессия закрыта тестом `ReaderHttpHandlerFactoryTests` (`Handler_НеИспользуетСистемныйПрокси`,
`ПрямоеСоединение_ИгнорируетПеременныеОкруженияПрокси`).

Факты Марка и повторная проверка из контейнера ценны и вне ридера: любой будущий клиент, который
рассчитывает на `CLAUDE_EGRESS_PROXY` как границу сети, ошибается — прокси не фильтрует ни HTTP
forward, ни HTTPS CONNECT к приватным/loopback-адресам. Граница обеспечивается только на уровне
клиента (`WithoutEgressProxy()` / `UseProxy = false`), а не самим прокси.

**Про DNS rebinding честно.** Окно TOCTOU между `SsrfGuard` и подключением закрывается
`ConnectCallback` — теперь единственным, прямым режимом (третьего больше нет, см. выше).

**Переход внутри ридера меняет модель угроз, и раздел 3 его не покрывает.** Макет
(`link-reader-proposal.md:45`) требует, чтобы ссылка в статье грузилась в тот же ридер. С этого
момента источник URL — недоверенная страница, а не лента: аргумент «атакующему нужно заставить
человека кликнуть свою ссылку» перестаёт работать после первого же клика, дальше человек кликает
по ссылкам, свёрстанным автором страницы, а результат ему показывается — то есть слепой SSRF
становится полузрячим. Поэтому переход внутри проходит **те же рубежи 1–4** (правила раздела 3
применяются к ссылкам в статье наравне с ссылками в чате), плюс потолок глубины (5) и общий
счётчик переходов в квоте из раздела 5. Без потолка цепочка «страница → ссылка → страница»
превращает бэкенд в скрапер чужой инфраструктуры от нашего IP.

### 3. У каких ссылок появляется кнопка

**До запроса — чёрный список расширений, а не белый.** Это главное решение раздела: у
подавляющего большинства настоящих статей расширения нет вообще (`/docs/guide`, `/issues/123`),
поэтому белый список `.html` убил бы 90% полезных ссылок. Прячем кнопку у архивов (`.zip`,
`.tar`, `.gz`, `.7z`, `.rar`), установщиков (`.exe`, `.msi`, `.dmg`, `.pkg`, `.deb`, `.rpm`,
`.apk`), медиа (`.mp4`, `.mkv`, `.mp3`, `.wav`), изображений (`.png`, `.jpg`, `.gif`, `.webp`,
`.svg`, `.ico`), офисных и бинарных (`.xlsx`, `.docx`, `.pptx`, `.iso`, `.jar`, `.whl`).
Явные исключения-разрешения: `.html`, `.htm`, `.md`, `.txt`.

**После ответа — по `Content-Type`:**

| Content-Type | Поведение |
|---|---|
| `text/html`, `application/xhtml+xml` | основной путь: SmartReader → markdown |
| `text/markdown` | отдаём как markdown — **защита однослойная**, см. ниже |
| `text/plain`, прочие `text/*`, `application/json` | **экранируем** и отдаём преформатированным |
| `application/pdf` | причина `pdf` |
| всё остальное | причина `not-a-page` |

**«Как есть» для не-markdown типов — ошибка, которой легко не заметить.** Текст этих ответов
полностью подконтролен чужому серверу, и если отдать его в markdown-рендер без экранирования,
он минует белый список тегов из шага 7 — то есть весь разбор HTML обойдён одним заголовком
`Content-Type: text/plain`. Оборачивание в тройные бэктики не спасает: ответ, содержащий тройные
бэктики, из фенса выходит и дальше исполняется как разметка. Экранирование обязательно, и это
не косметика.

**Строка `text/markdown` — единственная, где нет второго слоя.** У `text/html` есть и белый список
тегов из шага 7, и инварианты рендера; здесь белого списка нет по определению — чужой markdown
идёт в рендер как markdown. Путь при этом ходовой: `.md` в явных разрешениях, то есть любая ссылка
на `raw.githubusercontent.com` попадает сюда. Значит эта клетка таблицы целиком висит на
инвариантах 1 и 2, и трогать их, «раз это всего лишь markdown», нельзя.

**PDF в v1 не читаем — решение осознанное.** Три довода: это другой конвейер (не HTML),
встроенная смотрелка браузера показывает PDF заметно лучше текстовой колонки (вёрстка, таблицы,
схемы), а единственный имеющийся у нас инструмент — `markitdown` — опциональная хостовая
утилита, на которой фича была бы нестабильной. Отдельная причина ошибки, а не общая `not-a-page`,
потому что и текст другой («PDF лучше открыть в браузере»), и случай самый частый среди
нечитаемых. Если спрос появится — `markitdown` уже в проекте, это прямой путь для v2.

**Картинки в ридер не берём.** Картинка «рядом с чатом» — другая фича (лайтбокс), и лента уже
умеет показывать изображения. Оговорка: картинка **внутри** статьи рендерится как часть статьи —
это не то же самое, что открыть URL картинки как страницу.

### 4. Страницы под входом

Разделяем четыре исхода там, где наивная реализация даёт один пустой экран:

- **401, 403 без маркеров щита** → `auth-required`.
- **200, но `IsReadable == false` И в HTML есть `<input type="password">`** либо `<form>` с
  `action`, содержащим `login|signin|auth|session` → `auth-required`. Дёшево и честно.
- **200 или 503 с маркерами бот-щита** (заголовок `cf-mitigated`, `cf-ray`, `<title>Just a
  moment`), либо 429 → `blocked-by-site`. Это не «нужен вход», и текст должен быть другим.
- **404, 410** → `not-found` с формулировкой «не найдена или закрыта». По 404 от GitHub
  отличить приватный репозиторий от опечатки **невозможно**, и врать уверенным «требуется вход»
  хуже, чем сказать обе возможности одной строкой.

### 5. Пределы

| Предел | Значение | Почему |
|---|---|---|
| Таймаут заголовков ответа | 5 с | панель уже показывает скелетон |
| Таймаут всей операции | 10 с | дальше человек всё равно уходит, а выход — один клик |
| Потолок тела (после распаковки) | 2 МБ | длинная страница доков — 100–400 КБ; выше это оболочка или дамп |
| Редиректы | 5 | |
| Глубина перехода внутри ридера | 5 | см. раздел 2 |
| `SmartReader.MaxElemsToParse` | 100 000 | обрыв разбора на гигантском DOM |
| Одновременных чтений на владельца | 2 | |
| Чтений в минуту на владельца | 30 | прецедент — `Auth:PingRateLimit` |

Потолок считаем **на лету при чтении потока** (как в `SaveFromUrl`), а не только по
`Content-Length` — его может не быть. При превышении — честная ошибка `too-large`, а не
обрезка: обрезанный HTML парсится в изуродованную статью, и это хуже отказа.

**`MaxElemsToParse` — не защита от parser bomb**, и записывать его так было бы самообманом:
это настройка Readability, она обрывает алгоритм на **уже построенном** DOM, а AngleSharp к
тому моменту успел разобрать все 2 МБ вложенных тегов и потратить на них память и CPU. Реально
здесь работают потолок тела, общий таймаут и потолок одновременных чтений.

**Квота — на владельца, а не на сессию.** Формулировка «одно чтение на сессию» не выражается
в контракте `POST /api/reader/read { url }`: идентификатора сессии в теле нет, отменять нечего,
а если его добавить — придётся проверять владение сессией, иначе чужой `sessionId` в теле
отменяет чужое чтение. Отмена предыдущего запроса при новом клике — поведение **клиентское**
(панель показывает одну страницу, значит она же и обрывает свой прошлый запрос); серверу нужна
именно квота, и десять открытых чатов не должны давать десять параллельных слотов.

### 6. Причины ошибки

Коды машинные, тексты пишет Софья. Все они рисуются одним и тем же состоянием макета, поэтому
дробность ничего не стоит на фронте, зато каждый код ведёт к своему действию человека.

| Код | Когда |
|---|---|
| `invalid-url` | не разобрали адрес; схема не http(s); порт не 80/443; userinfo в URL |
| `local-address` | приватный/loopback/link-local адрес, в том числе после редиректа |
| `dns-failed` | хост не резолвится |
| `unreachable` | соединение не установилось или оборвалось |
| `tls-invalid` | сертификат не прошёл проверку |
| `timeout` | не уложились в лимит |
| `auth-required` | 401/403 либо страница входа под 200 |
| `blocked-by-site` | бот-щит, 429 |
| `not-found` | 404, 410 |
| `server-error` | 5xx |
| `too-many-redirects` | цепочка длиннее пяти |
| `not-a-page` | Content-Type не читаемый (архив, установщик, видео, изображение) |
| `pdf` | `application/pdf` |
| `too-large` | тело превысило потолок |
| `not-readable` | скачали, но статьи не нашли (SPA без SSR, пустая оболочка) |

В ответе рядом с кодом полезно отдавать `httpStatus` — для диагностики, человеку не показывать.

**Про то, что набор кодов — оракул внутренней сети.** Различие `local-address` / `dns-failed`
действительно сообщает, существует ли внутреннее имя и указывает ли оно в приватную сеть. Схлопывать
коды я всё же не буду: единственный, кто видит эту разницу, — сам человек в своей панели.
Содержимое ридера никуда не возвращается, и держится это на отдельном инварианте, который важнее
любого схлопывания кодов:

**В v1 нет кнопки «отправить прочитанное в чат» и никакого другого пути из ридера в контекст
модели.** Текст в панели — недоверенный, и попадание его в ход означает prompt injection с
приложенным каналом вывода: тогда страница получила бы возможность и подсовывать ссылки, и читать
результат. В макете такой кнопки нет — фиксирую это как решение, а не как совпадение, чтобы она
не появилась «по аналогии с панелью Документация», где источник доверенный.

**Сцепка, которую нельзя потерять:** решение не схлопывать коды **арендовано у этого инварианта**.
Появится путь из ридера в контекст модели — кнопка «в чат», MCP-инструмент чтения для персон,
фоновая AI-сводка прочитанного (продукт такие сводки любит) — и `local-address` с `dns-failed`
схлопываются в один код тем же коммитом.

### 7. Якоря `#fragment`

**Да, в v1 — но только дешёвой версией, целиком на фронте.**

Цепочка потерь такая: у исходного HTML есть `<h2 id="installation">`, при конвертации в markdown
идентификатор исчезает (в markdown его синтаксиса нет), а фронт заново назначает заголовкам id,
слагифицируя их текст. Значит якорь сработает тогда, когда `slug(текст заголовка) == fragment`.
У GitHub, MDN и практически всех генераторов документации фрагмент **и есть** слаг заголовка
(`#installation` ← «Installation»), так что общий случай покрывается совпадением по тексту.

Стоимость: хелпер слагификации и один `useEffect` со `scrollIntoView` — около 30 строк на фронте
и **ноль на бэкенде**, полный URL у клиента и так есть. Не совпало — молча открываем статью
сверху, без ошибки и без сообщения.

Дорогую версию (протащить исходные id до рендера) **отклоняю**: она требует HTML как формата
провода, а значит санитайзера и своего рендерера вместо markdown — то есть отменяет решение,
на котором держится вся безопасность вывода. Несоразмерно ради прокрутки.

Деталь реализации: `#fragment` **отбрасывается перед HTTP-запросом** — по спецификации он
клиентский, серверу не отправляется.

## Отклонённые альтернативы

**`markitdown` по скачанному HTML** (ноль новых зависимостей). Отклонено: он не удаляет
обвязку — навигация, подвал и баннер про куки приедут в статью, а это ровно то, ради чего
режим чтения существует. Плюс python-процесс на каждый клик (0,5–2 с) и опциональность
утилиты: где её нет, фича мертва. И он дешевле выглядит, чем есть: `MarkitdownService.ConvertAsync`
принимает **путь к файлу**, то есть недоверенный HTML пришлось бы сначала писать на диск.
Остаётся естественным путём для PDF в v2.

**Node-сайдкар с `@mozilla/readability` + `jsdom`** (референсная реализация). Отклонено: ломает
простоту «MCP-сервер = один файл на чистом Node без зависимостей», добавляет `npm install` в
деплой, второй процесс под присмотр и IPC. Не стоит того, когда есть живой порт под .NET.

**Свой экстрактор без зависимостей.** Отклонено: это переписывание эвристик Readability, хуже
оригинала. Классический NIH.

**Внешний сервис (`r.jina.ai`, Mercury и подобные).** Отклонено по требованию №1: URL человека
уходит третьей стороне. Соблазнительно выглядит самым дешёвым решением — именно поэтому
называю его здесь явно, чтобы к нему не вернулись.

## Последствия и риски

1. **Часть ссылок не откроется, и это нормальное поведение, а не дефект.** Сайты за Cloudflare
   отдадут `blocked-by-site`, документация на клиентском рендеринге — `not-readable`. Макет уже
   трактует ошибку нейтрально; важно, чтобы так же её трактовали мы, когда придут репорты.
2. **JS не исполняем и headless-браузер не добавляем.** Это другой продукт: вес, эксплуатация и
   принципиально больший периметр атаки. Явно вне области.
3. **Новая зависимость** — `SmartReader` + транзитивно `AngleSharp`. Живая (релиз от 25.07.2026),
   Apache-2.0. Риск заброшенности покрыт тем, что алгоритм стабилен, а слой изоляции тонкий.
4. **ToS и robots.txt.** `robots.txt` не запрашиваем и не обязаны: это единичное чтение по явному
   клику человека, а не обход сайта. По нагрузке на чужой сервер это ровно один визит браузера.
5. **Телеметрия видит домены** (см. раздел 1) — принято сознательно.
6. **TOCTOU при резолве DNS** на прямом пути — закрывается `ConnectCallback`, см. раздел 2.
7. **Egress-прокси (`CLAUDE_EGRESS_PROXY`) не держит периметр — проверено, поэтому ридер идёт
   мимо него.** И HTTP forward, и HTTPS CONNECT релеят на приватные/loopback-адреса без
   фильтрации (проверено с хоста и из контейнера, см. раздел 2). Клиент `link-reader` работает
   с прокси отключённым (`UseProxy = false`); в сетях без прямого egress ридер не работает —
   это принятая цена.
8. **Ридер расходует наш IP-репутационный ресурс.** Каждое чтение — визит от адреса сервера;
   квоты из раздела 5 существуют в том числе поэтому, а не только против нагрузки.

## Что проверить при реализации

- ~~Поведение egress-прокси~~ — **проверено** (раздел 2): релеит без фильтрации что с хоста, что
  из контейнера. Решение принято — клиент `link-reader` работает с `UseProxy = false`.
- Клиент `link-reader` соединяется напрямую **независимо от `HTTP_PROXY`/`HTTPS_PROXY`
  в окружении** — тест на игнорирование переменных прокси
  (`ReaderHttpHandlerFactoryTests.ПрямоеСоединение_ИгнорируетПеременныеОкруженияПрокси`).
- **Схема и порт** проверяются на каждом хопе, а не только у исходного URL — тесты с цепочками
  публичный → `127.0.0.1`, публичный → `file://`, публичный → `:6379`.
- Тело больше потолка обрывается по счётчику при отсутствии `Content-Length`, и счётчик стоит
  **после распаковки** — тест с gzip-бомбой (маленький ответ, огромный распакованный).
- Клиент `link-reader` создан с `UseCookies = false`: два последовательных чтения одного хоста
  не переносят `Set-Cookie` между собой.
- Белый список тегов: `<script>`, `<style>`, `<iframe>`, `<form>`, обработчики `on*` не переживают
  конвертацию в markdown.
- `javascript:` и `data:` в ссылках и картинках статьи не доходят до DOM (инвариант 2).
- Ответ `text/plain` с markdown-разметкой и с тройными бэктиками внутри рендерится как текст,
  а не как разметка.
- Ссылка вида `[x](appsettings.Local.json)` в статье **не** становится ссылкой на файл проекта
  (инвариант 3).
- **Относительные ссылки внутри статьи становятся абсолютными.** SmartReader требует URI именно
  для этого, но проверить тестом обязательно — от этого зависит «переход внутри ридера» из макета.
- Флаг `link-reader` гейтит **эндпоинт**, а не только кнопку и панель.
- Полный URL не появляется ни в одном логе; проверить и лог запросов, и свои `ILogger`.
- Тесты платформонезависимы (CI на Linux) — сетевые походы мокать, `SsrfGuard` проверять на
  литералах.

Строку про ридер в `CLAUDE.md` добавляет задача реализации, а не эта: карта проекта описывает
то, что в коде есть.
