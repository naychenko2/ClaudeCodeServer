# Полоса контролов композера — приоритетное схлопывание

Макет: [composer-strip-priority.html](composer-strip-priority.html) — светлая и тёмная темы
(переключатель в шапке), живой стенд с ползунком ширины (320…1100 px) и чекбоксами активных
бейджей, таблица ступеней правой группы, лестница жертв для предельного набора (три бейджа),
компактная пилюля механики отдельной секцией, поповер и меню «⋯» с реальным текстом, мобильная
колонка 360.

## Диагноз, а не симптом

Полоса контролов («губа» под полем ввода, `Composer.tsx`) — три flex-блока: фиксированный левый
(режим, вложение, диктовка), `badgesRef` с пилюлями активных механик и правая группа пикеров
(модель / усилие / собеседник). Сворачивание считает `useToolbarOverflow`: сколько круглых кнопок
левого блока влезает в одну строку, остальные — в «⋯».

До этапа 1 хук был устроен так, что инвариант «ширины трёх блоков от результата не зависят» был
нарушен на практике. `badgesRef` был единственным **сжимаемым** ребёнком полосы (`flexShrink: 1`
по умолчанию), а хук читал его текущий, уже сжатый `offsetWidth` как «несжимаемого соседа» —
то есть измерял следствие, а не причину. Единственное устойчивое равновесие такой петли: кнопки
слева показаны полностью, а пилюли бейджей сжаты почти в ноль — ровно симптом, который ловила QA.
Плюс два усугубляющих дефекта: порядок пилюль в `badgesRef` был обратен приоритету (то, что должно
жертвоваться последним, физически стояло первым и обрезалось первым), а `overflow: hidden` на
самом блоке резал содержимое **справа**, не разбирая, что именно там оказалось.

## Три перестановочные правки — этап 1

Три точечные правки убирают петлю и обрезку раньше, чем строится вся лестница ступеней, — их
можно отдать в реализацию первым коммитом, независимо от остального макета:

1. **Порядок пилюль по приоритету**: `[teamPill][teamImplementBadge][loopPill]`. Пилюля механики
   идёт первой — она меняет смысл кнопки «Отправить» прямо сейчас и не должна теряться первой при
   нехватке места.
2. **`flexShrink: 0` на `badgesRef` + снятие `overflow: hidden`** с блока. Бейджи состояния
   становятся несжимаемыми наравне с левым блоком и правой группой; обрезка перестаёт быть
   побочным эффектом переполнения и превращается в управляемое состояние (см. ступени ниже).
3. **Хук переходит с измерения `offsetWidth` на номиналы-константы.** `useToolbarOverflow`
   принимает готовые числа для левого блока, бейджей и правой группы вместо чтения DOM трёх
   несжимаемых соседей — тогда пересчёт математически сходится за проход, а не гоняется за
   собственным следствием.

*(Примечание: на момент написания предложения все три правки уже перенесены в рабочее дерево
`Composer.tsx` — `STRIP_LEFT_NOMINAL` / `STRIP_PILL_NOMINAL` / `STRIP_RIGHT_NOMINAL`,
порядок `badgesRef` и снятый `overflow: hidden`. Ступени по бюджету ниже — это следующий слой
поверх уже готового этапа 1, а не альтернатива ему.)*

## Ступени по бюджету — этап 2

`STRIP_COMPACT` (640) и `STRIP_WIDE` (900) как единственные точки решения исчезают: вместо двух
порогов — лестница дискретных ступеней, выбираемых по бюджету свободного места. Единственный вход
алгоритма — ширина полосы (`stripWidth`, уже измеряется) и набор дискретных флагов, какие бейджи
сейчас активны (`teamPill` / `teamImplementBadge` / `loopPill` — булевы, не измерения). DOM внутри
алгоритма не меряется вообще: каждый номинал закреплён `maxWidth` на самом элементе, чтобы факт
не мог превысить расчёт (иначе бюджет и реальность снова разойдутся, как до этапа 1).

**Номиналы (десктоп / мобила, px, «с учётом зазора»):**

| Блок | Значение |
|---|---|
| Левый блок (режим + обвязка) | 112 / 48 |
| «⋯» (резервируется, только когда реально что-то прячет) | 38 / 46 |
| Правая группа A-wide (всё словами, собеседник до 270px) | 534 (десктоп-онли) |
| Правая группа A (всё словами, собеседник ≤140px) | 384 |
| Правая группа B (усилие иконкой, модель+собеседник словами) | 313 |
| Правая группа B2 (усилие+собеседник иконками, модель словом) | 222 |
| Правая группа C (всё иконками) | 160 / 164 |
| Пилюля механики, полная / компактная | 150 / 130 (д), 54 / 72-touch (м) |
| Бейдж КР, с чипом «Авто» / без | 180 / 160 (д), 118 / — (м) |
| Пилюля цикла «до готово» | 155 (д), 62 (м) |

**Порядок жертв подписей правой группы** — по важности для человека: усилие первым
(на дефолте «Усилие» — имя контрола, ноль информации за 100 px), собеседник вторым (кто
ведёт чат важнее уровня рассуждения), модель последней (имя модели держится до предела).
Порядок зашит последовательностью форм: B схлопывает усилие, B2 добавляет собеседника,
C снимает и модель.

**Алгоритм выбора:** перебираем форму правой группы `A-wide → A → B → B2 → C`, берём первую,
при которой сумма `padX + левый + бейджи(в полной форме) + right + зазоры` ≤ `stripWidth`.
Если и при `C` не влезает — понижаем бейджи **по рангу снизу вверх**, не трогая уже выбранную форму C:

1. Имя в пилюле механики сворачивается (полная → компактная).
2. Чип «Авто» уезжает из полосы (переключатель не теряется — см. ниже).
3. Пилюля цикла «до готово» уезжает в «⋯».
4. Бейдж «Командная реализация» уезжает в «⋯».

Пилюля механики целиком (без имени, но с иконкой и ✕) остаётся **всегда** — она не жертвуется
дальше компактной формы ни при каком дефиците: без неё непонятно, что «Отправить» сейчас работает
иначе. «⋯» резервируется в бюджете, только когда в него реально что-то попало (шаги 3–4) — на
шагах 1–2 кнопка не появляется вообще.

**Условие сходимости:** каждая ступень даёт фиксированное число — либо ступень целиком влезает в
`stripWidth`, либо мы уже на последней ступени лестницы и показываем её как есть (визуальный
оверфлоу здесь невозможен ниже мобильных номиналов, см. таблицу проверки в конце).

## Свёрнутые состояния

- **Компактная пилюля механики**: `[иконка 28×28 → настройки][✕ 26×28 → снять]`. Разделитель
  между сегментами — не волосяная линия, а постоянная заливка `C.accentMuted` на сегменте ✕:
  волосяная граница `C.accentMuted` на фоне `C.accentLight` в тёмной теме визуально исчезает
  (оба токена там близки по светлоте), а заливка держит контраст в обеих темах. На тач-целях
  (мобила) оба сегмента растут до 36×36.
- **Бейдж КР без чипа «Авто»**: бейдж остаётся как есть (иконка, стадия/волна, пульс-точка), чип
  «Авто» рядом просто не рендерится.
- **Бейдж КР строкой в «⋯»**: полноценная строка меню (иконка + название + состояние одной
  строкой в `sublabel` + тумблер «Авто»), а не обрезанный текст бейджа. Клик по строке открывает
  тот же поповер, что и клик по бейджу в развёрнутой полосе.

## Обязательная часть спеки: переключатель «Авто-волны»

Сегодня переключатель авто-волн живёт **только** в чипе «Авто» рядом с бейджем КР
(`TeamImplementBadge.tsx`, кнопка `onToggleAuto`). Как только чип схлопывается (ступень 2 лестницы
жертв), это единственное место управления пропадает вместе с ним. Поэтому схлопывание чипа
**обязано** сопровождаться появлением строки-свитча «Авто-волны» в поповере самого бейджа КР —
между описанием режима и списком задач волны, с тем же обработчиком `onToggleAuto`. Без этой
строки схлопывание отнимает у пользователя действие, а не просто убирает подпись. Та же строка,
тем же текстом и тумблером, дублируется в пункте меню «⋯», когда в меню уезжает весь бейдж
(ступень 4) — эта часть уже покрыта секцией «Уведённые в „⋯“» макета.

## Тексты

- ✕ у пилюли механики (и полной, и компактной): **«Снять механику «{имя}»»** вместо безличного
  «Отменить режим» — сейчас в коде `title="Отменить режим"` (`ModePill` trailing-кнопка в
  `Composer.tsx`), нужно заменить на подставленное короткое или полное имя механики.
- Компактная пилюля механики — контейнер получает `role="group"` и `aria-label="Механика «{имя}»"`
  (сегодня это просто `span`), чтобы скринридер объявлял пилюлю как единый контрол, а не два
  несвязанных сегмента.
- `badgeTitle` бейджа КР (`TeamImplementBadge.tsx`) при схлопнутом чипе — добавить состояние
  авто-волн в состав тултипа: `{fullText} — {TEAM_IMPLEMENT_DESCRIPTION}, авто-волны {включены|выключены}`,
  иначе состояние переключателя видно только через клик в поповер.
- Кнопка «⋯», когда в ней есть активные (не выключенные) режимы — заголовок **«Ещё · есть
  включённые режимы»** вместо нейтрального «Ещё»: подсказывает, что в меню не просто резерв
  места, а живое состояние.

## Риски

- **Номиналы врут без `maxWidth` на самих элементах.** Бюджет — это обещание, а не измерение;
  если реальная пилюля или бейдж когда-нибудь станет шире табличного номинала (новый более
  длинный `shortName` механики, более длинный текст стадии КР), расчёт хука разойдётся с фактом
  так же, как до этапа 1 — только тише, потому что `overflow: hidden` больше не спрячет обрезку
  визуально, а просто вытолкнет полосу за край. Каждый номинал из таблицы обязан быть закреплён
  `maxWidth` на соответствующем элементе.
- **`flexShrink: 1` у правой группы вернёт старую петлю.** Правая группа обязана остаться
  несжимаемой (`flexShrink: 0`) в любой из своих форм A-wide/A/B/B2/C — иначе браузер сам начнёт
  ужимать пикеры до огрызков вида «Мод…» без ведома алгоритма ступеней.
- **Первый кадр при `stripWidth === 0`.** До первого замера ResizeObserver ширина полосы
  неизвестна; сегодня это трактуется как «полоса просторная». На узких экранах при `isMobile`
  правильнее сразу считать мобильную ступень C, а не ждать первого замера и мигать
  «слова → иконки» на глазах пользователя. Правило: `stripWidth === 0 ? (isMobile ? 'C' : 'B') : пересчёт по номиналам`.
- **Клапан дублей в «⋯» должен включаться по факту компактности пилюли, а не по
  `badgesOverflowed`.** Сегодняшний `badgesOverflowed` (сравнение `scrollWidth > clientWidth`)
  был нужен, пока обрезка шла через `overflow: hidden`; после его снятия `scrollWidth` и
  `clientWidth` у `badgesRef` совпадают почти всегда, и клапан молча перестаёт срабатывать —
  дубли пилюли цикла/КР в меню просто не появятся ни при какой ширине. Условие дублирования
  нужно переключить на прямой факт «эта пилюля сейчас в свёрнутой/меню-форме» (то, что уже
  вычисляет сам алгоритм ступеней), а не на измерение геометрии блока задним числом.

## Проверка на приоритетных ширинах

Ширина полосы — не ширина экрана: композер живёт в колонке чтения `CHAT_MAX_W = 950px`, на
планшетной раскладке (`MOBILE_MAX = 600` … `TABLET_MAX = 1199`) колонка уже экрана целиком.
Значения ниже — CSS-ширина устройства из `docs/design/target-devices.md` минус ориентировочная
служебная хрома (навигация/отступы); точную цифру на конкретной сборке подтверждает QA на живом
макете, здесь — ориентир для ревью алгоритма, а не гарантия пикселя.

| Устройство | CSS экрана | Полоса (≈) | Режим | Ступень (все 3 бейджа активны) |
|---|---|---|---|---|
| Galaxy Z Flip 8 (разворот) | 360 | ~336 | мобильный (`isMobile`) | предел: компактная пилюля + «⋯» (цикл и КР в меню) — третий телефонный кадр макета |
| POCO X7 Pro | ~407 | ~380 | мобильный | компактная пилюля + бейдж КР без «Авто», цикл ещё в полосе — второй телефонный кадр |
| Galaxy S25 Ultra | ~480 | ~450 | мобильный | как выше, ближе к «Авто» ещё виден — зависит от точной ширины, требует замера |
| Galaxy Z Fold 8 (разворот) | ~816 (расчёт, не замер) | ~700–750 | планшетный (десктоп-нюансы) | **зона неопределённости старой схемы**: ниже `STRIP_WIDE=900`, выше `STRIP_COMPACT=640` — старый бинарный порог здесь не решает ничего осмысленного, новая лестница даёт форму B или A по факту бейджей |
| Galaxy Z Fold 8 Ultra | ~835 (расчёт) | ~720–770 | планшетный | та же зона, что и Fold 8 |
| Galaxy Z TriFold (разворот) | ~720 | ~650–700 | планшетный | та же зона |
| MatePad 11.5 S (портрет) | 736 (замер) | ~680–720 | планшетный | та же зона |
| MatePad 11.5 S (ландшафт) | 1120 (замер) | до 950 (упирается в `CHAT_MAX_W`) | планшетный/десктопный | форма A или A-wide — места достаточно даже при всех бейджах |

Главный вывод таблицы: **бинарные пороги 640 и 900 не совпадают ни с одной реальной границей
приоритетных устройств** — все планшеты и складные в развороте (Fold 8, Fold 8 Ultra, TriFold,
MatePad портрет) попадают ровно в промежуток между ними, где старая схема отдавала либо
преждевременно урезанный, либо неоправданно широкий вид. При активных бейджах (КР + пилюля
механики + цикл — реалистичный случай во время командной волны) дефицит места начинается уже
около 900px, то есть у части этих устройств полоса без ступенчатого алгоритма реально не влезала
бы в одну строку. Именно эта зона — практическое обоснование лестницы, а не порог 640/900.

## Дизайн-система

Только токены `design.ts` / `theme.css` (`C.*`, `FS.*`, `R.*`, `SHADOW.*`) — макет и код номиналов
уже сверены построчно с `theme.css` в обеих темах. Компактная пилюля — вариант существующего
`ModePill`, не новый компонент; бейдж и его поповер — доработка существующего
`TeamImplementBadge.tsx`, `ToolbarOverflowMenu` — доработка существующего меню «⋯» (пункты уже
умеют иконку + подпись + `sublabel` + тумблер, нужна только строка-свитч и запись бейджа КР).

## Что макет не решает

Ширина `STRIP_LEFT_NOMINAL` при появлении в левом блоке новой несворачиваемой кнопки (кроме
режима/вложения/диктовки) в макете не пересчитана — это отдельная правка номинала, не новая
механика. Поведение при одновременной активности **более** трёх пилюль (сегодня их ровно три:
механика, КР, цикл) не рассматривалось — четвёртая механика потребует либо своего ранга в
лестнице жертв, либо явного решения продукта, что несовместимо с одновременной активностью.
