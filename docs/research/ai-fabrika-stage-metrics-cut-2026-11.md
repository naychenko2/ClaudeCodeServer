# Метрики этапа «исполнитель / ревью / человек» — мини-разрез (D0)

Мини-разрез к эпику «Процессы фичи» (`a149e308`), задача `044606ee`, доработка по вердикту R-D0 — задача `0eb41632`. Основание — строка D1 §8 разреза `docs/research/ai-fabrika-workflow-cut-2026-11.md`. Решение Андрея: на экране этапа время, ходы, токены и ожидание человека показываются **раздельно** по исполнителю, ревью и человеку.

## 0. Главное до деталей

1. **Новой модели хранения не нужно. Предпосылка §8 D1 «`AwaitingHumanSince` только на эпике» неверна** (отмечаю явно, это моя же формулировка):
   - пару `TaskItem.AwaitingHumanSince/Reason` пишет `TaskManager.SetAwaitingHuman` на **любую** задачу: через MCP `tasks_update(awaitingHuman)` и через `report_up(blocker)` по задаче чата;
   - каждое изменение пары уже ложится в журнал фичи событиями `waiting` / `waiting_cleared` с `taskId` (`TaskManager.WriteJournalTransitions`);
   - устарел только комментарий «у эпика» в `TaskItem.cs:181`.
2. **Время исполнителя и ревью берём из того же журнала**: записи `turn` с `taskId`. **Токены — из `SpendRecord.TaskId`.** У задачи ревью свой чат-исполнитель (`LinkedSessionId`), а `SpendMapping` пишет `TaskId = session.TaskId`. Поэтому расход ревью уже лежит под id задачи ревью. **Разметка «ревью/исполнитель» в записи расхода не нужна:** роль выводится из задачи (`Role`, `ReviewOf`). Писать её в запись значило бы завести вторую точку правды.
3. **Правка данных одна** — аддитивное поле `Initiator` в проекции `FeatureSpendRecord` (шов Core). Без него не посчитать реплики человека. Новых сторов, событий шины и писателей нет.
4. **Метрики считает чистая функция проектора** `FeatureStageMetrics.Build`, по образцу `FeatureStageIntervals`. Новой арифметики времени она не вводит, три её правила берутся из существующего кода и выносятся в общие функции:
   - ожидание человека — общая с `FeatureTimeline` и `FeatureTypical` функция эпизодов (И4);
   - минуты работы — правило интервала стадии `FeatureStageIntervals` со склейкой `GlueGap` (И6);
   - упавший ход — один предикат по реальному словарю `outcome` (И7).

## 1. Определения

**Задача этапа `T`** — задача фичи со `Stage` (B2). У фич до B2 — любая задача фичи, кроме `feature`/`consult` (§6).

**Ревью этапа `R(T)`** — задачи с `Role = review`, у которых `T.Id ∈ ReviewOf`. Других ролей в `R(T)` нет:
- `qa`/`final` в `R(T)` **не входят никогда**, ни с пустым `ReviewOf`, ни с непустым. Это самостоятельные этапы со своим экраном и своими метриками: они проверяют фичу или набор задач целиком, а не один этап;
- `rework` — это новая задача и, значит, свой этап (B2: слепок берёт текущую версию). Склейку «шаг + доработки» по `StepRef` (`run.StepChains`) D1b не делает: это свод по цепочке, а не метрика этапа (§7).

**Окно этапа:** `[T.CreatedAt, max(T.CompletedAt, CompletedAt задач R(T)) ?? now]`. `live = true`, пока `T` или любая задача `R(T)` не в `Done`.

**Ход** — один завершённый ход чата, привязанного к задаче: одна запись журнала `turn` = одно событие `TurnCompleted` для `TurnSeq` сессии. Продюсер `TurnCompleted` один (`FallbackLlmSessionAdapter`), он оборачивает и CLI, и локальный движок, поэтому ходы локальной модели считаются наравне с облачными. Субагенты внутри хода ходом не считаются: их время уже внутри интервала хода, а токены — в записи расхода хода.

| Доля | Время (минуты, wall-clock) | Ходы | Токены / стоимость |
|---|---|---|---|
| **Исполнитель** | интервалы работы по правилу интервала стадии (И6) для группы `{T}`, **минус** ожидание человека по `T` и интервалы очереди фич | `turns` — все записи `turn` с `taskId = T`; `errorTurns` — из них упавшие по предикату И7 | записи расхода с `TaskId = T` |
| **Ревью** | то же для группы `R(T)` (одно объединение по всем задачам ревью, минус их ожидание и очередь) | то же по `taskId ∈ R(T)` | записи с `TaskId ∈ R(T)` |
| **Человек** | эпизоды ожидания человека (И4) по `T` и `R(T)` в пределах окна, объединённые, **минус** интервалы очереди фич (`held(queue)..hold_cleared`, прецедент R-Q3B-4) | `waits` — число эпизодов `waiting`, начавшихся в окне; `replies` — ходы, **начатые** человеком (`Initiator = human`, защёлка `TurnFromHuman` в `SpendMapping`), в чатах `T` и `R(T)`, по расходу | **нет**: реплика человека тратит токены агента, эти токены входят в долю исполнителя или ревью — по задаче чата |

**Ходы и минуты — разные признаки, и это намеренно.** В `turns`/`errorTurns` идёт любая запись `turn`. В минуты — только записи с непустыми `StartedAt`/`EndedAt`, как в `FeatureStageIntervals.cs:67`. Ход без паспорта (паспорт не собран) в счётчике есть, а минут не добавляет. Отбрасывать его из счётчика нельзя: упавший до сборки паспорта ход — ровно тот случай, ради которого есть `errorTurns`.

`replies` — не «сообщения человека»: несколько сообщений, поданных в один ход, дают одну реплику. При выключенном Spend `replies` = `null` (§3).

### Три величины «работы» — и какая из них здесь

В проекте две величины «минуты работы»; доля этапа их не дублирует, а берёт одну из них с другим ключом группировки.

| Величина | Где | Состав | Паузы между ходами |
|---|---|---|---|
| интервал стадии | `FeatureStageIntervals.cs:96-129` | закрытые ходы + живой хвост, склейка при зазоре ≤ `GlueGap` (2 мин), группа — **стадия** | ≤ 2 мин — работа, длиннее — разрыв |
| work таймлайна | `FeatureTimeline.cs:463-486` (`WorkWallMinutes`, `AgentsSumMinutes`) | ходы ∪ `started`-периоды `[started, stopped \| Done \| now]` | любые — работа, пока исполнитель запущен |
| **доля исполнителя / ревью этапа** | новое, `FeatureStageMetrics` | **правило интервала стадии без изменений**, группа — `{T}` или `R(T)`; затем вычет ожидания и очереди | как у интервала стадии |

**Выбор: база — интервал стадии.** Экран этапа стоит рядом с «Хронологией», где полосы этапов рисует `FeatureStageIntervals`. Если доля посчитана по другому правилу, на соседних экранах будет два ответа на вопрос «сколько работали». У work таймлайна база другая: «пока исполнитель запущен». Паузы длиннее 2 мин он тоже считает работой, а для этапа они простой (`idleMinutes`). Это расхождение с таймлайном **намеренное**, оно фиксируется в И6 и в подсказке к числу (D1d).

**Чего в долях нет:**
- `device_wait` (ожидание устройства локального проекта) — это не человек. В `FeatureTimeline` он сложен с ожиданием, но в блоке этапа его нет; если понадобится — отдельной строкой позже;
- ожидание **на эпике** (мерж, решение по фиче) — это ожидание фичи, его показывает шапка, к этапу оно не относится;
- зазор «шаг сдан → ревью запущено» и паузы между ходами длиннее `GlueGap` — это `idleMinutes`, ничья доля.

**Перекрытия.** Приоритет тот же, что в `FeatureTimeline` (major 1): ожидание сильнее работы, работа внутри ожидания в минуты не идёт; очередь сильнее и того и другого. Доли **не обязаны** давать окно в сумме: ревью может идти параллельно доработке. Поэтому `idleMinutes = elapsed − |объединение трёх долей|`, а не остаток от суммы.

**Общее ревью** (`ReviewOf` из N > 1 задач) **не делим**: показываем целиком с `sharedWith: N`. Прецедент деления есть (`SharedSpendSplitter` делит общий чат поровну), но на экране одного этапа поделённые минуты одного ревью — выдумка. Итог фичи от этого не меняется: на уровне фичи ревью считается один раз.

**Округление** — `FeatureTimeMath.CeilMinutes` от суммарного `TimeSpan` объединённых интервалов доли (`MergeIntervals`), одно округление на долю. Своей арифметики округления не заводим.

## 2. Где хранится ожидание человека по этапу

**Решение: поле на задаче плюс журнал — оба уже есть.** Поле `AwaitingHumanSince/Reason` даёт «ждёт сейчас», журнал `waiting/waiting_cleared` — историю и минуты. Пишет одна пара методов `TaskManager` под `_awaitLock`.

| Путь | Действие | Точка в коде | `task_changed` |
|---|---|---|---|
| MCP `tasks_update(awaitingHuman: {ask})` | set | `TasksToolset.cs:675` → `SetAwaitingHuman` | да (`TasksToolset.cs:680`) |
| MCP `tasks_update(awaitingHuman: null)` | clear | `TasksToolset.cs:678` → `ClearAwaitingHuman(id)` | да |
| `chats_report_up(blocker: true)` из чата задачи | set | `SessionMessagingService.TrySetAwaitingHumanForBlocker` (`:237`) | да |
| человек написал в чат задачи | clear, если ожидание не новее ответа | `AwaitingHumanAnswerSubscriber.HandleHumanMessage` → `ClearAwaitingHuman(id, answeredAt)` | да |
| перезапуск исполнителя | clear | `TaskManager.MarkClaudeStarted` → `ClearAwaitingHuman(id)` (`TaskManager.cs:1629`) | у вызывающего — **проверить в D1b** |
| переход задачи в `Done` | clear | `TaskManager.Update` → `ClearAwaitingHuman(id)` (`TaskManager.cs:1243`) | у вызывающего (REST PUT, MCP `tasks_update`/`tasks_complete`) |
| поля `AwaitingHumanSince/Reason` в DTO `Create`/`Update` | прямая запись мимо `_awaitLock` | `TaskManager.cs:442`, `:1231` | — |

Последняя строка — не боевой путь: поля DTO помечены `[JsonIgnore]`, REST и MCP их не принимают, в продовом коде вызовов нет (Grep). Но журнал они пишут, а лок обходят. **В D1b — сторож:** тест, что тела REST `POST/PUT /api/tasks` с `awaitingHumanSince` поле не меняют. Убирать поля из DTO — вне шага.

**Что делает фронт при `task_changed`:**
- полезная нагрузка — задача целиком. Если `taskId` равен `T` или входит в `R(T)`, экран этапа перезапрашивает ручку этапа: числа считает только сервер, фронт их не досчитывает;
- живой счётчик «ждёт вас сейчас» тикает на клиенте от `waitingNow.since`. Это не арифметика долей, а показ одной метки (прецедент — шапка фичи).

Нового события шины и нового вида журнала нет.

## 3. Источник токенов и стоимости

`ISpendFeatureReader.Slice(ownerId = epic.OwnerId, taskIds = {T} ∪ R(T), sessionIds = [], excludeSessionIds = [], from = null)`, затем записи раскладываются по `TaskId`. Этого **достаточно**, разметка в `SpendRecord` не нужна (§0 п.2).

Правила — те же, что у `FeatureSpend`, через тот же признак:
- `costUsd` — только записи с надёжной ценой;
- `UnreliableCost` → `costPartial` и `hiddenCostModels` (единая точка `SpendCostReliability`);
- дневные агрегаты (`IsDaily`, старше `Spend:DetailDays`) несут `TaskId` и идут в токены как есть;
- общий оркестраторский чат (`Б9c`) этапу не атрибутируется: у него нет `TaskId` задачи этапа, и он остаётся в итоге фичи.

**Единственная правка:** в `FeatureSpendRecord` добавляется `Initiator` (аддитивно), его заполняет `SpendFeatureReader` из `SpendRecord.Initiator`. У дневных агрегатов инициатора нет (`DailySpendRow` его не сворачивает), поэтому при `IsDaily` в окне `replies` = `null`, а не заниженное число.

**Проверить в D1b тестом:** запуск исполнителя (`tasks_run_executor`, автозапуск, продолжение после паузы) пишет ход с `Initiator = agent`. Иначе каждый запуск посчитается репликой человека. Если запуск окажется `human`, это дефект разметки инициатора, а не повод вычитать первый ход в метриках.

Подсистема Spend выключена (шов `null`) → `tokens`/`costUsd`/`replies` = `null`, «≈», без 500. Прецедент — решение Андрея 20.10.

## 5. Инварианты и пути

**И1. Метрики этапа только читают.** Функция чистая: `(T, R(T), journal, spendRecords, now) → StageMetrics`. Интервалы очереди она строит сама из журнала той же общей функцией, что таймлайн (И4). Ни `TaskManager`, ни журнала как стора, ни стора расхода у неё нет — гарантия сигнатурой, как у `FeatureStageIntervals`.

**И2. Ожидание этапа пишет только пара `SetAwaitingHuman`/`ClearAwaitingHuman`, и каждое изменение попадает в журнал.** Пути — таблица §2. Что закрывает D1b:

| Путь | Закрытие в D1b |
|---|---|
| MCP set/clear, `report_up`, ответ человека | существующие тесты FS-E1/E2/E3b; проверить, что каждый ассертит `waiting`/`waiting_cleared` в журнале; недостающее — дописать |
| `MarkClaudeStarted`, переход в `Done` | тест «был `waiting` → перезапуск/закрытие → в журнале `waiting_cleared`»; проверить, что вызывающий шлёт `task_changed` |
| DTO `Create`/`Update` | сторож REST «поле не принимается» (§2) |

**И3. Ручка этапа не отдаёт чужого.** `T` ищется только внутри `run` фичи, полученного тем же гейтом, что `GET features/{featureId}` (`ProjectFull`, owner/`IProjectAccess`, единый 404). `R(T)` ⊂ `run.Reviews`, срез расхода — с `ownerId = epic.OwnerId`.

| Путь чтения метрик | Закрытие |
|---|---|
| ручка экрана этапа D1a (REST, под `[Authorize]`) | гейт фичи + `T ∈ run` (иначе тот же 404) |
| MCP | инструмента нет и в этом шаге не заводим |
| SignalR | `task_changed` несёт задачу, метрик в нём нет |

Тест: `taskId` задачи другой фичи того же владельца → 404. Задача чужого владельца → 404.

**И4. Эпизод ожидания и вычет очереди — в одной точке.** Сейчас пары «начало ожидания → его конец» строятся в **трёх** местах, и по составу они расходятся:

| Потребитель | Где | Виды | Окно / обрезка | Очередь | Пара начало→конец |
|---|---|---|---|---|---|
| таймлайн | `FeatureTimeline.cs:412-452` | `waiting` + `device_wait` | начало в `[from, to)`, конец режется по `to` | вычитается (`NetSpan`, `:427`) | первый `*_cleared` с `At ≥ начала` |
| «типичные» эпизоды | `FeatureTypical.cs:250-275` | только `waiting` | начало в `[from, to)`, конец режется по `to` | **не** вычитается | первый `waiting_cleared` с `At > начала` |
| активность фичи | `FeatureActivity.cs:100-113` | `waiting` + `device_wait` (+ `started`) | без окна, только `clipFrom` | не вычитается | первый `*_cleared` с `At ≥ начала` |

**Решение.**
1. В `FeatureTimeMath` выносятся две функции. `WaitingEpisodes(entries, startKind, clearKind, from, to, now)` возвращает эпизоды `(TaskId, Start, End)` по правилу таймлайна: начало в `[from, to)`, конец — первый `clearKind` той же задачи с `At ≥ Start`, иначе `now`, затем обрезка по `to`. `QueueIntervals(entries, from, to, now)` переезжает из `FeatureTimeline.cs:637` без изменений, `NetSpan` — вместе с ней.
2. **Ожидание человека во всём проекте = эпизоды `waiting` минус очередь.** Отличие таймлайна — только добавка эпизодов `device_wait`: это его заявленный состав «ожидание любое», а не вторая арифметика.
3. На общие функции в D1b переходят **три** потребителя минут ожидания:
   - `FeatureTimeline` — без смены поведения: `FeatureTimelineJournalTests` и `FeatureQueueTraceTests` зелёные без правок;
   - `FeatureStageMetrics` — фильтрует эпизоды по `{T} ∪ R(T)` и окну этапа;
   - `FeatureTypical.HumanWaitingMinutes`.
4. У `FeatureTypical` поведение **меняется в двух местах**, оба раза в сторону правила таймлайна:
   - вычитается очередь. Оговорка `FeatureTypical.cs:243-249` говорит, что единственная намеренная разница с таймлайном — `device_wait`; вычет очереди появился позже (R-Q3B-4), и его отсутствие здесь — пропуск, а не решение;
   - `waiting_cleared` в ту же миллисекунду, что и `waiting`, закрывает эпизод (было `>`, стало `≥`). Раньше такой эпизод тянулся до следующего `waiting_cleared` или до `to`.

   Оговорку `:243-249` D1b переписывает: «разница с таймлайном — только `device_wait`». Существующие тесты `FeatureTypical` с очередью или с `cleared` в момент начала, если такие есть, правятся с пометкой в коммите.
5. `FeatureActivity` **не переходит, и это осознанно.** Он отвечает на вопрос «когда фича жила» (интервалы активности без окна, под признак простоя), а не «сколько минут ждали». Окна `[from, to)` и вычета очереди у него нет по смыслу. Пара «начало → конец» у него та же (`≥`), минут ожидания он не отдаёт. D1b оставляет у его цикла комментарий: «пары — как `FeatureTimeMath.WaitingEpisodes`; минуты ожидания отсюда не считать».

**Сторож И4** — в `FeatureStageMetricsTests`, в тексте теста оговорки перечислены явно. Фикстура: фича из одного этапа `T` без ревью. В ней:
- два эпизода `waiting` на `T`, один из них частично внутри `held(queue)`;
- нет `device_wait` — иначе таймлайн шире доли «человек» по составу;
- нет ожидания на эпике — иначе таймлайн шире по задачам;
- нет упавших ходов внутри ожидания — в таймлайне вид `error` сильнее `waiting` и откусывает его минуты;
- все границы на целых минутах — у таймлайна округление методом наибольшего остатка, у доли — `CeilMinutes`.

Ассерты:
- `human.minutes == timeline.totals.waitingMinutes`;
- `human.minutes ==` минуты ожидания `FeatureTypical` той же фичи.

Вторая проверка — без оговорок о составе: после шага у обеих одна функция и один вычет очереди. Регрессионный тест на `FeatureTypical` — эпизод с очередью даёт net-минуты.

**И5. Роль расхода определяется задачей, а не записью.** В `SpendRecord` новых полей нет; разметка «ревью/исполнитель» = `TaskId → Role/ReviewOf`.

**И6. Минуты работы этапа — правило интервала стадии, одна функция склейки.** Склейка `FeatureStageIntervals.cs:96-129` (зазор ≤ `GlueGap`) и правило живого хвоста `:79-92` выносятся в `internal` функцию того же класса. Ключ группы — параметр: стадия для «Хронологии», `{T}` или `R(T)` для этапа. `FeatureStageMetrics` зовёт её и вычитает из результата ожидание человека и очередь. Своей склейки, своего `GlueGap` и своего хвоста у метрик этапа нет. С work таймлайна (`WorkWallMinutes`/`AgentsSumMinutes`) доля **не сравнивается и не обязана совпадать** (§1, таблица трёх величин).

Сторож И6: этап из одной задачи `T`, единственной в своей стадии, без ожиданий и очереди, границы на целых минутах, ходы с зазорами 1 мин и 5 мин. Ассерт: `executor.minutes ==` сумма `StageInterval.Minutes` этой стадии. Зазор 1 мин склеен в обоих, зазор 5 мин — разрыв в обоих и ушёл в `idleMinutes`.

**И7. Упавший ход — один предикат по реальному словарю.** Значения `error` в проде нет. Словарь `outcome` хода (журнал берёт `passport?.Outcome ?? e.Outcome`, `FeatureTurnJournalSubscriber.cs:127`):
- паспорт (`TurnRunPassport.cs:11-12`): `success`, `failed`, `egress_down`, `interrupted`, `cancelled`, `crashed`;
- фолбэк локального движка (`FallbackLlmSessionAdapter.cs:614, 753, 833, 1008`): `local_down`, `local_busy`, `local_file_missing`, `window_1m_unavailable`.

Предикат `FeatureTimeMath.IsFailedTurn(outcome)`: `outcome` не `null` и не `success`. Перечень на сегодня — девять значений выше, кроме `success`.

Почему отрицание, а не список. Новый исход отказа (а словарь растёт: `local_*` добавлялись по одному) попадает в `errorTurns` сам, без правки предиката. При списке он молча считался бы успехом — тот самый промах, что сейчас с `error`. `interrupted`/`cancelled` входят: для этапа ход не дал результата, чем бы ни был прерван. Разделить «упал» и «остановлен» — отдельное поле позже, если D1d попросит. `outcome = null` (нет ни паспорта, ни исхода в событии) — не ошибка: ход в `turns` есть, в `errorTurns` нет.

На предикат переходят:
- `FeatureStageMetrics` (`errorTurns`);
- `FeatureStageIntervals.BadOutcomes` (`:23`) — в D1b, иначе `LastOutcome` интервала стадии и `errorTurns` этапа разойдутся. Поведение меняется: `LastOutcome` начинает показывать `failed`/`crashed`/`local_*`, которые сейчас теряются. Это исправление, а не регрессия;
- `FeatureTimeline.cs:470` (`e.Outcome == "error"`, не срабатывает никогда) — в карточке дефекта `a6b5a2d0`, на тот же предикат. До его закрытия число ошибок таймлайна (0) и `errorTurns` этапа расходятся, расхождение известное.
