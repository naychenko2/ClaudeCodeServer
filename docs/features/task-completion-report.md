# Доклад о завершении задачи в чате

**Статус:** в работе (ветка `feat/task-completion-report`)
**Продукт:** Софья · **backend:** Денис · **frontend:** Кира · **ревью:** Глеб
**Связанные документы:** [ADR-001](../adr/ADR-001-task-and-chat-origin.md) (модель Z: L0-тост,
гостевая реплика, авто-ход постановщика)

## Проблема

Когда исполнитель закрывает делегированную задачу, `TaskExecutionService.TryDeliverCompletionAsync`
кладёт в чат постановщика **два сообщения об одном факте**:

1. **ШАГ 1** — гостевая реплика с маркером `↩ Отчёт по делегированной задаче: …`
   (фронт рендерит её бейджем `DelegationReportBadge`) и обрезанным до 400 символов итогом;
2. **ШАГ 2** — платный авто-ход постановщика, в котором персона **пересказывает тот же итог**.

Ни в одном из них нет пути к результату: хвост обрезки — `… итог целиком — в задаче
(tasks_get по id 7f3a…)`, то есть инструкция для модели, а не ссылка для человека. Чтобы
увидеть результат, человек уходит из чата на доску задач и ищет карточку глазами.

Тост в шторке уведомлений (L0) при этом работает правильно — у него есть `Url`.

## Решение (вариант 2 — «карточка как единственный носитель факта»)

**Карточка отвечает на вопрос «что сделано», реакция постановщика — только на «что делаем
дальше». Если ответа на второй вопрос нет, второго сообщения нет.**

1. **Тост L0 остаётся без изменений** — он единственный работает, когда чат закрыт.
2. **Карточка доклада получает действия:** «Открыть задачу» (панель задачи справа, на мобиле —
   модалка), «Чат исполнителя», счётчик приложенных файлов.
3. **Реакция постановщика — только по делу.** Промпт авто-хода перестаёт просить
   «отреагировать на отчёт» и просит **принять решение**: продолжаем, ставим новую задачу или
   работа закрыта. Решения нет — постановщик молчит, реплики в ленте не появляется.

### Макет карточки

```
+----------------------------------------------------+
| [ава] Денис · Backend            ✓ Задача выполнена |
|                                                     |
|  Пагинация истории чата                             |
|  ------------------------------------------------   |
|  Добавил постраничную загрузку, тесты зелёные.      |
|  Итог показан не полностью — открыть задачу         |
|                                                     |
|  [ Открыть задачу ]  [ Чат исполнителя ]  3 файла   |
+----------------------------------------------------+
```

## Требования

### Backend

- **B1. Карточке нужен `taskId`.** Сейчас связь с задачей живёт только в тексте реплики
  (`DelegationReportMarker` + заголовок). Прокинуть идентификатор задачи структурным полем
  сообщения, а не расширением строки-маркера: парсинг id из текста ломается на любом
  редактировании формата и попадает в контекст модели мусором. Способ (новое поле
  `StoredTextMessage` / отдельный тип сообщения) — на усмотрение backend + архитектор.
- **B2. Хвост обрезки — человеческий.** `DelegationReportBody`: вместо
  `… итог целиком — в задаче (tasks_get по id {id})` — `Итог показан не полностью — открыть задачу`.
  Лимит 400 символов сохраняется: тело реплики оплачивается на каждом следующем ходу чата.
- **B3. Пустой итог.** `(итог не указан)` → `Исполнитель не оставил описания результата`.
- **B4. Реакция только по делу.** `BuildDelegatorReactionPrompt`: постановщик отвечает, только
  если у него есть следующий шаг. Нечего сказать — ответ ровно `<no-reply/>`, и такой ход
  **не пишет реплику в ленту** (сообщение гасится, ход завершается штатно). Маркер и место
  его гашения согласовать с архитектором — важно, чтобы «пустой» ответ не оставлял ни
  призрачной реплики, ни следа «персона промолчала» в истории.
- **B5. Гашение дублирующего `chats_report_up`.** Если по задаче уже доставлен доклад
  (`CompletionDelivered`), финальный `report_up` из чата исполнителя не создаёт второе
  сообщение в родительском чате.

### Frontend

- **F1. Карточка вместо бейджа.** `DelegationReportBadge` → полноценная карточка доклада:
  заголовок-статус, название задачи, итог, ряд действий. Контролы — только из
  `components/ui/`, цвета — токены `C.*`.
- **F2. «Открыть задачу»** открывает существующую `TaskDetailsPane` в правой зоне
  (`DesktopWorkspace`), на мобиле — `TaskDetailsModal`. Новых экранов не заводим.
- **F3. «Чат исполнителя»** ведёт в чат-исполнитель задачи (`LinkedSessionId`).
- **F4. Файлы** — счётчик `linkedFiles` задачи; клик открывает задачу на её карточке.
  Файлов нет — элемент не рисуется.
- **F5. Обратная совместимость.** Старые реплики без `taskId` (уже лежащие в историях)
  рендерятся как сегодня — бейджем без действий.

## Тексты интерфейса

| Место | Текст |
|---|---|
| Заголовок карточки (успех) | Задача выполнена |
| Заголовок карточки (провал) | Задача не выполнена |
| Действие | Открыть задачу |
| Действие | Чат исполнителя |
| Хвост обрезанного итога | Итог показан не полностью — открыть задачу |
| Пустой итог | Исполнитель не оставил описания результата |

**«Что нового»:** Отчёт о выполненной задаче стал одним сообщением — с кнопкой «Открыть
задачу»: результат и файлы видно прямо из чата, не переключаясь на доску.

## Фич-флаг

`task-report-card` (`FeatureFlagCatalog.All` + `FLAGS` в `lib/featureFlags.ts`), дефолт
выключен. Под флагом — **и** карточка, **и** новый промпт реакции: смысл изменения в том, что
эти две части работают вместе.

**Критерии снятия:**
- 10+ делегированных задач подряд без второго сообщения об одном факте в ленте;
- волна «Командной реализации» отработала на новом промпте реакции — координатор по-прежнему
  принимает решения после докладов исполнителей и не зависает.

## Известные ограничения

Вскрылись на ревью, приняты осознанно — чинить не будем, но знать надо.

- **Переключение флага задним числом.** `delegationTaskId` пишется независимо от флага (чтобы
  включение подняло карточку и на докладах, доставленных раньше), а тексты выбираются на момент
  доставки. Поэтому доклады «периода выключенного флага» поднимутся карточкой со старым хвостом
  `… итог целиком — в задаче (tasks_get по id …)`, а при обратном выключении новые доклады
  отрендерятся бейджем без кнопки. Ожидаемое поведение, не баг.
- **Цитата маркера в код-блоке.** Если модель процитирует `<no-reply/>` внутри ```-блока,
  живая лента и история могут разойтись (в ленте пустой блок, после перезагрузки — с тегом
  внутри). Механика унаследована от `<team:talk/>`; чинить — лезть в сжатие буфера ради
  редчайшего сценария.
- **`<no-reply/>` стрижётся во всех чатах**, а не только под флагом — как и остальные
  протокольные маркеры. Разговор про HTML-теги может недосчитаться такого тега в ответе.
- **`TaskManager.GetBySession`** выбирает задачу по чату через `FirstOrDefault`: если чат за
  свою жизнь был исполнителем двух задач одного владельца, гейт ключуется на произвольной.
  Безопасной дешёвой правки нет — смена выбора меняет семантику для остальных вызывающих.

## Что уточнилось при реализации

- **Доклад пишется двумя типами сообщений** — исполнитель-персона едет
  `StoredTextMessage`/`GuestTextMessage`, исполнитель без персоны — `StoredUserMessage`/
  `UserMessageMessage`. `delegationTaskId` проставлен во все четыре ветки: иначе карточка
  появилась бы у половины докладов.
- **F2 реализован сплитом, а не панелью выбора задачи**: на десктопе задача встаёт правой
  половиной центральной зоны (тот же приём и сплиттер, что у открытого файла и «Чтения») —
  разговор остаётся слева. На планшете и мобиле места для сплита нет, там детали открываются
  модалкой поверх ленты.
- **Вход хода реакции тоже оставлял след.** `silent: true` гасит только призрак в очереди, а
  сам служебный промпт ложился в ленту и в историю пузырём от лица постановщика — то есть
  второе сообщение никуда не девалось, да ещё и показывало человеку `<no-reply/>`. Закрыто
  подписью-плашкой **«Доклад по задаче передан постановщику»** (`staffNote`), под флагом.

## Вне скоупа

- **Карточка при неуспешном завершении.** Сегодня доклада в чат при провале нет вовсе (только
  тост со ссылкой на задачу) — оставляем как есть, тексты заголовка заготовлены на будущее.
- **Реакция внутри карточки веткой** (вариант 3 обсуждения): требует нового типа связи
  «ответ на карточку» в ленте. Вернуться, если лента снова начнёт распухать.

## Критерии приёмки

1. Делегированная задача завершается → в чате постановщика **одно** сообщение о факте.
2. Постановщику есть что решить → его реплика появляется и содержит решение, а не пересказ итога.
3. Постановщику нечего решать → второго сообщения нет, следов «пустого хода» в ленте нет.
4. «Открыть задачу» показывает полный итог и файлы, **не уводя из чата**.
5. Флаг выключен → поведение ровно как до изменения (включая старые реплики в историях).
6. `dotnet build` и `dotnet test` зелёные; `npm run lint:design` зелёный.
