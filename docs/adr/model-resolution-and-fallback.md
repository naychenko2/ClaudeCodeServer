# ADR: Порядок резолва модели, классы ошибок фолбэка, защита от зацикливания

**Статус:** Принято
**Дата:** 2026-08-04
**Принимающие решение:** Андрей (владелец продукта)
**Автор:** Александр (тимлид/архитектор)
**Контекст волны:** переработка раздела «Поставщики моделей» — специальности персон,
пресеты правил выбора модели, фолбэк с ротацией подписок, пометка подмены в ленте чата.
Этот ADR фиксирует архитектурные решения ДО реализации; кода волна 2 пишет по нему.

## Контекст

Сегодня резолв модели размазан по трём точкам, но склейка слотов уже централизована:

- **`UserModelTierResolver.ModelFor(tier, ownerId)`** — единственная точка превращения
  слота (strong/medium/weak) в модель: личный слот пользователя → глобальный слот
  инстанса. Ею пользуются и `ModelAssignmentResolver`, и `CheapTextRunner`; CLAUDE.md
  прямо запрещает дублировать её логику.
- **`ModelAssignmentResolver`** — единый вход агентных мест каталога: явная модель →
  назначение админа (модель | слот) → слот по дефолту места.
- **Правила сущностей уже существуют точечно:** `TaskItem.ModelTier` и
  `Persona.ModelTier` (порядок у исполнителя задач — `TaskExecutionService.ResolveExecutorModel`:
  тир задачи → `Persona.Model` → `Persona.ModelTier` → место).
- **`Persona.Specialty`** (`PersonaSpecialty`: Analyst, Planner, Executor, …) — машинный
  тег роли; моделью пока не управляет, используется брифингом/оркестрацией/привязками.
- **Пул подписок** (`ClaudeSubscriptionPool`) — ротация аккаунтов Claude уже есть:
  `Pick(model)` выбирает наименее загруженный доступный аккаунт для нового чата,
  `MarkExhausted`/`IsExhausted` выводят исчерпанные из ротации (белый список окон
  `IsExhaustionWindow`: five_hour, seven_day), `SessionManager` помечает аккаунт по
  `rate_limit_event` живого хода, warmup-пинг возвращает воскресшие. Смена аккаунта у
  существующего чата — `MigrateProviderAsync` (кнопка карточки аккаунта на экране
  «Использование»).

Волна добавляет два новых источника решения (специальность персоны и пресеты правил)
и автоматический фолбэк при рантайм-ошибках. Риски, которые ADR обязан закрыть:
вторая точка истины резолва, фолбэк по ошибкам, которые ретраем не лечатся, и
зацикливание цепочки подмен.

## Решение

### 1. Порядок резолва модели

Единая цепочка приоритетов, сверху вниз, первый непустой ответ побеждает:

```
1. Явная модель сущности        (Session.Model, Persona.Model,
                                 TaskItem.ModelTier как явный выбор постановщика)
2. Правила сущности             (пресеты правил выбора модели, применённые
                                 к сущности; сюда же нормализуются сегодняшние
                                 Persona.ModelTier / TaskItem.ModelTier)
3. Специальность персоны        (настройка «специальность -> слот или модель»
                                 из нового стора, п. 5)
4. Место каталога               (назначение админа в LocalActionOverridesStore:
                                 конкретная модель | слот)
5. Слот                         (личный per-user слот -> глобальный слот
                                 инстанса; null -> дефолт CLI)
```

Ключевые уточнения:

- **Специальность стоит между правилами сущности и местом каталога.** Логика: явный
  выбор на сущности всегда сильнее ролевого дефолта; ролевой дефолт («все Executor'ы —
  средняя») сильнее назначения места («исполнитель задач — слот medium»), потому что
  специальность — более узкий разрез, чем место.
- **Никакой второй точки истины.** Шаги 3–5 реализуются РАСШИРЕНИЕМ существующих
  резолверов: специальность встраивается в `ModelAssignmentResolver.Resolve` /
  `PersonaModel` (и в `TaskExecutionService.ResolveExecutorModel` как источник маркера),
  а разворачивание слота в модель остаётся исключительно в
  `UserModelTierResolver.ModelFor`. Новый параллельный резолвер не заводится;
  копирование цепочки «личный слот → глобальный» в любом другом месте — дефект ревью.
- **Маркеры уровней наружу не текут** (действующее правило сохраняется): `tier:*`
  разворачивается внутри резолвера, в `Session.Model` оседает только конкретная модель
  либо null «по назначению места».

### 2. Классы ошибок, запускающих фолбэк

Фолбэк запускают только **рантайм-ошибки доставки**, при которых та же просьба на другой
паре «модель × подписка» имеет шанс пройти:

| Класс | Примеры | Фолбэк |
|---|---|---|
| Лимит запросов | HTTP 429; `rate_limit_event` rejected по окну из `IsExhaustionWindow` | да |
| Лимит использования | HTTP 403 с семантикой «usage limit reached» | да |
| Ошибка провайдера | HTTP 5xx | да |
| Недоступность эндпоинта | DNS-фейл, connection refused/timeout, обрыв TLS, любой обрыв stream — в том числе посреди уже начатого ответа | да |

Фолбэк **не запускают** (жёсткое правило):

- **Ошибка в содержании ответа** — невалидный JSON, оборванный маркер, «модель ответила
  не то». Это проблема качества, а не доставки; подмена модели здесь маскирует баг.
- **Отказ модели** (refusal по содержанию запроса) — другой моделью «дожимать» отказ
  нельзя ни технически (та же политика), ни этически.
- **Ошибки авторизации, кроме usage limit** — 401, 403 «invalid key»: это ошибка
  конфигурации, ротация её не лечит, а маскирует. Показываем пользователю.
- **400 invalid request** — запрос сломан у нас; на другой модели он сломан так же.
- **Ошибки инструментов внутри хода** и **interrupt пользователя**.

Классификатор ошибок — одна функция с белым списком классов (по образцу
`TurnTelemetry.ClassifyErrorType`: rate_limit / network / auth / …), не разбросанные по
коду `if`. Неизвестная ошибка = фолбэк НЕ запускается (fail-closed: лучше показать
ошибку, чем молча жечь лимиты других аккаунтов о неопознанную проблему).

### 3. Порядок фолбэка: сначала ротация подписок, потом смена провайдера

> **Актуализация 2026-08-08 (ADR-007 §4, §4.1):** уровень 2 «автоподбор
> модели-эквивалента по `Enabled`» удалён. Порядок теперь: уровень 1 (ротация
> подписок пула, тихо и бесплатно для потолка) → шаги цепочки хода (пресет или хвост
> тира явной модели) → честная ошибка. Раздел ниже сохранён как история решения о
> классах ошибок (§2) и защите от зацикливания (§4) — они в силе.

```
ошибка класса "фолбэк" на паре (модель M, подписка S1)
  |
  v
Уровень 1: та же модель M, другая подписка ТОГО ЖЕ провайдера
  - MarkExhausted(S1) + выбор следующей через существующий
    ClaudeSubscriptionPool.Pick(M) (учитывает исчерпание,
    SupportsModel, тариф, утилизацию)
  - переключение живого чата - существующий механизм
    MigrateProviderAsync (тот же, что у ручной кнопки)
  |  кандидатов не осталось
  v
Уровень 2: следующий провайдер по цепочке фолбэка
  (модель-эквивалент по слоту из настроек; переход
   помечается в ленте чата как подмена)
  |  цепочка исчерпана / потолок достигнут
  v
Ошибка пользователю (как сегодня, без подмены)
```

Обоснование порядка: смена подписки внутри провайдера сохраняет модель, качество и
транскрипт-совместимость — это наименьшая подмена; смена провайдера меняет модель и
заметна пользователю. **Новых механизмов ротации не заводим**: уровень 1 собирается из
уже существующих `MarkExhausted` → `Pick` → `MigrateProviderAsync`. Фолбэк лишь
оркеструет их; любые правки самой логики выбора аккаунта делаются в
`ClaudeSubscriptionPool`, а не в слое фолбэка.

### 4. Защита от зацикливания

- **Каждая пара «модель × подписка» пробуется не более одного раза за ход.** Учёт —
  in-memory набор попыток в контексте хода; пара, давшая ошибку, в этом ходу больше не
  кандидат, даже если пул снова предложит её (например, после снятия пометки исчерпания
  warmup-пингом посреди хода).
- **Глубина цепочки настраивается человеком, потолок 5.** Настройка «максимум подмен за
  ход» (дефолт предложит спека волны), значение клампится в диапазон 1..5. Потолок
  жёсткий: 5 записей о подмене в ленте — уже предел полезности; дальше честнее отдать
  ошибку.
- Достигнут потолок или кандидаты кончились → ход завершается ошибкой с указанием
  последней причины; все совершённые подмены остаются видимыми в ленте.
- **Перезапуск посреди начатого ответа ограничивают те же два механизма.** Обрыв stream
  запускает фолбэк в любой момент хода, включая уже начатый ответ (раздел 2), и защитой
  от бесконечной перегенерации служат не запрет подмены после первого токена, а принятые
  выше ограничители: каждая пара «модель × подписка» пробуется не более одного раза за
  ход и жёсткий потолок 5 подмен.

### 4.1. Поправка от 2026-08-07: уровень 1 намеренно тихий

Реализация расходится с первоначальной формулировкой выше («все совершённые подмены
остаются видимыми в ленте», «5 записей о подмене в ленте — предел полезности») — и это
**намеренно**, правка кода фиксируется здесь задним числом. Подмена **уровня 1** (ротация
подписок того же пула Claude — та же модель, тот же транскрипт) проходит **тихо**: маркер
`provider_switched` в ленту не пишется, пользователь видит ровно один ход без служебных
переключений между аккаунтами. Маркер появляется только при смене **типа поставщика** —
уход на стороннего провайдера или шаг цепочки пресета, — там подмена действительно меняет
модель и должна быть видна. Причина тихой ротации сохраняется в `LogDetail` и пишется в
лог для разбора (какой класс ошибки — 429, 5xx, обрыв — погнал смену аккаунта), наружу она
не идёт. Отсюда следствие: «потолок 5» теперь ограничивает только видимые подмены уровня
2+; уровень 1 в этом счётчике не участвует, так что формулировка «5 записей в ленте» к нему
отношения не имеет. **Не возвращайте маркер уровня 1 в ленту** — это сознательное решение,
а не упущение: тишина убирает шум служебных переключений, не лишая разбора (причина в логе).

### 5. Стор настроек специальностей и пресетов правил

Новый стор — `data/model-selection.json`, по образцу `LocalActionOverridesStore`
(immutable-снимок в памяти, запись целиком под локом, путь только от `DataPath`):

```json
{
  "version": 1,
  "global": {
    "specialties": { "executor": "tier:medium", "reviewer": "tier:strong" },
    "presets":     { "<presetId>": { "name": "…", "rules": [ … ] } },
    "fallback":    { "maxSubstitutions": 3, "providerChain": [ … ] }
  },
  "owners": {
    "<ownerId>": {
      "specialties": { "executor": "tier:strong" },
      "presets": { … },
      "fallback": { "maxSubstitutions": 1 }
    }
  }
}
```

- **Глобальные значения + per-owner override.** Чтение: секция владельца → глобальная —
  поле за полем (отсутствие ключа = «как глобально»), тем же паттерном, что личные
  слоты поверх слотов инстанса. Точный состав `rules` пресета фиксирует продуктовая
  спека волны; ADR фиксирует контейнер и семантику override.
- **Значения — те же маркеры, что в каталоге**: `tier:strong|medium|weak` либо id
  конкретной модели. Разбор — существующие `ParseTierRoute`/белый список
  `ModelTiers.TryParse`, не `Enum.TryParse`.
- **Бэкап:** файл лежит в `data/` и попадает в архив по умолчанию
  (`BackupPaths.ShouldInclude`); это настройка, не кеш — из исключений не выводить.
  Секретов не содержит. **Ломающее изменение формата = инкремент поля `version`
  в файле И `BackupSchema.Version`** — иначе старый код после отката молча обнулит стор
  (правило «Новое хранилище → сверься с бэкапом» из CLAUDE.md).

## Последствия

- Плюс: один порядок резолва для чатов, персон и задач; фолбэк собран из проверенных
  механизмов пула; подмена ограничена, а её видимость зависит от уровня — уровень 1 тихий,
  уровень 2+ видимый в ленте (см. §4.1).
- Минус/риск: цепочка приоритетов удлиняется — отлаживать «почему выбралась эта модель»
  сложнее. Митигация: резолв остаётся в двух файлах (`ModelAssignmentResolver`,
  `UserModelTierResolver`), каждый шаг логируется на Debug.
- Риск: фолбэк уровня 1 жжёт лимиты соседних аккаунтов при систематической ошибке.
  Митигация: fail-closed классификатор (неизвестное = не фолбэк) + правило «пара один
  раз за ход» + потолок глубины.
- Явно вне охвата этого ADR: состав правил пресета и UI (продуктовая спека и макеты
  волны 1), реализация пометки подмены в ленте (волна 2).
