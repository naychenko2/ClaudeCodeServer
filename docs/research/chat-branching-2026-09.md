# Ветвление чата: архитектурный разрез (2026-09-18)

Автор: Александр (тимлид/архитектор). Код не писался — это разрез решения под план Егора.
Всё ниже проверено по коду `master` на 2026-09-18 и замерами на реальных данных инстанса
`/srv/ccs/data` (878 папок истории, 487 чатов с парой «история + транскрипт»).

## 1. Решение одним абзацем

Ветка — **обычный новый чат с собственным `ClaudeSessionId`**, которому перед стартом
подкладывают два файла: обрезанный транскрипт CLI (`{профиль}/projects/{уплощённый cwd}/{новый
csid}.jsonl`) и обрезанный `data/sessions/{новый csid}/history.json`. Дальше работает штатный
путь: `CreateChatAsync/CreateAsync(resumeSessionId: новый csid)` → `StartNewSessionAsync`
подхватывает историю (`SessionManager.cs:3567-3570`), первый ход идёт `--resume`
(`ClaudeSession.cs:2578-2579`). Новых хранилищ, новых полей раскладки и новой ветки бэкапа
не заводится. Оригинал не изменяется вообще: ни одного `SaveSessions` по нему, ни `UpdatedAt`,
ни транскрипта (копируем чтением, источник не трогаем).

Ключевая физика: **транскрипт CLI — append-only журнал**, поэтому «история до шага» — это
**префикс файла**, а не результат обхода графа сообщений. См. §4 — там же доказательство,
почему обход по `parentUuid` ломает контекст.

Отсюда два вывода, которые определяют дизайн: **источник = самая длинная копия** (как уже
делает `ArchivedTranscriptStore.FindLongest`, `ArchivedTranscriptStore.cs:169-184`), и
**якорь границы — текст сообщения, а не его номер и не время**.

## 3. Схема хранения ветки

- **Профиль** — тот же, что у оригинала: `ConfigRootFor(ownerId, session.Provider)`
  (`SessionManager.cs:1931-1941`). У container-владельца он сам подменяется на
  `{ProfilesHostDir}/{ownerId}/{key}` — отдельной ветки кода для песочницы не нужно.
- **Папка** — по cwd **ветки**: `projects/{FlattenCwd(cwd)}`, где cwd считается
  `CwdForOwner(ownerId, TryResolveCwd(branchSession))` (`SessionManager.cs:1947-1951`,
  `:2188-2203`). Ветка **не наследует `WorktreePath`** оригинала (два чата в одном рабочем
  дереве — источник конфликтов правок), поэтому её cwd = корень проекта, и файл кладётся
  именно туда. Механика ровно как у `TranscriptMigrator.TryRelocateCwd`.
- **Имя файла** — новый `claudeSessionId = Guid.NewGuid().ToString()`. Гуид проходит
  `IsSafeSessionId` (`TranscriptMigrator.cs:18-25`), а единый гейт на старте сессии
  (`SessionManager.cs:3564-3566`) всё равно перепроверит.
- **Почему новый id, а не общий с оригиналом:** при совпадающем `ClaudeSessionId` два чата
  делят один транскрипт и одну `history.json` — это существующий и явно задокументированный
  инвариант удаления (`SessionManager.cs:7871-7890`). Ветка обязана быть независимой: своя
  лента, своё удаление, свой рост контекста.
- **История UI** — `data/sessions/{новый csid}/history.json`, префикс массива `StoredMessage`
  оригинала (`ChatHistoryService.cs:22-67` читает поэлементно и тихо пропускает неизвестные
  `kind` — это же свойство делает безопасным новый вид записи-плашки, см. §7).
- **Папку сабагентов `{csid}/` не копируем**: для `--resume` она не нужна, её содержимое уже
  отражено в скопированной ленте карточками `tool_use`.
- **Бэкап — ничего делать не нужно.** `BackupPaths` берёт из профилей CLI ровно ветку
  `projects/**` (`BackupPaths.cs:17`, `:117-123`), а `data/sessions/**` идёт целиком без
  исключений. Новый файл ветки попадает в архив автоматически именно потому, что мы не
  придумываем ему отдельное хранилище. Это прямой аргумент против соблазна завести
  `data/branch-transcripts/`.

## 4. Как найти границу «до этого шага» в файле транскрипта

**Правило: ветка = префикс строк исходного файла `[0, K)`.** Ничего не переупорядочиваем,
ничего не пересобираем.

Обоснование (проверено, §2): CLI пишет параллельные вызовы инструментов братьями по дереву,
а не цепочкой. Любая попытка «оставить только путь от листа» выбрасывает `tool_result`
соседней ветви, и следующий ход получает `tool_use` без результата — это гарантированная
ошибка запроса к модели. Префикс же воспроизводит файл ровно таким, каким он был в момент
окончания того хода: все братья, все служебные записи, согласованный `last-prompt.leafUuid`.
Лишние (мёртвые) боковые ветки в префиксе безопасны — CLI и сегодня их игнорирует.

**Поиск K:**
1. Читать файл построчно (`FileShare.ReadWrite`, как `TranscriptMigrator.CopyFileShared`), не
   загружая в память: хранить только позиции и тексты «человеческих» промптов.
2. Человеческий промпт = `type == "user"` И `isSidechain != true` И `isMeta != true` И
   `message.content` — строка либо массив **без** блоков `tool_result`. (Это тот же набор
   признаков, которым уже пользуется `TranscriptProbe.LastUserText`,
   `TranscriptProbe.cs:96-114`, — не изобретаем свой.)
3. Сопоставить последовательность `StoredUserMessage` истории (до якорного шага включительно)
   с этой последовательностью промптов: идём вперёд, для каждого сообщения истории ищем первый
   следующий промпт, содержащий его нормализованный текст (сравнение «содержит», потому что
   сервер клеит к промпту хвосты — recall, контекст, `RecallInTurnText`). Несопоставленные
   промпты транскрипта пропускаем — служебные ходы и вклейки выглядят именно так.

   **Сопоставление обязано быть fail-closed, а не «как получилось».** Жадный поиск по
   подстроке сам по себе тихо промахивается: короткое сообщение («да», «ок», «продолжай»)
   найдётся в чужом промпте, и тогда все последующие границы уедут на ход вперёд — пользователь
   получит ветку, включающую ровно тот ответ, от которого хотел уйти, и узнает об этом только
   по ответу модели. Поэтому три обязательных условия, любое нарушение → 409:
   - **полнота**: каждое неслужебное сообщение истории (без `auto`/`systemDirective`/
     `staffNote`/`viaAgent`) до якоря обязано найти свой промпт; «часть сошлась» не считается;
   - **монотонность**: позиции найденных промптов строго возрастают;
   - **однозначность**: якорный текст даёт ≥40 значимых символов, иначе кандидат принимается
     только при совпадении соседа (предыдущего сопоставленного промпта).
4. K = позиция строки **следующего** человеческого промпта после якорного хода (или конец
   файла, если ветвимся от последнего хода).
5. Хвостовая проверка: собрать `tool_use` id и `tool_result` id последнего хода префикса;
   есть непарные — отступить назад к предыдущей границе хода. Fail-closed, а не «починим
   синтетическим результатом».

**Якорь не нашёлся — отказ 409**, а не «отрежем как получится». По замеру это ~7% шагов
(и ~11% на свежих ходах); резать наугад значит отдать пользователю ветку с чужим контекстом,
чего он не увидит до первого ответа модели.

**Точный якорь — обязательная часть MVP, а не «потом».** Эвристика выше честно отказывает, но
по замеру §2 она будет отказывать примерно в каждом десятом шаге и почти в половине чатов
хотя бы раз. Поэтому одновременно с фичей: на конце хода писать в
`StoredResultMessage` (или `StoredUserMessage`) **uuid последней записи транскрипта** —
`leafUuid` уже лежит в записи `last-prompt`, а хвост транскрипта сервер и так умеет читать
(`TranscriptProbe`, `MainTranscriptTailer`). Тогда для всех новых ходов граница ищется точным
сравнением uuid, а текстовое сопоставление остаётся только для исторических чатов. Это
дешевле, чем потом объяснять пользователю, почему у одного сообщения кнопка работает, а у
соседнего — нет.

**Поле `sessionId` внутри записей** предлагаю переписать на новый id при копировании: имя файла
и содержимое должны сходиться, иначе в одной папке `projects/` окажутся два файла с одинаковым
внутренним `sessionId`. Наш код это поле не читает (проверено: парсятся только
`type`/`message`/`timestamp`), поведение CLI — **непроверенное допущение, снимается первым же
шагом реализации** (см. §10).

## 5. Адресация шага: что шлёт фронт

У элементов ленты нет стабильного id (`ChatItemView.tsx:1155` прямо про это), а индексы
`items` и `messages` расходятся (`normalizeHistory` вливает `workflow_progress` в `tool_use`
и группирует ошибки). Поэтому адрес — **порядковый номер сообщения пользователя**:

- `userMessageIndex` (0-based) — номер элемента `kind === 'user_message'` в ленте;
  для кнопки под ответом ассистента это номер **последнего** `user_message` выше него.
- `include`:
  - `turn` — ветка содержит историю **по конец этого хода** (кнопка под ответом ассистента);
  - `beforePrompt` — ветка содержит историю **до этого сообщения**, а его текст возвращается
    в ответе как черновик для композера (кнопка под своим сообщением).

Сервер считает тот же номер по `StoredUserMessage` в `history.json` — обе стороны считают
одно и то же множество, включая служебные ходы (они рисуются плашками, но остаются
`user_message`).

**Почему у своего сообщения «до», а не «включительно».** Транскрипт обязан заканчиваться
завершённым ходом: если оставить в нём висящий пользовательский промпт, следующий ход
подклеит второе пользовательское сообщение подряд и контекст поедет. Пользовательский смысл
клика под своим сообщением — «спросить иначе», и черновик в композере даёт ровно это, не
трогая физику. **Это единственное расхождение с буквой постановки** («копия до шага
включительно»); альтернатива «оставить промпт в транскрипте» реализуема, но требует
эмпирической проверки поведения CLI и API на двух user-сообщениях подряд — решение за
продуктом, техническая цена вопроса именно такая.

## 6. Контракт API (минимальный)

```
POST /api/chats/{id}/branch
{ "userMessageIndex": 12, "anchorText": "первые ~120 символов этого сообщения",
  "include": "turn" | "beforePrompt", "name": "..."? }
→ 200 { "chatId": "...", "projectId": "..."|null, "claudeSessionId": "...", "draft": "..."|null }
```

`anchorText` обязателен: индекс — это договорённость двух счётчиков, а живая лента клиента и
серверная история расходятся штатно (ради этого и живёт сверка `serverHistoryNewer`,
`chatReducer.ts:255`). Сервер сравнивает присланный текст с найденным по индексу
`StoredUserMessage` и на расхождении отдаёт 409 — вместо того чтобы молча отрезать не там.
Двойной клик по кнопке заводит две ветки с двумя копиями файла — кнопку на время запроса
блокировать на фронте (серверной идемпотентности не вводим: она потребовала бы ключа запроса
ради случая, который лечится `disabled`).

Один эндпоинт покрывает и чаты вне проектов, и проектные сессии: `ChatsController` уже так
работает (`GetOwned` резолвит владельца через проект — см. комментарий у `PUT
/api/chats/{id}/archived`, `ChatsController.cs:258-260`). Второго эндпоинта в
`SessionsController` заводить не надо — `migrate-provider` живёт там же по той же причине
(`ChatsController.cs:530`).

Коды: `404` — чат не найден/чужой; `400` — ветвить нечего (см. §9); `409` — идёт ход, либо
границу не удалось сопоставить. Тексты — человеческие, по конвенции
`InvalidOperationException` → `Conflict` (как `SetArchivedAsync`).

Фронту создание/открытие ничего нового не требует: ветка создаётся штатной фабрикой, поэтому
события списка чатов и навигация (`#/chats/{id}`, `#/project/{pid}/chat/{id}`, `lib/nav.ts`)
наследуются как есть.

## 7. Плашка «Ветка от чата …»

Образец «Продолжено на …» брать **только как визуальный**: технически `provider_switched` —
live-only событие, его нет в `PERSISTED_KINDS` (`chatReducer.ts:242-248`), и после F5 плашка
исчезает. Для ветки так нельзя: связь должна переживать перезагрузку.

Решение: **новая запись истории** `StoredBranchedFromMessage` (`kind: "branched_from"`,
поля: `sourceSessionId`, `sourceName`, `timestamp`) — последней записью скопированной истории,
то есть ровно в точке расхождения. Плюсы: живёт в `history.json`, переживает рестарт и смену
`claudeSessionId` (аккумулятор держит историю в памяти и переписывает файл целиком под текущим
ключом — `TurnAccumulator.cs:36-49`, `SessionManager.cs:8034`), а при откате кода старый бэкенд
её тихо пропустит (`ChatHistoryService.cs:41-46`).

Обязательные три правки-спутника: дискриминатор в `StoredMessage.cs`, элемент `ChatItem` и
рендер в `ChatItemView`, **и ключ в `PERSISTED_KINDS`** — иначе сверка «история сервера новее?»
будет считать длины с расхождением. Забыть последнее не выйдет: сторож
`chatReducer.test.ts:122-139` сверяет белый список с дискриминаторами `StoredMessage.cs`
один в один и покраснеет сразу.

Поле в `Session` (`BranchedFromSessionId`) для UI не нужно — списка веток в оригинале нет по
продуктовому решению, а плашка живёт в истории. Но завести его всё же стоит: это единственный
машинно-читаемый признак «этот чат — ветка», по которому backfill расхода сможет пропускать
унаследованные `result`-записи (§8), а разбор инцидента — понять происхождение файла. Поле
аддитивное, `BackupSchema.Version` не двигает.

## 8. Инварианты под угрозой и как удержать

| Инвариант | Риск | Как держим |
|---|---|---|
| Оригинал не меняется | случайный `SaveSessions`/`UpdatedAt`/архив | ветвление читает источник и не вызывает ни одного мутатора оригинала; тест: `UpdatedAt`, `ArchivedAt`, `ClaudeSessionId` оригинала до и после — равны |
| Удаление чата уносит транскрипт | ветка с общим csid унесла бы память оригинала | у ветки **свой** csid; гейт «на csid ссылается другой чат» (`SessionManager.cs:7879`) остаётся нетронутым |
| `resumeSessionId` — белый список | новый id формируется сервером | `Guid.NewGuid()`, плюс существующий гейт `StartNewSessionAsync` |
| Пути — только `SafePath.Join` | склейка `projects/{flat cwd}/{csid}.jsonl` | все сегменты — либо результат `FlattenCwd`, либо валидированный csid; целевой файл — через `SafeJoin`, как в `ArchivedTranscriptStore.cs:76` |
| Десктопный транскрипт не покидает грань | кадры экрана уехали бы в обычный чат | ветвление десктопного чата **запрещено** (§9). Гейт писать по `source.DesktopChat == true`; **`DesktopChatGuard.Refuse` тут не работает** — он ищет десктопный чат по совпадению `resumeSessionId` с чужим `ClaudeSessionId` (`SessionsController.cs:263-274`), а у ветки id новый, и проверка молча пропустит копию. Из `DesktopChatGuard` берём только текст константы |
| Правки идут в дерево чата, а не в чужое | ветка унаследовала бы чужой worktree либо продолжила править удалённое дерево | ветвление чата с `WorktreePath != null` на первой итерации **запрещено** (§9.8) |
| Явный opt-out «не сохранять решения» | ветка обошла бы `ExcludeFromDossiers` (гейт захвата — `Dossiers/DossierCaptureService.cs:195`) | поле наследуется веткой; см. §11 «наследование полей» |
| Атрибуция правок по файлам | ветка со скопированной историей заявит, что меняла все файлы оригинала (`ProjectFileSessionsIndex.cs:99-107`), а пометки «уже в git» (`CommittedFilePaths`) в неё не переедут | цена принимается осознанно: индекс строится из истории, вычищать её ради бейджа «Также меняли» дороже. Зафиксировать в тексте задачи, чтобы не всплыло как дефект |
| Учёт расхода | `SpendMaintenanceService` импортирует `StoredResultMessage.Usage` из историй (`SpendMaintenanceService.cs:50-84`) — копия истории = повторный счёт | на живом инстансе backfill одноразовый (`SpendStore.cs:226`), риск только при потере маркера (перенос/восстановление). Дешёвая страховка — пропускать чаты-ветки в backfill по признаку ветки |
| Container-владелец | путь профиля и cwd другие | только `ConfigRootFor(ownerId, …)` и `CwdForOwner(ownerId, …)`; «по соглашению» путь у них не сходится — источник искать `FindAllTranscripts` + фолбэк-скан (`TranscriptMigrator.cs:83-87`) |
| Бэкап покрывает новое хранилище | потеря ветки при восстановлении | новых хранилищ нет (§3); добавить в `BackupPathsTests` кейс «файл ветки в профиле попадает в архив» — он уже покрыт правилом `projects/**`, тест фиксирует намерение |
| Несколько копий транскрипта | взяли короткую копию → ветка без начала разговора | источник = **самая длинная** копия по `FindAllTranscripts` (147 чатов из 487 имеют копии разной длины); для архивного чата — плюс `ArchivedTranscriptStore` |
| Живой ход пишет в файл | копия с оборванным хвостом | отказ при `HasTurnInFlight` (`SessionManager.cs:1670`) + чтение через `FileShare.ReadWrite` + отбрасывание недописанной последней строки |
| Стабильность состава MCP | — | не затрагивается: ветка — обычный чат, состав инструментов зависит от сессии, а не от хода |

## 9. Явные отказы (закладывать сразу)

1. **Идёт ход или живут фоновые агенты** — 409, текстами по образцу `SetArchivedAsync`
   (`SessionManager.cs:1668-1675`). Причина та же: копируем файл, в который пишет CLI.
2. **Нет `ClaudeSessionId`** — 400 «чат ещё не обращался к модели: ветвить нечего». Копировать
   одну ленту без транскрипта нельзя: на экране история есть, в памяти модели нет — это ложь.
3. **Десктопный чат** — 400. Гейт — по `source.DesktopChat == true` (не `DesktopChatGuard.Refuse`,
   см. §8), текст берём готовый: `DesktopChatGuard.ResumeFromDesktop`. Инвариант
   ADR-008 запрещает и продолжать десктопный транскрипт в обычном чате, и создавать десктопный
   чат из чужого транскрипта — то есть ветвление невозможно в обе стороны.
4. **Транскрипт не найден ни в одном профиле и в архиве** — 400 «память этого разговора уже
   убрана плановой уборкой CLI». (Для `MigrateProviderAsync` это штатный случай, для ветвления —
   отказ: переносить нечего ≠ копировать нечего.)
5. **Границу не удалось сопоставить** — 409 «не удалось найти этот шаг в памяти модели;
   попробуйте ветвиться от другого сообщения».
6. **Групповой чат и чат в режиме штаба** (`Participants`, `TeamImplement`) — 400 на первой
   итерации: у них состояние волн/планов живёт в `Session`, а не в транскрипте, и ветка
   унаследовала бы ленту без состояния. Снимать запрет — отдельной задачей, если спросят.
7. **Файл больше потолка** (предлагаю тот же 512 МБ, что `ArchivedTranscriptStore.MaxCopyBytes`, `ArchivedTranscriptStore.cs:25`)
   — 400, чтобы одна кнопка не устроила копирование гигабайта под HTTP-запросом. Принимаемая
   цена фичи: каждая ветка — полноразмерная копия префикса в `projects/**`, то есть плюс
   столько же байт в облачном архиве (та же цена, что у `data/archived-transcripts`).
8. **Чат в отдельном worktree** (`WorktreePath != null`) — 400 на первой итерации. Ветка не
   наследует чужое рабочее дерево, а её cwd оказался бы другим: в скопированном контексте
   лежат абсолютные пути внутри `…/worktrees/{ветка}`, и модель продолжила бы править дерево,
   которое сносится вместе с чатом-источником (`SessionManager.cs:7905-7918`). Снимать запрет —
   только вместе с решением, куда ветка ходит.

Архивный чат ветвить **разрешаем**: источник ищем сперва в профилях, затем в
`data/archived-transcripts`; оригинал из архива **не возвращаем** (не трогаем `ArchivedAt`).

## 10. Что проверить ПЕРВЫМ шагом реализации (риск-первый порядок)

До всякого UI и REST — ручной эксперимент на живом CLI, он снимает непроверенные допущения
всей фичи:

0. **Какой `session_id` приходит в `system/init` при `--resume` подложенного файла.** Это
   допущение критическое, а не косметическое: `ClaudeSession.cs:4644-4647` присваивает
   пришедший id в `Info.ClaudeSessionId`, а `SessionManager.cs:8034` тут же переводит на него
   ключ записи истории. Если CLI отдаст **новый** id (форк резюмируемой сессии — поведение
   версионно-зависимое), то после первого же хода ветки подготовленные нами
   `data/sessions/{наш csid}/history.json` (вместе с плашкой `branched_from`) и файл
   `{наш csid}.jsonl` осиротеют: удаление чата чистит по ТЕКУЩЕМУ `ClaudeSessionId`
   (`SessionManager.cs:7871-7889`), и копия чужой переписки останется в профиле навсегда —
   и уедет в бэкап по правилу `projects/**`. То есть сломается ровно тот инвариант «удаление
   чата уносит транскрипт», ради которого написан этот гейт.
   **Если id меняется** — в схему добавляется уборка: на `system/init` ветки, увидев смену
   `ClaudeSessionId` относительно подготовленного, удалить старый `{csid}.jsonl` и папку
   `data/sessions/{csid}` (по образцу уборки локальной истории при переходе локаль→CLI,
   `SessionManager.cs:7897-7903`), под тем же гейтом «на csid не ссылается другой чат».
1. Взять транскрипт реального чата, отрезать префикс до конца N-го хода, положить под новым
   гуидом в тот же профиль и папку cwd.
2. Запустить `claude --print --resume {новый csid}` с вопросом на знание контекста.
3. Убедиться: ответ помнит разговор **до** точки отреза и **не** помнит то, что после.
4. Повторить дважды: с переписанным полем `sessionId` внутри записей и без — зафиксировать,
   какой вариант CLI принимает (ожидание: оба; факт неизвестен).
5. Отдельно — случай с параллельными `tool_use` в последнем сохранённом ходе.
6. Отдельно — чат, переживший компактизацию (`compact_boundary`): отрез до компакта и после.

Если п.3 не воспроизводится — вся схема хранения пересматривается, и лучше узнать это до того,
как в неё вложится фронт.

## 11. Наследование полей `Session` (решить до кода)

| Поле | Решение | Почему |
|---|---|---|
| `ProjectId`, `OwnerId`, `PersonaId`, `Model`, `Provider`, `Effort`, `Mode` | наследуем | ветка продолжает тот же разговор тем же собеседником; иначе первый же ход пойдёт другой моделью |
| `ExcludeFromDossiers` | **наследуем обязательно** | иначе ветвление обходит явный opt-out пользователя (`Session.cs:380-382`, гейт захвата `DossierCaptureService.cs:195`) |
| `AutoAllowTools` | **не наследуем** | «Разрешать всегда» нажато в конкретном разговоре — модель прямо это оговаривает (`Session.cs:399-407`); перенос тихо расширил бы выданное разрешение. Цена — человек переспросит один раз |
| `WorktreePath`/`WorktreeBranch` | не наследуем, ветвление таких чатов запрещено (§9.8) | два чата в одном дереве и чужие абсолютные пути в контексте |
| `TaskId`, `TaskExecution` | **не наследуем** | ветка чата-исполнителя — это разговор человека, а не второй исполнитель той же карточки: иначе `tasks_complete` из ветки закроет чужую задачу |
| `Context` (фича `chat-context`) | наследуем | материалы чата — часть того же разговора; копия дешёвая, ссылки те же |
| `ExpiresAfterMinutes`, `ArchivedAt`, `ArchiveBatchId`, `LastReadAt` | не наследуем | срок и архив — свойства конкретного чата, а не разговора |
| `VoiceMode`, `VoiceStyle`, `NotificationsMuted` | наследуем | настройки восприятия, человек их уже выбрал |
