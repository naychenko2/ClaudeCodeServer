## ADR-001. Происхождение задач и чатов

- **Статус:** Предложено, 2026-07-23. [ADR-001](../adr/ADR-001-task-and-chat-origin.md)
- **Решение:** единый хранимый факт происхождения — `TaskItem.SourceSessionId` (чат, породивший задачу); родитель чата — вычисляемый `parentSessionId` (`Session.TaskId → Task.SourceSessionId`), а уведомление постановщика — двухэтапное: дефолт L0 (бесплатное notification), активная реакция L1/L2 — опционально через движок проактивности.
- **Отвергнуто:** новый MCP-сервер «watch task» (второй источник истины, лишний процесс, адресат всегда человек); хранимый `Session.ParentSessionId` (денормализация против директивы `Session.cs:5`); джойнит фронтом по стору задач (иерархия молча разваливается при удалении задачи); join-барьер «когда готовы все N» (требует новой сущности «пакет делегирования»); программный autostart задачи (создание не должно неожиданно порождать сессию).
- **Реализация:** `backend/ClaudeHomeServer.Tasks/TaskManager.cs:181` (`SourceSessionId` записи), `backend/ClaudeHomeServer.Core/Services/SessionTaskLinks.cs` (вычисление родителя), `backend/ClaudeHomeServer/Services/SessionJsonConverter.cs` (wire-поля `parentSessionId`/`taskDone`), `backend/ClaudeHomeServer/Services/TaskExecutionService.cs` (`NotifyDelegatorAsync` — L0), `mcp/tasks-server/index.js` (проброс `TASKS_SESSION_ID`), фронт — `frontend/src/lib/chatTree.ts`, `frontend/src/components/ChatTreeRow.tsx`.
- **Актуальность:** этапы 1–2 реализованы (поле, вычисляемый родитель, L0, иерархия в `SessionList`). Этап 3 (L1/L2) — частично: движок `TaskStatusTriggerSource` существует (`backend/ClaudeHomeServer.TriggerSources/TaskStatusTriggerSource.cs:12`), но объявленного фильтра `createdByMe` в нём не нашлось — автосоздание правила и доставка ходом в исходный чат в нём не видны. Статус «Предложено» не обновлён, хотя решение в коде работает.

## ADR-002. God-nodes Code Graph в системный промпт

- **Статус:** Принято, 2026-07-27. [ADR-002](../adr/ADR-002-code-graph-god-nodes-in-prompt.md)
- **Решение:** per-ход slice top-10 god-nodes графа кода вставляется в системный промпт (`--append-system-prompt`) провайдером, а не через MCP: slice кэшируется по сигнатуре `BuiltAt` графа, при stale-файлах — soft-пометка, блок отключаем (null → молча пропускается).
- **Отвергнуто:** вариант B — ленивый MCP-инструмент «найди/объясни» (модель может не позвать → холодный старт не закрывается; +точка отказа; состав `tools/list` начинает зависеть от хода); вариант C — гибрид A+B (A даёт ~80% пользы, гибрид заметно дороже). B/C оставлены на Wave 3.
- **Реализация:** `backend/ClaudeHomeServer.CodeGraph/Services/CodeGraph/CodeGraph/CodeGraphPromptProvider.cs` (slice + кэш по `GetCacheSignature`, `GraphPersistence.cs:112`), `CodeGraphService.cs`, `CodeGraphContributor.cs` (Turn-вкладчик) — вертикаль `ClaudeHomeServer.CodeGraph`; панель «Граф» и REST — там же.
- **Актуальность:** решение в силе: slice в промпте на каждый ход. Местоположение и механизм изменились: файлы переехали из `Services/CodeGraph/` (где остался только `CodeGraphInspector.cs`) в вертикаль `backend/ClaudeHomeServer.CodeGraph/`, а провайдер `CodeGraphProvider` в `LlmSessionContext` превратился в Turn-вкладчика `CodeGraphContributor` (архитектура `PromptSectionContributors`).

## ADR-003. Code Graph в чатах с отдельным worktree

- **Статус:** Черновик (на согласовании), 2026-07-28. [ADR-003](../adr/ADR-003-code-graph-in-worktrees.md)
- **Решение:** для worktree чата строится отдельный полноценный граф (ключ — хеш пути, изоляция уже была): `?rootPath=` на эндпоинтах графа с белым списком (корень проекта или worktree сессии), env `CODEGRAPH_ROOT_PATH` у MCP, ленивый `FileWatcher`-watcher на путь worktree с автоснятием, slice основного дерева — как fallback, пока свой граф не построен.
- **Отвергнуто:** оверлей-дельта поверх основного графа (Roslyn для межфайловых рёбер требует полной компиляции — та же цена, плюс зависимость от `git` и гонка «ветка ушла, дельта прухла»); «оставить как есть, пометить в промпте» (граф превращается в справочник «где что лежало»); хранить граф ВНУТРИ worktree (untracked-файл срабатывал бы на гейте «в дереве есть несохранённые изменения»).
- **Реализация:** `backend/ClaudeHomeServer/Controllers/CodeGraphController.cs:67` (`?rootPath=` + `WatchPath("worktree:"+id)`), `backend/ClaudeHomeServer/Services/FileWatcherService.cs:178,225` (`WatchPath`/`UnwatchPath`), `backend/ClaudeHomeServer/Services/SessionManager.cs:2206` (снятие watcher'а), `backend/ClaudeHomeServer.Llm/Claude/ClaudeSession.cs:1621` (env), `mcp/codegraph-server/index.js:52`, `backend/ClaudeHomeServer/Services/Mcp/Http/CodeGraphToolset.cs:177`.
- **Актуальность:** оба уровня реализованы (собственный граф worktree, ленивый watcher, снятие, fallback slice). Разошлось только периферийное: после HTTP-изации MCP (ADR-012) worktree-путь больше не едет query-параметром/через env «на веру» — тулсет `CodeGraphToolset` резолвит дерево сессии сам; `?rootPath=` остался на REST. Статус «Черновик» не обновлён.

## ADR-004. Паспорта изменений («память кода»)

- **Статус:** «Черновик (на согласовании)», 2026-08-01. [ADR-004](../adr/ADR-004-change-dossiers.md)
- **Решение:** у каждого коммита из чата/задачи автоматически рождается «паспорт» (AI-выжимка: зачем, что решили, что отвергли, грабли) — пять подсистем: (1) связь «коммит ↔ чат» — трейлер `CCS-Session`/`CCS-Task` в сообщении коммита (коммит делает агент через Bash, сервер «знает» сам); (2) детект нового коммита — серверный поллинг HEAD, без git-хуков; (3) конвейер выжимки: `DossierCaptureService` (детект + сырьё) → `CheapTextRunner` (JSON) → `SecretRedactor` (свой, т.к. PII-санитайзер атрибутов OTel на свободный текст не применим); (4) хранение: `data/dossiers/{ownerId}/{projectId}.json` (source of truth) + архивный JSONL + Dify-датасет `{ns}:{user}:dossiers:{project}` (производный слой); (5) доставка: секция recall в промпт персоны (в существующий блок `PersonaMemoryService.BuildRecallAsync`, новых каналов нет) + MCP-инструменты `dossier_lookup`/`dossier_get`; git-экспорт вручную в ветку `ccs/dossiers/v1`; двухшаговая выкатка — два флага `change-dossiers`/`change-dossiers-recall`.
- **Отвергнуто:** `post-commit` hook (запись в репозиторий пользователя, конфликт с чужими/Entire-хуками, ломается в container); хуки Claude Code (`.claude/settings.json` — тем же файлом управляет наш сервер, зафиксированная точка конфликта пилота Entire); серверная эвристика атрибуции (время+автор+`FileChangeAttributor`: параллельные ходы и ручные коммиты дают ложную атрибуцию, «ложный паспорт хуже отсутствующего»); MCP `git_commit` единственным каналом (секция `git_write` по умолчанию выключена, агент коммитит Bash-ем); один `data/dossiers.json` на инстанс (перезапись целиком на каждый коммит, рост без границ); SQLite в v1 (своя ветка `BackupDatabase` + миграции; триггер пересмотра — файл >15 МБ или >3000 записей); только Dify (производный слой, source of truth обязан жить у нас); git notes (не переживают remote без push/fetch notes, не видны в UI хостингов); отдельный системный блок «паспортов» (третий конкурент места в промпте); только MCP без пассивного канала (персона не знает, что спрашивать, «правлю файл — вижу, зачем его меняли» не работает).
- **Реализация:** вертикаль `backend/ClaudeHomeServer.Dossiers/` (`DossierCaptureService.cs`, `DossierStore.cs`, `SecretRedactor.cs`, `CommitTrailers.cs`, `DossierAutoExporter.cs`, `DossierBranch.cs`, `DossierDiscussionService.cs`), `data/dossiers/`, флаг `change-dossiers-recall` (`FeatureFlag.cs:31`, `frontend/src/lib/featureFlags.ts:12`), секция recall — `PersonaMemoryService`.
- **Актуальность:** механика реализована (вертикаль на месте, трейлеры, стор, Dify-слой, recall, MCP, автоэкспорт в ветку). Разошлось: (1) ADR описывает ДВА флага (`change-dossiers` захват + `change-dossiers-recall`); в коде остался один — `change-dossiers-recall` (`FeatureFlag.cs:85`: «один из двух оставшихся флагов») — захват, судя по всему, дожил до безфлагового; (2) статус «Черновик (на согласовании)» от 08.2026 не обновлён, хотя фича работает; (3) фича выросла: появились обсуждения паспортов (`DossierDiscussionService/Store`) — в ADR их нет.

## ADR-005. Серверная часть режима чтения ссылок

- **Статус:** «Предложено», 2026-08-03. [ADR-005](../adr/ADR-005-link-reader-server.md)
- **Решение:** статья извлекается В ПРОЦЕССЕ бэкенда пакетом `SmartReader` (порт Mozilla Readability на AngleSharp; 0.11.1) — её собственный загрузчик никогда не использовать (обойдёт SSRF-проверку), HTTP — свой клиент `link-reader` (`AllowAutoRedirect=false` с SSRF-проверкой на каждый из ≤5 редиректов, `UseProxy=false` — egress-прокси проверенно не держит периметр; без кук, без Referer); `POST /api/reader/read {url}` (URL в теле, не query), тело ≤2 МБ; формат провода — MARKDOWN (обход DOM по белому списку тегов; `script/style/iframe/form` не переживают конвертацию физически) + три инварианта рендера: `rehype-raw` в ридере не появляется, `urlTransform` не пропускает `javascript:`/`data:` мимо дефолта, ридер рендерит своим экземпляром без `resolveFileMention` (чужой текст не должен открывать локальные файлы).
- **Отвергнуто:** `markitdown` по скачанному HTML (не удаляет обвязку — навигацию/подвал/баннер; python-процесс на каждый клик; и `MarkitdownService` принимает ПУТЬ к файлу — недоверенный HTML пришлось бы писать на диск); Node-сайдкар с `@mozilla/readability` + `jsdom` (ломает простоту «MCP-сервер = один файл», `npm install` в деплой, второй процесс + IPC); собственный экстрактор (NIH, переписывание эвристик Readability); внешний сервис (`r.jina.ai`, Mercury) — самый дешёвый, но URL человека уходит третьей стороне (требование №1), «назван явно, чтобы к нему не вернулись».
- **Реализация:** вертикаль `backend/ClaudeHomeServer.Reader/` (`ReaderService.cs`, `ReaderHttpHandlerFactory.cs:29` — `UseProxy = false`, `ReaderConnect.cs` — ConnectCallback/TOCTOU, `HtmlToMarkdownConverter.cs`, `ReaderQuotaService.cs`, `ReaderModels.cs` — 15 кодов ошибок), `backend/ClaudeHomeServer/Controllers/ReaderController.cs` (`/read`, `/image`, `/embed-check` — ADR-006), фронт — `frontend/src/pages/workspace/reader/` (ReaderBody.tsx — sandbox-iframe, ReaderArticle.tsx).
- **Актуальность:** реализован (все компоненты на месте, SmartReader 0.11.1 — та же версия, что в ADR). Разошлось: (1) гейт «флаг `link-reader`» (`ReaderController … + флаг link-reader`) — флага в коде больше нет: ридер работает по умолчанию (флаг удалён вместе с `chat-watchdogs`, `project-backgrounds` — единый паттерн «фича дожила, флаг снят»); (2) статус «Предложено» не обновлён.

## ADR-006. Проверка встраиваемости для панели «Чтение» (iframe-режим с MD-фолбэком)

- **Статус:** Предложено, 2026-08-04. [ADR-006](../adr/ADR-006-reader-embed-check.md)
- **Решение:** перед показом страницы целиком в sandbox-iframe панель сначала спрашивает бэкенд `POST /api/reader/embed-check` (headers-only GET тем же клиентом, что `/read`): браузер сам не сообщает о блокировке фрейма, а CORS не даёт прочитать заголовки; при `embeddable: false` — молча MD-чтение. iframe — строгий белый список: `sandbox="allow-scripts"`, `no-referrer`, `credentialless`, `allow=""`; `allow-same-origin`/`allow-forms`/попапы «запрещены навсегда», моста `postMessage` нет.

## ADR-007. Пресет как именованная цепочка моделей, матрицы уровней, `preset:{id}`, миграция v1→v2

- **Статус:** «Принято (реализовано 2026-08-08, волны 1–2 + фиксы ревью; уточнения §9/§10)», 2026-08-05. [ADR-007](../adr/ADR-007-model-preset-chains.md)
- **Решение:** (1) пресет = именованная упорядоченная ЦЕПочка из 1..5 шагов в лексике маршрутов (`tier:*`, id модели, `local`/`claude`/`default`), вложенные `preset:` запрещены; (2) «уровень выбирает СТРОКУ, сущность — МАТРИЦУ»: у персоны и специальности свои ячейки `TierStrong|Medium|Weak` + `DefaultTier`, разворачивание — единственная точка `UserModelTierResolver.ModelFor(tier, ownerId, narrowMatrices)` (персона → специальность → слоты владельца); (3) `preset:{id}` — значение лексики, принимают ВСЕ места выбора модели (кроме `TaskItem` — только уровень), хранится как есть, разворачивается на границе (`ExpandChain`), защита от петли «слот ↔ пресет» — набор посещённых ссылок; (4) автоподбор (`EquivalentModel`, обход `Enabled`) удалён: уровень 1 — тихая ротация подписок пула, дальше — шаги цепочки, исчерпалась — честная ошибка; бюджет подмен 3→4 (1+4=5, тихие ротации бесплатны); (5) явная модель несёт «хвост тира» как план отступления; подмена — состояние хода (CAS-восстановление, инвариант «провайдер == профиль со свежим транскриптом»); кулдаун сторонних провайдеров — `ProviderHealthRegistry` (TTL 5 мин/60 мин, глобальный, снимается успешным ходом); (6) миграция стора 1→2 (правила v1 разносятся в `DefaultTier`/матрицы, пресеты v1 удаляются) + инкремент `BackupSchema.Version`.
- **Отвергнуто:** «пресеты применяются все сразу» (v1: `ResolveRoute` обходил все пресеты — пресет теперь значение, а не постоянные правила); автоподбор модели-эквивалента (цепочка есть у ЛЮБОГО хода — «без настроек нет и магии»); контекстно-зависимое разворачивание `tier:*`-шагов (один пресет значил бы разные модели в двух местах — «трёхмерная» отладка); «разморозка» модели чата (`--resume` привязан к профилю, предсказуемость — чат заморожен на момент создания, это инвариант §9.1); `Persona.ModelTier` в цепочке (после упрощения формы это стала невидимая настройка — выведено из резолва, миграция значений в `TierMedium`); третий слой стора (открыли адресацию существующего per-owner: админ пишет чужой слой, остальные — свой).
- **Реализация:** вертикаль `backend/ClaudeHomeServer.Llm/`: `SpecialtySettingsStore` (`ExpandChain`, `FormatVersion`), `LocalActionOverridesStore.ParsePresetRoute`, `ModelAssignmentResolver` (цепочка + `TierOfModel`), `UserModelTierResolver.cs:71` (`ModelFor(..., narrowMatrices)`), `FallbackLlmSessionAdapter`, `ProviderHealthRegistry.cs`, `FallbackSettingsStore.cs:27-32` (`HardMaxSubstitutions = 5`, `DefaultMaxSubstitutions = 4`), `PersonaManager.MigratePersonaModelTiers`; фронт — `frontend/src/lib/presets.ts` (user-слои), `frontend/src/lib/__tests__/userLayers.test.ts` (сторож §10).
- **Актуальность:** ядро в силе (цепочки, матрицы, отсутствие автоподбора, бюджет 4/5, заморозка модели, миграции). Разошлось: (1) ADR-012 (2026-08-26, ПОЗЖЕ) схлопнул два слоя `SpecialtySettingsStore` (global + per-owner) в один глобальный — §9.5/§10 про «запись в слой пользователя» и адресацию `contextUserId` частично обгоняет/разъединяется с ADR-012, в ADR-007 это не отражено; (2) пути «Связанных артефактов» (`Services/SpecialtySettingsStore.cs` и т.п.) переехали в вертикаль `ClaudeHomeServer.Llm`; (3) open-вопросы §10.4 (версионирование user-слоя ETag/If-Match; декоративное `SpecialtySettingsResponse.userId`) по коду не закрыты — согласуется с самим ADR.

## ADR-009. Контракт формата маршрута локального действия (`local-actions.json`) (повторный номер)

- **Статус:** Принято, 2026-08-12. [ADR-009](../adr/ADR-009-local-action-route-format.md)
- **Решение:** маршрут «кто выполняет это место» — строка ровно восьми форм: `local`, `claude`, `default` (легаси ≙ `tier:medium`), `tier:strong/medium/weak`, `preset:{id}`, id модели; `direct:{id}` — не девятая форма, а подвид восьмой (только транспорт — прямой HTTP-адаптер); префикс — часть значения, правила регистра/тримма задокументированы несимметрично «как в коде»; валидация — полностью на записи (`PUT /{key}` → 400), чтение — осознанный fail-open (горячий путь, фон обязан быть живучим); фронт собственной лексики не заводит.
- **Отвергнуто/известные дыры:** строгий читатель на чтении (обрвал бы фон при любой рассинхронизии версий); валидация действует только для `PUT /{key}` — мимо неё: `SetMany` (массовое применение пресета, «единственный, кто реально пишет мусор»), ручная правка файла, секция `Ollama:Actions` (формат вообще другой — `bool`); `tier:*` в ячейках матриц, вложенный `preset:*` в шаге пресета, `preset:{id}` места каталога — только ОБЩИЙ пресет.
- **Реализация:** `backend/ClaudeHomeServer.Llm/LocalActionRouter.cs` (`Parse`), `LocalActionOverridesStore.cs` (`ParseTierRoute`, `IsPresetRoute`, `Set`/`SetMany`), `CloudCheapClient.cs` (`IsDirectRoute`/`StripPrefix`), `ModelAssignmentResolver.cs` (`ExpandStep`), `backend/ClaudeHomeServer/Controllers/LocalActionsAdminController.cs`, `data/local-actions.json`, фронт — `frontend/src/lib/modelProvidersShared.ts` (`TIERS[*].route`).
- **Актуальность:** решение в силе: восемь форм, канонический вид в `modelProvidersShared.ts` совпадает буква в букву, fail-open на чтении. Разошлись пути (ADR: `backend/ClaudeHomeServer/Services/Llm/…` — теперь вертикаль `ClaudeHomeServer.Llm`). Изъян, который ADR фиксировала как «закрыть позже» (валидация формы в `SetMany`), к 23.09.2026 НЕ закрыт: `SetMany` (`LocalActionOverridesStore.cs:115`) по-прежнему проверяет только известность ключа и непустоту.

## ADR-010. Пересборка и переопубликация прода из чата

- **Статус:** Предложено, 2026-08-18. [ADR-010](../adr/ADR-010-deploy-from-chat.md)
- **Решение:** сервер не деплоит себя: чат прода пишет заявку (`POST /api/deploy`), а исполняет её `deploy-agent` — процесс без родства с сервером (задача планировщика, скрипт живёт **вне** publish-дерева): сборка в staging при живом сервере → бэкап данных → окно 10–20 с (стоп, снимок релиза, старт) → health-гейт 3×/90 с → при провале автооткат на снимок `releases\<stamp>`; журнал `deploy-state.json` — единственная точка истины, новый инстанс сам докладывает исход в чат.
- **Отвергнуто:** detached-процесс вместо Task Scheduler (трюк с «сразу умирающим» `cmd` держится на гонке; дерево процессов строится по `ParentProcessId`); blue-green через junction (`C:\deploy\claude` зашито в `DockerPathMapper`, `tray.json`, автозапуск — переезд дороже пользы); дренаж активных ходов и нулевой downtime (отложены; окно в секунды принято); автооткат ДАННЫХ (за минуты жизни новой версии в сторы уже записано — данные восстанавливает только человек); самообновление агента на лету (агент копируется в свой каталог и запускается копией).

## ADR-014. Внутренние подсистемы (терминология, контракт, правило зависимостей, Этап 5)

- **Статус:** «Принято (этап 0 — контракт + пилот Video; этап 1 — сторож; этап 2 — вертикали; Этап 5 — полный разнос, решение 2026-09-08)», 2026-09-01. [ADR-014](../adr/ADR-014-internal-subsystems.md)
- **Решение:** (1) терминология: **модуль** (внешний процесс за YARP) ≠ **подсистема** (внутренняя регистрация в Microsoft DI), **вертикаль** = раздел продукта, **спина** = общий слой (DI, `McpSecretStore`, `Models`, `Services/Http`/`Security`), **шов** = явный интерфейс на границе; (2) контракт `IAppSubsystem { Key, Title, Register }` + `AddSubsystems` (порядок важен, дубликат `Key` — ошибка; объект после `Build()` выбрасывается, НЕ singleton), v1.1 — hosted-хелперы с Testing-гейтом, `ResolveDataDir`, опциональная app-фаза `IAppPhaseSubsystem`; (3) правило: **вертикаль зависит от спины и швов, но НИКОГДА от другой вертикали** — связь: шина `TurnEventBus` (факты) или явный шов (синхронное состояние); (4) НЕ переход на `AssemblyLoadContext` (DI — один контейнер на процесс, выгрузка части = выгрузка всего); (5) **Этап 5 (2026-09-08): ВСЕ вертикали — в отдельные `.csproj`**: критерий выноса — не швы, а отсутствие циклов на пробной сборке (греп `using` не свидетель — не видит полные имена, константы, литералы; одна сборка показывает только первую волну — до сходимости заглушками); спина лечится переносом в Core с сохранением namespace (Models целиком — 41 файл, `Protocol`, `ISessionBroadcaster`); Notes/Spend — динамические модули (dll в `modules/`).
- **Отвергнуто:** вынос по сборкам через `AssemblyLoadContext` (DI-контейнер не выгружается по части; indirection без выгоды);Desktop как «рефакторинг трёх god-объектов» (пересмотр: 3 строки + готовый шов `IDesktopTurnGate`); старое правило «остаток вертикалей без нового критерия не переносим» (отменено решением владельца 2026-09-08 — основание: целостность концепции, не экономика сборки; архитектор возражал, спор закрыт); Team-вынос (74 упоминания `SessionManager` — потребовал бы фасада на десятки методов) и Backup (инфраструктурный срез поперёк всех, `BackupSchema.Version` — глобальный счётчик, `BackupCli.TryHandle` до DI) — остаются в Main.
- **Реализация:** `backend/ClaudeHomeServer.Core/Services/Composition/IAppSubsystem.cs`, 32 вертикали-сборки `backend/ClaudeHomeServer.{Vertical}/` (сверено 2026-09-22: Backgrounds…Yandex), сторожа `backend/ClaudeHomeServer.Tests/Services/SubsystemBoundaryTests.cs` (рефлексия + `BoundaryIlScanner.cs` IL) и `SubsystemBoundaryCoverageTests.cs`, состав — `Program.cs` + `Controllers/`/`Hubs/`/ядро сессий (`Services/Team/`, `Services/Backup/` в Main).
- **Актуальность:** самый свежий из ADR: раздел «Статус Этапа 5 (сверено с кодом 2026-09-22)» — сверка накануне сегодняшнего дня. В коде 32 вынесенные вертикали + `Core` + `Tray` (entry-point, не вертикаль) — ровно список ADR; Team и Backup в Main — как решено. Расхождений не найдено (покоящиеся места: «разведка 15 вертикалей (2026-09-02) в `notes/`» — путь по памяти, и `modularity-roadmap-2026-09.md` ADR сам помечает мёртвой ссылкой).

## ADR-015. Зоны профилей CLI и правила их синхронизации

- **Статус:** «Предложено (решение на бумаге; реализация — отдельными задачами по этапам §8)», 2026-09-02. [ADR-015](../adr/ADR-015-cli-profile-sync-zones.md)

- **Отвергнуто:** наивное зеркало без манифеста (снесло бы ручные правки ADR-011 и раскладку самого CLI); зеркало по всему профилю (`projects/` — единственное, что бэкапится, + `plugins/`); полный отказ от синка с хоста (профили превратились бы в «чужой Claude»); двусторонний синк (полтора десятка профилей пишут в один источник без разрешающей стороны); пересоздание профиля (потеря `projects/` и креденшалов = перелогин); симлинки (права `SeCreateSymbolicLink` на Windows, не работают в песочнице); «всё общее в `--settings`» (покрывает только ключи, в песочнице не ставится).
- **Реализация:** `backend/ClaudeHomeServer.Llm/LlmProviderRegistry.cs` — `SyncUserProfile`/`SeedDefaultWorkflows`/`EnsureInstalledPluginsEnabled` (синк на ходе) и `NormalizeAll`/`AdoptProfileFiles`/`SyncTrashStore` (нормализация §5.4, `LlmProviderRegistry.cs:643+`), манифест `ProfileSyncManifestStore`; тесты `LlmProviderRegistryTests.cs:887+`, `BackupPathsTests.cs:78`; рантайм-слой — `ClaudeRuntimeSettings.cs` (вертикаль Llm), второй корень — `DockerProcessRunner.cs` (не затронут ADR).
- **Актуальность:** решение реализовано (манифест, усыновление, корзина, рубильник, нормализация — в коде), но шапка ADR так и не обновлена: «решение на бумаге» — не так, этапы §8 в коде есть. Разошлись пути «Связанных артефактов»: `LlmProviderRegistry.cs`/`ClaudeRuntimeSettings.cs` переехали из `backend/ClaudeHomeServer/Services/Llm/` в вертикаль `ClaudeHomeServer.Llm`. Follow-up «ретроспектива через 2 недели после `on`» (замер 02.09 + 14 дней = ~16.09) по коду не проверяется — это данные хоста.

## Без номера: «Специальности» — только настройки роли

- **Статус:** принято 25.08.2026 (волна 4 «Персонализированные специальности»). [specialties-personalization-review](../adr/specialties-personalization-review.md)
- **Решение:** персонализация подписей роли отменяется: название/описание берутся из каталога в одном виде на всех слоях; персонализируются только настройки роли (модели по уровням, пресеты секций промпта, типовые умения); состав каталога фиксирован — 14 ролей, оркестрация стоит на их ключах.
- **Отвергнуто:** словарь слоя с владельческими подписями; «эффективные» подписи рядом с системными в ответе `/api/specialties`; серверная валидация длины текста роли; отдельный фич-флаг — подпись роли это машинный контракт, владельческое имя лишь расхождение без пользы для маршрутизации.
- **Реализация:** `backend/ClaudeHomeServer.Core/Services/SpecialtyCatalog.cs` (14 ролей + «Не задана»), `backend/ClaudeHomeServer.Llm/SpecialtySettingsStore.cs`, `backend/ClaudeHomeServer/Controllers/SpecialtiesController.cs`, `backend/ClaudeHomeServer/Services/Team/TeamPlanningService.cs`, фронт — `frontend/src/features/personas/`.

## Без номера: порядок резолва модели, классы ошибок фолбэка, защита от зацикливания

- **Статус:** Принято, 2026-08-04. [model-resolution-and-fallback](../adr/model-resolution-and-fallback.md)
- **Решение:** единая цепочка резолва из пяти уровней (явная модель сущности → правила сущности/пресеты → специальность персоны → место каталога → слот; второй точки истины нет, слот разворачивается только в `UserModelTierResolver`); фолбэк запускают только ошибки ДОСТАВКИ пяти классов (RateLimit, UsageLimit, ProviderError, Unreachable, ContextOverflow) по классификатору `TurnErrorClassifier` на строковом `api_error_status` (инвариант паритета «статус ↔ текст», неизвестное = fail-closed); порядок: тихая ротация подписок того же пула (уровень 1, без маркера в ленте) → шаги цепочки (пресет/тир) → честная ошибка; анти-циклы: пара «модель × подписка» — не более одного раза за ход, жёсткий потолок 5 видимых подмен.
- **Отвергнуто:** фолбэк на «контентные» ошибки (невалидный JSON, refusal — это качество, не доставка, подмена маскирует баг); «автонастраиваемый уровень 2 — автоподбор модели-эквивалента по `Enabled`» (сам ADR актуализирован 2026-08-08: уровень 2 удалён, остался порядок из ADR-007 §4); повторение той же модели при `ContextOverflow` (окно — свойство модели, не аккаунта) — но шаг по цепочке к бóльшему окну да, с наблюдением реальной ёмкости (`ContextCapacityRegistry`); «строгий» читатель маршрута (fail-closed на чтении обрывает живой фон).
- **Реализация:** вертикаль `backend/ClaudeHomeServer.Llm/`: `ModelAssignmentResolver.cs`, `UserModelTierResolver.cs`, `TurnErrorClassifier.cs`, `ClaudeSubscriptionPool.cs` (Pick/MarkExhausted/MigrateProvider), `FallbackLlmSessionAdapter`, `ContextCapacityRegistry.cs`; настройки — `SpecialtySettingsStore`/`FallbackSettingsStore` (там же); ADR-012.
- **Актуальность:** ядро решения в силе (цепочка, пять классов, тихий уровень 1, потолок 5). Разошлось: (1) ADR-007 §3/§4.1, актуализированный сам ADR-007, и (2) файл стора: ADR описывает `data/model-selection.json` (global/owners, specialties/presets/fallback) — этих ключей в коде больше нет, настройки живут в `data/specialty-settings.json` (ADR-012, `SpecialtySettingsStore.cs`) + `data/model-fallback.json` (`FallbackSettingsStore.cs`). Названные классы (`ModelAssignmentResolver`, `UserModelTierResolver`, `TurnErrorClassifier`, `ClaudeSubscriptionPool`, `FallbackLlmSessionAdapter`, `ContextCapacityRegistry`) сейчас живут в вертикали `ClaudeHomeServer.Llm`.

## Что разошлось с кодом

Список только тех ADR, где сверка (2026-09-23, по коду, а не по ощущению) нашла расхождение.
Один системный паттерн встречается в большинстве пунктов: **фича дожилась до снятия флага**
(`chat-watchdogs`, `link-reader`, `project-backgrounds`, `change-dossiers`) — в ADR она
описана как «за флагом (Default: false, Stage: dev)», а флаг в каталоге/`FLAGS` больше нет.

  говорят о флаге `chat-watchdogs` (Default: false, Stage: dev) — флаг снят 2026-09-01,

  `createdByMe` в `TaskStatusTriggerSource` не нашлось.
