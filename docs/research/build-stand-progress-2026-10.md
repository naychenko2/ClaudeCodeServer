# Прогресс сборки и подъёма дев-стенда в чате — разведка и план (2026-10-03)

Вопрос: как показать в чате прогресс, когда агент **собирает** проект (`dotnet build`,
`npm run build`) и **поднимает дев-стенд** (`dotnet run` и ожидание порта). Сейчас это обычный
Bash, и на карточке видны только живая точка и таймер. Опора — готовый `run_tests`
(вертикаль `ClaudeHomeServer.TestRuns`, разведка [test-progress-2026-10.md](test-progress-2026-10.md),
канал `tool_progress` — [tool-progress-2026-10.md](tool-progress-2026-10.md)). Код не писали.

Замеры сделаны на живом 2026-10-03 в отдельном worktree HEAD `72598efe`: .NET SDK 10.0.202,
vite 8.0.16 (rolldown), 16 ядер, Windows-хост. Вывод снимался без TTY, как его увидит сервер.
Каждой строке ставилась метка времени прихода.

## 1. Сборка: что даёт `dotnet build`

Цель — `backend/ClaudeHomeServer/ClaudeHomeServer.csproj`, то есть то же, что собирает
`dotnet run` стенда. Решение `ClaudeHomeServer.slnx` состоит из 65 проектов. Замыкание
`ProjectReference` главного проекта — 40 проектов.

| Прогон | Время | Строк вывода | Строк `X -> …dll` |
|---|---|---|---|
| холодный (чистый worktree, с restore) | 77,6 с | 49 | 40 |
| no-op сразу следом | 18,9 с | ~49 | 40 |
| no-op с `-v:n` | 12,5 с | 1334 | 40 |
| инкремент в основном дереве после чужих правок | 35,9 с | 49 | 40 |

Что видно в выводе по умолчанию (minimal):

- **Строка `  Проект -> путь.dll` печатается на КАЖДЫЙ проект замыкания**, в том числе на
  актуальный, ничего не перекомпилирующий. Это честный счётчик «N из M проектов».
- Restore — строки `Determining projects to restore…` и `Restored …`, первые ~3 с. Отдельный
  этап не нужен, это часть сборки.
- **Ошибки** — строки `error CS…`. Разбор `VsTestConsoleParser.BuildErrors` из `run_tests`
  годится как есть.
- **Процент по числу проектов врёт.** Холодный прогон: 39 из 40 проектов готовы к 50-й секунде,
  а последний (сам `ClaudeHomeServer`, где лежат почти все `.cs`) идёт ещё 27 с, это 35% времени.
  Хронология: `ConPtyBridge` 8,6 с → `Core` 14,9 с → пачка вертикалей 20–38 с → `Llm` 45,4 с →
  остальные 47–50 с → `ClaudeHomeServer` 77,7 с. Счётчик «39 из 40» на полосе 97% повиснет на
  треть сборки.

Откуда взять M (общее число):

- **Из прошлой успешной сборки той же цели в том же дереве** — точно: строк `->` столько же, их
  печатают и актуальные проекты. Её же хронология даёт весовой процент: доля прошлого времени, к
  которой был готов последний завершённый проект. Для примера выше «39 из 40» ≈ 64%, а не 97%.
- **Первый раз** (прошлого прогона нет) — обход `ProjectReference` по XML. Это оценка: у главного
  проекта 41 ссылка против 40 строк `->`. `ConPtyBridge` идёт с `Condition="'$(OS)' == 'Windows_NT'"`,
  `StubModule` с `ReferenceOutputAssembly="false"`, а условий MSBuild сервер не вычисляет. Подпись
  «≈12 из 40», процент пунктиром с потолком 90, пока не готов последний проект.
- Точное M до сборки умеет только сам MSBuild (`-graph`, `-getItem`), но это лишний прогон
  оценки ценой в секунды. Не стоит.

Чего НЕ брать:

- **`-v:n`** — 1334 строки против 49. Даёт маркеры старта `Project … is building … on node N`, но
  сборка параллельная (16 узлов), и «сейчас собирается X» — это пять проектов сразу. Шум без пользы.
- **Terminal logger** (`--tl:on`) — живой прогресс только перерисовкой ANSI на TTY. Без TTY он
  выключается сам, а принудительный разбирать — то же, что `line`-репортер Playwright: хуже.
- **binlog** (`-bl`) — структурный, но читается после конца сборки, не живьём. Годится разве что
  артефактом для разбора, на прогресс не работает.
- Свой `-logger:` (сборка-плагин MSBuild) даёт точный старт и конец проекта, но это код, который
  нужно доставлять в песочницу и на устройство. Строк `->` хватает.

## 2. Сборка: что даёт `npm run build`

У нас `build` = `tsc -b && vite build && npm run build:notes && build:spend && build:image-editor
&& build:architecture` (каждый подмодуль — `cd modules/X && npx vite build && node -e …`).
Полный прогон — 190,8 с:

| Этап | Время | Что видно в выводе |
|---|---|---|
| `tsc -b` | 0,5 → 50,5 с | **ничего**: 50 с тишины, при ошибке — строки `error TS…` |
| `vite build` (основной) | 50,5 → 95,3 с | `vite v… building…` → **одной строкой в конце** `transforming...✓ 5826 modules transformed.` (61,8 с) → `rendering chunks...` → `computing gzip size...` → `✓ built in 44.85s` |
| второй env основного (`59 modules`) | 95,4 → 96,9 с | то же |
| `build:notes` / `spend` / `image-editor` / `architecture` | по ~20 с | строка `> frontend@0.0.0 build:notes`, дальше то же, что у vite |

- **Живого счётчика модулей без TTY нет.** «transforming N modules» приходит одной строкой уже
  ПОСЛЕ трансформации, а на TTY это перерисовка. Точного процента у vite нет.
- **Этапы видны точно.** npm эхом печатает каждый вложенный скрипт (`> frontend@0.0.0 build:notes`),
  vite печатает `building` и `✓ built in`. Число этапов известно ДО старта: это разбор строки
  `scripts.build` по `&&` из `package.json`. Подпись «vite build · этап 2 из 6», процент — по
  весам прошлого прогона (как у dotnet), без него — равными долями пунктиром.
- Внутри этапа vite — три под-этапа (`transforming` → `rendering chunks` → `computing gzip size`),
  годятся для подписи. Основное время уходит на `rendering chunks`: 63 → 95 с.
- Ошибка DTS Module Federation в замере — артефакт junction на `node_modules` пробного дерева, к
  делу не относится. Ошибки сборки — `error TS…` (tsc) и `[vite]:`/`✗ Build failed` (vite).
- ANSI в выводе rolldown есть даже с `NO_COLOR=1` (предупреждения `INVALID_ANNOTATION`): перед
  разбором режем ESC-последовательности.

## 3. Подъём стенда

### Что уже есть: `DevServerService` (подсистема «Сервисы»)

Сервер **уже умеет** запускать дев-серверы проекта: `DevServerService.StartAsync`
(`ClaudeHomeServer.ProjectServices/…/DevServerService.cs:149`). Запуск идёт через
`ILauncherFactory.ForProject`, что дальше:

- **Готовность** — порт известен (из конфига или из stdout по `PortRegex`) И принимает TCP;
  ждёт **до 30 с** (60 × 500 мс). Не дождался — `error` с хвостом лога, и процесс гасится.
- **Реестр** в памяти, ключ `projectId:serviceId`, владелец — пользователь, **не чат**. Логи идут
  по SignalR в панель, превью — прокси `/preview/{projectId}/**` на порт активного сервиса.
- **Кто гасит**: кнопка «Стоп» в панели, остановка бэкенда, уборщик мёртвых и зависших раз в
  минуту. Конец хода, удаление чата и «Стоп» хода стенд **не трогают**.
- **Порты**: явный из конфига, иначе `autoPort` — свободный от ОС; в песочнице — пул
  `Sandbox:PortRangeStart=42000`/`PortRangeSize=20`. **Запрета на 80/8080 нет** и белого
  диапазона нет.
- **Песочница**: `DockerProcessRunner`, порт из пула. **Локальный проект**: группа `FileBound`
  исполняется на устройстве, серверный `PreviewController` отказывает, у агента устройства своя
  копия той же вертикали.
- **MCP-инструментов нет**: агент не может ни запустить сервис, ни увидеть его, ни погасить.
  Только человек кнопками.

### Замер: время старта нашего стенда

`dotnet run --no-build --project ClaudeHomeServer -- --urls http://127.0.0.1:5593` в Development:
**`Now listening` через 2,3 с, HTTP 200 на `/` через 2,6 с.** Значит, подъём стенда — это
практически целиком сборка (19–78 с), а запуск и ожидание порта занимают секунды.

### Две находки по ходу замера (обе — реальные дефекты «Сервисов»)

1. **`ASPNETCORE_URLS` из окружения стенд игнорирует.** Первая попытка с
   `ASPNETCORE_URLS=http://127.0.0.1:5593` легла `Failed to bind to address http://0.0.0.0:5000`,
   вторая с `--no-launch-profile` молча поднялась на **:5000** вместо :5593. Причины две, и обе
   выше env по приоритету: `applicationUrl` профиля `launchSettings.json` (`dotnet run` его
   применяет: `Using launch settings from …`) и ключ `"Urls": "http://0.0.0.0:5000"` в
   `appsettings.Development.json`. Работает **только аргумент `--urls`** (командная строка в
   конфигурации ASP.NET старше всех). А `DevServerService` передаёт порт именно через
   `ASPNETCORE_URLS` (`DevServerService.cs:198-205`) и затем ждёт на `fixedPort`. Для dotnet-сервиса
   в песочнице, где порт обязан быть из пула, или с `autoPort` это значит: приложение слушает своё,
   а сервис ждёт чужой порт 30 с и падает «Таймаут: сервис не начал слушать порт». Хост под
   Windows проверен, песочница — по коду, вживую не проверено.
2. **30 с ожидания мало для `dotnet run` с холодной сборкой** (78 с у нас): сервис из
   `launchSettings` (`dotnet run --project X --launch-profile Y`, `ProjectServiceDiscovery.cs:401`)
   на чистом дереве гарантированно уходит в `error`, и его процесс гасится посреди сборки.

Обе стоит завести отдельными дефектами независимо от этой фичи.

### Что делать с процессом после «готов»

Стенд — долгоживущий процесс, и это главный довод за серверный инструмент: **фоновая Bash-команда
агента умирает вместе с процессом CLI** (ADR-013), то есть стенд, поднятый `dotnet run &`, живёт
не дольше хода-двух. Предложение:

- **Стенд живёт после ответа инструмента** и регистрируется в том же реестре `DevServerService`.
  Он виден в панели «Сервисы» (логи, превью, внешняя ссылка, кнопка «Стоп») — ни второго реестра,
  ни второго механизма гашения.
- **Владелец — проект и пользователь, как у панели.** Запись помнит чат-инициатор (только для
  подписи «поднят из чата X»): гасить стенд по концу хода нельзя, им пользуется следующий ход
  (e2e, ручная проверка человеком).
- **Гасят**: `stop_stand` агента, «Стоп» в панели, остановка бэкенда, уборщик. Повторный
  `start_stand` того же сервиса возвращает уже живой (`StartAsync` так и делает). **Автогашение
  простоя** (например, 2 ч без запросов через прокси и без вызовов) — отдельным этапом, после того
  как увидим, копятся ли стенды.
- **«Стоп» хода во время подъёма** гасит и сборку, и стартующий процесс (обрыв HTTP-вызова = `ct`,
  как у `run_tests`). После «готов» «Стоп» хода стенд не трогает.

### Порты

- **Всегда запрещены 80, 443, 8080** (боевой инстанс и Dify) — отказ до запуска, независимо от
  конфига сервиса. Для `autoPort` на хосте выбирать из `55xx–56xx`, а не любой свободный от ОС:
  та же конвенция, что у людей, и мимо портов чужих стендов. В песочнице — пул, как сейчас.
- **Порт навязывается аргументом `--urls`, а не env** (находка 1) для dotnet-сервисов;
  `PORT`/`ASPNETCORE_URLS` в env оставить для node-фреймворков.
- **Фактический порт сверяется со строкой `Now listening on:`** (у vite — `Local: http://…`):
  приложение назвало другой порт — честный отказ «слушает :5000 вместо :5593», а не 30 с ожидания.
- Занят чужим процессом — отказ с подсказкой (`autoPort` или другой порт). **Чужое не гасить**:
  `StopExternalAsync` с подтверждением остаётся только кнопкой человека.

### Готовность

TCP-проверка уже есть (`LoopbackResolver.IsListeningAsync`). Сверху — необязательный
`health_path` (например `/` или `/health`): **любой HTTP-ответ, включая 401/404, — стенд жив**,
как у пробы стенда Playwright (`TestRunService.ProbeStandAsync`), без прокси. Ожидание порта —
отдельный параметр (по умолчанию 120 с вместо 30), раз сборка вынесена из него.

## 4. Форма: отдельные инструменты, а не `kind=build` у `run_tests`

Почему НЕ `run_tests kind=build`:

- Другая форма результата (ни счётчиков тестов, ни `Totals`), другая подсказка в промпте, и
  модель, выбирающая «как собрать», не ищет инструмент с `tests` в имени.
- Стенд — долгоживущий процесс с другим жизненным циклом. Втиснуть его в «прогон» — значит
  сломать инварианты движка («одно дерево — один прогон», гашение по выходу).

Что предлагаю — **новый статический тулсет `dev`**, три инструмента:

| Инструмент | Что делает |
|---|---|
| `build` | `kind=dotnet` (target — проект/решение) или `kind=npm` (script — имя скрипта из `package.json`, по умолчанию `build`; target — каталог). Прогресс, сводка ошибок, лог в `.cc-attachments/build-runs/{id}/` |
| `start_stand` | `service` — id сервиса из «Сервисов» (как в панели) ИЛИ dotnet-проект/npm-скрипт; `port`/`auto_port`, `health_path`. Этапы: очередь → сборка → запуск → готов. Возвращает URL, порт, id сервиса, хвост лога при отказе |
| `stop_stand` | гасит стенд, поднятый продуктом (`service`); чужой процесс не трогает |

Отдельный статус-инструмент не нужен: `start_stand` уже поднятого сервиса возвращает его порт
сразу.

- **Инвариант `tools/list`**: состав тулсета постоянен, гейты — на вызове (`ReadOnly`/без Bash,
  локальный проект, выключенная вертикаль), как у `TestsToolset`.
- **Подсказка в промпте** — системной секцией, как `TestRunsHintContributor`: «`dotnet build`,
  `npm run build` — инструментом `mcp__dev__build`; дев-стенд поднимай `mcp__dev__start_stand`, а
  не `dotnet run &` в Bash — фоновый процесс Bash умрёт вместе с CLI, а стенд инструмента живёт
  дальше и виден в панели „Сервисы“». Секцию `run_tests` дополнить: «e2e против стенда —
  `start_stand`, его URL передай в `env.PLAYWRIGHT_BASE_URL`».
- Отдельный сервер, а не новые инструменты в `tests`: `mcp__tests__build` модель читает как
  «сборка тестов». Цена — ещё один узел `http` в конфиге CLI и фильтр `Keep("dev")`.
  Однокоренных имён нет (`build` / `start_stand` / `stop_stand`).
- Авто-разрешение в режиме «Авто» — как у `run_tests`. `MCP_TOOL_TIMEOUT` (600 с) и SSE-пульс
  транспорта (`McpTransportController`, общий для всех тулсетов) уже есть, доделывать нечего.

### Движок

Общую часть `TestRunService` выносим в конвейер фаз **внутри той же вертикали**
(`ClaudeHomeServer.TestRuns`, переименовывать проект не обязательно). Туда идут
`RunPhaseAsync` (старт со своим `TurnId`, вычитка, гашение дерева), захват гейта с подписью
очереди, серверный потолок, папка артефактов, блокировка «одно дерево — одна сборка» (общая с
тестами: `dotnet build` и `dotnet test` в одном дереве дерутся за `obj/bin`). Разборщики своих
видов — рядом: `DotnetBuildProgress` (строки `->`, M из памяти прошлых прогонов или из XML) и
`NpmBuildProgress` (этапы по `&&`, маркеры vite). Стенд — `DevServerService` плюс фаза сборки из
того же конвейера.

**Шов между вертикалями**: `start_stand` живёт в тулсете (Main), сборку берёт у `TestRuns`, а
запуск — у `ProjectServices`. Вертикали друг на друга не ссылаются (правило ADR-014), склейка — в
тулсете, как сейчас у `TestsToolset`.

`npm` на Windows — это `npm.cmd`, то есть `cmd.exe /c`. Тот же разбор, что у vitest: запускать
`node <npm-cli.js> run <script>` или разрешить только имя скрипта по `^[A-Za-z0-9:_.-]+$`, без
аргументов от модели. Сам скрипт — код репозитория, его `&&` и `cd` исполнит оболочка npm, это
нормально.

### Формат прогресса

| Фаза | dotnet `build` | npm `build` | `start_stand` |
|---|---|---|---|
| Очередь | «ждёт очереди сборок (занято N)» | то же | то же |
| Сборка | «12 из 40 проектов», процент по весам прошлого прогона (`Exact` — нет, пунктир), первый раз — «≈12 из 40» | «vite build · этап 2 из 6», под-этап vite в подписи | как dotnet / npm |
| Запуск | — | — | «запуск · жду порт 5593» |
| Готов | итог: «собрано за 1:18, 0 ошибок» | то же | «готов: http://127.0.0.1:5593 · 0:04» |

`TestRunStages.LabelOf` дополняется этапами `start` → «запуск» и `ready` → «готов». `Totals` у
сборки нет — карточке нужен итог без счётчиков тестов: строка этапов плюс текст результата.
Ссылка «открыть в Сервисах» на карточке стенда — по желанию.

## 5. Риски

- **Сироты.** Сборка — `Track = true` и свой `TurnId`, как у `run_tests`. Стенд в
  `DevServerService` запускается без `Track`: после краша бэкенда он живёт и находится
  `DevServerPortMemory` как `external`, гасится человеком с подтверждением. Это приемлемо и
  совпадает с нынешним поведением панели. Стенды, копящиеся от агентских подъёмов, закрывает
  автогашение простоя (этап 4).
- **Порты.** Чужой стенд на том же порту (два чата, дев-стенд :5000 на машине) — отказ с
  подсказкой, а не убийство. Сломать бой нельзя: 80/443/8080 запрещены жёстко.
- **OOM-гейт.** Сборка — `Heavy`, держит слот гейта. Запущенный стенд — нет: это резидент, а не
  всплеск. На Linux его держит потолок `ccs-agents.slice`, но стенды копятся в нём же — ещё один
  довод за автогашение. Память простаивающего стенда не замеряли.
- **Таймауты CLI.** Сборка — под тем же потолком 540 с, что `run_tests`. `start_stand` = сборка
  плюс до 120 с ожидания порта — общий потолок тоже 540 с, ожидание порта входит в него.
  Холодная сборка с очередью за чужой может не уложиться — тогда отказ с текстом «повтори:
  сборка дошла до N из M, следующий вызов будет инкрементальным».
- **Модель продолжает собирать Bash'ем.** Прогресса просто нет, как сейчас, регресса не будет.
  Принуждение хуком — не в первой версии, как и у тестов.
- **Порт навязан, а приложение слушает своё** (находка 1) — лечится `--urls` и сверкой с
  `Now listening on:`; для неизвестных рантаймов остаётся таймаут с хвостом лога.
- **Локальные проекты.** В первой версии отказ с текстом («стенд локального проекта — панелью
  „Сервисы“»): `DevServers` исполняется на устройстве, и серверный вызов должен ехать через
  канал устройства. Это отдельный этап после того, как обкатаем серверный.
- **Конкуренция за `obj/bin`** с параллельным Bash-`dotnet build` агента в том же дереве — то же,
  что у тестов: блокировка своих, предупреждение в описании инструмента.

## Рекомендация

Начать с **этапа 0** — это живые дефекты панели, и без них `start_stand` унаследует ожидание
чужого порта. Дальше **сборка** (этапы 1–4): дёшево, полезно сразу и обкатывает тулсет и
подсказку. **Стенд** (этап 5) — следом, поверх `DevServerService`, а не своим реестром. Процент
сборки честно показывать как оценку по весам прошлого прогона, точным — только счётчик «N из M
проектов» и номер этапа npm.
