# ТЗ команде ядра AI Home: LLM-канал для внешних модулей

- Статус: **готово к передаче** (проект AI Home, `C:\Sources\ClaudeCodeServer`; сессия «Платформа модулей AI Home»).
- Основание: контракт `integration-contract.md` **§10, v1.2** (лежит рядом, неотъемлемая часть ТЗ — все форматы, коды ошибок и лимиты определены там).
- Заказчик: команда модуля «Семейный бюджет» (проект «Личные финансы»). Первый потребитель — `family-budget`; канал проектируется универсальным под будущие модули.
- Приёмка: эталонным модулем `module-echo` (заглушку расширяет заказчик) и conformance-проверками **CT-12…CT-15** из контракта §9.

## Зачем

Решение владельца системы: **внешние модули не держат собственных ключей к LLM-провайдерам.** Модели — ресурс ядра: там адаптеры провайдеров, локальная модель, подписки и, главное, настройка «какая модель обслуживает какой тип задачи», сделанная в одном месте и на всю систему. Модуль приносит задачу, ядро решает, чем её считать.

Сегодня это невозможно: HTTP-поверхности у механизма фоновых задач нет, а обратного канала «модуль → ядро» контракт не содержит вовсе — модулю адресован единственный эндпоинт, публичный JWKS. Модульный токен RS256 работает только на префиксе `/api/modules/**`, на `/api/*` ядра стоит HMAC-валидация, то есть `401` по определению.

Практический эффект для первого потребителя: без канала автокатегоризация операций бюджета не работает вовсе — правила разбирают часть выписки, остальное уходит пользователю в «требует подтверждения».

## Порядок исполнения

**R11 → R12** (граница и безопасность; проверяется голым HTTP без UI) → **R10** (каталог и настройка модели) → **R13** (учёт). R10 можно вести параллельно R11/R12 — пересечение только в манифесте.

## Регрессионные требования (обязательные)

1. Все изменения — **аддитивные**: встроенные 41 действие, их маршруты и настройки в `local-actions.json` продолжают работать без изменений; HMAC-аутентификация `/api/*` не затронута; `/api/modules/**` ведёт себя ровно как в v1.1.
2. Прогон тестов ядра (`ClaudeHomeServer.Tests`) — зелёный, включая существующие `Module*`-тесты.
3. Ручной smoke: настройка модели любому встроенному действию из UI по-прежнему применяется без рестарта; одна сессия Claude со встроенными MCP.

## Вне объёма этого ТЗ

- **Vision / изображения.** Механизм фоновых задач работает только с текстом, мультимодальный путь существует лишь внутри агентной сессии (`ClaudeSession.BuildImageBlocks`). Распознавание фото чеков этим каналом не покрывается — контракт §10.6 фиксирует это явно. Отдельное решение владельца, отдельное ТЗ; форма §10.3 расширяется полем вложений минором, ломать её не придётся.
- **Стриминг ответа**, многоходовые диалоги, разделение system/user.
- **Выбор модели модулем** — сознательно исключён контрактом: модуль называет ключ действия, модель выбирает владелец. Просим не добавлять «удобное» поле `model` в запрос: оно обнуляет и настройку владельца, и учёт.
- Доменная логика бюджета (что именно категоризуется и какими промптами) — сторона заказчика.
- Маскирование персональных данных в промпте — обязанность модуля, ядро на это не полагается, но и не дублирует.
