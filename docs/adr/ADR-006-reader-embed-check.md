# ADR-006: Проверка встраиваемости для панели «Чтение» (iframe-режим с MD-фолбэком)

**Статус:** Предложено
**Дата:** 2026-08-04
**Принимающие решение:** Андрей (владелец продукта)
**Реализация:** backend — Денис, frontend — Кира
**Связанные:** [ADR-005](ADR-005-link-reader-server.md) (серверная часть режима чтения — не меняется)

## Контекст

Продуктовое решение: панель «Чтение» сначала пытается показать страницу **целиком** через
sandbox-iframe без кук и креденшалов, и только если встраивание запрещено или не удалось —
молча переключается на MD-чтение через существующий `POST /api/reader/read`, показывая режим
в шапке панели.

Почему нужен серверный пре-чек, а не «попробовать iframe и посмотреть»: браузер **не сообщает**
кросс-доменному родителю, что фрейм заблокирован `X-Frame-Options` / CSP `frame-ancestors` —
`onload` срабатывает и на заблокированном фрейме, события ошибки нет. Единственный надёжный
способ узнать заранее — прочитать заголовки ответа, а это может сделать только бэкенд
(браузерный `fetch` на чужой origin заголовки не отдаст из-за CORS).

Что уже есть и на что контракт опирается:

- `ReaderController` (`POST /api/reader/read`, `GET /api/reader/image`) — конвейер ADR-005,
  за флагом `link-reader`.
- `SsrfGuard.CheckAsync` — общий периметр локальных адресов, fail-closed.
- Клиент `link-reader` — `UseCookies=false`, `AllowAutoRedirect=false`, `UseProxy=false`,
  `ConnectCallback` с SSRF-фильтром (ADR-005 §2).
- `ReaderQuotaService` — 30 чтений/мин и 2 одновременных на владельца.
- `readerEligibility.ts` — клиентское правило «у какой ссылки есть кнопка-компаньон».
- Прецеденты sandbox-iframe: `WidgetView.tsx` (наш контент, `allow-scripts allow-forms
  allow-modals`), `PreviewView.tsx` (наш прокси, есть `allow-same-origin`). Ридеру равняться
  на первый, не на второй: контент чужой, модель доверия другая.

## Решение

### 1. Контракт эндпоинта проверки

```
POST /api/reader/embed-check
{ "url": "https://example.com/article" }
        |
        v
200 { "embeddable": true }
200 { "embeddable": false, "reason": "frame-denied" }
401 / 403 (нет флага link-reader) / 429 (квота)
```

- `[Authorize]` + флаг `link-reader` гейтит **эндпоинт**, как у `/read`.
- URL — **в теле POST, не в query**: те же лог-причины, что в ADR-005 §1 (адрес страницы не
  должен попадать в стандартный лог запросов и в реверс-прокси).
- Сервер делает **GET с `ResponseHeadersRead`** тем же клиентом `link-reader` и тем же
  конвейером рубежей 1–4 из ADR-005 §2: разбор URL (схема http/https, порт 80/443, без
  userinfo, `#fragment` отброшен), `SsrfGuard`, редиректы ≤ 5 с перепроверкой схемы, порта
  и адреса **на каждом хопе**. Тело ответа не читается — соединение закрывается после
  заголовков. HEAD не используем: у заметной доли сайтов он отвечает 405 или другими
  заголовками, чем GET.
- Таймаут — 5 с (только заголовки, ADR-005 §5). Квота: `TryAcquireRate` — **да** (счётчик
  общий с `/read`: квота существует ради IP-репутации сервера, а это исходящий запрос);
  слот `TryAcquireConcurrency` — **нет** (запрос без тела, короткий).

**Семантика вердикта** — по заголовкам **финального** ответа цепочки редиректов:

| Условие | Вердикт |
|---|---|
| финальный статус не 2xx | `false`, reason — код ADR-005 §6 по статусу (`auth-required`, `not-found`, `server-error`, `blocked-by-site`…) |
| сбой самой проверки (SSRF, DNS, таймаут, >5 редиректов…) | `false`, reason — соответствующий код ADR-005 §6 |
| `Content-Type` не `text/html` / `application/xhtml+xml` | `false`, reason `not-html` (в sandbox-iframe без plugins PDF и прочее не отрисуются) |
| `X-Frame-Options: DENY \| SAMEORIGIN \| ALLOW-FROM …` (любое валидное значение) | `false`, reason `frame-denied` |
| `X-Frame-Options` с невалидным значением (`ALLOWALL`, мусор) | заголовок игнорируется — как делают браузеры; строже браузера быть не нужно |
| CSP `frame-ancestors` (enforced-заголовок): `'none'` или явный список источников | `false`, reason `frame-denied` |
| CSP `frame-ancestors *` (или эквивалентные схемные вайлдкарды `http:`/`https:`) | не запрет |
| `Content-Security-Policy-Report-Only` | игнорируется — он не блокирует |
| ничего из перечисленного | `true` |

Явный список источников в `frame-ancestors` **не матчим** со своим origin: у инстанса их
несколько (`localhost:5173`, `:5000`, прод-домен за прокси), чужой сайт нас в списке не
назовёт никогда, а консервативный `false` всегда даёт рабочий MD-фолбэк. По той же логике
`ALLOW-FROM` (устаревший) — сразу `false`. `frame-ancestors` в `<meta http-equiv>` браузеры
игнорируют по спецификации, поэтому headers-only проверка корректна — тело читать незачем.

Поле `reason` — для телеметрии и отладки; **фронт на него не ветвится**: любой
`embeddable: false` → молчаливый переход к `POST /api/reader/read`, который сам покажет
человеку правильную ошибку своими кодами, если и MD-путь не пройдёт.

### 2. Последовательность на фронте

```
клик по кнопке-компаньону (ссылка прошла readerEligibility)
  |
  +- страница http:// при приложении на https://
  |    -> сразу MD-режим (mixed content: браузер
  |       такой iframe заблокирует сам, чек бесполезен)
  |
  +- POST /api/reader/embed-check { url }
       |
       +- embeddable: true  -> sandbox-iframe (раздел 3)
       |     + watchdog: не отрисовался за N секунд
       |       -> молча в MD-режим
       +- embeddable: false -> POST /api/reader/read
                               (существующий, без изменений)
```

- В шапке панели (`ReaderHeaderBar`) виден текущий режим — «страница» или «чтение» — и ручной
  переключатель: серверный вердикт авторитетен для заголовков, но не всеточен (бот-щит может
  ответить серверу иначе, чем браузеру пользователя), поэтому человек всегда может уйти в MD.
- TOCTOU (сайт сменил заголовки между проверкой и загрузкой фрейма) закрыт самим браузером:
  он заблокирует рендер, watchdog переключит в MD. **Проверка — оптимизация UX, а не рубеж
  безопасности; безопасность держит sandbox.**
- Переход по ссылкам **внутри** iframe остаётся во фрейме (навигация внутри sandbox
  разрешена) и рубежи сервера не проходит — это эквивалент обычного сёрфинга браузером
  пользователя, см. приватностную оговорку в разделе 4. Стек «Назад» панели на внутреннюю
  навигацию фрейма не реагирует.

### 3. Атрибуты sandbox-iframe — белый список

```html
<iframe
  src={url}
  sandbox="allow-scripts"
  referrerpolicy="no-referrer"
  credentialless
  allow=""
/>
```

| Атрибут | Зачем |
|---|---|
| `sandbox="allow-scripts"` | без скриптов не отрисуется большинство современных сайтов; всё остальное из sandbox-набора **не включается** |
| `referrerpolicy="no-referrer"` | сайт не узнаёт, откуда пришли — то же правило, что у картинок статьи в ADR-005 §1 |
| `credentialless` | second line of defense (Chrome): даже при ошибочном появлении `allow-same-origin` куки не вернутся; где не поддержан — безвреден |
| `allow=""` | пустая permissions policy: камера, микрофон, геолокация, автоплей — запрещены явно |

**Запрещено навсегда** (появление любого из этих токенов — дефект, а не настройка):

- `allow-same-origin` — ключевой запрет. Без него у документа opaque origin: браузер **не
  прикладывает куки и креденшалы** ни к навигации, ни к сабресурсам, storage недоступен —
  это и есть техническая реализация обещания «без кук и креденшалов». С ним же страница
  получает свой origin целиком (куки, localStorage, fetch с credentials) от имени
  пользователя.
- `allow-forms` — формы = отправка данных на чужой сайт из нашей панели; для чтения не нужны.
  (У виджетов `allow-forms` есть — но там контент наш.)
- `allow-popups`, `allow-popups-to-escape-sandbox` — попапы чужой страницы не нужны;
  «Открыть в браузере» — своя кнопка в шапке.
- `allow-top-navigation` (и `*-by-user-activation`) — чужая страница не должна уводить всё
  приложение.
- `allow-modals`, `allow-downloads`, `allow-pointer-lock`, `allow-presentation` — спам
  `alert()`, самопроизвольные загрузки и захват указателя из чужого контента.

**Никакого моста фрейм ↔ приложение:** обработчиков `message` от этого iframe не заводим,
`postMessage` внутрь не шлём. Это продолжение инварианта ADR-005 §6 «нет пути из ридера в
контекст модели» — он распространяется на iframe-режим дословно.

### 4. Что не меняется — явно

- **`SsrfGuard` — как есть.** Диапазоны, семантика, fail-closed — без изменений; `embed-check`
  — ещё один потребитель общего guard'а, не форк и не расширение.
- **ADR-005 — как есть.** Конвейер `/read`, инварианты рендера (§ «Решение»), коды ошибок §6,
  лимиты §5, `GET /api/reader/image` — не трогаются. MD-режим остаётся и фолбэком, и ручным
  режимом.
- **Приватностная оговорка — единственная содержательная разница режимов.** В iframe-режиме
  страницу грузит **браузер пользователя напрямую**: сайт видит IP человека, исполняет свой
  JS — по приватности это эквивалент «Открыть в браузере» (минус куки и Referer), а не
  MD-чтения, где наружу ходит сервер. Плашка первого использования (ADR-005 §1) написана про
  MD-режим («страницу открывает сервер») — её текст надо уточнить под два режима; формулировка
  за Софьей, факт фиксирую здесь.

### 5. Исключения — что через embed-check не проходит вообще

Пайплайн «iframe → MD» применяется **только** к внешним http(s)-ссылкам, у которых по
`readerEligibility` есть кнопка-компаньон. Поведение всего остального не меняется:

- **Внутренние якоря приложения** (`#/…`-роуты, `#fragment` текущей страницы) — не абсолютные
  http(s)-URL, кнопки-компаньона у них нет, `embed-check` не вызывается; работают как раньше.
- **Ссылки на файлы проекта** (`resolveFileMention` в чате) — открываются `FileViewer`'ом,
  в ридер и на `embed-check` не попадают.
- **Всё, что отсекает `readerEligibility`** (локальные хосты, IP-литералы, чёрный список
  расширений ADR-005 §3), — в iframe-режим не попадает тем же фильтром: правило «у какой
  ссылки есть кнопка» общее для обоих режимов, второго списка не заводим.

## Последствия и риски

1. **Один клик может стоить два запроса квоты** (`embed-check` + `read` при фолбэке) — при
   потолке 30/мин на владельца это приемлемо; если станет тесно, поднимаем потолок, а не
   выносим `embed-check` из-под квоты.
2. **Вердикт `true` не гарантирует отрисовку** (щиты, UA-зависимые ответы, TOCTOU) — закрыто
   watchdog'ом и ручным переключателем; репорты «показало белый экран, потом переключилось»
   — нормальное поведение, не дефект.
3. **Ложные `false` невозможно отличить от честных** без матчинга origin — принято: цена
   ошибки — MD-режим, который и так был единственным до этой фичи.
4. **iframe-режим возвращает сайту IP пользователя** — см. раздел 4; это осознанный размен
   «полный вид страницы против приватности MD-чтения», выбор виден и обратим в шапке панели.

## Что проверить при реализации

- `embed-check` ходит тем же клиентом `link-reader` (без кук, без прокси, `ConnectCallback`
  с SSRF-фильтром) — тест, что хендлер общий с `/read`, а не второй экземпляр с дефолтами.
- Схема/порт/`SsrfGuard` перепроверяются на каждом хопе редиректа `embed-check` — те же
  цепочки-тесты, что у `/read` (публичный → `127.0.0.1`, публичный → `:6379`).
- `X-Frame-Options: SAMEORIGIN` и `frame-ancestors 'self'` дают `false`; `ALLOWALL` и мусор
  в XFO — `true`; `Report-Only` — `true`.
- Тело ответа не читается (`ResponseHeadersRead` + закрытие после заголовков) — 2-гигабайтная
  страница не влияет на `embed-check`.
- Sandbox-iframe в разметке ридера не содержит запрещённых токенов из раздела 3 — тест на
  литерал атрибута.
- Флаг `link-reader` гейтит `embed-check`-эндпоинт, а не только кнопку.
- Полный URL не попадает в логи (`POST`-тело, свои `ILogger` — «домен + исход + длительность»).
- Внутренний якорь и ссылка на файл проекта в чате ведут себя как до фичи (регрессионная
  проверка, Вера).
