Волна 1: профиль режима, жёсткий гейт на уровне пользователя, окна и лимиты, «Уроки» по API-ключу с голосом, онбординг правил. Код не писал, разрез сделан по чтению кода.

## Главное решение
**Ребёнок — это обычный `user` с профилем `ChildMode`, а не новая роль.** Ограничения устроены как **allow-list** с отказом по умолчанию. Перечня запретов нет и не будет.

Почему именно так:
- Роль проверяется строкой `[Authorize(Roles="admin")]` в 27 файлах, а сервисный токен хода всегда несёт роль `user` (`JwtService.cs:82-87`). Новая роль разъехалась бы с этими проверками.
- Пользовательских контроллеров около ста, и каждый месяц появляются новые. Перечень запретов протухнет на первой же новой ручке. Allow-list при этом закрыт по построению.
- Профиль проверяется **по стору** (образец — `AdminByStoreHandler`), а не по claim, так что он сразу работает и для токена хода.

## 1. Данные и связь «родитель → ребёнок»
Новое поле `User.ChildMode : ChildProfile?`. Модель лежит в Core (`Models/ChildProfile.cs`). `null` означает обычного пользователя. Поле добавочное, поэтому `BackupSchema.Version` не меняется, а `users.json` и так попадает в бэкап.

```
ChildProfile {
  bool Enabled
  List<string> GuardianUserIds        // связь с родителем; в В1 заполняет админ
  string TutorPersonaId               // закреплённая персона-репетитор, владелец — сам ребёнок
  string ProviderKey                  // запись пула подписок с ApiKey (см. §4)
  string Model                        // закреплённая модель «Уроков», например sonnet
  Dictionary<string, SpaceLimits> Spaces   // ключи: "lessons" (В1), "studio" (В2)
  decimal? DailyBudgetUsd, MonthlyBudgetUsd
  int WarnMinutes = 5
  DateTime? RulesAgreedAt; string? RulesSummary   // итог онбординга правил
}
SpaceLimits { List<TimeWindow> Windows; int? DailyMinutes }
TimeWindow  { string From "HH:mm"; string To "HH:mm"; int[]? Weekdays }
```

Кто включает режим:
- Только админ, через новую ручку `PUT /api/users/{id}/child-profile`. Ручка живёт в `UsersController` под `[Authorize(Roles="admin")]` и закрыта `AdminByStore` от вызова из хода.
- До волны 2 отдельного кабинета родителя нет (решение Андрея: «до В2 лимиты задаёт админ»).

Проверки при включении:
- `ExecutionEnvironment == container`, иначе 400. Ребёнка заводим сразу в `container`, потому что смена среды при существующих чатах запрещена.
- `ProviderKey` резолвится в запись пула с `ApiKey`, иначе 400 (§4).
- Тьютор создаётся по шаблону провижнером `ChildTutorProvisioner` по образцу `DefaultAssistantProvisioner`. Для ребёнка `DefaultAssistantProvisioner.EnsureAsync` **не создаёт** ассистента.

**Единственная точка правды** — `IChildModePolicy` в Core. Метод `For(ownerId)` возвращает `ChildPolicySnapshot?`. Реализация в Main читает `IUserStore`. Инлайновых `user.ChildMode?.Enabled` в коде не заводим, как и в случае `ProjectCapabilities`. Политика fail-closed: если профиль есть, но не читается или не проходит валидацию, `For` возвращает снимок «запрещено всё».

Почему не фич-флаг. Ограничения зависят **только от профиля**. Флаг `child-mode`, если он нужен, прячет у админа лишь интерфейс включения. Выключенный флаг не должен снимать с ребёнка ни одного запрета.

**И1-бис. Проверка при запуске хода — последний рубеж.** В точке запуска хода (`TurnLaunchContextFactory.Compose`) для детского владельца сверяются поля чата:
- `Session.PersonaId == TutorPersonaId`
- `Provider == ProviderKey`
- `Model == profile.Model`
- `ProjectId == null`
- `Mode` берётся из профиля

Если хоть что-то разошлось, ход не стартует и завершается ошибкой, без «подстановки по-тихому». Эта проверка закрывает пути, которые п.1–19 пропустят завтра.

**Правило `tools/list`.** Состав зависит только от **владельца**: профиль — свойство пользователя, а не хода. Правило CLAUDE.md так допускает («от свойств сессии — может»). Включение или выключение профиля один раз перезапустит процесс CLI, и это нормально. Отказ на вызове (п.9) нужен как глубокая оборона, если состав разъедется.

**Сторожа (обязательны, в Б2/Б3):**
- `ChildModeEndpointGuardTests`: перебирает все эндпоинты из `EndpointDataSource` хоста. Детский токен получает 403 на любом эндпоинте без `[ChildAllowed]`. Сам список `[ChildAllowed]` заморожен в тесте, так что его расширение — осознанная правка теста.
- `ChildModeMcpGuardTests`: каждый инструмент каждого тулсета реестра проверяется на детский allow-list.
- Мутацией доказать, что сторож краснеет, если снять middleware.

## 3. Лимиты
**И3. Вне окна, сверх дневного лимита пространства и сверх бюджета новый ход ребёнка не стартует.** Проверка стоит **в точке запуска хода**, а не на входах. Так она покрывает разом `SendMessage`, автопродолжение после рестарта, ретраи и фолбэк. Отказ возвращается детским текстом и ошибкой хода. Начатый ход доживает до конца: допускаем перерасход в один ход. Его ограничивают закреплённые модель и effort.

- **Окна времени.** `PersonaAutomationService.InQuietWindow` (:572-581) выносится в Core-хелпер `DailyTimeWindow`: разбор «HH:mm», переход через полночь, таймзона через `TaskDueCalculator.ResolveTimeZone` и `User.TimeZone`. Автоматика персон переходит на тот же хелпер, второй реализации не будет. Если таймзона не задана, считаем по таймзоне **инстанса**, а не UTC, иначе окно уедет на 3 часа. Это развилка для Андрея, по умолчанию — Москва из конфига.
- **Время в пространстве** считается присутствием, а не длительностью ходов: ребёнок думает между ходами. Фронт шлёт `POST /api/child/heartbeat {space}` раз в 60 с, пока вкладка видима. Сервер копит минуты в журнале `data/child-usage/{owner}.json` по дням и пространствам. Журнал — новое хранилище в `data/`, поэтому сверка с бэкапом обязательна.
- **Статус для оболочки:** `GET /api/child/status` возвращает остаток минут, конец окна и флаг «осталось ≤ WarnMinutes». Отсюда предупреждение за 5 минут и мостик в офлайн.
- **Бюджет.** Расход уже пишется per-owner (`SpendStore.Record`, `DailySpendRow`). Spend — вертикаль, поэтому гейт берёт его через **шов в Core** `IOwnerSpendReader.TodayUsd/MonthUsd(ownerId)`, а реализация живёт в `ClaudeHomeServer.Spend`. Если подсистема Spend выключена, шов равен `null`, и ход ребёнка **отказывается** с текстом «бюджет не проверить» — без бюджета не пускаем. В учёт входят ходы, TTS (`TtsController.cs:158`) и в В2 генерации.

## 4. Маршрут модели: «Уроки» только по API-ключу
**И2. Ход ребёнка никогда не идёт по подписке**, ни основной, ни из пула, ни фолбэком, ни фоновым действием.

Как это выражено. Не через слоты и пресеты: пресет — это цепочка с фолбэком, и она может увести на подписку. Решение такое:
- В `appsettings.Local.json` добавляется запись пула `ClaudeSubscriptionPool` с `ApiKey` **и без** `OAuthToken`, например ключ `anthropic-api-kids`. Это отдельный ключ API Anthropic, чтобы расход ребёнка был виден отдельно в консоли Anthropic.
- Профиль ссылается на неё через `ProviderKey`. Чат «Уроков» создаётся с `Provider = ProviderKey` и `Model = profile.Model`.
- `UserModelTierResolver` не трогаем: у детского чата модель закреплена явно, слоты ребёнка админ ставит в ту же модель для фоновых мест.

Пути к И2 и где они закрываются:

| Путь | Где |
|---|---|
| Наследуемый env процесса `CLAUDE_CODE_OAUTH_TOKEN` (`Program.cs:197-205`; чистка в `LlmProviderRegistry.cs:537-545` его **оставляет**) | Для детского хода env **вычищает** `CLAUDE_CODE_OAUTH_TOKEN` и ставит изолированный `CLAUDE_CONFIG_DIR` (`BuildOAuthCliEnv` с ApiKey, :1315). Признак едет в контексте запуска хода, нового шва не нужно. |
| Выбор подписки из пула (`ClaudeSession.cs:4619-4632`) | `ProviderKey` — запись с ApiKey, поэтому OAuth не выбирается. Если у записи нет ключа, это **отказ запуска**, а не тихий откат на родную подписку. |
| Доставка токена подписки в песочницу (`DockerProcessRunner.cs:267-271`) | Для детского владельца токен не доставляется |
| Фолбэк хода (`FallbackLlmSessionAdapter`, цепочки ADR-007) | Цепочка детского хода пуста: отказ провайдера = ошибка хода |
| Шлюз `/gw` (`UpstreamSelector.IsSubscription` :29) | У ребёнка нет локальных проектов (п.16), путь недостижим. Сторож проверяет, что детский владелец не получает `IsSubscription = true`. |
| Фоновые one-shot (`OneShotClaudeRunner.cs:107/119`, `CheapTextRunner`) | Детский владелец → локальная модель или выключено (И1 п.18) |

**Проверка в Б4, на слово не принимать.** Нужно на живом CLI подтвердить, что при наличии `ANTHROPIC_API_KEY` и отсутствии `CLAUDE_CODE_OAUTH_TOKEN` ход действительно идёт по ключу. Свидетельство — запись `api-request` в транскрипте и строка расхода в консоли Anthropic по этому ключу.

Это дёшево: промпт плюс разбор маркера плюс `notifications`. Закрывает пункт «мониторинг», без которого запускать дочку на облачной модели против правил Anthropic — пробел.

## 5. Голос и онбординг правил
- **Голос переиспользуем целиком:** `Session.VoiceMode` и `VoiceStyle` (`Session.cs:514/520`), `POST /api/tts` (`TtsController.cs:30/87`, в allow-list), секция `voice-mode` (`ClaudeSession.cs:4056`, `VoicePrompts.cs:13`), STT в браузере. Нового нет, кроме узкой ручки `PUT /api/child/chats/{id}/voice`: широкая `PUT api/chats/{id}` меняет и модель. TTS тратит деньги и попадает в бюджет.
- **Онбординг правил** — новый вид `OnboardingKinds.ChildRules` по механике `OnboardingController.user/start` (:55-87). Интервью ведёт тьютор, и в нём ребёнку объясняют правила, которые **уже выставил админ**. Ручка применения `POST /api/child/rules/agree` пишет **только** `RulesAgreedAt` и `RulesSummary`, лимиты она не меняет никогда. Аналог `apply-transcript` (:198) не переносим: тот переписывает персону.
- Пока `RulesAgreedAt == null`, пространство «Уроки» открывает только онбординг правил.

## 6. Что закладываем сейчас под волну 2
Закладываем то, что В1 и так использует или что дорого менять в формате:
- `ChildProfile.GuardianUserIds` — связь для кабинета родителя.
- `ChildProfile.Spaces` со строковыми ключами и `Session.ChildSpace` (`"lessons"`, позже `"studio"`). Ключ `studio` добавится записью без миграции; его наполнение — отдельная работа В2.
- Журнал присутствия `data/child-usage/` — источник недельной сводки (время, пространства).
- `IChildModeGate` с allow-list пар (сервер, инструмент). Гейт под «Студию» в В2 уже есть, но сам список пар в В1 пуст, а «Студия = пары `image-editor`/`local-media`» не обещано: какие инструменты безопасны, решается отдельно (фильтр выхода, квота; консультация 1df6eea5).

**Не закладываем** (швы не впрок):
- **Чтение переписки родителем.** `SessionStore.GetOwned` (:626) остаётся строгим, общего админ-обхода не будет никогда. В В2 появится отдельный метод `GetForGuardian(sessionId, guardianId)`. Он допустим только при открытом стоп-сигнале этого чата, только для `GuardianUserIds` и ставит видимую ребёнку пометку `Session.GuardianViewedAt`. Это единственный путь, и он ляжет в таблицу путей И1 В2.
- **Фильтр картинок.** В2: узел safety-checker **в шаблонах `ComfyWorkflows`** (произвольный граф запрещён инвариантом local-media), плюс проверка промпта до постановки в очередь.

## Решения (для ADR-041)
1. Ребёнок = `user` + `User.ChildMode`, новой роли нет. Включает только админ, проверка по стору.
2. Ограничения — allow-list с отказом по умолчанию по метаданным эндпоинта, методам хаба и парам (MCP-сервер, инструмент). Последний рубеж — сверка закреплённых полей чата при запуске хода.
3. Лимиты и бюджет проверяются при запуске хода. Бюджет fail-closed через шов `IOwnerSpendReader`.
4. Модель — отдельная запись пула с API-ключом. Подписка вычищается из env, песочницы, фолбэка и фона. Отказ — ошибка, а не откат на подписку.
5. Отвергнуто:
   - роль `child` — расходится с 27 строковыми проверками и сервисным токеном;
   - перечень запретов — протухает;
   - маршрут через пресеты и слоты — цепочка фолбэка ведёт на подписку;
   - общий админ-доступ к чужим чатам.

## Открытые развилки для Андрея (закрыты 17.11, итог — ADR-041, «Решения Андрея»)
1. Стоп-сигнал в В1 (рекомендую — да, без доступа к переписке).
2. Веб-поиск в «Уроках»: в В1 рекомендую выключить, пока нет фильтра выхода.
3. Таймзона по умолчанию для окон, если у ребёнка `TimeZone` не пришёл.
4. Браузерное STT отправляет голос ребёнка в Google: согласен ли он с этим или нужен серверный STT.
