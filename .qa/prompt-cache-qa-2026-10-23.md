# QA «Индикатор prompt cache и перенос в новый чат» — 23.10.2026

Стенд: worktree `ClaudeCodeServer-prompt-cache-handoff` (ветка `feat/prompt-cache-handoff`), dotnet run, `:5560`,
`appsettings.Local.json` (DataPath `backend/ClaudeHomeServer/data-qa`, `Auth:DevPassword=12345`, провайдер minimax).
Вход: admin. Фич-флаг `prompt-cache` включался через `PUT /api/feature-flags/prompt-cache` и через UI («Эксперименты»).

## Как проверялись данные кэша

Живой ход через Claude-провайдера невозможен: OAuth Anthropic истёк («Failed to authenticate: OAuth session expired»),
а для стороннего провайдера (minimax) `ClaudeSession.BuildPromptCacheState` по замыслу возвращает `null`
(поле `promptCache` в result не заполняется). Поэтому состояние кэша подставлялось в `history.json` чата
(`promptCache` в result: `anchorAtMs`, `ttl`, `readTokens`, `writtenTokens`, `missReason`), после чего стенд
перезапускался — сервер отдаёт подставленные данные тем же путём, что и живые (проверено curl'ом по
`GET /api/projects/{pid}/sessions/{sid}/history`).

## Что работает

| Сценарий | Факт |

## Находки

### S2 — при выключенном фич-флаге индикатор и секция кэша остаются видимы

Шаги:
1. `PUT /api/feature-flags/prompt-cache {"enabled":false}` (admin).
2. Открыть чат с данными кэша (в тестовой копии — подставлены в `history.json`), перезагрузить страницу.
3. Открыть поповер кольцевой пилюли.

Ожидалось (сценарий 7 ТЗ): при выключенном флаге нет ни индикатора, ни кнопки переноса, ни диалога порогов.
Фактически:
- циферблат в шапке виден (`button[aria-label="Контекст 6% · Кэш промпта — нажмите для деталей"]`);
- в поповере есть целая секция «Кэш промпта» с «Осталось», «В кэше», «Срок кэша», «Последний промах»;
- кнопка «Когда предупреждать об остывании» (диалог личных порогов) доступна;
- скрыты только кнопка «Перенести в новый чат» и строка промаха в подвале.

Причина: флаг проверяется в `ChatItemView` (строка промаха) и в `PromptCacheSection` (кнопка переноса), но не в
`RingPillBadge`/`CacheDial` и не в самой `PromptCacheSection` (кнопка порогов). Бэк присылает `promptCache` в result
независимо от флага (`ClaudeSession.BuildPromptCacheState` флаг не смотрит), так что данные приходят всегда.

### S2 — «чат занят» не даёт честного 409: перенос молча уходит холодным путём

Шаги:
1. Чату с тёплым кэшем (anchor + TTL 1ч) отправить длинное сообщение, чтобы ход шёл (статус сессии — `Working`).
2. Через 5–6 с: `POST /api/chats/{id}/handoff`.

Ожидалось (сценарий 4 ТЗ): «чат занят — честный 409».
Фактически: `200 OK`, тело `{chatId, projectId, draft, warm:false}` — тёплый путь отменён, записку собрал дешёвый
раннер по транскрипту, новый чат создан. То есть действие выполняется вопреки занятости чата, а человек вместо
отказа получает молчаливую подмену пути. Код это допускает намеренно (`WarmHandoffBlocker` → «тихий холодный путь,
без ошибки»), но это расходится с критерием приёмки.
409 наблюдается только на повторный клик по кнопке («Перенос этого чата уже идёт»).

## Наблюдения (не дефекты)

- Порт «1 поток на владельца» для холодного пути проверен косвенно: параллельные переносы разных чатов не мешают
  друг другу, повторный клик по одному чату даёт 409. Полностью сценарий «две одновременные записи одного владельца
  в очереди» не проверен.
- Плоский ответ 502 на неудачном переносе (ход передачи упал по OAuth) приходит человеческим текстом («claude
  завершился с кодом 1: Failed to authenticate…») — это проверено, текст показывается в поповере.
- Передаточная записка в двух проверенных переносах содержала внутренние правила продукта (трейлер `CCS-Session` в
  разделе «Где остановились», правила работы со звуком/видео) — записка описывает не разговор, а системный промпт.
  Качество текста записки, а не механика фичи; вероятно, стоит поправить промпт раннера/чата.
- В ленте подвал (плашка «✓ N шаг …») отрисован только у последнего хода; у более ранних ходов подвала нет, поэтому
  строка «кэш не помог» там и не появляется. По коду (`ChatItemView`) условие показа не привязано к «последнему
  ходу» — если подвал не-последнего хода когда-либо отрисуется, строка появится и там.
- Поля диалога порогов — `input[type=search]`: на мобиле это клавиатура поиска вместо числовой.
- Текст ошибки диапазона не указывает, какое именно поле неверно («Порог часового кэша — 1–59 мин, 5-минутного — 1–4 мин»).
