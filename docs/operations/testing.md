# Тесты: наборы, шарды, сторожа, пул хостов

Как устроен прогон бэкенд-тестов после фичи «Ускорение тестов» и что из этого обязан знать
каждый, кто пишет или гоняет тесты. Правила написания теста (платформонезависимость, паттерн
«интервал — опция, ожидание — событие», метки категорий) — в
[conventions.md](../architecture/conventions.md), раздел про тесты; здесь — устройство прогона
и обязанности автора теста, которые держат сторожа.

> Документ описывает только то, что есть в коде ветки. Базового списка медленных тестов
> нет и не заводится: он протухает за неделю. Медленное находит профиль и сторож длительности (CI и ручной `--check`).

## Наборы и метки

Монолит `ClaudeHomeServer.Tests` и остальные тестовые проекты гоняются двумя проходами:

| Проход | Фильтр | Что внутри |
|---|---|---|
| **Fast** | `Category!=Host&Category!=Slow&Category!=Integration&Category!=Node&Category!=Bench` | всё, что не помечено исключаемой категорией |
| Остальное | `(Category=Host\|Category=Slow\|Category=Integration\|Category=Bench)&Category!=Node` | вторым проходом на шарде CI; вместе два прохода дают весь шард |

Fast — **исключение категорий**, а не перечень меток: новый тест без меток попадает в Fast сам.
Отсюда две обязанности автора:

- `[Trait("Category", "Host")]` на **классе**, который поднимает `TestWebApplicationFactory`
  (xUnit v2 не наследует трейты класса, метка нужна на самом классе). Держит сторож `HostCategoryGuardTests`.
- `[Trait("Category", "Slow")]` на **методе** без хоста, который не укладывается в гейт
  длительности. Это временная мера до перевода ожидания на событие; навсегда в Slow — тесты,
  чья стоимость в самой работе (спавн процесса, скан решения), их перечень — в conventions.md.
  Метка на **весь класс** допустима только там, где дорог каждый его тест (те же классы «навсегда в
  Slow»); класс из тестов с разной стоимостью метят по методам.

**Инвариант покрытия Slow.** Slow выпадает только из быстрого контура: Fast в предгейте и
первого прохода шарда CI. Из второго прохода CI (`NOT_FAST` в ci.yml) и из полного прогона
перед мержем Slow не исключается никогда — метка переносит тест из быстрого прохода в
медленный, но не отменяет его.

**Правило новой метки.** Новая `Slow` в диффе требует обоснования в сообщении коммита: замер
(секунды, load) или причина стоимости — процесс, ffmpeg, inotify, скан решения. Метка на весь
класс без обоснования, что дорог каждый его тест, — возврат на ревью. Рост меток виден в отчёте профиля
(`test-profile.py`, строка «Под Slow»: число тестов и меток по исходникам `backend/`, `[Theory]`
считается одним тестом; тест под двумя метками — метка на методе внутри класса с меткой — считается один раз);
это отчёт, а не гейт — порога и базового списка нет, список протухает.
Строка «Fast» рядом даёт число тестов и классов набора по его TRX; если TRX с префиксом `fast` среди переданных
нет, строка называется «Все переданные TRX» и считает всё переданное.

Категория `Node` исключена и из CI (нужен Node и `frontend/node_modules`); `Dns` в CI гоняется.

Фильтр Fast записан в трёх местах: `FAST_FILTER` в
[test-profile.py](../../scripts/test-profile.py), `FAST` в [ci.yml](../../.github/workflows/ci.yml)
и проверка «быстрые тесты» в секции `Pregate` [appsettings.json](../../backend/ClaudeHomeServer/appsettings.json).
Меняешь набор — правь все три.

## Как гонять

В чате агента тесты — только инструментом `mcp__tests__run_tests` (прогресс, очередь сборок,
«Стоп»), не Bash. Таблица ниже — для голого терминала и для того, что делает сам инструмент.

«Полный прогон перед мержем» — зелёный CI на PR ветки (оба прохода, `Slow` включён); без PR —
`scripts/test-shards.py --run` монолита плюс `run_tests` по каждому проекту, а не один `run_tests` на slnx.

| Задача | Команда |
|---|---|
| Какие тестовые проекты задела правка | `scripts/tests-affected.sh` (по `git diff` и графу `ProjectReference`; только читает git) |
| Один набор тестов | `dotnet test backend/ClaudeHomeServer.Tests --filter "FullyQualifiedName~Services.SessionManager"` |
| Fast по решению | `dotnet test backend/ClaudeHomeServer.slnx --no-build --filter "Category!=Host&Category!=Slow&Category!=Integration&Category!=Node&Category!=Bench"` |
| Монолит шардами локально | `python3 -I scripts/test-shards.py --run backend/ClaudeHomeServer.Tests --results .cc-attachments/test-shards` (`-n auto` по умолчанию, явное `-n 3` — фиксированно) |
| Fast шардами (как в предгейте) | `python3 -I scripts/test-shards.py --run-fast backend/ClaudeHomeServer.slnx --split backend/ClaudeHomeServer.Tests=3,backend/ClaudeHomeServer.Llm.Tests=2 --filter "<фильтр Fast>" --results .cc-attachments/pregate-fast` (с `CCS_TEST_SHARDS_ADAPTIVE=backend/ClaudeHomeServer.Tests=4` — N монолита по нагрузке) |
| Профиль прогона по TRX | `python3 -I scripts/test-profile.py <папка с TRX или .trx>` |
| Профиль для раскладки (3 спокойных прогона) | см. «Профиль раскладки: как снимать» ниже |
| Сторож длительности | `python3 -I scripts/test-profile.py <папка TRX набора Fast> --check` |
| Тесты самих скриптов | `python3 -I scripts/test_test_profile.py` и `python3 -I scripts/test_test_shards.py` |

Заметки:

- `--run` берёт готовую сборку (`dotnet test --no-build`) — сначала собери. Папка результатов
  получает `shard{i}.log` и TRX каждого шарда; в конце печатаются стена и пик RSS дерева
  процессов (на Linux). Без `--timings` раскладка идёт по хешу имени класса; с профилем —
  `python3 -I scripts/test-profile.py <trx> --json > profile.json` и `--timings profile.json`
  (несколько профилей через запятую — вес класса берётся МЕДИАНОЙ, см. ниже).
- `--check` гонять **только на TRX набора Fast**: там любой тест дольше порога — нехостовый
  тест без метки Slow. Гейт — 5 с (`--threshold`), тесты от 2 с до порога печатаются блоком
  «цель доводки» без падения. `--latest-run` берёт TRX последнего прогона из общей папки
  (окно 600 с), а не всё накопленное. `--run-fast` (предгейт) такой смеси не допускает: каждый его прогон пишет
  TRX и логи в свою подпапку `--results/<метка>-<pid>` (хранятся последние 5), и профиль для следующей
  раскладки берётся из самой свежей подпапки с TRX — два прогона подряд или параллельно не смешиваются, а TRX
  чужого прогона не может «доказать» убитый шард. `--run` пишет прямо в `--results`: каталог на прогон.
- В `xunit.runner.json` монолита `maxParallelThreads` = 12 и `longRunningTestSeconds` = 2;
  у `Llm.Tests` — `maxParallelThreads` = 4, параллель коллекций включена. Монолит идёт под
  **Server GC** (`ServerGarbageCollection` в его csproj, в .NET 10 — с DATAS): Workstation GC
  стоял в паузах до 40 % прогона. Замер 17.11.2026 на worker (192 потока, 2 шарда, полный
  монолит):

  | Конфигурация | Стена | Пик дерева шардов | Самый тяжёлый testhost |
  |---|---|---|---|
  | Workstation GC, 6 потоков | 297 с | 8,7 ГиБ | 4,5 ГиБ |
  | Workstation GC, 12 потоков | 308 с | 11,5 ГиБ | 6,5 ГиБ |
  | Workstation GC, 6 потоков, `GCgen0size` 256 МиБ | 248 с | 8,6 ГиБ | 4,6 ГиБ |
  | Server GC, 6 потоков | 187 с | 7,1 ГиБ | 3,5 ГиБ |
  | **Server GC, 12 потоков** | **148 с** | **8,3 ГиБ** | **4,5 ГиБ** |
  | Server GC, 16 потоков | 158 с | 9,4 ГиБ | 5,1 ГиБ |
  | Server GC, 24 потока | 159 с | 12,8 ГиБ | 6,4 ГиБ |

  Выше 12 потоков стена не падает, а память растёт: тесты больше ждут, чем считают.
- **Память testhost — живые хосты, а не число тестов.** Утилизированный `WebApplicationFactory`
  обязан отпустить весь граф: поток, созданный при старте хоста (наблюдатель файлов, свой
  `Thread`), несёт `ExecutionContext` с AsyncLocal `HostFactoryResolver+HostingListener` и держит
  хост, пока жив. Так `PhysicalFileProvider` источника `data/subsystems.json` (его `AddJsonFile`
  создаёт сам и никто не освобождал) копил хосты: testhost рос линейно до 17 ГиБ и падал по OOM
  (16.11.2026, 232 потока `.NET File Watcher` при ~15 живых хостах). Проверка: число потоков
  testhost (`/proc/<pid>/task/*/comm`) и inotify-дескрипторов по ходу прогона не растёт, а
  держится около числа живых хостов.

## Шарды по классу

Монолит режется **по классам**, а не по пространствам имён (перекос) и не по методам
(классовые фикстуры не делятся).

- **Раскладка.** [test-shards.py](../../scripts/test-shards.py): жадная упаковка классов по
  длительностям из профиля (`test-profile.py --json`); класс, которого в профиле нет, — в шард
  по стабильному хешу полного имени `mod N`. Профиль учитывает, что серийный класс держит один
  поток прохода: оценка стены шарда — `max(самый долгий класс, сумма / 5)` на проход, а не
  голая сумма. Списка шардов в репозитории нет: раскладка считается на каждый прогон из
  `dotnet test --list-tests`.
- **Фильтр шарда.** `python3 -I scripts/test-shards.py --list LIST.txt --shard 2/6 --timings profile.json`
  печатает фильтр VSTest вида `FullyQualifiedName~Класс.|…` (точка не даёт зацепить класс с тем
  же префиксом).
- **Самопроверка** в каждом режиме: каждый тест списка попадает ровно в один шард, иначе exit 1.
  Объединение шардов равно списку тестов — состав не сокращается.
- **Профиль раскладки: как снимать.** Вес класса берём из **спокойных одиночных прогонов**, а не
  из прогона под нагрузкой: в R3 профиль снят при load1 65–108, класс весил 78 с вместо 6, и
  жадная упаковка положила оба тяжёлых класса в один шард. Процедура (каждый прогон — один
  процесс на проект, проекты **по очереди**, не параллельно друг другу; префикс TRX `fast-` обязателен —
  по нему профиль отдаёт секунды Fast):

  ```bash
  F='Category!=Host&Category!=Slow&Category!=Integration&Category!=Node&Category!=Bench'
  python3 -I scripts/test-shards.py --slnx backend/ClaudeHomeServer.slnx \
      --exclude ClaudeHomeServer.Tests,ClaudeHomeServer.Llm.Tests --shard 1/1 > backend/ClaudeHomeServer.FastRest.slnx
  for i in 1 2 3; do
    for t in backend/ClaudeHomeServer.Llm.Tests backend/ClaudeHomeServer.Tests backend/ClaudeHomeServer.FastRest.slnx; do
      dotnet test $t --no-build --filter "$F" --logger "trx;LogFilePrefix=fast-$(basename $t)" \
          --results-directory .cc-attachments/profile/run$i/$(basename $t)
    done
    python3 -I scripts/test-profile.py .cc-attachments/profile/run$i --json > .cc-attachments/profile/run$i.json
  done
  rm backend/ClaudeHomeServer.FastRest.slnx
  # раскладка по медиане трёх профилей
  python3 -I scripts/test-shards.py --run-fast backend/ClaudeHomeServer.slnx \
      --split backend/ClaudeHomeServer.Tests=3,backend/ClaudeHomeServer.Llm.Tests=2 --filter "$F" \
      --timings .cc-attachments/profile/run1.json,.cc-attachments/profile/run2.json,.cc-attachments/profile/run3.json
  ```

  `--timings` принимает список через запятую: секунды и Fast класса — **медиана** по профилям, где
  он есть (один выброс из трёх отсекается). Медиана нижняя: при двух профилях берётся меньший, а не среднее
  (выброс не усредняется); просить чётное число профилей незачем — нужно нечётное, лучше три. Секунды и Fast
  класса считаются по одним и тем же профилям (с разбивкой Fast) — профиль старого формата без неё на класс
  не влияет, если есть профили с разбивкой. Пересчитывай профиль после резки больших классов и
  после заметного роста набора. Одиночный прогон монолита Fast идёт ~45 с, `Llm.Tests` ~30 с, rest ~33 с
  (замер 30.10, load1 ≈ 20 из-за фонового стенда LLM).
- **Код выхода шарда.** `wait_all` отдаёт 0, только если все шарды вышли с 0; убитый сигналом шард
  (−9 OOM-killer, −6 SIGABRT) красный, `max()` не проглатывает его нулём соседа. Единственное
  исключение — дефект 0f5bd660: testhost падал SIGABRT уже ПОСЛЕ полного зелёного прогона (в логе
  `Passed! Failed: 0`, TRX записан; 1 из 8 прогонов). Сигнальный код шарда по классам прощается,
  только если `trx_proof` доказал всё сразу: TRX шарда свежий (не старше его запуска с допуском 1 с на зерно mtime файловой системы — `MTIME_SLACK`), в нём есть
  каждый тест шарда по списку `--list-tests` и нет результатов кроме Passed/пропуск; в stderr
  идёт предупреждение «аварийно завершился после зелёных тестов (код −N)». Положительный код,
  шард без TRX или с неполным TRX и rest-процесс (состав не листается) остаются красными.
- **Локальная модель стены шарда.** Оценка `max(самый долгий класс, сумма / PARALLEL)` верна, пока
  шарды не конкурируют за CPU. CI считает с `PARALLEL = 5` (4 vCPU раннера), локальные `--run` и
  `--run-fast` — с `LOCAL_PARALLEL = 3` (`--parallel N` переопределяет): на рабочей машине десятки
  testhost'ов rest и чужая нагрузка забивают процессор, и стена шарда следует за суммой его
  длительностей. При 5 в `Llm.Tests-2` легло 39 с суммы против 18 с у соседа, и он держал стену.
- **CI** ([ci.yml](../../.github/workflows/ci.yml)): сборка один раз, её `bin` едет артефактом
  в матрицу — монолит 6 шардов, `Llm.Tests` 2 шарда по классам, остальные тестовые проекты
  («rest», 3 шарда) — по проектам (`--slnx … --exclude … --shard i/N` печатает slnx шарда).
  Каждый шард гоняет два прохода (Fast, затем остальное) и (в CI) сторож длительности. Профиль прошлого
  прогона лежит в кэше (job `backend-profile`), его веса и раскладывают следующий прогон.
  Число шардов меняется только в матрице.
- **Порог сторожа в CI — 30 с** (`DURATION_GUARD_THRESHOLD` в `ci.yml` — единственное место CI-порога; ручной порог 5 с — `CHECK_THRESHOLD` в `scripts/test-profile.py`): на 4 vCPU
  раннера стена теста вырастает в разы, там ловятся только грубые регрессии. **В предгейт сторож
  НЕ входит** (решение FINAL-2, 30.10): предгейт идёт на общей машине при load1 45–70, и замер
  показал шум по Fast: порог 5 с краснел на 57–141 тестах каждого прогона, 15 с — на 2–13, 20 с —
  в двух прогонах из четырёх, 30 с — в одном (31,9 с у теста, который в одиночном прогоне идёт
  0,3–2,5 с). Каждый раз краснели РАЗНЫЕ тесты — это нагрузка, а не медленный код. Острый порог
  5 с — ручной `--check` на спокойной машине.

## Перезапуск флаков в быстром гейте

Предгейт «быстрые тесты» (`test-shards.py --run-fast`, и так же `--run`) после красного прогона
**один раз** перезапускает упавшие тесты: последовательно, по `dotnet test --no-build` на проект
(сборку упавшего теста берём из TRX), фильтром по точному FQN. Длинный список режется на несколько
запусков по 8000 символов фильтра (`RERUN_FILTER_CHARS`), так что предел командной строки Windows
(32 767) не достигается. TRX и логи перезапуска лежат в `<--results>/rerun/`, вне подпапки прогона,
чтобы профиль раскладки их не учитывал.

- **Прошли со второго раза все** — exit 0, в сводке блок `Флаки (прошли со второго раза): N` с FQN
  каждого, список — в `<--results>/flaky.json` (FQN, класс, сборка, время; старый файл удаляется в начале
  каждого прогона). **Флак в гейте зелёный, но не прощён:** на каждый заводится карточка-дефект.
  Перезапуск снимает шум, а не саму проблему.
- **Флаки видны в карточке зелёного предгейта:** проверка остаётся зелёной (красная серия не растёт), но
  в сводке записи — `⚠ быстрые тесты: флаки N` и до 10 FQN (`PregateRules.Summary`). Флаки же копятся
  в журнал `<--results>/flaky.jsonl` (строка на флак: время UTC, FQN, класс, сборка, ветка, коммит;
  последние 2000 строк) — он, а не перезаписываемый `flaky.json`, источник для карточек дефектов.
- **Хоть один упал снова** (или не нашёлся во втором запуске) — красный, `Упали дважды: …` отдельно от флаков.
- **Упавших больше `RERUN_MAX` = 20** (`--rerun-max N`) — это поломка, а не флак: перезапуска нет,
  красный, строка `Перезапуск пропущен: упало K > RERUN_MAX (20)`.
- **Аборт не маскируется.** Перезапуск идёт, только если КАЖДЫЙ красный шард красен упавшими тестами
  в полном TRX. Сигнальный код (кроме прощённого `trx_proof`), TRX без провалов или неполный (по списку
  `--list-tests`), нет TRX, обрыв testhost в логе — без перезапуска, честный красный: перезапуск повторяет
  только упавшие, а что не успело пройти — неизвестно.
- **Выключение:** `--no-rerun` или `CCS_TEST_SHARDS_RERUN=0`. CI-режимы (`--shard`, `--verify`, `--slnx`)
  перезапуск не делают вовсе: в CI флак должен быть виден.

## `run_tests`: монолит шардами

Монолит без `filter` инструмент гоняет **несколькими процессами `dotnet test` параллельно**
([TestShards.cs](../../backend/ClaudeHomeServer.TestRuns/TestShards.cs)):

- Настройка `TestRuns:MonolithShards` — **потолок** (по умолчанию 4, допустимо 1–6; 1 — прежний
  один процесс) и `TestRuns:MonolithTarget` (`backend/ClaudeHomeServer.Tests`) в `appsettings.json`.
- **N по нагрузке машины** (`TestRuns:AdaptiveShards`, по умолчанию `true`; правило —
  `AdaptiveShards` в TestShards.cs и `choose_shards` в test-shards.py, одни константы и одна
  таблица тестов на обеих сторонах): `load1 < 0,5·nproc` — потолок, `< 1,5·nproc` — 3, иначе 2;
  по ядрам `N ≤ max(1, floor(nproc / 4))` (у шарда свой testhost с xunit `maxParallelThreads=12`; меньше
  ~4 ядер на шард — процессы только мешают друг другу: 24 потока — 6, 8 — 2, 4 — 1); по памяти
  `N ≤ floor(запас / память на шард)`, не меньше 1; нет `/proc` (Windows, macOS) — 3. **Память на
  шард — пик RSS на шард прошлого прогона × 1,2** (не ниже 1 ГиБ), нет записи — запасные 3,5 ГиБ (к ним
  множитель не применяется: запас уже внутри). Пик пишется, только когда шардов было ≥ 2: сервер —
  `data/build-memory/shard-peak.json` (пик RSS деревьев шардов по `/proc`, раз в 0,5 с; в песочнице не
  меряется — PID там у docker-клиента), скрипт — `<--results>/shard-peak.json` (у `--run-fast` пик всего
  дерева делится на шарды адаптивных проектов: оценка сверху, безопасная сторона). Запись сама
  вниз не сходит, если прошлый пик прижал N к 1: так вышло с записью 11,4 ГиБ на шард, снятой до
  починки утечки хостов (16.11.2026), — такую запись удаляют руками, следующий прогон с N ≥ 2
  запишет новую. **Запас —
  минимум `MemAvailable` и `memory.max − memory.current` по цепочке cgroup**, в которой пойдут
  шарды: у сервера — от `Execution:Isolation:Slice` (каталог slice ищется у предков своего cgroup по
  правилу systemd `ccs-agents.slice` → `ccs.slice/ccs-agents.slice`, uid не зашит; без изоляции —
  свой cgroup), у скрипта — от своего cgroup из `/proc/self/cgroup` (scope прогона со своим
  `MemoryMax` и slice над ним). Нет cgroup, везде `max` или мусор — только `MemAvailable`. Почему
  так: хост бывает свободен при почти полном slice (02.11 — 28 ГиБ на хосте при 16,9 из 24 в
  slice), а OOM убивает по лимиту slice. 3,5 ГиБ на шард — замер 2026-10-29 (N=3 — пик 9,5 ГиБ) с
  запасом. **Потолок 4, а не 6: пик RSS при N=6 не замерен** — 02.11 slice был занят на 22 из
  24 ГиБ при load1 71, замер не влезал; поднимать `MonolithShards` (и потолок в Env предгейта)
  только после замера `--run -n 6`. Зачем правило:
  днём (load 30–50 на 24 потоках) статическая параллель упирается в CPU — тот же монолит тремя
  шардами 123–132 с при load 5–11 и 176–218 с при load 30–50, — а в тихие окна три шарда
  недогружают машину. Выбор и причина — в строке цены итога («шардов параллельно: 6 — load1 7,2
  из 24, свободно 31 ГиБ, в cgroup 7 ГиБ»); у `test-shards.py --run`/`--run-fast` — первой строкой вывода.
  `--verify`/`--shard`/`--slnx` (CI) от нагрузки не зависят: `auto` там значит 3. Откат без
  пересборки: `AdaptiveShards=false` и `MonolithShards=3`.
- Шарды включаются, только когда цель — монолит, `filter` не задан и подсчёт тестов
  (`--list-tests`) прошёл; иначе — один процесс, как раньше. Любой `filter` отключает шарды:
  дроби им прогон по-прежнему.
- Все шарды идут под **одним** слотом `BuildConcurrencyGate`: второго семафора нет, счётчик
  единственный на процесс. У каждого шарда свой `TurnId` и свой TRX (`results-shard{i}`);
  оборван любой — оборван прогон, код выхода — первый ненулевой.
- Раскладка — **по числу тестов класса**, а не по секундам: профиля длительностей у сервера
  нет. Самопроверка покрытия та же, что в CI; не сошлась — прогон идёт одним процессом.
- **Потолок прогона прежний — 540 с** вместе с очередью сборок (против 600 с `MCP_TOOL_TIMEOUT`
  хода). Шарды его не меняют: они сокращают стену монолита, а не снимают потолок. Подробности
  потолка и запретов аргументов — [mcp-servers.md](../architecture/mcp-servers.md), раздел
  «Прогон тестов».
- **Цена — память.** Каждый шард — свой testhost: замер 2026-10-29 — N=1 даёт пик RSS 5,5 ГиБ,
  N=3 — 9,5 ГиБ при лимите `ccs-agents.slice` 18 ГиБ. Упёрлись в память — снижай
  `MonolithShards`, а не лимит.

### Общий отпечаток сборки

`run_tests` пропускает сборку, если отпечаток исходников дерева (путь, mtime, размер `.cs`,
`.csproj`, `.props`, `.targets`, `.json`, `.resx`) совпал с отпечатком последней **успешной**
сборки той же цели. Набор отпечатков один на процесс (`PhasePipeline.Fingerprints`), пишут его и
`run_tests`, и инструмент `build`: «build → run_tests» без правок собирает один раз. Сборка
решения `.slnx` покрывает каждый его проект (причина пропуска — «дерево не менялось после сборки
backend/X.slnx»); сборка проекта решение не покрывает. Отпечаток снимается ДО сборки, упавшая
или прерванная сборка его не пишет; только память процесса — после рестарта первая сборка
обязательна.

## Сторожа

| Сторож | Что стережёт | Где |
|---|---|---|
| `HostCategoryGuardTests` | класс, поднимающий хост, помечен `Host`; скан по метаданным собранных сборок всех тестовых проектов slnx (после правки тестов собери решение — сторож видит собранное) | `Guards.Tests`, Slow |
| `PooledHostGuardTests` | класс пула не меняет конфиг общего хоста (`ExtraServices`, `ExtraConfig`, `WithWebHostBuilder`) | `Guards.Tests`, Slow |
| `HostPerClassRatchetGuardTests` | храповик «хост на класс»: `TestWebApplicationFactory` и её наследники не создаются в тест-классе мимо вложенной фикстуры (подробно — ниже) | `Guards.Tests`, метод Slow |
| `CollectionDefinitionGuard` | определения xunit-коллекций лежат в сборке самих тестов (см. ниже) | вызывается из `Tests` и `Llm.Tests` |
| `test-profile.py --check` | нехостовый тест без `Slow` дольше порога | CI (30 с), ручной `--check` на спокойной машине (5 с); в предгейт не входит |

Предгейт шага (секция `Pregate` в `appsettings.json`) включает «быстрые тесты» (Order 35: Fast без
пересборки, `test-shards.py --run-fast`: монолит шардами по нагрузке (см. ниже) и `Llm.Tests` 2 шарда по классам, остальные
тестовые проекты — одним процессом на rest-slnx, всё параллельно; раскладка по профилю TRX прошлого
прогона из той же папки, первый прогон — по хешу класса) после `build`; закрытие задачи она
не блокирует, результат виден ревьюеру. **Конфиг проверки серверный, а скрипт —
из дерева ветки**, поэтому в `--split` только числа (`ClaudeHomeServer.Tests=3`): `parse_split`
деревьев старше адаптивных шардов падает на `=auto`, и каждый их предгейт стал бы красным.
Адаптивность включает `Env` проверки — `CCS_TEST_SHARDS_ADAPTIVE=backend/ClaudeHomeServer.Tests=4`
(проект=потолок): старый скрипт переменную не видит и идёт прежними 3 шардами, новый выбирает N по
правилу под этим потолком; число из `--split` для него — значение без переменной. `Env` у
`PregateCheckOptions` — поверх него служебные `DOTNET_CLI_UI_LANGUAGE=en`, `DOTNET_NOLOGO=1`.

Сканирующие сторожа `HostCategoryGuardTests` и `PooledHostGuardTests` делят один скан решения
(`HostScan.Solution`), храповик берёт его только ради счётчика хостовых классов (≥ 100), а
создателей фабрик ищет собственным вторым проходом по IL. Общим у храповика с `HostCategoryGuardTests`
остаётся и перечисление тестовых сборок (`HostCategoryGuardTests.TestAssemblies()`, зовётся из
`HostPerClassRatchetGuardTests.FactoryCreators`): правка этого перечисления меняет охват сразу обоих сторожей. Основные проверки помечены `Slow`: скан
сборок решения — работа, а не ожидание.

## Хост на класс и пул общих хостов

Контроллер-тест, который поднимал `TestWebApplicationFactory` на каждый тест, — главный
пожиратель времени. Две ступени лечения, от простой к сложной:

1. **Хост на класс.** Класс берёт `IClassFixture<…>` с вложенной фикстурой-хостом; всё, что
   тесты меняют в общем хосте или графе сервисов, **явно сбрасывается** в конструкторе класса
   (конструктор xUnit выполняется перед каждым тестом) или изолируется построением — новый
   владелец и свои каталоги на тест. Образцы: коммит `808f8428b` (Projects, AgentDownloads,
   LlmProxy, Hardware: 67,1 с → 17,3 с), `db43e9b44` (граф на класс в `TeamWaveServiceTests` и
   `ChatArchiveServiceTests`, сброс в `ResetTestState`), `62d151050` (там же — снос сессий и
   задач предыдущего теста: класс не зависит от порядка тестов). Сброс проверяй мутацией, как в
   `db43e9b44`: убрал возврат состояния — тест обязан покраснеть.

   Устройство. Хост — **вложенная** фикстура `Hosts : TestWebApplicationFactory`, класс берёт её
   через `IClassFixture<Класс.Hosts>` и получает в конструкторе (образец —
   `ImageEditorTransformTests`). Нужна другая конфигурация хоста (`ExtraServices`, `ExtraConfig`,
   `WithWebHostBuilder`) — **подкласс фабрики на каждую конфигурацию** и `Hosts`-обёртка с
   `IDisposable`, которая держит его экземпляром (образец —
   `backend/ClaudeHomeServer.Tests/AudioEditor/AudioEditorControllerTests.cs`: `EngineHost` —
   соседний вложенный тип тест-класса, подкласс фабрики с фейковым движком, а `Hosts.Engine` —
   его экземпляр), а не хост на тест. Правила изоляции: общее изменяемое состояние хоста (рабочие
   папки, сторы, очереди) сбрасывается **в конструкторе тест-класса**, а не в фикстуре —
   конструктор xUnit выполняется перед каждым тестом, фикстура живёт один раз на класс; данные
   (проект, владелец, каталог) тест заводит свои, уникальные на тест (GUID), чтобы кэши и сторы
   по данным не делили записи между тестами и порядок прогона не влиял.
2. **Пул общих хостов** ([SharedHostPool.cs](../../backend/ClaudeHomeServer.TestKit.Host/SharedHostPool.cs)):
   один хост на ключ конфигурации на процесс тестов; класс подключается
   `IClassFixture<PooledHost>` (образец — `TasksControllerTests.Host`). Каталог — свой на класс,
   владельцы — свои (`NewOwner()`), общих `testuser`/`seconduser` в хосте пула **нет**: случайный
   `CreateAuthenticatedClient()` падает на входе, а не делит данные с соседями. Пул — не
   `ICollectionFixture`: коллекция сериализовала бы классы, а пул их не сериализует.

**В пул нельзя:** классы с `ExtraServices`/`ExtraConfig`/`WithWebHostBuilder` (конфиг общего
хоста не меняется; сторож плюс проверка при каждой выдаче хоста), `*DisabledTests`, честные e2e
и классы, проверяющие «пустое состояние» всего хоста. Классы `SessionManager*Tests` (бывший
`SessionManagerTests`, разрезан по темам) вне пула: там тяжёлый конструктор на каждый тест, а не
хост. Нужен свой хост — свой подкласс `TestWebApplicationFactory` в `IClassFixture`. Расширять
пул только по цифре профиля.

## Храповик «хост на класс»

Без сторожа новый тест-класс снова поднимет хост на каждый тест, поэтому правило закреплено
`HostPerClassRatchetGuardTests` (`backend/ClaudeHomeServer.Guards.Tests/Services/`). Скан — по
метаданным и IL собранных тестовых сборок (на примитивах разбора `HostScan`; после правки тестов собери решение).

- **Правило.** `new` фабрики (`TestWebApplicationFactory` и любого наследника по цепочке баз)
  допустим только во **вложенной фикстуре**: в самой фабрике-наследнике и её вложенных типах, а
  также в держателе хоста — типе `Класс+Hosts` из `IClassFixture<…>` тест-класса (xunit передаёт
  его в конструктор сам; если тест-класс создаёт держатель сам через `new`, это уже не фикстура и
  красное). Сторож смотрит на тело тест-класса, его async-машины и замыкания, любые вложенные
  типы тест-класса (кроме названных выше) и базовые классы из той же тестовой сборки: фабрика в
  любом из них — красное, если тест-класса нет ни в `Remainder`, ни в `UndoneH0`. **Не видит:**
  внешний helper-класс, который сам создаёт фабрику, а тест лишь на него ссылается (нужен граф
  вызовов между типами, дешёвого способа без ложных срабатываний на пулы хостов нет; ограничение
  названо в докстринге стража).
- **`Remainder`** — осознанные исключения: тест-класс → причина, почему хост на конфигурацию или
  на тест задуман (подсистемы `Composition`, проверки DI-регистрации, хост без настроенного секрета
  и т. п.). Новая строка требует обоснования; без него её нет.
- **`UndoneH0`** — недоделанный перевод на хост на класс: классы, которые ещё поднимают хост на
  тест. Это **долг, а не решение**. Как закрутить — переведи класс на
  `Hosts : TestWebApplicationFactory` + `IClassFixture` и **удали его строку**. Рост долга держат
  две защиты:
  1. **Устаревшая запись — красное.** Строка у класса, где фабрики в коде уже нет, краснит
     основной тест («запись остатка устарела»): оставить её после перевода нельзя.
  2. **Потолок размера.** Константы `UndoneH0Ceiling` (сейчас 56) и `RemainderCeiling` (сейчас 28)
     проверяет тест `ОстатокИДолгНеВышеПотолка`: дописать строку в список без правки константы —
     красное. Класс с хостом на тест, которого нет ни в одном списке, краснит основной тест. При
     удалении записи потолок опускают **вручную**; поднять его можно той же правкой стража, и это
     видно в ревью диффа — защита опирается на ревью, а не на запрет.
- **Не вакуумный:** основной тест требует не менее 100 хостовых классов в решении
  (`HostScan.Solution`). Три вспомогательных теста проверяют: потолки списков; что `Remainder` и
  `UndoneH0` не пересекаются; что у каждой записи причина не пустая. Инвариантом это не является,
  но по данным видно: у всех записей `UndoneH0` причина — одна и та же формула «недоделанный H0:
  …», по ней долг и отличим от осознанных исключений.
- **Метка.** Slow стоит только на основном тесте (скан решения 2–5 с); три вспомогательных —
  без метки. Значит основная проверка идёт **только в полном прогоне**: Fast и предгейт её не
  гоняют, а CI — гоняет вторым проходом (`NOT_FAST` в ci.yml). Красный храповик ты узнаешь из
  CI/полного прогона, не из предгейта; потолки (вспомогательный тест) краснеют и в Fast.

## Замер «до/после» (порог 35 %)

Порог ускорения 35 % — правило фичи «Ускорение тестов», принятое при доводке 30.10 (карточка
эпика в трекере; в репозитории документа с ним нет). Он проверяется парой замеров одним и тем же скриптом
[`scripts/test-profile.py`](../../scripts/test-profile.py) по TRX:

- **«До»** — профиль CI (артефакт `test-profile.json` / TRX job'ов), «после» — **тот же скрипт**
  на прогоне после изменения. Пара снимается **на одной машине в одинаковых условиях** (одна
  нагрузка `load1`, один набор шардов и фильтр): стена тестов под конкуренцией за ядра плавает
  от нагрузки (замер Fast R5 ниже: load1 ≥ 17,9, порог «при load1 < 12» не проверен).
- **Монолит шардами и изолированный прогон не смешивай.** Сумма времени классов в шардовом
  прогоне и время того же класса в одиночном прогоне — разные величины (разное число хостов в
  процессе, разная конкуренция); сравнивай «до» и «после» одного вида (урок перевода классов на хост на
  класс в этой фиче).
- Профиль по классам даёт `test-profile.py --json`; при плавающей нагрузке бери медиану
  нескольких спокойных прогонов, как в замере Fast R5 ниже.

## Проба обратного порядка

Тест-класс на хосте на класс не должен зависеть от порядка тестов. Проверка — **временный**
`ITestCaseOrderer` из `Xunit.Sdk`, который разворачивает порядок, подключённый атрибутом
`[TestCaseOrderer(...)]` на проверяемый класс; после пробы ордерер и атрибут удаляются.
Главная ловушка: адаптер VSTest порой **не вызывает** ордерер, и проба оказывается вакуумной
(порядок прежний, зелёный прогон ничего не доказал). Поэтому порядок проверяй **по TRX**: время
старта (`startTime`) тестов класса обязано идти в развёрнутом порядке; если не идёт — проба
недействительна, а не успешна.

## Коллекции xunit

Имена коллекций — константы `TestCollections` в TestKit (`Inotify`, `ProcessGlobalState`).
**Определения `[CollectionDefinition]` живут в каждой тестовой сборке** (`TestCollectionDefinitions.cs`
в `ClaudeHomeServer.Tests` и `ClaudeHomeServer.Llm.Tests`): xunit находит их только в
прогоняемой сборке, из TestKit определения молчали и `[Collection(…)]` становился неявной
коллекцией «по имени» — классы последовательны внутри, но параллельны всему остальному и
упирались в общий бюджет inotify пользователя. В TestKit остаются только константы.

- Сторож `CollectionDefinitionGuard` ([TestKit](../../backend/ClaudeHomeServer.TestKit/CollectionDefinitionGuard.cs),
  коммит `0c29e9d2c`) проверяет: каждое используемое имя имеет определение в своей сборке,
  `Inotify` определён с `DisableParallelization`, в TestKit определений нет. Его зовут
  `CollectionDefinitionGuardTests` в `Tests` и в `Llm.Tests`.
- **Новый тестовый проект с `[Collection(TestCollections.*)]` обязан завести свои определения
  и вызвать сторож сам:** сторож проверяет только те сборки, которые его вызывают, и чужую
  забытую не поймает.
- Семантика одного имени различается по сборкам намеренно: `ProcessGlobalState` в `Llm.Tests` —
  с `DisableParallelization`, в монолите — без него (зафиксировано в обоих файлах определений).

## Ожидания в тестах

Тест, который ждёт тик продукта, платит этим тиком на каждом прогоне. Порядок перевода —
в conventions.md («интервал — опция, ожидание — событие»); коротко:

- интервал продукта — `internal`-поле или опция с **прежним** дефолтом, дефолт держит отдельный
  тест на значение;
- ожидание в тесте — `TaskCompletionSource`/событие продукта с `WaitAsync(потолок)`; таймаут —
  **красный**, `Task.WhenAny(tcs, Delay)` без проверки результата проглатывает его;
- **negative-окно** («за N секунд ничего не случилось») ограничено и выводится из тестовых же
  интервалов продукта, а не из полного таймаута «на всякий случай»;
- проверка мутацией: убери сигнал (`TrySetResult`) — тест обязан покраснеть по таймауту.

Образцы: `08c2fc082` (W1: `ExecutorIdlePollInterval` и сигнал простоя из фейка через
`TaskCompletionSource`, 10,15 с → 0,1 с) и `968a2572a` (W4: пауза-прогрев снята, negative-окна

## Мутации в копии

**Правило.** Мутацию («убрал строку — тест покраснел») доказывай в тёплой копии, а не в общем
дереве, где параллельно работают соседи:

```bash
C=$(scripts/mutation-copy.sh create)     # копия текущего коммита со ВСЕМИ незакоммиченными правками
# ... мутация и dotnet build / dotnet test в "$C" как обычно ...
scripts/mutation-copy.sh remove "$C"     # по окончании — обязательно
```

**Сборку и прогон в копии — тоже инструментами, не Bash'ем.** `mcp__tests__run_tests` и
`mcp__dev__build` принимают необязательный параметр `tree` — последнюю строку stdout `create`
(`tree="$C"`); `target` остаётся относительным корня копии. Прогон идёт в той же очереди сборок и
под тем же единственным `BuildConcurrencyGate`, что и в дереве чата. Принимается **только**
законная копия: прямой потомок корня копий (`$CCS_MUTATION_ROOT` или `~/.cache/ccs-mutation`) без
символических ссылок в пути, с метаданными `.meta/<имя>`, чей `source` — дерево ЭТОГО чата
(worktree задачи). Вторая легальная форма `tree` — **worktree проекта чата**: путь, который числится в
`git worktree list` репозитория проекта (сверка по канонической форме: ссылки разыменованы, `..`
свёрнуты; нужен `.git` в корне). Так исполнитель, сам заведший дерево из корня проекта, собирает и
тестирует именно его. Блокировка дерева и отпечатки сборки ключуются по корню `tree`, поэтому разные
worktree друг друга не держат (разбор Platformex 04–07.11: 473 отказа «уже идёт прогон» — все в
корне, где работали 115 чатов). Любой другой путь — отказ с подсказкой обеих форм (произвольный путь =
запуск чего угодно на хосте). В чатах-исполнителях задач `dotnet test`, `dotnet build` и `npx vitest` из Bash режет
хук PreToolUse (`ClaudeRuntimeSettings`, признак — `CCS_TASK_EXECUTOR=1` в окружении CLI):
в обычных чатах человека и у оркестраторов он молчит. Основание — разбор транскриптов 01–04.11:
155 запусков из Bash за три дня, ≈140 из них в копиях мутации, мимо очереди и под потолок
`ccs-agents.slice`.

**Копировать дерево руками в `/tmp` (`cp -r`, `rsync`, `git clone`) нельзя:** такая копия
собирается с нуля — все ~92 проекта, мимо `BuildConcurrencyGate` (сборка внутри хода не
гейтуется) — и остаётся на диске (03.11: 41 копия за сутки, 115 копий на 95 ГБ в `/tmp`,
нагрузка до 70 при 24 потоках). Копии живут в `${CCS_MUTATION_ROOT:-~/.cache/ccs-mutation}`,
забытые убирает `scripts/mutation-copy.sh gc [--older-than-hours N]` (дефолт 24 ч; копию с живым
процессом — cwd или открытый файл — не трогает); `create` сам молча зовёт ту же уборку перед каждой
новой копией (копии старше суток уходят без расписания, сбой уборки `create` не роняет). Тест скрипта — `python3 -I scripts/test_mutation_copy.py`.

**Источник собери на текущем коммите до `create`** (`mcp__dev__build`): хеш коммита вшит в
`AssemblyInformationalVersion` каждого проекта (`1.0.0+<sha>`), поэтому obj от прошлого коммита
пересобирает ВСЁ — и в копии, и в самом дереве. `create` об этом предупреждает.

**Как устроена копия и почему так** (замеры 03.11, машина 24 потока, load1 в скобках):

- `git worktree add --detach --no-checkout` на HEAD источника плюс rsync файлов по
  `git ls-files -co --exclude-standard` с сохранением mtime. `.git` в копии нужен — тесты ищут
  корень подъёмом до `.git`; mtime нужен — иначе все исходники «новее» obj. Голый `rsync` дерева
  отпал: потащил бы игнорируемый мусор основного дерева (`data/`, `worktrees/`, ~13 ГБ).
- Из артефактов — только `obj/` и `bin/*/*/ref/` (≈150 МБ из 15 ГБ: `bin/` — это копии зависимостей,
  не вход компиляции, и доезжает сборкой только для собранных проектов). Копия после `create` —
  ≈270 МБ за 21–24 с (load1 41–47).
- **Абсолютные пути ломают инкрементальность**, и `dotnet restore` их не лечит: в
  `*.CoreCompileInputs.cache` лежит SHA-256 от `@(Compile);@(ReferencePath);…`, а пути ссылок на
  проекты абсолютные. В копии хеш другой → CoreCompile во всех проектах с `ProjectReference`
  (замер без лечения: после правки `Memory.Tests` пересобрались 2 проекта вместо 1; при лечении
  только по `.slnx` — 20 проектов за 2:49, load1 68: часть проектов в решение не входит).
  Лечение в `create`: текстовые артефакты obj переписываются на путь копии, затем по КАЖДОМУ
  `.csproj` с obj прогоняется цепочка CoreBuild до `CoreCompile` (с `PrepareResources` —
  `EmbeddedResource` тоже в хеше), и пересчитанным файлам возвращается mtime источника.
- Итог: холодная сборка решения — 1:45 (load1 37→46); в копии после правки одного `.cs`
  `ClaudeHomeServer.Memory.Tests` — 22 с (load1 51), `ClaudeHomeServer.Tests` — 1:39 (load1 54),
  в обоих случаях пересобран ровно один проект. Сборка тяжёлого тестового проекта раздувает
  копию до ≈7 ГБ за счёт `bin/` его зависимостей — поэтому `remove` обязателен.
- Хардлинки на `bin/` источника не используются намеренно: не проверено, что компилятор и `Copy`
  не пишут поверх существующего inode, а цена ошибки — испорченное дерево источника.

Это то, что не сделано или не доказано; не считай их решёнными.

- **TeamWave + ChatArchive ≈ 15 с.** Порог 13 с на сумму двух классов не взят: по замеру `62d151050`

- **Баланс шардов монолита в CI не идеален:** ×1,20 по времени job и ×1,44 по чистому времени
  тестов (замер штаба 29.10; как посчитан показатель, в репозитории не записано). Раскладка уже
  учитывает серийные классы (`b4d282039`), но равенства по чистому времени не даёт.
- **Inotify-классы монолита идут последовательным хвостом.** Коллекция `Inotify` определена с
  `DisableParallelization`: её классы xunit запускает после параллельной части, по одному. В
  `Llm.Tests` они дополнительно помечены `Slow` и уходят из Fast.
- **Замер Fast R5 (30.10, `--run-fast`, `Tests=3,Llm.Tests=2`, профиль — медиана трёх спокойных
  прогонов).** load1 перед стартом ни разу не опустился ниже 17,9 (ждали 3 мин: стенд LLM `strata`
  держит ~6 ядер), поэтому порог «≤ 60 с при load1 < 12» **не проверен**. Стена по TRX: `PARALLEL = 5` —
  100,4 / 84,1 / 71,4 с (держит `Llm.Tests-2`); `PARALLEL = 3` — 79,5 / 73,8 / 59,4 с (держат шарды
  `Llm.Tests`). Для сравнения: до резки 106–123 с, R3 80–99 с при load1 65–108. Серийные классы Fast

  настоящие процессы `sh -c sleep` и под нагрузкой тянут 10–15 с на тест вместо долей секунды.
- **Rest в Fast под нагрузкой флакает на таймингах чужих тестов.** Падали по одному за прогон, набор
  каждый раз разный: `ConsumersTailContributorTests.Потолки_…` (CodeGraph.Tests; тест не меняет
  3-секундный `DefaultTimeout`, при таймауте `BuildAsync` отдаёт `null` и `!` даёт NRE),
  `NpmBuildServiceTests.Разбор_…` (порог `watch.Elapsed < 100ms`), `TurnTokenAdapterBranchesTests.СбойЗапускаПроцесса`,
  `TaskManagerHoldRaceTests.ClearHold_…`, `VideoEditorToolsetTests.Ожидание_идущей_съёмки…`. Все —
  привязанные к часам ожидания в тестах чужих проектов, не к раскладке. Карточка дефекта 6af27416.
- **Режим `run_tests` — без профиля и без `env`.** Серверная раскладка шардов идёт по числу
  тестов класса, а не по секундам (профиля у сервера нет); параметр `env` инструмента принимает
  только белый список Playwright, для `dotnet` переменные окружения тестов задать нельзя.
- **Windows: прогрев после `Start()` у наблюдателя не проверен.** Пауза-прогрев `Task.Delay(200)`
  в тестах `TurnFileWatcher*` снята в W4, потому что на Linux подписка `InotifyBackend` ставится
  синхронно в `Start()` и запись после него видна сразу. У `FileSystemWatcherBackend`
  (Windows/macOS) такая гарантия не проверялась: всплывёт флак «событие не пришло» на Windows —
  начинать с этого места.

## Новый тестовый проект: чек-лист

1. Имя на `.Tests` и запись в `ClaudeHomeServer.slnx`: «rest» подхватывает проект сам
   (шардирование по проектам), сторожа Host и пула сканируют все `.Tests` из slnx.
2. Использует `TestWebApplicationFactory` — метка `Host` на каждом таком классе; собери решение
   и запусти `HostCategoryGuardTests`.
3. Использует `[Collection(TestCollections.*)]` — свои `[CollectionDefinition]` в сборке проекта
   и вызов `CollectionDefinitionGuard.AssertLocalDefinitions` из его теста.
4. Класс хочет общий хост — `IClassFixture<PooledHost>` и своя изоляция данных; не подходит под
   «в пул нельзя» — свой хост на класс.
5. Перед сдачей: Fast по проекту, `test-profile.py --check` на его TRX, тесты скриптов, если
   правил `scripts/`.
6. Сборка поднимает хост сама (Kestrel, не `TestServer` фабрики) — заведи `TestEnvironmentBootstrap`
   с `[ModuleInitializer]`, вызывающим `TestEnvironmentGuard.SetTestingEnvironment()` (образцы —
   монолит и `Mcp.Tests`). Не утверждай, что инициализатор TestKit срабатывает «при загрузке
   сборки»: для зависимой сборки он срабатывает при первом обращении к её коду.
