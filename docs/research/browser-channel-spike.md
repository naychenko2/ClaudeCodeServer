# Спайк: браузерный канал (MV3/CDP) против UIA для ADR-008

**Дата:** 2026-08-20
**Связанный ADR:** [ADR-008 Десктопный агент](../adr/ADR-008-desktop-agent.md), разделы
«Форма снапшота UIA» и открытые вопросы
**Прототип:** `tools/browser-spike/` (MV3-расширение + native messaging host на чистом Node,
вне основного решения)
**Предыдущие части:** [спайк UIA, часть 1](uia-snapshot-spike.md) и [часть 2](uia-snapshot-spike.md)
(динамика и CacheRequest); [проверка фактов канала](browser-channel.md)

> Цель — ответить на главный вопрос: **снимает ли DOM-канал класс отказа «тихая подмена
> цели» и какой ценой**. Скорость перестала быть аргументом после части 2 (кеш UIA —
> 0.44 с), осталась подмена: правило «роль + имя + геометрия» указывает на другой элемент
> и считает его тем же — до 45 % в Проводнике, до 20 % в Chromium-списке.

## Вердикт

**DOM-канал снимает тихую подмену полностью — но не данными, а ключом.** У DOM есть то,
чего нет у UIA-снапшота: стабильный идентификатор живого узла `backendNodeId` (аналог UIA
`RuntimeId`, который часть 2 использовала как oracle, но не как ключ продукта). С ним
подмена невозможна по построению: узел либо жив (тот же bid — можно действовать), либо
создан заново (честное «элемент исчез», новый срез). Три числа центрального замера:

| Ключ идентичности | Скролл списка (3 тика) | Настоящая DOM-виртуализация | Жёсткая перерисовка |
|---|---|---|---|
| Правило ADR «роль+имя+геометрия» | **подмена 99.0 %** | **подмена 89–93 %** | **подмена 99.7 %** |
| `backendNodeId` (oracle) | **удержание 100 %, подмена 0** | удержание 8 %, честных «исчез» 92 %, **подмена 0** | удержание 0.3 %, честных «исчез» 99.7 %, **подмена 0** |

Правило ADR на DOM-данных ведёт себя **хуже, чем на UIA** (99 % против 20–45 %): CDP
`Accessibility.getFullAXTree` отдаёт строки списков ролью `generic` с пустым именем — та же
слепота, что у UIA (`Group ""`), но геометрический допуск на странице, где почти все
элементы — строки, находит «похожего» почти всегда. Отсюда главный вывод для ADR-008:
**ключ идентичности браузерного драйвера — `backendNodeId`, не отпечаток**; отпечаток
остаётся fallback'ом для источников без ключа.

Цена канала — не в технике (срез быстрее и полнее UIA в 3 раза), а в дистрибуции и
обвязке: автоматической установки unpacked-расширения в branded Chrome **не существует**
(проверено пятью путями, см. «Дистрибуция»), в продакшен браузерный канал означает
публикацию в Web Store, вечную плашку отладки и засыпающий service worker.

## Методика

Замеры — теми же метриками, что часть 2 UIA, чтобы сравнение было честным:

- **Oracle «тот же элемент»** — `backendNodeId` (CDP): уникален для живого узла, переживает
  смещение и смену геометрии, умирает вместе с узлом. Для виртуализированных списков
  пересоздание узла — это и есть истина, как `RuntimeId` в части 2.
- **Правило ADR-008**: роль+имя, размер ±5 %, смещение центра ≤ полувысоты/полуширины;
  из прошедших допуск выбирается ближайший по центру. Исходы: held (тот же bid) /
  lost_false (узел жив, правило никого) / subst_live и subst_dead (правило указало на
  другого) / gone_ok (узел мёртв, правило честно сдалось).
- **Страницы те же, что в части 1**: `page-simple.html`, `page-vlist.html` (1500 строк),
  плюс две новые: `page-vlist-windowed.html` (настоящая DOM-виртуализация — 1500 строк
  данных, в DOM только окно ~30, скролл пересоздаёт узлы, как react-window) и
  `page-iframe.html` (cross-origin iframe, origin A :8801 → origin B :8802). Реальная
  страница с формой — `https://httpbin.org/forms/post`.
- Действия вносятся программно, как будет делать продукт: скролл — 3 тика колеса
  (`Input.dispatchMouseEvent`, deltaY 120), ресайз — `Browser.setWindowBounds` (+10 %),
  смена вкладки — activate туда-обратно, перерисовка — из JS страницы.
- **Транспорт замеров**: прямой CDP к Chrome 151 (dev-профиль `--user-data-dir`, порт
  9333 — запрет Chrome 136+ касается только дефолтного профиля). Это тот же протокол,
  что доставит расширение через `chrome.debugger` (обёртка над CDP; домены
  `Accessibility`/`DOMSnapshot`/`Input` идентичны) — числа переносимы. Расширение и
  native messaging проверены отдельно на Chrome for Testing 152 (там жив `--load-extension`):
  SW поднимается, `connectNative` запускает хост, канал работает — см. замер 5.

## Замер 1: тихая подмена под скроллом (центральный)

Доли от элементов базового среза A (фильтр ADR: интерактивные или с собственным текстом),
разрешённых в срезе B после действия. «Подмена» = правило уверенно указало на другой узел
(subst_live + subst_dead); same_rect — геометрия совпала ±2px (клик ушёл бы в ту же точку).

| Страница × шаг | база | held | lost_false | **подмена** | same_rect | bid held | bid gone |
|---|---:|---:|---:|---:|---:|---:|---:|
| vlist — покой (контроль) | 1504 | 100 % | 0 | **0** | 0 | 100 % | 0 |
| vlist — скролл 3 тика, серия 1 | 1504 | 0.3 % | 0.7 % | **99.0 %** | 0 | **100 %** | 0 |
| vlist — скролл 3 тика, серия 2 | 1504 | 0.3 % | 0.7 % | **99.0 %** | 0 | **100 %** | 0 |
| vlist — скролл 3 тика, серия 3 | 1504 | 0.3 % | 0.7 % | **99.0 %** | 0 | **100 %** | 0 |
| windowed — покой (контроль) | 30 | 100 % | 0 | **0** | 0 | 100 % | 0 |
| windowed — скролл, серия 1 | 30 | 6.7 % | 0 | **93.3 %** | 0 | 6.7 % | 93.3 % |
| windowed — скролл, серия 2 | 37 | 8.1 % | 0 | **91.9 %** | 0 | 8.1 % | 91.9 % |
| windowed — скролл, серия 3 | 37 | 8.1 % | 0 | **89.2 %** | 0 | 8.1 % | 91.9 % |

Чтение:

- **Правило ADR на DOM-данных ломается тотально** (99 % на vlist). Механика та же, что в
  части 2 у UIA: после скролла цель уехала, в допуске оказался другой узел с той же
  «ролью+именем» — у CDP AX строки это `generic ""`. Вся подмена diff_rect (same_rect 0 %):
  правило указывает на узел в другом месте экрана — тихий промах на другую строку данных.
- **`backendNodeId` на обычной странице идеален**: DOM без виртуализации не пересоздаёт
  узлы — 100 % удержания после любого количества скроллов.
- **На настоящей DOM-виртуализации** узлы пересоздаются (bid gone 92–93 %) — но это
  честные потери: агент отвечает «элемент исчез» и берёт новый срез, а не кликает в
  соседнюю строку. Правило в тех же условиях в 9 из 10 случаев молча подменяет цель.

Сравнение с UIA (те же метрики части 2): подмена правила на Chromium-списке была
23.5–30.1 %; здесь 99 % потому, что страница почти целиком список (в UIA-окне половина
элементов — нераскольная обвязка: лента, панели). По классу отказа вывод одинаковый:
**правило на «роль+имя» на списках недостоверно в обоих мирах; oracle-ключ есть только
в DOM-канале — и он делает подмену невозможной**.

## Замер 2: ключ идентичности и его стойкость

| Действие | Правило ADR | `backendNodeId` | Путь в дереве |
|---|---|---|---|
| Покой (контроль, все страницы) | 100 % held | 100 % | 100 % |
| Скролл vlist | 0.3 % held, 99 % подмена | **100 %** | 100 %* |
| Скролл windowed | 8 % held, 92 % подмена | 8 % + 92 % честных потерь | 100 %* |
| Смена вкладки (туда-обратно) | 100 % | **100 %** | 100 % |
| Ресайз окна +10 % | 22 % held, **78 % ложных потерь** | **100 %** | 100 % |
| Перерисовка текста на месте (soft) | 100 % | **100 %** | 100 % |
| Пересоздание контейнера (hard) | 0.3 % held, 99.7 % подмена (вся same_rect) | 0.3 % + 99.7 % честных потерь | 100 %* |

\* путь «выживает» формально — но это адрес, а не элемент: на windowed/hard по тому же
пути стоит УЖЕ ДРУГОЙ узел (другой bid, другие данные). Путь в дереве — **не ключ
идентичности** для виртуализированных списков и перерисовок: он сам источник тихой подмены.

Итог по ключу: **`backendNodeId`** — переживает скролл, ресайз, смену вкладки и правку
текста; умирает только при реальном пересоздании узла, и это смерть видимая и честная
(ответ «элемент исчез», а не подмена). Атрибуты (`id`, `data-testid`) — вспомогательное
поле для хит-теста и логов, как `AutomationId` в части 1: их нет у большинства узлов.
Ресайз — единственное действие, где правило ADR даёт 78 % ложных «изменился» при живых
узлах: подтверждение правки ADR «после ресайза ref не переиспользуется» — с bid она не
нужна, ref остаётся валиден.

Медианы 5 повторов; «после фильтра» — фильтр ADR (интерактивные или собственный текст).

| Страница | Источник | Время | Сырой JSON | Узлов | После фильтра |
|---|---|---:|---:|---:|---:|
| simple | DOMSnapshot | 3 мс | 12 КБ | 52 | 40 |
| simple | AX-дерево | 6 мс | 53 КБ | 131 | — |
| simple | DOM из content | 3 мс | 7 КБ | 51 | 40 |
| vlist (1500) | DOMSnapshot | 38 мс | 358 КБ | 1507 | 1504 |

| vlist (1500) | DOM из content | 140 мс | 299 КБ | 1506 | 1504 |

Сравнение с UIA после кеша (часть 2): худший случай **0.44 с (UIA, Edge 1500-список) →
~0.15 с (DOM-канал: DOMSnapshot 38 мс + AX 114 мс)** — ×3 быстрее при **полном** составе.
Разница принципиальна в другом: UIA отдавал ~95 узлов (Chromium виртуализировал AX-дерево
по видимости), DOM отдаёт все 1507 — состав не зависит от того, что движок счёл нужным
материализовать. Цена: полный срез не влезает в бюджет строк модели, нужна viewport-обрезка
на стороне драйвера — с `backendNodeId` она безопасна (внеэкранные узлы живы, ref валиден,
добрать их можно без пере-снятия).

## Замер 4: сравнение трёх источников

| Источник | Даёт | Не даёт | Оценка |
|---|---|---|---|
| `DOMSnapshot.captureSnapshot` | bid, rect, путь, атрибуты, текст, все фреймы, ~40 мс на 1500 узлов | роли/имена (AX-семантика) | **Основной**: дёшево, полный, с ключом идентичности |
| `Accessibility.getFullAXTree` | роли/имена по bid | геометрию; строки списков — `generic ""`; OOPIF не разворачивает | Дополнение к DOMSnapshot для имён интерактивных элементов; как основной — нет (объём ×3, слеп к iframe) |
| DOM из content script | всё, кроме `backendNodeId` | ключ идентичности (путь — не ключ, см. замер 2); требует `<all_frames>` на каждый фрейм | Не годится для ref'ов; годится как fallback без debugger-прав |

Рабочая связка спайка — join: DOMSnapshot (bid/rect/path/attrs) + AX (role/name) по
`backendNodeId`. Сырой объём DOMSnapshot на 1500-страничном списке — 358 КБ JSON; лимит
сообщения к native-хосту 64 МиБ покрывает с запасом ×180.

## Замер 5: service worker и native messaging (Chrome for Testing 152)

Расширение загружено через `--load-extension` (в branded Chrome невозможно — см.
«Дистрибуция»), native messaging host зарегистрирован в HKCU под фактический ID
расширения. Сценарий: ~2 минуты ping/pong каждые 250 мс + лёгкий срез каждые 10
итераций, затем 45 с полной тишины (> 30-секундного таймаута SW) и контрольный ping.

- **Нагрузка (121 с): 0 разрывов.** 454 ping → 454 pong, максимальный RTT 177 мс
  (типичный — единицы миллисекунд), 50 сообщений к хосту суммарно 5 КБ. Порт
  `connectNative` держит service worker живым под трафиком — разрывов нет.
- **Тишина 45 с: SW умер несмотря на открытый native-порт** (1 disconnect). Открытый
  порт продлевает жизнь SW под активностью, но не вопреки таймауту в покое —
  «`connectNative` держит SW» верно только при обмене.
- **Восстановление автоматическое**: контрольный вызов разбудил SW, `ensurePort`
  переподключился сам (1 reconnect), ping прошёл за 1 мс; счётчик pong не потерял ни
  одного (455/455). Для продукта это значит: штатный цикл «уснул → разбудили →
  переподключился» работает без кнопки, но индикация разрыва нужна — канал молчит,
  пока нет очередного обращения.
- Замер односеансный (один прогон ~3 мин): частоту разрывов на длинной дистанции
  (часы, много вкладок) не оценивал — для решения о драйвере достаточно, что класс
  отказа («рвётся и не восстанавливается») не воспроизвёлся.

## Замер 6: cross-origin iframe

Фикстура: страница origin A (:8801) с iframe origin B (:8802).

- **`DOMSnapshot.captureSnapshot` видит содержимое чужого фрейма целиком**: в ответе два
  документа (28 + 26 узлов), узлы OOPIF приходят с текстами и атрибутами. Непроверенное в
  research-доке закрыто: собирать iframe можно одним вызовом, без per-frame обхода.
  **Нюанс**: координаты узлов второго документа — в системе самого фрейма (x:8, y:17), а
  не страницы; для клика драйвер обязан прибавлять rect iframe-элемента из родительского
  документа (+ его скролл).
- **`Accessibility.getFullAXTree` отдаёт только main frame**: чужой фрейм виден как узел
  `Iframe` без содержимого. Для AX-семантики OOPIF нужен отдельный вызов с `frameId`.
- Content script с `allFrames` видит оба фрейма, но не может собрать кросс-origin
  геометрию в одном дереве (у каждого фрейма своя система координат и своё «окно»).

## Дистрибуция: автоматической установки нет (результат, не препятствие)

Пять путей установки unpacked-расширения в branded Chrome 151 проверены практически:

1. `--load-extension` — **игнорируется** (удалён из branded-сборок в Chrome 137;
   подтверждение факта из research-дока на живой машине).
2. JS-клик «Загрузить распакованное» по WebUI через CDP — пикер открывается, путь
   вводится, **Chrome молча отбрасывает результат** (вероятно, отсутствует user gesture).
3. Настоящий клик мышью по вычисленным координатам кнопки — не доведён: foreground-lock
   ОС не отдаёт фокус окну из фонового процесса, а файловый диалог `IFileOpenDialog`
   не автоматизируется (`WM_SETTEXT` Edit игнорируется, `BM_CLICK` требует выбранного
   элемента в списке).
4. Вписывание unpacked-записи в `Preferences` профиля — **Chrome вычищает при старте**
   (контроль целостности).
5. `chrome.developerPrivate.loadDirectory` — требует `DirectoryEntry`, недоступный без
   `chrome.fileSystem`.

Плюс находка для прототипа: **поле `key` в манифесте unpacked-расширения ломает загрузку**
(диалог «Ошибка загрузки расширения», воспроизведено на CfT 152) — детерминировать ID
расширения через key нельзя; ID назначается из пути загрузки, и для `allowed_origins`
native messaging его нужно взять фактический после установки.

Вывод для ADR-008: дистрибуция браузерного канала в продакшен — **только публикация в
Chrome Web Store** (в т.ч. непубличным листингом) либо ручная установка в режиме
разработчика пользователем. Это срок (внешнее ревью) и операционный риск, не деталь
реализации — зафиксировано в research-доке ранее, теперь подтверждено экспериментально.

## Следствия для ADR-008

1. **Если браузерный канал принимается** — ключ идентичности в нём обязан быть
   `backendNodeId` (замер 1–2), срез — join DOMSnapshot+AX (замер 4), ввод —
   `Input.*` через `chrome.debugger`. Отпечаток «роль+имя+геометрия» в браузерном
   драйвере не использовать вовсе: на DOM-данных он хуже, чем на UIA.
2. **Состав среза резать по viewport** на стороне драйвера (полный состав доступен
   дёшево, но не нужен модели целиком); внеэкранные ref остаются валидными благодаря bid.
3. **Дистрибуция — срок**: начинать публикацию Web Store заранее или сознательно
   остаться на UIA. Промежуточный вариант (режим разработчика) годен только для
   tech-preview.
4. OOPIF собирается одним `DOMSnapshot.captureSnapshot` (с пересчётом координат),
   AX-имена внутри чужого фрейма — отдельным вызовом по `frameId`.
5. UIA не заменяется: `chrome://`, встроенный PDF, остальные приложения остаются на нём;
   браузерный канал — второй драйвер `desktop_ui`/`desktop_act` по решению владельца,
   как и зафиксировано в research-доке.

## Грабли, найденные прототипом (для будущего клиента)

- Формат `DOMSnapshot` в Chrome 128+ изменился: `strings` — общий массив на верхнем
  уровне (не per-document), `bounds` — массив массивов (не флэт), `attributes` —
  per-node флэт пары (не map), собственный текст — `nodeValue` #text-узлов.
- CDP-ввод (`Input.dispatchMouseEvent`) доходит только в выведенную на передний план
  вкладку (`Page.bringToFront`), иначе колесо молча теряется.
- `Accessibility.enable` не нужен для `getFullAXTree`, но узлы `role=listitem` приходят
  как `generic` — AX-слой Chromium не отображает ARIA-роль в CDP-роли без запроса полей.
- Chrome for Testing не запускает sandbox из папки репозитория («Отказано в доступе») —
  для спайка обходится `--no-sandbox`.
- Фоновая вкладка не строит layout: DOMSnapshot по неактивной вкладке пуст.
