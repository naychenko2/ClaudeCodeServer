# ADR-026: обучение LoRA персонажа из продукта

- **Статус:** предложено 2026-10-10, ждёт принятия Андреем. Разрез — Александр (задача `9a63f34f`), план — Егор (`b045651a`, дельта версий `a908a2f6`). Решения по развилкам приняла Софья по полномочиям Андрея (ночь 09→10.10); они записаны ниже как принятые, возражения Андрея их отменяют. 10.10 приведено к коду среза 1 по финальному ревью (`80ef61a1`): §5, §11, §13.
- **Основа:** ручной прогон LoRA v1 от 2026-10-09 (чат «Улучшение работы с персонажами»), режим B ([LoRA + фото-образец](../features/image-editor.md)), [ADR-020](ADR-020-local-media-audio.md) (узел `CcsAudioWorker`), [ADR-014](ADR-014-internal-subsystems.md) (границы вертикалей), [ADR-023](ADR-023-turn-context.md). Макеты: [character-lora-train.html](../mockups/character-lora-train.html), [записка](../mockups/character-lora-train-proposal.md).
- **Контракты, маршруты, JSON и коды:** [ADR-026-contracts.md](ADR-026-contracts.md).

## Контекст

LoRA персонажа сейчас обучают вручную. Ai-toolkit запускают на GPU-машине при **остановленном** ComfyUI, вручную режут кропы, пишут yaml и кладут веса в `models/loras`. Режим B (триггер + LoRA + одно фото-образец) принят на проде. Сходство по ArcFace на 4 сценах по центроиду — 0,766 при пороге 0,72. Без LoRA этот режим хуже. Значит, обучение должно быть доступно из карточки персонажа, без ручного труда и без остановки общей видеокарты.

Факты ручного прогона v1 (`andreyk.yaml`):

- ai-toolkit `a949f21`, `arch: qwen_image_2`, веса `qwen_image_2.1_int8_convrot`;
- convrot8, `low_vram`, rank 16 / alpha 16, lr 1e-4, adamw8bit, bf16;
- 2000 шагов, `save_every` 250, разрешения 512/768/1024;
- 44 кропа «голова / по пояс» из 46 фото, подписи по шаблону, без control и mask.

Замеры прогона:

- 1 ч 51 мин на 2000 шагов вместе с пробными картинками ai-toolkit;
- VRAM 12,6 из 24 ГБ;
- чекпоинт ≈80 МБ.

Сравнение чекпоинтов в режиме B (LoRA + фото, сила 0,8, 4 сцены, по 2 seed), среднее сходство:

| Чекпоинт | Среднее сходство |
|---|---|
| 1750 | **0,74** |
| 2000 | 0,69 |

У 2000 провал на спокойном лице: 0,55 против 0,70.

Пробные картинки ai-toolkit (только текст, без образца) ранжируют наоборот: шаг 2000 там лучший (0,70/0,77/0,76/0,79). В бою стоит `andreyk_qwen21_v1_000001750.safetensors`. Попытка v2 в edit-режиме (target, control, mask, rank 32) дала 7 с на шаг и сходство 0,65, это хуже, чем без LoRA.

Дыра, которую фича вскрыла. Список LoRA в ComfyUI общий на инстанс. Ни `GET image-editor/loras`, ни проверка имени в патче, ни сборка запроса генерации владельца не проверяют: любой владелец видит и может выбрать чужую LoRA по имени. Закрывается шагами 1а/1б плана (`LoraNamespace`), до этой фичи.

## Решения

### 1. Разрез и шов

Обучение — это новая операция того же движка local-media: узел-воркер в **общей очереди ComfyUI**, как `rvc_train`. Отдельной GPU-службы и отдельной очереди нет.

| Слой | Что | Где |
|---|---|---|
| Core | шов `ILocalLoraTrainer` и DTO; `LoraNamespace` — видимость и пути весов | `ClaudeHomeServer.Core/Services/ImageEditor/` |
| Images | `LocalMediaService.Lora.cs` (старт, отмена, сбор), `LocalLoraTrainerAdapter.cs` (реализация шва), граф `ComfyWorkflows.Lora.cs`, ветка сбора без записи в проект | `ClaudeHomeServer.Images/Services/LocalMedia/` |
| GPU | op `lora_train` и `lora_delete` в узле `CcsAudioWorker`, семейство `lora` в `workers.json`, `worker_lora.py` в своём venv ai-toolkit, yaml из шаблона | `deploy/comfyui/lora/` + строки в `deploy/comfyui/audio/ccs_audio_worker/__init__.py` |
| ImageEditor | хранилище обучающих фото, записи версий `runs/<runId>.json`, ручки, фоновый доводчик | `ClaudeHomeServer.ImageEditor/Characters/`, `Controllers/` |
| Фронт | секции «Фото для обучения», «Обучение», «Версии» | `frontend/src/features/imageEditor/characters/` |

- **Отдельный шов, а не расширение `ILocalImageMedia`.** У того байтовый контракт на секунды: тикет — `prompt_id`, результат держится в памяти. У обучения другой жизненный цикл: часы, хранение в сторе, переживание рестарта, файлы на GPU.
- **Граница вертикалей:** `ImageEditor → Core ← Images`, прямой ссылки нет. Шов необязательный (`ILocalLoraTrainer?`): нет подсистемы `images` → ручки отвечают `503 no_seam`, а не 500. Сторожа `SubsystemBoundary*` не меняются.
- **Точка правды о ходе обучения одна — `LocalMediaJobStore`** (`data/local-media-jobs.json`): статус, `prompt_id`, ETA, итоговое имя весов. В проекте лежит запись версии `characters/<slug>/lora/runs/<runId>.json` — указатель `jobId` и итог. Прогресс туда не копируется.
- **Узел.** Переиспользуем `CcsAudioWorker`. Механика та же: занять очередь, выгрузить модели, запустить venv, ждать, уважать `/interrupt`. Цена — имя узла вводит в заблуждение. Это отмечаем в README, дубль ~200 строк не заводим.

### 2. Изоляция весов (принятое решение 1)

- Веса владельца лежат только в `models/loras/ccs/<ownerKey>/…`, где `ownerKey` — `ownerId` без дефисов в нижнем регистре.
- Прогон — в `ccs/<ownerKey>/<slug>-<runId>/<slug>.safetensors`. Каталог строит **узел**, из запроса он берёт только сегменты, проверенные регэкспами.
- **Видимость решает одна функция — `LoraNamespace.VisibleTo(ownerId, name)`**, и вызывается она в трёх точках:
  1. `GET image-editor/loras` — фильтр списка;
  2. патч LoRA персонажа и `connect` версии — отказ `403 lora_not_visible` до записи;
  3. `CharacterStore.ForRequest` — LoRA, не видимая владельцу, отбрасывается из `CharacterRef`. Манифест — обычный файл проекта, агент может вписать в него чужое имя через Write.

  Своей проверки префикса нигде больше не заводим.
- **Ручные LoRA вне `ccs/`** (например `andreyk/…`) переносятся в `ccs/<ownerKey>/…`, манифесты переписываются (шаг 1в). Миграция катится **в одно окно с фильтром**: перенос файлов → перепись манифестов → выкатка фильтра. Иначе фильтр сразу отрежет LoRA у живых персонажей.

### 3. Защита от захвата карты (принятое решение 2)

Обучать может любой пользователь с local-media. Защита — **на бэкенде**, кнопка в UI её не заменяет. Все проверки выполняются под тем же `_submitGate`, что и постановка задач, до загрузки фото и до очереди:

1. Тумблер `LocalMedia:LoraTrainEnabled`, по умолчанию `false`. Выключен → `403 disabled`.
2. **Одно обучение на инстанс:** есть незавершённая задача `lora_train` любого владельца → `409 gpu_busy` с `busyUntil`. Очереди обучений нет, второе не ставится. Новый счётчик `LocalMediaJobStore.ActiveLoraTrainCount()`: прежний `ActiveHeavyCount(owner)` считает по владельцу.
3. **Одно активное обучение на владельца** → `409 owner_busy`. Своё обучение — это и `gpu_busy`. Код `owner_busy` отдаётся первым: человеку важнее «у тебя уже идёт».
4. **Шаги — только из пресета.** По проводу едет имя пресета, а не число. Таблица пресетов есть у бэкенда (ETA) и у воркера (yaml). Неизвестный пресет → `400 bad_preset`.
5. Обычные лимиты local-media остаются: `MaxQueuedPerOwner`, `MaxComfyQueue` → `409 queue_full`.
6. **Отменить чужое обучение может админ** (`User.IsInRole("admin")`) — ручкой уровня инстанса. Владелец отменяет своё из карточки персонажа.
7. Перед стартом UI требует подтверждение «видеокарта будет занята ≈ N мин, генерации встанут в очередь». Бэкенд принимает старт только с `confirm: true`. Защиты это не добавляет, но запуск по ошибке без явного жеста человека исключён.

Агенту инструмента запуска в срезе 1 **нет**: это часы GPU для всех, запуск решает человек. Состав `tools/list` не меняется.

### 4. Очередь (принятое решение 3)

- **Срез 1 — одна задача ComfyUI на всё обучение** с `timeout_minutes` 240 (потолок узла). Генерации всех владельцев ждут её в той же очереди. Об этом предупреждает подтверждение.
- **Отмена:**
  - ждущую задачу снимает `POST /queue {"delete":[id]}`;
  - идущую — `POST /interrupt {"prompt_id": id}`. С `prompt_id` ComfyUI прерывает только этот прогон, проверено на 0.37 (`ComfyClient.InterruptAsync`);
  - узел ловит прерывание `throw_exception_if_processing_interrupted` и убивает группу процессов воркера.
- **Рестарт бэкенда.** Задачу держит `LocalMediaJobStore`, результат добирает `LocalMediaCollector`, запись версии доводит `LoraTrainingFinisher`. `watch_start` и Monitor к продуктовой задаче отношения не имеют: это будильники агента.
- **Рестарт `comfyui-h3`** во время обучения убивает прогон. Задача станет `failed`, повтора нет, человек перезапускает. Повтор упавшего сегмента — забота среза 2.
- **Сегменты** (~500 шагов с продолжением с чекпоинта; генерации проходят между ними) — срез 2. Их цену решает время старта из замера 1г.

### 5. Датасет и хранение обучающих фото (принятое решение 4)

- Отдельная загрузка **20–50 фото «для обучения»**: меньше 20 — `400 too_few_photos` до очереди, больше 50 не принимаются. Фото персонажа (3–10) не участвуют.
- **Хранилище — в `data/` вне проекта:** `data/lora-training/<ownerKey>/<projectKey>/<slug>/<sha16>.<ext>`.
  - Ключ — по владельцу, проекту и персонажу: slug уникален только внутри проекта.
  - Имя файла — первые 16 hex SHA-256 содержимого. Дубль отсекается по имени.
  - Путь собирается только через `SafePath.Join` от корня `data`; сегменты проходят регэкспы.
- **Почему не `characters/<slug>/training/` в проекте:** до 50 × 8 МБ = до 400 МБ на персонажа оседали бы в git проекта, в синке базы знаний и в истории файлов.
- **Бэкап — исключены (решение Софьи, 10.10).** Каталог `lora-training/` не едет в основной архив: это биометрия (лица) и до 400 МБ на персонажа, а основной архив уезжает в облако. Фото — исходные данные человека, после восстановления их загружают заново; веса и записи версий не теряются. Исключение — одна строка в `BackupPaths.ShouldInclude` по образцу кешей и тест `BackupPathsTests`; формат не меняется, `BackupSchema.Version` не трогаем.
- Проверки на загрузке, бэкенд, без GPU:
  - формат `jpg/png/webp` по сигнатуре (`ImageFormatSniffer`);
  - ≤ 8 МБ (`CharacterStore.MaxPhotoMb`);
  - короткая сторона ≥ 512 px: это наименьшее разрешение обучения, порог — решение ADR, а не замер;
  - не больше 50;
  - дубли.
- Проверку «одно крупное лицо» делает воркер при нарезке. Отброшенные фото с причинами возвращаются в итоге. Годных меньше 15 → прогон падает с `too_few_faces`. 15 — порог этого ADR, не замер. Предпроверка лиц на загрузке — срез 2 (узел `CcsFaceSimilarity`).
- **`photosHash`** = `sha256:` + hex SHA-256 от отсортированных имён фото, соединённых `\n`. Имена — хеши содержимого, поэтому порядок загрузки на результат не влияет. Считается при старте и пишется в запись версии.
- **Фото на GPU** доезжают штатной загрузкой ComfyUI `POST /upload/image` с `type=input` и `subfolder=ccs/<ownerKey>/<runId>`, тем же `ComfyClient.UploadInputAsync`.
  - ComfyUI сам не пускает подпапку за пределы `input`, подпапку строит `LoraNamespace`, имена — `<sha16>.<ext>`.
  - Произвольных путей на GPU-машине бэкенд не пишет никогда.
  - Узел принимает только входы под `ccs/<ownerKey>/<runId>/` и после прогона (успех, ошибка, прерывание) удаляет этот каталог сам.
- **Кропы и подписи — на воркере:** InsightFace, «голова» (2,6 × лица) и «по пояс» (5,5 × лица), квадрат, как у v1. Подпись — шаблон `photo of <trigger>, <head shot|waist-up shot>`.
  - Классовое слово v1 («a bald man») шаблон не воспроизводит. Это риск по качеству, его ловит приёмка.
  - control и mask не используем.

### 6. Триггер (принятое решение 5)

По умолчанию `ccs` + slug без дефисов, обрезанный до 24 символов. Формат `^[a-z][a-z0-9_]{2,23}$`. Человек может сменить его при старте, иначе — `400 bad_trigger`. Триггер пишется в запись версии и при подключении копируется в `providers.local.trigger`.

### 7. Пресет и чекпоинт (принятое решение 7)

Срез 1 — один пресет `standard`: параметры v1 (rank 16, alpha 16, lr 1e-4, adamw8bit, bf16, convrot8, `low_vram`, 512/768/1024), **2000 шагов, `save_every` 250**. Результат — **чекпоинт 1750**.

Обоснование:
- в режиме B, в котором LoRA реально работает, 1750 дал 0,74 против 0,69 у 2000;
- 2000 провалился на спокойном лице;
- именно 1750 прошёл приёмку 0,766 и стоит в бою.

Доказательство слабое: один прогон, 2 seed. Поэтому чекпоинт — константа пресета на воркере, а не зашитое в бэкенд число: смена — правкой одной строки шаблона.

- Воркер переименовывает `*_000001750.safetensors` в `<slug>.safetensors`, остальные чекпоинты удаляет.
- Обучать сразу до 1750 не стали: в срезе 2 чекпоинт 2000 нужен кандидатом автовыбора.
- Пробные картинки ai-toolkit в продукте **выключаются**. Они не нужны срезу 1, ранжируют иначе, чем режим B, и съедают время из 1 ч 51 мин. Если на коммите `a949f21` выключить их нельзя, Марк оставляет их и ETA учитывает это.

### 8. Версии и подключение (принятое решение 6)

- Каждое обучение — **версия**: запись `characters/<slug>/lora/runs/<runId>.json`, статусы `training | ready | failed | cancelled | deleting`.
- **Активная LoRA одна:** `providers.local.lora` (имя файла) + `trigger` + `strength`. `ReadLora`, `ForRequest` и адаптер генерации не меняются.
- **«Подключена» не хранится, а выводится:** `run.loraFile == providers.local.lora`. Указателя на `runId` нет, иначе получится вторая точка правды со старым разделом «LoRA для локальной модели».
- **Автоподключение — только если `providers.local.lora` пусто** («первое обучение»). Если подключена ручная LoRA, версия ждёт кнопку «Подключить», иначе обучение незаметно подменило бы рабочую ручную LoRA. Все последующие версии подключаются только кнопкой.
- **Подключение** пишет `lora` и `trigger` из записи. `strength` остаётся прежней, без неё ставится 0,8. Запись идёт через `CharacterStore` (`CharacterLoraPatch.Set`) с теми же проверками `VisibleTo` и «есть в списке ComfyUI», что у патча.
- **Предел — 5 версий** на персонажа: считаются `ready` + `training`. Шестой старт → `409 version_limit` до очереди.
- **Удаление версии.**
  - Подключённая сначала снимается (`CharacterLoraPatch.Removal()`), затем запись получает статус `deleting`.
  - Файл на GPU стирает op `lora_delete` (каталог прогона строит узел) в общей очереди. Пока идёт чужое обучение, это до ≈2 ч.
  - После успеха доводчик стирает запись. Запись в `deleting` в список версий не попадает.
- **`photosHash`:** пометка «фото изменились после обучения» сравнивает текущий хеш с хешем **подключённой** версии. Автопереобучения нет.

### 9. Прогресс

Канала прогресса в `CcsAudioWorker` нет, но в продукте он уже есть: `ComfyClient.ListenProgressAsync` слушает WebSocket `/ws`, событие `progress` с `prompt_id`. По нему видео-адаптер показывает шаги сэмплера. Решение — **сообщение узла, а не файл и не опрос**:

- воркер печатает `CCS_PROGRESS {"step": n, "total": m}`;
- поток-читатель узла запоминает последнее значение;
- цикл ожидания узла, это поток исполнения задачи, раз в 0,5 с вызывает `comfy.utils.ProgressBar(m).update_absolute(n, m)`;
- ComfyUI сам шлёт `progress` с `prompt_id`. Вызов из потока-читателя не годится: контекст исполнения ComfyUI привязан к потоку задачи.

Бэкенд держит один слушатель на идущее обучение (их на инстансе не больше одного) и хранит последний шаг **в памяти** адаптера. В стор и в манифест шаг не попадает.

После рестарта бэкенда слушатель поднимается при первом `GetAsync`. До первого события шаг неизвестен. Сокет недоступен → UI показывает **ETA без шагов** («осталось ≈ N мин» по `StartedAt + EtaSeconds`), тексты это предусматривают. Шаг 0 при статусе `running` означает «готовим фото и загружаем модель».

### 10. Политика ОЗУ и выгрузки — по замеру 1г (10.10)

Замер Марка (задача `1bc8f6a1`): конфиг v1, 200 шагов на условие, сэмплер раз в секунду, OOM и своп — 0. Логи и CSV — `.cc-attachments/lora-measure/results/` основного репозитория.

| Условие | Пик ОЗУ WSL (из 52 208 МБ) | Пик VRAM (из 24 576 МБ) | Старт до 1-го шага | с/шаг |
|---|---|---|---|---|
| (в) ComfyUI остановлен | 17 171 МБ (32,9 %) | 17 185 МБ (69,9 %) | ≈125 с (холодный кэш) | 2,27 |
| (б) ComfyUI жив, после `/free` | 17 917 МБ (34,3 %) | 17 587 МБ (71,6 %) | ≈97 с | 2,27 |
| (а) ComfyUI жив, модель загружена | 33 804 МБ (64,7 %) | **24 191 МБ (98,4 %)** | ≈120 с | 2,31 |

Падение gpuhost 09.10 вызвано не замером: перезагрузку запустил Windows Update (событие 1074, `MoUsoCoreWorker.exe`), событий OOM не было.

**Решение — ветка (Б): воркер внутри общей очереди ComfyUI с полной выгрузкой перед стартом.**
- Узел для op `lora_train` выгружает **все** модели. У семейства `lora` нет `vram_mb`, поэтому идёт путь `soft=False`: `mm.unload_all_models()`, `gc.collect()`, `soft_empty_cache(force=True)`. Это тот же эффект, что `/free` с `unload_models` и `free_memory` в замере (б).
- Бюджетная выгрузка (`vram_mb`) для `lora` **запрещена**. Узкое место — не ОЗУ, а VRAM: в (а) свободными оставались 385 МБ на фазе квантизации. При любой новой правке узла ветка без выгрузки для `lora_train` — дефект.
- Останавливать ComfyUI не нужно: (б) и (в) идут с одинаковой скоростью (2,27 с/шаг), разница по ОЗУ 0,7 ГБ. **Ветка (Н) отвергнута:** её условие «пик ОЗУ (б) > 45 ГБ» не наступило (17,9 ГБ, запас 65,7 %), а остановка ComfyUI (Н1) не даёт ни скорости, ни памяти.
- Генерации, пришедшие во время обучения, ждут в очереди (§4). После обучения первая из них грузит свою модель заново — это цена, а не дефект.

**ETA.** Формула в коде: шаги × с/шаг + `LocalMedia:LoraTrainStartSeconds`.
- 2,35 с/шаг (ручной прогон) оставляем: замер дал 2,27–2,31, и сохранение чекпоинтов каждые 250 шагов в замер не входило — остаётся запас.
- Старт — **150 с** вместо дефолта 300: замерено 97–125 с с базовым сэмплом, плюс запас на холодный кэш. В продукте пробные картинки выключены, поэтому реальный старт будет короче, ≈50–77 с.

- Полные 2000 шагов с сохранением чекпоинтов.
- Выбросы VRAM короче секунды между отсчётами сэмплера.

### 11. Уборка

- **`deleting`** — доводчик на каждом круге зовёт `DeleteRunAsync`: `Pending` → ждёт, `Deleted` → стирает запись, `Failed` → повтор на следующем круге.
- **Входы прогона** (`input/ccs/<ownerKey>/<runId>/`) удаляет узел в `finally`. Если процесс ComfyUI упал, их уберёт `lora_delete` при удалении версии. `LocalMediaCleanup` их не трогает: имена не подходят под его шаблон, и это правильно.
- **Неуспешный прогон** — узел удаляет свой каталог весов в `finally`.
- **Обучающие фото при удалении персонажа или проекта — срез 1.** Персонажа убирает ручка удаления в `ImageEditorController` (`CharacterTrainingPhotos.Purge`). Проект удаляет Main, который на ImageEditor не ссылается, поэтому уборка идёт через шов `IProjectTrainingPhotoCleaner` в Core: реализация в ImageEditor, нет подсистемы — `null`, шаг пропускается. Тесты — `CharacterTrainingPhotosTests`, `ProjectsControllerTrainingPhotosCascadeTests`.
- **Сироты весов** при удалении персонажа или проекта (до 5 × 80 МБ на GPU) — **срез 2**. Остаточный риск фиксируем: место на диске, а не изоляция, потому что видимость режет `VisibleTo`.

### 13. Решения по ходу реализации (Андрей и Софья, 10.10)

Приняты по ходу среза 1, записаны как принятые:

1. **Миграция ручных LoRA (шаг 1в) — только `andreyk`.** Каталоги `bfs` и «NSFW Qwen Lora» не переносятся: они остаются вне `ccs/`, и после выкатки фильтра `VisibleTo` их не видит никто. Перенос весов — `deploy/comfyui/lora/migrate-manual-loras.sh --only andreyk`, перепись манифестов — `scripts/migrate-lora-manifests.py` для владельца этих весов.
2. **Отмена уже завершённого обучения — `204`, идемпотентно** (и у владельца, и у админа). Фронт после отмены перечитывает статус и видит итог. Контракт — [ADR-026-contracts.md](ADR-026-contracts.md), §7.2 и §7.4.
3. **ComfyUI недоступен — версия остаётся `training`.** Доводчику без списка LoRA нечем автоподключить, поэтому он не переводит запись ни в `ready`, ни в `failed`, а доводит её на следующем круге после восстановления. Тест — `LoraTrainingFinisherTests.ComfyUnavailable_KeepsTraining_ThenReadyAndConnectedAfterRecovery`.
4. **Обучение без задачи в сторе — код `lost`.** Запись `training`, чьей задачи `LocalMediaJobStore` уже не знает, переходит в `failed` с кодом `lost`, а не висит вечно. Реализация — отдельная правка 6г (Денис), в этой версии ADR она ещё не влита.

## Последствия

- **Плюсы:**
  - обучение из карточки без ручного труда;
  - видеокарта не останавливается (в ветке (Б));
  - дыра видимости LoRA закрыта одной функцией в трёх точках;
  - ход обучения переживает рестарт бэкенда;
  - версии позволяют сравнить и откатиться.
- **Минусы:**
  - генерации всех владельцев ждут до ≈81 мин (оценка ETA §10) за чужим обучением, это смягчает только предупреждение;
  - имя узла `CcsAudioWorker` вводит в заблуждение;
  - до 400 МБ фото на персонажа в `data/`; в архив они не едут, после восстановления их загружают заново;
  - сироты весов на GPU до среза 2;
  - чекпоинт 1750 обоснован одним прогоном.
- **Инварианты, которые фича держит:**
  - граф и запись на GPU — только из шаблонов (`ComfyWorkflows` + yaml-шаблон воркера); путь, yaml или число шагов из запроса не принимаются;
  - per-owner — `LoraNamespace` + `ownerKey` во всех путях;
  - состав `tools/list` не меняется;
  - обучение идёт в процессе `comfyui-h3`, а не в `ccs-agents.slice` (урок OOM 09.10);
  - ручные прогоны на gpuhost — только `systemd-run --user`.
- **CLAUDE.md:** одна строка в разделе «Генератор картинок» (шаг 8 плана, текст — в контрактах, раздел «Карта»).

## Критерии приёмки среза 1

1. Новая LoRA, обученная из продукта на 20–50 фото пресетом `standard`, в режиме B с фото-образцом даёт **среднее сходство по ArcFace ≥ 0,72 по центроиду** на 4 эталонных сценах. Это те же сцены и инструмент, что у приёмки v1: `.cc-attachments/char-tests/tools/arcface_score.py`.

   - первое обучение подключается само, второе — нет;
   - подключить, вернуться, удалить подключённую;
   - ручная LoRA не подменяется;
   - `version_limit`;
   - второй пользователь видит `gpu_busy` и не видит и не может подключить чужое (`403`);

   - рестарт бэкенда во время обучения;
   - фото без лица отброшено с причиной.
