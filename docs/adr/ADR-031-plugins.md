# ADR-031: Плагины — пакет из существующих примитивов, мост панели v1, модель прав

- **Статус:** Принято, 2026-10-17 (Александр); принято Софьей до старта пачки C1 (шаги 3.1/3.2).
- **Основа:** разрез «Плагины и build-it-yourself UX» (задача `ab0682be`), план Егора (задача `b5215b40`, риск 5 — «контракт моста только в задаче»), эпик `802bb754`. Связанные решения: [ADR-014](ADR-014-internal-subsystems.md) (подсистемы и сторожа границ), [ADR-015](ADR-015-cli-profile-sync-zones.md) (зоны профилей CLI), [ADR-016](ADR-016-local-projects.md) (локальные проекты, `ProjectCapabilities`), [ADR-012](ADR-012-mcp-over-http-transport.md) (тулсеты MCP), [ADR-016 Viaduct](ADR-016-viaduct-architecture-section.md) (образец моста sandbox-iframe).
- **Флаги:** `plugins-mvp` (установка, skills/команды, панели) и `plugins-build-yourself` (черновики агентом). Оба `Default: false`, заводятся шагом 1.1. Плюс тумблер подсистемы `Subsystems:plugins:Enabled`.
- **Карта фичи:** [docs/architecture/plugins.md](../architecture/plugins.md).

## 1. Контекст и силы

Нужна плагин-система с build-it-yourself UX: пользователь одним промптом просит «добавь работу с Linear», и агент собирает пакет из панели, slash-команды и навыка для персон. Образец — bb (getbb.app), где так устроены GitHub, память агента, расписания.

Силы, которые тянут решение в разные стороны:

- **Недоверенный код.** Пакет пишет агент или чужой автор. Веб-морда торчит наружу: код плагина с доступом к JWT, стору или DOM хоста — это RCE в браузере владельца.
- **Многопользовательность.** bb однопользовательский, у нас изоляция per-owner — первое требование. Профили CLI (`data/claude-profiles/{key}`) и `~/.claude/skills` общие на инстанс и зеркалятся синком (ADR-015): всё, что туда положено, получают все владельцы.
- **У нас уже есть почти всё.** Нативный формат плагина Claude CLI (`skills/`, `commands/`) с доставкой флагом `--plugin-dir` (есть в CLI 2.1.301, повторяемый, действует только на запуск). Sandbox-iframe с мостом `postMessage` (`WidgetView`, `ViaductFrame`). Личный реестр MCP с allow-list. `McpSecretStore`, `SsrfGuard`, `SafePath.Join`, `RecursiveDirectoryWatcher`.
- **Подпись запуска CLI.** Всё, что влияет на аргументы процесса CLI, перезапускает его вместе со всеми MCP-серверами («Stream closed»). Набор зависит только от свойств сессии, не от хода.
- **Правило вертикалей.** Плагину нужны данные Notes и Tasks, но вертикаль не может ссылаться на другую вертикаль (ADR-014).

### Рассмотрено и отвергнуто

| Вариант | Почему нет |
|---|---|
| Панель плагина в основном бандле / Module Federation remote от пользователя | Недоверенный код получает JWT, весь стор и DOM хоста |
| Серверный код плагина: C# через `DynamicModules` или JS-рантайм в бэкенде | Полное доверие, нет выгрузки, упавший плагин гасит хост. Для логики есть MCP |
| Внешний YARP-модуль на плагин | Отдельный процесс на каждый плагин — слишком тяжело для «панель + навык» |
| Своё хранилище навыков и свой механизм команд | Вторая точка правды рядом с CLI. Нативный формат уже умеет namespacing `plugin:skill` |
| Запись навыков в `~/.claude/skills` или в профиль CLI | Утечка между владельцами: каталоги общие на инстанс |
| Один `kind` на плагин (`panel`/`command`/`skill`) | Запрещает главное — «один промпт → панель + команда + навык» |
| Права на каждый навык | Навык — текст для модели, он ничего не исполняет. Права на нём ничего не ограничивают |
| Окно «разрешить?» на каждый вызов | Усталость от согласий: через неделю все жмут «да» |
| HMR и dev-сервер для панелей | Пересобирать нечего: бандлера нет, серверного кода нет |

## 2. Решение

### 2.1. Плагин = пакет из существующих примитивов

Своего рантайма для плагинов не строим. Плагин — пакет под одним манифестом и одним согласием человека:

| Вклад | На чём едет |
|---|---|
| Навык и slash-команда | Нативный формат плагина CLI, доставка `--plugin-dir` из каталога владельца. Команда = навык с `user-invocable`, отдельного механизма команд нет |
| Панель | Sandbox-iframe без `allow-same-origin` с мостом v1 (§3) |
| Логика с внешним миром (Linear, GitHub) | Запись личного реестра MCP (ссылка из манифеста) или серверный прокси по праву `net:{host}` |
| Триггер (после MVP) | Существующие `TriggerSources`, только ссылка |

**Серверного кода плагина в процессе бэкенда нет и не будет.**

### 2.2. Манифест

У пакета два манифеста: нативный CLI `.claude-plugin/plugin.json` (из него CLI берёт имя
пакета — спайк plugin-dir-name-spike-2026-10.md) и наш `ccs-plugin.json` (источник правды
схемы ниже; `id`/`contributes`/`permissions`). Корневой `plugin.json` — не нативный манифест
(R10-1): без `.claude-plugin/plugin.json` CLI назовёт пакет именем каталога (`{version}`),
что ломает привязку навыка по slug.

```json
{
  "id": "local-3f9a/linear-notes",
  "name": "Linear из заметок",
  "version": "0.1.0",
  "bridge": { "v": 1 },
  "contributes": {
    "skills":   ["skills/linear-sync"],
    "commands": ["commands/linear.md"],
    "panels":   [{ "id": "main", "slot": "sidebar", "entry": "panel/index.html", "title": "Linear" }],
    "requires": {
      "mcp":     ["linear"],
      "secrets": [{ "name": "LINEAR_TOKEN", "required": true }]
    }
  },
  "permissions": {
    "requested": ["notes:read", "net:api.linear.app", "secret:LINEAR_TOKEN"]
  }
}
```

- `id` — глобальный `{publisher}/{slug}`. В MVP publisher = `local-{ownerShort}`, позже — автор каталога.
- `contributes` — набор вкладов: `skills`, `commands`, `panels`. Любой из массивов может быть пуст, хотя бы один вклад обязателен. `requires` вкладом не считается.
- `contributes.requires.secrets` — секреты пакета: имя и признак `required`. Обязательный секрет, не заданный владельцем, блокирует выдачу прав (grant), а не саму установку (minor 11: свести с фактическим поведением `PluginsController.Grant`).
- `permissions.requested` — **запрошенные** права, потолок. Выдаёт их человек (§4).
- `bridge.v` — версия моста панели, с которой пакет собран (§3.5).
- Неизвестные поля разбор игнорирует (forward-compat). Источник правды схемы — модель `Core/Models/Plugins/PluginManifest.cs`; пример выше обязан с ней совпадать.

**Обоснование выбора формы.** Три поля — объекты, а не скаляры и плоские массивы, чтобы расширять их без ломающего изменения формата:

- `bridge` — объект: версия моста v2 добавится как `{ "v": 2 }` со своими полями рядом, разбор v1-пакетов не меняется.
- `secrets` — объекты: признак `required: true` блокирует выдачу прав (grant), пока секрет не задан (решение В2 макетов; minor 11: не «установку»). Строкой это не выразить.
- `permissions` — объект: сейчас в нём единственное поле `requested`, позже рядом может встать, например, `granted` для предвыданных прав каталога без смены типа поля. Выданные человеком права при этом живут в записи установки (§2.3), не в манифесте.

### 2.3. Хранилище и установка

```
data/plugins/{ownerId}/
  packages/{id}/{version}/   — неизменяемые пакеты
  installed.json             — записи установки
  _drafts/{slug}/            — черновики build-it-yourself
```

- Запись установки ссылается на пакет по **id + version + sha256**, хранит **выданные** права (`granted`), `enabled` и источник.
- **Источник установки — строка, а не enum** (`"draft"`, `"upload"`, позже `"catalog:{ref}"`); неизвестные значения при разборе терпим. Урок `McpCatalogRef`: новое значение enum при откате кода унесло бы файл владельца в `.corrupt`.
- Пакет проходит **валидатор по allow-list файлов**: `ccs-plugin.json` (наш), `.claude-plugin/plugin.json` (нативный CLI, **обязателен** — его отсутствие `deny-native-manifest-missing`, пустой/отсутствующий `name` — `deny-name-missing`), `skills/**/SKILL.md` и вспомогательные `.md`, `commands/*.md`, `panel/**` (статика). Корневой `plugin.json` в allow-list не входит (R10-1). Отказ на всё остальное, прежде всего `hooks/`, `.mcp.json`, `bin/`, `settings.json`, `agents/` — это исполнение кода или обход allow-list MCP. Отказ на символические ссылки, выход за корень, превышение размера и числа файлов. Окончательный перечень запрещённого уточняет спайк (шаг 0).
- Каталог пакетов монтируется в песочницу **read-only**.

### 2.4. Вертикаль `ClaudeHomeServer.Plugins`

Одна новая вертикаль (`IAppSubsystem`, ключ `plugins`, тумблер `Subsystems:plugins:Enabled`): хранилище, валидатор, REST установки и согласия, мост панели, прокси `net:`, тулсет `plugins`.

В Core — только модели (`Models/Plugins/`) и два шва:

- `IPluginDirSource` — «каталоги плагинов для запуска (owner, persona, project)». Его читает Llm (`ClaudeSession`) опциональной зависимостью (`?? []`).
- `IPluginCapability` — обработчик операций одного права. Регистрирует **вертикаль-владелец данных**: Notes — `notes:read`, Tasks — `tasks:read`. Направление `Notes → Core ← Plugins`, ссылки вертикаль → вертикаль нет.

Отключаемость по ADR-014: выключенная подсистема не регистрируется; мост и прокси отвечают честным 503 с причиной; обязательный параметр конструктора от Plugins вне вертикали — дефект.

**Событие `plugins_changed`: живое обновление панели.** Установка плагина изменилась (установка/обновление/принятие черновика, grant прав, enable/disable, uninstall, запись/удаление секрета) — панель в UI подхватывает новую версию/права/секреты без ручного переоткрытия. Точка испускания — **хранилище, а не контроллеры**: `PluginStore` (`SaveInstalled`/`Update`/`Update<T>`) и `PluginSecretsStore` (`Set`/`RemoveSecret`/`RemovePlugin`) — все записи установки/секретов идут через них, поэтому новая ручка не «забудет» испустить событие. `Update<T>`/`RemoveSecret`/`RemovePlugin` — только при фактическом изменении (no-op не шумит). Брокастер — Core-шов `ISessionBroadcaster` (необязательный параметр конструктора: DI авто-инъектит, в тестах и выключенной подсистеме — null, запись без события). Отправка `ToOwner(ownerId)` — **после записи, вне `lock`** стора; полезной нагрузки нет, клиент сам перечитывает `GET /api/plugins`; чужой владелец ничего не получает.

### 2.5. Доставка навыков и команд

- `ClaudeSession` добавляет `--plugin-dir` на каждый включённый пакет владельца из `IPluginDirSource`.
- Набор считается **только от свойств сессии** (владелец, персона, проект), никогда от хода. Установка, удаление и смена версии вступают в силу **со следующего хода**: `installed.json` перечитывается на каждый ход, и процесс CLI перезапускается, если состав `--plugin-dir` изменился. Это закрывает риск 2 плана Егора.
- Персоне плагин открывает привязка типа `Skill` с target `plugin:{id}/{skill}` (единый формат, разбор — `Core/Models/Plugins/PluginSkillTarget`; новый enum не нужен). Гейт — на уровне всего плагина: `--plugin-dir` грузит пакет целиком, фильтровать навыки внутри — значит переписывать пакет на лету.
- Пакеты не попадают ни в `~/.claude/skills`, ни в `data/claude-profiles/*/plugins`: `LlmProviderRegistry.SyncDirs` синхронизирует папку `plugins` профилей между собой, и туда наши пакеты класть нельзя.
- Плагины профиля CLI (`installed_plugins.json`, которые уже читает `SkillsService`) и плагины владельца — **разные источники**, в API и UI метятся явно.
- **Per-owner mount (M6).** В общей `cc-sandbox` bind-mount — корень `data/plugins`, но эффективная per-owner изоляция — через `--plugin-dir`, который указывает только на подкаталог `data/plugins/{owner}/` владельца. Чужие пакеты в аргументы не попадают. **Секреты в mount не едут никогда**: они живут в `McpSecretStore` (не в `data/plugins`), поэтому ни на устройство, ни в контейнер не попадают.
- **Флаг не гейтит доставку (M11, осознанно).** Бэкенд НЕ проверяет `plugins-mvp` при доставке `--plugin-dir`: флаг гейтит установку и UI, а не доставку. Если владелец снимет флаг после установки, CLI продолжит получать пакеты — доставка идёт от записи установки, а не от флага (флаг не «выключает» уже установленные пакеты задним числом).

### 2.6. Build-it-yourself

- Агент пишет **только** в `data/plugins/{owner}/_drafts/{slug}/` и **только** через MCP-тулсет `plugins`: `draft_create`, `draft_write_file`, `draft_validate`, `draft_preview`. Сервер пишет через `SafePath.Join` и прогоняет валидатор. Встроенный Write не годится: у container-владельцев каталог не смонтирован на запись, у local-владельцев Write пишет куда угодно.
- **Инструментов install, approve и grant у агента нет по построению**, это держит сторож на состав тулсета. Принять черновик, выдать права, ввести секрет может только человек кнопкой и только по пользовательскому JWT; сервисный JWT получает 403.
- Всё вне пакета (добавить сервер в реестр MCP, завести токен) агент только **предлагает**, делает человек.
- Состав `tools/list` тулсета `plugins` не зависит ни от флага, ни от хода; флаг проверяется на бэкенде отказом.

## 3. Мост панели v1

### 3.1. Песочница

- Панель монтирует компонент хоста `PluginFrame` в `<iframe sandbox="allow-scripts">` **без `allow-same-origin`**. Origin фрейма непрозрачный: ни куки, ни JWT, ни хранилища хоста.
- Навигация iframe не несёт заголовок `Authorization`, а все ручки у нас под JWT Bearer. Поэтому в MVP хост сам забирает entry панели по REST (с JWT, только из установленного пакета владельца) и монтирует её через `srcdoc` (как `WidgetView`). Перед монтированием хост вставляет CSP: `default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data: blob:; font-src data:; connect-src 'none'; form-action 'none'; base-uri 'none'; frame-src 'none'` (константа `PANEL_CSP`, та же стоит в оболочке, §3.6), а также шим `plugin-kit` (мост и CSS-токены тем). Панель монтируется во фрейм-оболочку, а не прямо в страницу хоста: устройство описано в §3.6.
- Следствие: **панель MVP — один самодостаточный HTML** (скрипты и стили инлайн, потолок размера задаёт валидатор). Многофайловые панели — открытый вопрос (§7).
- React хоста во фрейм не передаётся. Панель — статический HTML/ESM, при желании со своим vendored preact. Шим `plugin-kit` (хост вставляет его в `<head>`) даёт панели три вещи:
  - **Токены тем `--cc-*`** — **значения доставляет хост, а не шим** (S8): CSS-переменные хоста `--c-*` во фрейм не доходят, поэтому хост читает **свои** вычисленные `--c-*` текущей темы и мапит их в `--cc-*` (`CC_TOKEN_MAP`/`readHostTokens` в `panelTokens.ts`), инжектит в `<style id="cc-tokens">` при сборке srcdoc (first-paint, без вспышки) и обновляет сообщением `theme` (шим `plugin-kit.js` переписывает блок — панель перекрашивается без перезагрузки). В ките (`theme.css`) **палитры нет — только структура**: единственный источник правды по палитре — тема хоста (`lib/theme.css`, обе темы), ручной копии в панели нет. Атрибут `data-cc-theme="dark"` шим проставляет на `<html>` по `init`/`theme` — для CSS самой панели, ключащегося от темы; значения `--cc-*` всегда на `:root`.
  - **Набор классов** контролов под дизайн-систему: `.cc-btn`/`.cc-input`/`.cc-list`/`.cc-list-item`/`.cc-card`/`.cc-badge`/`.cc-empty`/`.cc-notice`/`.cc-skeleton`. Опт-ин: голые `button`/`input` не стилизуются — панель, рисующая контролы сама, не ломается.
  - **Шрифт** — вшитый Hanken Grotesk для латиницы (data: URL, отсюда `font-src data:` в CSP панели); кириллица — системный фолбэк, потому что в бесплатном Hanken Grotesk кириллических глифов нет (у хоста та же история — паритет: панель и хост рендерят кириллицу одним системным шрифтом).
  Справочник шима для авторов панелей (API `ccsPlugin`, правило высоты, набор классов, шрифт) — [plugin-kit.md](../features/plugin-kit.md).

### 3.2. Приём сообщений

Хост принимает сообщение, только если выполнены **все** условия:

```ts
e.source === frameWindow      // окно СВОЕГО фрейма панели: frames[0] оболочки (§3.6)
&& e.origin === 'null'        // фрейм без allow-same-origin шлёт с непрозрачного origin
&& msg?.source === 'ccs-plugin'
&& msg.v === 1
```

Остальное молча отбрасывается, как в `ViaductFrame`. Хост отправляет во фрейм `postMessage(msg, '*')`: адресат — конкретное окно, а origin непрозрачного фрейма назвать нельзя. Поэтому **в сообщения хоста не кладётся ничего, чего панель не вправе видеть**.

### 3.3. Формат сообщений

Конверт у всех сообщений общий: `{ source, v: 1, type, ... }`. Из фрейма приходит `source: 'ccs-plugin'`, от хоста уходит `source: 'ccs-host'`.

**Фрейм → хост**

| type | Поля | Смысл |
|---|---|---|
| `ready` | — | Шим загрузился, ждёт `init`. Повторный `ready` игнорируется |
| `call` | `id: string`, `op: string`, `args: object` | Вызов операции хоста. Ответ — `result` с тем же `id` |
| `resize` | `height: number` | Высота контента документа панели в px (шим меряет `body.scrollHeight`). Хост ставит её фрейму: не ниже 48, не выше 20 000, не чаще раза за кадр. Прокрутку держит хост — у обёртки фрейма внутри карточки; внутренний документ не прокручивается |

**Хост → фрейм**

| type | Поля | Смысл |
|---|---|---|
| `init` | `plugin: {id, version}`, `slot`, `context`, `theme`, `locale`, `granted: string[]`, `tokens` | Ответ на `ready` |
| `result` | `id`, `ok: true, data` или `ok: false, error: {code, message}` | Итог `call` |
| `theme` | `theme`, `tokens` | Смена темы без перемонтирования |
| `context` | `context` | Смена контекста слота (например, другой проект) |

- `theme` — имя темы (`light`/`dark`) **и значения токенов `--cc-*`** этой темы (поле `tokens`): шим переписывает `<style id="cc-tokens">`, панель перекрашивается без перезагрузки. Первичная тема и её токены приходят в `init` (тоже с полем `tokens`).
- `context` — только то, что слот явно отдаёт: `projectId` и id выбранного объекта, если он есть. Список чатов, стор, JWT, данные других владельцев во фрейм не попадают никогда.
- `granted` — информационная копия выданных прав, чтобы панель могла прятать недоступное. **Источник правды — сервер**: панель, соврав себе про права, получит `denied`.

### 3.4. Путь вызова

1. Фрейм шлёт `call {id, op, args}`.
2. `PluginFrame` сам добавляет то, что фрейм подделать не может: id и версию **смонтированного** плагина и контекст слота (`projectId`). Затем вызывает `POST /api/plugins/{id}/call` с пользовательским JWT, в теле `{op, args, context}`.
3. Сервер проверяет: подсистема включена (иначе 503), владелец JWT = владелец установки (иначе 404), установка `enabled`, `ProjectCapabilities` проекта контекста допускает плагины, право операции есть в `granted` (иначе 403). Только после этого вызывает `IPluginCapability`.
4. Ответ хост пересылает во фрейм как `result`.

Операции называются `{область}.{глагол}`; каждая требует ровно одного права, сопоставление объявляет её обработчик. MVP:

| op | Право | args |
|---|---|---|
| `notes.search` | `notes:read` | `{query, limit?}` |
| `notes.read` | `notes:read` | `{id}` |
| `tasks.list` | `tasks:read` | `{status?, limit?}` в пределах проекта контекста |
| `net.fetch` | `net:{host}` + `secret:{name}` при `auth` | `{url, method?, headers?, body?, auth?: {secret, header, prefix?}}` |

`net.fetch` выполняет серверный прокси: только точный хост из `granted`, `SsrfGuard`, без редиректа на другой хост, таймаут и потолок размера ответа. `SsrfGuard` проверяется на **каждом шаге редиректа** (редирект на приватный адрес — тот же SSRF), а боевой транспорт (`SocketsHttpHandler.ConnectCallback`) **закрепляет адрес**: резолвит хост прямо перед TCP-connect и подключается к первому публичному адресу, закрывая TOCTOU-окно (DNS rebinding) между проверкой и соединением; имя хоста в URI остаётся исходным (Host и TLS SNI не ломаются). Секрет подставляет сервер в заголовок `auth.header` (префикс нормализован: ровно один пробел до значения, ноль при пустом префиксе), в ответ и во фрейм он не попадает (эхо вычищается на уровне байт).

**Исключение — `storage.*`.** Это не операция моста в смысле таблицы выше, а локальная операция оболочки (хоста): `PluginFrame` перехватывает домен `storage` и обслуживает его сам (`frontend/src/features/plugins/hostOps/storage.js`), на сервер вызов **не уходит** — `POST /api/plugins/{id}/call` не дёргается, серверный `IPluginCapability` для него не регистрируется. Право `storage` проверяет хост по своей копии `granted` (коды `denied`/`unavailable`/`invalid`/`limit` формирует хост). Данные — в `localStorage` под префиксом `ccs.plugin.<ownerId>.<pluginId>.`, который собирает только хост. Операции: `storage.get {key}` → `{exists, value}`, `storage.set {key, value}` → `{}`, `storage.remove {key}` → `{removed}`, `storage.keys {}` → `{keys, bytes}`; потолки и жизненный цикл — [plugin-kit.md](../features/plugin-kit.md#хранилище-storage). Серверная сторона знает право только как допустимое значение манифеста (`PluginPermission`).

HTTP-статусы ошибок `call` (код в теле JSON не меняется, фронт различает по нему): `denied` → 403, `not_found` → 404, `invalid` → 400, `unavailable` → 503, `timeout` → 504, `limit` → 429, `upstream` → 502, прочее → 500.

**ADR-016 (локальные проекты).** Прокси `net:` — исходящая сетевая операция **сервера**, вне шлюза `/gw` (сервер ходит в сеть сам, а не через шлюз локального проекта). Для серверных проектов это допустимо; в локальных проектах плагины выключены через `ProjectCapabilities` (инвариант 8), поэтому прокси на устройство не торчит. Осознанный выбор: альтернатива — проксировать `net:` через шлюз `/gw` — сложнее (нужен маршрут на каждый хост), а в MVP локальные плагины и так выключены.

Коды ошибок `error.code`: `denied` (нет права), `not_found` (нет установки или объекта), `invalid` (не тот формат args, неизвестный `op`), `unavailable` (подсистема или фича выключены, локальный проект), `upstream` (сбой внешнего хоста у `net.fetch`), `timeout`, `limit` (превышен потолок размера или числа вызовов в полёте).

Хост ограничивает число одновременных вызовов одного фрейма и размер `args`. Числа фиксирует шаг 3.2 в `CLAUDE.md` вертикали.

### 3.5. Версионирование

- `v` — целая версия протокола. Пакет объявляет `bridge` в манифесте; хост, не поддерживающий эту версию, панель не монтирует, а показывает заглушку «Панель собрана для более новой версии».
- **Внутри v1 разрешены только аддитивные изменения:** новые `type`, новые `op`, новые необязательные поля. Неизвестные `type` и поля обе стороны игнорируют. Неизвестный `op` → `invalid`.
- **Ломающее изменение = v2.** Хост держит v1 и v2 одновременно, пока в установленных пакетах есть `bridge: { "v": 1 }`. Снятие v1 — отдельное решение с миграцией черновиков.
- **Уточнение смысла `resize` (2026-10-21)** — не ломающее изменение, а исправление v1 до публикации: шим, который встраивается в каждую панель, всегда слал высоту контента, ручной `resize(h)` перетирается следующим замером; режим «желаемой высоты» несовместим с `html{overflow:hidden}` кита. Поле `mode` сознательно не вводилось. Это формальное исключение из правила «только аддитивные изменения»: потребителей нет, фича закрыта dark launch (`plugins-mvp` выключен по умолчанию), сторонних авторов панелей нет.
- **Значения токенов в `init`/`theme` (2026-10-21)** — тоже не ломающее изменение, а исправление v1 до публикации: сообщения `init` и `theme` несут не только имя темы, но и **значения** токенов `--cc-*` (поле `tokens`). Причина: панель — sandbox-iframe без `allow-same-origin`, `--c-*` хоста до неё не доходят, а своих значений у панели больше нет — палитру доставляет хост (§3.1); без передачи значений панель палитру хоста не знает. Формальное исключение из правила «только аддитивные изменения»: потребителей нет, фича закрыта dark launch (`plugins-mvp` выключен по умолчанию), сторонних авторов панелей нет.
- Ожидаемые аддитивные шаги после MVP: `notes:write:{prefix}`/`tasks:write` (новые `op`), `project-files:read`, открытие ссылки через хост, события «данные изменились» от хоста.

### 3.6. Сборка документа панели

Решение принято по ревью QA-фиксов: ReDoS в разборе HTML регулярками, `meta refresh` и `<base>` в панели, две сборки одного документа.

- **Документ собирает только фронт**, одной функцией `buildPanelSrcdoc` для установленной панели и для предпросмотра черновика. Сервер HTML панели не разбирает и не собирает: `Assets` и `GET /api/plugins/drafts/{slug}/panel` отдают файл байт в байт. Серверный `srcdoc`-эндпоинт и слияние `<head>` панели с `<head>` хоста удалены. HTML панели целиком кладётся в `<body>` после CSP и шима, конкатенацией без разбора. Собственная meta-CSP панели в `<body>` не действует, и это не поддерживается: действует только CSP хоста.
- **Навигацию панели держит оболочка.** CSP навигацию собственного документа не ограничивает (`navigate-to` в браузерах нет), а `sandbox` само-навигацию разрешает. Глобальный `frame-src` у SPA ограничить нельзя: хост уже встраивает во фреймы произвольные https-страницы (ридер ссылок, эфиры). Поэтому `buildPanelSrcdoc` возвращает документ-оболочку без скриптов. В его meta-CSP стоит **та же константа `PANEL_CSP`, что и в документе панели** (§3.1, с `frame-src 'none'`), а в разметке ровно один `<iframe sandbox="allow-scripts" srcdoc="…">` с документом панели (значение атрибута экранируется). Браузер сверяет навигацию фрейма с `frame-src` его **родителя**, то есть оболочки. Поэтому `meta refresh`, `location.*`, ссылки и `<base target>` панели фрейм не уводят. Свою оболочку панель увести не может: песочница не даёт навигировать предков, кроме top, а top закрыт отсутствием `allow-top-navigation`.
- **Оболочка — 100 % и без собственного скролла.** `<style>` оболочки: `html,body{margin:0;height:100%;overflow:hidden} iframe{display:block;border:0;width:100%;height:100%}` — внутренний `<iframe srcdoc>` растянут на 100 %×100 % (без этих стилей он жил бы в дефолтных 300×150: контент не растягивался и прокручивался сам). Во внутреннем документе `html{overflow:hidden}` (шим): фрейм не прокручивается сам. Высота фрейма — из сообщения `resize` (высота контента, §3.3); до первого `resize` фрейм на 100 %. Скролл один — у обёртки фрейма внутри карточки (документ хоста, наш стиль полосы: он задан в `index.css` хоста и внутрь iframe не попадает), оболочка и внутренний документ `overflow:hidden`; предпросмотр черновика устроен так же (различается лишь высота окна: 800, на мобиле 560). Контент длиннее страховочного потолка (20 000 px, §3.3) — хост показывает плашку «Панель длиннее 20 000 px» над контентом: виден только его верх.
- **Политика оболочки = политика панели, одна константа.** Документ из `srcdoc` наследует CSP создателя, и унаследованная политика складывается с собственной meta панели. Отсюда два следствия. Политика оболочки не может быть строже панельной: первая редакция этого раздела (`default-src 'none'; style-src 'unsafe-inline'; frame-src 'none'`) гасила инлайн-скрипты панели, и панель была мертва во всех трёх движках. А раз политика оболочки наследуется, она действует с момента создания документа панели, а не с момента разбора её meta. Поэтому ошибка порядка в сборке (HTML панели оказался раньше meta) барьер не снимает. Оболочка только с `frame-src 'none'` тоже работает, но держит две разные строки CSP и теряет это свойство.
- **Chromium после заблокированной навигации показывает во фрейме страницу ошибки** (`chrome-error://chromewebdata/`), и панель перестаёт работать; Firefox и WebKit оставляют её живой (`about:srcdoc`). Запрос наружу не уходит ни в одном движке. Принимаем как есть: честная панель себя не навигирует, а враждебная ломает только саму себя, то есть отказ закрытый. Чинить (перезагрузкой фрейма или ретрансляцией) не будем: это код ради враждебного пакета. Отдельной заглушки для панели, умершей после `ready`, тоже не заводим: во фрейме остаётся страница ошибки браузера, а до `ready` срабатывает обычный `bridge_timeout`. `location = 'about:blank'` не блокируется ни одним движком (`frame-src` не проверяет `about:`). Утечки нет: панель просто стирает себя.
- **Мост идёт напрямую, без ретрансляции.** Окно панели — `outer.contentWindow.frames[0]`: индексный доступ к кросс-доменному `WindowProxy` разрешён. Хост сверяет `e.source` с ним и шлёт `postMessage` в него же. Панель, в свою очередь, отправляет в `window.top` (не в `parent`): после оболочки `parent` панели — это оболочка без скриптов, и сообщения в неё теряются. Хост шлёт прямо в `frames[0]` — без этого при двух уровнях вложенности сообщения панели уходят в оболочку, а не к хосту.
- **Что закрывает какой слой.** `sandbox` без `allow-forms`, `allow-popups` и `allow-top-navigation*` закрывает отправку форм, `window.open`, `target=_blank|_top|_parent`. `default-src 'none'` закрывает `<iframe>`, `<object>`, `<embed>`, `<link rel=prefetch>` и внешние картинки. `connect-src 'none'` закрывает `fetch`, XHR, WebSocket, EventSource и `sendBeacon`. `base-uri 'none'` закрывает `<base>`. `frame-src 'none'` оболочки закрывает любую навигацию фрейма панели, включая `data:`, `blob:` и `javascript:`; не закрывает только `about:blank`, и утечки через него нет.
- **Потолок панели — 256 КиБ** на файл под `panel/`, одна константа `PluginPackageValidator.MaxPanelFileBytes`. Её применяют валидатор пакета, запись черновика, `Assets` и панель черновика (413); фронт дублирует число и не монтирует панель сверх него. Начали с малого намеренно: поднять потолок можно без поломки, опустить — нет.
- **Сырые ответы инертны сами по себе.** JWT принимается и из `?access_token=` на любой ручке, значит файл панели можно открыть верхним документом нашего origin. Поэтому `Assets` и панель черновика отвечают с `Content-Security-Policy: sandbox; default-src 'none'` и `X-Content-Type-Options: nosniff`.
- **Валидатор HTML панели не проверяет.** Лексический поиск `meta refresh` и `<base>` обходится одной строкой скрипта (`location = …`) и даёт ложную уверенность. Барьер — оболочка, а не разбор.
- **Подтверждено в браузерах** (спайк 2026-10-20, Playwright 1.63: Chromium 153, Firefox 155, WebKit 26.6; 35 входов × 3 движка × 5 режимов). С оболочкой на `PANEL_CSP` ни один из 34 атакующих входов не дал запроса на чужой хост, мост валиден 35 из 35 (`ready`, `e.source === frames[0]`, `origin === 'null'`). Без оболочки утекают 12 входов во всех движках: `meta refresh` в семи формах, `location.href/replace/assign`, `window.location =`, `a.click()` с `_self`. Не работают и отвергнуты: `frame-src 'self'` в оболочке, а также атрибут `csp` на `<iframe>`. Без meta в оболочке навигация уходит наружу, с meta панель мертва. Скрипты и сырые данные лежат в `.cc-attachments/panel-spike/` (`spike.mjs`, `results-final.json`, `extras.mjs`, `csp-attr.mjs`); каталог локальный и в git не входит. Отчёт — задача QA 7b9da5cf.
- **Остаточный риск.** Два канала утечки CSP не закрывает ни в одном движке. WebRTC: `connect-src 'none'` не мешает `RTCPeerConnection` собирать ICE-кандидаты через чужой STUN (`iceGatheringState = 'gathering'` везде). DNS-prefetch: директивы для него нет, `<link rel=dns-prefetch>` проходит без нарушений CSP. Оба канала позволяют вынести данные небольшими порциями: в имени хоста или в адресе STUN-сервера. Сам сетевой обмен (UDP, DNS) Playwright не видит, поэтому он не измерен. Поэтому инвариант 1 означает «выход наружу браузерными API, которыми управляет CSP, закрыт», а не «утечка выданных данных невозможна». Выдавая право на чтение данных (`notes:read`, `tasks:read`), человек доверяет пакету и в части утечки, это пишем в диалоге согласия.

### 3.7. Панель плагина в рельсе

**Ключ.** `plugin:{publisher}/{slug}:{panelId}` — ключ на панель, а не на плагин: у каждой панели плагина своя карточка. Версии в ключе нет: при обновлении плагина карточка остаётся на своём месте в раскладке. Ключ принимается **по синтаксису** (регулярное выражение + `PLUGIN_KEY_MAX_LEN = 64`), а не по списку установленных плагинов: стор читает раскладку из localStorage при импорте модуля, а список плагинов (асинхронный GET) в этот момент ещё не известен — иначе карточки молча выселялись бы из раскладки. Реестр: `isPluginPanelKey` / `isPanelKey` / `pluginPanelKey` в `frontend/src/pages/workspace/panelCatalog.ts`.

**Карточка.** Своя карточка рельса на каждую панель плагина (решение Андрея). Карточка — обычная панель рельса через общий `PanelShell`; отдельной ветки в рельсе для плагинов нет, кроме «докнуть новые ключи в первую группу» (`RAIL_GROUPS` статичен, `panelCatalog.ts:290`; новые ключи `sortRail` дописывает хвостом группы в каталожном порядке, `panelStackState.ts:588`). Мета панели (заголовок, иконка) приходит пропсом `pluginPanelMeta`: `WorkspacePage` собирает её по списку установленных плагинов и передаёт через `DesktopWorkspace` в `PanelZone` (`resolveMeta`). Для ключей `plugin:*` `panelMeta` всегда `undefined`; без пропса заголовок и иконку даёт запасная `panelMetaResolved`.

**Управление.** Контролы панели (перезагрузка, «Права…») — в шапке карточки через `PanelHeaderSlot` (портал), а не отдельной шапкой внутри панели: панель не рисует свою `Island`/`IslandHeader` — иначе получается «панель в панели» (десктоп-ветка `inShell`: `PluginFrame.tsx:561–567`).

**Скролл.** Один — у обёртки фрейма внутри карточки (документ хоста, поэтому полоса наша: стиль задан в `frontend/src/index.css` и внутрь iframe не попадает). Оболочка и внутренний документ панели — `overflow:hidden` (§3.6). Предпросмотр черновика устроен так же, различается лишь высота окна (800, на мобиле 560).

**Мобильный вид.** Одна вкладка «Плагины» с переключателем панелей (`PluginPanelsSwitcher`), а не вкладка на каждую панель. Решение Софьи, снято с Андрея.

**Старый слот.** `pluginPanels` упразднён: `LEGACY_KEY_ALIASES['pluginPanels'] = null` — прежние раскладки не переносятся, карточки встают на своё место по правилам рельса.

**Живое обновление.** Событие `plugins_changed` от хранилища (§2.4) → фронт перечитывает `GET /api/plugins`. Ключ фрейма (`pluginFrameKey`) включает версию плагина и отсортированный набор выданных прав, поэтому обновление плагина и смена прав пересоздают фрейм. Сборка мусора — только по диффу живого списка (`forgetPluginKeys`): плагин, которого в новом списке нет, теряет свои ключи из раскладки; упавший запрос ничего не выносит.

**Палитра.** От хоста (§3.1) — не дублируем.

## 4. Модель прав

- **Права крупные и называют поверхности хоста.** MVP: `notes:read`, `tasks:read`, `net:{exact-host}`, `secret:{name}`, `storage` (данные в браузере человека, проверяет хост, а не сервер — §3.4). Glob'ов по файловой системе нет. `write`-права, `project-files:read`, `notes:write:{prefix}` — после MVP (§7).
- **`requested` ≠ `granted`.** Манифест несёт потолок. Человек выдаёт права в диалоге установки, их подмножество хранится в записи установки. Выдать право, которого нет в `requested`, — 400.
- **Согласие — один раз при установке.** Обновление, которое расширяет `requested`, требует повторного согласия; новые права автоматически не выдаются. Окна «разрешить?» на каждый вызов нет. Исключение — будущие разрушающие операции под существующим флагом `workspace-destructive`.
- **Семантика обновления.** «Принять» черновика (установка по тому же id) сразу записывает `granted = старые ∩ новые`: права, которые остались в `requested`, переносятся на новое содержимое, новые не выдаются никогда. Диалог согласия при обновлении с непустыми выданными правами показывается **всегда**, даже если `requested` не вырос, но он только уведомляет и позволяет **сузить** права (`grant` заменяет `granted` целиком); расширить через него то, чего нет в `requested`, нельзя (400). «Отмена» в диалоге обновление **не откатывает**: пакет уже установлен, права равны пересечению. Id пакета выводит сервер (`PluginIdentity.Resolve`), агент его не выбирает: подменить id уже установленного плагина, чтобы унаследовать его права, нельзя (`bad-id`). Подробности контракта — `backend/ClaudeHomeServer.Plugins/CLAUDE.md`.
- **Запись секрета — одно правило.** Значение секрета пишется, только если секрет заявлен в манифесте (`requires.secrets`) и покрыт **выданным** правом `secret:{name}`; плагину выключенному секреты не пишутся (409). Это одинаково для `PUT /secrets/{name}` и для `grant` (в `grant` «выданные» права — права из того же тела), явное удаление (`value: null`) права не требует.
- **Проверка — на сервере при каждом вызове**, по актуальной записи установки, без кэша: отозвал право — со следующего вызова `denied`. Исключение — `storage.*`: его проверяет хост по своей копии `granted` (§3.4); копия обновляется вместе со списком установок (`plugins_changed` → `GET /api/plugins`).
- **Права защищают мост панели, а не агента.** Агенту права не нужны и ограничить его не могут: возможности агента задают его инструменты (`PersonaAccessPolicy`, allow-list MCP, среда исполнения). Навык плагина меняет поведение агента, но не даёт ему новых возможностей; в UI это пишем прямо. Главная угроза навыка — долговременная prompt-инъекция. Защита: установку делает только человек и видит полный текст навыков, источник помечен, позже добавятся подпись и хеш.
- **Секреты** хранятся per-owner механизмом `McpSecretStore`, имя файла — в `BackupPaths.SecretFileNames`. После сохранения значение не показывается, в UI только «задан» или «не задан».

## 5. Инварианты

1. **Песочница панели.** `sandbox` без `allow-same-origin`, JWT и стор хоста во фрейм не попадают, `connect-src 'none'`, весь выход наружу — только мостом; навигацию фрейма панели держит оболочка с той же `PANEL_CSP` (`frame-src 'none'`, §3.6, там же остаточный риск). Приём сообщений — по `e.source === win && e.origin === 'null'` плюс метке протокола.
2. **Per-owner изоляция.** Пакеты, установки, черновики, права и секреты ключуются владельцем. Каждый `{id}`-эндпоинт сверяет владельца установки: чужое — 404. Даже будущее общее хранилище пакетов (`_shared/{sha256}`) не делает общими права и секреты.
3. **Пакеты не попадают в общие каталоги CLI** (`~/.claude/skills`, `data/claude-profiles/*`). Только `--plugin-dir` из каталога владельца.
4. **Набор `--plugin-dir` зависит от сессии, не от хода.** Изменение применяется со следующего хода: `installed.json` перечитывается на каждый ход, и процесс CLI перезапускается, если состав изменился.
5. **Пара mount ↔ `DockerPathMapper` правится одной правкой.** Расхождение даёт exit=1 и ложный `Unreachable` у каждого container-владельца при зелёных тестах.
6. **Валидатор по allow-list.** Исполняемые части формата CLI-плагина (`hooks/`, `.mcp.json`, `bin/`, `settings.json`, `agents/`) в пакет не попадают.
7. **Агент не устанавливает плагины.** Install, approve и grant — только человеком по пользовательскому JWT.
8. **ADR-016.** В MVP плагины в локальных проектах выключены через `ProjectCapabilities` с текстом причины, без инлайнового `if (project.IsLocal)`. Каталог пакетов и секреты на устройство не едут. Прокси `net:` — серверный выход в сеть вне шлюза `/gw`; это допустимо, потому что работает только для серверных проектов.
9. **Источник установки — строка**, неизвестные значения терпим.
10. **Граница вертикалей.** Plugins не ссылается на Notes и Tasks; обработчики прав приходят через Core-шов `IPluginCapability`.

## 6. Trade-offs

| Выбрали | Против | Цена |
|---|---|---|
| Нативный формат плагина CLI + `--plugin-dir` | Своё хранилище навыков | Зависим от формата CLI, который может дрейфовать между версиями. Нужна проба загрузки тестового плагина при обновлении CLI и строгий allow-list файлов |
| Применение со следующего хода (процесс перезапускается при смене состава) | Мгновенное применение | Установил плагин — в текущем чате он появится со следующего хода: CLI перезапускается при изменении состава `--plugin-dir`, иначе переиспользует существующий процесс |
| Iframe с непрозрачным origin, `srcdoc` | Основной бандл | Панель не может использовать React хоста и его контролы. Свой UI через `plugin-kit`, в MVP только один HTML-файл |
| Крупные права, согласие при установке | Тонкие права, согласие на вызов | Право `notes:read` открывает все заметки владельца, а не папку. Сужение — следующими правами, аддитивно |
| Гейт персоны на весь плагин | Гейт на отдельный навык | Нельзя дать персоне половину плагина |
| Навыки едут в системный блок | Подгрузка по требованию | Описания навыков раздувают каждый ход, установка обнуляет prefix cache. Нужен потолок числа и объёма описаний на сессию; по умолчанию плагин включается привязкой |
| Прокси `net:` на сервере | Сеть из фрейма | Сервер делает исходящие запросы за пользователя. Нужны точный хост, `SsrfGuard`, запрет редиректа, лимиты |
| «Одна вкладка — один владелец» (токен: сначала `sessionStorage`, сторож смены входа, отказ в `PluginFrame`) | Общий токен профиля без контроля | Смена входа в соседней вкладке перезагружает эту; в окне до перезагрузки панель получает `denied`, а запросы приложения в окне смены входа — от нового владельца. Устройство — [plugins.md](../architecture/plugins.md) |

## 7. Что осталось открытым

- **Триггеры** (webhook, cron) — после MVP, через существующие `TriggerSources`.
- **Marketplace и шаринг между владельцами** — после MVP. Раскладка готова: общее хранилище `data/plugins/_shared/{sha256}` подключается без миграции записей установки, меняется только резолв пути. Нерешено: подпись пакетов, доверие к publisher, модерация.
- **Плагины в локальных проектах** — после MVP. Нужно решить, как доставлять каталог на устройство и как прокси `net:` уживается со шлюзом `/gw`.
- **`write`-права** (`notes:write:{prefix}`, `tasks:write`) и `project-files:read` — после MVP, аддитивно в мосте v1.
- **Многофайловые панели.** `srcdoc` не умеет относительные ресурсы. Кандидат — короткоживущие билеты на ассеты пакета (как билеты ADR-016). Решаем, когда упрёмся в потолок одного HTML.
- **Потолок контекста от навыков** — конкретные числа (сколько плагинов и сколько байт описаний на сессию) задаёт шаг 2.1 по замеру.
- **Тексты UI для двух видов «плагинов»** (профиля CLI и владельца) — согласует Софья.
- **Пример манифеста в ADR vs фактическая модель.** Первая редакция §2.2 разошлась с `PluginManifest.cs` в трёх полях (`bridge`, `requires.secrets`, `permissions`); исправлено по ревью пачки A. Сторожа, который держит пример §2.2 в синхроне с моделью, нет: дрейф снова поймает только ревью. Кандидат — тест, разбирающий JSON-блок §2.2 моделью и проверяющий `Validate()`.
- **Перечень запрещённых файлов пакета** уточняется по итогам спайка (шаг 0): как CLI ведёт себя с `hooks/` и другими частями формата в local и container.
