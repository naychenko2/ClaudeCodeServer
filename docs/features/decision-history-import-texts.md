# Тексты: README ветки истории решений и импорт в панели

Этап 4 фичи «История решений» (`change-dossiers`): чтение ветки `ccs/dossiers/v1` обратно
в приложение. Здесь лежат **окончательные** формулировки — копировать как есть, вариантов на
выбор нет. Техчасть — [ADR-004](../adr/ADR-004-change-dossiers.md) §6, макет панели —
[decision-history-proposal.md](../mockups/decision-history-proposal.md), макет диалога импорта —
[decision-history-import-v1.html](../mockups/decision-history-import-v1.html), макет диалога выгрузки —
[dossier-export-dialog.md](../mockups/dossier-export-dialog.md), общий словарь фичи — заметка
проекта «Тексты — Паспорта изменений (UI, empty-state, «Что нового»)».

Словарь остаётся прежним: для человека фича называется **«История решений»**, единица —
**запись**. Слова «паспорт», «досье», «dossier» в интерфейсе и в README ветки не появляются
(они живут в коде и в ADR). Действия — пара **«Выгрузить в репозиторий» / «Загрузить из
репозитория»**: симметрия читается без объяснений, а слова «экспорт» и «импорт» остаются
командными.

## 1. README.md в корне ветки `ccs/dossiers/v1`

Файл пишется при каждой выгрузке вместе с остальным деревом ветки. Его читает человек,
который открыл ветку на GitHub и, возможно, про AI Home слышит впервые, — поэтому текст
самодостаточен и не отсылает к интерфейсу приложения за объяснением. Содержимое постоянно:
подстановок и плейсхолдеров нет, побайтово одинаковый файл при каждой выгрузке (иначе
экспорт плодил бы коммиты на пустом месте).

Текст файла целиком:

````markdown
# История решений

Эта ветка — память о том, **зачем** менялся код. Её ведёт AI Home: когда код меняют из чата
или задачи, приложение сохраняет цель изменения, принятые решения,
отвергнутые варианты и грабли. По команде человека накопленное выгружается сюда — в отдельную
ветку рядом с кодом, чтобы знания уезжали вместе с репозиторием, а не оставались в одном
приложении.

`git blame` отвечает «кто и что». Эта ветка отвечает «зачем».

## Что здесь лежит

```
dossiers/{yyyy}/{mm}/{sha7}-{slug}.md   одна запись — один коммит
discussions/{yyyy}/{sess7}-{slug}.md    конспект обсуждения — не переписка
index.json                              оглавление: коммит → файл записи
README.md                               этот файл
```

Запись лежит в папке года и месяца коммита, к которому относится. Имя файла — первые 7
символов SHA коммита и короткая транслитерация его заголовка; если двум коммитам достался
один и тот же префикс, он удлиняется до различимого. Внутри — заголовок коммита, якоря
(SHA, дата, изменённые файлы и затронутые типы), а дальше разделы «Зачем», «Решения», «Отвергнуто»,
«Грабли», «Инварианты». Пустых разделов не бывает: чего не было — того и нет.

Рядом с записями лежат конспекты обсуждений — `discussions/{yyyy}/{sess7}-{slug}.md`,
один файл на чат: решения и их аргументы, отвергнутые варианты, прозвучавшие требования.
Это протокол сути разговора, снятый по его ленте, — а не сама переписка.

`index.json` — оглавление ветки, по нему ищут запись, не перебирая папки:

```json
{
  "version": 1,
  "entries": [
    {
      "sha": "полный SHA коммита",
      "file": "путь к файлу записи в этой ветке",
      "subject": "заголовок коммита",
      "committedAt": "дата коммита",
      "discussion": "путь к конспекту обсуждения, если чат его имеет",
      "taskId": "идентификатор задачи, если изменение делалось по задаче",
      "supersededSha": ["SHA, которые этот коммит заменил при squash или rebase"]
    }
  ]
}
```

## Как найти запись по SHA коммита

Ветку не нужно выкладывать в рабочую папку — читайте прямо из git.

Через оглавление (надёжный путь: находит и коммиты, переписанные squash'ем — они остаются
в `supersededSha`):

```
git show ccs/dossiers/v1:index.json
```

Напрямую по имени файла — быстрее, когда SHA не переписывали:

```
git ls-tree -r --name-only ccs/dossiers/v1 | grep 1a2b3c4
git show ccs/dossiers/v1:dossiers/2026/08/1a2b3c4-dobavit-import.md
```

Если ветка пришла с `git fetch`, но локальной ещё нет — подставьте
`origin/ccs/dossiers/v1`.

## Ветку не редактируют руками

Каждая выгрузка перезаписывает содержимое ветки целиком, поэтому ручные правки исчезнут при
следующей — и незаметно. Ветка обычная во всём остальном: `git pull` и `git push` работают
как всегда, рабочую папку выгрузка не трогает, в историю кода эти коммиты не попадают.

У кого проект открыт в AI Home — загружает записи отсюда к себе одной командой в панели
«История решений»; чужие записи приложение не перезаписывает своими.

## Чего здесь нет

Дословной переписки. В запись попадает выжимка — цель, решения, отказы, грабли, —
а обсуждение едет конспектом: решения, аргументы, отвергнутое. Разговоры, помеченные
в приложении как «не сохранять решения», не выгружаются вовсе — ни записью, ни
конспектом. Секреты вычищаются перед записью в ветку.
````

## 2. Подписи в панели «История решений»

### 2.1. Действие импорта

Кнопка «Загрузить» открывает модалку подтверждения (`decision-history-import-v1.html` §4):
импорт ничего не пишет в репозиторий и не трогает рабочую папку — читать чужие записи
не опаснее, чем открыть панель, — но у пользователя должна быть возможность отказаться
и увидеть итог (что приехало, что было пропущено, почему ничего не приехало) до закрытия.
Модалка живёт на одном маунте и проходит шесть фаз внутри себя, без переоткрытия —
карточка не моргает.

Иконка — `Download` (парная к `Upload` у выгрузки). Приложение читает то, что уже есть
в локальном репозитории, и `git fetch` за человека не делает — это отражено в тексте
про ненайденную ветку.

Тексты модалки:

| Место | Текст |
|---|---|
| Кнопка в шапке панели (десктоп), `title` | Загрузить из репозитория |
| Чип в теле панели (мобила), подпись | Загрузить |
| Заголовок модалки (фаза `confirm`) | Загрузить историю решений из репозитория |
| Тело модалки (фаза `confirm`) | Из ветки `ccs/dossiers/v1` подтянутся записи, которых у вас ещё нет. Ваши записи не изменятся: если по коммиту есть и ваша, и приехавшая — в списке будут обе. |
| Кнопка главная (фазы `confirm` / `loading`) | Загрузить |
| Кнопка второстепенная (фазы `confirm` / `loading`) | Отмена |
| Кнопка финальная (фазы `success` / `nothing` / `noBranch`) | Закрыть |
| Кнопка повтора (фаза `error`) | Повторить |

### 2.2. Итог импорта

| Случай | Текст сообщения |
|---|---|
| Загружены новые записи, часть уже была | Загружено записей: 3. Уже было в истории: 12. |
| Загружены новые записи, дублей не было | Загружено записей: 3. |
| Новых нет, ветка прочитана | Новых записей нет — всё, что есть в ветке, уже в истории решений. |
| Ветки в репозитории нет | Загружать пока нечего: выгруженной истории решений в репозитории не нашлось. Возможно, её ещё ни разу не выгружали — или выгрузил коллега, но к вам она ещё не приехала: обновите репозиторий (git fetch) и повторите. |
| Ошибка чтения | Не удалось загрузить историю решений. Ничего не изменилось — попробуйте ещё раз. |

Числа подставляются на место `3` и `12`. Форма «Загружено записей: N» выбрана нарочно —
она читается верно при любом числе, без склонений и без «запись/записи/записей» в коде.
Вторая фраза («Уже было в истории: N») **опускается целиком**, когда дублей не было; писать
«Уже было в истории: 0» нельзя — это сообщение о том, чего не произошло.

Тон сообщений — нейтральный: успех не празднуем (`success` только у «Загружено записей»),
пустой результат не считаем ошибкой (нейтральный тост, не warning), ненайденная ветка — это
подсказка, а не сбой.

Текст ненайденной ветки утверждён 20.08.2026 взамен прежнего («В репозитории нет ветки
`ccs/dossiers/v1`…»): тот начинался с отрицания технического объекта, и человек читал первые
слова как «нет файла/папки» — сообщение об ошибке файловой системы. Утверждённая формулировка
держится трёх правил, менять их нельзя:

- **Первая фраза — про состояние дела, а не про отсутствие объекта.** «Загружать пока нечего» —
  это ответ на нажатую кнопку, а не диагноз поломки.
- **Обе причины названы.** Приложение читает локальный репозиторий и не отличает «ещё ни разу
  не выгружали» от «выгрузка есть, но не приехала», поэтому текст покрывает оба случая и даёт
  один следующий шаг.
- **Имени ветки в тексте нет.** Человек уже видел `ccs/dossiers/v1` на карточке подтверждения;
  повтор в исходе возвращает интонацию системной ошибки. `git fetch` — обычным текстом, без
  моноширинного оформления, по той же причине.

### 2.3. Происхождение записи

| Что показываем | Текст |
|---|---|
| Своя запись в общем списке | пометки нет |
| Запись из репозитория, автор известен | Из репозитория · Андрей Найченко |
| Запись из репозитория, автора нет | Из репозитория |
| Тултип пометки, автор известен | Запись приехала из ветки `ccs/dossiers/v1` — её выгрузил Андрей Найченко. |
| Тултип пометки, автора нет | Запись приехала из ветки `ccs/dossiers/v1`. |
| Своя запись **рядом с** импортированной по тому же коммиту | Ваша запись |

Имя автора — из коммита ветки `ccs/dossiers/v1`, которым запись выгружали (кто нажал
кнопку, тот и подписан). Не определилось — показываем пометку без имени, «Автор неизвестен»
не пишем: пустая подпись честнее выдуманной.

Своя запись в общем списке **не подписывается**: 90% списка — свои записи, и подпись «Ваша
запись» на каждой строке превращается в шум, который перестают читать. Пометка «своё»
появляется ровно там, где есть с чем спутать, — в паре записей об одном коммите (ниже).
Слов «импорт», «экспорт», «origin», «ветка-источник» в подписях нет — «из репозитория»
говорит то же самое человеческим языком.

### 2.4. Две записи об одном коммите

Когда по одному коммиту есть и своя запись, и приехавшая, панель показывает обе — своя
сверху. Над парой:

> **Две записи об одном коммите**
> Ваша запись сохранена как есть — загрузка ничего не перезаписывает. Рядом — как тот же
> коммит описали в репозитории.

Пояснение отвечает на вопрос, который человек задаёт первым («почему их две и какая
правильная?»), и снимает главный страх («мою затёрли?»). Обе записи полноценны: чужая
не сворачивается в примечание к своей — это другой взгляд на то же изменение, а не
дубликат.

Если своей записи по коммиту нет, приехавшая показывается обычной карточкой с пометкой
происхождения — заголовка группы и пояснения не появляется.
