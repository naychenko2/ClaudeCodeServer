## Requirements Summary

Источник: [default-personas-onboarding-spec.md](default-personas-onboarding-spec.md) (все решения финальные).

1. **Инвариант**: каждый новый чат, создаваемый человеком через UI, начинается с персоной. Только новые чаты людей; старые чаты, служебные сессии исполнителей задач и one-shot вызовы не затрагиваются.
2. **Онбординг пользователя**: обязательный чат-интервью при первом логине (и ретро — при следующем логине существующего пользователя без дефолт-персоны). Ведёт системный «Мастер настройки» (системный промпт, без персоны). Итог — личная дефолт-персона (имя, роль, характер, аватар), подтверждённая пользователем; она «просыпается» и здоровается в том же чате.
3. **Онбординг проекта**: обязательный чат-интервью при создании проекта (ретро — при первом открытии существующего проекта после релиза). Ведёт личная дефолт-персона. Итог — персона-«руководитель проекта», назначенная дефолтной для проекта.
4. **Профиль дефолт-персон**: обычная персона + признак «дефолтная»: `Specialty=Coordinator`, `Access=Full`, включённый модуль `personas-manage`, автопривязки (задачи, заметки, данные проекта).
5. **Жизненный цикл**: дефолт можно сменить на подходящую по зоне; удалить текущую дефолтную — только с преемником (проверка на бэке). Остаться без дефолта нельзя.
6. **Мост в командные механики**: руководитель проекта в релевантный момент предлагает механику из реестра `teamMechanics.ts` одной кнопкой; запуск только по подтверждению; при отказе решает сам и повторно в этом разговоре не предлагает. Автозапуска нет.
7. **Аватары**: аватар релевантной персоны вместо нейтральной AI-иконки в 4 местах (AiLauncher, WaitingIndicator, EmptyState, ChatItemView) по правилу «чат → текущая персона чата; контекст проекта вне чата → дефолт проекта; глобально → личная дефолт-персона»; нейтральная иконка — fallback до онбординга. Анимация аватара в wait-индикаторе — по варианту, согласованному владельцем из предложенных дизайнером.
8. **Релиз**: всё одним релизом за одним фич-флагом, по умолчанию выключен.

## RALPLAN-DR Summary

### Principles
1. **Дефолт-персона — указатель, а не тип**: признак «дефолтная» живёт ссылкой на владельце (`User`/`Project`), сама персона — обычная (`Models/Persona.cs` не получает флага).
2. **Онбординг — обычная сессия существующего рантайма**: никакого параллельного чат-движка; спец-промпт + существующие MCP-инструменты персон.
3. **Инвариант держит фронт, бэк страхует**: UI не умеет создать чат без персоны при включённом флаге; бэк валидирует, но не ломает служебные пути.
4. **Состав MCP-инструментов стабилен** (инвариант CLAUDE.md, раздел «MCP-серверы»): новые инструменты добавляются в `tools/list` безусловно, ограничения — на бэкенде.
5. **Минимум нового серверного состояния для моста в механики**: предложение механики — маркер в тексте ответа (по образцу `<promise>ГОТОВО</promise>` из work-loop), отказ — инструкция промпта, не стор.

### Decision Drivers (top 3)
1. **Обратная совместимость сторов** `data/users.json`, `data/projects.json`, `data/personas.json`, `data/sessions.json`: только nullable-поля, без инкремента `BackupSchema.Version` (аддитивное изменение — не ломающее по правилу «Новое хранилище → сверься с бэкапом» из CLAUDE.md).
2. **Курица-и-яйцо интервьюеров** (R8 спеки): сессия мастера настройки обязана работать без персоны, но с доступом к созданию персон — этим определяется механика доставки инструментов.
3. **Один фич-флаг на всё** (R6): каждая видимая часть гейтится одним ключом, dark launch по механике `FeatureFlagCatalog` (`backend/ClaudeHomeServer/Models/FeatureFlag.cs`).

### Viable Options

**A. Где хранить defaultPersonaId**
- **A1 (выбрано): поля на владельцах** — `User.DefaultPersonaId` (`Models/User.cs`) и `Project.DefaultPersonaId` (`Models/Project.cs`).
  - Плюсы: инвариант «ровно один дефолт» бесплатен (одно поле — одно значение); `GET /api/auth/me` (`Controllers/AuthController.cs`) и DTO проекта уже отдаются фронту; сторы уже в бэкапе.
  - Минусы: две точки правды при удалении персоны — нужен каскад-проверка в `PersonasController.Delete` (`Controllers/PersonasController.cs:287`).
- **A2: флаг `IsDefault` на `Persona`** — плюсы: признак виден в карточке без джойна; минусы: «ровно один» превращается в инвариант со сканом всех персон зоны, гонки при смене, миграция `personas.json`. Отклонено.

**B. Онбординг-чат: обычная сессия со спец-промптом vs отдельный флоу**
- **B1 (выбрано): обычная `Session` c полем `OnboardingKind` (`"user" | "project"`, null у прочих)** + системный промпт мастера/наставника, создаваемая новым `OnboardingController`. Персону создаёт сам AI через MCP-инструменты персон (пресет `personas-manage` уже существует — `Services/PersonaBindingsService.cs:45-62`), назначение дефолта — новый MCP-инструмент `personas_set_default` → бэк-экшен.
  - Плюсы: переживает рестарт/резюм (`--resume`), весь существующий UI чата (стрим, аватары, permission) бесплатно; «просыпание» персоны = существующий `POST {sessionId}/persona` (`Controllers/SessionsController.cs:63`) + слой персоны пересобирается каждый ход (`PersonaPromptBuilder`, CLAUDE.md «Персоны»).
  - Минусы: завершение онбординга — событийное (нужен SignalR-сигнал `onboarding_completed`), LLM может «не дойти» до создания персоны — купируется жёстким протоколом в промпте и перезапуском чата.
- **B2: экранный wizard с формами + `ai/quick-create` (`Controllers/PersonasController.cs:572`)** — отклонён самой спекой (R2: «живой чат-интервью, не формы»); `ai/quick-create` остаётся внутренним референсом для промпта мастера.
- **B3: отдельный state-machine-флоу вне чат-рантайма** — максимум контроля, но дублирует стрим/пермишены/историю; отклонено.

**C. Как фронт гарантирует инвариант «чат только с персоной»**
- **C1 (выбрано): единый хелпер создания + гейт-экран.** Все 7 точек создания чата человеком (`pages/WorkspacePage.tsx:878,897`, `pages/ChatsPage.tsx:158`, `lib/ai/startChat.ts:46,53`, `components/SessionList.tsx:140`, `features/home/RecentSessionsWidget.tsx:37`, `features/home/QuickActions.tsx:61`) переводятся на новый хелпер, который при включённом флаге вызывает `api.personas.createChat(defaultId, { projectId })` (`lib/api.ts:584`, бэк — `PersonasController.cs:306`). Плюс страховка бэка: `personaId` в телах create (`lib/api.ts:854, 886`) и 400 при его отсутствии под флагом.
  - Плюсы: одна точка выбора персоны контекста; групповые чаты (`api.chats.createGroup`) и служебные пути (`SessionManager` для задач) не затронуты.
  - Минусы: правка 7 колл-сайтов — механическая, зато проверяемая grep'ом.
- **C2: только бэк-валидация 400** — фронт получал бы ошибки вместо UX; отклонено как основной механизм, оставлено как страховка.

**D. Мост в механики: как персона предлагает запуск**
- **D1 (выбрано): маркер в тексте**: промпт-блок руководителю (серверный мини-каталог механик) велит выводить `<team-mechanic id="..." topic="..."/>`; `ChatItemView.tsx` детектит и рендерит карточку с кнопкой; клик отправляет `buildTeamTurnText(id, topic, DEFAULT_TEAM_SETTINGS)` (`features/team/teamMechanics.ts:191`). «Не навязывать после отказа» — инструкция промпта (стейт не нужен: транскрипт хода в контексте).
  - Плюсы: ноль нового серверного состояния; тот же паттерн, что маркер work-loop (CLAUDE.md «Механики OmO») и детект `detectTeamMechanic` (`teamMechanics.ts:283`).
  - Минусы: дрейф C#-каталога и `teamMechanics.ts` — купируется тестом на соответствие id.
- **D2: предложение через widgets MCP (`widget_show`)** — интерактивнее, но виджет-рантайм тяжелее, зависит от tool-ключа `widgets` и не даёт фронту типизированного запуска механики. Отклонено.

## Acceptance Criteria

Из спеки (переносятся как есть):
- [ ] Новый чат (в проекте и вне) невозможно создать без персоны: UI всегда подставляет дефолт-персону контекста или явно выбранную.
- [ ] Первый логин нового пользователя → обязательный чат-онбординг; на выходе личная дефолт-персона, подтверждённая пользователем.
- [ ] Существующий пользователь без дефолт-персоны получает тот же визард при следующем логине; пропустить нельзя.
- [ ] Создание проекта → чат-онбординг с личной дефолт-персоной; на выходе руководитель проекта, назначенный дефолтом проекта.
- [ ] Существующий проект без руководителя получает визард при первом открытии после релиза.
- [ ] Дефолт-персоны: Specialty=Coordinator, Access=Full, personas-manage, автопривязки; реально создают/правят других персон из чата.
- [ ] Смена дефолта в настройках; удаление текущей дефолтной требует преемника (бэк-проверка).
- [ ] В чате с руководителем: подходящая задача → предложение механики с кнопкой; подтверждение запускает, отказ → решает сам, повторно не предлагает в этом разговоре.
- [ ] Аватар релевантной персоны в AiLauncher, WaitingIndicator, EmptyState, ChatItemView по правилу контекста; до онбординга — нейтральные иконки.
- [ ] Анимация аватара в wait-индикаторе — по согласованному владельцем варианту.
- [ ] Всё за одним фич-флагом (`FeatureFlagCatalog.All` + `FLAGS`), по умолчанию выключено.

Технические дополнения (проверяемые):
- [ ] `User.DefaultPersonaId` принимает только глобальную персону владельца; `Project.DefaultPersonaId` — только проектную персону этого проекта (400 иначе).
- [ ] `DELETE /api/personas/{id}` для текущей дефолтной без валидного `successorId` → 400 с текстом причины; с валидным — преемник назначен, персона удалена, память вычищена (`_memory.DeletePersonaAsync`, `PersonasController.cs:292`).
- [ ] `GET /api/auth/me` отдаёт `defaultPersonaId` и `needsOnboarding`; DTO проекта отдаёт `defaultPersonaId`.
- [ ] `POST /api/projects/{id}/sessions` и `POST /api/chats` при включённом флаге владельца и отсутствии `personaId`/`resumeSessionId` → 400; при выключенном флаге поведение байт-в-байт прежнее.
- [ ] Состав `tools/list` MCP-сервера персон не зависит от хода (зелёный `McpToolsetStabilityTests`).
- [ ] `mcp__personas__personas_set_default` из делегированного хода → отказ (`[DenyOnDelegatedTurn]`).
- [ ] `dotnet build`, `dotnet test`, `npm run build`, `npm run lint:design` — зелёные; новые тесты не используют Windows-литералы путей (CI на Linux, CLAUDE.md «Соглашения»).
- [ ] Каталог механик в C# и `TEAM_MECHANICS` в `teamMechanics.ts` согласованы по id (тест).

## Implementation Steps

### Волна 1 — модели и стор (бэкенд)

**1. Поля дефолта и онбординга.**
- `backend/ClaudeHomeServer/Models/User.cs`: добавить `public string? DefaultPersonaId { get; set; }` и `public string? OnboardingSessionId { get; set; }` (резюм прерванного онбординга). Признак «онбординг пройден» = `DefaultPersonaId != null` — отдельного bool не заводить.
- `backend/ClaudeHomeServer/Models/Project.cs`: добавить `public string? DefaultPersonaId { get; set; }` и `public string? OnboardingSessionId { get; set; }`.
- `Models/Session.cs`: добавить `public string? OnboardingKind { get; set; }` (`"user" | "project"`, null — обычный чат).
- Бэкап: поля аддитивные nullable внутри существующих сторов `data/` — инкремент `BackupSchema.Version` НЕ нужен; проверить, что `BackupValidation.Validate` не ломается (ничего не менять, только прогнать тесты).

**2. Фич-флаг.**
- `backend/ClaudeHomeServer/Models/FeatureFlag.cs`: константа `FeatureFlagKeys.DefaultPersonasOnboarding = "default-personas-onboarding"`; строка в `FeatureFlagCatalog.All` (`Default: false`, `Stage: "dev"`, Title «Персоны по умолчанию и онбординг»).
- `frontend/src/lib/featureFlags.ts`: ключ `defaultPersonasOnboarding: 'default-personas-onboarding'` в `FLAGS`.

### Волна 2 — назначение дефолта и жизненный цикл (бэкенд; зависит от 1)

**3. Назначение дефолта.**
- `Controllers/PersonasController.cs`: новый экшен `POST {id}/make-default`. Валидация: персона владельца; `Scope==Global` → пишет `User.DefaultPersonaId` через `UserStore`; `Scope==Project` → пишет `Project.DefaultPersonaId` своего проекта (проект `OwnerId == UserId`, иначе 400). Broadcast SignalR-событием (по образцу `Broadcast("updated", id)` там же) — это же событие фронт использует для инвалидации кэша `auth.me` / DTO проекта (см. шаг 13): смена дефолта видна резолверу аватаров без перезагрузки.
- **Досев профиля дефолта — ТОЛЬКО в онбординг-пути** (свежесозданная мастером/наставником персона): `Specialty=Coordinator`, `Access=Full`, Tool-привязка `personas-manage` Mode=Auto (ключ из `ToolCatalog`, `PersonaBindingsService.cs:45`), Tool-привязки `tasks`, `notes`; проектной — плюс существующий `SeedProjectDefaults` (`Services/PersonaBindingsService.cs:384`). Вынести в метод `PersonaBindingsService.SeedDefaultPersonaProfile(ownerId, persona)`, вызывать из онбординг-финализации (шаг 7), **не** из `make-default`: ручная смена дефолта из настроек существующую персону не трогает — молчаливая дозапись `Access=Full`+manage была бы тихой эскалацией прав. Автопривязка «персоны проекта» из спеки покрывается модулем `personas-manage` (scoped по проекту) — новый тип привязки не заводить.

**4. Удаление с преемником.**
- `Controllers/PersonasController.cs:287` (`Delete`): если `id` — текущий `User.DefaultPersonaId` владельца или `Project.DefaultPersonaId` любого его проекта, требовать query `successorId`; преемник валиден по той же зоне (глобальный/та же проектная команда) и не равен удаляемой; переназначить дефолт, затем удалить. Без преемника — 400 `{ error: "Это дефолт-персона: выберите преемника" }`.

**5. Выдача фронту.**
- `Controllers/AuthController.cs` (`/api/auth/me`, район строк 42–49): добавить `defaultPersonaId = me?.DefaultPersonaId`, `needsOnboarding = флагВключён && me?.DefaultPersonaId == null`, `onboardingSessionId`. **Нормализация сироты на чтении**: если `DefaultPersonaId` указывает на несуществующую персону — отдавать фронту null (и для `Project.DefaultPersonaId` так же); тогда онбординг-гейт сам чинит осиротевший дефолт вместо молчаливого нарушения «остаться без дефолта нельзя».
- DTO проекта (`ProjectsController` / сериализация `Project`): `DefaultPersonaId` и `OnboardingSessionId` уходят как есть (модель сериализуется целиком — проверить, что фронтовый тип `Project` в `frontend/src/types/index.ts` дополнен).

### Волна 3 — онбординг-рантайм (бэкенд; зависит от 2)

**6. Промпты онбординга.**
- Новый файл `backend/ClaudeHomeServer/Services/Prompts/OnboardingPrompts.cs`: (а) промпт «Мастера настройки» — интервью о пользователе и его задачах, затем создание персоны инструментами `mcp__personas__*` (референс структуры черновика — `BuildDraftPrompt` в `PersonasController.cs`), показ результата на подтверждение, после явного «да» — вызов `personas_set_default`; (б) промпт-надстройка онбординга проекта для личной дефолт-персоны — интервью о проекте, создание проектной персоны-руководителя (`scope=project`), подтверждение, `personas_set_default`. Оба промпта: жёсткое «без пропуска», по-русски.

**7. OnboardingController + завязка в сессию.**
- Новый `Controllers/OnboardingController.cs`: `POST /api/onboarding/user/start` — если `User.OnboardingSessionId` жив, вернуть его; иначе создать чат вне проекта (путь `SessionManager`, как `POST /api/chats`) с `OnboardingKind="user"`, записать в `User.OnboardingSessionId`. `POST /api/onboarding/project/{projectId}/start` — аналогично: проектная сессия с `PersonaId = User.DefaultPersonaId` (400, если личного дефолта нет), `OnboardingKind="project"`, записать в `Project.OnboardingSessionId`. **Идемпотентность атомарно**: двойной `start` (две вкладки, повторный логин) не должен породить две сессии и перезапись id — lock per-user/per-project в контроллере или `SessionManager`. Кейс «`OnboardingSessionId` указывает на удалённую сессию» → создаётся новая (явный тест).
- **Врезка промпта — в `SessionManager.BuildPersonaLayer` (`SessionManager.cs:1254`)**, канал — `LlmSessionContext.PersonaPromptProvider` (`:1872`): для `Session.OnboardingKind != null` провайдер возвращает соответствующий промпт из `OnboardingPrompts` (у сессии мастера — вместо слоя персоны; у проектного онбординга — надстройкой к слою личной дефолт-персоны). `ClaudeSession` модель `Session` не знает и `OnboardingPrompts` не читает — вторую точку сборки промпта не заводить. MCP-сервер персон сессии мастера включается существующим механизмом (для сессии без персоны `PersonaBindingsService.SectionOrigin` возвращает `Explicit` — manage доступен без доработок гейтов).
- Завершение: финализация после `make-default` (шаг 8): для `OnboardingKind=="user"` — досев профиля (шаг 3), назначить свежую персону этой сессии (`SessionManager.SetPersona`, тот же путь, что `SessionsController.cs:63` — лениво через `AdapterStale`, активный ход не рвётся), очистить `User.OnboardingSessionId`, послать SignalR `ServerMessage` типа `onboarding_completed` (новый record в `Protocol/ServerMessage`); для `"project"` — досев + очистить `Project.OnboardingSessionId`, то же событие. «Просыпание»: следующий ход идёт уже слоем новой персоны (пересборка каждый ход — CLAUDE.md «Персоны»); приветствие — существующий рендер `Persona.Greeting` в чате персоны. **Фронт снимает гейт не по `onboarding_completed` mid-turn**, а по концу хода (`result`) или кнопке «Перейти в систему» (см. шаг 11) — иначе гейт схлопнется посреди кульминации, до приветствия персоны.

**8. MCP-инструмент назначения дефолта.**

## ADR

**Decision.** Персоны по умолчанию реализуются указателями `User.DefaultPersonaId` / `Project.DefaultPersonaId` (A1); онбординг — обычными сессиями существующего чат-рантайма с полем `Session.OnboardingKind` и промптами через `PersonaPromptProvider` (B1 + правка Архитектора №1); инвариант «новый чат человека — только с персоной» держит фронтовый хелпер `createChatWithContextPersona` со страховкой 400 на бэке под фич-флагом (C1+C2); мост в командные механики — текстовый маркер `<team-mechanic/>` с карточкой-кнопкой и фронтовым дедупом (D1 + правка №6); всё за одним фич-флагом `default-personas-onboarding`.

**Drivers.** (1) Обратная совместимость сторов `data/` — только nullable-поля, без инкремента `BackupSchema.Version`; (2) «курица-и-яйцо» интервьюеров — сессия мастера без персоны уже получает personas-manage существующим механизмом (`SectionOrigin` → `Explicit`); (3) один фич-флаг на весь релиз (dark launch).

**Alternatives considered.** A2 (флаг IsDefault на Persona) — инвариант «ровно один» дорожает до скана, гонки; B2 (wizard-формы) — отклонён спекой R2; B3 (state-machine вне чат-рантайма) — дублирует стрим/пермишены/историю; D2 (widgets MCP) — тяжелее рантайм, нет типизированного запуска; C2-only (только бэк-400) — ошибки вместо UX.

**Why chosen.** Максимальное переиспользование существующего рантайма (чат-стек, resume, permission, MCP-модуль manage, `SeedProjectDefaults`) при минимуме нового состояния; стохастика LLM в двух критичных точках (выход из гейта, повтор предложения после отказа) подпёрта детерминированными рельсами: fallback «Создать персону из разговора» и фронтовый дедуп карточек.

**Consequences.** Плюс: фича почти не добавляет серверного состояния и полностью гейтится флагом; минус: качество онбординга зависит от промптов `OnboardingPrompts` (итерации ожидаемы); появляется вторая семантика у `POST /personas/{id}/make-default` (REST свободный, MCP — только из онбординг-сессии); тест соответствия каталогов механик читает фронтовый файл из бэкенд-теста.

**Follow-ups.** (1) Ворота дизайнера: 2–3 варианта анимации аватара wait-индикатора, согласование с владельцем (блокирует только шаг 19); (2) после обкатки решить судьбу «пустых» чатов у выключивших флаг пользователей не стоит — флаг глобального релиза снимается штатно по готовности; (3) тексты «Что нового» и промптов онбординга — отдельная продуктовая итерация.
