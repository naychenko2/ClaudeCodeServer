# Прогресс долгих прогонов тестов в чате — разведка (2026-10-02)

Вопрос: как показать в чате прогресс `dotnet test` и фронтовых e2e. CLI выдаёт вывод
foreground-Bash только целиком, в `tool_result` (см. [tool-progress-2026-10.md](tool-progress-2026-10.md), §1).
Канал на фронт уже есть: `tool_progress` по `toolUseId`, MCP-тулсет берёт id из
`_meta.claudecode/toolUseId` и шлёт прогресс через `ISessionBroadcaster.ToSession`. Код не писали.

Все замеры ниже сделаны на живом: CLI 2.1.287, .NET SDK 10.0.202, Playwright 1.60.

## 1. Что печатает наш `dotnet test`

Все тестовые проекты — **xunit 2.9 + `xunit.runner.visualstudio`, то есть VSTest**, а не
Microsoft.Testing.Platform. CI: `dotnet test backend/ClaudeHomeServer.slnx --no-build`.

- **Вывод по умолчанию (minimal)** — только упавшие и пропущенные тесты плюс итоговая строка.
  Живого счётчика нет.
- **`--logger "console;verbosity=normal"`** — строка на КАЖДЫЙ тест: `Passed X [407 ms]`,
  `Failed X`, `Skipped X`. Строки приходят **пачками раз в ~1,5 с** (VSTest копит результаты),
  этого хватает. На мини-проекте (12 тестов по 0,4 с) и на наборе `BuildConcurrencyGate`
  реального проекта (13 тестов) счётчик шёл живьём.
- **Вывод локализован**: на этой машине `Пройден` / `Не пройден` / `Всего тестов`. Перед
  разбором обязательно `DOTNET_CLI_UI_LANGUAGE=en` (проверено: даёт `Passed` / `Total tests`).
- **Общее число заранее** VSTest во время прогона не сообщает. Его даёт отдельный проход
  `--list-tests --no-build`, и он дешёвый:

  | Что | Время | Тестов |
  |---|---|---|
  | `ClaudeHomeServer.Tests.dll` | 2,4 с | 7951 |
  | то же с `--filter` | 2,3 с | 13 |
  | весь `ClaudeHomeServer.slnx` (23 сборки) | 6,0 с | 10 778 |

  Список требует уже собранных сборок, поэтому порядок такой: `dotnet build` → `--list-tests
  --no-build` → `dotnet test --no-build`. Число из списка может немного разойтись с фактом
  (параметризованные тесты с несериализуемыми данными считаются по-разному), поэтому процент
  ограничиваем потолком 99 и в итоге берём реальное число из итоговой строки.
- **Итог для модели** надёжнее брать не из консоли, а из TRX
  (`--logger "trx;LogFileName=…"`): имена упавших тестов, сообщения и стеки в виде XML. Консольная
  строка нужна только для прогресса.

## 2. Какие у нас e2e

Playwright: `frontend/e2e/*.spec.ts`, **74 теста в 18 файлах**, запуск `npm run test:e2e`
(`playwright test`), `workers: 1`, `retries: 0`, таймаут теста 90 с. Тесты гоняются **против
уже запущенного приложения** (`PLAYWRIGHT_BASE_URL`, по умолчанию :5000, логин из
`E2E_USER`/`E2E_PASS`). Само приложение они не поднимают, и в CI их нет.

Что дают репортеры (временный спек на 5 тестов по 0,7 с, один падает):

- `list` — сразу `Running 5 tests using 1 worker`, затем `ok 1 … (711ms)` / `x 4 …` по мере
  прохождения. **Общее число известно с первой строки, так что процент честный.**
- `line` — `[3/5] …`, но с ANSI-управлением курсором, разбирать его хуже.
- Свой репортер получает `onBegin` с `suite.allTests().length` (проверено: `BEGIN total=5`) и
  `onTestEnd` со статусом. Для нашей задачи он избыточен: `list` даёт то же.
- Для итога подходит `json` (`PLAYWRIGHT_JSON_OUTPUT_NAME=…`): упавшие тесты, ошибки, пути к
  трейсам. Берём `--reporter=list,json` и `FORCE_COLOR=0`.
- Список (`--list`) занимает 8,6 с, и он не нужен: число уже есть в `Running N tests`.
- Если включены `retries`, в выводе появляются строки `retry #1`. Счётчик ведём по тестам, а не
  по попыткам.

Vitest (`npm test`) идёт секунды, прогресс ему не нужен.

## 3. Ключевые находки про долгий MCP-вызов (проверено своим HTTP MCP-сервером)

| Опыт | Итог |
|---|---|
| `tools/call` ждёт 150 с, настройки по умолчанию | **Через 60 с CLI обрывает вызов**: `tool_result` = `"The operation timed out."`, соединение закрыто. Сервер об этом узнаёт только по закрытию сокета |
| То же с `MCP_TOOL_TIMEOUT=600000` в окружении CLI | Вызов на 90 с дождался ответа (`done 90`) |
| Прерывание (`control_request interrupt`) через 8 с после `tool_use` | `tool_result` сразу отклонён, **HTTP-соединение закрыто сразу**. `notifications/cancelled` CLI не шлёт |
| `_meta` в `tools/call` | `{"claudecode/toolUseId":"toolu_…","progressToken":2}`, ключ карточки есть |
| Модель и MCP-инструмент | CLI прячет MCP-инструменты за `ToolSearch`: модель сначала делает `select:mcp__probe__long_wait` и только потом вызывает |

Отсюда:

- По умолчанию **синхронный MCP-инструмент длиннее 60 с невозможен**. Похоже, именно поэтому
  `local_jobs_wait` ждёт не больше 15 с (`LocalMediaService.MaxWaitSeconds`), а модель вызывает
  его повторно.
- «Стоп» до сервера доходит обрывом запроса. Параметр `ct` контроллера `McpTransportController`
  — это `RequestAborted`, так что отмена прогона по «Стоп» получается бесплатно, если по `ct`
  гасить дерево процесса. Без этого прогон осиротеет и будет молотить дальше. Та же история при
  таймауте 60 с: CLI ушёл, а процесс живёт.

## 4. Варианты

### (А) MCP-инструмент `run_tests`: сервер сам запускает прогон (фаворит)

Сервер запускает процесс через `ILauncherFactory.ForProject(project)`, читает stdout построчно,
разбирает строки и шлёт `tool_progress` на карточку по `toolUseId`. Модель получает сжатую
сводку.

- **Прогресс**: точный, как в таблице §5.
- **Защита от OOM лучше нынешней**: spec с `Heavy = true` и слот `BuildConcurrencyGate.AcquireAsync(spec, ct)`.
  Сейчас тесты, запущенные агентом из Bash, гейт **не видит вовсе** (они потомки процесса CLI),
  а через инструмент встают под общий потолок. Изоляция та же, что у прогрева worktree: local
  на Linux получает systemd-scope в `ccs-agents.slice` (её делает `LocalProcessRunner`), container
  идёт через `DockerProcessRunner`. Пока ждём слот, на карточке «ждёт очереди сборок (занято 2)».
- **Отмена**: по `ct` (обрыв запроса = «Стоп» или таймаут CLI) вызываем `launcher.Kill(process,
  turnId)`. **В песочнице нужен свой `TurnId` в spec**: убийство docker-клиента не трогает
  процесс в контейнере, драйвер добивает его по метке (`IProcessLauncher.Kill`). У
  `WorktreeBuildWarmup` метки нет, это копировать нельзя.
- **Длительность**: нужно одно из двух.
  1. **Синхронный вызов + `MCP_TOOL_TIMEOUT`** в окружении CLI (`ClaudeSession`, где уже стоит
     `MCP_TIMEOUT=30000`), например 30 мин, плюс свой серверный потолок на прогон. Значение
     постоянное, от хода не зависит, сигнатуру запуска не дёргает. Цена: затягивается таймаут и
     у чужих MCP-серверов из личного реестра (зависший внешний сервер будет держать ход дольше
     60 с; «Стоп» работает). Для локальных проектов ключ надо добавить в
     `RemoteProcessRunner.AllowedEnvKeys`.
  2. **`run_tests` + `run_tests_wait`** порциями по ≤50 с, по образцу `local_jobs_wait`.
     Таймаут CLI не трогаем, но каждая порция — лишний шаг модели (повторное чтение всего
     контекста из кэша; 10-минутный прогон = ~12 шагов), а «Стоп» между порциями прогон не
     гасит, нужен свой сторож.

  **Рекомендую вариант 1**: прогресс непрерывный, отмена естественная, токенов не жжёт.
- **Локальные проекты (ADR-016)**: `ForProject` на устройстве даёт `RemoteProcessRunner`, у
  которого stdio тоже идёт потоком, так что технически работает. Но в первой версии лучше
  отказывать через `ProjectCapabilities` («тесты локального проекта запускай Bash'ем»), как
  делает `local-media`. TRX/JSON-файл итога лежит на устройстве, и читать его придётся через
  ретранслятор.
- **Минус**: модель должна выбрать инструмент вместо привычного Bash (см. §6).

### (Б) Читать файл вывода фоновой Bash-команды CLI

У фоновой Bash CLI пишет вывод в `%TEMP%\claude\<slug-cwd>\<session>\tasks\<task_id>.output`
(путь виден и в `task_notification.output_file`), и файл растёт живьём. У foreground-Bash
`output_file` пустой (замер прошлой записки), так что вариант работает **только при
`run_in_background`**.

- Карточка Bash закрывается квитанцией запуска сразу, и прогресс пришлось бы рисовать на
  фоновой задаче (`PendingBg`), а не на карточке.
- Путь — внутренняя раскладка CLI, без контракта. В песочнице файл внутри контейнера, на
  устройстве — на чужой машине.
- Фоновую Bash CLI убивает вместе со своим процессом (ADR-013); агент должен её ещё и ждать.
- Гейт сборок и изоляцию не даёт.

Не рекомендую: хрупко и покрывает только часть случаев.

### (В) Свой dotnet-логгер / playwright-репортер шлёт прогресс на сервер

Логгер (`--logger`, `--test-adapter-path`) или репортер (`--reporter`) отправляет `POST` на
бэкенд. `toolUseId` в Bash-процесс CLI не передаёт, поэтому связывать придётся через
переменные окружения процесса CLI (сессия + токен), которые наследуют потомки, а сервер
сопоставляет их с идущим foreground-Bash сессии (`task_started` с `tool_use_id`). При
параллельных Bash в одном ходе сопоставление неоднозначно.

- Нужен сетевой путь из песочницы и с устройства (там только шлюз), токен в окружении всех
  потомков хода, а агент должен помнить флаги (или их прописывают в props/конфиг каждого
  репозитория — работает только у нас).
- Гейт сборок и изоляцию тоже не даёт.

Плюс один: агент остаётся в Bash. Но частей больше, чем у (А), а польза меньше. Не рекомендую.

## 5. Формат прогресса

| Фаза | dotnet | e2e (playwright) |
|---|---|---|
| Очередь | «ждёт очереди сборок» (неопределённая полоса) | — (лёгкий запуск, вне гейта) |
| Сборка | «сборка» — неопределённая полоса; ошибка компиляции = конец, в итог первые ошибки `error CS…` | — (приложение уже запущено) |
| Подсчёт | `--list-tests --no-build`, 2–6 с, подпись «подсчёт тестов» | число из `Running N tests` |
| Прогон | **точно**: `(passed+failed+skipped)/total`, подпись «412 из 7951 · упало 2», `Exact = true`, потолок 99 | **точно**: по строкам `ok`/`x`/`-`, «12 из 74 · упало 1» |
| Без списка (`--list-tests` упал) | счётчик без процента: «412 пройдено» + неопределённая полоса | — |

Сабсекундная частота не нужна: шлём не чаще раза в 0,5–1 с (VSTest и так отдаёт пачками).
Упавшие тесты показываем на карточке сразу, по мере появления.

## 6. Как заставить агента выбрать инструмент

- **Состав `tools/list` не зависит от хода**: новый статический тулсет (например `tests`,
  инструменты `run_tests`, без `_wait`). Гейты — на вызове (сессия владельца, проект на
  сервере), как у `LocalMediaToolset`.
- Описание инструмента модель **не видит до `ToolSearch`** (опыт §3). Поэтому подсказка нужна в
  системном промпте, секцией с точным именем: «`dotnet test` и `playwright test` запускай
  инструментом `mcp__tests__run_tests`, а не Bash: он показывает прогресс в чате, встаёт в
  очередь сборок и останавливается по „Стоп“». Секция может зависеть от проекта (есть `*.sln*`
  / `playwright.config.*`), от хода — нет.
- Принуждение (хук `PreToolUse` на Bash с отказом `dotnet test`) в первой версии не ставить:
  ложные срабатывания на `dotnet test --list-tests` и чужие сценарии. Сначала посмотреть, как
  часто модель промахивается.

## 7. Что вернуть модели

- Строка итога: `FAILED 3, passed 7948, skipped 12 из 7963 за 4:12` (по каждой сборке, если их
  несколько).
- Упавшие тесты из TRX/JSON: полное имя, сообщение (до ~20 строк), стек — первые 5 кадров
  своего кода. Общий потолок ответа ~8–10 КБ. При переполнении — «и ещё N упавших» плюс путь к
  полному логу.
- Полный лог и TRX/JSON пишем в проект, в `.cc-attachments/test-runs/<id>/` (скрыто из дерева и
  git, хостовый путь видно и из песочницы через маппинг). Модель при нужде читает их Read'ом.
- Ошибки сборки — первые 20 строк `error`, без лога MSBuild.

## 8. Риски

- **Затянутый `MCP_TOOL_TIMEOUT` действует на все MCP-серверы хода**, включая внешние из
  реестра. Смягчение: умеренное значение (30 мин) и свой серверный потолок `run_tests`.
- **Разбор консоли зависит от формата VSTest и Playwright.** Фиксируем `en`-локаль и логгер;
  тест разбора на записанных образцах вывода; переход на MTP или xunit v3 сломает разбор
  (сторож — тест-образец).
- **Модель продолжает гонять тесты Bash'ем.** Тогда прогресса просто нет, как сейчас:
  регресса не будет.
- **Конкуренция за `obj/bin`** с параллельной сборкой агента в том же дереве. Отказывать не
  надо, достаточно предупреждения в описании; прогрев worktree уже решает ту же драку проверкой
  `obj/`.
- **e2e требуют живого стенда**: инструмент его не поднимает. При недоступном `baseURL` —
  быстрый отказ с текстом («подними стенд :5000»), а не 74 таймаута по 90 с.
- **Осиротевший процесс** при падении бэкенда посреди прогона. `Track = true` даёт расстрел
  дерева при штатной остановке, но стартовая зачистка сирот `ProcessRegistry` фильтрует только
  claude/node (комментарий `ProcessSpec.Track`), и `dotnet`/`testhost` после краша она не
  подберёт. На Linux их держит scope в `ccs-agents.slice`, на Windows-хосте нужно либо
  расширить фильтр, либо смириться. В песочнице — `TurnId`.

## 9. Оценка объёма

| Шаг | Объём |
|---|---|
| Тулсет `tests` + `run_tests` (dotnet): запуск через `ForProject`, `Heavy` + гейт, `TurnId`, kill по `ct`, серверный потолок | ~1 день |
| Разбор VSTest (сборка → list → прогон), TRX → сводка, тесты на записанных образцах | ~1 день |
| `MCP_TOOL_TIMEOUT` в env `ClaudeSession` (+ `AllowedEnvKeys`), секция промпта с подсказкой | ~0,5 дня |
| Playwright: `list,json`, проверка стенда, сводка | ~0,5–1 день |
| Фронт: подпись «N из M · упало K» уже умеет `tool_progress`; список упавших по ходу — по желанию | 0–0,5 дня |
| **Итого** | **~3–4 дня** |

## Рекомендация

Делать **(А)**: синхронный `run_tests` с поднятым `MCP_TOOL_TIMEOUT` и подсказкой в промпте.
Первым шагом — dotnet на серверных проектах: точный процент через `--list-tests` (+2–6 с), гейт
сборок и отмена по «Стоп». Вторым — playwright (процент точный сразу). Локальные проекты и
принуждение хуком — после того, как посмотрим на живом, как модель выбирает между инструментом
и Bash. (Б) и (В) не делать.
