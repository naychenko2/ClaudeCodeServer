# Редактор картинок в личных чатах вне проекта: разрез (2026-09-29)

Запрос Андрея: полоса «Картинки» (редактор v3, ADR-019) должна работать и в чате без проекта
(`Session.ProjectId == null`). «Сохранить в проект» там недоступно по построению, взамен можно
скачать картинку. Документ — разрез для раскладки по шагам: что под угрозой, что урезаем и какой
путь минимальный. Всё ниже сверено с кодом `master` на 38b036a3.

## Главный вывод

Жёсткая привязка к `Project` в модуле **тоньше, чем кажется**. Почти всё внутри модуля ключуется
строкой `projectId`, а не объектом `Project`: задачи и котировки (`ImageEditJobService.Find` сверяет
`job.ProjectId == projectId`), шаги рабочей папки (`ImageEditStep.ProjectId`, `ImageEditSteps.Open`),
выбор человека (`data/image-editor-prefs/{ownerId}/{projectId}.json`), события (`ImageThreadChangedMessage.ProjectId`).
Хранилище нитей от проекта не зависит совсем: `data/image-threads/{ownerId}/{sessionId}.json`.
Объект `Project` (то есть `RootPath`) нужен только там, где идёт работа с **диском проекта**: гейт
контроллеров, образцы из проекта, персонажи, открытие нити по файлу, `transform` от файла, `save`.

Поэтому минимальный путь такой: **область редактора (scope) вместо проекта**. У чата проекта это
`project.Id`, у личного чата — одна константа владельца (`"personal"`). Всё, что трогает диск
проекта, у личной области закрыто явным отказом, а не падением.

## 1. Инварианты под угрозой и как их не нарушить

### 1.1. `ProjectLinkGuard.ResolveInside` и запись в проект — неприменимы, а не «кнопка скрыта»

Всё, что ведёт путь от `project.RootPath`, у личного чата физически некуда вести:

| Место | Что делает | Вне проекта |
|---|---|---|
| `ImageEditorController.Save`, `SaveCheck` | запись `FileMode.CreateNew`, проверка имени | ручки нет: `404`/`400 not_in_project`, не 500 |
| `ImageEditorController.Transform` с `Base.Path` | читает файл проекта | `400`, если прислан `Base.Path`; от шага (`Base.StepId`) — работает |
| `ThreadsController.Open` с `file` / непустым `draftFolder` | нить по файлу проекта | только черновик `draftFolder: ""` |
| `ImageEditLaunchAssembler.AssembleAsync`: `ReferencePaths`, `CharacterSlug`, `SourcePath` | чтение с диска проекта | отказ `invalid_request`, если что-то из этого прислано |
| `Characters*` | папка `characters/` проекта | ручек нет |

Инвариант «перезаписи нет» (`CreateNew`) при этом **не ослабляется**: записи в проект вне проекта
нет вообще. Главное правило для исполнителя: у `Project?` = `null` каждая ветка «диск проекта»
обязана вернуть явный отказ ДО обращения к `RootPath`. `null!` через `out Project project`, как
сейчас в `Gate`, недопустим: первое же `project.RootPath` даст `NullReferenceException` и 500.

### 1.2. Нить и владение чатом — скрытая зависимость от `ProjectId` есть, в трёх местах

Хранилище `ImageThreadStore` чистое. Зависимость сидит в `ImageThreadService` и в гейте ручек:
владение чатом там **выводится из проекта** («чат этого проекта, а проект уже свой»):

- `ThreadsController.Gate`: `session.ProjectId != found.Id` → 404. Для личного чата проекта нет,
  поэтому владение надо проверять напрямую: `directory.ResolveOwnerId(session) == UserId`
  **и** `session.ProjectId is null`. Без второго условия личная ручка откроет нити чата проекта
  мимо гейта проекта (флаг `FileBound`, локальные проекты ADR-016).
- `ImageThreadService.OwnChat(projectId, sessionId)`: `s.ProjectId == projectId`. Это то же правило, и
  от него зависят `OwnThread` → запуск в нить и сохранение.
- `ImageThreadService.RunningLaunch`: `session.ProjectId != job.ProjectId` → `null`. **Это самая
  опасная грабля**: без правки запуск в личном чате пройдёт, трата запишется, а варианты **никогда
  не станут версиями**. Карточка навсегда повиснет в «Рисуем…», ошибки нигде не будет.
- `RecoverInterruptedAsync`: `projectId is null` → все задачи считаются мёртвыми (что после
  перезапуска верно), но `BroadcastAsync` пропускается. Некритично, но правится той же функцией.

Как не нарушить: одна функция сопоставления «сессия ↔ область» (например
`ImageEditScope.Of(session)` → `session.ProjectId ?? Personal`), и её зовут все четыре места.
Инлайновых `?? "personal"` по месту не заводить: разойдутся.

### 1.3. Ключ личной области — один на владельца, НЕ на чат

Соблазн взять ключ `chat-{sessionId}` ломает ветвление: `ImageThreadLifecycle` на
`session/branched` копирует нити с теми же `threadId` и шагами, а шаг хранит `ProjectId` старой
области. `ImageEditSteps.Open` сверяет `found.Step.ProjectId == projectId` → в ветке все версии
пропадут. В проекте это не всплывает, потому что ветка остаётся в том же проекте.

Поэтому ключ личной области — **константа** (`"personal"`). Изоляция от этого не страдает:

- шаги лежат под `data/image-editor/{ownerId}/…`, задачи сверяют `OwnerId`, чужой владелец их не видит;
- принадлежность нити чату держит хранилище нитей (`{ownerId}/{sessionId}.json`) и `OwnThread`.

Между личными чатами одного владельца шаги формально «видны» по `stepId`, но только самому
владельцу: это его же картинки, и «угадать» случайный `stepId` чужого чата значит угадать свой.
Ключ не пересекается с id проекта: те — `Guid.ToString()` с дефисами. Двоеточие в ключе нельзя:
`ImageProjectPrefsStore.Safe` его запрещает.

### 1.4. Персонажи и образцы из проекта — урезаем осознанно

У личного чата нет дерева файлов, значит нет ни `characters/`, ни «образца из проекта». Другой
источник (личная библиотека персонажей владельца) — отдельная фича с хранилищем, бэкапом и UI;
в первую итерацию она не входит. Остаётся **«+ Образец → С компьютера»**: он приходит байтами
(`References` в multipart) и `RootPath` не трогает. В полосе у личной области скрываются чип
персонажа, пункт «Персонажи» и пункт «Из проекта» в выборе образца.

### 1.5. Швы `ImageEditorSubsystem`: кому нужен проект

| Шов | Нужен `Project`? | Вне проекта |
|---|---|---|
| `IChatFeed.AppendRecordAsync(sessionId, …)` | нет | работает как есть |
| `ISessionBroadcaster.ToOwner` | нет (`ProjectId` в событии — просто строка) | работает, в событие едет ключ области |
| `ISessionDirectory` | нет, но гейт выводит владение из проекта | проверка через `ResolveOwnerId`, см. 1.2 |
| `IProjectManager` | да | не зовётся |
| `IProjectFiles.NotifyMutated(root, …)` | да | не зовётся: записи в проект нет |
| `IImageRaster`, `IImagePlaceSettings`, `ILocalImageMedia`, `IHiggsfieldAccess` | нет | работают как есть |
| `ISpendCollector` | нет, `SpendRecord.ProjectId` nullable | **писать `null`, а не `"personal"`** — иначе «Расход» получит несуществующий проект |
| `IDelegatedTurnGate` | нет | касается только тулсета, а он вне проекта не едет |
| `ITurnEventBus` (`ImageThreadLifecycle`) | нет | удаление и ветвление личного чата уже работают |
| `ImageThreadPathTracker` | да (переименования файлов проекта) | не касается: у личных нитей нет файла |

Трата, лимиты и потолки исполнителя (2 задачи на владельца, 4 на инстанс, `MaxLaunchesPerTurn`)
ключуются по владельцу и работают без изменений. Единственная правка — `WriteSpend` пишет
`ProjectId` области, если это проект, и `null` у личной.

### 1.6. MCP-тулсет `image-editor` вне проекта не раздаётся — и в первой итерации не нужен

`SessionManager.BuildImageEditorContext` возвращает `null` при пустом `session.ProjectId`, и блок
хвоста хода `ImageEditorStateContributor.HasThreads` тоже требует `ProjectId`. Значит, в личном
чате у агента нет ни инструментов, ни блока состояния картинок. Для постановки это нормально:
человек рисует сам, агент картинок не видит. **Не чинить в этой итерации**: условие входит в
сигнатуру запуска CLI (`McpToolsetStabilityTests`), и его смена — отдельная задача со своим риском.
Попутное следствие — «Сохранить в проект» у агента и так нет (ADR-019, решение 1).

Одна оговорка для текста интерфейса: пометки «в режиме Чат» уходят агенту снимком-вложением
(`takeMarksAttachment`), и это вне проекта работает. Но агент, получив их, ничего не нарисует:
инструмента `image_generate` у него нет. Режим «Чат» у личной области стоит либо скрыть, либо
честно подписать.

### 1.7. `FileBound`-гейт (ADR-016) не мешает

`ProjectCapabilityAttribute` без `projectId` в маршруте пропускает вход дальше. Сторож G1
требует разметку только у входов с параметром проекта, у личного маршрута его нет. Отметку
`ProjectCapabilityArea.Platform` («вход проверен, файлов проекта не трогает») стоит поставить
явно, чтобы намерение было видно; нужна ли она G1 формально — проверить прогоном сторожа.

## 2. Минимальный путь

### Бэкенд (Денис)

1. **Область.** В модуле — `ImageEditScope(string Key, Project? Project)` плюс `const Personal = "personal"`
   и `Of(Session)`. `ImageEditLaunchAssembler.LaunchAsync/AssembleAsync` принимает область вместо
   `Project`: `project.Id` → `scope.Key`, диск проекта — только при `scope.Project is { } p`,
   иначе отказ на `ReferencePaths` / `CharacterSlug` / `SourcePath`.
2. **Сопоставление чата.** `OwnChat`, `OwnThread`, `RunningLaunch`, `RecoverInterruptedAsync` —
   через `ImageEditScope.Of(session).Key`. Это обязательный шаг, а не полировка (см. 1.2).
3. **Ручки личной области.** Новый маршрут
   `api/image-editor/chats/{sessionId}/…`, `[Authorize]`, `[ProjectCapability(Platform)]`. Гейт: флаг →
   сессия существует, `ResolveOwnerId(session) == UserId`, `session.ProjectId is null` → область
   `Personal`. Состав: `catalog`, `quote`, `jobs` (POST, GET, DELETE, `variants/{n}`), `steps/{stepId}`,
   `transform` (только от шага), `threads/*` (как у `ThreadsController`, `Open` только с
   `draftFolder: ""`), `prefs` (GET/PUT, `characterSlug` принудительно `null`). **`save`, `save/check` и
   `characters*` не заводить**. Реализация — общий код с проектными контроллерами за
   гейтом-областью, а не копия: две копии разойдутся в проверках, а это ровно дыра ADR-018 §2.
   Проектные маршруты не менять.
4. **Трата.** `WriteSpend`: `ProjectId = scope.Project?.Id` (у личной `null`), см. 1.5.
5. **События.** `ImageThreadChangedMessage`, `ImageEdit*Message`, `image_prefs_changed` несут
   `ProjectId = scope.Key`. Контракт поля не меняется, меняется смысл: «ключ области».

### Фронтенд (Кира)

1. **Хост полос.** `ComposerStripCtx.projectId` и `isAvailable({ projectId })` → `string | null`.
   В `ChatPanel.tsx:2881` условие `project && !embedded` у `ComposerStripHost` снимается до
   `!embedded`, встроенная полоса Git передаётся только при `project`. Полоса «Руки»
   (`handsStripAvailable`) на `null` обязана вернуть `false`. `LocalHandsStripFeed` (`:2880`) не трогать.
2. **Ключ области — внутри модуля.** Функция `imageScope(projectId: string | null)` → `projectId ?? 'personal'`
   и `imageBase(scope, sessionId)` → `/projects/{id}/image-editor` либо
   `/image-editor/chats/{sessionId}`. `api.ts` и `threadsApi.ts` строят URL только через неё.
   Сигнатуры с `projectId: string` можно оставить строковыми (ключом области), но тогда
   **ни одно место с ключом области не зовёт проектное API каркаса** (`appApi.files.fileUrl`,
   `ProjectImagePicker`, `CharactersPanel`). Это проверить grep'ом по модулю: типы здесь не спасут.
3. **Карточки ленты.** `ChatItemToolCtx.projectId` в личном чате `null` — сейчас `LaunchAnchor`
   (`VersionCards.tsx:225`) и якорь нити рисуют только fallback-текст. Нужна область из
   `projectId ?? 'personal'`.
4. **«Сохранить» → «Скачать».** Скачивание уже есть: `IconButton «Скачать»` в `VersionCard`
   (`VersionCards.tsx:134`, `download(src, name)` по `stepUrl`/`variantUrl`). Нужно только
   `versionPrimary` (`model.ts:162`) у личной области отдавать не `'save'`, а `'download'`
   (главная кнопка «Скачать»), и скрыть «Сохранить»/«Сохранить как…» в `EditorModal` (`:172`), а также
   бейдж «черновик / в проекте» у `VersionCard`. Серверной ручки для скачивания не нужно.
   Имя файла у черновика — `threadName()` = «новая картинка» без расширения; лучше `image-v{N}.{ext}`.
5. **Урезанное в полосе.** Скрыть: чип персонажа, «Персонажи», «Из проекта» в образцах,
   открытие из дерева файлов. Остаются «Новая картинка» (черновик в корне), генерация, правка
   от версии, правки без ИИ от шага, образцы с компьютера, выбор поставщика/модели/числа.

### Проверка готовности

- Бэкенд: запуск в личном чате → варианты стали версиями (тест на `RunningLaunch` с
  `session.ProjectId = null`; мутация — вернуть старое сравнение, тест краснеет).
- Ветвление личного чата: версии видны в ветке (тест на ключ-константу).
- Чужой личный чат и личная ручка на чате проекта → 404 одинаковым телом.
- `save` / `characters` по личному маршруту → 404, а не 500. `transform` с `Base.Path` → 400.
- Трата личного запуска: `ProjectId == null`, `SessionId` проставлен.
- Сторожа: `SubsystemBoundaryTests`, `McpToolsetStabilityTests` (без изменений), G1 по `ProjectCapability`.
- Фронт: `npx tsc -b`, `npm run lint:design`; в личном чате нет Git и «Рук», есть «Картинки»,
  нет «Сохранить», «Скачать» отдаёт файл.

## 3. Что осознанно не делаем в первой итерации

- Агентский сценарий вне проекта (MCP `image-editor`, блок хвоста хода) — см. 1.6.
- Персонажи и образцы для личных чатов — нужен свой источник, см. 1.4.
- Нить по файлу: у личного чата файлов нет, только черновик. Загрузка своей картинки как
  исходника («открыть с компьютера») — полезный следующий шаг, но это новый вход нити с загрузкой
  байтов (`Open` сейчас принимает только путь), а не снятие ограничения.
- Перенос картинки из личного чата в проект.

## 4. Где проходит граница

Понятие «проект может отсутствовать» (`string | null`) живёт на уровне каркаса: `ChatPanel`,
`ComposerStripHost`, `ComposerStripCtx`, `ChatItemToolCtx`. Внутри модуля редактора всегда есть
непустая **область**: либо проект, либо `personal`. Проектные ручки, их тесты и контракт с
`ProjectCapability` не меняются. Меняются гейт-область, четыре точки сопоставления чата и
трата. Так правка остаётся локальной, и не приходится протаскивать `projectId: string | null`
через все ~40 сигнатур фронта модуля и через сборщик запуска.

Решение стоит закрепить коротким дополнением к ADR-019 («§ личная область»), когда реализация
пройдёт ревью. Иначе следующий читатель `CLAUDE.md` модуля («в любом чате проекта») будет
считать это ограничение действующим.
