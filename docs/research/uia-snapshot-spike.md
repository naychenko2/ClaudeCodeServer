# Спайк: пригодность UIA-снапшота для модели (ADR-008)

**Дата:** 2026-08-13 (часть 1) · 2026-08-19 (часть 2)
**Связанный ADR:** [ADR-008 Десктопный агент](../adr/ADR-008-desktop-agent.md), раздел «Форма
снапшота UIA»
**Прототип:** `tools/uia-spike/` (консольная утилита .NET 10 + FlaUI.UIA3, вне основного решения)

> Цель — проверить экспериментом, пригоден ли формат снапшота, заложенный в ADR-008, **до того,
> как по нему начнут писать клиент**. Отрицательный результат меняет форму снапшота, а значит и
> раздел ADR.

## Вердикт

**Формат ADR-008 НЕ пригоден как есть.** Пять из шести допущений в разделе «Форма снапшота» не
выдерживают встречи с реальными окнами:

1. **Бюджет ~120 строк** провален на 3 окнах из 6 (Проводник 266, VS Code 251, Outlook 236).
2. **Идентичность по `AutomationId`** невозможна: ID дублируется (Проводник: 10 дубликатов —
   `UpButton`, `ScrollbarThumb` и т.д.) и отсутствует у большинства элементов (Outlook 18.6 %,
   Edge 28 %). Это не «ключ когда есть», а шумовое поле.
3. **«Более одного кандидата в допуске = безусловный отказ»** ложно срабатывает на 6–13 % элементов
   (Outlook 6.4 %, Edge 12.6 %), почти полностью — на элементах с пустым `Name`.
4. **Стоимость построения снапшота** на Chromium доходит до **17.4 с** — это ломает интерактивность
   (дедлайн `ui` в ADR — 20 с, и это на один снимок, а не на батч).
5. **Кадр + снапшот одним захватом** технически реализуемы, координаты совпадают (100 %), но зазор
   равен времени `capture` — на тяжёлых окнах те же 17 с, то есть «одномоментность» фикция.

Корректирующее действие — раздел «Форма снапшота» ADR-008 переписать по пункту «Требуемые
изменения формата» ниже. Открытый вопрос № 5 ADR (этот спайк) — закрыт отрицательным ответом.

## Что измерено и как

Прототип `tools/uia-spike/` (FlaUI.UIA3, обёртка над UIA3 COM) снимает снапшот top-level окна:
обход ControlView-дерева через `TreeWalker`, для каждого узла — `ControlType`, `Name`,
`AutomationId`, `BoundingRectangle`, `IsOffscreen`, поддерживаемые паттерны. Фильтр ADR
(«actionable ИЛИ собственный текст, исключая offscreen») применён как в ADR. Замеры на реальных
приложениях машины-владельца, интерактивная сессия.

Две методические оговорки (важны для интерпретации):

- **Дерево зависит от способа обхода.** Быстрый счёт узлов (`TreeWalker` без чтения свойств) и
  полный захват со свойствами дают **разные** деревья на Chromium/Electron (см. пункт 4). В
  таблице ниже «узлов всего» — это полный захват со свойствами: именно он нужен агенту, потому что
  без свойств фильтр и отпечаток не построить.
- **Динамика (скролл, ресайз, смена вкладки) вносилась внешним шагом** между запусками, а не внутри
  прототипа: программный скролл через паттерны UIA непортабелен между тулкитами. Серии стабильности
  в таблице — статичные (окно в покое); это нижняя граница: любое реальное действие только
  увеличит расхождение.

## Сводка по пунктам 1–6

### 1. Объём — бюджет 120 строк нереалистичен

Три окна из шести не влезают: Проводник 266, VS Code 251, Outlook 236. Для них «свёрнуто ещё N»
(хвост ADR) прячет 116–146 элементов каждый — это не край дерева, а содержимое рабочей области
(пункты списков, кнопки ленты, строки таблицы). Edge с длинным списком влез в 120 только потому,
что Chromium отдал для 1500-строчного списка ~95 accessibility-узлов видимой части — то есть
«виртуализация» спасает бюджет, но это свойство движка, а не формата.

### 2. Стабильность отпечатка — стабильна в статике, но `AutomationId` не уникален

Серии (3 снимка в покое) на Проводнике и Outlook: отпечаток «роль+имя+размер+позиция» совпал на
**100 %**, правило инвалидации ADR (роль+имя, ±5 % размер, смещение центра ≤ полувысоты) — тоже
**100 %**. Состав (`filtered`) между снимками не дрейфит. **Но**: на Проводнике **10 дублирующихся
`AutomationId`** (`UpButton`, `ScrollbarThumb`, `DownPageButton`, `DownPageButton`,
`System.ItemNameDisplay`, `DropDown`, …) — это стрелки прокрутки и повторяющиеся колонки. То есть
`AutomationId` в ADR — **не первичный ключ**: он не уникален даже в одном окне и отсутствует у
большинства элементов.

### 3. Ложная неоднозначность — 6–13 % элементов отказывают на ровном месте

| Окно | filtered | С >1 кандидатом | % | макс. кандидатов |
|---|---:|---:|---:|---:|
| Блокнот | 35 | 0 | 0.0 % | 1 |
| Проводник | 266 | 0 | 0.0 % | 1 |
| Outlook | 236 | 15 | **6.4 %** | 3 |
| Edge (2 вкладки) | 95 | 12 | **12.6 %** | 4 |

Допуски ADR (±5 % размер, смещение центра ≤ полувысоты) идеально работают на чистых Win32-окнах и
**систематически пасуют** на Chromium/Electron и Win32-rich. Все коллизии в Edge — на элементах с
**пустым `Name`** (`Pane ""` с одинаковой геометрией: вложенные `div`-контейнеры Chromium). В
Outlook — дубли ленты, эмблем, данных писем. По правилу ADR это безусловный отказ: на Chromium
каждое восьмое действие модели упрётся в «элемент изменился, вот новый снапшот» без реального
изменения.

### 4. Прогрев accessibility в Chromium — гипотеза «греть N секунд» не подтвердилась

Перепроверка предыдущего замера (5 окон, без прогрева):

- **Лёгкая страница** (`page-simple.html`, свежее окно): `count` = `capture` = 101, стабильно на
  повторах. «Прогрев по времени» **не нужен** — дерево доступно сразу.
- **Тяжёлая страница** (1500-строчный список + вторая вкладка): `count` = 61, `capture` = 3067.
  Расхождение **×50** — это не время после старта, а **ленивая материализация дерева при чтении
  свойств**: `TreeWalker` без свойств видит малую часть, а `GetSupportedPatterns`/`Name` заставляют
  Chromium достроить полное accessibility-дерево.
- **Фоновая вкладка не попадает в снапшот**: на окне с двумя вкладками активная определяет состав.

Вывод: значимые факторы — **объём страницы** и **чтение свойств vs обход**, а не «прогрет ли Edge N
секунд». Предыдущий замер корректен в том, что Chromium отдаёт неполное дерево «без запроса», но
механизм — лень свойств, а не таймер прогрева.

### 5. Стоимость — 17 секунд на тяжёлом Chromium

| Окно | `capture`, мс |
|---|---:|
| Блокнот | 267 |
| Edge, обычная страница | 467 |
| VS Code (Electron) | 1412 |
| Проводник | 2136 |
| Outlook | 2127 |
| Edge, длинный список (2 вкладки) | **17 436** |

Лёгкие Win32 — четверть секунды. Средние (Проводник, Outlook, VS Code) — 1.4–2.1 с. Тяжёлый
Chromium — 17 с. Дедлайн `ui` в ADR — 20 с; один снимок Edge съедает 87 % бюджета, а кадров в
батче может быть несколько. Без кеширования свойств интерактивный агент на браузере/Electron
недопустимо медленный.

### 6. Set-of-mark — реализуемо, координаты совпадают, но зазор = время `capture`

На Блокноте: кадр (`BitBlt`) = 55 мс, `capture` = 213 мс, итого 269 мс одним заходом.
`coords_inside_frame` = **35/35 (100 %)** — прямоугольники UIA точно совпадают с пикселями кадра
(DPI PerMonitorV2 даёт физические координаты в обоих случаях). Метки (set-of-mark) наносятся по
экранным координатам элементов, проверено на PNG.

Зазор между кадром и снапшотом = время `capture`. Для статичного окна это безопасно (269 мс). Для
тяжёлого — те же 17 с, на динамичном окне метки на кадре относятся к устаревшему срезу. Запасной
вариант ADR (`desktop_screen` принимает `snapshotId` и отвечает `snapshot_stale`) — не запасной, а
**обязательный**: без него «одномоментность» гарантируется только на лёгких окнах.

## Требуемые изменения формата (для раздела ADR)

| Допущение ADR-008 | Что показал спайк | Изменение |
|---|---|---|
| Бюджет ~120 строк | 3 окна из 6 не влезают (до 266) | Поднять до **250–300** + приоритизация: сначала элементы в области просмотра (viewport) и с непустым `Name`; хвост честно считать «свёрнуто N», но не прятать за ним содержимое |
| Идентичность по `AutomationId` (когда есть) | ID дублируется (Проводник) и отсутствует у большинства (Outlook 18 %, Edge 28 %) | Убрать `AutomationId` как первичный ключ. Идентичность — **только отпечаток** «роль + имя + геометрия + позиция». `AutomationId` — вспомогательное поле для хит-теста/логов, не для разрешения цели |
| «>1 кандидат в допуске = безусловный отказ» | 6–13 % ложных отказов, все на пустом `Name` | Элементы **без `Name` и без «контрол-паттерна»** (Invoke/Toggle/Value/SelectionItem) исключать из снапшота модели. При множестве кандидатов — **разрешать hit-test'ом точки** (ADR упоминает hit-test «перед кликом», но он должен снимать неоднозначность, а не дублировать отказ) |
| Допуски ±5 % / половина высоты | На чистых окнах идеальны, на Chromium/Outlook пасуют | Допуски оставить, но разрешение неоднозначности — по `Name`+`AutomationId`+hit-test, а не «безусловный отказ» |
| Стоимость построения не оговорена | До 17 с на Chromium | Ввести бюджет времени `ui` на построение снапшота; требовать `CacheRequest` (FlaUI) для пакетного чтения свойств; на тяжёлых окнах ограничивать глубину/регион |
| «Кадр и снапшот одним захватом» как норма | Зазор = время `capture` (до 17 с) | Оставить как цель для лёгких окон, но `snapshot_stale`-чек по `snapshotId` сделать **обязательным** для всех окон: единственный честный способ связать метки на кадре с `ref` |

## Приложения, которые ломают формат

- **Chromium (Edge, VS Code/Electron).** Ленивая материализация дерева (`count` vs `capture` до ×50),
  17 с на построение, 12.6 % ложных отказов на пустых `Pane`, фоновые вкладки не видны. Самый
  тяжёлый класс для плоского снапшота.
- **Win32 rich (Outlook, COM-лента).** 236 элементов (бюджет), `AutomationId` лишь у 18.6 %,
  6.4 % ложных отказов (дубли ленты/эмблем/данных писем).
- **Проводник (Win32/UXA).** 266 (бюджет), 10 дублирующихся `AutomationId`.
- **UWP hosted apps («Настройки», `spokenly`).** В фоне — suspended, дерево пустое (0–1 узел).
  Top-level HWND процесса контента (`SystemSettings`) не отдаёт дерево; окно живёт в
  `ApplicationFrameHost` (рамка), а реальный контент — в hosted-процессе. Для десктоп-агента это
  значит: «окно по PID» недостаточно — нужна логика главного окна с учётом hosted apps, и UWP-окно
  вне foreground снапшоту не поддаётся.
- **Любой процесс, не отдающий свойства.** `Name` и `AutomationId` бросают
  `PropertyNotSupportedException` на части элементов (UWP, отдельные Win32). Safe-access с
  fallback — обязателен, иначе снятие снапшота падает целиком.
- **Свёрнутое в трей приложение (Telegram).** HWND не существует, пока пользователь не развернёт.
  Агент не может «посмотреть окно мессенджера», если оно в трее.

## Воспроизведение

```powershell
cd tools/uia-spike
dotnet build
dotnet run -c Debug -- windows                    # список видимых top-level окон
dotnet run -c Debug -- capture <pid> [--lines]    # объём + стоимость + строки формата ADR
dotnet run -c Debug -- count <pid>                # быстрый счёт (без свойств) — для пункта 4
dotnet run -c Debug -- series <pid> --count 3     # стабильность отпечатка + дубли AutomationId
dotnet run -c Debug -- collisions <pid>           # частота множественных кандидатов
dotnet run -c Debug -- warmup <pid> --delay 3000  # два снимка с интервалом (прогрев)
dotnet run -c Debug -- som <pid> --out x.png      # кадр + снапшот одним захватом, метки на PNG
```

Прототип вне `ClaudeHomeServer.slnx`, зависимость `FlaUI.UIA3` только в `tools/uia-spike/`. В
продакшен-код бэкенда и фронта спайк не лез, в основное решение зависимостей не добавлено.

# Часть 2: динамика отпечатка и CacheRequest (2026-08-19)

Закрыты открытые вопросы 6 и 7 ADR-008: поведение правила инвалидации **под действием**
(скролл, ресайз, смена вкладки) и подтверждение `CacheRequest` как лекарства от 17 секунд.
Прототип расширен командами `dynamics`, `cache` и `panel`; действия вносятся программно —
колесо и клавиши через `SendInput`, ресайз через `SetWindowPos` (+10 %, с восстановлением),
как это будет делать продукт.

## Вердикт части 2

- **Вопрос 7 (CacheRequest): подтверждён с запасом.** Кеш поддерева одним вызовом
  (`ElementFromHandleBuildCache` + `TreeScope_Subtree`) сбивает худший случай с
  **17.8 с до 0.44 с (×40)** при **100 % состава** на всех окнах. Бюджет 5 секунд из ADR
  выполняется на всём наборе; пошаговый walker-кеш тоже влезает (×7), но стабильно теряет
  по одному элементу — брать именно subtree-режим.
- **Вопрос 6 (правило инвалидации под действием): не безопасно в текущем виде.** Тихая
  подмена систематична на скролле виртуализированных списков — до **45 %** элементов
  (Проводник) и до **20 %** (Chromium-список), всегда на строках, неотличимых по
  «роль+имя». Ресайз даёт 60–65 % ложных «элемент изменился». Нужна третья правка раздела
  «Форма снапшота» — см. «Требуемые изменения по части 2» ниже.

## Методика

- **Oracle «тот же элемент» — UIA `RuntimeId`**: уникален для живого элемента, переживает
  смещение и смену геометрии, умирает вместе с элементом (виртуализация пересоздаёт узлы —
  для замера это и есть истина). Правило ADR сверяется с oracle: «удержало» = нашёлся
  элемент с тем же rid; «тихая подмена» = в допусках нашёлся другой; «ложная потеря» =
  цель жива (rid есть во втором снимке), правило не нашло. Контроль `action=none`
  валидирует oracle: в покое rid стабилен на 100 % известных, состав не дрейфит.
- Правило ADR: роль+имя, размер ±5 %, смещение центра ≤ полувысоты (и ≤ полуширины —
  оговорка части 1). Из прошедших допуск выбирается ближайший по центру — эмуляция
  разрешения hit-test'ом центра из ревизии 3 ADR.
- Подмена разделена на классы: **same_rect** (кандидат с той же геометрией ±2px — клик
  уйдёт в ту же точку) и **diff_rect** (геометрия другая — тихий промах). На
  виртуализированных списках same_rect тоже опасен: точка та же, а строка данных под ней
  уже другая.
- Окна: Блокнот (400 строк), Проводник (System32, вид «Подробности»), VS Code (Electron),
  Edge с обычной страницей и с 1500-строчным списком. Outlook не запущен — почтовый клиент
  владельца не открывали, класс Win32-rich покрыт Проводником. Ctrl+End в Edge
  программно не долетает до страницы (фокус документа) — «до конца» измерено на Блокноте и
  Проводнике, для Chromium-списка — серии скролла.

## Замер 1: правило инвалидации под действием (вопрос 6)

Доли от элементов базового снимка; «подмена» = правило нашло другого в допусках.

| Окно × действие | held | lost_false | подмена | из неё diff_rect |
|---|---:|---:|---:|---:|
| Блокнот — покой (контроль) | 100 % | 0 | 0 | 0 |
| Блокнот — скролл 3 тика | 97.6 % | 2.4 % | 0 | 0 |
| Блокнот — в конец (Ctrl+End) | 90.2 % | 0 | 0 | 0 |
| Блокнот — ресайз +10 % | 35.3 % | **64.7 %** | 0 | 0 |

### Тихая подмена — примеры (главный класс отказа)

Механика одна и та же в Проводнике и Chromium:

- Строки виртуализированного списка **неотличимы по отпечатку**. Проводник в виде
  «Подробности» отдаёт ячейку как `Edit` с `Name` = заголовок колонки — в снапшоте десятки
  одинаковых `Edit "Имя"`; в Chromium-списке строки — безымянные `Group`.
- Smooth scrolling останавливает сетку со сдвигом 0–4px. Допуск «смещение центра ≤
  полувысоты» (11px при высоте строки 22px) этот сдвиг покрывает — правило находит
  **соседнюю строку, пересозданную виртуализацией** (другой rid), и считает её той же
  целью. Клик уходит в соседний файл/строку без единого сигнала.

```
Проводник, скролл 3 тика (сдвиг сетки 4px):
  base Edit Имя 236x22 @(1069,377) rid=28524.107371200.0
   -> Edit Имя 236x22 @(1069,381) rid=28524.1438708656.0   ← соседняя строка, тихий промах

Edge 1500-строчный список, скролл 3 тика (сдвиг 4px):
  base Group "" 1320x32 @(445,231) rid=42.201696.4.12.5.19
   -> Group "" 1320x32 @(445,227) rid=42.201696.4.12.5.47  ← соседняя строка, тихий промах

Фон на Chromium в любом прогоне (в покое тоже):
  base Pane "" 1345x858 @(440,154) rid=42.136398.4.0.0.995
   -> Pane "" 1345x858 @(440,154) rid=42.136398.4.0.0.1002 ← вложенные div, та же точка
```

От фазы остановки скролла зависит, попадает ли подмена в diff_rect (сдвиг 4px — соседняя
строка на 4px ниже) или в same_rect (целочисленный сдвиг — на место цели встаёт другая
строка): два прогона Проводника дают 45.1 % / 0 % diff_rect при одинаковой полной доле
подмены ~45 %. В same_rect-случае клик уходит в ту же точку — но строка данных под ней
другая, для продукта это та же тихая порча цели.

## Замер 2: CacheRequest против 17.4 секунды (вопрос 7)

Три режима чтения одного и того же ControlView-дерева: `plain` — живые свойства (как в
части 1), `walker` — пошаговый кеш на каждом узле (`Get*ElementBuildCache`), `subtree` —
кеш всего поддерева одним вызовом (`ElementFromHandleBuildCache`, `TreeScope_Subtree`,
`TreeFilter=ControlViewCondition`). Перед замером — прогрев (полный plain-захват,
выброшен): иначе первый режим платил бы за ленивую материализацию Chromium. 3 повтора,
в таблице медиана; «состав» — доля `filtered`-элементов plain-снимка, отсутствующих в
кеш-режиме.

| Окно | узлов | plain, мс | walker, мс | subtree, мс | ×subtree | состав walker | состав subtree |
|---|---:|---:|---:|---:|---:|---|---|
| Блокнот | 60 | 420 | 99 | **59** | ×7 | 97.8 % | **100 %** |
| Проводник | 318 | 3758 | 652 | **250** | ×15 | 99.6 % | **100 %** |
| VS Code (Electron) | 206 | 1569 | 294 | **48** | ×33 | 99.5 % | **100 %** |
| Edge, обычная страница | 102 | 730 | 127 | **34** | ×21 | 98.9 % | **100 %** |
| Edge, 1500-строчный список | 3104 | 17 831 | 2659 | **444** | **×40** | 99.2 % | **100 %** |

- **17.4 с из части 1 воспроизводится как «тёплый»**: тёплые plain-захваты того же окна —
  16.2–23.1 с. Прогрев не лечит: материализованное дерево Chromium читается по-свойству
  так же медленно, стоимость — в живых чтениях, а не в первичной материализации.
- **Кеш не теряет дерево.** Subtree-режим: 0 пропавших, 0 добавленных, 100 % покрытие на
  всех окнах (сравнение по роли+имени+геометрии). Walker стабильно теряет ровно 1 элемент
  (0.4–2.2 %) на любом окне — артефакт пошаговых `BuildCache`-переходов; ещё одна причина
  выбрать subtree.
- **Регион/панель не понадобился**: бюджет 5 с выполняется на всём наборе с subtree-кешем.
  Для справки замерена панель без кеша на Проводнике: список файлов 2435 мс против окна
  целиком 2872 мс (×1.2, покрытие состава 78.7 %) — **сначала кеш, потом регион**;
  регион без кеша почти ничего не даёт.

## Требуемые изменения по части 2 (для раздела ADR)

| Пункт ADR | Что показала часть 2 | Изменение |
|---|---|---|
| «Допуски инвалидации подтверждены: в покое 100 %» | В покое — да; под действием тихая подмена до 45 % на списках, ложная потеря до 65 % на ресайзе | Правило инвалидации применять **только к целям с уникальным отпечатком «роль+имя» в снапшоте**. Для неуникальных (ячейки таблиц, безымянные строки списков) совпадение в допусках НЕ считать удержанием — отвечать «элемент изменился» (безопасная инвалидация через новый снапшот). Это штатный поток: скролл списка всё равно пересоздаёт строки |
| «Бюджет 5 с, свойства читаются пакетно (`CacheRequest`)» | Подтверждено: ×7–40, худший случай 0.44 с | Конкретизировать режим: **кеш поддерева одним вызовом** (`ElementFromHandleBuildCache` + `TreeScope_Subtree` + `ControlViewCondition`), состав 100 %. Пошаговый walker-кеш — не вариант (медленнее и теряет по элементу) |
| — | Ресайз окна ломает допуск ±5 % у 60–65 % элементов | После ресайза окна **не переиспользовать ref совсем** — снапшот целиком инвалиден (с кешем это стоит десятки миллисекунд). Зафиксировать как отдельное правило |

**Вердикт по форме снапшота.** Форма из ревизии 3 финализируется по пункту стоимости
(`CacheRequest` подтверждён), но правило инвалидации требует третьей правки — двух
ограничений из таблицы выше (уникальность отпечатка как предусловие доверия правилу;
ресайз = полная инвалидация). Без них агент будет молча кликать в соседнюю строку списка.
