# ADR-032: грабли исполнителей и журнал изменений памяти

- **Статус:** предложено 2026-10-18 (Артём по просьбе Андрея: «делай ADR и замер»). Решение 1 готово к реализации. Решение 3 — пилот за флагом, его судьба решается по критериям раздела «Пилот».
- **Вход:** замер [experience-layer-measure.md](../research/experience-layer-measure.md) на 123 реальных задачах исполнителей (20 целей, 186 записей опыта, артефакты — [experience-layer-measure/](../research/experience-layer-measure/)).
- **Источник идей:** Hy-Memory (Tencent Hunyuan, Apache-2.0, `hy-memory==2.0.3`): слой опыта сцен `working`/`coding` и версионные атомарные факты L2.
- **Связано:** [ADR-004](ADR-004-change-dossiers.md) (паспорта изменений: `SecretRedactor`, захват по завершению хода), [ADR-024](ADR-024-spheres.md) (полки памяти), ADR-031 «Плагины» (хуки; пока в ветке `feat/plugins`), `docs/research/roadmap-team-zone.md` §③ (provenance, подтверждение autolearn).

## Контекст

Память персон у нас уже того же класса, что Hy-Memory в режиме `pro`. Есть autolearn после хода (`PersonaMemoryAutolearnService`, `TeamMemoryAutolearnService`) и сверка ADD/UPDATE/DELETE/NOOP в стиле Mem0 (`MemoryWriteResolver`). Есть дедупликация при близости ≥0,85, recall со свежестью и важностью (`MemoryScorerCore`) и суточная консолидация (`MemoryConsolidationCore`). Заменять её на Hy-Memory не нужно: это отдельный Python-сервис с ChromaDB рядом с Dify и миграция персон, сфер, заметок и паспортов ради того, что уже работает.

Чего у нас нет, а у Hy-Memory есть:

1. **Опыт задач.** Исполнители каждый раз открывают одни и те же грабли заново.
2. **История записи.** `UPDATE` резолвера, `memory_rethink` и merge консолидации перезаписывают текст, а `DELETE` и вытеснение удаляют запись бесследно. Ни откатить, ни объяснить, откуда взялась формулировка, нельзя.

Замер (подробности — в отчёте) показал:

| Что | Результат |
|---|---|
| Экономия вызовов: идеальный поиск / поиск по постановке / поиск по ошибке | 6,6% / **3,2%** / 3,3% |
| Доля экономии от граблей окружения и тестовой инфраструктуры | **91%** |
| Знание кода конкретной фичи | 11 вызовов на 20 задач |
| Цели с вредной записью (устарела, неверно обобщена, противоречит другой) | **7 из 20** |
| Самая дорогая грабля (T098, ~70 вызовов) | **уже была в CLAUDE.md** |

Вывод: слой опыта в форме Hy-Memory, то есть опыт каждой задачи с поиском по тексту задачи, у нас почти ничего не даёт и заметно вредит. Ценность есть в узкой части — граблях окружения, — и только если они проверены и приходят вовремя.

## Решения

### 1. Журнал изменений памяти вместо перезаписи (принять)

- **Один писатель на полку** пишет событие в `data/memory-changes/YYYY-MM.jsonl` при каждом разрушающем изменении: `UPDATE` и `DELETE` резолвера, `memory_rethink`, `memory_forget`, merge и drop консолидации, вытеснение по retention, `adopt` в сферу.

  ```
  { v: 1, ts, shelf: "persona:{id}"|"team:{project}"|"sphere:{id}", entryId,
    op: "update"|"delete"|"merge"|"drop"|"evict"|"adopt",
    before: { text, type, salience } | null, after: { text, type, salience } | null,
    actor: "agent"|"autolearn"|"resolver"|"consolidation"|"user", sessionId?, mergedFrom?: [entryId] }
  ```

- **Recall журнал не читает**, в Dify он не синхронизируется, модель записи (`PersonaMemoryEntry`, `TeamMemoryEntry`) не меняется.
- **Зачем:** provenance из roadmap ③-3.2 («откуда эта формулировка»), откат неудачного merge и разбор вредных записей. Замер показал, что они реальны: `E077` устарела после коммита `f3bd64489`, `E034` против `E041` — прямое противоречие.
- **Хранение:** 180 дней по имени файла, чистка — в существующей консолидации. В бэкап — по тем же правилам, что сторы памяти (проверить `BackupPaths` на шаге 1).
- **Сбой записи журнала** — `Debug` в лог, основная операция не падает.
- **Отклонено:** версии внутри записи, как L2 у Hy-Memory (неизменяемые факты с цепочкой версий). Это раздувает сторы, которые целиком живут в памяти процесса, ломает хеши диффового синка в Dify и требует миграции. Журнал даёт то же без изменения модели.

### 2. Слой опыта в форме Hy-Memory (отклонить)

Опыт каждой задачи с подтягиванием по тексту постановки не делаем. По замеру это 3,2% вызовов при вредной записи в каждой третьей цели. Медиана ранга полезной записи по постановке — 26-е место: «перенеси тесты Llm» не похоже на «как считать `--list-tests`».

### 3. Грабли проекта — пилот за флагом `executor-pitfalls`

Узкий слой: только грабли окружения, инструментов и тестовой инфраструктуры проекта, с проверкой повтором и подсказкой в момент ошибки.

- **Хранение — полка памяти команды проекта**, а не новое хранилище. В конец `TeamMemoryType` добавляется `Pitfall`, в конец `TeamMemorySource` — `AutoTask`: порядок enum менять нельзя. Аддитивные поля записи: `Confirmations`, `Disputes`, `SourceTaskIds`, `Commit` (HEAD на момент извлечения). Дедуп, резолвер, консолидация и синк в Dify — существующие из `MemoryShelf`.
- **Извлечение.** `TaskExecutionService.OnTaskCompleted` для задач исполнителей с `ClaudeResult=success` делает один вызов дешёвой модели (`ICheapTextRunner`) на выжимке транскрипта: вызовы инструментов, ошибки, реплики — как `digest.py` в замере. Промпт сужен до граблей окружения: «упало → что сработало», «как поднять, проверить, остановить», «ловушка инструмента». Знание кода фичи и итоги задачи сюда не идут: фактам есть место в паспортах ADR-004. Перед записью текст проходит `SecretRedactor`.
- **Проверка повтором вместо подтверждения человеком.** Новая грабля пишется кандидатом и в подсказки не попадает. Активной она становится, когда:
  - ту же граблю независимо извлекли из другой задачи (дедуп ≥0,85 → `Confirmations++`, нужно ≥2);
  - или её подтвердил человек в UI памяти команды.

  Кандидаты без подтверждения удаляются через 14 дней. Ручное подтверждение каждой записи не делаем: по замеру это ~1,6 записи на задачу, при ~100 закрытых задачах в день (октябрь, AI Home) вручную не разобрать.
- **Доставка — подсказка в момент ошибки.** Результат инструмента с ошибкой → поиск по активным граблям с текстом ошибки и предыдущим вызовом в качестве запроса → не больше 1 подсказки на ошибку и 5 на сессию, порог по score. По замеру на пороге 20 это ~4 подсказки на задачу, точность 19%. Подсказка короткая: «Похоже на известную граблю (2026-10-17, `abc1234`): … Не подтвердилось — `pitfall_dispute(id)`». Шов (PostToolUse-хук CLI или хук платформы из ADR-031) выбирается на шаге плана.
- **Постоянную вставку в начало сессии не делаем.** Самая дорогая грабля замера уже была в CLAUDE.md и не помогла. Ещё один постоянный блок — это токены в каждом ходе без доказанной пользы.
- **Обратная связь.** MCP `pitfall_dispute(id, why)` → `Disputes++`. При `Disputes ≥ Confirmations` запись снимается из подсказок и уходит на разбор. Всё изменение текста идёт через журнал из решения 1.
- **Лимиты:** не больше 40 активных граблей на проект, вытеснение — существующим retention-скорингом.

## Пилот

- **Включение:** флаг `executor-pitfalls` на проекте AI Home. Половина задач исполнителей по хешу id получает подсказки, вторая половина — контроль. Срок — 2 недели или 150 задач в каждой группе.
- **Метрики:**
  1. вызовов инструментов на задачу;
  2. ошибок инструментов на задачу;
  3. судейская разметка 20 случайных задач с подсказками по методике замера: сколько показанных граблей исполнитель всё равно повторил и сколько подсказок увели не туда.
- **Оставить**, если выполнено всё сразу: вызовов меньше хотя бы на 3% **или** ошибок меньше хотя бы на 15%; вредных подсказок, которым исполнитель последовал, не больше 1 на 20 задач.
- **Свернуть**, если нет: флаг выключается, полка `Pitfall` остаётся данными для разбора, журнал из решения 1 остаётся в любом случае.

## Отклонено

| Вариант | Почему нет |
|---|---|
| Заменить нашу память на Hy-Memory | Тот же класс системы; миграция персон, сфер, заметок и паспортов; второй стек хранения рядом с Dify |
| Опыт каждой задачи с поиском по постановке (сцены `working`/`coding`) | 3,2% экономии, вредная запись в 7 из 20 целей |
| Индукция схем, System 2 (`evolve()`, L6) | У персоны лимит 150 записей. На таком объёме дешёвая модель скорее выдумает абстракцию, чем найдёт её. Пользы не измеряли и не видно, где она возьмётся |
| Цепочка диффов кода (`coding`, `chain_store`) | Закоммиченное уже покрывают паспорта ADR-004. Откаченные версии внутри сессии в замере ни разу не понадобились |
| Намерения со сроком (L7) | Покрываются задачами с напоминаниями |
| Модель Hy-Memory-30B-A3B для autolearn | ~60 ГБ в BF16. Обе 3090 заняты прод-моделью, вторую модель на 30B ставить некуда |
| Дописать грабли в CLAUDE.md | Самая дорогая грабля замера там уже была. 525 строк постоянного контекста её не предотвратили |
| Постоянный блок граблей в начале сессии исполнителя | Тот же довод плюс токены в каждом ходе. Можно вернуться, если пилот реактивной доставки провалится по полноте |

## Последствия

- **Решение 1:** небольшая правка в местах записи `MemoryShelf`, `PersonaMemoryService`, `MemoryWriteResolver`, `MemoryConsolidationCore` плюс тест на каждую операцию. Модель данных не меняется, миграции нет.
- **Решение 3** добавляет один вызов дешёвой модели на завершённую задачу исполнителя: выжимка ~10–15 тыс. токенов, до ~100 задач в день. На локальной модели — бесплатно, но это очередь GPU.
- **Риски пилота:**
  - **устаревание граблей** — обходится полями `Commit`, «дата в подсказке», `pitfall_dispute` и журналом;
  - **шум подсказок** — 81% подсказок на пороге 20 по замеру мимо; лечится лимитами на сессию и порогом;
  - **малая выборка замера** — 20 целей, окно 30 часов, плотные серии, то есть скорее верхняя граница пользы. Ответ на это — пилот с контролем, а не сразу полный объём.

## План шагов

1. Журнал изменений памяти: формат, писатель, точки записи, тесты, чистка (решение 1).
2. Полка `Pitfall`: аддитивные поля, enum в конец, правила активации и устаревания, тесты.
3. Извлечение на `OnTaskCompleted`: выжимка транскрипта, промпт, `SecretRedactor`, флаг `executor-pitfalls`.
4. Доставка по ошибке: выбор шва, поиск, лимиты, `pitfall_dispute`.
5. Пилот 2 недели и разметка по методике замера, затем решение «оставить или свернуть» в этот ADR.
