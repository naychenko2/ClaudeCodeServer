## Зачем

Корневой `CLAUDE.md` грузится в контекст КАЖДОЙ сессии — это не документация, а постоянная
плата токенами. Файл растёт сам собой (каждая фича дописывает абзац), а усыхает только
руками. Нужна кнопка: проверить гигиену карты и показать человеку, что именно раздулось,
что протухло и что можно свернуть в ссылку.

Замер на нашем репозитории (21.09.2026, ветка master):

| Показатель | Значение |
|---|---|
| Корневой `CLAUDE.md` | 974 строки / 100 248 байт (~33 000 токенов) |
| Ориентир Anthropic | ≤200 строк |
| Секций `##` | 28, из них длиннее 40 строк — 7 |
| Три крупнейшие секции | «Внутренние подсистемы» 257, «LLM-провайдеры» 110, «Реализовано» 106 — половина файла |
| Ссылок на пути | 54 (только локальные пути; всех markdown-ссылок в файле 67), из них **мёртвых 2** |
| Вложенных `CLAUDE.md` | 3 (Video, Desktop, Telemetry) |

Мёртвые ссылки на сегодня: `backend/ClaudeHomeServer/Services/Deploy/CLAUDE.md` (файла нет) и
`backend/ClaudeHomeServer/Models/FeatureFlag.cs` (переехал в `ClaudeHomeServer.Core/Models/`).
Обе воспроизведены прототипом сканера — фича ловит реальные дефекты в первый же прогон.

## Принципы

1. **Модель не читает карту целиком.** Сначала детерминированный сканер, модели уходит его
   отчёт. Факт «существует ли путь» модель обязана получать, а не угадывать.
2. **Автоправок нет.** Запись в `CLAUDE.md` — только по явному утверждению человека: каждое
   предложение отмечается отдельно, отмеченные применяются вместе (Р10.1). Файл под git, его
   параллельно правят исполнители задач в общем дереве.
3. **Сканер самоценен.** Фаза 1 проверяема без модели и без UI; модель и экран строятся поверх
   готового отчёта.
4. **Факт важнее формулировки.** Модель не ответила или отдала битый JSON — показываем факты
   сканера без формулировок, а не пустой экран и не выдуманные предложения. Где факт и
   суждение модели стоят рядом, первым идёт факт.
5. **Пороги — настройка, а не константа.** Разные проекты живут с разной картой.

## Р1. Двухфазность и её доказательство

**Фаза 1 — сканер** (детерминированный, без модели): размер, мёртвые ссылки, длинные секции,
секции со ссылками на `docs/*`, вложенные карты.
**Фаза 2 — one-shot модели** по отчёту: формулировки предложений.

Допущение «отчёт влезет в окно» проверено прототипом на живом файле: **100 248 байт входа →
2 364 символа отчёта (~790 токенов)**, сжатие в 40 раз. Профиль `CheapProfile.Large` — это
`NumCtx: 16384` (`LocalActionCatalog.cs:141-143`), то есть запас двадцатикратный даже для карты
вчетверо крупнее нашей. Сам файл (~33 000 токенов) в это окно не влезает — двухфазность не
украшение, а единственный способ уложиться.

## Р2. Вертикаль и файл сканера

**Вертикаль `Docs`**, новый файл `backend/ClaudeHomeServer.Docs/ProjectMapScanner.cs`,
namespace `ClaudeHomeServer.Services.Docs`.

Почему `Docs`, а не `ProjectServices`:

- в `DocsIndexService` уже живут `LinkRegex()`, `HeadingRegex()`, `FenceRegex()`
  (`DocsIndexService.cs:2065` и соседние) — `internal static partial`, то есть доступны **только
  внутри сборки `ClaudeHomeServer.Docs`**. Сканер переиспользует их, а не заводит свой третий
  набор регулярок разбора markdown;
- `Docs` уже зовёт модель через Core-шов: `DocumentAiService.cs:36,55,69,80` —
  `cheap.RunAsync(Llm.LocalActionCatalog.DocFormat, …)`. Прецедент «вертикаль Docs → `ICheapTextRunner`»
  существует, новых швов не требуется;
- `ProjectServices` — про дев-серверы и прокси `/preview/**`, разбор markdown там чужероден.

**Сторож границ не трогаем.** Запись `Docs` в `Boundaries` уже есть
(`SubsystemBoundaryTests.cs:891-906`), новой не заводим — дубль записи сторожа не ловят ни один
(известная грабля, CLAUDE.md «Внутренние подсистемы»). Ссылка на Core легальна: допуск идёт по
**имени сборки** (`IsCoreAssembly`, комментарий на `SubsystemBoundaryTests.cs:144-147`), а не по
namespace, — «сборка `ClaudeHomeServer.Core` — спинка целиком».

Регистрация сервиса — `Program.cs` рядом с остальными сервисами `Docs` (`:477-483`): у вертикали
`Docs` нет `IAppSubsystem`, её сервисы регистрируются вручную. Заводить `DocsSubsystem` в рамках
этой задачи не надо — это отдельная уборка со своей ценой.

## Р2а. Сканер — расширение индекса доков, а не новый парсер

Уточнение Андрея 21.09 после чтения кода, проверено замерами (ниже). Разбор markdown в
`DocsIndexService` уже доведён до связного вида: заголовки со слагами, исходящие ссылки
(`OutLinks`), обратные (`Backlinks`), кеш по корню и области. Сканеру остаётся добрать
недостающее, а не строить второй разбор.

**Причина наших мёртвых ссылок найдена и она в индексе** — `DocsIndexService.cs:911`:

```csharp
var kind = byPath.ContainsKey(target) ? DocLinkKind.Doc : DocLinkKind.Repo;
```

`byPath` — корпус доков. Всё, чего в нём нет (любой `.cs`, `.ts`, файл вне области), молча
получает вид `Repo`, и **существование на диске не проверяется вообще**. Поэтому ссылка на
переехавший `FeatureFlag.cs` выглядит здоровой.

**Замер, который меняет вес этой находки.** Прогнал проверку существования по всему нынешнему
корпусу (`docs/**` + `README.md`, резолв — копия `ResolveRelative`, содержимое ```-блоков
пропущено): **754 ссылки, 165 не существуют на диске, из них 161 — настоящие протухшие**.
Шума ровно 4. Массовая причина — Этап 5: документы ссылаются на `backend/ClaudeHomeServer/Services/…`,
откуда код уехал в отдельные `.csproj` (`ADR-002`, `ADR-004`, `ADR-009`, `ADR-012`, `ADR-013`,
`ADR-015` и другие).

Отсюда: **проверка существования `Repo`-ссылок — не побочный бонус уборки карты, а отдельная
находка на 161 реальный дефект корпуса.** Она самоценна, проверяема без модели и без UI и
идёт первым шагом.

Три поправки к её включению, каждая из замера:

1. **Не новое значение `DocLinkKind`, а новое поле в `DocLink`.** Enum живёт в Core
   (`Models/DocsIndex.cs:11`) и едет во фронт строкой; `DocsPanel.tsx:1453,1466` ветвится по
   `kind === 'repo'` и открывает файл. Четвёртое значение фронт не знает — клик молча
   перестанет работать. Булево поле (`Missing`) старое поведение не трогает.
2. **`IsExternal` (`:2153`) знает только `http`/`https`/`mailto`/`//`.** `javascript:` и
   `data:text/html;base64,…` — примеры из ADR-005 про SSRF — попадут в «мёртвые файлы».
   Фильтр схем чинится до включения проверки, иначе два ложных с первого прогона.
3. **161 плашка разом — это продуктовый вопрос, а не технический.** Показывать красноту в
   каждом втором документе панели нельзя; находки идут отдельным отчётом-аудитом, как в нашем
   экране уборки. Порядок разбора — решение постановщика.
4. **`Missing` нельзя кэшировать вместе с корпусом — иначе плашка врёт.** Отпечаток кеша
   считается по файлам ОБЛАСТИ (`Fingerprint`, `DocsIndexService.cs:810-828`: путь + mtime +
   размер каждого файла корпуса, то есть `docs/**` и `README.md`), а `Missing` зависит от
   наличия файлов КОДА (`RepoTargetExists`, `:2171`). Переехал `.cs` — ни один документ не
   изменился, отпечаток тот же, корпус отдаётся из кеша: панель показывает старое состояние.
   Симметрично и обратное, а оно хуже: человек починил переехавший файл, а плашка «ссылка
   мертва» висит до следующей правки любого документа или до перезапуска — фича выглядит
   сломанной именно в момент, когда сработала.

   Решение: **`Missing` считается вне кеша, при отдаче**, а не запекается в `DocLink` при
   сборке корпуса. Проверка — `File.Exists` по `Repo`-ссылкам документа: у страницы их
   единицы, стоит микросекунды и не требует ни TTL, ни кнопки «Проверить заново» (ручная
   перепроверка — это способ жить с неверным кешем, а не чинить его). Для отчёта-аудита по
   всему корпусу (754 ссылки) проход разовый, по запросу, и тоже вне кеша.

## Р3. Предварительная уборка: `ClaudeMdExpander` → Core

**Это единственное место, где задача задевает чужой код, и без него разрез роняет сторожа.**

Карта едет в контекст не как файл, а с раскрытыми `@`-импортами (`@rules/git.md`). В продукте это
уже реализовано: `ClaudeMdExpander.Read(path)` — глубина 5, циклы, потолок 256 КБ. Сканер обязан
мерить РАСКРЫТЫЙ размер: проект с `CLAUDE.md` в 20 строк и пятью `@`-импортами платит за всё
дерево, и без раскрытия отчёт соврёт в пользу «всё хорошо».

Сейчас файл лежит в `backend/ClaudeHomeServer.Llm/Claude/ClaudeMdExpander.cs` — вызов из `Docs`
был бы «вертикаль → вертикаль», сторож поймает.

Решение — **перенос в спину по буквальному прецеденту `SafePath`** (CLAUDE.md: «Спина лечится
переносом в Core с сохранением namespace, call-site'ы не меняются»):

`backend/ClaudeHomeServer.Llm/Claude/ClaudeMdExpander.cs` → `backend/ClaudeHomeServer.Core/Services/Llm/Claude/ClaudeMdExpander.cs`

Перенос дешёвый и проверенный:

- namespace `ClaudeHomeServer.Services.Llm.Claude` **не меняется** — в Core уже есть каталог
  `Services/Llm/Claude/` с `TranscriptProbe.cs` того же namespace;
- у класса ноль зависимостей от `Llm`: только `System.Text`, `File`, `Path`;
- call-site'ов два: `ClaudeSession.cs:4378` и `ClaudeMdExpanderTests.cs` — **ни один не правится**.

Волна 4 добавит в этот же класс перегрузку раскрытия **от уже прочитанного текста** —
`apply` держит в руках единственный снимок файла и повторно читать его с диска не имеет права
(Р10а). Существующий `Expand(path)` при этом становится её тонкой обёрткой: две реализации
раскрытия — это два разных `baseSha` и вечный 409 (разбор в Р8).

**Пределы раскрытия — часть контракта отчёта, а не деталь реализации.** У `ClaudeMdExpander`
три исхода, при которых раскрытый размер перестаёт быть правдой, и каждый обязан доезжать до
человека отдельным признаком, а не молча:

| Исход в раскрывателе | Что значит | В отчёте (имена — как в коде волны 1) |
|---|---|---|
| `MaxTotalChars` = 256 КБ исчерпан (`:19, :68`) | хвост дерева импортов в контекст не поехал | `expansionTruncated: true` — цифра бюджета занижена, «всё хорошо» может быть ложью |
| `MaxDepth` = 5 (`:17, :81`) | глубже импорты не раскрыты | `importDepthExceeded: true` |
| Целевого файла импорта нет | импорт мёртв — CLI подставит комментарий «импорт не прочитан» | находки `deadImports[]` + счётчик `deadImportCount`, рядом с мёртвыми ссылками |

Оба признака усечения — **булевы, а не счётчики**: точное число неразвёрнутых импортов
раскрыватель не считает, а человеку хватает «отчёт неполон, и вот почему». Имена полей здесь и
в Р8 сверены с реализацией волны 1 (`MapHygieneReport`) — расхождение плана с кодом стоило бы
исполнителям волн 2 и 3 по циклу «написал — не собралось».

Мёртвый `@`-импорт — это **та же мёртвая ссылка, только дороже**: битая ссылка в тексте стоит
человеку одного клика в никуда, а битый импорт означает, что правило, которое автор считал
частью карты, в контекст не едет вовсе. Резолв — тот же, что у самого раскрывателя
(`ResolveInside`: `@~/…`, абсолютные и уводящие выше папки остаются строкой как есть и
находкой не считаются — CLI их тоже не раскрывает).

## Р4. Что считается картой проекта

Не один файл. Источник правды — то, что реально собирает продукт (`ClaudeSession.cs:4363-4366`).
**Но читаем мы шире, чем пишем**, и это разные списки:

| Файл | Входит в отчёт | Правится кнопкой |
|---|---|---|
| `<корень>/CLAUDE.md` | да, основной предмет | **да, и только он** |
| `<корень>/.claude/CLAUDE.md` | да, справочной строкой | нет |
| `@`-импорты корневой карты (`rules/*.md` и т.п.) | да, в раскрытом размере и как `deadImport` | нет |
| `<профиль CLI>/CLAUDE.md` | **нет** — это личный файл пользователя, не проекта | нет |
| Вложенные `CLAUDE.md` в подпапках | да, но **справочным списком**, а не находкой | нет |

**Предмет правки — ровно `<корень>/CLAUDE.md`** (решение Андрея по блокеру 1 ревью, 21.09).
Причина не в трудоёмкости, а в форме контракта: `apply { baseSha, ids[] }` адреса файла не
несёт, и предложение из второй карты применять некуда. Достраивать адресацию до списка файлов
отвергнуто — весь UI, тексты и Р10 написаны под один файл, а `.claude/CLAUDE.md` у наших
проектов не встречается вовсе.

Отсюда **инвариант записи, обязательный к соблюдению исполнителем волны 4:** предложение с
непустым `apply` может родиться только из находки в корневой карте. Находки из
`.claude/CLAUDE.md`, вложенных карт и импортов показываются, но `apply` у них `null` всегда —
и это не «пока не сделано», а решение. Сканер уже устроен так же: в отчёте `Path` и `BaseSha`
единственные, `SecondMap` и `NestedMaps` — справочные `MapFileRef` без возможности что-либо
адресовать. Механизм, а не договорённость: у находки не из корневой карты `apply` не
заполняется в принципе, потому что заполнять его нечем — адреса файла в контракте нет.

**Вложенная карта — не дефект, а правильный приём** (возражение Майи, принято). Наши три
вложенных файла (Video, Desktop, Telemetry) подхватываются по месту работы и есть ровно то
прогрессивное раскрытие, к которому уборка и ведёт. Плашка серьёзности рядом с ними отправит
человека чинить здоровое. В отчёте они идут отдельным блоком без плашек и без действий, с
оговоркой, что в общий счёт контекста не входят.

Карты нет вовсе — это не ошибка, а штатный ответ «карты нет» (у большинства проектов
пользователя её и не будет).

`docs/CLAUDE-local.md` (у нас — 14,7 КБ) в счёт **не входит**: он едет только при `BareMode`
как `SystemPromptFile` и обычные ходы за него не платят. Упомянуть его в отчёте стоит одной
справочной строкой — он показывает, что компактная карта того же проекта уже написана и
цель достижима.

**Обход дерева обязан исключать** `.git`, `node_modules`, `bin`, `obj` и `.claude/worktrees`.
Проверено на живом репозитории: наивный `find` нашёл 8 файлов `CLAUDE.md` вместо 4 — половина
это копии в рабочих деревьях, и в отчёте они были бы чистым мусором.

## Р5. Правило резолва ссылок

Проверяются **только markdown-ссылки** вида `[текст](путь)`. Правило резолва — по фактическому
устройству наших карт:

1. Внешние (`http://`, `https://`, `mailto:`) — пропускаем, в сеть не ходим.
2. Абсолютные (`/…`, `C:\…`) — помечаем «не проверяли», **в `SafePath.Join` не отдаём**:
   у примитива задокументировано, что на Linux `/a/b` станет относительным и приклеится к
   корню, то есть проверка «ссылка наружу» молча исчезнет (`SafePath.cs:4-9`).
3. Относительные — резолвим **от каталога файла** (так делает `ResolveRelative` индекса,
   `:2161`, и так же поступают GitHub и панель «Документация»). Если от каталога не нашлось,
   а от корня проекта нашлось — это **не «живая» и не «мёртвая», а третий, отдельный исход:
   «резолвится только от корня проекта»**.

   **Правка прежней редакции плана.** Раньше здесь был тихий фолбэк «не нашлось от каталога —
   ищем от корня, считаем живой». Замер показал, что он прячет настоящий дефект: во всех трёх
   вложенных картах (Video, Desktop, Telemetry) ссылки написаны от корня репозитория, и по
   стандарту markdown они битые — ни на GitHub, ни в панели по ним не перейти. Рабочими они
   выглядят только для агента, у которого рабочий каталог и есть корень. Тихо объявив их
   живыми, мы бы узаконили 9 неработающих ссылок; объявив мёртвыми — соврали бы агенту.
   Честно — показать как есть и оставить решение человеку.

   Цифра, на которой это проверено: добавление четырёх карт к корпусу даёт **+11 находок, из
   них по-настоящему мёртвых только 2** (наши, в корневом `CLAUDE.md`), а остальные 9 —
   ровно этот третий случай (Desktop 3, Telemetry 5, Video 1).
4. Выход за корень (`../..`) — ловим `UnauthorizedAccessException` от `SafePath.Join` и
   помечаем «ссылка за пределы проекта». Сканер от этого не падает.
5. **Содержимое кодовых блоков (``` и ~~~) не разбирается вовсе** — ни ссылки, ни заголовки.
   Найдено самопроверкой: прогон прототипа по ЭТОМУ плану дал две «мёртвые ссылки», и обе
   оказались иллюстрациями внутри примеров — шаблон `[текст](путь)` и намеренно устаревший
   путь в примере JSON. В документации про документацию такие примеры — норма, и сканер,
   который на них ругается, обесценивает себя на первом же прогоне. Состояние «внутри забора»
   у разбора заголовков уже есть — то же состояние обязано гасить и разбор ссылок.

**Голые пути в бэктиках (`` `lib/featureFlags.ts` ``) на существование НЕ проверяем.** Замер:
из 16 таких путей в нашей карте буквально существуют 2. Остальные верны, но сокращены
(`lib/featureFlags.ts` = `frontend/src/lib/featureFlags.ts`), либо рантайм-файлы (`data/*.json`),
либо машинно-локальные (`appsettings.Local.json` в `.gitignore`). Проверка дала бы 14 ложных
тревог из 16 — это шум, который обесценит настоящие находки.

## Р7. Место в каталоге действий

Одна строка в `LocalActionCatalog.Builtin` плюс константа ключа
(`backend/ClaudeHomeServer.Core/Services/Llm/LocalActionCatalog.cs`), по образцу соседа
`project-icon` (`:279-280`):

```csharp
new(ProjectMapHygiene, "Уборка карты проекта", "Проекты", CheapProfile.Large,
    DefaultLocal: false, Tier: ModelTier.Medium),
```

Группа «Проекты» уже существует. `DefaultLocal: false` — предложения по отчёту это связный
текст на русском, качество формулировок тут и есть продукт. `Agentic` не ставим: агентная
сессия не нужна, все факты приносит сканер. Отдельный `CloudTimeoutMs` не задаём — хватает
профильного (300 с у `Large`).

Место автоматически появится в админской вкладке «Применение» и в
`PUT /api/admin/local-actions/{key}` — они рендерятся из `LocalActionCatalog.All`.

**Потолок вывода — ограничение, которое ломает фичу на локальном исполнителе, если его не
учесть в ФОРМЕ ответа.** Цифры проверены по коду (`LocalActionCatalog.cs:141-143`):

| Маршрут | Потолок вывода | Хватает ли |
|---|---|---|
| Облако (`CloudNumPredict` у `Large`) | 8192 токена | да, с запасом |
| Локальная модель (`NumPredict` у `Large`) | **1024 токена** | нет, если модель диктует весь объект |

Место `DefaultLocal: false`, то есть по умолчанию уходит в облако — но исполнителя назначает
админ, и «Локальная» здесь допустимый выбор. На нём 15 предложений с полями `fact` +
`modelSays` + `anchor` заведомо выходят за килотокен: ответ обрывается на полуслове, разбор
JSON возвращает null, человек видит тихий фолбэк «факты без формулировок» — симптом,
неотличимый от «модель не настроена» (прод 2026-08-05 дал ровно эту картину на планировщике).

**Настройкой это не лечится:** `NumPredict` переопределяется только для профиля целиком
(`Ollama:Profiles:large:NumPredict`), то есть для всех мест `Large` разом, а у `LocalAction`
пер-местного потолка вывода нет — единственное пер-местное поле там `CloudTimeoutMs`
(`:39-41`). Поднимать потолок всему профилю ради одного места — плата памятью Ollama на
каждом вызове любого соседа.

Лечится формой ответа (Р8): модель возвращает только `{ id, severity, modelSays }`, `modelSays`
ограничен 120 символами, число предложений — `MaxSuggestions: 8`. Оценка вывода:
8 × ~90 токенов + обвязка ≈ 770 токенов, запас к потолку локали ~25 %. Всё остальное
(`fact`, `anchor`, `savingLines`, `apply`) сервер берёт из собственного отчёта — модель этих
полей не диктует, и не только ради экономии токенов (Р8а).

## Р8. Контракт: факты сканера и предложения модели

Два ответа, а не один: факты приходят мгновенно, модель — десятки секунд. Разделение позволяет
показать половину отчёта сразу (требование Киры и Майи независимо друг от друга).

**Ответ сканера** (форма проверена прототипом на живом файле):

```jsonc
{
  "path": "CLAUDE.md", "exists": true,
  "baseSha": "…",              // хеш РАСКРЫТОГО состава карты; едет обратно в review и apply
  "lines": 974, "bytes": 100248, "approxTokens": 33416,
  "expandedLines": 974, "importCount": 0,   // с раскрытыми @-импортами (Р3)
  "expansionTruncated": false, "importDepthExceeded": false,  // пределы раскрытия (Р3)
  "deadImports": [], "deadImportCount": 0,  // @-импорт, целевого файла нет
  "budget": { "recommendedLines": 200, "overBudget": true },
  "sections": [                // только кандидаты (> порога), не весь файл
    { "title": "Внутренние подсистемы (Services/Composition)", "startLine": 268,
      "lines": 257, "docsRefs": 6, "firstLine": "Внутренние границы продукта — …" }
  ],
  "deadLinks": [
    { "section": "Фич-флаги (feature toggles)", "line": 845,
      "target": "backend/ClaudeHomeServer/Models/FeatureFlag.cs", "reason": "notFound",
      "candidates": ["backend/ClaudeHomeServer.Core/Models/FeatureFlag.cs"] }
  ],
  "nestedMaps": [ { "path": "backend/ClaudeHomeServer.Video/CLAUDE.md", "lines": 41 } ],
  "skipped": [ { "target": "C:\\Users\\…", "reason": "absolute" } ],
  "suggestions": [ /* см. ниже: те же поля, что в ответе review, с modelSays: null */ ]
}
```

(Имена и типы полей — по фактической реализации волны 1, `ProjectMapScanner.MapHygieneReport`:
там же живут `expansionTruncated` / `importDepthExceeded` — **булевы**, а не счётчики, — и
пара «полный счётчик + усечённый список» у каждой группы находок, плюс общий `truncated`.
Пример выше сокращён; источник правды — код, а не этот блок.)

**`suggestions[]` отдаёт сам `scan`, и у каждого есть `id`.** Это прямое следствие Р8а: `apply`
адресуется по `id`, значит `id` обязан существовать ДО обращения к модели и приезжать человеку
вместе с фактами. Фронт ничего не синтезирует из `deadLinks[]` сам: списки находок в отчёте
остаются фактурой (и для модели, и для диагностики), а список действий — это `suggestions[]`.

**`apply` заполняется ровно у одного вида находки — `dead-link`.** У остальных трёх он `null`
по определению, а не «пока не реализован»:

| `kind` | `apply` | Почему |
|---|---|---|
| `dead-link` | патч, если выполнены оба условия формулы из Р10а | единственная однозначно механическая правка |
| `dead-import` | `null` всегда | Р4: `@`-импорты кнопкой не правятся |
| `root-relative` | `null` всегда | Р5.3 решил показать как есть: исходов два (переписать путь или узаконить), выбор за человеком — механической правки тут нет |
| `long-section` | `null` всегда | Р10.2: вынос секции — содержательная работа |

**Источник якорной строки для `id` — по виду находки, без исключений:**

| `kind` | Якорная строка в формуле `id` |
|---|---|
| `dead-link`, `root-relative` | `anchorText` — markdown-ссылка целиком |
| `dead-import` | строка импорта целиком (`@rules/git.md`) |
| `long-section` | текст заголовка секции, нормализованный так же, как `anchorText` |

Иначе формула `id` = SHA-256(`kind` + якорная строка) для секций просто не вычисляется, и
исполнитель скатится к порядковому номеру — ровно к тому, что Р8а.3 запрещает.

**`baseSha` считается по раскрытому составу карты, а не по одному файлу.** Формула — одна и
без вариантов: **SHA-256 от раскрытого текста карты** (а не от содержимого самого файла).
Список импортированных путей сканер целиком не знает — раскрыватель
отдаёт склеенный текст, и вложенные импорты второго уровня в нём уже растворены; хеш
раскрытого текста покрывает их все и меняется при правке любого. Цена решения одна и она
приемлема: правка формата служебных маркеров раскрывателя (`<!-- ↓ … -->`) разом протухает
все `baseSha` — после такого деплоя первый `apply` вернёт 409, человек нажмёт «Проверить
заново». Важная оговорка: раскрытие для хеша делается **всегда**, в том числе когда импортов
ноль — иначе `baseSha` считается по двум разным правилам (файл против раскрытого текста), и у
карты, в которую импорт добавили, хеш скакнёт без единой содержательной правки. Подсчёт
`expandedLines` при этом остаётся как есть (без импортов — по самому файлу): там лишний проход
добавлял бы строку от нормализации концовки и отчёт показывал бы `expandedLines > lines`.
Причина всего этого — прямая: правка `rules/git.md` не меняет ни байта
в `CLAUDE.md`, и при хеше по одному файлу обе опирающиеся на `baseSha` проверки становятся
ложью именно в том сценарии, ради которого раскрытие и вводится — «файл не изменился с
момента скана» пропустит изменившуюся карту, а кеш ответа модели отдаст формулировки по
устаревшему составу. Текущая реализация сканера считает `Sha256(main.Text)` — это правится
в волне 1, до того как на `baseSha` встанет запись.

**Обе стороны обязаны раскрывать карту ОДНИМ кодом, и это проверяется тестом.** `scan` держит
в руках путь, `apply` — уже прочитанный текст (Р10а, единственный снимок), поэтому волна 4
добавляет в `ClaudeMdExpander` перегрузку от текста: `Expand(text, baseDir)`, а нынешний
`Expand(path)` становится её тонкой обёрткой (`File.ReadAllText` + вызов). Требование —
побайтовое равенство `Expand(File.ReadAllText(p), dir).Text == Expand(p).Text`, с тестом,
включающим файл БЕЗ финального перевода строки и файл с CRLF.

Почему это не педантизм: раскрыватель не тождественен даже при нуле импортов — он разбирает
текст на строки и склеивает их обратно через `\n`, то есть файл без финального перевода строки
его приобретает. Малейшее расхождение двух реализаций даёт 409 на **каждом** `apply`, а человек
видит штатную плашку «файл изменился после проверки» — неотличимую от настоящей гонки. Фича
выглядела бы рабочей и не применяла бы ничего никогда.

Адресация записи при этом **остаётся по корневому файлу** (Р4): хеш отвечает на вопрос «то же
ли я читал», путь — на вопрос «куда писать», и смешивать их не надо. Практическое следствие,
которое обязан знать исполнитель волны 4: правка импортированного `rules/*.md` посторонним
процессом даёт `409` на `apply`, хотя сама карта не менялась. Это осознанно: отказ здесь
дешевле записи по устаревшей картине, а человеку показывается штатная плашка «файл изменился
после проверки · Проверить заново» (состояние уже заложено в раскладку).

`skipped[]` в ответе остаётся (он дешёвый и полезен в диагностике), но **в UI не выводится**:
«не проверяли» — не находка и не действие, а строка, которую человек не может ни починить, ни
осмыслить. Фронту волны 3 его не показывать.

**Кто какие предложения порождает** — важное следствие двухфазности: механические предложения
(мёртвая ссылка, у которой сканер нашёл ровно одного кандидата) формирует **сканер** и отдаёт
прямо в ответе `scan` — модель для них не нужна вовсе. Модель **не добавляет предложений
вообще**: она пишет суждение поверх тех фактов, что уже нашёл сканер, и у фактов вида
`long-section` `apply` всегда `null`. Отсюда и раскладка экрана:
группа «Правки в один клик» рисуется сразу, а группа «Работа для чата» догружается.
Практическое следствие: **при неработающей модели фича остаётся полезной** — ровно те две
мёртвые ссылки, что есть у нас сегодня, чинятся без единого обращения к LLM.

**Ответ модели — три поля и больше ничего.** Модель получает пронумерованные факты сканера
(`id` каждого) и возвращает суждение по ним:

```jsonc
{
  "modelNote": null,           // причина неполноты человеческим текстом, не молчание
  "suggestions": [{
    "id": "a1b2c3d4",                       // id ФАКТА сканера, не выдуманный
    "severity": "high | medium | low",      // ровно три градации
    "modelSays": "Похоже на пересказ ADR-014 — свернуть в ссылку"   // ≤ 120 символов
  }]
}
```

**Предложение, которое видит человек,** сервер собирает сам, сшивая суждение модели с фактом
сканера по `id`:

```jsonc
{
  "baseSha": "…",              // подставляет СЕРВЕР из свежего скана, не модель
  "modelNote": null,           // заполняет СЕРВЕР при отказе модели, не модель
  "suggestions": [{
    "id": "a1b2c3d4",
    "severity": "medium",                   // из ответа модели, иначе дефолт по kind
    "kind": "dead-link | dead-import | root-relative | long-section",  // из факта сканера
    "fact": "257 строк, внутри ссылка на docs/adr/ADR-014-internal-subsystems.md",
    "modelSays": "Похоже на пересказ ADR-014 — свернуть в ссылку",
    "anchor": { "line": 268, "heading": "Внутренние подсистемы (Services/Composition)" },
    "savingLines": 257,
    "apply": {                              // null ⇒ кнопки нет вовсе
      "before": "[FeatureFlag.cs](backend/ClaudeHomeServer/Models/FeatureFlag.cs)",
      "after":  "[FeatureFlag.cs](backend/ClaudeHomeServer.Core/Models/FeatureFlag.cs)",
      // якорь замены — текст, не номер строки; тождественно равен before (Р10а)
      "anchorText": "[FeatureFlag.cs](backend/ClaudeHomeServer/Models/FeatureFlag.cs)"
    }
  }]
}
```

Решения формы и почему именно так:

- **`firstLine`, а не тело секции.** Модели уходят заголовки и первые строки — этого хватает,
  чтобы узнать «секция пересказывает ADR-014», и только это удерживает отчёт в 790 токенах.
- **`docsRefs`** — число живых ссылок на `docs/*` внутри секции: сильный признак пересказа
  существующего документа (у трёх наших крупнейших секций он 6–8).
- **`fact` и `modelSays` — РАЗНЫЕ поля, и это главное решение контракта.** Модель не читала
  карту целиком, значит её суждение — догадка по метаданным. Факт сканера показывается
  основным текстом, фраза модели — вторичной. Поменять местами — человек снесёт живой раздел,
  поверив красивой фразе (возражение Майи, принято).
- **`apply: null` вместо отсутствия ключа.** Применимость определяется **наличием готового
  патча, а не типом находки**: мёртвая ссылка чинится кнопкой только если сканер нашёл ровно
  один файл с тем же именем; ноль или два кандидата — решение человека. Без этого поля фронт
  начнёт угадывать по `kind`, и половина кнопок «Применить» окажется ложью (возражение Майи,
  подтверждено требованием Киры «`apply: null`, чтобы не гадать по наличию ключа»).
- **`severity` — ровно три значения:** у `ui/Badge` три подходящих тона
  (`danger`/`warning`/`neutral`), четвёртая градация потребовала бы нового цвета в обе темы.
- **`before`/`after`, а не unified diff.** Проверено: на бэкенде генератора unified diff нет и
  пакета (`DiffPlex` и т.п.) в `.csproj` нет — весь дифф в продукте приходит от git
  (`/git/diff`, `/files/diff`), а правку нужно показать ДО записи, когда git её ещё не видит.
  Писать LCS-алгоритм ради показа замены одной ссылки несоразмерно; механическая правка по
  конструкции точечная. Полный дифф после применения доступен штатно — в панели «Изменения».
- **`anchorText`.** Применение идёт по якорю-тексту, а не по номеру строки: между проверкой и
  применением файл могли подвинуть.
- **`modelNote` заполняет СЕРВЕР, а не модель** (правка редакции 3). Смысл поля — показать
  настоящую причину отказа вместо глухого «не удалось»: по глухому человек не починит «модель
  для разбора не настроена». Но основной сценарий отказа — тот, где ответа модели нет вовсе
  (не настроена, таймаут, битый JSON), и достать оттуда текст невозможно. Поэтому источник
  один: сервер пишет `modelNote` из класса ошибки, при успешном разборе оно `null`, а в схеме
  разбора ответа модели этого поля нет (иначе модель могла бы подсунуть свой текст вместо
  диагноза — см. Р8а).
- **`kind` — ровно четыре значения, все из фактов сканера:** `dead-link`, `dead-import`,
  `root-relative`, `long-section`. Прежние `duplicate` и `other` вычеркнуты (редакция 3): они
  были бы суждением модели, а `kind` берётся из факта (Р8а.1) — и «секция пересказывает
  ADR-014» это как раз `long-section` плюс фраза в `modelSays`, а не отдельный вид находки.
  Оставить их значило бы держать в enum два недостижимых варианта и открыть обратно дыру
  «модель диктует `kind`».
- **Суждения приходят поверх ПОЛНОГО списка фактов.** Модель промолчала по части находок или
  упёрлась в `MaxSuggestions` — факты всё равно показываются, с пустым `modelSays`. Иначе
  счётчик группы в шапке («Работа для чата · 7», считается по фактам скана) разошёлся бы с
  содержимым группы, а при мёртвой модели группа исчезла бы целиком — при живых фактах. Это
  прямое применение принципа 4 «Факт важнее формулировки».
- **`MaxSuggestions` принуждает СЕРВЕР, а не промпт.** Число просится в промпте, но модель
  может вернуть больше; после сопоставления с фактами сервер оставляет первые
  `MaxSuggestions` сопоставившихся суждений, остальные отбрасывает. Без этого расчёт потолка
  вывода (Р7) — надежда, а не предел.

Промпт строится по отчёту и просит JSON. Разбор — с тем же тихим фолбэком, что у `project-icon`
(`ProjectIconGlyphService.ParsePick`, `ExtractJsonObject`): битый JSON = факты сканера без
формулировок, а не ошибка экрана.

## Р8а. Чем держится инвариант «механические правки формирует сканер»

Двухфазность делалась ради ровно одного инварианта: **в файл попадает только то, что
посчитал детерминированный код**. В прежней редакции он держался на послушании модели — и это
была дыра, а не инвариант: ничто не мешало модели вернуть заполненный `apply`, выдуманный
`anchor.line` или ссылку на несуществующую секцию, и `apply` записал бы это в `CLAUDE.md`.
Инвариант такого веса обязан держаться кодом. Четыре механизма, каждый — на границе разбора
ответа модели:

1. **`apply` у ответа модели обнуляется безусловно.** Не «валидируется», не «проверяется на
   непротиворечивость» — поле не читается из её ответа вовсе, потому что его нет в схеме
   разбора (Р8: модель диктует `id`, `severity`, `modelSays`). Патч берётся ТОЛЬКО из факта
   сканера по `id`. То же для `fact`, `anchor`, `savingLines`, `kind`: их модель знать не
   могла — она видела отчёт, а не файл.
2. **Предложение, не сопоставимое с фактом свежего скана, отбрасывается.** `id` из ответа
   модели ищется в фактах; не нашёлся — предложение выброшено, а не показано с пустым фактом.
   Модель, выдумавшая несуществующую секцию, не доедет до экрана.
3. **`id` детерминирован от содержимого:** первые 8 байт SHA-256 от `kind` + якорной строки
   по виду находки (таблица в Р8: у `long-section` это заголовок секции, у ссылок —
   `anchorText`), нормализованной схлопыванием пробелов и `TrimEnd`. Не
   порядковый номер и не GUID. Причина в том, что факты сканера **не кэшируются вовсе**
   (Р10.5): `apply` пересканирует карту заново, и `ids[]`, присланные фронтом, обязаны
   находиться в СВЕЖЕМ скане. Порядковый номер съехал бы при любой правке выше по файлу, и
   человек применил бы не то предложение, которое отметил, — молча и с записью в файл. С
   хешем от содержимого несовпадение даёт честный `failed: unknownId`.
4. **`severity` из ответа модели — единственное, что проходит как есть**, и то через белый
   список трёх значений с дефолтом по `kind` (`dead-link` → `high`, остальное → `medium`).
   Цена ошибки тут — неверный цвет плашки, а не правка файла.

Тесты (обязательные, каждый бьёт по конкретному механизму):

- модель вернула предложение с непустым `apply` — в итоговом ответе `apply` взят из факта
  сканера, а присланный проигнорирован;
- модель вернула `id`, которого нет в фактах, — предложение отброшено, остальные целы;
- модель вернула `anchor.line`, не совпадающий с фактом, — в ответе значение сканера;
- `id` одной и той же находки совпадает в двух независимых сканах и не зависит от порядка
  находок в файле.

## Р9. Эндпоинты

Новый контроллер `ProjectMapController` в Main (`api/projects/{projectId}/map-hygiene`).
В `DocsController` не лезем: гигиена карты — не часть корпуса документации.

| Метод | Назначение |
|---|---|
| `GET  …/map-hygiene/scan` | только сканер: мгновенно, без модели и без трат |
| `POST …/map-hygiene/review` | формулировки модели поверх фактов; тело `{ baseSha }` |
| `POST …/map-hygiene/apply` | применить отмеченные; тело `{ baseSha, ids[] }` |

Владение — дословно как у соседей (`ProjectsController.cs:461`):
`var p = projects.GetById(id); if (p is null || p.OwnerId != UserId) return NotFound();`
— 404 на чужой проект, существование не подтверждаем.

**Адреса файла в теле `apply` нет и не будет** — предмет правки ровно один (Р4). Если когда-то
понадобится править вторую карту, это новая развилка контракта, а не добавление поля: менять
придётся и UI, и тексты, и Р10а.

**`review` сверяет `baseSha` так же, как `apply`, и так же отвечает `409`.** Ход модели идёт до
трёх минут, и за это время карту в общем дереве вполне могут дописать. Без сверки сервер отдал
бы формулировки по новому составу поверх старых фактов на экране — с другими `id`, то есть с
чекбоксами, которые тихо перестали совпадать с находками. Отказ здесь дешёв: человек видит уже
заложенную в раскладку плашку «файл изменился после проверки · Проверить заново».

`apply` отвечает честным отчётом `{ applied[], failed: [{ id, reason }], newSha, scan }` по
образцу `POST /api/projects/{id}/preset` (`onboarding-intro.md:199`), а не мнимой атомарностью:
часть правок могла не найти свой якорь. Свежий `scan` в ответе избавляет фронт от второго
запроса ради перерисовки шапки. Закрытый список `reason` (фронт по ним не ветвится, но человеку
показывается своя строка на каждый): `anchorNotFound`, `ambiguousAnchor`, `unknownId`,
`notApplicable` (предложение без `apply`).

**Карты нет на момент `apply`** (удалили или переименовали, пока отчёт был открыт) — `409` с
той же плашкой «файл изменился после проверки», а не 404 и не необработанное исключение:
сверка `baseSha` этот случай ловит первой, и для человека он неотличим от «карту подменили».

**Грабля фронта, обязательная к учёту:** дефолтный таймаут `request()` — 30 с
(`lib/offline.ts:318`), а ход модели до минуты; без явного `timeoutMs: 180_000` (образец —
`api.ts:1339`, `analyzePrompt`) обрыв покажется пользователю как «действие недоступно офлайн».

## Р10. Инварианты записи

1. **Ни одна правка не применяется без явной отметки человеком.** Чекбоксы сняты по умолчанию,
   у неприменимых предложений чекбокса нет вовсе, автоприменения нет ни на одном пути.
   Применить несколько отмеченных за раз можно — «Отметить все» это тоже действие человека,
   и каждая отметка видна ему на экране вместе со счётчиком в кнопке. Запрещено другое:
   предотмеченные галочки и любая запись, которой человек не видел.
2. **Применяются только механические правки** (починка мёртвой ссылки). Вынос секции в
   `docs/*` кнопкой не делается никогда: это содержательная работа, и её цена — потеря знания,
   оплаченного инцидентами.
3. **Проверка перед записью:** файл не изменился с момента скана (сверка хеша) — иначе 409.
   Карту параллельно правят исполнители задач в общем дереве.
4. **Ни одной перезаписи вслепую** — прямая перекличка с требованием приёмки знакомства v2:
   «затёртый `CLAUDE.md` считается дефектом» (`project-onboarding-v2.md:17-19`).
5. **Ничего не кэшируется — ни факты, ни ответ модели.** Факты пересчитываются всегда
   (миллисекунды, а устаревший факт опаснее пересчёта) и ложатся в основание `id`
   предложений (Р8а.3). Кэш ответа модели — **отложен до после обкатки** (правка редакции 3):
   три поля в `Project` (`MapReview`, `MapReviewAt`, `MapReviewSha`) плюс своя ось протухания
   заводятся ради одного повторного нажатия у фичи, которую открывают редко и по поводу. Цену
   этого кеша видно только на живой фиче: сколько раз подряд её реально открывают и мешает ли
   минута ожидания. Прецедент хранения (`Session.ArchiveSummary`/`ArchiveSummaryAt`,
   `Session.cs:476-478`) никуда не денется — вернуться к нему можно, когда появится ответ на
   «мешает ли». Инвалидация, если кеш вернётся, — по расхождению сохранённого `baseSha` с
   текущим (по раскрытому составу, Р8).

## Р10а. Контракт записи

Самая опасная половина фичи: всё остальное читает, эта пишет в файл, который грузится в
каждую сессию. Доопределён в редакции 3 — прежний план описывал её одной строкой «применение
по якорю-тексту», из которой исполнитель мог сделать две разные вещи.

**Форма правки.** Ровно одна: замена подстроки `apply.anchorText` на `apply.after` в файле
`<корень>/CLAUDE.md`. Ни вставок, ни удалений строк, ни правок по номеру строки. Всё, что не
сводится к такой замене, приходит с `apply: null` и кнопки не имеет.

**`anchorText` — это ровно то, что заменяется, и он тождественно равен `before`.** Три поля в
`apply` (`before`, `after`, `anchorText`) — не три разные строки: `before` и `anchorText` —
одна и та же подстрока под двумя именами, первое для показа человеку, второе для поиска в
файле. **Расширять якорь окружающим контекстом ради уникальности запрещено:** тогда `after`
пришлось бы достраивать тем же контекстом, человек в «было → стало» видел бы одно, а в файл
уезжало бы другое — ровно та порча карты, ради защиты от которой писан весь этот раздел.
Неуникальный якорь не расширяется, а обнуляет `apply` (правило ниже).

Конкретно `anchorText` — **markdown-ссылка целиком**, `[текст](путь)`, а не голый путь. Разница
принципиальна для уникальности: один и тот же путь в карте встречается многократно (в тексте,
в бэктиках, в примерах), а полная ссылка с тем же текстом — обычно один раз. Оба наших
сегодняшних дефекта чинятся именно так.

**Когда `apply` не `null` — единственная формула, и она касается ТОЛЬКО `kind: dead-link`**
(у `dead-import`, `root-relative` и `long-section` `apply` пуст по определению, таблица в Р8):

> `apply != null` ⟺ находка — `dead-link`, сканер нашёл **ровно один** одноимённый
> файл-кандидат (Р8) **И** `anchorText` встречается в карте **ровно один раз вне кодовых
> заборов**.

Условия независимы, и ни одно не выводится из другого: кандидат отвечает на «чем чинить»,
уникальность — на «где чинить». Исполнитель, реализовавший только одно, получит либо запись
не в ту строку, либо кнопку, ведущую в никуда.

**Якорь обязан быть уникален вне кодовых блоков.** Случай «путь упомянут в карте дважды»
типичен — у нас, например, `docs/adr/ADR-014-internal-subsystems.md` встречается в тексте
многократно. Наивная замена первого вхождения молча починила бы не ту строку, и человек узнал
бы об этом из git-диффа, если бы посмотрел. Правило:

| Вхождений `anchorText` вне кодовых заборов (``` и ~~~) | Что делает сервер |
|---|---|
| ровно 1 | заменяет |
| 0 | `failed: anchorNotFound`, файл не тронут |
| 2 и больше | `failed: ambiguousAnchor`, файл не тронут |

Уникальность проверяется **на этапе скана** (предложение с неуникальным якорем рождается уже
с `apply: null` — кнопки человек не увидит вовсе) **и ещё раз перед записью** (между сканом и
применением карту могли дописать). Вторая проверка не дублирующая: она закрывает окно, первая
бережёт человека от кнопки-обманки.

**Кодовые заборы (``` и ~~~) не разбираются и на записи тоже.** Инвариант Р5.5 в прежней
редакции соблюдала только читающая половина: замена по подстроке спокойно залезает в пример
внутри забора — а в карте про карты таких примеров много (этот план сам себе доказательство:
прототип нашёл в нём две «мёртвые ссылки», обе внутри примеров). Механизм: перед заменой файл
размечается тем же проходом с флагом `inFence`, что и при сканировании, вхождения внутри
заборов из подсчёта и из замены исключаются. Отсюда прямое следствие: цель, встречающаяся
один раз в тексте и один раз в примере, — **один** кандидат, а не два, и замена состоится.

**Модель записи — read-verify-write под локом, и файл читается РОВНО ОДИН РАЗ.** Порядок:

1. взять лок на файл (`SemaphoreSlim` per-путь в сервисе; параллельный `apply` по той же
   карте — реальный сценарий: два окна продукта у одного человека);
2. прочитать карту целиком **одной строкой текста** и запомнить, был ли BOM (окончания строк
   специально фиксировать не нужно — при замене подстроки они не трогаются, см. ниже);
3. **пересчитать `baseSha`** по раскрытому составу — раскрытие считается **от уже
   прочитанного текста** (`Expand(text, basePath)`), а не повторным `Read(path)` с диска;
   сверить с присланным, расхождение даёт `409`, дальше не идём;
4. пересканировать карту **из того же текста в памяти** (перегрузка сканера, принимающая
   текст, а не путь), найти факты по присланным `ids[]` (неизвестный `id` → `failed`);
5. применить замены к тому же тексту, каждую с проверкой уникальности вне заборов;
6. записать: temp-файл рядом + `File.Move(tmp, path, overwrite: true)` — по образцу
   `JsonFileStore.cs:318-360` (уникальное имя temp через `Guid`, не фиксированное `.tmp`:
   два одновременных `Move` поверх одного файла на Windows дают Access denied);
7. отпустить лок, вернуть `{ applied[], failed[], newSha, scan }`.

**«Один раз» — это требование, а не оптимизация, и оно держит Р10.4 («ни одной перезаписи
вслепую»).** Читать файл на шагах 3, 4 и 5 заново означало бы вот что: правка постороннего
процесса, попавшая между сверкой хеша и записью, оказалась бы сверена в одном тексте, а
перезаписана другим — `File.Move` поверх снёс бы чужую правку целиком, а не заменил подстроку.
Сверка `baseSha` при этом отработала бы «успешно» и ничего бы не поймала. С единственным
снимком такое невозможно по конструкции: что сверили, то и записали.

Между шагом 2 и шагом 6 остаётся честное TOCTOU-окно — лок закрывает его только внутри
процесса, а карту правят и исполнители задач в общем дереве, и человек в редакторе. Это
признано и до конца не лечится: полностью закрыть окно можно было бы только эксклюзивным
захватом файла на всё время, а он поссорил бы фичу с любым открытым редактором. Цена
остаточного риска ограничена: чужая правка, пришедшая в это окно, будет потеряна — но ровно
она одна и только если уложилась в миллисекунды между чтением и `Move`. Дальше её защищает
git, и именно поэтому фича существует только для файла под версионным контролем.

**BOM и окончания строк сохраняются.** Грабля прямого действия: построчный разбор
(`text.Split('\n')`) с последующей сборкой через `\n` превращает CRLF-файл в LF одной правкой
— дифф на 974 строки вместо одной, а карту после этого не отревьюить. Правила:

- запись идёт **заменой подстроки в исходном тексте**, а не пересборкой из строк — тогда
  окончания и BOM сохраняются сами собой, и это главный механизм, а не дисциплина;
- кодировка при записи — `UTF8Encoding(encoderShouldEmitUTF8Identifier: BOM был)`: файл с BOM
  остаётся с BOM, без — без (`File.ReadAllText` BOM съедает молча, `File.WriteAllText` по
  умолчанию его не пишет — без явной передачи признак теряется);
- `anchorText` и `after` приходят от сканера, который читал тот же текст, поэтому искать
  якорь с `\r` внутри не требуется — он вырезан из одной строки.

**Тесты контракта записи:**

- якорь встречается дважды вне заборов → `failed: ambiguousAnchor`, файл не изменился
  (сверка по хешу до и после);
- якорь встречается один раз в тексте и один раз внутри забора (проверить и ```, и `~~~`) →
  замена состоялась, и
  именно в тексте, а пример внутри забора цел;
- якорь есть ТОЛЬКО внутри забора → `failed: anchorNotFound`, файл не тронут;
- CRLF-файл после `apply` остаётся CRLF (проверка на самих байтах, не на `ReadAllText`);
- файл с BOM после `apply` остаётся с BOM;
- `baseSha` устарел из-за правки ИМПОРТИРОВАННОГО файла (сама карта не менялась) → `409`;
- одно предложение не нашло якоря, второе нашло → первое в `failed`, второе применено,
  `newSha` соответствует записанному файлу.

## Р11. Фич-флаг

`project-map-hygiene`, `Default: false`, `Stage: "dev"` — dark launch по конвенции. Три шага
фронта: строка в `FeatureFlagCatalog.All`
(`backend/ClaudeHomeServer.Core/Models/FeatureFlag.cs`), ключ в `FLAGS`
(`frontend/src/lib/featureFlags.ts`), обёртка `useFeature`.

**Плюс серверный гейт — четвёртый шаг, и он обязателен.** Спрятать кнопку во фронте недостаточно:
веб-морда торчит наружу, а `POST …/apply` пишет в `CLAUDE.md`. Незавершённая фича с открытой
ручкой записи — лишний риск ровно там, где цена ошибки максимальна. Проверка владельца на
`review` и `apply` по образцу `DossiersController.cs:138`:

```csharp
if (!flags.IsEnabled(UserId, FeatureFlagKeys.ProjectMapHygiene)) return NotFound();
```

Именно `NotFound`, а не `Forbid`: выключенной фичи для этого пользователя не существует.
`GET …/scan` гейтить не обязательно (он ничего не меняет и ничего не стоит), но и вреда от
единообразия нет — решает исполнитель волны 3.

### Раскладка отчёта

`Modal width={MODAL_W.wide}` (720, уже в шкале), высота фиксированная — содержимое от проекта к
проекту разное, прыгающая карточка мешает сравнивать. Мобильную шторку `Modal` делает сам
(`useIsMobileModal`), отдельной раскладки не пишем.

Все числа в примерах ниже — **с одного замера** (наш `master`, 21.09.2026, шапка «Зачем»):
974 строки, 28 секций, 7 длиннее порога в 40 строк, 2 мёртвые ссылки. В редакции 2 они
разъехались между разделами («3 секции длиннее 80 строк» при пороге 40, группы «· 4» и «· 11»
при 2 и 7 замеренных) — в документе, где цифры и есть доказательство, это читается как разные
редакции, склеенные вместе.

Шапка — метки `Badge size="sm"`: «7 секций длиннее 40 строк» (`warning`), «2 мёртвые ссылки»
(`danger`), «Ориентир: до 200 строк» (`neutral`). Порог в метке называется явно: он
настраиваемый (Р6), и «длинная секция» без указания порога — оценка, выданная за факт.
**Прогресс-бара «487 % от нормы» не рисуем:** у большого проекта карта объективно больше, и
приговор в процентах обесценивает весь отчёт.

Тело — **один список, две озаглавленные группы, не табы**: «Правки в один клик · 2» и «Работа
для чата · 7». Табы прячут половину картины и дают ложное «я прибрался», когда закрыт только
механический таб, — а весь вес файла (473 строки из 974, это три крупнейшие секции) сидит как
раз во второй группе.
Подвал — «Ещё в проекте»: вложенные карты справочно, без плашек и действий (Р4).

Честность «применить можно не всё» держится на трёх вещах, а не на дисклеймере: заголовки групп
прямо называют способ, **у неприменимых предложений чекбокса нет вовсе** (галочка, которая
ничего не делает, врёт сильнее любой подписи), счётчик в кнопке считает только применимое.
Чекбоксы в группе 1 **по умолчанию сняты** — предотмеченная галочка это не «явное утверждение
человека», а дефолт, который прокликивают; цена — одна кнопка «Отметить все».

**Двухфазная загрузка:** факты и группа 1 показываются сразу, на месте группы 2 —
`WaitingIndicator` с подписью «Читаю карту и прикидываю, что свернуть…». Один спиннер на весь
экран здесь неуместен: детерминированная половина отчёта уже готова и уже полезна.

Состояния, которые обязаны быть: скан идёт · модель думает · модель отказала (настоящая причина
+ «Повторить») · предложений ноль («Карта в порядке») · карты нет («Создать через /init») ·
применено частично · файл изменился после проверки (плашка + «Проверить заново») · 360 CSS.

## Р12. `DefaultScope` трогать не надо

Сканеру область документации не нужна: он читает карту напрямую по известным путям (Р4) и
работает у проекта с любой настройкой, в том числе без документации вовсе.

влияет; если включать — тумблером области, а не сменой дефолта.

Разбор развилки целиком (в том числе почему опасение про общий кеш у соседей по `RootPath` не

|---|---|---|---|

## Волны реализации

**Волна 1 — сканер (самоценна, проверяема без модели и UI).** Разложена по шагам 0–4 раздела
«Порядок работ»: правка `IsExternal` → `Missing` у `Repo`-ссылок → третий исход резолва →
размеры секций → перенос `ClaudeMdExpander` в Core и `ProjectMapScanner` с эндпоинтом `scan`.
Критерий: на нашем репозитории отчёт находит ровно 2 мёртвые ссылки и 7 длинных секций, без
ложных срабатываний; аудит корпуса — 161 находку.

**Волна 2 — формулировки модели.** Строка каталога, промпт, сшивка ответа с фактами по `id`
и обнуление всего, что модель знать не могла (Р8а), `POST …/map-hygiene/review`. Кэш ответа
не делаем (Р10.5).

Критерий приёмки — **проверяемый, а не «качество формулировок»** (в редакции 2 у волны 2
критерия не было вовсе). Прогон на нашей карте, по 3 независимым запускам:

| Что меряем | Порог |
|---|---|
| Предложений сопоставилось с фактами сканера (`id` найден) | ≥ 80 % от вернувшихся |
| Предложений со ссылкой на несуществующую секцию доехало до ответа | **0** (механизм Р8а.2, а не везение) |
| Ответ уложился в потолок вывода, JSON разобран | 3 из 3 запусков |
| `modelSays` длиннее 120 символов | 0 после усечения на сервере |

Тексты формулировок оцениваются человеком глазами — это и остаётся допущением, но допущение
теперь ограничено: сопоставимость, длина и отсутствие выдумок проверяются машинно.
**Golden-прогон сохраняется** в `docs/research/project-map-review-golden-2026-09.md`: отчёт
сканера, промпт, три сырых ответа модели и разобранный результат. Без него следующая правка
промпта окажется правкой вслепую — сравнивать будет не с чем.

**Волна 3 — UI, часть 1.** `Checkbox` в `ui/`, типы и клиент API, `ProjectMapSection`, модалка с
фактами скана и пустыми состояниями, фич-флаг (вместе с серверным гейтом, Р11). Критерий:
кнопка есть, факты видны, модель не дёргается; при выключенном флаге `review`/`apply` отвечают
404.

**Волна 4 — UI, часть 2 и применение.** `POST …/map-hygiene/apply` по контракту записи Р10а
(уникальный якорь вне кодовых заборов, read-verify-write под локом, temp + `File.Move`, BOM и
окончания строк сохраняются), карточки предложений, выборочное применение, второй вход в
`PromptSnapshotDialog`. Критерий: предложение применяется, «было → стало» видно до записи,
все тесты Р10а зелёные.

Волны 3 и 4 — **две отдельные задачи исполнителю, а не одна**: ~600–700 строк нового фронтового
кода в одно окно не лезут (оценка Киры, принята).

## Тесты

Пишутся в `ClaudeHomeServer.Tests` (у `Docs` есть `InternalsVisibleTo ClaudeHomeServer.Tests`).
Обязательные кейсы — каждый закрывает грабли, найденные замером, а не гипотезу:

1. ссылка относительно корня репо из вложенной карты — **третий исход** («только от корня»),
   не «мёртвая» и не «живая» (Р5.3);
1а. `javascript:`/`data:`-цель — `External`, а не отсутствующий файл (Р2а.2);
1б. `Repo`-ссылка на существующий файл вне области — `Missing = false`; на переехавший —
    `Missing = true`, при этом `Kind` остаётся `repo` и клик в панели не ломается (Р2а.1);
2. абсолютный путь в `SafePath.Join` не уходит, помечается `skipped` (Р5.2);
3. `../..` — `skipped`, сканер не падает (Р5.4);
4. `##` внутри ```-забора не считается заголовком секции;
5. **ссылка внутри ```-забора не проверяется и в `deadLinks` не попадает** (Р5.5) — кейс
   найден самопроверкой на живом тексте, а не придуман;
6. `@`-импорт увеличивает `expandedLines` (Р3);
7. карты нет — штатный ответ, не исключение;
8. `.claude/worktrees` и `node_modules` в `nestedMaps` не попадают (Р4);
9. чужой проект — 404;
10. мёртвая ссылка с двумя одноимёнными кандидатами отдаёт `apply: null` (Р8);
11. `apply` с устаревшим `baseSha` — 409, файл не тронут (Р10.3);
12. якорь-текст не найден — предложение уходит в `failed`, остальные применяются (Р9);
13. мёртвый `@`-импорт — находка в `deadImports`; упёрлись в `MaxDepth`/`MaxTotalChars` —
    `importDepthExceeded`/`expansionTruncated` в отчёте, а не молчание (Р3);
14. `baseSha` меняется при правке импортированного файла, хотя сама карта не менялась (Р8);
15. `Missing` меняется после переезда `.cs`-файла без единой правки документов — то есть
    считается вне кеша корпуса (Р2а.4).

Волна 2 (Р8а): модель вернула `apply` — сервер его отбросил; `id` не из фактов — предложение
выброшено; `anchor` от модели проигнорирован; `id` одинаков в двух сканах и вычисляется для
находки `long-section` (у которой `anchorText` нет); модель вернула больше `MaxSuggestions`
суждений — сервер оставил первые N; модель не ответила вовсе — факты показаны полностью,
`modelSays` пуст, `modelNote` заполнен сервером; `review` с устаревшим `baseSha` — 409.

Волна 4 (Р10а): два вхождения якоря → `ambiguousAnchor`; вхождение только внутри забора
(проверить и ```, и `~~~`) → `anchorNotFound`; вхождение в тексте и в заборе → заменено в
тексте, пример цел; кандидат ровно один, но якорь неуникален → `apply: null` ещё на скане;
CRLF остаётся CRLF; BOM остаётся BOM; карты нет на момент `apply` → 409, не исключение.

Платформонезависимость обязательна (CI на Linux): пути через `Path.GetTempPath()` +
`Path.Combine`.

## Что НЕ делаем

- **Фоновый процесс, правящий карту по расписанию.** Нет измеримого критерия «знание не
  потеряно», а файл хранит инварианты, оплаченные инцидентами.
- **`@`-импорты как способ экономии контекста** — они не ленивые, грузятся сразу.
- **Проверку голых путей в бэктиках** — 14 ложных из 16 (Р5).
- **Вынос секций кнопкой** — только руками человека (Р10.2).
- **Новое хранилище под отчёт** — не кэшируется ничего: ни факты сканера, ни ответ модели
  (Р10.5).
- **Генератор unified diff на бэкенде** — механическая правка показывается как «было → стало»,
