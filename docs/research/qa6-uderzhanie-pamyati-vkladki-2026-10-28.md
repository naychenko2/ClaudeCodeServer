## Прямой ответ

**Второго независимого источника роста, который «убивает вкладку», на стенде не воспроизвелось: устойчивого роста памяти вкладки нет ни в одном из трёх сценариев.** Память после прогрева выходит на плато (~56 МБ) и держится там.

Найдено при этом конкретное удержание, у которого **нет потолка**: после ухода из чата в куче вкладки остаются **base64-вложения чата** (3 PDF по сумме 4,06 МиБ + ZIP 0,86 МиБ ≈ 9 МБ на чат с вложениями). Удерживают их **незакрытый курсор чтения IndexedDB (`IDBCursorWithValue` → `IDBRequest` → `V8EventHandler`)** и **незавершённые `Promise`/`Generator`**. Это и есть кандидат на «вкладка падает по памяти в сценарии чатов»: он накапливается по мере открытия новых чатов с вложениями, тогда как ленты чатов (потолок 8) и сырые истории (потолок 5) урезаны. Заведена карточка-дефект.

**Панель «Локальные модели» (дополнение Андрея) источником не является:** при просто открытой панели 5 минут — плато 43,5 МБ, история медиа и превью в памяти не растут, **подписки и таймеры снимаются корректно** (тяжёлый опрос `/api/local-model/stats` раз в 2 с прекращается после закрытия панели; остаётся только лёгкий опрос раз в 60 с, он смонтирован на странице, а не на панели).

**Стор `meta` растёт** (32 → ~103 МиБ за прогон), но рост упирается в потолки классов ADR-036: класс содержимого файлов доходит до 220 записей / 67,9 МиБ при потолке 64 МиБ, служебные записи — 25,2 МиБ разово. Сверх потолков выхода не зафиксировано.

## Метод

* **Heap:** CDP `Runtime.getHeapUsage` (usedSize/totalSize + embedder/backingStorage) после `HeapProfiler.collectGarbage` **дважды** с паузой; `Performance.getMetrics` — как второе мнение по used heap; `Memory.getDOMCounters` — документы/узлы/слушатели.
* **Heap-снимок:** `HeapProfiler.takeHeapSnapshot` (парные: «до» и «после» в **одинаковом состоянии экрана**), разбор по классам (тип + имя, агрегат `self_size`), отдельно — крупные строки.
* **Кто удерживает:** собственный retainer-анализ снимка (`retainer.cjs`): обратные рёбра → цепочка от объекта к корню. **Грабли формата:** в рёбрах `to_node` — это смещение в плоском массиве `nodes` (кратно 6), а не индекс узла; без деления на `NODE_FIELDS` цепочки выходят пустыми.
* **Стор:** курсором по всем ключам стора `meta` базы `ccs-offline`, размер = UTF-8 байты `JSON.stringify(entry.data)`, классификация по префиксам классов (`offline:`, `offlinenotes:`, `offlinechat:`, `offlinefile:`).
* **Грабли измерения (важно):** чтение стора `getAll()` **оставляет в куче `IDBCursorWithValue` со значением** — это выглядит как «удержание приложения», но это артефакт замера. Лечится явным `cursor.close()`; после правки в замерах остались только честные удержания.
* **Документ вкладки не перезагружался** ни в одном прогоне (`performance.getEntriesByType('navigation').length === 1` во всех снимках) — иначе память обнулилась бы и замер был бы бессмыслен.
* Стенд поднят с `LocalModelStats:Enabled=true` — без этого поллер статистики молчит, `/api/local-model/stats` отдаёт `configured:false`, и панель «Локальные модели» для админа не появляется вовсе (флаг `local-model-stats` у владельца включён, но гейт поллера — отдельная настройка).

**Стор растёт всегда и одинаково: +60…+95 МиБ за прогон, и это происходит даже без единого открытия чата (L1 — только список чатов, 5 минут).** Состав класса содержимого файлов разобран отдельно (L2): **220 записей, 67,9 МиБ, из них помеченных («k», keep) — 220, свободных («f») — 0**. Потолок файлового класса — `FILE_CLASS_MAX_BYTES = 64 МиБ` (`frontend/src/lib/offline.ts:860`), и их оценка веса — длина текста ответа (`text.length`), то есть с моим независимым JSON-подсчётом одного порядка.

**Это не регресс ADR-036:** вытеснение работает (второй проход по помеченным снимает лишнее, когда `keepBytes > _fileMaxBytes`, `offline.ts:1313–1319`), и после ужима класс держится у потолка (67,9 МиБ ≈ 64 МиБ + одна свежая запись сверху). Рост стора — **заполнение классов до потолков**, а не бесконечный рост. Сверх потолка выхода не зафиксировано ни в одном прогоне.

## c3 — Разбор удержания по классам

### Что растёт в heap-снимке (Δ за прогон, типично)

| класс | Δ | что это |
|---|---|---|
| `system / InstructionStream` | +2,9…+3,2 МиБ | **байткод лениво загруженных чанков** (BackButton/HubHeader/image-editor-remote и т.п.) — не данные |
| `system / TrustedByteArray` | +0,34…+0,51 МиБ | служебные байтовые массивы V8 |
| `Object` | +0,38…+0,46 МиБ (×7–10 тыс.) | мелкие объекты приложения |
| строковые данные (`string`) | **≈ 0** | данных в виде строк почти не добавляется |

### Что реально удерживается: base64-вложения чата

После ухода из чата (снимок «после», на экране списка чатов) в куче живы **3 строки-PDF (4,06 МиБ суммарно) и 1 ZIP-вложение (0,86 МиБ)** — суммарно **≈ 9 МБ на один чат с вложениями**. Retainer-цепочки (собственный анализ снимка):

```
string 'JVBERi0xLjcK…' (1,66 МиБ)
  object Object (48 Б) ← base64
  array (?) (336 Б) ← 20
  object Generator (52 Б) ← parameters_and_registers
  object system / Context (20 Б) ← extension
  hidden system / PromiseReaction ← [2] → object Promise → object Generator   ← незавершённая асинхронная обработка

string 'JVBERi0xLjUKJ…' (1,20 МиБ)
  object Object (28 Б) ← base64
  object Object (28 Б) ← data
  native IDBCursorWithValue (152 Б) ← <symbol>     ← НЕЗАКРЫТЫЙ КУРСОР ЧТЕНИЯ СТОРА
  native IDBRequest (248 Б) ← <symbol>
  object system / Context (36 Б) ← s
  native V8EventHandlerNonNull → native EventListener → native InternalNode
```

Два разных механизма удержания одного и того же бинарника: **курсор чтения IndexedDB** и **незавершённый промис/генератор**. Ни у одного нет потолка; у лент чатов (`useSession._store`, максимум 8 сессий) и сырых историй (`_cursors`, максимум 5) потолки есть, у вложений — нет.

### Панель «Локальные модели» — по классам и по подпискам

| что смотрели | результат |
|---|---|
| рост при просто открытой панели (5 мин, без действий) | used 47,9 → 43,5 → 43,4 → 43,4 → 43,6 → 43,5 МиБ — **плато, роста нет**; Δ heap-снимка +1,4 МиБ |
| живой поток | опрос `/api/local-model/stats` — 0,8 запроса/с при открытой панели (50 → 91 → 130 запросов за блоки по 60 с) |
| история медиа и превью в памяти | **не растут**: снапшот Δ +1,4 МиБ за 5 минут; DOM-картинок с `data:`-URL — 0 |
| подписки при закрытии панели | **снимаются корректно**: после ухода с панели компонентов `localModel` в DOM — **0**, запросов к `/api/local-model/*` за 60 с — **2** (только лёгкий опрос 60 с, он живёт на странице) |
| грабли | иконка панели **не переключатель**: повторный клик снова открывает панель, а не закрывает; закрывает кнопка «Скрыть «Локальные модели»» |

## c4 — Вывод и карточка-дефект

**Источник падения вкладки не найден** (устойчивого роста нет ни в одном сценарии; панель «Локальные модели» чиста). **Найден конкретный удерживаемый объект без потолка** — base64-вложения чатов в куче вкладки (≈ 9 МБ на чат, удержание через незакрытый `IDBCursorWithValue` и незавершённые промисы).

**Карточка-дефект:** `5f107f90-6738-4f6f-9d9f-3b37dd00a81a` — «Вкладка удерживает base64-вложения чата после выхода из чата — без потолка» (kind=defect, featureId `b51a754c-…`, шаги воспроизведения и цепочки удержания внутри).

Правок кода не вносилось (задача — замер).

## Что НЕ проверено

* **Длительная сессия (часы работы вкладки)** — не воспроизводилась: 20 циклов и 5 минут простоя — максимум, что позволяла сессия. Если у Андрея вкладка живёт сутками, накопление базы64-вложений (дефект) и `useSession._store`/`_cursors` (потолки 8 и 5) могут вести себя иначе.
* **Медиа-часть панели «Локальные модели» в полном виде:** ComfyUI на машине не запущен (`/api/local-model/stats/media` → `comfy.status: disabled`), поэтому живая скорость генерации, очередь и реальные превью не измерялись. История медиа в сторе (`data/local-media-history`) — 3 файла, 152 КБ; в куче не росла.
* **Потолок класса файлов на пределе:** класс доходил до 67,9 МиБ при потолке 64 МиБ — вытеснение сработало, но «переполнение сверху» (запись сверх потолка между проходами) не измерялось отдельно.
* **Другие владельцы и другой объём чатов** (у «мелких» владельцев класс файлов не наполнится).
* **Прод не трогался**: все замеры — на копии данных; боевой стенд и боевые данные не использовались.
