# ADR-007: Пресет как именованная цепочка моделей, матрицы уровней, маршрут `preset:{id}`, миграция стора v1→v2

**Статус:** Принято (реализовано 2026-08-08, волны 1–2 + фиксы ревью)
**Дата:** 2026-08-05
**Принимающий решение:** Андрей (владелец продукта)
**Автор:** Александр (тимлид/архитектор)
**Связанные ADR:** [model-resolution-and-fallback.md](model-resolution-and-fallback.md) — остаётся
в силе в части классов ошибок (§2) и защиты от зацикливания (§4). Настоящий ADR
**уточняет** его §1 (шаг «специальность» переосмысляется в матрицу), **меняет** §3
(порядок фолбэка) для ходов с цепочкой и **заменяет** семантику пресетов из §5.

## Контекст

Фича «Поставщики моделей» (коммиты `432986c6`, `e14c013d`) реализовала пресеты не так,
как задумал владелец продукта. Целевая модель — дословно:

> «В пресете должна быть цепочка последовательности переключения между моделями, в том
> числе от разных провайдеров. Пресет мы сохраняем под каким-то именем, и дальше в
> настройках выбора модели мы можем использовать preset. То есть там, где мы в любых
> местах, где мы указываем конкретное название модели, мы можем выбрать preset. И это
> означает, что должна отрабатывать цепочка этих моделей. То есть, если какая-то первая
> не сработала, срабатывает вторая, либо третья, либо четвертое.»

И уточнение по персонам и специальностям:

> «Для персоны для специальности должна быть возможность настроить выбрать сильную,
> среднюю и слабую модели и для тех, и для других, и там же должна быть возможность
> использовать пресеты.»

Как реализовано сейчас (`Services/SpecialtySettingsStore.cs`, `FormatVersion = 1`):

- Пресет — `ModelRoutePreset { Id, Name, Description, Rules[] }`, где `ModelRouteRule` —
  пара «специальность (или `any`) → ОДИН маршрут». Никакой цепочки нет.
- Пресеты **не выбираются**: `ResolveRoute(ownerId, specialty)` обходит ВСЕ пресеты
  подряд (личные, затем глобальные — `EffectivePresets`) и берёт первое совпавшее
  правило. Пресет — не значение, а сборник правил, применяемых всегда.
- Привязка «модель специальности» физически живёт правилом внутри пресета — своего
  поля у специальности (`SpecialtyTemplateSettings`) нет. Своих слотов уровней нет
  ни у специальности, ни у персоны: `tier:*` всегда означает слот владельца
  (`UserModelTierResolver.ModelFor`: личный слот → глобальный слот инстанса).
- Фолбэк (`FallbackLlmSessionAdapter.ResolveNextTarget`) подбирает следующего кандидата
  **автоматически**: уровень 1 — другая подписка того же пула (`SubscriptionCandidates`),
  уровень 2 — обход `LlmProviderRegistry.Enabled` с моделью-эквивалентом по слоту
  (`EquivalentModel`). Пользователь порядком переключения не управляет.

Расхождение тройное: пресет — не цепочка, пресет — не значение, а «сильная/средняя/
слабая» существует только на уровне владельца. Этот ADR фиксирует целевую архитектуру
следующей итерации; код по нему пишет волна реализации.

## Решение

### 1. Структура пресета: имя + упорядоченная цепочка шагов

```json
{
  "id": "…",
  "name": "Мой рабочий каскад",
  "description": "…",
  "steps": [ "tier:strong", "glm-5.2", "local" ]
}
```

- `ModelRoutePreset` v2: `{ Id, Name, Description, Steps: List<string> }`. Класс
  `ModelRouteRule` и поле `Rules` умирают (миграция — §6).
- Шаг — маршрут в **существующей лексике** `LocalActionOverridesStore`: `tier:strong|medium|weak`,
  id модели любого настроенного провайдера, `local`, `claude`, `default`. Новых видов
  значений шаг не добавляет; разбор `tier:*` — существующий `ParseTierRoute`, никакого
  `Enum.TryParse`.
- Шаг НЕ может быть ссылкой `preset:{id}` — вложенность запрещена валидацией
  (`ValidateLayer` отвергает слой с таким шагом, контроллер отдаёт 400). Причина:
  вложенность превращает разворачивание в обход графа с циклами; пользы у неё нет —
  цепочку можно записать плоско.
- `tier:*`-шаг внутри пресета разворачивается **по владельцу хода** через
  `UserModelTierResolver` (личный слот → глобальный), БЕЗ матриц персоны/специальности
  (§2): пресет — сущность уровня владельца/инстанса, он не знает, из чьей ячейки на
  него сослались, и не должен менять смысл от места ссылки.
- **Длина цепочки: 1..5, потолок общий с фолбэком** — константа
  `FallbackSettingsStore.HardMaxSubstitutions` (сейчас 5), своей константы у пресета
  не заводится. Обоснование: шаги цепочки после первого — это и есть подмены; второй
  потолок с другим числом дал бы две истины об одном пределе. Валидация длины —
  в `ValidateLayer`.
- Пресеты продолжают жить в `SpecialtySettingsStore` двумя слоями (глобальные +
  личные РЯДОМ, решение «Глобальные + личные рядом» сохраняется). Поиск пресета по id
  при разворачивании ссылки — в порядке `EffectivePresets`: личные раньше глобальных.

### 2. Матрицы уровней: у персоны и специальности — свои «сильная/средняя/слабая»

Ключевой принцип, развязывающий узел «у слова "сильная" несколько источников»:

> **Уровень (tier) выбирает СТРОКУ. Сущность выбирает МАТРИЦУ.**
> Уровень — это «насколько сложна работа» (его ставит задача, персона или дефолт
> места), а не «какой моделью». Какая модель стоит за уровнем — решает самая узкая
> заполненная матрица.

**Хранение** (имена ячеек — по образцу уже существующих `LlmProviderConfig.TierStrong|TierMedium|TierWeak`):

- Персона: `Persona.TierStrong|TierMedium|TierWeak: string?` (в `data/personas.json`).
- Специальность: `SpecialtyTemplateSettings.TierStrong|TierMedium|TierWeak: string?`
  плюс `DefaultTier: ModelTier?` (см. ниже). Семантика слоёв сохраняется как у
  остальных полей шаблона: запись специальности в per-owner слое заменяет глобальную
  ЦЕЛИКОМ (полевого слияния между слоями нет — действующее правило стора).
- «Любая специальность» (наследник правила `any` v1): запись той же формы
  `SpecialtySettingsLayer.DefaultSpecialty: SpecialtyTemplateSettings?` — применяется,
  когда у конкретной специальности записи нет.
- Значение ячейки: **id конкретной модели ИЛИ ссылка `preset:{id}`** (§3). Пустая
  ячейка = «у этой матрицы ответа нет, спроси следующую». `tier:*` в ячейке запрещён
  валидацией: ячейка уже адресована уровнем, тир внутри неё — либо тавтология, либо
  петля («strong = tier:weak»).

**Кто задаёт уровень** (источники уровня, по убыванию приоритета):

```
TaskItem.ModelTier (постановщик задачи)
  -> Persona.ModelTier (уровень персоны)
  -> SpecialtyTemplateSettings.DefaultTier (уровень специальности)
  -> дефолт места каталога (LocalActionCatalog.EffectiveDefaultTier)
```

`DefaultTier` специальности — новое поле, замена прежней роли «специальность даёт
`tier:*`-маршрут» (шаг 3 ADR model-resolution-and-fallback §1): специальность больше
не источник маршрута, а источник уровня и матрица его разворачивания.

**Чья матрица разворачивает уровень** (по убыванию узости, первая непустая ячейка
строки побеждает):

```
уровень T
  1. матрица персоны            Persona.TierStrong|Medium|Weak
  2. матрица специальности      запись специальности (owner-слой -> глобальный),
                                затем DefaultSpecialty (owner -> глобальный)
  3. слоты владельца            User.ModelTier* -> AppSettings.ModelTier*
                                (существующий UserModelTierResolver.ModelFor)
```

**Место `Persona.Model` и семантика `Persona.ModelTier`:**

- `Persona.Model` (явная модель) остаётся сильнее всего — не трогается.
- `Persona.ModelTier` МЕНЯЕТ СМЫСЛ: раньше «работай средней моделью владельца»,
  теперь «работай своей средней» — уровень разворачивается по матрицам, а не сразу
  по слотам. Это ломающее изменение семантики, фиксируем явно. **Миграция данных не
  нужна:** у всех существующих персон и специальностей матрицы пусты, разворачивание
  проваливается в слоты владельца — поведение до первого заполнения ячейки байт в
  байт прежнее. Смысл сдвигается только в момент, когда человек сам заполняет матрицу.

**Инвариант единственной точки разворачивания.** Правило CLAUDE.md «слот в модель
превращает только `UserModelTierResolver.ModelFor`» сохраняется и расширяется: у
`UserModelTierResolver` появляется перегрузка, принимающая **контекст-данные** —
упорядоченный список узких матриц (персоны, специальности), уже найденных вызывающим:

```
ModelFor(tier, ownerId, IReadOnlyList<TierMatrix> narrowMatrices)
  // обходит narrowMatrices по порядку, затем существующий путь
  // «личный слот -> глобальный слот»
```

Выбран вариант «функция принимает контекст», а не «слой перед функцией»: слой-обёртка
стал бы второй точкой, которую пришлось бы запрещать дублировать; сервисные зависимости
(PersonaManager, SpecialtySettingsStore) в `UserModelTierResolver` при этом НЕ
затягиваются — вызывающие (`ModelAssignmentResolver`, `TaskExecutionService`,
`SessionManager.ResolveDefaultModel`) передают матрицы как значения, они у них и так
под рукой. Существующая перегрузка `ModelFor(tier, ownerId)` остаётся для мест без
персоны (фоновые действия, `CheapTextRunner`) и эквивалентна вызову с пустым списком.

Если ячейка выигравшей матрицы — `preset:{id}`, уровень разворачивается сразу в
цепочку шагов пресета (§3), и дальше действует фолбэк по цепочке (§4).

### 3. `preset:{id}` — новое значение лексики маршрутов

- Новый префикс в `LocalActionOverridesStore`: `PresetPrefix = "preset:"` (рядом с
  `TierPrefix`), парсер `ParsePresetRoute(route) → presetId?` — по образцу
  `ParseTierRoute`.
- Ссылку обязаны принимать **все места выбора модели**: три слота владельца/инстанса
  (`User.ModelTierStrong|Medium|Weak`, `AppSettings.ModelTierStrong|Medium|Weak`),
  ячейки матриц персоны и специальности (§2), `Persona.Model`,
  значения мест каталога в `LocalActionOverridesStore` («Кто что выполняет»),
  `Session.Model` как явный выбор чата.
  **Исключение (решение владельца продукта после ADR): у `TaskItem` пресета нет** —
  задача говорит только уровнем (`TaskItem.ModelTier`), а чем её делать решает
  исполнитель; поле `preset:{id}` в задаче не заводим. Это расхождение с ранней
  формулировкой «явная модель задачи» — оно осознанно и снято здесь.
- **Хранится как есть, разворачивается на границе запуска.** Ссылка в сторах не
  материализуется в модель — как и `Model = null` у сессии, она резолвится каждый ход,
  поэтому правка пресета действует на все места сразу без пересохранения. Шлюзы
  разворачивания — те же, что у слотов: `ClaudeSession.EffectiveModel` (через
  `ModelAssignmentResolver`) и `OneShotClaudeRunner.ResolveModel`; в `Session.Model`
  и наружу маркеры `preset:*`/`tier:*` не текут (действующее правило).
- **Единая точка разворачивания цепочки** — новый метод
  `SpecialtySettingsStore.ExpandChain(route, ownerId) → IReadOnlyList<string>`: для
  обычного маршрута возвращает список из одного элемента, для `preset:{id}` — шаги
  пресета. Разворачивание `tier:*`-шагов в модель остаётся за `UserModelTierResolver`
  (§1: по слотам владельца, без матриц). Результат для агентного места — первый
  пригодный шаг цепочки становится моделью хода, остаток — планом фолбэка (§4);
  шаги `local` и `direct:*` агентным местам непригодны и при развороте пропускаются
  (та же фильтрация, что сегодня в `ModelAssignmentResolver.Resolve`).
- **Защита от цикла через слоты.** Слот или ячейка может содержать `preset:{id}`,
  а шаг пресета — `tier:*`, который разворачивается обратно в слот. Разворачиватель
  ведёт набор уже посещённых ссылок (id пресетов + тир-слоты); повторное вхождение —
  шаг отбрасывается с Warning. Глубина косвенности и так ограничена запретом вложенных
  пресетов и запретом `tier:*` в ячейках матриц — набор нужен только против петли
  «слот ↔ пресет».
- **Ссылка на удалённый пресет** — fail-open вниз: трактуется как пустая ячейка/пустой
  маршрут (резолв уходит на следующий шаг своей цепочки приоритетов), в лог — Warning
  с местом и id. Жёсткая блокировка удаления пресета «на него ссылаются» не строится:
  ссылки размазаны по нескольким сторам (`users.json`, `personas.json`,
  `local-actions.json`, `specialty-settings.json`), и надёжный обратный индекс — цена
  выше пользы. Продуктовая часть (показ «где используется» при удалении) — вне этого
  ADR, у Софьи.
- Для **фоновых мест** (`LocalActionRouter`/`CheapTextRunner`) пресет разворачивается
  в цепочку кандидатов, подставляемую НА МЕСТО «выбранного» в существующей цепочке
  деградации: `шаги пресета → локальная Ollama → claude`. Хвост-страховка сохраняется —
  фоновые вызовы обязаны оставаться дешёвыми и живучими.

### 4. Стыковка с фолбэком: цепочка заменяет автоподбор

Действующий фолбэк (ADR model-resolution-and-fallback §3) двухуровневый: ротация
подписок → автоподбор следующего провайдера с моделью-эквивалентом (`EquivalentModel`,
обход `Enabled`). Новое правило:

```
маршрут хода развернулся в цепочку (пресет)
  |
  v
шаг i цепочки = модель Mi (после разворачивания tier:*)
  Уровень 1 (без изменений): ротация подписок провайдера
  модели Mi - MarkExhausted -> Pick -> перенос транскрипта.
  "Шаг исчерпан" = все подписки этого провайдера для Mi
  исчерпаны или уже пробованы в этом ходу.
  |  шаг исчерпан
  v
переход к шагу i+1 цепочки (помечается в ленте как подмена)
  |  цепочка кончилась / потолок подмен достигнут
  v
ошибка пользователю (автоподбора НЕТ)
```

- **Автоподбора не существует (решение владельца 2026-08-08, ужесточение
  первоначального §4).** Уровень 2 прежнего фолбэка (обход `Enabled` +
  `EquivalentModel`) удалён полностью. Цепочка есть у ЛЮБОГО хода: маршрут через
  пресет/слот разворачивается в неё штатно, а явная конкретная модель достраивает
  «хвост тира» (см. §4.2). Ход, чья цепочка исчерпана (или состоит из одного
  элемента при пустом слоте), после уровня 1 завершается честной ошибкой — без
  настроек нет и магии.
- **Ротация подписок — под-шаг каждого элемента цепочки.** Уровень 1 сохраняется
  как есть (существующие `MarkExhausted` → `Pick` → миграция транскрипта, новых
  механизмов ротации не заводится — подтверждаем §3 старого ADR).
- **Ограничители зацикливания наследуются без изменений** (§4 старого ADR): каждая
  пара «модель × подписка» пробуется не более одного раза за ход; число подмен за ход
  клампится `FallbackSettingsStore.ResolveMaxSubstitutions` (per-owner → global →
  дефолт 3). Следствие, фиксируем осознанно: цепочка из 5 шагов при потолке подмен 3
  может не дойти до хвоста — потолок подмен есть бюджет хода и он сильнее маршрутного
  плана. Классы ошибок (§2 старого ADR) не меняются: цепочка срабатывает только на
  рантайм-ошибки доставки. Уточнение 2026-08-08: потолок подмен тратится ТОЛЬКО на
  смену типа поставщика (`IsProviderSwitch` — шаг цепочки). Тихие ротации подписок
  одного пула Claude бесплатны: это та же модель на другом аккаунте, а не подмена.
  Защита от зацикливания остаётся на наборе пар «модель × подписка» (`attempted`) —
  он конечен и ограничивает обе категории.
- Механика передачи: `FallbackLlmSessionAdapter` получает при создании не только
  `Func<string?> effectiveModel`, но и хвост цепочки хода (шаги 2..N, уже без
  непригодных значений); `tier:*`-шаги разворачиваются по владельцу сессии в момент
  перехода (слоты могли смениться за время хода — берём актуальные).

### 4.1. Явная модель несёт план отступления своего тира

Явная конкретная модель M (выбор чата, замороженная модель персоны) — не «одинокая»
модель, а голова цепочки: построение цепочки хода достраивает ей хвост — шаги
развёрнутой цепочки слота её тира ПОСЛЕ позиции M (или всю цепочку, если M в ней не
найдена; дедуп по существующему списку).

Тир M определяет `ModelAssignmentResolver.TierOfModel`: членство в РАЗВЁРНУТЫХ
цепочках слотов владельца (strong → medium → weak, без учёта регистра), фолбэк —
дефолтный тир места. Это закрывает §5 п.1: реверс-эвристика тира по литералу слота
удалена вместе с автоподбором, слот-пресет больше не ломает определение тира.

Следствия, принятые осознанно:
- «я выбрал X» означает «X, а при сбое — хвост цепочки его тира»; подсказка «Сейчас
  пойдёт» показывает цепочку;
- пустые слоты → хвоста нет → после пула честная ошибка.

### 4.2. Подмена — состояние хода, не выбор чата

`ApplyTarget` пишет `Info.Model/Provider` только на время хода (процесс попытки
пересобирается из них); в конце хода исходная пара восстанавливается покомпонентно с
CAS-семантикой (компонент восстанавливается, только если его текущее значение равно
последнему применённому адаптером — ручная правка пользователя во время хода не
перетирается; ABA «пользователь выбрал ровно подменённую модель» принят осознанно).
Восстановленное значение персистится (`SaveSessions` после restore) — рестарт сервера
не возвращает залипание на подмене.

**Что именно восстанавливается — решает накопленный за ход признак «была ли хоть одна
смена типа поставщика»** (`anyProviderSwitch`, накапливается по «или», а не тип последней
подмены), потому что транскрипт CLI физически лежит в профиле последней пары, на которой
прошёл ход (`TranscriptMigrator.TryMigrate` — копия, не перенос):
- *за ход не было смены типа поставщика* (только тихие ротации подписок того же пула,
  `IsProviderSwitch: false`) — `Provider` НЕ восстанавливается: чат остаётся на аккаунте,
  где прошёл ход и лежит свежий транскрипт. Качество не страдает (та же модель), а
  поведение совпадает со штатным `TryPoolFailover`, который тоже переезжает навсегда;
- *за ход БЫЛА смена типа поставщика* (хотя бы один `IsProviderSwitch: true` — шаг
  цепочки/сторонний провайдер, возможно с последующей тихой ротацией внутри нового пула) —
  восстанавливаются и модель, и провайдер (иначе выйдет несовместимая пара вроде
  `opus × kimi`), но ПЕРЕД этим транскрипт копируется обратно в профиль исходного
  провайдера из актуального `_profileRoot` (профиль последней пары — там лежит свежий
  ответ) — туда пойдёт `--resume` следующего хода. Обратный перенос не перезаписывает
  более полную историю усечённым источником (гонка «result раньше флаша CLI»): если
  приёмник длиннее — копия пропускается с Warning. Накопление по «или» закрывает сценарий
  «шаг цепочки → 429 → тихая ротация → успех»: тип последней подмены здесь `false`, и
  присваивание (а не `|=`) оставило бы несовместимую пару `Model × Provider` персиститься.

Инвариант, который держат обе ветки: **`Session.Provider` и профиль со свежим
транскриптом всегда указывают на одно и то же место**. Нарушение этого инварианта —
молчаливая потеря последнего ответа из контекста CLI (регрессия, найденная ревью
2026-08-08). Любая точка, меняющая `Info.Provider`/`_profileRoot` (включая стартовую
подмену по кулдауну), обязана переносить транскрипт или не подменять вовсе (fail-open).

### 4.3. Кулдаун недоступности провайдера

`ProviderHealthRegistry` (in-memory, TTL ~5 мин, не персистится и не бэкапится):
помечаются ТОЛЬКО сторонние провайдеры при классах Unreachable/ProviderError. Ключи
подписок пула Claude кулдауном не помечаются никогда — здоровье пула ведёт
`ClaudeSubscriptionPool` (исчерпание/warmup), и стартовая подмена не имеет права
обходить уровень 1. Использование: пропуск остывших шагов при переборе цепочки и
стартовая подмена хода с явной моделью мёртвого стороннего провайдера; оба места
fail-open — если все кандидаты в кулдауне, пробуем несмотря на пометки. Стартовая
подмена переносит транскрипт в профиль шага ДО подмены (инвариант §4.2); при провале
переноса подмена не применяется — ход идёт на исходной паре.

**Глобальность реестра (осознанное решение).** `ProviderHealthRegistry` один на процесс и
не разрезан по владельцу: пометка недоступности от хода одного пользователя гасит стартовые
попытки у всех. Это не нарушает изоляцию данных — реестр описывает здоровье стороннего
эндпоинта, а конфиг сторонних провайдеров общий на инстанс (не per-owner); ходы разных
владельцев стучатся в один и тот же физический эндпоинт, и если он недоступен — он
недоступен всем. Разрез по владельцу лишь маскировал бы наблюдение и заставлял каждого
повторно убеждаться в мёртвости эндпоинта. Подписки пула Claude (секреты per-owner)
кулдауном не помечаются (см. выше), поэтому глобальность реестра их не затрагивает.

### 5. Вскрытые конфликты с существующим резолвом

Места, где матрицы трутся о существующий код; волна реализации обязана их закрыть,
ревью — проверить.

1. **Обратное определение тира в фолбэке.** `FallbackLlmSessionAdapter.ResolveTier`
   восстанавливает тир текущей модели сравнением со СЛОТАМИ ВЛАДЕЛЬЦА — модель из
   ячейки персоны/специальности он не узнает и молча посчитает Medium, из-за чего
   `EquivalentModel` при автоподборе возьмёт у стороннего провайдера среднюю вместо
   сильной. Решение: тир хода известен на границе запуска (он выбирал строку матрицы) —
   передавать его в адаптер явно, реверс-эвристику `ResolveTier` оставить только как
   фолбэк для ходов, где уровень не участвовал. **Закрыто волнами 1–2 (2026-08-08):**
   тир передаётся явно (`ModelAssignmentResolver.TierOfModel` — членство в развёрнутых
   цепочках слотов, см. §4.1), реверс-эвристика `ResolveTier` удалена вместе с
   автоподбором.
2. **Разворачивание уровня при создании сессии.** `SessionManager.ResolveDefaultModel`
   разворачивает заданный уровень в модель при создании чата и дальше тот живёт как
   явная модель (действующее исключение из правила «резолв каждый ход»). С матрицами
   это разворачивание обязано идти через ту же перегрузку
   `UserModelTierResolver.ModelFor(…, narrowMatrices)`, а известное следствие
   расширяется: смена ячейки матрицы задним числом на уже начатый чат не влияет —
   как сегодня смена слота.
3. **`TaskExecutionService.ResolveExecutorModel` отдаёт маркер наружу.** Сегодня он
   возвращает `tier:*`-строку, которую разворачивает `ModelAssignmentResolver.Resolve`
   по слотам владельца. С матрицами разворачивание маркера обязано получать матрицы
   персоны-исполнителя — сигнатура цепочки «исполнитель задач» меняется (маркер должен
   ехать вместе с контекстом персоны, а не голым).
4. **Пресет разворачивается без матриц (§1).** Ячейка «strong = preset:X», где пресет
   X начинается шагом `tier:strong`, даст слот ВЛАДЕЛЬЦА, а не ячейку персоны — по
   принятому правилу «пресет не знает, откуда на него сослались». Это осознанное
   поведение, но на границе UX оно может удивить; текст-подсказка в UI — у Софьи.
5. **Отладка «почему выбралась эта модель» дорожает.** Матрица добавляет к цепочке
   приоритетов ещё одно измерение. Митигация прежняя (ADR model-resolution-and-fallback,
   «Последствия»): резолв остаётся в двух файлах (`ModelAssignmentResolver`,
   `UserModelTierResolver`), каждый шаг — включая «какая матрица выиграла ячейку» —
   логируется на Debug.

### 6. Миграция стора: `SpecialtySettingsStore.FormatVersion` 1 → 2

Цель — ни одна заданная человеком привязка «специальность → маршрут» не пропадает.

Порядок (однократно при `Load`, файл с `version: 1`):

1. Для каждого слоя (глобальный и каждый per-owner) НЕЗАВИСИМО обходим его пресеты
   в текущем порядке списка, внутри пресета — правила по порядку; первое совпадение
   выигрывает (та же семантика, что у `ResolveRoute` v1). Правило `{specialty: X, route: R}`:
   - `R = "tier:T"` → `Specialties[X].DefaultTier = T`, если пуст. Матрица не
     заполняется — разворачивание уровня проваливается в слоты владельца, что байт
     в байт совпадает с поведением v1 («работай T-моделью владельца»);
   - `R = конкретная модель M` → все три ячейки `Specialties[X].TierStrong|Medium|Weak = M`,
     если запись ещё не создана. В v1 маршрут-модель означал «эта специальность всегда
     ходит M, независимо ни от чего» — заполнение всей строки сохраняет это;
   - правило `{specialty: "any"}` → то же самое в `DefaultSpecialty` слоя.
   Эквивалентность резолва сохраняется: v1 обходил личные пресеты раньше глобальных,
   v2 читает запись owner-слоя раньше глобальной.
2. Пресеты v1 после разноски правил **удаляются**. Осознанная потеря: имена и
   контейнеры правил не переносятся — пресет v2 является другой сущностью (цепочка,
   а не сборник правил), автоконвертация правил разных специальностей в цепочку дала
   бы бессмыслицу. Эффективное поведение (какая специальность каким маршрутом идёт)
   сохраняется.
3. Известное расхождение после миграции, фиксируем явно: в v1 маршрут специальности
   смотрелся ТОЛЬКО когда у персоны не было ни `Model`, ни `ModelTier`; в v2 персона
   с `ModelTier = strong` при мигрированной строке «все ячейки = M» получит M (ячейка
   узкой матрицы), а не сильный слот владельца. Это следствие принятой семантики
   «уровень разворачивается по самой узкой матрице», а не дефект миграции.
4. Файл сохраняется с `version: 2`. Существующая защита от отката уже работает:
   код v1 при виде `version: 2` игнорирует файл с warning и стартует с дефолтов
   (`Load` в `SpecialtySettingsStore`), а не молча портит его.
5. **`BackupSchema.Version` инкрементируется (4 → 5)** — правило CLAUDE.md «ломающее
   изменение формата любого стора = инкремент версии бэкапа», иначе старый код после
   восстановления из свежего бэкапа молча обнулит стор.

Стор `personas.json` миграции не требует: поля матрицы персоны новые, пустые ячейки
меняют ровно ничего.

### 7. Что ломается в текущем поведении (явный список)

| Было (v1) | Становится (v2) |
|---|---|
| Пресеты применяются «все сразу»: `ResolveRoute` обходит все личные + глобальные | Пресет применяется только там, где на него явно ссылаются (`preset:{id}`) |
| `ResolveRoute(ownerId, specialty)` — обход правил пресетов, возвращает маршрут | Уходит; специальность читается как запись: `DefaultTier` (источник уровня) + матрица (разворачивание уровня) |
| Специальность — источник МАРШРУТА (шаг 3 старого ADR §1) | Специальность — источник УРОВНЯ (`DefaultTier`) и матрица его разворачивания |
| `Persona.ModelTier` = «работай N-моделью владельца» | = «работай своей N»: слот владельца — только если матрицы персоны и специальности пусты |
| Правило `any` внутри пресета | Понятие исчезает; мигрирует в запись `DefaultSpecialty` слоя |
| `ModelRouteRule`, `ModelRoutePreset.Rules` | Удаляются; пресет = `Steps[]` |
| `UserModelTierResolver.ModelFor(tier, ownerId)` — единственная форма | Плюс перегрузка с матрицами-данными; старая форма = пустой список матриц |
| Фолбэк всегда автоподбирает провайдера (уровень 2) | При цепочке — только её шаги; автоподбор лишь без цепочки |
| Значения мест — модель, слот, `local`/`claude`/`default` | Плюс `preset:{id}` во всех местах выбора модели; плюс ячейки матриц (модель или `preset:{id}`) |

UI раздела «Поставщики моделей» и карточки персоны/специальности меняются
соответствующе — продуктовые сценарии и тексты у Софьи, вне этого ADR.

### 8. Тест-гейт: настройка обязана быть связана с поведением

В этой фиче дважды настройка оказывалась декоративной (в первой реализации
`ResolveRoute` никто не вызывал; цепочки не существовало вовсе). Волна реализации
обязана включать тесты-сторожа, привязывающие настройку к поведению, — ревью без них
не проходит:

- **Резолв пресета:** в `LocalActionRoutingTests` (там сегодня живут тесты
  `ModelAssignmentResolver`) — место каталога / ячейка со значением `preset:{id}`
  даёт модель ПЕРВОГО шага цепочки (включая разворачивание `tier:*`-шага по
  владельцу); битая ссылка — резолв уходит на следующий приоритет.
- **Матрицы:** там же — при уровне T модель берётся из ячейки персоны; при пустой
  ячейке персоны — из ячейки специальности (owner-слой раньше глобального, запись
  специальности раньше `DefaultSpecialty`); при пустых матрицах — из слота владельца
  (эквивалентность старому пути). Плюс кейс `DefaultTier` специальности как источника
  уровня при пустых `TaskItem.ModelTier`/`Persona.ModelTier`.
- **Фолбэк:** в `FallbackLlmSessionAdapterTests` — ход с цепочкой при ошибке
  фолбэк-класса перезапускается на модели ВТОРОГО шага (а не на модели-эквиваленте
  автоподбора), и автоподбор не срабатывает после исчерпания цепочки; тир хода,
  переданный явно, побеждает реверс-эвристику `ResolveTier` (§5 п.1).
- **Миграция:** в `SpecialtySettingsStoreTests` — файл v1 с правилами (личными и
  глобальными, `tier:*`, конкретная модель, `any`) после загрузки даёт тот же
  эффективный резолв, что и до миграции (с оговоркой §6 п.3).

## Последствия

- Плюс: пресет становится тем, чем его видит владелец, — именованным планом
  переключения, применимым в любом месте выбора модели; порядок фолбэка при цепочке
  детерминирован и управляем человеком, а не эвристикой `EquivalentModel`.
- Плюс: «сильная/средняя/слабая» получает три уровня узости (персона → специальность →
  владелец) при одном принципе «уровень — строка, сущность — матрица»; смысл уровня
  как меры сложности работы не размывается.
- Плюс: разворачивание живёт в прежних точках (`ExpandChain` — цепочки,
  `UserModelTierResolver.ModelFor` — уровень в модель), вторая точка истины не
  появляется.
- Минус/риск: лексика маршрутов растёт (`tier:` + `preset:` + id + псевдо-значения) —
  каждому месту ввода нужна валидация ссылки; митигация — общий парсер в
  `LocalActionOverridesStore` и 400 на неизвестный id при сохранении настройки
  (битая ссылка возможна только после удаления пресета, и она fail-open вниз).
- Минус: миграция теряет имена пресетов v1 и (осознанно) сдвигает поведение персон
  с `ModelTier` поверх мигрированной строки-модели (§6 п.3). Принято; фича молодая,
  реальных накопленных пресетов минимум.
- Риск: петля «слот → пресет → tier → слот»; закрыта набором посещённых ссылок при
  развороте (fail-closed: повтор = шаг отбрасывается) плюс запретами вложенности
  пресетов и `tier:*` в ячейках.
- Вне охвата: UI и продуктовые тексты (Софья), пометка подмены в ленте (существующий
  механизм используется как есть), правила доступа специальностей
  (`SpecialtyTemplateSettings.Access/Tools` не трогаются).
