# Инциденты: форма запросов к SigNoz и состав досье

Как раздел «Инциденты» достаёт данные из SigNoz, что именно попадает в досье (и, значит,
в промпт кнопки «Объяснить») и где у этой связки известные дыры.

Код: [Telemetry/Incidents/](../../backend/ClaudeHomeServer/Telemetry/Incidents/) —
`IncidentQueries` (тела запросов и разбор), `SignozQueryClient` (сеть),
`IncidentDossierService` (сборка), `IncidentDossierText` (единственное текстовое
представление досье). Схема самих запросов v5 и грабли дашбордов — в
[dashboards.md](dashboards.md).

## Источник данных: query API, не ClickHouse

Всё читается через **`POST {SignozUrl}/api/v5/query_range`** и `GET /api/v1/alerts`.
Прямой SQL к ClickHouse не используется сознательно: порты 8123/9000 наружу из overlay
не проброшены, а пробрасывать их — заводить креды и расширять поверхность ради данных,
которые query API отдаёт как есть.

`SignozUrl` обязан включать base-path (`http://localhost:3301/telemetry-proxy`): с v0.134
SigNoz поднимает весь HTTP-сервер под ним, и без префикса живы только health-пробы.

## Три запроса досье

Все три — одна форма: `schemaVersion: "v1"`, окно в миллисекундах, `requestType` и
`compositeQuery.queries[].spec`. Фильтр задаётся строкой-выражением (`filter.expression`),
разрезы — массивом `groupBy`. Ответы лежат в `data.data.results[]`.

| Что | requestType | signal | Фильтр |
|---|---|---|---|
| Разрез по тегу | `time_series` | `metrics` | `deployment.environment = '<контур>'` |
| Упавшие ходы | `raw` | `traces` | `name = 'chat.turn' AND outcome = 'error' AND …` |
| Логи окна | `raw` | `logs` | `(severity_text = 'Warning' OR severity_text = 'Error') AND …` |

Метрика и тег разреза выбираются по имени правила (`alertname`): «Всплеск ошибок LLM» →
`ccs.llm.errors` / `error_type`, «Отказы MCP-инструментов» → `ccs.mcp.errors` /
`tool_name`, и так далее (`IncidentDossierService.BreakdownByRule`). Незнакомое правило
разрезается ошибками LLM — самый частый класс инцидентов.

Тела собираются `Utf8JsonWriter`, а не склейкой строк. Причина конкретная: самодельное
экранирование значения фильтра превращало апостроф в `\'` — escape, которого в JSON нет.
SigNoz отвечал 400, а разрез молча оказывался пустым. Сторож — `IncidentQueriesTests`
(тела гоняются с апострофом, кавычкой, слешем и кириллицей).

Окно разбора — `Telemetry:Incidents:WindowMinutes` (по умолчанию 60 минут до срабатывания);
у горящего инцидента правый край всегда «сейчас».

## Что попадает в досье (и в промпт «Объяснить»)

Досье собирает **детерминированный код без участия модели**. Модель зовётся только по
кнопке «Объяснить» (место каталога `incident-explain`) и получает готовый текст —
ровно тот, что виден в карточке и уходит в описание задачи.

| Раздел досье | Источник | Что именно |
|---|---|---|
| Заголовок, важность, контур, время | SigNoz alerts API | имя правила, `severity`, `deployment.environment`, `startsAt` |
| Разрез | метрики | значение тега и число срабатываний |
| Упавшие ходы | трейсы | время, `provider`, `model`, `error_type`, длительность, `chat_id` |
| Затронутые чаты | локальные сторы | имя чата и проект (`SessionManager`), сумма токенов за окно (`SpendStore`), имена отвалившихся инструментов (`McpCallLog`) |
| Логи | логи | время, уровень, текст сообщения (до 400 символов) |

**Чего в досье нет:** реплик чатов, промптов, имён персон и пользователей, путей на диске.
Это важно понимать вместе со следующим: досье склеивает обратно данные, которые
`PiiRules` намеренно разводил по разным местам, а «Объяснить» отправляет его в маршрут,
который админ может увести на стороннего провайдера (GLM, DeepSeek). Изменение состава
таблицы выше — изменение того, что уезжает наружу.

## Связка «инцидент → чат»

Держится на теге **`chat_id`** (стабильный id чата CCS) в спанах `chat.turn` и
`process.start`. Тег `session_id` для этого не годится: там csid claude CLI, которого нет
на первом ходу и который перезаписывается на каждом `system/init`.

`chat_id` внесён в KEEP `PiiRules`. Правила работают по default-deny, поэтому при удалении
строки тег выбрасывался бы **молча** — ни ошибки, ни лога, просто разбор перестал бы
находить чаты. Сторож — `PiiSanitizerTests.ChatId_IsKept`: он падает, если строку убрать.

## Известные ограничения

- **Логи связаны с ходом только по времени.** У логов пустой `trace_id` — корреляцию
  логов со спанами мы не включали, а KEEP под неё не расширяли. Поэтому в досье попадают
  все Warning/Error за окно инцидента, а не только относящиеся к упавшим ходам.
- **Чужой контур.** Боевой SigNoz видит оба инстанса, поэтому инцидент может прийти с
  `deployment.environment`, отличным от нашего. Локальных чатов по нему нет и быть не
  может — карточка показывает плашку «другой контур», а не пустой список.
- **История погасших инцидентов — 50 записей** (`AlertStateStore.MaxHistory`, файл
  `data/alert-state.json`). Диплинк на инцидент старше этого даёт 404 — карточка говорит
  «ссылка устарела», а не «сетевой сбой».
- **Ретро-миграции тега не было.** До появления `chat_id` связка не работала; retention
  трейсов 30 дней, история выровнялась сама.
