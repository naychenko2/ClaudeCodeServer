## 1. Топология

```
                        Браузер (PWA-оболочка ядра)
                         │  cc_token (HMAC JWT ядра)
                         ▼
  ┌───────────────────────────────────────────────────────────┐
  │  ЯДРО AI Home — единственная публичная точка входа          │
  │  [SPA]  [/api/* ядра]  [Module Gateway (YARP)]              │
  │   MF-loader ──────────────┐        │ /api/modules/{id}/**   │
  │   MCP node-прокси ────────┤        │ + инъекция identity    │
  └───────────────────────────┴────────┼───────────────────────┘
                                        ▼ (модуль виден ТОЛЬКО ядру)
                        ┌───────────────────────────────┐
                        │  СЕРВИС МОДУЛЯ (отдельный      │
                        │  процесс, своя БД, свой деплой)│
                        └───────────────────────────────┘
```

Весь трафик к модулю — через gateway ядра (`/api/modules/{id}/**`): и браузер, и MCP. Сервис модуля наружу не публикуется. Подключение модуля = запись в реестре + перезапуск ядра (hot-plug вне scope v1).

## 2. Манифест модуля `module.json`

Читается ядром на старте из каталога `modules/` или списка в конфиге.

```jsonc
{
  "schemaVersion": "1.0",           // мажор.минор контракта
  "id": "family-budget",            // slug: сквозной ключ (маршрут, MF-remote, MCP)
  "version": "0.1.0",               // semver модуля; бьётся в ?v= remoteEntry
  "displayName": "Бюджет",
  "description": "Семейный бюджет",
  "backend": {
    "baseUrl": "http://127.0.0.1:5100",  // внутренний адрес сервиса
    "healthPath": "/health",
    "routePrefix": "/api/modules/family-budget"
  },
  "frontend": {                     // опционально
    "remoteEntry": "/api/modules/family-budget/ui/remoteEntry.js",
    "exposedModule": "./Tab",
    "tab": { "label": "Бюджет", "icon": "wallet", "order": 45 }
  },
  "mcp": [                          // опционально
    { "key": "budget", "command": "node", "args": ["mcp/budget-server/index.js"] }
  ],
  "llm": {                          // опционально, §10 (с v1.2)
    "actions": [
      { "key": "categorize-operation", "title": "Категоризация операций бюджета",
        "profile": "text", "defaultLocal": true }
    ]
  },
  "scopes": ["budget.read", "budget.write"],  // возможности модуля, НЕ per-user права
  "auth": { "audience": "aihome-module:family-budget" }
}
```

Обязательные: `schemaVersion, id, version, displayName, backend.*`. Поле `auth.identity` в v1 отсутствует — JWKS-валидация мандатна.

## 3. Backend-интеграция (gateway)

Ядро генерирует из реестра на модуль: маршрут `module-{id}` (`Match.Path = {routePrefix}/{**}`, `Transform PathRemovePrefix`) + кластер на `baseUrl` с active health-check на `healthPath` (образец в ядре — маршрут forgejo). Провайдер YARP — **добавочный** к существующему `LoadFromConfig`, не замена.

Требования к сервису модуля: `200 OK` на `GET {healthPath}` без аутентификации (это про **прямой** вызов на `baseUrl` — именно так ходит active health-check YARP; через gateway health закрыт аутентификацией, см. CT-1 v1.6); работа только под своим `routePrefix`; identity — исключительно из модульного токена (§5); внутренняя доменная авторизация (например, членство семьи) — ответственность модуля.

### 3.1 Лимиты data-plane (per-route для `module-*`)

| Параметр | Значение | Примечание |
|---|---|---|
| Max request body | **100 МБ** → иначе `413` | фото чеков 5–15 МБ, PDF/Excel-выписки, запас ×3 |
| Proxy activity timeout | **300 с** (бездействия, не суммарный) | чтение байтов сбрасывает счётчик |
| Streaming/SSE | обязателен, gateway не буферизует ответы | модуль шлёт keep-alive `: ping` ≤30 с |
| Response body | без лимита (стриминг) | |
| WebSocket | вне scope v1 | |

Рекомендация модулям: операции >60 с оформлять асинхронно (`202` + polling).

### 3.2 Ошибки gateway (зарезервированные формы)

- Модуль unhealthy/недоступен → `503` + `Retry-After: 15` + `{"error":"module_unavailable","moduleId":"...","retryAfterSeconds":15}`
- Таймаут → `504` + `{"error":"module_timeout","moduleId":"..."}`

Коды `module_unavailable|module_timeout` эмитит только gateway; модуль их использовать не вправе. UI-хост модуля рисует degraded-состояние по этим формам и по фейлу загрузки remoteEntry.

## 5. Аутентификация

Ядро — единственный эмитент identity. Раздача HMAC-секрета ядра модулям запрещена.

### 5.1 Модульный токен (RS256), схема заморожена в мажоре 1

Header: `alg=RS256` (константа), `typ=JWT`, `kid` (`^[a-z0-9-]{8,64}$`).

| Claim | Тип/формат | Значение |
|---|---|---|
| `iss` | константа | `"ClaudeHomeServer"` |
| `aud` | константа-шаблон | `"aihome-module:{moduleId}"`, точное сравнение |
| `sub` | строка ≤64, непрозрачная | userId (сейчас GUID lowercase); модуль НЕ парсит |
| `name` | UTF-8 ≤128 | отображаемое имя пользователя (для «кто внёс», AC-10) |
| `scope` | scopes через пробел (RFC 8693) | `^[a-z][a-z0-9._-]{1,63}$` каждый; подмножество манифеста |
| `chan` | enum | `"gateway"` \| `"mcp"` — канал выпуска |
| `iat`,`nbf`,`exp` | NumericDate | `nbf=iat`; clock skew при валидации 60 с |
| `jti` | GUID, опционален | ядро эмитит всегда; для логов |

Неизвестные claims модуль игнорирует (forward-compat). Добавление claim = минор schemaVersion; изменение существующего = мажор.

TTL по каналу: `chan=gateway` — **5 мин**; `chan=mcp` — **60 мин** (stdio-MCP не перевыпускает токен посреди хода). Режим отказа по контракту: агентский ход длиннее 60 мин получает `401` на инструментах модуля — корректное поведение, лечится новой сессией.

### 5.2 Gateway: два режима входа (v1.1 — CT-9)

На каждый запрос `/api/modules/**` gateway различает тип входного `Authorization`:

- **(а) Клиентский `cc_token`** (HMAC-схема ядра, браузерный data-plane) → gateway **срезает** его и вставляет свежий модульный токен `chan=gateway`. Браузер модульный токен никогда не держит.
- **(б) Уже-модульный токен** (валидная RS256-подпись ключом ядра + `aud` данного модуля + `chan=mcp`) → **passthrough**: gateway пропускает его насквозь без переобёртки. Это путь MCP-прокси (§6): stdio-процесс держит один токен весь ход и не может перевыпустить его посреди хода, поэтому TTL `chan=mcp` = 60 мин, а gateway не переминчивает.
- **Любой иной `Authorization`** → `401` на границе ядра, до модуля не доходит.

**Edge-инварианты применяются в обоих режимах**: безусловная срезка всех клиентских `X-AIHome-*` на входе, лимит тела §3.1, гейт видимости §8/FeatureFlag, формы ошибок §3.2.

Безопасность passthrough: форвардится только токен, подписанный приватным ключом самого ядра — браузер его подделать не может (ключа нет) и `chan=mcp`-токен никогда не получает (он живёт лишь в env серверного MCP-прокси). Это единственное контролируемое место, где инвариант «срезаем всё клиентское» ослабляется — и только для самоподписанного ядром модульного токена.

### 5.3 JWKS и ротация

- Ядро публикует JWKS: `/.well-known/aihome-modules/jwks.json`.
- Модуль кэширует JWKS 10 мин; неизвестный `kid` → немедленный рефреш (rate limit 1/30 с, иначе `401`).
- Ротация: **новый ключ публикуется в JWKS ДО первой подписи им**; старый остаётся в JWKS ≥24 ч после последней подписи (≫ max TTL 60 мин).
- JWKS недоступен: работа с кэша + grace 10 мин, затем `503` (fail-closed).

### 5.4 Авторизация в модуле

`aud` → `sub` (кто) → `scope` (что разрешено модулю) → собственная доменная проверка модуля (для бюджета — членство семьи: allowlist userId, `403` вне списка). «Валидный токен» ≠ «доступ». `scopes` — возможности модуля, не механизм per-user прав.

## 6. MCP-серверы модуля

Ядро на ходу сессии добавляет каждый `mcp[]` из манифеста в mcp-config **данными** (аддитивный цикл, существующие встроенные серверы не трогаются):

```
servers[mcp.key] = { command, args: [resolve(moduleDir, ...)],
  env: { MODULE_API_URL:  "{ядро}/api/modules/{id}",   // через gateway!
         MODULE_API_TOKEN: <модульный токен chan=mcp, TTL 60 мин>,
         MODULE_ID: "{id}" } }
```

MCP-прокси модуля ходит на gateway, не напрямую в сервис.

## 7. Frontend (Module Federation) — якоря фиксируются после спайка R5a

- Remote name = `manifest.id`; exposes `./Tab` → `React.ComponentType<AIHomeModuleContext>`.
- `remoteEntry` и все чанки — под `{routePrefix}/ui/**`: **публичная статика без аутентификации**, `Cache-Control: public, max-age=31536000, immutable`, версия через `?v={module.version}`. В `ui/` — только статика бандла, ни байта данных.
- Оболочка ядра: generic module-screen (`#/module/{id}`), вкладки из реестра (label/icon/order), `ModuleHost` монтирует remote и передаёт контекст:

```ts
interface AIHomeModuleContext {
  user: { id: string; name: string };
  apiBase: string;                  // "/api/modules/{id}"
  getToken: () => string | null;    // cc_token для Authorization на apiBase
  theme: { mode: 'light'|'dark' };  // + CSS-переменные ядра
  navigate: (hash: string) => void;
  onTitleChange?: (t: string) => void;
  schemaVersion: string;
  kitEntry?: string;                // v1.6: абсолютный URL remoteEntry дизайн-кита ({origin}/remoteEntry.js)
  kitVersion?: string;              // v1.6: DESIGN_KIT_VERSION — модуль сверяет мажор перед loadRemote
}
```

### 7.1 Platform Runtime (привязан к мажору schemaVersion)

```
schemaVersion 1.x ⇒
  react / react-dom : shared singleton, requiredVersion ^19.2.0
                     strictVersion — норматив для МОДУЛЯ-потребителя (он проверяет совместимость);
                     у ХОСТА singleton + eager (eager обязателен: иначе React уезжает в чанк с
                     top-level-await, и при «офлайн → reconnect → re-render» ловится React #300
                     на всём UI). Проверка версии срабатывает у потребителя shared-скоупа,
                     хост здесь — поставщик инстанса.
  MF-рантайм        : @module-federation/runtime мажор 2.x — ОДИНАКОВЫЙ у хоста и модуля
  JS target         : ES2022, native ESM
  Браузеры          : последние 2 мажора Chrome/Edge/Safari
  Тема              : только CSS-переменные ядра (lib/theme.css, data-theme)
```

Patch зависимостей — свободно у ядра; минор react = минор schemaVersion с анонсом; мажор react = мажор schemaVersion. Модуль не тащит собственный React.

**Про мажор MF-рантайма (уточнение v1.3, куплено блокером на живом стенде 2026-07-25).** Строку про рантайм пришлось выписать отдельно, потому что совпадения версии React недостаточно. Оболочка была собрана `@module-federation/vite` 1.19.1 (рантайм **2.8.0**), модуль — 1.4.1 (рантайм **0.8.x**). Хост публикует shared-скоуп в формате рантайма 2.x, remote читает его рантаймом 0.8, не находит там React хоста и молча подхватывает собственный фолбэк-бандл. Дальше компонент рендерит react-dom хоста, а хуки берёт из своего React, где диспетчер `null` — вкладка падает на первом же хуке с `Cannot read properties of null`. Симптом выглядит как ошибка модуля, хотя ни одна из сторон контракт формально не нарушала: про рантайм в нём не было ни слова.

Отсюда правило: **мажор `@module-federation/runtime` — такой же якорь мажора 1, как и версия React.** Ядро при смене мажора рантайма обязано анонсировать это мажором `schemaVersion`; модуль сверяет фактическую версию в своих `node_modules`, а не версию плагина-обёртки — номера плагина и рантайма не совпадают и меняются независимо.

Проверка на стороне модуля — одна команда, встроить в приёмку:

```
node -p "require('@module-federation/runtime/package.json').version"   # ожидается 2.x
```

**Про design-kit как shared (уточнение v1.4).** Совпадения React и рантайма федерации достаточно, чтобы модуль *монтировался*, но не чтобы он *выглядел как ядро*. У ядра есть дизайн-система: токены (`lib/design.ts` — `C`, `FONT`, `FS`, `R`, `SP`, `SHADOW`, `ISLAND`, `TB` и др.) и компоненты-примитивы (`components/ui/*` — `Island`, `IslandHeader`, `IslandScaffold`, `Modal`, `Button`, `IconButton`, `Field`, `Toggle`, `PillSwitch`, `EmptyState`, `CanvasBackdrop`). Без доступа к ним модуль вынужден дублировать и то и другое своими силами — а значит, неминуемо расходиться с ядром визуально при любом редизайне последнего.

Поэтому с v1.4 ядро **экспонирует design-kit через `exposes` в `vite.config.ts`** под фиксированным именем **`aihome_shell/design-kit`** (зафиксировано v1.5), а модули потребляют его через `loadRemote`. Тем самым design-kit становится таким же shared-якором мажора 1, как React и MF-рантайм: его мажор привязан к мажору `schemaVersion`, модуль не тащит собственных примитивов.

**Состояние на 2026-07-26 (v1.6, сдано ядром):** `DESIGN_KIT_VERSION` = **1.1.0**, 45 экспортов — токены (включая брейкпоинты) и примитивы `Island`/`IslandHeader`/`IslandScaffold`, `Modal`, `Button`, `IconButton`, `Field` (семейство), `Toggle`, `PillSwitch`, `SegmentedControl`, `EmptyState`, `CanvasBackdrop`, `Menu`/`MenuItem`, `BackButton`, `ModalActions`/`useIsMobileModal`, `ConfirmDialog`, `IslandSplitter`, `IslandSidebarSplitter`, `ICON_SIZE`/`ICON_STROKE`/`ICON_PROPS`. Expose-чанк 29,57 КБ, тянет три loadShare-обёртки (react, jsx-runtime, react-dom) — оболочку за собой не тащит. **`ToolbarOverflowMenu` в кит не вошёл** (единственный не-leaf: тянет `ToolbarIconButton` из `Toolbar.tsx`); модуль его не запрашивает — ⋯-меню собирается из `Menu`/`MenuItem` + `IconButton`.

Порядок подключения на стороне модуля (v1.6): `kitEntry` и `kitVersion` приходят в `AIHomeModuleContext`, `type: 'module'` обязателен — remoteEntry ядра нативный ESM и грузится через `import()`, без этого флага загрузка падает невнятной ошибкой:

```js
registerRemotes([{ name: 'aihome_shell', entry: ctx.kitEntry, type: 'module' }]);
const kit = await loadRemote('aihome_shell/design-kit');
```

**Типы кита** генерируются ядром в `dist/@mf-types/**` и раздаются статикой с того же origin, что и `remoteEntry.js`.

**T-1 (2026-07-26, РЕШЕНО обеими командами): типы на билд-машине.** Раздача типов по HTTP решает потребление в рантайме, но модуль компилируется отдельно и, как правило, тогда, когда ядро не запущено — значит на `tsc` их резолвить неоткуда. Вариант «скрипт-подкачка перед сборкой» отвергнут: он делает сборку модуля зависимой от живого чужого процесса, и первым же местом отказа будет CI, где ядро не поднято — фолбэк отработает молча, и сборка пойдёт против устаревшего снапшота под видом свежего. Тихо деградирующая автоматизация хуже её отсутствия.

**Принято: модуль вендорит снапшот типов кита в свой репозиторий** — при двух условиях, превращающих костыль в дисциплину:

1. Снапшот несёт версию кита **в себе** — в заголовке файла (`// design-kit types snapshot, DESIGN_KIT_VERSION 1.1.0`) либо в имени. «Против чего собрано» видно в диффе, а не выясняется в рантайме.
2. Модуль в рантайме сверяет `ctx.kitVersion` со своим снапшотом: **мажор** не совпал — не монтируемся (уже в контракте); **минор** разошёлся — предупреждение в консоль. Расхождение всплывает при первом запуске, а не на CT-16 через неделю.

Вместе с обязательством ядра поднимать `DESIGN_KIT_VERSION` на любое изменение состава (см. версионирование выше) этого достаточно: чтобы понять, надо ли обновлять снапшот, сравниваются две строки.

Форма на будущее, когда снапшоты начнут мешать: ядро при сборке кладёт `dist/@mf-types` + `package.json` в версионированный `aihome-design-kit-{version}.tgz`, модуль ставит его обычной зависимостью — резолв и сверку версии делает npm, живое ядро для сборки не нужно. Вводить не раньше, чем появится боль.

Границы expose:
- **Токены** отдаются целиком — это константы и строки-ссылки на CSS-переменные (например, `C.bgMain === 'var(--c-bg-main)'`), дёшево и без поведения.
- **Компоненты** — самодостаточный bundle: каждый примитив должен собираться без подтягивания внутренних зависимостей ядра (приложение, роутер, сторы). `Island` уже чистый лист — зависит только от `design.ts` и React; `Modal`/`IslandScaffold` команда ядра фактурит в чистый entry, при этом `IslandScaffold` получает self-contained режим (сам владеет сплиттером по пропу `storageKey`, ≈10 строк) — хук состояния наружу не экспозится (v1.5).
- **`lucide-react`** — **shared НЕ применяется** (v1.6, пересмотрено по замеру): lucide-react — tree-shakable набор чистых SVG-компонентов без общего состояния; MF-shared выключает tree-shaking у хоста и уводит весь пакет (~1004 КБ) в отдельный чанк ради экономы единиц КБ дублирующихся иконок — лечение дороже болезни в ~100×. Вместо shared — **якорь major-версии**: lucide-react major 1.x одинаковый у хоста и модуля, проверяется на приёмке той же однострочной командой, что и MF-рантайм (`node -p "require('lucide-react/package.json').version"`). Каждый (хост и модуль) тришейкает нужные ему иконки сам; кит реэкспортирует только `ICON_SIZE`/`ICON_STROKE`/`ICON_PROPS` (дизайн-система иконок = размер/толщина/линии, не сами SVG).
- **Глобальные CSS — обязательство оболочки, не expose** (v1.6, уточнено командой ядра). Классы и keyframes из `index.css` ядра (`cc-overlay`, `cc-modal-card`, `cc-sheet-card`, `cc-spin`, `cc-shimmer-text`, `cc-smoke`, скролл-хелперы `cc-scroll-x`/`cc-hide-scrollbar`/`cc-no-scrollbar` и одноимённые keyframes) уже находятся в DOM-контексте модуля, потому что их грузит оболочка — отдавать их через MF не требуется. Ядро объявляет их **публичной поверхностью кита**: переименование или удаление = мажор `schemaVersion`. Без этой гарантии `Modal`/`Button` рендерятся «голыми», а спиннер не вращается. `lib/theme.css` (`--c-*`, `--shadow-*`, `--canvas-*`) — то же обязательство. Исключение: `cc-iconbtn` живёт не в CSS-файле — его инжектирует сам `IconButton`, то есть он приезжает вместе с компонентом и отдельной гарантии не требует.
- Тема по-прежнему только через глобальные CSS-переменные.
- Поле `model`/выбор конкретной реализации модулю недоступен — как и в §10, модуль потребляет кит как есть; кастомизация только через props примитивов.

**Версионирование кита (уточнено v1.6 — прежняя формулировка была ловушкой).** До v1.6 здесь стояло «смена состава экспорта = мажор». По букве этого правила сданный кит `1.1.0`, где к `1.0.0` **добавились** `Menu`/`MenuItem`, `BackButton`, `ConfirmDialog`, `ModalActions`, сплиттеры, обязан был стать `2.0.0` — и модуль, сверяющий мажор, отказался бы монтироваться на совместимом ките. Правило приведено к обычной semver-логике:

- **мажор** design-кита = мажор `schemaVersion`; поднимается на **удалении или переименовании** экспорта, смене сигнатуры примитива — то есть на всём, что ломает существующего потребителя. При несовпадении мажора модуль отказывается монтироваться с понятной ошибкой;
- **минор** — на **добавлении** экспорта или расширении пропсов с сохранением совместимости;
- обязательство ядра (2026-07-26): `DESIGN_KIT_VERSION` поднимается на **любое** изменение состава экспортов, а не только на ломающее, и новая версия называется в письме при сдаче. Значит потребителю достаточно сравнить две строки, чтобы понять, надо ли обновлять снапшот типов (см. T-1 ниже).

## 8. Версионирование

`schemaVersion` = мажор.минор контракта. Несовместимый мажор → модуль не поднимается (лог + пропуск). Минор выше поддерживаемого → работа на общих полях + предупреждение. Якоря мажора 1: путь `/api/modules/{id}`, JWT-схема §5.1, JWKS-URL и aud-схема, MF-expose `./Tab`, форма `AIHomeModuleContext`, Platform Runtime §7.1.

### 8.1 Правило совместной правки: раздел и его чеклист — один коммит (v1.6)

**Правка раздела и правка проверяющих его CT из §9 идут одним коммитом.** Это не стилистика, а вывод из двух живых инцидентов 2026-07-26 — оба класса «документ противоречит сам себе», оба нашлись до приёмки только случайно:

- §10.4 развели `module_hidden` и `action_not_declared`, а CT-14 в §9 остался требовать `404` на необъявленное действие. Обе команды реализовали корректно — и получили бы красный тест с поиском несуществующего дефекта;
- §7.1 требовал «смена состава экспорта = мажор», по чему сданный кит `1.1.0` (добавлены `Menu`, `BackButton`, `ConfirmDialog`, …) обязан был выйти как `2.0.0` — и модуль, сверяющий мажор, отказался бы монтироваться на полностью совместимом ките.

Оба раза причина одна: раздел и его чеклист правились порознь и разъехались. Отсюда правило и его следствие: **меняя требование — сразу проверь, какой CT его проверяет, и правь их вместе; заводя новый CT — сошлись в нём на раздел, который он проверяет.** Если правка требования не затрагивает ни одного CT, это повод спросить, чем требование вообще проверяется.

Предложено командой ядра, принято командой модуля.

## 9. Conformance: эталонный модуль `module-echo`

Делает **команда модуля** (владелец контракта владеет исполняемой формулировкой). Состав: backend (`GET /health`; `GET /echo/whoami` → `{sub,name,scope,chan}` из провалидированного токена; `POST /echo/upload` → принятый размер; `GET /echo/stream` → SSE 1 соб/с, 60 с; с v1.2 — `POST /echo/llm` → обменивает свой токен на `chan=host` и зовёт §10.3 с действием `echo-echo`, возвращая ответ модели как есть); frontend (`remoteEntry` c `./Tab`: рендерит `user.name` и результат `whoami`); MCP-сервер с tool `echo_whoami`. Манифест echo с v1.2 объявляет `llm.actions: [{ key: "echo-echo", title: "Эхо через модель", profile: "small", defaultLocal: true }]`.

Чеклист (версионируется с контрактом):

## 10. LLM-канал модуля (v1.2)

Модуль **не держит своих ключей к LLM-провайдерам**. Языковые модели — ресурс ядра: у него адаптеры провайдеров, локальная модель, подписки и, главное, настройка «какая модель обслуживает какой тип задачи», сделанная владельцем системы в одном месте. Модуль приносит задачу, ядро решает, чем её считать.

Из этого следует инвариант, определяющий весь раздел: **модуль называет ключ действия, а не модель**. Выбор модели, провайдера и фолбэков — всегда за ядром. Модуль, который может попросить конкретную модель, обходит и настройки владельца, и учёт расхода, поэтому такой возможности в контракте нет.

### 10.1 Объявление LLM-действий в манифесте

```jsonc
"llm": {
  "actions": [
    { "key": "categorize-operation",              // ^[a-z][a-z0-9-]{1,63}$, уникален в модуле
      "title": "Категоризация операций бюджета",  // то, что видит владелец в настройках
      "profile": "small" | "text" | "large",      // профиль нагрузки ядра (контекст/лимит/таймаут)
      "defaultLocal": true }                      // дефолт маршрута до настройки владельцем
  ]
}
```

Ядро регистрирует эти действия в своём каталоге типов фоновых задач наравне со встроенными, под неймспейсом `module:{moduleId}:{key}`, группой — `displayName` модуля. Владелец настраивает им модель тем же механизмом и в том же месте, что и встроенным задачам; смена маршрута действует без перезапуска.

Неймспейс — не косметика, а граница безопасности: модуль не может ни объявить, ни вызвать действие вне `module:{своего id}:*`, поэтому перехватить маршрутизацию встроенных задач ядра он не в состоянии.

Модуль без блока `llm` каналом не пользуется — вызовы от него отклоняются.

### 10.2 Host-токен (`chan=host`)

Модульные токены §5.1 живут коротко и привязаны к обработке входящего запроса. Категоризация же догоняет импорт уже после ответа пользователю: выписка на несколько сотен операций не укладывается ни в 5 минут `chan=gateway`, ни в activity timeout §3.1 — по контракту такие операции и так оформляются асинхронно (`202` + polling). Значит модулю нужен собственный, более долгий канал в ядро.

```
POST {AIHOME_CORE_BASEURL}/api/host/token
Authorization: Bearer <модульный токен chan=gateway | chan=mcp>
→ 200 { "token": "<RS256, chan=host>", "expiresIn": 3600 }
```

- Выпускается на тот же `sub` и тот же `aud`, что и предъявленный токен: **расход всегда атрибутирован пользователю**, от имени которого модуль работает. Анонимных фоновых вызовов канал не предусматривает.
- TTL 60 мин, схема claims — §5.1, `chan="host"` (добавление значения enum — минор, §5.1 допускает).
- `chan=host` принимается **только** на `/api/host/**`. На `/api/modules/**` он даёт `401`: иначе модуль мог бы час ходить сам в себя от имени пользователя в обход §5.2.
- **`/api/host/**` выведен из HMAC-схемы ядра** (`AddAuthentication(JwtBearer)` у ядра покрывает `/api/*`): host-канал разводится отдельной схемой валидации RS256-модульного токена. Зафиксировано явно, чтобы при уборке в `Program.cs` кто-то случайно не накрыл `/api/host/**` HMAC и не сломал канал.
- **Rate-limit на выпуск host-токена** на пару `(moduleId, sub)`: иначе модуль в `401`-петле дёргает выпуск в цикле, тратя RSA-подпись. Превышение → `429` + `Retry-After`.
- **Гейт видимости `module-{id}` срабатывает уже на `POST /api/host/token`**, а не только на `/complete`: скрытый флагом модуль не получает host-токен вовсе. Коды различаются по каналу (см. §10.4).
- Модуль кэширует токен и обновляет по истечении или первому `401`.

**Почему обмен токена, а не инъекция `chan=host` в заголовок при проксировании.** Не ради экономии RSA-подписи (то побочный эффект), а по структуре: категоризация догоняет импорт уже после ответа пользователю (`202` + polling), и проксируемого запроса в этот момент нет — вставлять заголовок физически некуда. Долгий токен, который модуль держит сам — единственная схема, покрывающая фоновый сценарий.

### 10.3 Вызов модели

```
POST {AIHOME_CORE_BASEURL}/api/host/llm/complete
Authorization: Bearer <chan=host>

{ "action": "categorize-operation",   // ключ БЕЗ неймспейса — ядро достраивает его из aud
  "prompt": "…",
  "responseFormat": "json" | { …JSON-схема… },   // опционально
  "timeoutMs": 30000 }                           // опционально, не выше потолка профиля

→ 200 { "text": "…", "model": "qwen3:4b", "route": "local",
        "usage": { "inputTokens": …, "outputTokens": …, "costUsd": … } | null }
```

`responseFormat` — просьба, а не гарантия: часть маршрутов умеет структурированный вывод, часть нет. Модуль обязан переживать ответ, не соответствующий схеме, — как переживает и полное отсутствие LLM.

`usage` может быть `null` (не все маршруты его отдают). Поле `model`/`route` — справочные, для логов модуля; принимать по ним решения модуль не должен.

### 10.4 Ошибки

| Код | Когда |
|---|---|
| `400` | нет `action` или `prompt`; `responseFormat` невалиден |
| `401` | токен не `chan=host`, протух, чужой `aud`, битая подпись |
| `403` | `{"error":"module_hidden"}` — на host-канале (`/api/host/**`): модуль скрыт флагом `module-{id}` у этого `sub`. **На gateway-пути** (`/api/modules/**` по `cc_token`) скрытый модуль отдаёт `404 module_not_found` (как в §5.2/ModulesController) — намеренно, чтобы не раскрывать существование модуля браузеру; модуль же про себя знает, ему корректнее `403`. |
| `403` | `{"error":"action_not_declared"}` — ключа нет в `llm.actions[]` **вызывающего** модуля. Сюда же попадает попытка назвать ключ чужого модуля — и это правильный ответ: для модуля чужих действий не существует, неймспейс не пробивается по построению. Разведено с `module_hidden` (v1.6): «меня скрыли у пользователя» и «я не объявил действие» — разные починки. |
| `404` | `{"error":"action_unknown"}` — ключ **есть** в манифесте вызывающего, но отсутствует в каталоге ядра: действие отбраковано валидацией манифеста либо реестр не прогрет. **Это не ошибка модуля, а рассинхрон ядра** — чинится не на стороне модуля, потому и отделено от `403`. |
| `413` | промпт больше лимита §10.5 |
| `429` | превышена конкурентность модуля, + `Retry-After` |
| `503` | `{"error":"llm_unavailable"}` — все шаги маршрута провалились |
| `504` | `{"error":"llm_timeout"}` — вышло время профиля/запроса |

Модуль обязан работать при `503` — деградируя, а не падая: для бюджета это значит «операция уходит в требующие подтверждения», а не «импорт сломался».

### 10.5 Лимиты, учёт, приватность

| Параметр | Значение |
|---|---|
| Размер промпта | ≤ 256 КБ → иначе `413` |
| Одновременных вызовов на модуль | ≤ 4 → сверх лимита `429` |
| Таймаут | потолок профиля действия; `timeoutMs` может только уменьшить |

- **Учёт ведётся всегда, метрики расхода — best-effort.** Ядро обязательно пишет факт вызова + маршрут + `(moduleId, action, sub)` на каждый запрос — без этого модуль, гоняющий сотни операций через категоризацию, жжёт квоту невидимо (а сегодня фоновые one-shot в общий учёт не попадают вовсе). Расходные метрики (токены, `costUsd`) пишутся там, где их отдаёт провайдер: на claude-пути они есть, на локальной модели и прямом адаптере агрегатора — нет и быть не может. `costUsd` на локальной модели не ожидается.
- **Тело промпта не пишется в общие логи ядра.** Модуль, со своей стороны, обязан маскировать персональные данные до отправки (для бюджета — ФИО контрагентов); смена транспорта с прямого вызова провайдера на канал ядра этого требования не отменяет.

### 10.6 Вне объёма v1.2

- **Изображения (vision).** Механизм фоновых задач ядра работает только с текстом; мультимодальный путь существует лишь внутри агентной сессии. Распознавание фото чеков этим каналом не покрывается и планируется отдельно — добавление поля вложений в §10.3 будет минором.
- **Стриминг ответа**, многоходовые диалоги, разделение system/user.
- **Выбор модели модулем** — не отложен, а сознательно исключён (см. инвариант в начале раздела).
